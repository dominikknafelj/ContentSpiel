# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

ContentSpiel is a Rails 8.1 CMS: a page-tree-driven public website plus CS Studio, its own admin. Content editors build pages out of ordered content blocks (rich text, images, post listings), organize them in a tree, and the same tree drives navigation, routing, and the sitemap. Rich text is Tiptap/ProseMirror JSON. Everything is translated via Mobility into the languages switched on in Settings (three by default, en/de/es, out of the 38 in `config/supported_locales.rb`).

## Setup & Commands

```sh
docker compose up -d          # Postgres 17, published on host port 5433 -- start this first
bin/setup --skip-server       # installs gems, prepares dev + test databases
bin/rails db:seed             # the built-in groups (every environment), and in development an admin account and demo content (see db/seeds.rb)
bin/rails server               # or `bin/dev`, which runs server + `tailwindcss:watch` (see Procfile.dev)
```

- App: http://localhost:3000
- Sign in: http://localhost:3000/cs-studio/sign-in (`<ADMIN_PATH>/sign-in`)
- Admin (CS Studio, behind the same sign-in): http://localhost:3000/cs-studio (`ContentSpiel::ADMIN_PATH`, configurable via `ADMIN_PATH`)

**Tests:** `bin/rails test` (full suite, minitest). Single file: `bin/rails test test/models/page_test.rb`. Single test: `bin/rails test test/models/page_test.rb -n test_method_name` or `bin/rails test test/models/page_test.rb:42`. System tests: `bin/rails tailwindcss:build`, then `PARALLEL_WORKERS=6 bin/rails test:system` (the whole browser suite, whatever file is named after it: one file is `bin/rails test test/system/admin/tree_test.rb`), on a quiet machine (check `sysctl -n vm.loadavg`: a load near the core count is not quiet). On macOS prefix every test command with `PGGSSENCMODE=disable`: a parallel run can otherwise hang forever. A new worktree runs `bin/rails db:test:prepare` once. Never run a build while tests run, and a running `bin/dev`'s `theme_css:watch` counts as one. `VERBOSE=1` prints what tests print, `COVERAGE=1` writes `coverage/index.html`. CI runs the browser suite for every pull request and a merge to `main` is not tested again.

Before writing a test, or to read what CI runs, read `docs/reference/writing-tests.md`, and `test/system/README.md` before a browser test.

**A theme:** `THEME_PATH=<folder> bin/dev` draws the site with a theme folder; `bin/rails 'theme:new[PATH]'` writes a copy of the default theme to start from, `bin/rails theme:check` says what is wrong with a folder, and `bin/theme-build-check` builds the stylesheet under the second theme and starts production under it (it writes `app/assets/builds`, so it is run alone). The test environment ignores `THEME_PATH`: a test is drawn by the second theme with `with_plain_theme { … }`, or by a changed copy of it with `with_theme_copy` (`docs/reference/theming.md`, "In tests").

**Lint/scan** (all run in CI, see `.github/workflows/ci.yml`):
```sh
bin/rubocop            # style (rubocop-rails-omakase, config in .rubocop.yml)
bin/brakeman            # static security analysis
bin/bundler-audit       # known CVEs in gems
bin/importmap audit     # known CVEs in JS deps (import maps, no npm/node_modules)
```

`config/brakeman.ignore` lists the warnings Brakeman is told to skip: none today (the four "SQL Injection" ignores on constant-built SQL went when `Media::Search` and `Translations::StateIndex` stopped building SQL text). A new entry needs its `note` saying why the warning is false; `bin/brakeman` must exit 0 either way.

**DB:** `bin/rails db:prepare` / `db:migrate` / `db:test:prepare`. Schema lives in `db/schema.rb` (Postgres, jsonb-heavy) -- no `db/structure.sql`.

**Deploy:** Kamal (`.kamal/`), containerized via `Dockerfile`. Not typically invoked from Claude Code sessions. What production asks of its host is eight variables (`docs/reference/hosting.md`): `PUBLIC_HOST`, the site's address with its scheme, from which the hosts that are answered, forced HTTPS and the address in mailed links all follow (`HostSettings.apply`; `config/environments/production.rb` sets none of them itself, and `config/deploy.yml` holds `PUBLIC_HOST` only as a commented line to fill in); `ASSUME_SSL=1` for a proxy that sends no `X-Forwarded-Proto`; `THEME_PATH`, the site's theme folder, under which production does not start when the folder is refused or the stylesheet was built for another theme (`docs/reference/theming.md`); `SECRET_KEY_BASE`, without which (and without a secret in the credentials) production stops at boot with a message of its own; `SETUP_TOKEN`; and the three of telemetry below. Outgoing mail takes seven more, all optional (`MAIL_SMTP_SERVER`, `MAIL_SMTP_PORT`, `MAIL_SMTP_SECURITY`, `MAIL_SMTP_USERNAME`, `MAIL_SMTP_PASSWORD`, `MAIL_SENDER_NAME`, `MAIL_SENDER_ADDRESS`), each overriding its field of Settings → Mail (`docs/reference/mail.md`). A production boot prints which address it serves, and that the host match is exact, as `[ContentSpiel]` lines at info. A site's forms take answers only with the Active Record encryption keys (without them every form says it can't take answers), and behind a CDN the CDN's ranges go in `config.action_dispatch.trusted_proxies`, or the forms' rate limit counts every visitor as one (`docs/reference/hosting.md`, "Forms").

**Telemetry** prints nothing unless asked, in development too: `OTEL_CONSOLE=1 bin/dev` (exactly `1`) prints spans to the terminal, `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` sends them, and with none of the three the SDK is not configured at all (`Telemetry.exporter_kind`); the test environment records in memory. Whatever is configured records a request's or a job's trace and nothing of the background's polling (`Telemetry::WorkSampler`).

### Rules a change can break silently

A rule a test holds is in the reference file for its area, under this same heading, with the test that names it; a failing guard's message is where it is learned. Here is what no test holds: the rules with no guard, whole, then, file by file, the part with no guard of a rule that stands whole in that file.

- A record outside the viewer's scope is not found, not forbidden: look it up through `AccessControl.scope` and answer 404, and use `AccessControl.holds?` for navigation only, never to gate a write.
- A permission or content type removed from its registry is dormant, not gone: a grant naming it matches nothing but is carried through every save until someone presses Remove, and a group is judged on its grants as stored (`LiveGrants#as_stored`).
- The owner flag changes only through `PATCH users/:id/owner`; the ordinary user form does not permit `owner`.
- `Audit.record` is the one write path of the append-only audit log, and no secret reaches a snapshot, a log line or a page: a password digest, a token's `lookup_digest`, an API key (`Audit::Snapshot::NEVER_STORED`, `filter_parameters`).
- A token or API key is never rendered, logged or audited after it is created.
- `Settings::Save` and `Locales::Enable`/`Disable`/`MakeDefault`/`Configure` lock the settings row first (`site.lock!`) and decide from the locked row.
- Every autosave, block reorder, block form and tree move of a CS Studio screen is sent through `app/javascript/saving/queue.js`, never from a hand-built request beside it, and an autosave carries its base (`base_updated_at`: the record's `updated_at`, and for the page settings form the page's `settings_changed_at`) so a stale one is refused with a 409 and nothing is written.
- Content screens autosave (on a published or scheduled record a save writes the rows and is not a publication: the line reads "SAVED · NOT PUBLISHED"); configuration screens (Settings, Groups, Users, Your account) save explicitly through `Admin::Ui::SaveBarComponent`.
- Choosing a library image for a hero or an image block goes through `Media::Choosing`, and the database's own foreign key is what keeps an image in use from being deleted.
- Editing an already-published record needs `publish`, not just `edit`, because the person who may change it is the person who may publish it (drafts spec D5; a save is not a publication, so the reason is not that typing goes live); a save that changes only the publish state needs only `publish` (`Posts::Save` / `Pages::Save#publish_only?`).
- `Pages::Save` and `Posts::Save` take only the keys in their `ATTRIBUTES` lists; moving and trashing belong to `Pages::Move` and `Trash::Move`. Under a language, those two and `ContentBlocks::Save` refuse by name, writing and auditing nothing, a key they would drop (`ApplicationService#unknown_language_keys_refusal`; `test/services/posts/save_test.rb`, `test/services/pages/save_test.rb`, `test/services/content_blocks/save_test.rb`).
- A password changes only through `Users::UpdatePassword` or `Users::Save`, never `update!` on the model: they end the user's sessions and audit the change.
- Rich text is written through `#assign_body`, never the raw Mobility accessor.
- The foreign keys to library images stay NO ACTION, never `on_delete: :restrict`: Postgres 18 reports SQLSTATE 23001, which Rails doesn't map to `ActiveRecord::InvalidForeignKey`, so every rescue would miss it (`MediaForeignKeysNoAction`).
- `FormsMailer` keeps a form's mail out of the log through Action Mailer's private class hook `set_payload_for_mail`; a Rails upgrade means re-reading that hook (`test/mailers/forms_mailer_test.rb`: "a form's mail is in no log line, at debug either" fails on a rename, not on a change of what the hook is handed).
- `turbo-rails` is pinned in the `Gemfile`; an upgrade means re-reading `app/javascript/saving/` and the header of `app/javascript/controllers/admin/saving/save_bar_controller.js` against the new Turbo source.
- A block changes container in three places and no other: `ContentBlocks::Reorder` (with `moved_from`), which is the only one a person asks for by name and in the editor is sent only by `admin--editor--blocks#move` (the drop, the menu and the keyboard all call it) inside `app/javascript/saving/queue.js`, the send itself being `app/javascript/editor/move_queue.js` (`test/lib/editing_tab_header_test.rb` holds only that its send carries the tab header); `ContentBlocks::Destroy#lift` (a column to the top level, "Remove section, keep blocks"); and `ContentBlocks::Save#fold_removed_columns` (a column to the last column left, when a section's layout is narrowed). `ContentBlocks::Save` reads `section_id` and `section_column` from its caller for a new block only.
- Code asks `capability?(:container)` (`ContentBlock#container?`) and the definition's `columns` (`#column_count`), never `block_type == "section"`.
- `admin--editor--section-choice` alone moves a section's settings region into the rail and puts it back. **No guard** for a second script that moves it (that it is one element moved, never a copy, is held by browser tests: `docs/reference/save-rule-and-write-queue.md`, "A form moved in the document stays one form").
- An audit event's old-to-new values are `field_changes`, never `changes` (`ActiveRecord::Dirty` owns that name), and the log is append-only in Postgres too: the trigger `db/triggers/audit_events_append_only.sql` is reapplied after every schema load.

### Pitfalls

Each of these ends a description in `docs/reference/` and is repeated here because the mistake it names is easy to make.

- **Public URLs** (`docs/reference/page-tree-and-routing.md`; the comments in `page.rb`, `public_site/paths.rb` and `tree_ranking.rb` hold the two-pages-one-URL and nil-position footguns):
  Read the extensive comments in `page.rb`, `public_site/paths.rb` and `tree_ranking.rb` before changing any of this -- the two-pages-one-URL and nil-position footguns they guard against are non-obvious and previously shipped as bugs (see commit `da80c58`).
- **Public routing** (same file; `config/routes.rb` carries the history of the 500-vs-404 regression):
  Read the routes.rb comments before touching `format: false` or the locale constraint; there's a documented history of a 500-vs-404 regression here.
- **The write queue** (`docs/reference/save-rule-and-write-queue.md`; every write of an autosave screen is serialised on this assumption):
  The queue assumes Turbo's morphing page refresh stays off.
  Notes, presence and an open editor (`docs/reference/live-editing.md`: plain GETs merged by `editing/merge.js`, and notes' by `notes/merge.js`, both on the one merge core `live/keep_merge.js`) are refreshed part by part for the same reason (`docs/reference/notes.md`, "Live delivery"): no `turbo_refreshes_with`, no `broadcast_refresh`, no `<meta name="turbo-refresh-method">`. All three are refused by `test/lib/notes_guards_test.rb` ("nothing in the app turns on Turbo's page refresh or morphing, or broadcasts one"), and any broadcast but `Live::Signals`' by `test/models/notes/signals_test.rb`.
- **Import-map pins** (`docs/reference/rich-text.md`; the option to re-add after re-pinning is `preload: "admin"`, which keeps the editor off public pages):
  Re-pinning Tiptap (`bin/importmap pin @tiptap/core @tiptap/starter-kit @tiptap/extension-link ...`) writes the new pins without that option — re-add `preload: "admin"` afterwards (the table pins, `@tiptap/extension-table`, `@tiptap/pm/tables` and `prosemirror-tables`, are pinned with it and carry it too; pinning them raised `prosemirror-view` and `prosemirror-transform` by a patch release, which stays) (`test/integration/public_javascript_test.rb` catches a miss).
- **AI requests** (`docs/reference/translations.md`; the three that must agree are the provider's 25 s timeout, `AI::Translate::MAX_FIELDS` / `MAX_CHARACTERS`, and `proxy.response_timeout: 75` in `config/deploy.yml`):
  Keep the timeout, the cap and the proxy setting in step when changing any of them.
- **Active Record encryption keys** (same file; an env var that is set wins over the credentials for that key alone, so the keys must not be split between the two):
  Setting only some of the env vars therefore mixes two key sets, so keep all three in the same place.
  Once keys are set, keep them: losing them makes the stored AI key unreadable, and the fix is to remove it and enter it again.

### i18n / Mobility

Translated attributes (`Page#title/slug/subtitle/meta_title/meta_description`, `Post#title/slug/excerpt`, `ContentBlock#caption`) are plain jsonb columns via the Mobility `:jsonb` backend (`config/initializers/mobility.rb`); rich text (`Post#body`, `ContentBlock#body` — pages have none) is the same jsonb backend, one Tiptap/ProseMirror JSON document per locale, via `HasRichTextBody` (see `docs/reference/rich-text.md`), not ActionText. Available/default locales are set once in `config/application.rb` (`config.i18n.available_locales`), not in the Mobility initializer, because Mobility needs it at load time to define per-locale accessors. Falls back to `:en` everywhere. Because translated columns are jsonb, `where(slug: ...)` on them is a bug (comparing jsonb to a string) — use Mobility's `.i18n` scope, as the slug-uniqueness validations on `Page`/`Post` do.

## Key Conventions

- **No RSpec** — Minitest + fixtures (`test/fixtures/`), not factories.
- **No Devise / no ActiveAdmin** — auth and admin (CS Studio) are both hand-rolled as described above; don't reach for those gems' idioms.
- **No compatibility code before it is needed.** Code for a client, a link, a variable or data that cannot exist is not written: no alias for an old name, no fallback for an old shape, no importer for a source nobody has. From 0.1.0 on a removal is a breaking change, and is listed under "Removed" in `CHANGELOG.md`'s next section.
- **No npm/webpack** — JS is import-maps only (`importmap-rails`); CSS is Tailwind via `tailwindcss-rails` (`bin/rails tailwindcss:watch` in dev).
- **Long, load-bearing code comments are the norm in this codebase**, especially in `page.rb`, `content_block.rb`, `post.rb`, and `routes.rb` — they document non-obvious invariants and past incidents (e.g. the Accept-header 500, the two-pages-one-URL collision). Read them before changing the code they annotate, and match that density when adding similarly non-obvious logic; don't strip them out during cleanup. **A comment states a current invariant, a hazard or a reason; never the plan step, the review round or what used to be there: history lives in git and the pull request.**
- **New admin strings are keys, not literals.** A string a person reads in CS Studio lives in `config/locales/admin/` and is read with `t(".key")` (a component: `admin.components.<scope>.key`, via `Admin::AdminComponent`, in the one file per component folder, `config/locales/admin/<folder>.en.yml`, `notes.en.yml` being the one exception, which stays whole because it holds notes' own keys and the strings notes puts on other screens' components, both guarded by `test/lib/source_layout_test.rb`; a script: `messages(element).t(key)` from the server's `data-messages`). The shared components and the admin layout are converted and `test/lib/admin_i18n_test.rb` keeps them free of English (its `CONVERTED` list grows with each screen). The scheme, the plural/interpolation/date rules and what is out of scope: `docs/reference/i18n.md`. A string the public site's own templates say to a visitor that no editor typed is a key too, in `config/locales/public.en.yml` under `public.`, read in the visitor's language with English as an explicit fallback (no I18n fallbacks are configured, and the test environment raises on a missing key), as `Blocks::CodeComponent#string` reads the Code block's four; a page's or a post's template reads its words through `site_string` (`public.site`: "In this section", "Tagged"), and both go through `PublicStrings.read`, the one language-or-English lookup; the site's other strings are still literals, and nothing holds a public template to keys yet.
- **Never define `Admin::<Domain>`.** A module or class under `Admin` named like anything at the top of `app/models`, `app/services`, `app/queries`, `app/values`, `app/constraints` or `lib` shadows that constant for every bare reference inside `module Admin`, so a screen's components go in a namespace named after the *screen* (`Admin::MediaLibrary::`, `Admin::TrashScreen::`), and `test/lib/admin_namespace_shadow_test.rb` derives the names, explains the trap and fails on one.
- **Where a component goes.** A component is in `app/components/admin/ui/` when more than one screen uses it (or the layout does, or a registry such as `columns/` or `fields/`), otherwise in the folder of the screen that owns it, and its class name follows the folder (`Admin::Ui::DialogComponent`, `Admin::PagesScreen::TreeComponent`). One thing is tested: nothing is loose in `app/components/admin/` but `admin_component.rb` (`test/lib/source_layout_test.rb`). The class name following the folder is Zeitwerk's doing, and a file in the wrong place fails `bin/rails zeitwerk:check`. Which folder a component belongs in is a convention with no test: it is a judgement made at review, so look at who renders it when you add a second user to a one-screen component.
- **Where a script goes.** A topic has one name and up to two folders with it: its Stimulus controllers in `app/javascript/controllers/admin/<topic>/` and its plain modules in `app/javascript/<topic>/`. A controller's identifier follows its path (`admin--notes--live`). A behaviour of a shared control is in `ui`, what only the layout uses in `shell`, and autosave, the save bar and the write queue are one topic, `saving`, and the block editor's plain modules (`containers`, `move_queue`, `menu_moves`, `keyboard_moves`, `adding`: each takes the blocks controller as its `host`; `drag` takes none, and its `loadSortable` is also the one SortableJS loader of the page tree and of Settings' rows) are `editor`, the module folder of the topic whose controllers are in `controllers/admin/editor/`. The public site's entry point is `site`, as CS Studio's is `admin`; a theme's controller lives in the theme's folder, never under `app/javascript`. `i18n`, `search` and `live` are the three module folders with no topic of that name: `i18n` and `search` are helpers every screen shares, `live` is what the notes, presence and editing topics share: the cable connection (`live/connection`: the socket, its pooled subscriptions, the tab's id) and the merge core notes and live editing draw a fetched answer with (`live/keep_merge`). Nothing is loose in `controllers/admin/`, and a module folder with no topic of its name is refused (`test/lib/source_layout_test.rb`).
- **Where a class goes.** `app/models` holds the Active Record models, each domain's namespace and its entry file (`audit.rb` beside `audit/`), `Current` and the registries; a plain value object goes in `app/values` (`Pagination`, `Theme`, `TreeOrder`), a route constraint in `app/constraints` (`LocaleRouteConstraint`, `Setup::RedirectConstraint`), a read that spans models in `app/queries`, a write in `app/services`. `lib/` is a sixth place, for what `config/environments/` or an initializer needs before autoloading is ready, or hands to something that keeps it for the life of the process: `SiteAddress` and `HostSettings` (`production.rb` runs before any autoloading is set up), `Telemetry` with its scrubber (the OpenTelemetry SDK keeps the objects it is given) and `ContentSpiel::Plugins` (`lib/content_spiel/plugins.rb`, required BEFORE `Bundler.require`, so a gem may name the hook when its own files load; it keeps the hooks' blocks across every reload), and `ContentSpiel::TestDatabase` (`lib/content_spiel/test_database.rb`, the test database's name for a working folder, required by path from `config/database.yml`, which is read before autoloading), `ContentSpiel::VERSION` and `IMAGE` (`lib/content_spiel/version.rb`, read by the release task and the image's entrypoint). Such a file uses nothing of Rails that is not loaded yet, is required explicitly from `config/application.rb` although `lib/` is autoloaded (`config.autoload_lib`), and is therefore not reloaded: a change to it needs a restart in development. The site commands' plain Ruby is there too, required by path and not from `config/application.rb`: `site_generator.rb`, `theme_generators.rb` and `dev_files.rb` in `lib/content_spiel/`, with the `.tt` files of `lib/site_template/`, which `bin/contentspiel` requires before the application starts, so `config/application.rb` tells Zeitwerk to leave them alone, as it does `version.rb` (which is the one of these it requires); and `release.rb` and `upgrade.rb`, which stay autoloadable and are also required by path (`upgrade.rb` by `bin/contentspiel`; `release.rb` by `upgrade.rb`, `lib/tasks/release.rake` and `release.yml`, which loads it with no bundle). Nothing else goes there, but for Rails' own places: `lib/tasks` and `lib/generators` (a generator and its `.tt` templates, `bin/rails generate block_type`), which `autoload_lib` ignores (`ignore: %w[assets tasks generators]`). Both guards below look at all six directories (rake tasks are `.rake` files and are not scanned).
- **Queries are Active Record, then Arel, then SQL, and a fragment has a name on the model.** What Active Record's own syntax says exactly is said that way (a hash condition, `where(published_at: ..now)`, `where.not`, `.or`, `merge`, `group(:column)`, `where(id: relation.select(:id))`). What it can't say is Arel nodes, never a string — a strict or column-to-column comparison (`arel_table[:published_at].gt(now)`), a function, a jsonb operator, LIKE, a row comparison, `EXISTS`, `COUNT(*) FILTER`, a join with its own `ON`, an ordering by an expression — built through `SqlNodes` (`app/values/sql_nodes.rb`), with Ruby values handed to the nodes, never interpolated. A SQL string stays only where Arel has no node (`upsert`'s `ON CONFLICT`, `LOCK TABLE`, the recursive heredoc in `PublicSite::Paths`) and carries `# sql: <reason>` on its line or the line above, as does a statement sent to the connection (`test/lib/sql_strings_test.rb`). Either way it is a named scope on the model or a method of the query object or index that owns it, with a line saying what it answers, and a controller or component calls it by name: `Tag.named` / `name_containing` / `by_name`, `TitleSearch` (`title_matching(text, locale:)`, `title_matching_any_locale(text)` on `Page` and `Post`), `Publishable.scheduled`, `Page.trash_roots` / `trash_branch_members`, `User.name_or_email_containing`, `Audit::Event.older_in_log_than` / `newer_in_log_than` / `newest_per_subject`, `Translations::StateIndex.work_list`. A search scope escapes its own text (`SqlNodes.like_pattern`), so a caller hands over what was typed and never escapes it again.
- **A controller's Turbo Stream answers are one responder per outcome**, in `app/controllers/admin/answers/` (`Admin::Answers::*`: `BlockSaved`, `BlockRefused`, `BlockGone`, `Stale`, `Held`, with `BlockDrawing` and `PublishingStreams` as the streams they share), drawn with the view they are handed, and the controller's action ends in `answer(...)`; the refusal's status is `Admin::RefusalStatus` and a toast's stream `Admin::ToastStream`, each written once (`app/controllers/concerns/admin/`). A decision stays in the action and the service; a responder only draws.
- **Dependency order.** Models, queries (`app/queries`) and services know nothing of components, helpers or controllers — with one exception by design: a type definition registers its components (`app/models/content_types/*.rb`, `block_types/*.rb` and `app/models/forms/built_in_field_types.rb` name the components that render the type: `t.component`, `t.list_component`, `t.detail_component`, and a form field type its `input:`), because that registration is the plugin seam. Components may know models and queries; controllers orchestrate services and never write a record themselves. A model or query that needs *wording* returns data and a component renders it: `Audit::Sentence` is the actor as facts, the sentence as parts and the subject as a route *name* with its arguments, and `Admin::AuditScreen::SentenceComponent` turns that into a name, markup and a URL; `Dashboard::Activity` returns rows holding such a sentence and builds no component. Route resolution happens in components and controllers, from a fixed set of route names the lower layer may hand up (`Audit::Sentence::Route`), with the request's own URL options. The reason is the direction of change: a screen is rebuilt far more often than a rule, and a model that renders, or a query that picks a component, has to be rewritten with every screen that shows it — and can't be used from MCP, a job or the console, where there is no view. Among the domains the same direction holds: `RichText` and `ContentModel` at the bottom, then `AccessControl` and `Audit`, the content models, the derived indexes (`PublicSite`, `Translations`, `Media`), services, and controllers and components on top; a lower layer never references a higher one. `test/lib/dependency_direction_test.rb` keeps it so: under `app/models`, `app/queries`, `app/services`, `app/values`, `app/constraints` and `lib` (comments stripped) it fails on a `…Component` constant, `ApplicationController`, `ActionController`, `url_helpers` and `Rails.application.routes`, with an `ALLOWED` list that names each exception and its reason (the type definitions' component registration; `RichText::HtmlRenderer` and `BuiltIns` building HTML with Action View's tag helpers; `Media::Asset`'s Active Storage URLs) and fails on an entry that matches nothing. What a lower layer needs from a higher one comes in as data or a callable: rich-text components are drawn by `RichText.component_renderer`, assigned in `config/initializers/rich_text.rb`; a `Jump::Search` row carries `[route name, args, params]`, which `Admin::JumpHelper` resolves against a fixed list; `PostGraph::Global` and `PostGraph::Local` take `url_for:` with no default, and `PostGraph::Search` answers ids the controller turns into URLs; and the starter content is written by `StarterContents::EnsureHome` and `StarterContents::Add`, since `StarterContent` (a model) holds only the sample data and `added?`.
- **A change that alters what a person sees or does, in CS Studio or on the public site, names the guide pages it affects in its pull request under "Documentation", or says "none".** The guide lives in its own repository, `contentspiel-docs`, the documentation site, and is updated there before the change is released; no guide text is kept in this repository.
- **Design docs**: `docs/superpowers/specs/` and `docs/superpowers/plans/` hold the original design specs and implementation plans this app was built from — useful background when a change touches the page tree or content blocks.
