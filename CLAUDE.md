# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

ContentSpiel is a Rails 8.1 CMS: a page-tree-driven public website plus CS Studio, its own admin. Content editors build pages out of ordered content blocks (rich text, images, post listings), organize them in a tree, and the same tree drives navigation, routing, and the sitemap. Rich text is Tiptap/ProseMirror JSON. Everything is translated via Mobility into the languages switched on in Settings (three by default, en/de/es, out of the 38 in `config/supported_locales.rb`).

## Setup & Commands

```sh
docker compose up -d          # Postgres 17, published on host port 5433 -- start this first
bin/setup --skip-server       # installs gems, prepares dev + test databases
bin/rails db:seed             # the built-in groups (every environment), and in development an admin account and demo content (see db/seeds.rb)
bin/rails server               # or `bin/dev`, which runs server + `tailwindcss:watch` (see Procfile.dev)
```

- App: http://localhost:3000
- Sign in: http://localhost:3000/cs-studio/sign-in (`<ADMIN_PATH>/sign-in`)
- Admin (CS Studio, behind the same sign-in): http://localhost:3000/cs-studio (`ContentSpiel::ADMIN_PATH`, configurable via `ADMIN_PATH`)

**Tests:** `bin/rails test` (full suite, minitest). Single file: `bin/rails test test/models/page_test.rb`. Single test: `bin/rails test test/models/page_test.rb -n test_method_name` or `bin/rails test test/models/page_test.rb:42` (line number). System tests (Capybara on Cuprite, headless Chrome) are separate: `bin/rails test:system` (the whole browser suite, whatever file is named after it: one file is `bin/rails test test/system/admin/tree_test.rb`); run `bin/rails tailwindcss:build` first, and on a laptop cap the workers (`PARALLEL_WORKERS=6 bin/rails test:system` — twelve flakes under load). On macOS prefix every test command with `PGGSSENCMODE=disable`: a parallel run can otherwise crash a forked worker in the pg gem and hang forever. `test/application_system_test_case.rb` prepends `StaleNodeAtOnce` to Cuprite's nodes so a poll whose element died in a Turbo visit fails at once instead of spending half a second per element — that is what made toasts that had come and gone look "missing". Two more rules for a system test: a link into the `#content` frame (a media tile, a trash tab, a list row) is promoted by Turbo to a page visit a few dozen milliseconds after the frame has rendered, and until that visit's `turbo:load` the screen is still arriving — a field typed into can be re-rendered, a Back can be cancelled by the late visit, a link clicked can lose to it — so a test that goes on to read or use the new screen follows the link through `click_frame_link` (`test/application_system_test_case.rb`: a link by its text, or a block for anything else, including a form whose answer redirects inside the frame), the one shared helper; `click_tile` in the media tests and `click_tab` in the trash tests are thin wrappers around it, and no test keeps its own copy of the wait. A `_top` form pressed in that window is held by the write queue and sent afterwards (the promotion hold, see `docs/reference/save-rule-and-write-queue.md`); `test/system/admin/promotion_hold_test.rb` presses without the wait on purpose and must keep doing so. And a test that resizes the window puts the size back in an `ensure`, because the browser is shared with the tests that follow. A test never waits for an element that only a `hover:` style reveals (the CI browser reports it can't hover): click it with `visible: :all`. A notes system test clears `localStorage["cs-notes-open"]` in its teardown (the drawer remembers "open" per browser), never follows a link inside `turbo-frame#notes` with `click_frame_link` (that frame is never promoted to a visit: click and assert), and, before it causes a signal, waits with `await_notes_live` until every cable subscription of the page has been answered; the suite's `test` cable adapter delivers to the browsers as it is, so no test switches adapters. A test that stubs `window.fetch` intercepts only its own request and hands every other to the real `fetch` it saved, because the editors' live parts (presence, notes, live editing) fetch too: a stub that takes everything answers or holds theirs; and a stub that counts or scripts "the writes" of an editor passes a request to `/cs-studio/editing/` through untouched and uncounted, because a claim and a release are writes in the queue. Two people are two Capybara sessions (`using_session`), and every presence system test is built that way (`test/system/admin/presence_test.rb`, `presence_lists_test.rb`): time is not moved with `backdate` (that moves `updated_at`, which `presence_marks` does not have). A test writes a mark's `seen_at` or `state_at` itself with `update_columns` to make a row stale or an away person older, and shortens a script's intervals (its refresh, its slow timer, its interval between readings) through the element's values; where it must show that nothing happens it holds a `sleep` with its `# sleep: <reason>`, which the sleeps guard permits. `await_notes_live` waits for presence's subscriptions as well as notes' (a part that is an element of the page says it on its own `data-live-part`, `app/javascript/live/state.js`). An open page or post editor catches up once when its live-editing subscription is confirmed, and `await_admin_controllers` waits for that too (`await_live_part`: the region `#editing` says `answered`), because a test that touched the page before it would see it reconciled under it. A test of the stale machinery itself (a 409, "Changed elsewhere") makes the colleague's save with `as_unheard(actor)`, which drops the signal: a save the editor heard of is drawn into it, and its next save is no longer stale. A reservation's clock is moved on its row (`update_all(changed_at: 3.minutes.ago)` for a lapsed hold, `requested_at: 6.seconds.ago` for a request that is due), the scripts' waits are shortened through the region's values, and the unit tests hand `now:` to the statements; the two-connection tests (`Editing::ReservationRaceTest`, `Editing::TakeOverRaceTest`) force an order with their `behind` helper, which waits until Postgres says the second statement is blocked behind the first (`docs/reference/live-editing.md`, "In tests"). **The system suite needs a quiet machine:** macOS background services (Software Update, Spotlight, photo analysis) at a load average of 80 to 110 made two whole runs worthless on 2026-10-10, with failures that were the machine's. Check `sysctl -n vm.loadavg` before a run (a load near the core count is not quiet), and a run that takes twice its usual time is not a result. **Never run a build while tests run** (`bin/rails tailwindcss:build`, `bin/dev`'s `theme_css:watch`, `bin/theme-build-check`): the public stylesheet's build takes its stamp (`app/assets/builds/.theme.stamp`) away for as long as it runs and writes it again only when it succeeded, two tests read the working tree's stamp (`test/models/setup/system_check_test.rb`: "the row's own probe reads the build's stamp: this suite's stylesheet is the default theme's"; `test/integration/admin/system_status_test.rb`: "the theme row names the theme that draws the site and no path of the server, and warns when the stylesheet is another theme's"), and every public integration test reads `app/assets/builds/theme.css`. Development and test share that stylesheet and its entry (`tmp/theme/entry.css`): a test run leaves the default theme's behind, also under a running `bin/dev`, and `bin/theme-build-check` does the same on its way out.

**System tests fail on any JavaScript error.** `JsErrorCollector` (`test/support/js_error_collector.rb`, prepended to `Ferrum::Page`) records `Runtime.exceptionThrown` and `console.error` (Stimulus reports a throwing action there, with an Error argument's first stack line appended to the message), and the teardown fails the test. A test that expects one wraps the step in `expect_js_error(pattern, times:)`; `JsErrorCollector::IGNORED` holds the matchers that are let through (one Turbo AbortError), each with its reason. A click is `press` (a native click, so a control a person couldn't press is not found); `press_by_script` is the exception and carries a one-line comment naming why. **No fixed sleeps:** `test/lib/system_test_sleeps_test.rb` fails on a `sleep` in a system test without `# sleep: <reason of at least ten characters>` on the same line; a test waits for a condition with `assert_eventually(wait:, message:)`, `await_js(condition, wait:)`, `click_frame_link`, `assert_writes_settled` (the write queue is empty; trivially true on a screen with no autosave form, so useless for a form that is paused or failed), `await_frames` (three animation frames and a task: enough to let an event's synchronous work finish before asserting that something did NOT happen, not enough to wait out a timer such as a debounce or a retry delay), `backdate(record, by:)` (puts `updated_at`, and a page's `settings_changed_at`, in the past without a callback, because the browser's clock does not follow `travel_to`) and, for an AI-provider test that needs a request kept in flight, `GatedProvider` (`test/support/gated_provider.rb`, a latch: `hold!`, `release`, `reset!`). `capture_sql` (`test/test_helper.rb`) returns the statements a block runs, for a test that says a write costs the same at any size.

A local run is quiet: what tests themselves print (the statements a migration test runs, the seed file's "Seeded dev accounts" lines) is swallowed, and shown only for a block that fails. `VERBOSE=1 bin/rails test` prints all of it, and CI always sets `VERBOSE` (`TestOutput` in `test/test_helper.rb`; a test that prints wraps the call in `TestOutput.quietly { ... }`).

Coverage is on request: `COVERAGE=1 bin/rails test` (SimpleCov, line and branch) writes `coverage/index.html`, which `bundle exec simplecov open` shows; the parallel workers' results are merged into the one report. It is off by default, since a run of one file would report a meaningless few percent. CI turns it on for the unit suite and keeps the report as the `coverage` artifact. There is no minimum yet, so a drop doesn't fail a run.

**A theme:** `THEME_PATH=<folder> bin/dev` draws the site with a theme folder; `bin/rails 'theme:new[PATH]'` writes a copy of the default theme to start from, `bin/rails theme:check` says what is wrong with a folder, and `bin/theme-build-check` builds the stylesheet under the second theme and starts production under it (it writes `app/assets/builds`, so it is run alone). The test environment ignores `THEME_PATH`: a test is drawn by the second theme with `with_plain_theme { … }`, or by a changed copy of it with `with_theme_copy` (`docs/reference/theming.md`, "In tests").

CI runs the browser suite as four jobs side by side (a runner has two cores): `bin/system-test-shard <index> <total>` deals the files so each job takes about the same time, by the seconds per file in `test/system_test_seconds.yml` (measured once on a runner; the table needs no upkeep: a file it does not list counts by its number of tests, and a stale number only makes the jobs a little uneven), `test/lib/system_test_shards_test.rb` keeps every file in exactly one shard, and the one check `system-test` speaks for the four. CI runs for a pull request only, and a new push to it ends the run before it: a merge to `main` is not tested again (the repository is private and a full run is about 48 billed Actions minutes), so `main` is run by hand when that is wanted (`gh workflow run CI --ref main`). A push to `main` does build the CMS's image and push it to the registry under the commit's id (`.github/workflows/image.yml`, about five billed minutes; `docs/reference/hosting.md`, "How a site's image is built"), which is what a site pins. A change that touches only `docs/`, a top-level `.md` file or `.github/workflows/image.yml` skips the browser suite; the unit suite always runs, because its guards read `CLAUDE.md` and `docs/reference`.

**Lint/scan** (all run in CI, see `.github/workflows/ci.yml`):
```sh
bin/rubocop            # style (rubocop-rails-omakase, config in .rubocop.yml)
bin/brakeman            # static security analysis
bin/bundler-audit       # known CVEs in gems
bin/importmap audit     # known CVEs in JS deps (import maps, no npm/node_modules)
```

`config/brakeman.ignore` lists the warnings Brakeman is told to skip: none today (the four "SQL Injection" ignores on constant-built SQL went when `Media::Search` and `Translations::StateIndex` stopped building SQL text). A new entry needs its `note` saying why the warning is false; `bin/brakeman` must exit 0 either way.

**DB:** `bin/rails db:prepare` / `db:migrate` / `db:test:prepare`. Schema lives in `db/schema.rb` (Postgres, jsonb-heavy) -- no `db/structure.sql`.

**Deploy:** Kamal (`.kamal/`), containerized via `Dockerfile`. Not typically invoked from Claude Code sessions. What production asks of its host is eight variables (`docs/reference/hosting.md`): `PUBLIC_HOST`, the site's address with its scheme, from which the hosts that are answered, forced HTTPS and the address in mailed links all follow (`HostSettings.apply`; `config/environments/production.rb` sets none of them itself, and `config/deploy.yml` holds `PUBLIC_HOST` only as a commented line to fill in); `ASSUME_SSL=1` for a proxy that sends no `X-Forwarded-Proto`; `THEME_PATH`, the site's theme folder, under which production does not start when the folder is refused or the stylesheet was built for another theme (`docs/reference/theming.md`); `SECRET_KEY_BASE`, without which (and without a secret in the credentials) production stops at boot with a message of its own; `SETUP_TOKEN`; and the three of telemetry below. A production boot prints which address it serves, and that the host match is exact, as `[ContentSpiel]` lines at info.

**Telemetry** prints nothing unless asked, in development too: `OTEL_CONSOLE=1 bin/dev` (exactly `1`) prints spans to the terminal, `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` sends them, and with none of the three the SDK is not configured at all (`Telemetry.exporter_kind`); the test environment records in memory. Whatever is configured records a request's or a job's trace and nothing of the background's polling (`Telemetry::WorkSampler`).

### Rules a change can break silently

Each rule names the test that guards it where there is one; the reference file in the index explains the reasoning.

- Every public URL is a stored `public_paths` row derived by `PublicSite::Paths.refresh`, the one entry point (a caller says what it touched and never which posts that could move; `rebuild!` is the same function over everything): never write one by hand, never resolve a request by walking the tree, never call a function inside `paths.rb`, and keep `test/models/public_site/paths_test.rb` (parity with a full rebuild: "every write path leaves public_paths equal to a full rebuild") green when a write path feeds a URL; `test/lib/public_paths_entry_test.rb`: "outside its own file PublicSite::Paths is asked to refresh, to rebuild, or to read: nothing calls a function inside the entry point". A post's address is derived from the list blocks and the tags AS PUBLISHED, so a write path that changes either belongs in the parity test ("changing a live page's list block to another type moves no address until the page is published").
- A publish is refused only for the record's OWN address (`Publishing.keep_address!`, `Publishing::AddressTaken`, rescued by `Pages::Save`, `Posts::Save` and `Publishing::PublishChanges`); another record that loses its address yields, is logged and reported once, and the publish dialog names it beforehand, as it names, in a second group, every live record the publish would MOVE to another address, old and new (`Publishing::Changes.addresses`, the `lost` and the `moved` of `PublicSite::Paths.foresee`; a POST, never a GET: it tries the publish under the row lock and rolls it back) (`test/integration/public_drafts_test.rb`: "removing a page's list block when another page lists the posts too MOVES them: named beforehand with the old and the new address, and the old one then redirects", "removing a page's list block and publishing drops a live post to no address: named beforehand, not refused, logged and reported once, and the addresses are a rebuild's").
- Every content, settings, user, group and token write goes through an `ApplicationService` that calls `authorize!(` and `record_event(`, and a controller never writes a record itself (`test/services/service_contract_test.rb`, `test/services/service_behaviour_contract_test.rb`).
- Presence is one of the two writes that are not an `ApplicationService` (an edit reservation is the other, below): `Presence::Channel` writes and deletes its own `presence_marks` rows through `Presence::Mark` (one statement each, no callbacks), because a presence is not content, nobody asks for it by name and a row is ignored by every read after `Presence::STALE_AFTER`; it is never audited, never touches the record it is on (no `touch`, no `updated_at`) and never moves the content version, so a presence write says `# version: none (presence is not content)` on its line, and presence knows nothing of notes (`test/models/presence/mark_test.rb`: "presence writes nothing but its own row: not the record, not the content version, not the audit log"; `test/channels/presence/channel_test.rb`: "presence writes nothing of the record, of the content version or of the audit log"; `test/integration/admin/presence_test.rb`: "presence is read and never written: the record, the content version and the audit log do not move"; `test/lib/version_bump_test.rb`).

- A theme's Code template is promised nine names (`block`, `page`, `lines`, `code`, `language`, `language_label`, `filename`, `caption`, `string`), the seven `--th-syn-*` tokens and the copy script's markup (its targets, its action, its values), each changed only with a release note. A method that only the DEFAULT template's layout needs is written in that template and never added to `Blocks::CodeComponent`, because every method the default template calls must be on the line (`head_attributes` and `file_id` were on it for one review: a theme whose bar also holds the caption would have hidden the caption with them). `string` answers its four keys and no other, so a key a theme's author mistyped is never I18n's "Translation missing" sentence as a button's word. And every syntax colour stays at 4.5:1 on each ground a code block has, in both schemes (`test/values/theme/contract_test.rb`: "the Code block is in the contract: its template is replaceable with the methods it may call, and its seven syntax tokens are themed tokens in the highlighter's order", "a default component template calls no method of its component that its line does not name"; `test/lib/theming_reference_test.rb`: "the Code block's tables name exactly the methods of its entry, the four words and what the copy script reads"; `test/components/blocks/code_component_test.rb`: "string answers the four words and nothing else: another key raises with the four where a theme is written, and in production is empty and logged once"; `test/integration/design_tokens_test.rb`: "every syntax colour is readable on every ground a code block has: the page, a tinted band and a strong band, in both themes", 42 pairs; `test/integration/theme_pages_test.rb`: "a theme replaces the Code block's template from the contract's names alone, and a theme that does not is drawn the default one"). **No guard** for a theme outside this repository whose template still writes a renamed target, and the contract's method guard does not see a call inside a string's interpolation, a `self.` call or an inherited method.

### Pitfalls

Each of these ends a description in `docs/reference/` and is repeated here because the mistake it names is easy to make.

- **Public URLs** (`docs/reference/page-tree-and-routing.md`; the comments in `page.rb`, `public_site/paths.rb` and `tree_ranking.rb` hold the two-pages-one-URL and nil-position footguns):
  Read the extensive comments in `page.rb`, `public_site/paths.rb` and `tree_ranking.rb` before changing any of this -- the two-pages-one-URL and nil-position footguns they guard against are non-obvious and previously shipped as bugs (see commit `da80c58`).
- **Public routing** (same file; `config/routes.rb` carries the history of the 500-vs-404 regression):
  Read the routes.rb comments before touching `format: false` or the locale constraint; there's a documented history of a 500-vs-404 regression here.
- **The write queue** (`docs/reference/save-rule-and-write-queue.md`; every write of an autosave screen is serialised on this assumption):
  The queue assumes Turbo's morphing page refresh stays off.
  Notes, presence and an open editor (`docs/reference/live-editing.md`: plain GETs merged by `editing/merge.js`) are refreshed part by part for the same reason (`docs/reference/notes.md`, "Live delivery"): no `turbo_refreshes_with`, no `broadcast_refresh`, no `<meta name="turbo-refresh-method">`. All three are refused by `test/lib/notes_guards_test.rb` ("nothing in the app turns on Turbo's page refresh or morphing, or broadcasts one"), and any broadcast but `Live::Signals`' by `test/models/notes/signals_test.rb`.
- **Import-map pins** (`docs/reference/rich-text.md`; the option to re-add after re-pinning is `preload: "admin"`, which keeps the editor off public pages):
  Re-pinning Tiptap (`bin/importmap pin @tiptap/core @tiptap/starter-kit @tiptap/extension-link ...`) writes the new pins without that option — re-add `preload: "admin"` afterwards (`test/integration/public_javascript_test.rb` catches a miss).
- **AI requests** (`docs/reference/translations.md`; the three that must agree are the provider's 25 s timeout, `AI::Translate::MAX_FIELDS` / `MAX_CHARACTERS`, and `proxy.response_timeout: 75` in `config/deploy.yml`):
  Keep the timeout, the cap and the proxy setting in step when changing any of them.
- **Active Record encryption keys** (same file; an env var that is set wins over the credentials for that key alone, so the keys must not be split between the two):
  Setting only some of the env vars therefore mixes two key sets, so keep all three in the same place.
  Once keys are set, keep them: losing them makes the stored AI key unreadable, and the fix is to remove it and enter it again.

### i18n / Mobility

Translated attributes (`Page#title/slug/subtitle/meta_title/meta_description`, `Post#title/slug/excerpt`, `ContentBlock#caption`) are plain jsonb columns via the Mobility `:jsonb` backend (`config/initializers/mobility.rb`); rich text (`Post#body`, `ContentBlock#body` — pages have none) is the same jsonb backend, one Tiptap/ProseMirror JSON document per locale, via `HasRichTextBody` (see `docs/reference/rich-text.md`), not ActionText. Available/default locales are set once in `config/application.rb` (`config.i18n.available_locales`), not in the Mobility initializer, because Mobility needs it at load time to define per-locale accessors. Falls back to `:en` everywhere. Because translated columns are jsonb, `where(slug: ...)` on them is a bug (comparing jsonb to a string) — use Mobility's `.i18n` scope, as the slug-uniqueness validations on `Page`/`Post` do.

## Key Conventions

- **No RSpec** — Minitest + fixtures (`test/fixtures/`), not factories.
- **No Devise / no ActiveAdmin** — auth and admin (CS Studio) are both hand-rolled as described above; don't reach for those gems' idioms.
- **No npm/webpack** — JS is import-maps only (`importmap-rails`); CSS is Tailwind via `tailwindcss-rails` (`bin/rails tailwindcss:watch` in dev).
- **Long, load-bearing code comments are the norm in this codebase**, especially in `page.rb`, `content_block.rb`, `post.rb`, and `routes.rb` — they document non-obvious invariants and past incidents (e.g. the Accept-header 500, the two-pages-one-URL collision). Read them before changing the code they annotate, and match that density when adding similarly non-obvious logic; don't strip them out during cleanup.
- **New admin strings are keys, not literals.** A string a person reads in CS Studio lives in `config/locales/admin/` and is read with `t(".key")` (a component: `admin.components.<scope>.key`, via `Admin::AdminComponent`, in the one file per component folder, `config/locales/admin/<folder>.en.yml`, `notes.en.yml` being the one exception, which stays whole because it holds notes' own keys and the strings notes puts on other screens' components, both guarded by `test/lib/source_layout_test.rb`; a script: `messages(element).t(key)` from the server's `data-messages`). The shared components and the admin layout are converted and `test/lib/admin_i18n_test.rb` keeps them free of English (its `CONVERTED` list grows with each screen). The scheme, the plural/interpolation/date rules and what is out of scope: `docs/reference/i18n.md`. A string the public site's own templates say to a visitor that no editor typed is a key too, in `config/locales/public.en.yml` under `public.`, read in the visitor's language with English as an explicit fallback (no I18n fallbacks are configured, and the test environment raises on a missing key), as `Blocks::CodeComponent#string` reads the Code block's four; the site's other strings are still literals, and nothing holds a public template to keys yet.
- **Never define `Admin::Media` or `Admin::Trash`** — either module would shadow the top-level `Media`/`Trash` namespaces (models and services) for every bare `Media::`/`Trash::` reference lexically inside `module Admin`, a `NameError` that has already shipped once mid-task. That's why the media library's admin components are `Admin::MediaLibrary::` and the Trash screen's are `Admin::TrashScreen::`. The same goes for **`Admin::Translations`, `Admin::AI` and `Admin::Ai`**, which would shadow `Translations::`/`AI::`: the translation screens' components live under `Admin::TranslationScreen::`. The same goes for **`Admin::Audit`** (it would shadow `Audit::Event`/`Sentence`/`Filter`): the audit log's components live under `Admin::AuditScreen::`. And for **`Admin::Dashboard`** (it would shadow the `Dashboard::` queries): the dashboard's components live under `Admin::DashboardScreen::`. And for **`Admin::Notes`** (it would shadow `Notes::`): the notes components live under `Admin::NotesScreen::`, and the controllers are `Admin::NotesController`, `Admin::NoteThreadsController` and so on, classes and not a namespace. A screen's components go in a namespace named after the *screen*, never after a domain module: besides those, `Admin::EditorScreen::`, `Admin::PostsScreen::`, `Admin::SettingsScreen::`, `Admin::TokensScreen::`, `Admin::GroupsScreen::`, `Admin::UsersScreen::`, `Admin::PagesScreen::` (the page tree), `Admin::MindGraphScreen::` and `Admin::Shell::`, and `Admin::Ui::` for the shared building blocks that belong to no one screen (the dialog, the toast, the fields' wrappers, the save bar) (`Settings::`, `Groups::`, `Users::` and `ApiTokens::` are service namespaces a bare `Admin::Settings` and so on would shadow the same way). The same goes for **`Admin::Presence`** (it would shadow `Presence::`), **`Admin::Live`** (`Live::Signals`, `Live::RecordChannel`), **`Admin::RecordKinds`** and **`Admin::PersonName`**: presence's components live under `Admin::PresenceScreen::`, its controller is `Admin::PresenceController`, a class and not a namespace; and for **`Admin::Editing`** (it would shadow `Editing::`): live editing's components are the editors' own (`Admin::EditorScreen::HoldStripComponent`, `LiveRegionComponent`, `HolderAvatarComponent`, `UpdatedMarkComponent`), its controller is `Admin::EditingController` and its concern `Admin::EditingClaims`, and inside `module Admin` they write `::Editing::`; and for **`Admin::Publishing`** (it would shadow `Publishing::`): its controller is `Admin::PublishingController` and its concern `Admin::PublishingState`, and inside `module Admin` they write `::Publishing::` (`test/lib/publishing_guards_test.rb`: "Admin::Publishing is not defined"); and for **`Admin::PostGraph`** (it would shadow the Mind graph's queries, `PostGraph::`) and **`Admin::TreeOrder`**: the Mind graph's components live under `Admin::MindGraphScreen::` (the legend, the status key, a swatch), its controller is `Admin::MindGraphController`, a class and not a namespace, and a component under `Admin::` writes `::TreeOrder`; and for **`Admin::Theme`**, **`Admin::ThemeFolder`** and **`Admin::ThemeCss`** (they would shadow `Theme`, `ThemeFolder` and `ThemeCss`): theming has no screen in CS Studio, its one row there is `Setup::SystemCheck`'s; and for **`Admin::CodeHighlight`** (it would shadow `CodeHighlight`, which the editor's tile reads from inside `module Admin`, written `::CodeHighlight`; the code field's input is `Admin::Fields::CodeField`); and the slot registry, which holds component classes and is no domain, is `Admin::Slots` (`app/components/admin/slots.rb`, a loose file named in `test/lib/source_layout_test.rb` beside the base class). One test guards every one of them, `test/lib/admin_namespace_shadow_test.rb`. Its names are derived, not listed: whatever sits at the top of `app/models`, `app/services`, `app/queries`, `app/values`, `app/constraints` and `lib` (so `Admin::Telemetry`, `Admin::SiteAddress` and `Admin::HostSettings` are refused too) — a directory is a namespace, a file a class or module (so `Admin::Page` is refused too) — each both as Zeitwerk inflects it and as a plain camelize would (hence `Ai`), so a new domain is guarded the day its directory appears. It fails when `Admin` defines one of those names and when a bare reference from inside `Admin` doesn't reach the top-level constant; its allow-list (`ALLOWED`) is empty, and an entry needs its reason written beside it. The Tags screen has no components of its own.
- **Where a component goes.** A component is in `app/components/admin/ui/` when more than one screen uses it (or the layout does, or a registry such as `columns/` or `fields/`), otherwise in the folder of the screen that owns it, and its class name follows the folder (`Admin::Ui::DialogComponent`, `Admin::PagesScreen::TreeComponent`). One thing is tested: nothing is loose in `app/components/admin/` but `admin_component.rb` (`test/lib/source_layout_test.rb`). The class name following the folder is Zeitwerk's doing, and a file in the wrong place fails `bin/rails zeitwerk:check`. Which folder a component belongs in is a convention with no test: it is a judgement made at review, so look at who renders it when you add a second user to a one-screen component.
- **Where a script goes.** A topic has one name and up to two folders with it: its Stimulus controllers in `app/javascript/controllers/admin/<topic>/` and its plain modules in `app/javascript/<topic>/`. A controller's identifier follows its path (`admin--notes--live`). A behaviour of a shared control is in `ui`, what only the layout uses in `shell`, and autosave, the save bar and the write queue are one topic, `saving`. The public site's entry point is `site`, as CS Studio's is `admin`; a theme's controller lives in the theme's folder, never under `app/javascript`. `i18n`, `search` and `live` are the three module folders with no topic of that name: `i18n` and `search` are helpers every screen shares, `live` is the cable connection the notes, presence and editing topics share (`live/connection`: the socket, its pooled subscriptions, the tab's id). Nothing is loose in `controllers/admin/`, and a module folder with no topic of its name is refused (`test/lib/source_layout_test.rb`).
- **Where a class goes.** `app/models` holds the Active Record models, each domain's namespace and its entry file (`audit.rb` beside `audit/`), `Current` and the registries; a plain value object goes in `app/values` (`Pagination`, `Theme`, `TreeOrder`), a route constraint in `app/constraints` (`LocaleRouteConstraint`, `Setup::RedirectConstraint`), a read that spans models in `app/queries`, a write in `app/services`. `lib/` is a sixth place, for what `config/environments/` or an initializer needs before autoloading is ready, or hands to something that keeps it for the life of the process: `SiteAddress` and `HostSettings` (`production.rb` runs before any autoloading is set up), `Telemetry` with its scrubber (the OpenTelemetry SDK keeps the objects it is given) and `ContentSpiel::Plugins` (`lib/content_spiel/plugins.rb`, required BEFORE `Bundler.require`, so a gem may name the hook when its own files load; it keeps the hooks' blocks across every reload). Such a file uses nothing of Rails that is not loaded yet, is required explicitly from `config/application.rb` although `lib/` is autoloaded (`config.autoload_lib`), and is therefore not reloaded: a change to it needs a restart in development. Nothing else goes there, but for Rails' own places: `lib/tasks` and `lib/generators` (a generator and its `.tt` templates, `bin/rails generate block_type`), which `autoload_lib` ignores (`ignore: %w[assets tasks generators]`). Both guards below look at all six directories (rake tasks are `.rake` files and are not scanned).
- **Queries are Active Record, then Arel, then SQL, and a fragment has a name on the model.** What Active Record's own syntax says exactly is said that way (a hash condition, `where(published_at: ..now)`, `where.not`, `.or`, `merge`, `group(:column)`, `where(id: relation.select(:id))`). What it can't say is Arel nodes, never a string — a strict or column-to-column comparison (`arel_table[:published_at].gt(now)`), a function, a jsonb operator, LIKE, a row comparison, `EXISTS`, `COUNT(*) FILTER`, a join with its own `ON`, an ordering by an expression — built through `SqlNodes` (`app/values/sql_nodes.rb`), with Ruby values handed to the nodes, never interpolated. A SQL string stays only where Arel has no node (`upsert`'s `ON CONFLICT`, `LOCK TABLE`, the recursive heredoc in `PublicSite::Paths`) and carries `# sql: <reason>` on its line or the line above, as does a statement sent to the connection (`test/lib/sql_strings_test.rb`). Either way it is a named scope on the model or a method of the query object or index that owns it, with a line saying what it answers, and a controller or component calls it by name: `Tag.named` / `name_containing` / `by_name`, `TitleSearch` (`title_matching(text, locale:)`, `title_matching_any_locale(text)` on `Page` and `Post`), `Publishable.scheduled`, `Page.trash_roots` / `trash_branch_members`, `User.name_or_email_containing`, `Audit::Event.older_in_log_than` / `newer_in_log_than` / `newest_per_subject`, `Translations::StateIndex.work_list`. A search scope escapes its own text (`SqlNodes.like_pattern`), so a caller hands over what was typed and never escapes it again.
- **Dependency order.** Models, queries (`app/queries`) and services know nothing of components, helpers or controllers — with one exception by design: a type definition registers its components (`app/models/content_types/*.rb` and `block_types/*.rb` name the components that render the type: `t.component`, `t.list_component`, `t.detail_component`), because that registration is the plugin seam. Components may know models and queries; controllers orchestrate services and never write a record themselves. A model or query that needs *wording* returns data and a component renders it: `Audit::Sentence` is the actor as facts, the sentence as parts and the subject as a route *name* with its arguments, and `Admin::AuditScreen::SentenceComponent` turns that into a name, markup and a URL; `Dashboard::Activity` returns rows holding such a sentence and builds no component. Route resolution happens in components and controllers, from a fixed set of route names the lower layer may hand up (`Audit::Sentence::Route`), with the request's own URL options. The reason is the direction of change: a screen is rebuilt far more often than a rule, and a model that renders, or a query that picks a component, has to be rewritten with every screen that shows it — and can't be used from MCP, a job or the console, where there is no view. Among the domains the same direction holds: `RichText` and `ContentModel` at the bottom, then `AccessControl` and `Audit`, the content models, the derived indexes (`PublicSite`, `Translations`, `Media`), services, and controllers and components on top; a lower layer never references a higher one. `test/lib/dependency_direction_test.rb` keeps it so: under `app/models`, `app/queries`, `app/services`, `app/values`, `app/constraints` and `lib` (comments stripped) it fails on a `…Component` constant, `ApplicationController`, `ActionController`, `url_helpers` and `Rails.application.routes`, with an `ALLOWED` list that names each exception and its reason (the type definitions' component registration; `RichText::HtmlRenderer` and `BuiltIns` building HTML with Action View's tag helpers; `Media::Asset`'s Active Storage URLs) and fails on an entry that matches nothing. What a lower layer needs from a higher one comes in as data or a callable: rich-text components are drawn by `RichText.component_renderer`, assigned in `config/initializers/rich_text.rb`; a `Jump::Search` row carries `[route name, args, params]`, which `Admin::JumpHelper` resolves against a fixed list; `PostGraph::Global` and `PostGraph::Local` take `url_for:` with no default, and `PostGraph::Search` answers ids the controller turns into URLs; and the starter content is written by `StarterContents::EnsureHome` and `StarterContents::Add`, since `StarterContent` (a model) holds only the sample data and `added?`.
- **A change that alters what a person sees or does, in CS Studio or on the public site, names the guide pages it affects in its pull request under "Documentation", or says "none".** The guide lives in its own repository, `contentspiel-docs`, the documentation site, and is updated there before the change is released; no guide text is kept in this repository.
- **Design docs**: `docs/superpowers/specs/` and `docs/superpowers/plans/` hold the original design specs and implementation plans this app was built from — useful background when a change touches the page tree or content blocks.
