# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

ContentSpiel is a Rails 8.1 CMS: a page-tree-driven public website plus CS Studio, its own admin. Content editors build pages out of ordered content blocks (rich text, images, post listings), organize them in a tree, and the same tree drives navigation, routing, and the sitemap. Rich text is Tiptap/ProseMirror JSON. Everything is translated into three locales (en/de/es) via Mobility.

## Architecture

### The page tree

`Page` (`app/models/page.rb`) is a `closure_tree` (gem `closure_tree`), backed by a `page_hierarchies` closure table, with exactly one root (the homepage, enforced by `only_one_root_page`). Sibling order is the `position` column; closure_tree renumbers it, but reordering ("type a new position number" -- there is no drag-and-drop) is implemented on top of that in `remember_requested_position`/`place_among_siblings` because closure_tree's own renumbering doesn't do what a literal "move to rank N" UI needs.

Every public URL is precomputed and stored: the `public_paths` table (`PublicPath`, one row per record per locale, `current: true` for the live URL and `current: false` for the redirects an old URL leaves behind) is derived by `PublicSite::Paths` from model callbacks (`HasPublicPaths`), never written by hand -- a page save resyncs its whole subtree (`sync_subtree`), since a slug change on an ancestor shifts every descendant's URL, plus every post its listing blocks give a URL to. The public router (`PagesController#show`) asks `PublicSite::Resolver` for a URL, which is a single indexed lookup in that table plus the visibility rule (`:published`, or `:preview` for signed-in editors) rather than a walk of the tree per request; `PublicSite::Urls` builds links the other way round. Sibling ranking lives in `Page::TreeRanking` (`app/models/page/tree_ranking.rb`). Read the extensive comments in `page.rb`, `public_site/paths.rb` and `tree_ranking.rb` before changing any of this -- the two-pages-one-URL and nil-position footguns they guard against are non-obvious and previously shipped as bugs (see commit `da80c58`).

### Content blocks

`ContentBlock` (`app/models/content_block.rb`) is one polymorphic-by-enum table (`block_type`: `rich_text` / `image` / `post_list`) belonging to a `Page`, ordered by `position`, edited via nested attributes inside the page form in CS Studio. `Post` uses the same single-model-plus-enum shape for its own `content_type` (`blog` / `resume_entry` / `now_update`). A `post_list` block's `settings` jsonb names a `content_type` filter, a `tag`, and a `limit`; `listed_posts` is the canonical query both the listing partial and the permalink-resolution fallback in `PagesController` must agree on.

### Public routing

Routes: `config/routes.rb`. Two catch-all routes, declared last (named routes like `/cs-studio`, `/mcp`, `/up` must win first; the unprefixed catch-all also skips `/rails/active_storage/...`, whose routes Rails draws after this file): `get ":locale(/*path)"` for an explicit locale prefix (`/de/about`), and `root`/`get "*path"` for no prefix at all (served in `SiteSetting#default_locale`, editable in CS Studio's Settings module, checked per request — not a code-level default). `PagesController#redirect_default_locale_prefix` 302s an explicit prefix that happens to name the *current* default locale to the unprefixed URL, so each page has exactly one canonical address even though the default can change at runtime. `PagesController#show` resolves the path through `PublicSite::Resolver` against `public_paths`, where pages and posts both have rows: a post's URL is its canonical listing page's path plus its own slug (`PublicSite::Paths.canonical_page`) — posts have no page-tree node of their own. An old URL answers a 301 to the current one; a miss, a draft (outside preview) or a trashed record is a 404. `PagesHelper#page_url_path`/`#post_url_path` and `config/sitemap.rb` both mirror the same default-locale-omits-prefix rule when building links — grep for `default_locale` if changing how locales map to URLs. Read the routes.rb comments before touching `format: false` or the locale constraint; there's a documented history of a 500-vs-404 regression here.

### Admin (CS Studio)

Our own admin, mounted at `ContentSpiel::ADMIN_PATH` (`config/initializers/admin_path.rb`, default `cs-studio`, configurable via `ADMIN_PATH`, one URL segment, can't be a reserved path), behind the same session-based auth as the rest of the app (no separate admin auth) plus the permission checks in "Access control and audit" below. Controllers live under `app/controllers/admin/` (`Admin::BaseController` and per-module controllers: `DashboardController`, `PagesController`, `PostsController`, `ContentBlocksController`, `TagsController`, `SettingsController`, `LanguagesController`, `UsersController`, `GroupsController`, `ApiTokensController`, `AuditEventsController`, `AccountsController`, `PasswordsController`, `SessionsController`, `SystemStatusController`, `MindGraphController`, `LinkTargetsController`, `MediaController`, `MediaAssetsController`, `StarterContentsController`, `TrashController`, `TreeController`). Every write goes through a service object (`app/services/`, e.g. `Pages::Save`, `ApiTokens::Issue`), never straight from a controller — see individual services' own comments for authorization and audit-event conventions. `Admin::BaseController#require_permission(key)` gates whole admin areas (403 on refusal); record-scoped controllers load through `AccessControl.scope` instead, so an out-of-scope id 404s; views use the `can?(key, record = nil)` helper (`app/helpers/access_control_helper.rb`) to hide buttons a signed-in user couldn't act on anyway. Views use autosave (`admin--autosave` Stimulus controller, `Admin::AutosaveResponses#autosave_stream`) rather than a submit button for most edits.

CS Studio's start page is the **dashboard** (`Admin::DashboardController#show`, dashboard spec `2026-09-30-dashboard-design.md`), not the pages list: `root to: "dashboard#show"` inside the admin scope, so `admin_root_path` means the dashboard and the pages list moved to its own `admin_pages_path` (`/<admin>/pages`) — every redirect and link that used to mean "the pages list" (the trash's post-move redirect, "back" links, sign-in, setup completion) now points at `admin_pages_path` explicitly. It's open to every signed-in user (`BaseController::MODULES`'s `permission: nil` entry, listed first), including one whose groups hold no grants at all: each list it shows comes from `Dashboard::Feed` (`app/queries/dashboard/feed.rb`), already read-scoped through `AccessControl.scope`/`AccessControl.holds?` the same way every other admin list is, so a user who can read nothing simply sees empty lists rather than a 403. The dashboard has two columns — "Your work" (my drafts, my scheduled items, what I last edited, "mine" meaning `author_id` for a post or, for any record including a page, that its *newest* audit event's actor is me) and "On the site" (what goes live next and what changed recently, site-wide) — plus a quick-create bar (a title + content-type quick draft through `Posts::Save`, "New page", "Upload image"). Every list, including "recently edited by you", is driven by one `LATERAL` join to each record's newest audit event rather than a Ruby-side filter-after-load, so the dashboard still renders in a constant number of queries whatever the data size (a per-list limited query, one batched "newest event per listed record" query, one actor/user preload) — see `Dashboard::Feed`'s own comments for the query shapes. "By <name>" (`Admin::DashboardScreen::RowComponent#changed_by`) reads that newest event's user — a change made through an API token still reads as the token's own user, never the token — and prints the user's **email** (`User` has no name column), "by System" for a nil actor (including one whose user record has since been deleted — the two aren't told apart; the audit log is where that distinction still lives), and nothing at all for a record with no event. "Show all" on a filtered list (Drafts, Scheduled, Going live next) opens the posts list pre-filtered to that status (`admin_posts_path(status:)`) — the only filtered list CS Studio has; it shows every readable post in that state, not just mine.

Every CS Studio and MCP request also runs inside the **site time zone** (`site_settings.time_zone`, default `"UTC"`): `SiteSetting#effective_time_zone` resolves the stored name to an `ActiveSupport::TimeZone`, falling back to UTC for a value that doesn't resolve (a blank or no-longer-valid stored zone) rather than letting `Time.use_zone` raise and 500 every request; `Admin::BaseController` and `McpController` each wrap their actions in `around_action :use_site_time_zone { Time.use_zone(Current.site.effective_time_zone) { ... } }`. That's what lets the existing `Time.zone.parse`/`strftime` call sites (schedule inputs, "Saved HH:MM", the dashboard, the trash and audit screens) show and parse local time without change — storage stays UTC throughout, and MCP's own dates are still emitted as ISO-8601, now with the site's offset rather than always `Z`.

### i18n / Mobility

Translated attributes (`Page#title/slug/subtitle/meta_title/meta_description`, `Post#title/slug/excerpt`, `ContentBlock#caption`) are plain jsonb columns via the Mobility `:jsonb` backend (`config/initializers/mobility.rb`); rich text (`Post#body`, `ContentBlock#body` — pages have none) is the same jsonb backend, one Tiptap/ProseMirror JSON document per locale, via `HasRichTextBody` (see "Rich text" below), not ActionText. Available/default locales are set once in `config/application.rb` (`config.i18n.available_locales`), not in the Mobility initializer, because Mobility needs it at load time to define per-locale accessors. Falls back to `:en` everywhere. Because translated columns are jsonb, `where(slug: ...)` on them is a bug (comparing jsonb to a string) — use Mobility's `.i18n` scope, as the slug-uniqueness validations on `Page`/`Post` do.

### Auth

Custom session-based auth (`app/controllers/concerns/authentication.rb`), not Devise — `has_secure_password` on `User`, signed cookie holds a `Session` id, `Current.session`/`Current.user` per-request. `ApplicationController` requires authentication by default; `PagesController` (the public site) opts out with `allow_unauthenticated_access`. `ApiToken` is a separate `has_secure_password`-backed token model (hashed, revocable) for non-session API access, now bound to one `AccessControl::Group` (`group_id`, not null) that bounds what it may do regardless of its user's own rights — see "Access control and audit" below for what being signed in or holding a token actually permits. Active Storage's own write endpoints (`POST /rails/active_storage/direct_uploads`, the Disk service's `PUT`) require a signed-in session too (`config/initializers/active_storage_access.rb`, 401 otherwise) — the app never uses direct uploads; every upload goes through a CS Studio controller.

### Access control and audit

`AccessControl::Permissions` (`app/models/access_control/permissions.rb`) is a registry like `ContentModel::Registry`/`RichText::Schema`: built-in keys are unprefixed (`posts.read/create/edit/publish/delete`, `pages.read/create/edit/publish/move/delete`, `tags.manage`, `media.upload`, `media.manage`, `settings.manage`, `languages.manage`, `users.manage`, `groups.manage`, `tokens.manage`, `system_status.view`, `audit.view`, `trash.empty` — see `AccessControl::BuiltIns`), plugin keys must be `owner/name`, and a duplicate raises `AccessControl::DuplicatePermission`; registration happens in `config/initializers/types.rb`'s `to_prepare`, alongside the block/content-type/rich-text registries, reset-then-register so a dev reload doesn't double-register. `AccessControl::Group`/`Membership`/`Grant` (tables `access_control_groups`, `access_control_memberships`, `access_control_grants`) carry the actual rights: a group's grants each name a permission key plus a jsonb `scope` limited to `content_types` (array), `page_ids` (array, matched via `page_hierarchies` so a branch grant covers descendants), and `own` (boolean, matched against `Post#author_id`) — grants combine with OR, and every scope key set on one grant must match (AND) for that grant to apply. Four groups are seeded by name (`AccessControl::Seeds::BUILT_IN`, applied by the `SeedAccessControlGroups` data migration and by `db/seeds.rb`'s `ensure_built_in_groups!`): Admin (every registered permission, unscoped), Editor, Author (`posts.edit` scoped `own: true` — note its `posts.read`/`posts.create` are unscoped by design, so a seeded Author can still read every post, not just their own), Read only. Library images have no scopes: `media.upload` uploads, browses and chooses them (pointing a hero or image block at one needs it plus an existing asset, `Media::Choosing`, while clearing needs only the edit right), `media.manage` (Admin and Editor, added to already-seeded groups by `GrantMediaManageToBuiltInGroups`) edits or deletes any of them, and an image's uploader (`created_by_id`) may edit or delete their own with `media.upload` alone (`Media::Ownership` — a token still needs its group to hold `media.upload`). `users.owner` is a separate boolean flag, not a group — an owner is allowed everything regardless of grants, the last owner can't be demoted or deleted (`User`'s own validation), and every user-changing service (`Users::Save`/`Destroy`/`UpdatePassword`, via the shared `Users::OwnerProtection` concern) refuses a non-owner touching an owner's account at all, and refuses managing any user whose groups aren't a subset of the actor's own assignable rights (`#outranked?`) — so `users.manage` is bounded by what you could already grant yourself, never a blanket "any admin may manage any user". The same bound applies to groups: `AccessControl.can_manage_group?(actor, group)` ("may this actor manage this group as it stands" — every grant it holds is one they could hand out) gates removing members or grants (narrowing a grant counts), deleting a group, and changing a user's membership, in `Users::Save`, `Groups::Save` and `Groups::Destroy`. Only a `User` is ever an owner (`AccessControl.owner?`): an `ApiToken` — even an owner's — is judged on its effective rights (group ∩ user) by `can_grant?`/`can_assign_group?`/`can_manage_group?` and the owner-only rules. A grant whose content type is no longer registered is dead (matches nothing, shown unticked in the group editor, dropped on the next save of that group); if nobody has saved the group since, re-registering the content type revives it with its old meaning.

`AccessControl.allowed?(actor, key, record = nil, channel:)` (`app/models/access_control.rb`, delegating to `AccessControl::Checker`) is the one decision point: a subject key (`posts.*`/`pages.*`) requires `record` (nil raises `ArgumentError` — no scope-free allow by omission), an admin-area key ignores it; a `User` is allowed if any of their groups' grants match, an `ApiToken` only if a grant of the token's own group matches *and* its user is separately allowed — the intersection, so a token narrows but never widens its user's rights; a `nil` actor is allowed on the trusted channels `:setup`, `:console`, `:system` (and no channel at all) and denied on `:admin`/`:mcp`/`:public` (`PublicController` sets `:public`; nothing on the public site calls a service or access control today). The setup wizard creates the founding owner through `Users::Save` as that trusted nil actor on `:setup`, and every later step runs as the signed-in owner (`SetupController#act_as_signed_in_user`), so its events are attributed. `.holds?` is the same decision without a record, for nav/buttons only ("does this user hold `posts.edit` anywhere"), never to gate a write. `.scope(actor, key, relation, channel:)` (`AccessControl::Scoping`) narrows a `Post`/`Page`/`ContentBlock` relation to what's readable — used by every CS Studio list, the page tree, link-target/related-post/mind-graph search, `/preview`, and MCP's list/get tools — and `.tree_visibility`/`.preload_branches` exist purely for the page tree's cost profile: ancestors of a readable page are returned separately as `context_only` (greyed out, no actions, so a deep readable page still shows its path to the root), and `preload_branches` loads every listed page's closure-table ancestry in one query so per-row `allowed?` checks in a rendered list cost nothing extra. Everywhere a record could be looked up outside its scope — a CS Studio URL by id, an MCP `get_post`/`update_post`, a preview link — the answer is **not found, not forbidden**: a 404 or tool error, never a 403, so a locked-out record's existence isn't disclosed (one accepted trade-off: the related-posts editor discloses a *count* of hidden relations it can't show, "+N related posts you can't open", without naming them).

Every content, settings, user, group and token write funnels through `ApplicationService` (`app/services/application_service.rb`) — the exceptions are sessions (sign-in/out, audited directly as `session.*` by `Admin::SessionsController`), the `setup_completed_at` marker `Setup.complete!` sets, and derived rows (`public_paths`, closure-table rows) the models maintain themselves: `#authorize!(key, record)` calls `AccessControl.allowed?`; on refusal a service returns `denied(key, record, message: nil)`, which records one `access.denied` audit event (outside the service's own transaction — a rolled-back forged write still leaves exactly one, coalesced, denial) and answers with the fixed message `"You don't have permission to #{permission.label.downcase}"`. `#record_event(action, subject:, field_changes:, metadata:)` is the write side, called inside the transaction so a rollback leaves no trace. `test/services/service_contract_test.rb` enforces this isn't opt-in: it eager-loads every `ApplicationService` subclass and greps its `#call` source for both `authorize!(` and `record_event(`, failing loudly on a service that forgot either (an explicit `# audit: none (reason)` comment is the only escape hatch). One interim rule worth knowing before touching autosave: **editing an already-published record needs `publish`, not just `edit`**, because CS Studio's autosave writes straight to the live record — this goes away once pending revisions (Phase 3 versioning) exist. The converse holds too: a save that changes *only* the publish state (`published`/`published_at`, nothing else) needs only `publish` (`Posts::Save`/`Pages::Save#publish_only?`), so a read + publish "Publishers" group works.

`Audit.record(action, subject:, field_changes:, snapshot:, metadata:)` (`app/models/audit.rb`) is the single write path for the log (`Audit::Event`, table `audit_events`) — reading actor/channel/request id/IP off `Current` rather than taking them as arguments, so a caller can't forge them. `*.updated` and `access.denied` events coalesce (`Audit::Coalescer`): a burst within `Audit::COALESCE_WINDOW` (exactly 10 minutes, measured from the *previous* event's `last_occurred_at`, not `occurred_at`, so a continuous autosave session keeps extending one row for as long as it runs) merges into the open row instead of one row per keystroke pause; everything else stays discrete. Each event carries `field_changes` (old → new per field, named `field_changes` — never `changes`, which `ActiveRecord::Dirty` already owns) and a full `snapshot` of the subject after the change (`Audit::Snapshot`, the version basis Phase 3 versioning will build on) — both scrubbed of secrets twice over (a `NEVER_STORED` list, then a pass through `Rails.application.config.filter_parameters`), so a password digest, token digest, or raw token can never land in the log even if a snapshot serializer dumped raw `attributes`. The table is append-only twice: `Audit::Event` itself refuses any update outside its three coalescing columns and any destroy, and the Postgres trigger `db/triggers/audit_events_append_only.sql` refuses the same at the SQL level (covering `delete_all`/`update_all`/raw SQL too — deliberately not `TRUNCATE`, so `db:truncate_all` still works in development) — reapplied after every schema load, not just every migration, via `config/initializers/db_triggers.rb` hooking `ActiveRecord::Tasks::DatabaseTasks.load_schema`, since `db/schema.rb` itself can't carry a trigger and `db:schema:load`/`db:reset`/parallel test workers' own database copies all bypass migrations entirely. After the writing transaction commits, `Audit.record` publishes `ActiveSupport::Notifications.instrument("audit.content_spiel", event:)` — the plugin hook for anything that wants to react to audit events, never before commit, so a rolled-back write triggers nothing.

### Rich text

`Post#body`/`ContentBlock#body` (via `HasRichTextBody`, `app/models/concerns/has_rich_text_body.rb`) store a Tiptap/ProseMirror JSON document per locale, read back as a `RichText::Document` value object (`app/models/rich_text/document.rb`) and written through `#assign_body` rather than the raw Mobility accessor. Node/mark types (built-ins: `doc paragraph heading bulletList orderedList listItem blockquote codeBlock horizontalRule hardBreak text youtube image` / `bold italic strike code link internalLink`) are declared in the `RichText::Schema` registry (`app/models/rich_text/schema.rb`, `built_ins.rb`) — the plugin seam: plugins register prefixed `owner/name` types, duplicates raise. `Document#validate` checks types/attributes are registered and allowed, enforces the editor's own content model (each node's `content` expression and mark `excludes`, mirrored from the vendored Tiptap extensions — `code` can't combine with another mark, no empty text nodes, a `listItem` starts with a paragraph, no empty quotes/lists; the one deliberate difference is that `doc` may be empty), so nothing the server accepts opens read-only in the editor, and that referenced records (internal links, image `Media::Asset`s -- see "Media library" below) exist; existence checks only block references that are new relative to the locale's *stored* document, so a pre-existing dead reference never blocks an unrelated edit, and validation only re-runs on the locales that actually changed in a given save. `#to_html`/`#to_markdown`/`.from_markdown` convert to/from rendered HTML (via `RichText::HtmlRenderer`, always scrubbed by `RichTextScrubber`) and CommonMark (via `RichText::Markdown`, backed by `commonmarker`); the render cache key (`Rails.cache.fetch`) is `["rich_text", digest, RichText::Schema.version, locale, preview, PublicSite.current_content_version, RichText.code_revision]` — `content_version` is memoised per request on `Current` and bumps whenever anything publishing/renaming/deleting a link or asset target could invalidate a cached render, since a document's own digest only covers the document, not the world its links and images resolve against; `RichText.code_revision` (`KAMAL_VERSION`, else a `REVISION` file, else a value chosen at boot) covers the code, so a renderer or component markup change reaches pages after a deploy instead of Solid Cache serving the old HTML.

MCP (`create_post`/`update_post`/`get_post`) exchanges `body` as Markdown: standard nodes are CommonMark, custom nodes are directives (`::youtube{id="…"}`, `::image{asset="42" alt="…" caption="…"}`) on their own line, and internal links are `[text](cs:page/42)` / `[text](cs:post/7)`. Directives are recognised inside list items and quotes too (`- ::youtube{…}`). Unknown directives are kept as text and reported as warnings, never a hard failure; whatever the Markdown can express but the editor's content model can't (a bold code span, an empty quote) is repaired by `RichText::ContentRepair`, also with a warning. Markdown can't spell an empty paragraph or a trailing hard break, so those two don't survive a round trip; otherwise editor-shaped documents round-trip exactly over `Document#normalized` (which also moves whitespace at the edges of bold/italic/strike runs outside the mark).

The Tiptap editor is vendored under `vendor/javascript` via import maps (`config/importmap.rb`) — no npm, no CDN at runtime. There are two entry points: the public site (and setup/sign-in) imports `application` (Turbo plus the site's own controllers); CS Studio's layout imports `admin` (`app/javascript/admin.js`: `application` plus `controllers/admin/*`). CS Studio's controllers, `rich_text/*`, Tiptap/ProseMirror, SortableJS and D3 are all `preload: "admin"`, so they're modulepreloaded in CS Studio and never on a public page. Re-pinning Tiptap (`bin/importmap pin @tiptap/core @tiptap/starter-kit @tiptap/extension-link ...`) writes the new pins without that option — re-add `preload: "admin"` afterwards (`test/integration/public_javascript_test.rb` catches a miss).

`bin/rails rich_text:migrate_from_action_text` (`lib/tasks/rich_text.rake`) runs `RichText::ActionTextImport`, which orchestrates the conversion of every stored ActionText/Trix body — it never aborts partway and reports counts plus every unmapped fragment — handing each HTML fragment to `RichText::HtmlImport`, the per-fragment HTML → `RichText::Document` converter. The ActionText tables are dropped by a later, guarded migration (`db/migrate/20260928040000_drop_action_text.rb`) that refuses to run while unimported rows remain, unless `FORCE_DROP_ACTION_TEXT=1` overrides the guard.

### Media library

`Media::Asset` (`app/models/media/asset.rb`, table `media_assets` -- Zeitwerk would otherwise demodulize `Media::Asset` down to `assets`, so `self.table_name` is explicit, same as `Media::Usage`/`media_usages` below) is the one place any image enters the app: a `title`, translated `alt`/`caption` (Mobility jsonb, same backend and fallback chain as every other translated attribute), and a `has_one_attached :file` with four named, preprocessed variants (`VARIANT_WIDTHS`: `w480`/`w960`/`w1600`/`w2400`, `resize_to_limit` so none ever upscales, WebP, enqueued right after upload for every allowed type except GIF, which the global rule leaves unresized). `#srcset` only ever lists a variant with a finished `ActiveStorage::VariantRecord` -- never triggers or waits on processing itself -- so a slow, missing or failed transform just means fewer `srcset` entries, never a 500; `<img src>` (`#url`/`#src`) always points at the original regardless, and once there are variants the original is also the widest `srcset` candidate (when its width is known -- a browser never falls back to `src` once `w` descriptors exist). `#alt_text(override:, locale:)`/`#caption_text(override:, locale:)` are the one place the resolution order lives: a rich-text node's single-valued override (a String) wins outright, then this asset's own translation along the fallback chain; a *translated* override (a block's `alt`/`caption`, a page's `hero_alt`) is passed whole as its `{locale => value}` jsonb (`read_attribute`, not `translated(...)`) and interleaved per locale -- the override in a locale, then the asset in that locale, then the next locale -- so an override written in another language never beats the asset's default in this one. A page hero, an image block and a rich-text `image` node all call through these rather than reading `alt`/`caption` directly, and `Media::PictureComponent` (`app/components/media/`) is the one place every image render builds its `<img srcset sizes>` tag from (lazy by default; the page hero passes `loading: "eager", fetchpriority: "high"`). Allowed types are png/jpeg/gif/webp, byte-sniffed against the actual bytes (never a client's Content-Type header or filename), max 10 MB -- SVG stays refused everywhere, and the site logo stays its own separate `SiteSetting` attachment outside the library (moving it in, with the SVG sanitising that would need, is tracked in the roadmap, not built).

Three places reference a library asset -- `pages.hero_media_asset_id`, `content_blocks.media_asset_id` (both plain FKs to `media_assets` -- default NO ACTION, not `on_delete: :restrict`: Postgres 18 reports a RESTRICT violation as SQLSTATE 23001, which Rails doesn't map to `ActiveRecord::InvalidForeignKey`, so every `rescue` of it would miss; `MediaForeignKeysNoAction`) and a rich-text `image` node's `asset_id` (`RichText::BuiltIns`) -- and `Media::Choosing` (shared by `Pages::Save`/`ContentBlocks::Save`) is what lets *choosing* one need `media.upload` and an existing asset id while *clearing* it needs only the ordinary edit right already being checked, refusing a forged or nonexistent id as a validation failure on the field the editor sees rather than letting it reach Postgres as an FK-violation 500 (an asset deleted between that check and the write still hits the FK; `Pages::Save`/`ContentBlocks::Save`/`Posts::Save` rescue `ActiveRecord::InvalidForeignKey` into the same "doesn't exist" failure, `Media::Choosing#vanished_media_failure`). Embedding an image that's already in the library in *rich text* needs no `media.upload` -- it's content editing, covered by the right to edit the post or block, and only the asset's existence is validated (`RichText::BuiltIns`' `image` node); uploading a new image, and browsing the library in the picker, do need `media.upload`. Where an asset is actually used is entirely derived, never hand-maintained: `Media::Usage`/`Media::UsageIndex` (`app/models/media/`, table `media_usages`, unique on `(media_asset_id, owner_type, owner_id, role, locale)` with `nulls_not_distinct: true` so two rows that both have a nil `locale` still collide as "the same usage" instead of silently duplicating) rebuilds one owner's (`Page`, `ContentBlock` or `Post`) *entire* set of rows at once -- delete-then-reinsert, never an incremental diff -- from inside the same save/destroy service transaction that changed it; `bin/rails media:reindex` (`Media::UsageIndex.rebuild_all`) recomputes the whole table any time it's suspected stale (a bug, a direct SQL edit, a restored backup). `Media::Asset#used?`/`#usages_summary` read this table to back the library's "Unused" filter and a detail panel's "Used on" list, and it's the database's own FK -- not this table -- that's the actual guarantee behind "can't delete an asset that's in use" (`Media::Destroy`). Editing or deleting needs `media.manage` (seeded onto Admin and Editor) or, via `Media::Ownership`, being the asset's own uploader with `media.upload` alone -- see "Access control and audit" above for the full permission story, including how a token is judged.

CS Studio's own Media module (`Admin::MediaController`, `Admin::MediaLibrary::GridComponent`/`DetailComponent`) is the grid/search/detail/multi-file-upload home, searched through `Media::Search` (title, alt in any locale, and filename, one bound `:q` reused across all three ILIKEs -- shared with MCP below so both search the library the same way); `Admin::MediaAssetsController` is a separate, narrower upload-only JSON endpoint for `Media::PickerComponent` (`app/components/media/`, the one modal dialog that every hero/image-block field -- via `Admin::Columns::MediaColumnComponent` -- and the Tiptap editor's Image button open) -- two unrelated callers sharing `Media::Upload`, not one feature split across two endpoints. MCP exposes the library read-only as `list_media_tool`/`get_media_tool` (`app/mcp/mcp/tools/`), paginated the same "about 50 per call" way as the rest of MCP's list tools. `db/migrate/20260929050000_move_images_into_media_library.rb` moved every legacy `Page#hero_image`/`ContentBlock#image` Active Storage attachment into this one storage path -- deduping identical files by blob checksum, recording which assets it created in a ledger table (`media_library_migrated_assets`, so its own `down` can roll back cleanly without touching a pre-existing or later-uploaded asset), leaving in place (and reporting, never silently dropping) any attachment whose blob type the library refuses, and adding the `rich_text` usage rows for bodies that already embedded a library image (rich-text uploads and ActionText-imported images predate the index; without those rows such an image reads as "Unused" and can be deleted -- a rich-text reference has no FK). `20260929070000_backfill_rich_text_media_usages.rb` runs that same additive, idempotent SQL for databases that ran the move before it did, and `RichText::ActionTextImport` refreshes each owner it writes. `bin/rails media:orphans` lists (and, with `CONFIRM=1`, purges) blobs with no attachment at all -- duplicates that migration deliberately never deleted, plus ActionText leftovers -- and `bin/rails media:variants` re-enqueues whichever of a non-GIF asset's four named variants still has no `VariantRecord` (a failed or lost job, an asset that predates a width), idempotent since it only ever looks at what's actually processed, never at what's currently queued. Interim state: until a variant has actually been processed, a page serves the original file at full size. `ActiveStorage::VariantRecord`'s own max id/count feed `PublicSite.content_version` (see "Rich text" above) -- a newly processed variant is exactly the kind of change that can make a page's already-cached render worth invalidating.

### Trash

Pages, posts and library images are soft-deleted (spec `docs/superpowers/specs/2026-09-29-trash-design.md`); a single block, a tag, a group, a user or a token is still deleted for good. Columns: `trashed_at` (indexed) and `trashed_by_id` (FK to `users`, `on_delete: :nullify`) on `pages`/`posts`/`media_assets`, plus `pages.trash_root_id` (FK to `pages`, `on_delete: :nullify`) naming the page an editor actually picked, and `site_settings.trash_retention_days` (default 30, `0` = never purge automatically, edited in CS Studio's Settings module). `Trashable` (`app/models/concerns/trashable.rb`) gives `kept`/`trashed` scopes and `#trashed?` -- deliberately **no `default_scope`**, which would silently hide rows from closure_tree, uniqueness checks, associations and the Trash screen itself. Hiding is explicit instead, at the narrowing points: `AccessControl.scope` (kept only unless called with `trashed: true`, which only the Trash screen does -- so every CS Studio list, the tree, pickers, `/preview`, MCP and the "not found, not forbidden" id lookups inherit it), `PublicSite::Resolver` (and its listing-page fallback), `listed_posts`, navigation, internal-link rendering (a link to a trashed page or post renders as plain text), the sitemap, the related-posts editor, the media library/picker/search, `Media::Choosing` and rich-text image validation (a trashed image reads as missing), and MCP's post and media tools. `test/integration/trash_visibility_test.rb` pins every one of them with a kept-vs-trashed pair; a new list, search, picker or public query over pages, posts or images belongs in it. URLs are freed through `PublicSite::Paths` itself, not by any trash code: `compute_path` returns nil for a trashed record and `canonical_page` ignores listing blocks on trashed pages, so saving a changed `trashed_at` deletes (on trash) or rebuilds (on restore) the record's `public_paths` rows -- redirects included, not recreated on restore -- through the ordinary model callbacks, and nothing (`rebuild!`, `sync_posts`, a save elsewhere) can resurrect a trashed record's URL. The public site answers 404 for a trashed page or post, not 410. `Page::TreeRanking` counts kept siblings only, so "move to rank N" means rank N among the pages an editor can see.

Four services (`app/services/trash/`), all `ApplicationService`s, audited as `page|post|media.trashed/restored/purged` and `trash.emptied`. `Trash::Move` trashes a page with its whole kept branch (descendants flagged with `update_all`, one shared timestamp and `trash_root_id`, root saved last so a single `sync_subtree` pass sees them trashed; a descendant already trashed on its own keeps its own root) -- the root saved with `save!(validate: false)`, callbacks still running, so a record that has gone invalid since its last save (an unregistered content type, a reserved slug) can still be cleared away, while `Trash::Restore` keeps full validation -- and refuses an image while a *kept* page or post still uses it (`Media::Asset#used_by_kept_owner?`) -- which is what makes it safe that rich-text image rendering never looks at an asset's trash state. `Trash::Restore` brings back exactly the pages sharing the root's `trash_root_id`; a page trashed as a branch member comes back only with its root, or alone under a new `parent:` (same checks as `Pages::Move`: `pages.move` on the page, `pages.create` under the target, never itself or a descendant; the CS Studio picker is a server-rendered `<select>` of pages scoped on `pages.create`). Slugs were free while in the trash, so a slug taken in the meantime moves to the first free `-2`, `-3`, ... suffix, per locale (taken in `de` but free in `en` changes only `de`). Restoring a page or post also restores every trashed library image its hero, blocks or bodies still reference, each with its own `media.restored` event (metadata `restored_with`), so a restored page never points at a trashed image; a page's own `page.restored` lists the branch members that came back in `restored_page_ids` (mirroring `page.trashed`'s `descendant_ids`). A refusal that names a branch's root names it by title only when the actor may read it (`Trash::ItemPermissions#branch_root_name`), "the page it was moved to the trash with" otherwise. `Trash::Purge` is the permanent delete `Pages::Destroy`/`Posts::Destroy`/`Media::Destroy` used to be: a page takes its whole subtree deepest first (all of it must be trashed), recording one `page.purged` per destroyed page -- the root's listing the rest in `descendant_ids`, each descendant's naming the root in `purged_with` -- and is refused for a member of another page's still-trashed branch -- purge the root instead; an image goes only once no usage row at all points at it (trashed owners included), an FK violation becoming an ordinary failure, the file purged after commit. `Trash::Empty` runs `Purge` over `Trash.roots` (page branches, then posts, then images -- so an image's trashed owners are gone first), each item in its own savepoint, reporting what it skipped -- an exception out of one item's purge is rescued into a skip ("Couldn't be deleted: <class>"), so the rest still go and `trash.emptied` is still recorded; the retention job rescues and logs the same way. Permissions (`Trash::ItemPermissions`): moving, restoring or purging one item needs its ordinary delete right (`pages.delete`/`posts.delete` with their scopes, or for an image `media.manage` / uploader with `media.upload`); `trash.empty` (Admin only) empties everything **and** permits purging any single trashed item, never moving or restoring. `Trash::PurgeExpiredJob` (`app/jobs/trash/`) purges roots older than the retention period via `Trash.each_root(trashed_before:)` (re-finding each root at its turn, so a subpage already swept by an ancestor's branch purge isn't purged twice), as the trusted nil actor on the `:system` channel; it's scheduled in `config/recurring.yml`, which only runs where Solid Queue is the adapter (production -- development and test use the default adapter, so nothing purges on its own there).

CS Studio: `Admin::TrashController` (`/cs-studio/trash`) lists page branch roots ("+N subpages"), posts and images newest first, 50 per page, loaded only through `AccessControl.scope(..., trashed: true)` on the delete right (so an id the viewer can't act on is a 404), with Restore, Delete permanently and Empty trash behind `Admin::ConfirmDialogComponent`. The editors' delete buttons are "Move to trash" now, and the flash (`Admin::FlashComponent`) offers Undo. Its components live under `Admin::TrashScreen::`, never `Admin::Trash::` -- see "Key Conventions".

### SEO / sitemap

`config/sitemap.rb` (gem `sitemap_generator`) walks the published page tree across all locales; built via `rake sitemap:create`, output to `public/sitemap.xml`.

## Key Conventions

- **No RSpec** — Minitest + fixtures (`test/fixtures/`), not factories.
- **No Devise / no ActiveAdmin** — auth and admin (CS Studio) are both hand-rolled as described above; don't reach for those gems' idioms.
- **No npm/webpack** — JS is import-maps only (`importmap-rails`); CSS is Tailwind via `tailwindcss-rails` (`bin/rails tailwindcss:watch` in dev).
- **Long, load-bearing code comments are the norm in this codebase**, especially in `page.rb`, `content_block.rb`, `post.rb`, and `routes.rb` — they document non-obvious invariants and past incidents (e.g. the Accept-header 500, the two-pages-one-URL collision). Read them before changing the code they annotate, and match that density when adding similarly non-obvious logic; don't strip them out during cleanup.
- **Never define `Admin::Media` or `Admin::Trash`** — either module would shadow the top-level `Media`/`Trash` namespaces (models and services) for every bare `Media::`/`Trash::` reference lexically inside `module Admin`, a `NameError` that has already shipped once mid-task. That's why the media library's admin components are `Admin::MediaLibrary::` and the Trash screen's are `Admin::TrashScreen::`; `test/lib/admin_media_namespace_test.rb` and `test/lib/admin_trash_namespace_test.rb` guard both.
- **Design docs**: `docs/superpowers/specs/` and `docs/superpowers/plans/` hold the original design specs and implementation plans this app was built from — useful background when a change touches the page tree or content blocks.
