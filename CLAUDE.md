# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

ContentSpiel is a Rails 8.1 CMS: a page-tree-driven public website plus CS Studio, its own admin. Content editors build pages out of ordered content blocks (rich text, images, post listings), organize them in a tree, and the same tree drives navigation, routing, and the sitemap. Rich text is Tiptap/ProseMirror JSON. Everything is translated into three locales (en/de/es) via Mobility.

## Setup & Commands

```sh
docker compose up -d          # Postgres 17, published on host port 5433 -- start this first
bin/setup --skip-server       # installs gems, prepares dev + test databases
bin/rails db:seed             # creates a development admin account (dev only, see db/seeds.rb)
bin/rails server               # or `bin/dev`, which runs server + `tailwindcss:watch` (see Procfile.dev)
```

- App: http://localhost:3000
- Sign in: http://localhost:3000/cs-studio/sign-in (`<ADMIN_PATH>/sign-in`)
- Admin (CS Studio, behind the same sign-in): http://localhost:3000/cs-studio (`ContentSpiel::ADMIN_PATH`, configurable via `ADMIN_PATH`)

**Tests:** `bin/rails test` (full suite, minitest). Single file: `bin/rails test test/models/page_test.rb`. Single test: `bin/rails test test/models/page_test.rb -n test_method_name` or `bin/rails test test/models/page_test.rb:42` (line number). System tests (Capybara on Cuprite, headless Chrome) are separate: `bin/rails test:system`; run `bin/rails tailwindcss:build` first, and on a laptop cap the workers (`PARALLEL_WORKERS=6 bin/rails test:system` — twelve flakes under load). On macOS prefix every test command with `PGGSSENCMODE=disable`: a parallel run can otherwise crash a forked worker in the pg gem and hang forever. `test/application_system_test_case.rb` prepends `StaleNodeAtOnce` to Cuprite's nodes so a poll whose element died in a Turbo visit fails at once instead of spending half a second per element — that is what made toasts that had come and gone look "missing". Two more rules for a system test: a link into the `#content` frame is promoted by Turbo to a page visit a few dozen milliseconds after the frame has rendered, and a form pressed in that gap is sent (the server does the write) but its answer is dropped when the visit starts — so after clicking such a link (a media tile, a trash tab, a list row) wait for `turbo:load` before pressing anything (`click_tile` in `test/system/admin/media_library_test.rb`, `click_tab` in `test/system/admin/trash_test.rb`); and a test that resizes the window puts the size back, because the browser is shared with the tests that follow. A test never waits for an element that only a `hover:` style reveals (the CI browser reports it can't hover): click it with `visible: :all`.

A local run is quiet: what tests themselves print (the statements a migration test runs, the seed file's "Seeded dev accounts" lines) is swallowed, and shown only for a block that fails. `VERBOSE=1 bin/rails test` prints all of it, and CI always sets `VERBOSE` (`TestOutput` in `test/test_helper.rb`; a test that prints wraps the call in `TestOutput.quietly { ... }`).

Coverage is on request: `COVERAGE=1 bin/rails test` (SimpleCov, line and branch) writes `coverage/index.html`, which `bundle exec simplecov open` shows; the parallel workers' results are merged into the one report. It is off by default, since a run of one file would report a meaningless few percent. CI turns it on for the unit suite and keeps the report as the `coverage` artifact. There is no minimum yet, so a drop doesn't fail a run.

**Lint/scan** (all run in CI, see `.github/workflows/ci.yml`):

## Architecture

### The page tree

`Page` (`app/models/page.rb`) is a `closure_tree` (gem `closure_tree`), backed by a `page_hierarchies` closure table, with exactly one root (the homepage, enforced by `only_one_root_page` and, as a database backstop, the partial unique index `index_pages_on_single_root`). `page_type` is an enum with `validate: true`, so a forged value is an ordinary validation failure on the field, not an `ArgumentError`. Sibling order is the `position` column; closure_tree renumbers it, but reordering ("type a new position number" -- there is no drag-and-drop) is implemented on top of that in `remember_requested_position`/`place_among_siblings` because closure_tree's own renumbering doesn't do what a literal "move to rank N" UI needs.

Every public URL is precomputed and stored: the `public_paths` table (`PublicPath`, one row per record per locale, `current: true` for the live URL and `current: false` for the redirects an old URL leaves behind) is derived by `PublicSite::Paths` from model callbacks (`HasPublicPaths`), never written by hand -- a page save resyncs its whole subtree (`sync_subtree`), since a slug change on an ancestor shifts every descendant's URL, plus every post its listing blocks give a URL to. The public router (`PagesController#show`) asks `PublicSite::Resolver` for a URL, which is a single indexed lookup in that table plus the visibility rule (`:published`, or `:preview` for signed-in editors) rather than a walk of the tree per request; `PublicSite::Urls` builds links the other way round. Sibling ranking lives in `Page::TreeRanking` (`app/models/page/tree_ranking.rb`). Read the extensive comments in `page.rb`, `public_site/paths.rb` and `tree_ranking.rb` before changing any of this -- the two-pages-one-URL and nil-position footguns they guard against are non-obvious and previously shipped as bugs (see commit `da80c58`).

### Content blocks

`ContentBlock` (`app/models/content_block.rb`) is one polymorphic-by-enum table (`block_type`: `rich_text` / `image` / `post_list`) belonging to a `Page`, ordered by `position`, edited in CS Studio as block cards, each its own autosaving form (see "Blocks" under the design system). `Post` uses the same single-model-plus-enum shape for its own `content_type` (`blog` / `resume_entry` / `now_update`). A `post_list` block's `settings` jsonb names a `content_type` filter, a `tag`, and a `limit`; `listed_posts` is the canonical query both the listing partial and the permalink-resolution fallback in `PagesController` must agree on. A post's typed fields (`Post#fields`) name themselves in words wherever an error shows — `Post.human_attribute_name` turns `fields.speakers.0.name` into "Speakers, row 1: name" (without I18n lookup, so the German admin UI will need to revisit it) — and a typed date must be `yyyy-mm-dd` (`ContentModel::FieldSet::DATE_FORMAT`): free text that doesn't parse is *refused* on the field rather than silently wiping the stored date.

### Public routing

Routes: `config/routes.rb`. Two catch-all routes, declared last (named routes like `/cs-studio`, `/mcp`, `/up` must win first; the unprefixed catch-all also skips `/rails/active_storage/...`, whose routes Rails draws after this file): `get ":locale(/*path)"` for an explicit locale prefix (`/de/about`), and `root`/`get "*path"` for no prefix at all (served in `SiteSetting#default_locale`, editable in CS Studio's Settings module, checked per request — not a code-level default). `PagesController#redirect_default_locale_prefix` 302s an explicit prefix that happens to name the *current* default locale to the unprefixed URL, so each page has exactly one canonical address even though the default can change at runtime. `PagesController#show` resolves the path through `PublicSite::Resolver` against `public_paths`, where pages and posts both have rows: a post's URL is its canonical listing page's path plus its own slug (`PublicSite::Paths.canonical_page`) — posts have no page-tree node of their own. An old URL answers a 301 to the current one; a miss, a draft (outside preview) or a trashed record is a 404. `PagesHelper#page_url_path`/`#post_url_path` and `config/sitemap.rb` both mirror the same default-locale-omits-prefix rule when building links — grep for `default_locale` if changing how locales map to URLs. Read the routes.rb comments before touching `format: false` or the locale constraint; there's a documented history of a 500-vs-404 regression here.

### Admin (CS Studio)

Our own admin, mounted at `ContentSpiel::ADMIN_PATH` (`config/initializers/admin_path.rb`, default `cs-studio`, configurable via `ADMIN_PATH`, one URL segment, can't be a reserved path), behind the same session-based auth as the rest of the app (no separate admin auth) plus the permission checks in "Access control and audit" below. Controllers live under `app/controllers/admin/` (`Admin::BaseController` and per-module controllers: `DashboardController`, `PagesController`, `PostsController`, `ContentBlocksController`, `TagsController`, `TagSuggestionsController`, `SettingsController`, `LanguagesController` (the Languages card's instant actions only; there is no Languages screen), `AiKeysController`, `UsersController`, `UserSuggestionsController`, `GroupsController`, `ApiTokensController`, `AuditEventsController`, `AccountsController`, `PasswordsController`, `SessionsController`, `SystemStatusController`, `TranslationsController`, `TranslationConfirmationsController`, `MindGraphController`, `LinkTargetsController`, `JumpController`, `MediaController`, `MediaAssetsController`, `StarterContentsController`, `TrashController`, `TreeController`). Every write goes through a service object (`app/services/`, e.g. `Pages::Save`, `ApiTokens::Issue`), never straight from a controller — see individual services' own comments for authorization and audit-event conventions. `Pages::Save` and `Posts::Save` take only the keys in their `ATTRIBUTES` lists in `attributes:`; any other (`parent_id`, `position`, the trash columns, a translated attribute) raises `ArgumentError`, because moving and trashing belong to `Pages::Move` and `Trash::Move`. `Admin::BaseController#require_permission(key)` gates whole admin areas (403 on refusal, rendered inside the CS Studio layout, never a bare error page); record-scoped controllers load through `AccessControl.scope` instead, so an out-of-scope id 404s; views use the `can?(key, record = nil)` helper (`app/helpers/access_control_helper.rb`) to hide buttons a signed-in user couldn't act on anyway. Content views use autosave (`admin--autosave` Stimulus controller, `Admin::AutosaveResponses#autosave_stream`) rather than a submit button, configuration screens an explicit Save; "The save rule" below says which is which and how a stale save is refused.

CS Studio's start page is the **dashboard** (`Admin::DashboardController#show`, dashboard spec `2026-09-30-dashboard-design.md`), not the pages list: `root to: "dashboard#show"` inside the admin scope, so `admin_root_path` means the dashboard. The Pages module is at `/<admin>/pages`, which is not a list but a redirect: `Admin::PagesController#index` sends a viewer who can open Home to Home's editor (303, the editing language kept, the flash kept) and otherwise shows the empty state "Choose a page from the tree" beside the tree; `Admin::BaseController#pages_landing_path` is the same decision for every redirect that used to mean "the pages list" (the trash's post-move redirect, starter content, a page's own delete). Sign-in and setup completion deliberately land on `admin_root_*`, the dashboard. It's open to every signed-in user (`BaseController::MODULES`'s `permission: nil` entry, listed first), including one whose groups hold no grants at all: every list it shows is already read-scoped through `AccessControl.scope`/`AccessControl.holds?` the way every other admin list is, so a user who can read nothing simply sees empty cards rather than a 403. The page is a quick-create row (`Admin::DashboardScreen::QuickCreateComponent`: a title, a type select and "Create draft" — a post draft through `Posts::Save`; choosing "Page" opens the New page dialog with the title carried over instead of creating anything), three cards in an auto-fit grid — "Your drafts" and "Going live next" from `Dashboard::Feed` (`app/queries/dashboard/feed.rb`, at most five rows each, "→" to the posts list filtered by `scope=drafts|scheduled`), and "Needs translation" from `Dashboard::TranslationNeeds` (per target language the viewer's readable pages, posts and — for a `media.upload` holder — images from `Translations::StateIndex.summary`, plus the most recently changed outdated item; hidden with one language) — and then **Recent activity** (`Dashboard::Activity`), with a link to the full audit log for `audit.view`. "Mine" in the drafts card means `author_id` for a post or, for any record including a page, that its *newest* audit event's user is me — "newest" ignoring `access.denied` (a refused attempt is no change, `Dashboard::Feed::NOT_A_CHANGE`) and, for a page or post, also counting events about any content block it currently owns, since editing a block is editing its owner. It is decided in SQL by one `LATERAL` join to each record's newest audit event rather than a Ruby-side filter-after-load, so each list stays one query per model whatever the data size.

**Recent activity** is the newest *content* audit events (pages, posts, blocks, library images; never `access.denied`, `session.*`, `user.*`, `group.*`, `token.*` or `settings.*`; the allow-list is `Dashboard::Activity::ACTIONS`), one sentence each — "<name> published “<title>”" with the title linking to the record's editor (`Admin::DashboardScreen::ActivityRowComponent`) — looking back `Dashboard::Activity::WINDOW` (90 days). The read scope is applied *in the event query itself* (`audit_events.subject_id IN (readable ids)` per subject type, a block event through its readable owner, images for a `media.upload` holder), never by over-fetching and filtering in Ruby, which under-filled the feed and leaked how much hidden activity there was; a record the viewer can't read, a trashed one or a deleted one leaves no row at all ("not found, not forbidden"), a trashed record's whole history disappearing with it until it is restored. `index_audit_events_on_recent` serves the `ORDER BY last_occurred_at DESC` scan. The query returns data only: a `Dashboard::Activity::Row` is `(event, record, sentence, at, span_end)`, the sentence an `Audit::Sentence` (see the audit log below) whose actor is facts, not a name — the viewer ("You"), a user, a `user_id` that names nobody any more, or nobody — and `ActivityRowComponent` hands it to `Admin::AuditScreen::SentenceComponent`, which is where a user is named, through `Admin::UserNameComponent` (the one place CS Studio names a user): the `display_name`, "a deleted user" when `user_id` names a user who no longer exists (`audit_events` has no FK on it; a token event whose user is gone reads the same), "System" only for an event with no user at all. A change made through an API token shows its *user* (round avatar) "via <token name>" beside an MCP chip (`Admin::ChannelChipComponent`, which draws an unknown channel as a plain chip and nothing for none), the name being the `audit_events.actor_label` written when the event was recorded (`Audit::Event#via_label`; it survives the token being deleted, and an event recorded before tokens had names reads "via an API token"), the token itself never loaded. A coalesced burst shows the time it last extended, the whole span as its tooltip.

**The audit log** (`Admin::AuditEventsController`, `audit.view`, never content-scoped) tells every event as one sentence through `Audit::Sentence` (`app/models/audit/sentence.rb`: plain data -- actor facts, parts, a route name + params for the subject, a `security` flag -- never markup or a component; `Admin::AuditScreen::SentenceComponent` draws it), the dashboard's feed words its rows through the same class so the two can't differ. A sentence for an action outside `Audit::Sentence::ACTIONS` (a plugin's) is the generic "<actor> did <action> on <subject>"; the actions in `Audit::Sentence::SECURITY_ACTIONS` (a failed sign-in, a refusal, an owner change, a token issued or revoked, a user or group deleted) carry the `security` flag, and the row draws their key in warn ink. `test/models/audit/sentence_test.rb` greps `app/` for every recorded action name and fails for one without a sentence (interpolated and variable call sites are listed explicitly there). A subject links only when the viewer may open it, decided for the whole page of events in a bounded number of queries (`Audit::Sentence::Targets`); an unreadable, trashed or deleted one is the label the event stored, as plain text, and a failed sign-in never echoes the attempted address. The list is `last_occurred_at DESC, id DESC` under day headers in the site time zone (`Admin::AuditScreen::DayListComponent`), filtered by `Audit::Filter` (user, action, type, channel, a `range` preset or custom `from`/`to`, a `subject_type`+`subject_id` chip; junk is "all"), "Load older" over `offset` (it replaces the page; "Newer" goes back). A coalesced row shows its span ("16:05–16:31", `Admin::AuditScreen::TimeSpan`), and `audit_events.occurrences` (1, incremented by `Audit::Coalescer` each time an event merges into the row) is the "N saves" on the event page. The event page (`EventHeaderComponent`, `ChangesComponent`) shows field changes as word diffs per language (`Translations::SourceDiff` drawn by `Admin::WordDiffComponent`, shared with the translation reference card), "Changed" for a body, and Older/Newer through the same filtered order; an id outside the filters is a 404. Components live under `Admin::AuditScreen::`, never `Admin::Audit` (`test/lib/admin_audit_namespace_test.rb`).

Every CS Studio and MCP request also runs inside the **site time zone** (`site_settings.time_zone`, default `"UTC"`, stored as a Rails zone name — an IANA identifier like `"Europe/Berlin"` is normalised to its Rails name on save, because the Settings select's option values are Rails names and every Save resends the whole form; the select also always lists the stored value, so a value written around the model is resent unchanged rather than replaced by the first option): `SiteSetting#effective_time_zone` resolves the stored name to an `ActiveSupport::TimeZone`, falling back to UTC for a value that doesn't resolve (a blank or no-longer-valid stored zone) rather than letting `Time.use_zone` raise and 500 every request; `Admin::BaseController` and `McpController` each wrap their actions in `around_action :use_site_time_zone { Time.use_zone(Current.site.effective_time_zone) { ... } }`. That's what lets the existing `Time.zone.parse`/`strftime` call sites (schedule inputs, "Saved HH:MM", the dashboard, the trash and audit screens) show and parse local time without change — storage stays UTC throughout, and MCP's own dates are still emitted as ISO-8601, now with the site's offset rather than always `Z`. The public site (and `/preview`) still renders dates in UTC — tracked in the roadmap, since it needs the render cache to vary on the zone.

#### CS Studio design system

The design pass (spec `docs/superpowers/specs/2026-10-03-cs-studio-design-pass-design.md`, handoff in `docs/design/cs-studio-handoff-v3/`) rebuilt CS Studio's shared parts. Where the spec and the handoff disagree, the spec wins; from the handoff's CSS only `--cs-chrome` and `--cs-cat-1…6` (with their `--color-*` mappings in `app/assets/tailwind/content-spiel.tailwind.css`) were taken, everything else keeps the repo's own tokens. `test/lib/admin_design_rules_test.rb` pins the rules that are easy to break one innocent edit at a time: no raw colour literal (hex of any length, `rgb()`/`hsl()`) and no `dark:` variant other than `dark:scheme-dark` in `app/views/{admin,layouts,setup}`, `app/components/admin` or `app/javascript/controllers` (a colour is a token, and tokens already switch with the theme); translation chips and language tabs never mention `danger` (translation states are never red; red is for destruction and failure only); and the replaced components (and `Translations::CachedStatus`) stay deleted, with `danger_outline` appearing nowhere under `app/`. The namespaces that would shadow top-level modules stay forbidden (see "Key Conventions").

**Shared components** (each has a Lookbook preview in `test/components/previews/admin/` and a test in `test/components/admin/`), and what each replaced:
- `Admin::StatusChipComponent` (Draft / Scheduled / Live chip with a glyph and an `aria-label`; Live draws no chip in the page tree) replaced `StatusBadgeComponent`; `Admin::TranslationChipComponent` replaced `TranslationScreen::StateBadgeComponent`; `Admin::LanguageTabsComponent` replaced `LanguageSwitcherComponent`. Colour is never the only cue.
- `Admin::ContentTypeDotComponent` marks a content type with a dot (indexes 1–6 filled, 7–12 rings, then cycling) next to its name; the index is `colour_index` on `ContentModel::ContentTypeDefinition`, defaulted by `Registry#register` to the smallest unused one.
- `Admin::DialogComponent` / `Admin::ConfirmDialogComponent(destructive:)` and `Admin::DialogHelper#dialog_trigger` replaced the old confirm dialog and every inline `onclick`. The `admin--dialog` controller lives on `<body>`: a `mousedown` handler (`remember`) records where a press began and a `click` handler (`backdrop`) closes only when it began *and* ended on the backdrop, so a text selection dragged out of a dialog doesn't close it. Dialog forms and the media picker live once in the layout, outside `#content` (forms can't nest). There are no inline event handlers: `test/lib/inline_handlers_test.rb` fails on any view or component that uses one of the events it lists — wire behaviour through `data-action`. That test is the whole enforcement. The app's CSP (`config/initializers/content_security_policy.rb`) sets only `frame-src` (self and youtube-nocookie.com), `object-src 'none'` and `base-uri 'self'`; there is no `script-src` and no nonce, so the browser itself refuses no script (a script CSP is a roadmap row). `Admin::DialogComponent`'s `hang: true` hangs a dialog from a fixed top edge instead of centring it, for one whose height changes while it is open (New page, New post; the media picker does the same through `.admin-media-picker`), so nothing moves under the pointer when its content arrives.
- `Admin::ButtonComponent` variants: `primary`, `secondary`, `ghost`, `danger` (solid red, a dialog's destructive confirm only) and `danger_text` (a secondary button whose label alone is red: the trigger of a destructive action outside a dialog; it replaced the red-outline `danger_outline`). `size: :small` is the compact button of an inline box.
- `Admin::CheckboxComponent` is the one checkbox (`.cs-checkbox`: accent fill, 2px radius, a visible focus ring) — the user and group forms and the permission matrix all use it; it is still a plain `<input type=checkbox>`, so a form posts what `check_box_tag` did.
- Toasts replaced `Admin::FlashComponent`: `Admin::ToastRegionComponent` renders `#toasts` in the layout (deliberately not `data-turbo-permanent`, so a toast never survives into the next page), and `Admin::ToastComponent` is one toast. `flash[:notice]` is a success toast, `flash[:alert]` an error, `flash[:warning]` a warning (never auto-hides, like an error; a bulk action that did some posts and refused or failed others says so this way, naming the failures, and keeps its Undo), and `flash[:undo]` (`{ "label" =>, "url" => }`, JSON-encoded by the session; rendered as a `button_to` POST, never a GET link, because every follow-up is a write) an Undo toast that stays 8 s, while errors and warnings never auto-hide; a Turbo Stream answer uses the `toast_stream` helper, which appends to `#toasts`. A toast never comes back from Turbo's page cache: `admin--toast` strips toasts from any render that comes out of the cache (a preview or a Back/Forward restoration) — not `data-turbo-temporary`, which Turbo implements by deleting the element from the live page on every cached snapshot, a promoted frame navigation included, so a just-relayed toast would vanish. The autosave error toast is one per form: it carries the id `toast-<error prefix>`, a failed autosave replaces it and the next successful one removes it. A frame request inside `#content` gets "relay" toasts, because `#toasts` sits outside the frame. Page moves and block reorders offer Undo this way. `Admin::MenuComponent` / `admin--menu` is the one dropdown (the rich-text toolbar's Insert menu, row actions); `admin--busy` disables a submitting button and shows its busy state.
- Lists: `Pagination` (`app/models/pagination.rb`; page 1 for any junk in `?page=`, an out-of-range page reported rather than clamped) with `Admin::PaginationComponent`; `Admin::TimeAgoComponent` ("just now", "1m ago"; the exact time is the tooltip); `admin--auto-submit` for filter forms (type, choose, the list updates — no button), `Admin::ListLinksHelper#list_params` so links keep the active filters; an in-card `Admin::EmptyStateComponent`. The posts list, the Trash and the Translations matrix paginate the same way, 50 a page.
- Form controls: `.cs-select` (via `setup_select_class`; the chevron is for a drop-down only, a `multiple` select keeps its native list), `Admin::FileDropComponent` (+ `controllers/file_drop_controller.js`), `Admin::PrefixInputComponent` (the slug's `/de/` prefix, no double slash), `Admin::PasswordFieldComponent` (+ `controllers/password_field_controller.js`, show/hide and a strength meter), `Admin::ErrorSummaryComponent`, and `Admin::ChipInputComponent` (+ `admin--chip-input`). The chip input is a multi-value field with autocomplete — the post editor's tags and related posts, a post-list block's tag filter (`single: true`): the form's source of truth is real controls, one hidden input per chip (`post[tag_names][]`) plus a blank sentinel ahead of them so an emptied list still submits and saves as empty, and typing in the search box is swallowed at the component's root so it never queues a save. Its suggestions come from `search_url:` — the tag chips ask `GET /<admin>/tags/suggest` (`Admin::TagSuggestionsController`: up to eight names, prefix matches first, each with its readable-post count shown only to a `posts.read` holder; open to `posts.read`, `pages.edit` or `tags.manage`, anyone else gets the 403), the related-posts chips and the rich-text editor's link search ask `Admin::LinkTargetsController`; the debounce, one-request-at-a-time and stale-answer logic is `app/javascript/search/suggestions.js`, shared by both. A new tag name is capped at `Tag::MAX_NAME_LENGTH` (50) characters; the chip is marked invalid at once and the server refuses the whole save naming it. The two non-`admin/` controllers sit in `app/javascript/controllers/` because sign-in and setup load them without the admin entry point. An invalid field's border follows the error slot through the inherited custom property `--cs-field-invalid-border` set by the `.admin-column` / `.admin-field` wrappers (reset inside `.admin-rich-text-popover` and `.admin-translation-suggestion`, whose own inputs aren't the field).
- Passwords need `User::MINIMUM_PASSWORD_LENGTH` (12) characters; the message is "Use at least 12 characters." (locale format in `config/locales/en.yml`, `i18n_customize_full_message`, so it isn't prefixed with the attribute name).

**Form placement.** A form is centred only when it is the whole screen (sign-in, password reset, the setup wizard) or sits in a dialog; inside the shell every form starts at the left edge of the content area, under the page heading, however narrow it is. Width is capped, not position: about 420px for single fields, 560px for a simple form, up to 880–1000px for a form with grids or a matrix (the handoff's numbers). The 403 and 404 messages are the only centred things inside the shell, and `test/lib/admin_design_rules_test.rb` fails on any other `mx-auto` under `app/views/admin` or `app/components/admin`.

**Theme.** Three-way: Light, Dark, Auto. `Admin::ThemeSwitchComponent` writes the choice to `localStorage["cs-theme"]` and the `theme_controller.js` sets `<html data-theme data-theme-choice>` — `data-theme` is the resolved light/dark the tokens switch on, `data-theme-choice` is what the switch marks as chosen — before first paint. The public site's footer keeps its own two-state toggle (`layouts/public/_theme_toggle.html.erb`); there is no shared toggle partial any more.

**Shell.** `Admin::BaseController::MODULES` entries carry `group:` (`:content`, `:people`, `:system`), which `Admin::Shell::SidebarComponent` renders as the sidebar sections (Dashboard stays first); the sidebar also holds the ⌘K field, the account block (`display_name`, then "email · role" on one line, Change password, Sign out) and the theme switch. `Admin::Shell::TopBarComponent` appears below 1280px, where the sidebar becomes a drawer (the page-tree column becomes one below 1024px); `admin--drawer` owns open state, scrim and Escape, and the CSS keys on `data-open` (`.admin-shell` in `content-spiel.tailwind.css`). In the page tree, a context-only row (an ancestor shown only as the path to a readable page) is greyed text with no actions, a row has a hover "+" only where `pages.create` holds under it and a drag handle only where `pages.move` does, the homepage has no handle, and a row shows "↻N" (outdated) and "○N" (missing) summed over the target languages, hidden at zero, from `Translations::StateIndex.counts_for` read once by `Admin::TreeComponent` (never red; the tooltip names the languages). The Trash entry carries `trash_badge_count` (`Admin::TrashController.visible/roots/badge_count`, the number of branch roots the viewer may act on, so it matches the Trash screen). A 403 and a 404 render inside the layout (`admin/errors/forbidden`, `admin/errors/not_found`; `rescue_from ActiveRecord::RecordNotFound`); a non-HTML request (a Turbo Stream, a `fetch`) gets a bare `text/plain` 404 so the caller doesn't mistake it for a stream.

**⌘K "Jump to…".** `Admin::JumpController` answers `GET /<admin>/jump?q=` with `Jump::Search` (`app/queries/jump/search.rb`): pages, posts and library images (read-scoped through `AccessControl.scope`, trash hidden), then CS Studio's modules as **Sections**, destinations inside the Settings screen as their own **Settings** group ("Settings › Site", "Publishing", "Languages", "AI translation", each behind the permission its section's controller asks for), and **Actions** (New page and New post open their dialogs; the rest are links); five rows per group. Pages and posts match **titles only** — in every language, via `jsonb_each_text` on the translated jsonb columns — never bodies (full-text search is a separate roadmap row); images go through `Media::Search` like the library does. A page or post row shows a non-Live status chip at its right end (`Admin::StatusChipComponent`, Live draws none). `Admin::Shell::CommandPaletteComponent` is the dialog (an ESC chip beside the field and a hint row, "↑↓ MOVE · ↵ OPEN · ⌘↵ NEW TAB"), `admin--command-palette` the controller (⌘K / Ctrl+K, arrows, Enter; ⌘/Ctrl+Enter opens the row in a new tab). The shortcut does nothing while another modal dialog is open: the editor closes what is open first.

**The save rule.** Content autosaves (`admin--autosave`, the status line "SAVED 10:42", or "SAVED TO SITE 10:42" for a live record, whose edits go straight to the site): the page and post editors, block cards, the Media panel, a tag's name. Configuration is saved explicitly — Settings (every card of it, Languages included), Groups, Users, Change password — through `Admin::SaveBarComponent` with `admin--save-bar`: a form footer that is always visible, in the form's own column under the fields and sticky at the bottom of the window ("Save · Cancel · N unsaved changes"; Save is disabled, and the footer reads "No unsaved changes", while an existing record has nothing to save; `Admin::SaveBarHelper#save_bar_form_data(dirty:, always:)` — `dirty` re-renders with the typed invalid values still counted, `always` keeps Save enabled from the start for a new record). A successful save stays on the screen it was made on with a toast: Settings 303s to itself ("Settings saved"), a group and a user to their own editor ("Group saved", "User saved"; a new user to the new user's editor, "User created"); only a delete leaves for the list. Single actions (publish, trash, restore, revoke, a language added, turned off or made the default, the AI key, an owner change) are instant, behind a confirm dialog where they destroy or re-point something. Drag has a keyboard path (Space, arrows, Space) and its own styling (`.admin-drag-ghost`, `.admin-drag-chosen`, `.admin-drag-fallback`); the Sortables run with `forceFallback` (SortableJS's own pointer-driven drag, a clone on `<body>`), because the handles are `<button>`s and Firefox can't start a native drag from one.

**How the footer counts.** `admin--save-bar` compares what the form would *submit* now against a snapshot taken on connect (a disabled control and an unticked box are absent), so it doesn't depend on the order nested controllers connect in, and a value typed back is no change. One key per control: a radio group is one key, a checkbox is `name=value` while ticked, and anything else is its name plus its *position* among the controls of that name (`name#0`, `name#1`, …), so the rows of a list (`site_setting[social_links][][name]`) count separately. A hidden input is ignored unless it carries `data-save-bar-track` — the real control behind a widget (a member chip, the language order, a removed content type's carrier), whose script dispatches a bubbling `input` or `change` on it when it sets the value; `Admin::ChipInputComponent`'s `track:` marks its inputs that way. For every key but a checkbox's, an absent key and an empty string are the same value, so a blank row added to a list is not yet a change. The count is announced for the whole page as `admin--save-bar:state` on `document` (`detail: { unsaved, count }`; a late listener asks with `admin--save-bar:query`), and `admin--pending-lock` is its listener: while anything is unsaved it disables its `control` targets (a link gets `aria-disabled` and its click swallowed) and shows its `hint`, "Save or cancel your changes first." — the instant actions beside a form answer by reloading the screen, which would throw the pending changes away. A *named* control of the explicit-save form itself is never locked (disabled, it would drop out of what the form submits and count as a change that keeps the lock on), so an instant action's fields belong to a form of their own through `form=`.

**The leave guard** ("Leave without saving?" · "You have N unsaved changes on this screen." · **Keep editing**, which has the focus, / **Discard changes**; the `leave-dialog` in the layout) is page-level, one prompt however many forms a screen has, and covers four ways out: a Turbo visit (`turbo:before-visit`); a *link* that navigates the `#content` frame, stopped at `turbo:click` before Turbo has started anything; Back and Forward within the document (a `popstate` listener put ahead of Turbo's own, the traversal undone with `history.go`); and a page unload (`beforeunload`, the browser's own prompt — which is also all that Back to an entry from before a full page load gets). It does **not** cover a GET *form* submitted into `#content` or a script setting the frame's `src`: no explicit-save screen has either, and one that adds a filter form beside its save form must revisit this first. The footer's Cancel never asks; a same-page `#field` link (the error summary's) moves the focus by hand and adds no history entry; the visit a `#content` frame navigation is promoted to is let through once. A screen with one of these forms is never restored from Turbo's page cache (`save_bar_form_data` adds `turbo-cache-control: no-cache` to the head). The Back and frame-link guards read Turbo internals (`Turbo.session.history`'s `onPopState` and `currentIndex`, `history.state.turbo.restorationIndex`, the order of `turbo:click` and the frames' link interceptors), listed in the header of `save_bar_controller.js`; `turbo-rails` is pinned (`Gemfile`) for them and for the write queue, and an upgrade means re-reading both files against the new source. Where an internal is missing the guard stands back and only `beforeunload` remains.

**A stale autosave is refused, not saved.** The three record editors (the page settings form, a block card, the post form) carry the record's `updated_at` as it loaded (`base_updated_at`, iso8601 with microseconds). A save whose base is older than the record as just loaded is answered 409 by `Admin::AutosaveResponses#refuse_stale_autosave` before any service is called: the record is untouched, nothing is audited, the status line reads "● CHANGED ELSEWHERE" and `Admin::EditorScreen::ChangedElsewhereComponent` fills the header's `#editor-notice` — "Changed by <name> <time ago>. Your text is still here so you can copy it; reloading shows the latest version." and Reload, a full-page visit that discards the typed text. The name comes from the audit log bounded by the refused save's own base (only later events can have made it stale; the newest change by someone else is preferred; a change by the viewer's own other tab says so; with no event at all it says "Changed elsewhere."). The answer carries no new base, so every later save of that form is refused too until Reload. A blank or unparseable base is not stale (non-JS and scripted clients never send one). The check and the save are not atomic: two saves on the same base within one request's length can both pass. The Media panel and the tag rows still save on a stale base and warn afterwards (`:saved_over`, "SAVED · ALSO CHANGED ELSEWHERE — RELOAD TO SEE THE LATEST", deliberately not the refusal's wording). The Settings form is refused like the editors, as a page rather than a stream: it carries `base_updated_at`, and a Save on a stale base re-renders the screen at 409 with "Settings were changed elsewhere since you opened this screen. Reload to see the latest — your changes are still in the form." and the typed values kept. Because every block write `touch`es its page, a block's answer moves the page settings form's `base_updated_at` forward to the touched page's — only when the base that request carried (`X-Page-Base-Updated-At`) was still current before the write. The page tree's move (and its Undo toast) sends the same header, but only when the moved page is the one open in the editor, since `Pages::Move` saves that page and so moves its `updated_at` (`Admin::TreeController#page_base_streams`). A post's tags are covered the other way round: `Tags::Rename`, `Tags::Destroy` and `Tags::Merge` touch every post carrying the tag, so a post form that was open (it resends every tag chip on every autosave) is refused as stale instead of re-creating a deleted tag or putting the old name back. A 403 answer (a save refused for want of permission) is a rendered answer, not a failure to retry: the status line reads "Not saved — you don't have permission to change this", an error toast says so, and the form stays unclean. The page and post editors are never restored from Turbo's page cache (`turbo-cache-control: no-cache` in their `<head>`), so Back never shows a form with a stale base; they also carry `turbo-prefetch: false`, so a hover-prefetched answer older than a save is never used for a click from an editor.

**The write queue.** That only holds together if one screen's writes are serialised, so `app/javascript/autosave/queue.js` runs every `admin--autosave` form's save, block reorder, Turbo block form (add, duplicate, delete, Undo) and tree move (with its Undo) one at a time: a request is sent only after the previous answer has been received, its new bases written into the hidden fields and — for a Turbo Stream answer — the answer's own streams applied, recognised by their markup (`holdTurboRequest` releases its slot only then), and each reads the freshest base at send time. An unchanged form sends nothing. Nothing that replaces the page starts until the queue is empty and every form has sent what it holds (`drained()`, bounded by `DRAIN_LIMIT_MS`), and three things replace a page: a Turbo **visit** waits in `turbo:before-visit`; a **frame navigation** inside `#content` has its REQUEST held (the same `turbo:before-fetch-request` listener holds a GET carrying `Turbo-Frame: content`), and its render waits again only when a write was queued since the request went out (`writes` against `frameRequestedAt`, or a busy queue) -- the answer is then older than that save, so the frame's URL is fetched again after the drain and that is rendered instead; and **any non-GET Turbo form submission** made while a save is outstanding waits in `turbo:before-fetch-request`, whichever form it is (Still correct — mark up to date, Save key, tag delete, sign out, the header's actions). The redirect a Turbo form submission ends in, and the visit a `#content` frame navigation is promoted to, are never held (they arrive with the answer Turbo already fetched; each such note expires after 2 s, `VISIT_NOTE_LIMIT_MS`). The header's page-replacing actions (Publish, Unpublish, Schedule, Move to trash) additionally drain at `submit` through `admin--queue-hold`, which declines to run when a form ended unclean (refused, invalid, offline) because its redirect would throw away the text a 409 bar promised to keep. A task belongs to the page generation its form was rendered on: a generation is the `<body>` element plus the count of `#content` frame renders (`isCurrentGeneration`), and a body Turbo is about to replace is retired at `turbo:before-render` (read from `Turbo.navigator.currentVisit.willRender`, a Turbo internal); a task that outlives its page is still sent but renders nothing into the new document. `drained()` never rejects (a form whose flush throws is skipped, so a link that waited is never stranded). A form's save state (what it last saved, what it last sent, whether it is paused by a 409 or failed) lives in a `WeakMap` keyed by the form element, so a block card moved by drag keeps its paused or failed state and is not sent again as it is; after Duplicate, focus goes to the copy's drag handle. The queue assumes Turbo's morphing page refresh stays off. A block reorder and a tree move are hand-built `fetch`es inside the queue; `app/javascript/autosave/order_request.js` judges their answer: only a Turbo Stream is rendered, and a redirect to sign-in, any other answer or no answer puts the card or row back where it was and raises an error toast (cloned from `#toast-error-template` in the layout) — a reorder the server refuses goes back too. Closing or reloading the tab is the one way out the queue can't hold: while the screen is not `settled()` (something queued, debounced or retrying, or a form paused or failed) a `beforeunload` listener, present only while an autosave form is registered, asks for the browser's own prompt.

**Editor header.** One component serves the page and the post editor (`Admin::EditorScreen::HeaderComponent`, sticky): a breadcrumb row (a page's ancestors, a post's content type; a crumb the viewer may not open is plain text) carrying the save status, Preview, one primary action and a ⋯ menu; the title with its status chip; the public path (always shown while the record has one; "View on site" only while live); the language tabs; and a `suggest` slot for "Suggest translations for N empty fields". A live record has no primary button at all — only the hint that its changes appear on the site as soon as they're saved; a draft offers Publish, a scheduled record "Publish now" and "Edit schedule". Everything else sits in the ⋯ menu: Activity (`audit.view`), Schedule… (a draft only; **no scheduling a live record**), Unpublish, and Move to trash last after a divider (the homepage can't be). Every publish/unpublish/schedule/trash form carries `data-turbo-frame="_top"` so the answer re-renders the tree and the sidebar's Trash badge. The dialogs are siblings after the `<header>` (it is sticky and would clip a modal). Schedule is `Admin::EditorScreen::ScheduleDialogComponent`: a `datetime-local` read in the site time zone (the line below the field names it), "Remove schedule" when one exists, and the rules of `Admin::Scheduling` — a time in the future, at most 50 years ahead — enforced by the controllers' `schedule` actions and not by `Pages::Save`/`Posts::Save`, which may set a past `published_at`; a refusal travels as `flash[:schedule_error]` (never a toast) and reopens the dialog with it. **View only:** a readable record the viewer can't edit gets a "View only" badge and a hint (including "changing a live post needs the right to publish" for the interim publish rule), its form fields are wrapped in `<fieldset disabled>` styled `.admin-view-only`, and block cards, chip inputs and rich-text editors go inert.

**Translation pair.** In a non-default language every translated field is a pair (`.admin-translation-pair`): the primary-language original in `Admin::EditorScreen::ReferenceCardComponent` beside the field's own input, stacking below 880px of the *form's* width (`container-type: inline-size` on `.admin-translation-form`, not the viewport; the card's `<details>` folds only when stacked). Fields that are the same in every language are not inputs on a translation tab (so its autosave can never send or change them) but one collapsed "Shared fields (N)" disclosure (`Admin::EditorScreen::SharedFieldsComponent`); a schema group field's value is shown there as a summary, and in the reference card as the raw hash. An outdated field's card turns `warn` and shows "↻ CHANGED <time ago>" and one of: the word diff of the text the translation was made from against the original now (`Translations::SourceDiff`), "Formatting changed", "The text is too long to compare word by word." or just the current original; its actions are **Suggest update** and **Still correct — mark up to date** (`Translations::Confirm`, writing only `translation_sources` via `update_columns`, so `updated_at` and the autosave base don't move; the button belongs to the layout's confirm form through `form=`). The slug is a prefixed input (`Admin::PrefixInputComponent`), the hero a library image with a per-use alt, SEO fields have soft character counters (`admin--char-count`), and a content type's own fields sit in their own group. A per-use override (a page hero's alt, an image block's alt and caption) shows the library's text as its placeholder and a **Reset** once it holds its own (`admin--override-field`, `admin/shared/_override_field`).

**Blocks.** `Admin::BlockCardComponent`: a drag handle, the type name (a button that collapses the card), and a ⋯ `Admin::MenuComponent` (Move up, Move down, Duplicate, a divider, "Delete block…"); `admin--blocks#refreshMoveState` keeps Move up/down right after every move, add and delete. A block whose stored type isn't registered any more is the minimal "Unavailable type" card (danger border, "Delete block…" its only action). There is one dashed "+ Add block" row at the end of the list (`Admin::BlockPickerComponent`: a `button_to` per registered type POSTing to `create`); Duplicate is what inserts below a block. A post-list block's Type, Tag and Limit share one row, Tag being a one-value chip input.

**Rich-text dialogs.** The editor's toolbar is grouped (`RichTextColumnComponent::TOOLBAR_GROUPS`, plus the Insert menu) and one row wide. Insert image goes through the media picker and then a form-width dialog for alt text and caption; YouTube and "Page link" are dialogs too. `Admin::EditorScreen::RichTextDialogsComponent` renders the three once in the layout (outside `#content` and every autosave form, so their fields never feed an autosave); `admin--rich-text-dialog` fills and opens them over `rich-text-dialog:open` / `rich-text-dialog:closed` events naming the opening editor, so two editors on one page never cross wires. The page search is `app/javascript/rich_text/target_search.js` over `Admin::LinkTargetsController`.

**New page and New post** are dialogs rendered once in the layout (`Admin::EditorScreen::NewPageDialogComponent`, `NewPostDialogComponent`, only for a viewer who holds `pages.create` / `posts.create` anywhere) as a shell — a loading line, an empty `<turbo-frame>` and a disabled Create button. `admin--new-record` loads the form when the dialog opens (`GET /pages/new?parent_id=&title=` or `/posts/new?type=&title=`, answered by `Admin::EditorScreen::NewPageFormComponent` / `NewPostFormComponent`), the trigger's own `data-new-page-*-param` / `data-new-post-*-param` attributes becoming the preset (read on `admin--dialog:opening`), so the form is always built from the current tree; the same URLs are the standalone no-JS pages. The page form's "Inside" offers only parents where the viewer may create (`AccessControl.creatable_parents`). ⌘K's "New page" / "New post" open the same dialogs.

**The posts list.** `Admin::PostsController#index`: a toolbar (`Admin::PostsScreen::ToolbarComponent`: title search, a segmented `scope` control with counts — All, Live, Drafts, Scheduled — that respect every other filter but not the scope itself, and Type, Tag and Translation drop-downs; one GET form with `admin--auto-submit`; `status` is the old name of `scope` and still reads), 50 rows a page, and a table (`TableComponent`) with a per-row ⋯ menu. Selecting rows shows the bulk bar (`BulkBarComponent`, `admin--bulk-select`) for **Publish** and **Move to trash**, posted to `POST /posts/bulk` and run by `Posts::Bulk` (an `# audit: none` service: it writes nothing itself — every post goes through `Posts::Save` or `Trash::Move`, so each is authorised with its own scope, audited and answered on its own). Ids load only through `AccessControl.scope(..., "posts.read")`: one that is missing, trashed or out of scope is *not found* — counted, never named. There is no all-or-nothing: each post runs in its own savepoint, an exception counts as that post's failure, and the answer is one toast (`Admin::BulkResponses`, bounded because it lives in the session cookie) separating done, refused (readable but not actionable), failed (with the first reason), already live, scheduled posts left as scheduled (publishing never discards a schedule) and not found. Something done *and* something refused, failed or not found is a warning toast (`flash[:warning]`, which never auto-hides, because the toast is the only place the failures are named); nothing done is an error toast. The selection column and the bulk bar exist only for a viewer who holds `posts.publish` or `posts.delete`; a row's own "Move to trash" replaces the selection with that row and puts the previous ticks back if its dialog is cancelled. At most `Posts::Bulk::MAX_IDS` (200) per call. A bulk trash offers Undo (`POST /trash/restore_many`, `Posts::BulkRestore`, the same contract through `Trash::Restore`) only while its URL fits `MAX_UNDO_URL` and the URL plus the sentences fit `MAX_FLASH_BYTES` (bytes, not characters — the answer lives in the session cookie); otherwise the toast says where to find the posts.

**Settings** is one screen (`Admin::SettingsController`, `/<admin>/settings`): an in-page nav of anchors (`#site`, `#languages`, `#publishing`, `#ai`; `Admin::SettingsScreen::NavComponent`), a card per section (`SiteCardComponent`, `LanguagesCardComponent`, `PublishingCardComponent`, `AiCardComponent`) and ONE form, `#settings-form`, on ONE save footer — a plain `PATCH`, never a Turbo Stream: 303 with "Settings saved", the screen re-rendered at 422 with the error summary (`Admin::SettingsScreen::Values` puts the typed values back over the stored ones), or at 409 on a stale base. The module opens for `settings.manage` **or** `languages.manage`; each card and its nav link render only for the right that owns them (Languages: `languages.manage`; Site, Publishing, AI translation: `settings.manage`), and the service enforces the same split: `Settings::Save(site, attributes:, translations:, languages:)` decides from what it is *passed* which rights it needs — a site part needs `settings.manage`, `languages:` needs `languages.manage`, a call with both needs both, checked before anything is assigned — so the controller passes exactly what was posted and a forged field outside the viewer's right is a 403 with one `access.denied`, never silently dropped. `languages:` is the complete ordered rows (`code`, `fallback`), applied inside Save's own transaction through `Locales::Configure#apply` (which checks `languages.manage` itself and records `language.configured` only when something changed), so one Save is all-or-nothing; a languages-only call leaves the site row alone. The Site card holds every enabled language's title and tagline at once (`site_setting[translations][<code>][title]`, ids `settings-<code>-title`); its language tabs are in-page buttons that only switch which pair is visible (`Admin::LanguageTabsComponent(mode: :buttons)`, `admin--settings-tabs`; `?locale=` picks the tab shown first, and a refusal on a translated field shows the default language's tab, where the required title lives), so switching never counts as a change or asks to leave. Social links are repeated rows (`admin--repeat-rows`; removing the last row clears it rather than deleting it, so an emptied list still posts). The form never carries `default_locale`.

**Languages** are the Languages card: rows with a drag handle (`admin--sortable-rows`: the same SortableJS options and keyboard path as the block list, writing one tracked `site_setting[language_order]` field so a reorder is one change), the language's own name and path, a Default radio and a single "Falls back to" select — order and fallbacks wait for Save. A fallback select stores a one-element list or none; a language stored with several shows the first, and the others are dropped only when that row's fallback is changed and saved. What happens at once is `Admin::LanguagesController`, each a form of its own outside `#settings-form` (reached with `form=`), each a 303 back to `#languages` with a toast, each `languages.manage`: Add language (`Locales::Enable`), Turn off (`Locales::Disable`, behind a dialog; refused for the default) and Default — `PATCH settings/languages/:id/default`, `Locales::MakeDefault`, event `language.default_changed`, behind "Make <Name> the default?", whose "(N items)" is `Translations::StateIndex.translated_record_count` (kept records holding at least one stored translation). `MakeDefault` assigns the code, clears the *new* default's own fallbacks (its select reads "None (default)" and is disabled, so no screen could clear them), lets the model carry the title and tagline over, and rebuilds the translation states. The radio goes back when its dialog is closed any other way (`admin--default-language`), and all three are `admin--pending-lock` controls. `GET settings/languages` is a 301 to `settings#languages`; there is no Languages screen.

**The AI translation card.** Provider and model are fields of the Settings form. The key is not — it is never rendered, so it can't be a pending change — and has its own controller: `Admin::AiKeysController`, `PATCH` / `DELETE /<admin>/settings/ai_key`, `settings.manage`, writing through `Settings::Save` and answering with Turbo Streams that replace only the key component (`AiKeyComponent`: "● Key saved · added 2 Oct", the year added when it isn't this year, "Key saved" alone for a key older than the column, "No key yet"; Replace or Add key, Remove… behind a dialog; a blank key is a 422 with "Enter the API key first."), its forms, a toast and an empty test result. `site_settings.ai_api_key_saved_at` is set with the key and cleared with it (`SiteSetting#ai_api_key_saved_on` is the day in the site zone); it is bookkeeping, kept out of audit field changes. **The carried base:** a key write moves the settings row's `updated_at`, so the key forms carry the main form's base (`main_base_updated_at`) and the answer moves the main form's `base_updated_at` forward only when the request wrote something *and* the carried base was parseable and still current before the write; otherwise nothing moves and the forms come back carrying what they were given, so a key saved from a stale tab neither unlocks that tab's Save nor cancels its 409. **Test connection** (`SettingsController#test_ai_connection`) tests the *saved* provider, model and key and answers "● CONNECTED · 412 MS" or the provider's message (`AiTestResultComponent`); `admin--ai-settings` disables it while provider or model differ from what is saved ("Save provider and model first. Tests the saved settings."), while anything else is pending, and while a test is running. The hint is per control: the test row and the key row may each show their own.

**AI assistant** (`Admin::ApiTokensController`, `Admin::TokensScreen::CreateStepComponent` / `ConnectStepComponent` / `TableComponent`) is a numbered flow: 1 · Create a token (a required name, a group from those the viewer may assign with its description under the select — `admin--group-hint` — and Create token), 2 · Add it to your assistant (the MCP URL and the client configuration, each with Copy), then the tokens table: Name, Acts as, Group, Created, Last used, Status, "Revoke…" behind a dialog; revoked tokens stay listed. `api_tokens.name` is required, stripped, at most `ApiToken::MAX_NAME_LENGTH` (60) characters and unique per user among that user's *active* tokens, case-insensitively — a validation backed by the partial unique index `index_api_tokens_on_user_and_lower_name_active`. `ApiTokens::Issue.call(user, group:, name:)` treats a nil name as "pick the next free Token N" and any String, a blank one included, as the name to validate; CS Studio and the setup wizard always pass a String, so a missing name is "Name can't be blank". The reveal is the POST's own answer — the same screen with the warn box in step 1 and the token filled into the configuration, `no-store`, never a redirect and never in Turbo's cache — and no part of a token is rendered, logged or audited afterwards. The token's name is what the audit log shows: `Audit.record` writes it to `audit_events.actor_label` once, at insert (it is not a coalescing column), so "via <name>" survives the token row.

**Groups.** The list (`Admin::GroupsScreen::ListComponent`) is card rows that are links, with member and token counts from two grouped queries. The editor (`admin/groups/_form`, `Admin::PermissionMatrixComponent` composing the rest) is rows, not a grid: eleven `PermissionRowComponent`s (Posts ×5, Pages ×6), each a tick, the short label with the key in mono, scope chips, and "Edit scope" opening a `ScopeEditorComponent` in place — content types as a multi-select (none ticked = all) and an "Own only" toggle for posts, a tri-state branch tree for pages (`BranchTree`, `admin--branch-picker`: chosen, a greyed tick for a page a chosen ancestor already includes, a dash for an ancestor of a chosen page) — then `ToggleListComponent` cards for the unscoped keys, one more per plugin area. Open and close are only `hidden`; everything stays in the form, and the scope of an unticked permission is ignored. **A form saved as rendered changes nothing**, which is why some things are carried as hidden inputs: a stored branch root the viewer can't open ("A page you can't open (kept)"), a chosen context-only ancestor, a redundant stored root (a root plus its own descendant; its hidden input is enabled only while the box is disabled as implied), and a *removed content type*. The last is drawn as a warn chip "! <name> · this type no longer exists" with **Remove**, on a tracked hidden input, so pressing Remove is a counted change; with no live type left the chips read "All content types" followed by the warn chips, which is what Save stores.

`Groups::Save` reads such a carried name by one narrow rule (the comment above `#live` is the authority; keep this in step with it): a posted grant is read as a stored grant, unchanged, only when the stored grant is a live `LiveGrants` entry with removed types of its own (never a wholly dead grant), the permission is the same, the posted scope *minus that entry's own removed types* is exactly the entry's live scope (the same live types, the same `own`, the same pages), and no other posted grant has already been read as that entry. Everything else is compared raw, so `can_grant?` sees the removed name and only an actor whose own grant covers it passes. The consequence, on purpose: a non-owner who couldn't hand out the removed name can change such a grant only after pressing Remove on it, and the row says so ("Remove this type before changing the row."). A removed name is dormant, not meaningless — re-registering a type of that name revives it — so it may stay or shrink, never appear, move or widen unchecked. **View only:** a stored group the viewer can't manage as it stands (`AccessControl.can_manage_group?` false) gets the notice "This group has permissions you can't hand out, so you can only view it.", the whole form in `<fieldset disabled class="admin-view-only">`, no footer and no delete zone; scopes still open through a link ("View scope"), which a disabled fieldset doesn't disable. The locked tick ("You can't grant this", a greyed disabled box whose scope is carried) is a defensive rendering only: a stored grant the viewer couldn't hand out makes the whole group view-only, and the lock is judged on the *live* scope of a grant still exactly as stored, so no stored state reaches it. Members are a chip input (`MembersComponent`, tracked) over `GET /<admin>/users/suggest` (`Admin::UserSuggestionsController`: `groups.manage`, at least two characters, at most eight rows, name or email, prefix matches first, owners never offered — "Owners aren't listed: they already have every permission." — while an owner already stored as a member stays a chip until removed). The delete zone (`DeleteZoneComponent`, after the form, custom groups only) names the member count and the active tokens that go with the group ("<name> — <user>", ten then "and N more") in its confirm dialog; a built-in group gets a note instead.

**Users.** `users.name` is optional; `User#display_name` is the one reader (name, else email). The list (`Admin::UsersScreen::ListComponent`) is card rows that are links: an initial, name or email, "(you)", an OWNER tag, group chips or "No groups", and the last sign-in — `Users::LastSignIn.for(users)` (`app/queries/users/last_sign_in.rb`), one grouped `MAX(occurred_at)` over the `session.created` audit events for the whole page, no column on the user; no event reads "Never". The editor (max 880px): name and email, the password behind "Set a new password…" (a `<details>`; blank keeps the password, closing it clears what was typed, and a typed password is never rendered back), the groups as cards (`GroupCardsComponent`: the card is the label of its checkbox; a group the viewer can't assign is sunken with "You can't grant this group." and, when ticked, carried by a hidden input), "Save user". Owner rights and deletion are zones after the form, both `admin--pending-lock` controls: the **owner zone** (`OwnerZoneComponent`, shown to owners on an existing user) opens "Make owner…" / "Remove owner rights…" dialogs that post `PATCH users/:id/owner` (`owner=1|0`, anything else a 400), which calls `Users::Save` and nothing else — the last owner's button is disabled with the reason; an owner can't be created in one step. The **read-only states** come from one predicate shared with the services, `Users::Manageability.for(actor, user)` → `:editable`, `:owner_protected` ("Only owners can change other owners.") or `:outranked` ("This user has permissions you don't have, so you can't change them."): a notice, a disabled fieldset, no footer and no zones. `Users::OwnerProtection` delegates its predicates to the same class, so the screen and the services can't drift; the view decides nothing — a forged write against a read-only user is still the services' 403 and one `access.denied`. A signed-in user edits their own name on the **Change password** screen (`Admin::AccountsController`, `account/password`): the name form (`PATCH account/profile`, `Users::UpdateProfile`, `_top` so the sidebar's account block follows) above the password form, each with its own footer and one shared Leave prompt; a wrong current password is an error on that field ("That's not your current password."), and the subtitle's promise — you stay signed in here, other sessions end — is the services' own rule.

**Tags** (`Admin::TagsController`, `admin/tags/index`): a card table of names that are inputs — text until hovered or focused, autosaving a rename through `Tags::Rename` — a post count linking to the posts list filtered by that tag (kept posts the viewer may read; "—" without `posts.read`), and a ⋯ menu with "Merge into…" and "Delete tag…". There is one Merge and one Delete dialog for the whole list, outside every form, filled from the pressed row (`admin--tag-dialogs`); their sentences count *every* post carrying the tag, trashed ones included, because that is what the action touches and what the event records. `Tags::Merge.call(source, into:)` (`tags.manage`) runs in one transaction with both tag rows locked in id order: every post carrying the source gets the target (no duplicate join rows), the carriers are touched (so an open post form is refused as stale), every listing block whose `tag` setting names the source — on trashed pages too — is repointed and its page touched, the source is deleted, and one `tag.merged` event is recorded on the target (metadata `merged`, `posts`); after the commit `PublicSite::Paths.sync_posts` runs for the content types of the blocks that named either tag, since a post's canonical page depends on tags only through those blocks. No undo, no per-post event. `Tags::Listings` holds what Rename, Destroy and Merge share.

**System status** (`Admin::SystemStatusController`, `system_status.view`): "N of M checks passed · last run HH:MM", warnings first, each check an `Admin::SystemCheckRowComponent` (the setup wizard draws the same rows with `copyable: false`). A check may carry a console `command`, shown in a code box with Copy (`admin--clipboard`). The outgoing-mail warning's command resets a password through `Users::UpdatePassword` — never `update!` on the model — so it is audited and ends that user's sessions (`Setup::SystemCheck::MAIL_FALLBACK_COMMAND`, a static string). "Run checks again" is a GET with prefetch off, because the storage check writes and deletes a probe.

**The preview bar** (`Public::PreviewBarComponent`, rendered first in the public layout on `/preview…` only): a fixed 36px bar, "PREVIEW · <title> · <Draft | Scheduled | Live> · <language>", Edit and Exit preview. It is the public site's chrome: the public stylesheet only, no admin JavaScript, and its colours are the theme tokens `--th-preview-bg` / `--th-preview-ink`, which do not switch with light and dark. Edit opens the record's editor in the previewed language. Exit preview goes to the record's public URL in that language when it is live, and otherwise to CS Studio's list (the pages landing for a page, the posts list for a post) — there is no public page to leave for.

**Mind graph** (`Admin::MindGraphController`, `PostGraph` in `app/queries/post_graph.rb`, `admin--mind-graph` on d3-force). The data is `{ nodes: [{ id, title, type, colour_index, status, url }], tags: [{ id: "tag-<id>", name, count }], edges: [{ source, target, kind: "related" | "tag" }] }`: every post the actor may read, one tag node for each tag on at least two *readable* posts (derived only from those posts, its count the readable number, so nothing about unreadable posts shows), an edge per `PostRelation` and one from each tag to each of its posts; four queries whatever the size, no cap on posts. It carries no colour: the page draws a node from its `colour_index` through the `--cs-cat-N` tokens (`.mg-*` classes), a live post filled, a draft or scheduled one hollow. `Admin::MindGraphLegendComponent` names the types present, Tag, "Draft or scheduled" and the two edge kinds (related solid, shared tag dashed), and a client-side filter (All / Related / Tags) hands the simulation only what is visible. Post nodes are links (Enter and Space open the editor); tag nodes are not focusable.

### i18n / Mobility

Translated attributes (`Page#title/slug/subtitle/meta_title/meta_description`, `Post#title/slug/excerpt`, `ContentBlock#caption`) are plain jsonb columns via the Mobility `:jsonb` backend (`config/initializers/mobility.rb`); rich text (`Post#body`, `ContentBlock#body` — pages have none) is the same jsonb backend, one Tiptap/ProseMirror JSON document per locale, via `HasRichTextBody` (see "Rich text" below), not ActionText. Available/default locales are set once in `config/application.rb` (`config.i18n.available_locales`), not in the Mobility initializer, because Mobility needs it at load time to define per-locale accessors. Falls back to `:en` everywhere. Because translated columns are jsonb, `where(slug: ...)` on them is a bug (comparing jsonb to a string) — use Mobility's `.i18n` scope, as the slug-uniqueness validations on `Page`/`Post` do.

### Auth

Custom session-based auth (`app/controllers/concerns/authentication.rb`), not Devise — `has_secure_password` on `User`, signed cookie holds a `Session` id, `Current.session`/`Current.user` per-request. `ApplicationController` requires authentication by default; `PagesController` (the public site) opts out with `allow_unauthenticated_access`. `ApiToken` is a separate `has_secure_password`-backed token model (hashed, revocable, named — see "AI assistant" under the design system) for non-session API access, bound to one `AccessControl::Group` (`group_id`, not null) that bounds what it may do regardless of its user's own rights — see "Access control and audit" below for what being signed in or holding a token actually permits. Active Storage's own write endpoints (`POST /rails/active_storage/direct_uploads`, the Disk service's `PUT`) require a signed-in session too (`config/initializers/active_storage_access.rb`, 401 otherwise) — the app never uses direct uploads; every upload goes through a CS Studio controller.

### Access control and audit

`AccessControl::Permissions` (`app/models/access_control/permissions.rb`) is a registry like `ContentModel::Registry`/`RichText::Schema`: built-in keys are unprefixed (`posts.read/create/edit/publish/delete`, `pages.read/create/edit/publish/move/delete`, `tags.manage`, `media.upload`, `media.manage`, `settings.manage`, `languages.manage`, `users.manage`, `groups.manage`, `tokens.manage`, `system_status.view`, `audit.view`, `trash.empty`, `ai.translate` — see `AccessControl::BuiltIns`), plugin keys must be `owner/name`, and a duplicate raises `AccessControl::DuplicatePermission`; registration happens in `config/initializers/types.rb`'s `to_prepare`, alongside the block/content-type/rich-text registries, reset-then-register so a dev reload doesn't double-register. `AccessControl::Group`/`Membership`/`Grant` (tables `access_control_groups`, `access_control_memberships`, `access_control_grants`) carry the actual rights: a group's grants each name a permission key plus a jsonb `scope` limited to `content_types` (array), `page_ids` (array, matched via `page_hierarchies` so a branch grant covers descendants), and `own` (boolean, matched against `Post#author_id`) — grants combine with OR, and every scope key set on one grant must match (AND) for that grant to apply. Four groups are seeded by name (`AccessControl::Seeds::BUILT_IN`, applied by the `SeedAccessControlGroups` data migration and by `db/seeds.rb`'s `ensure_built_in_groups!`): Admin (every registered permission, unscoped), Editor, Author (`posts.edit` scoped `own: true` — note its `posts.read`/`posts.create` are unscoped by design, so a seeded Author can still read every post, not just their own), Read only. Library images have no scopes: `media.upload` uploads, browses and chooses them (pointing a hero or image block at one needs it plus an existing asset, `Media::Choosing`, while clearing needs only the edit right), `media.manage` (Admin and Editor, added to already-seeded groups by `GrantMediaManageToBuiltInGroups`) edits or deletes any of them, and an image's uploader (`created_by_id`) may edit or delete their own with `media.upload` alone (`Media::Ownership` — a token still needs its group to hold `media.upload`). `users.owner` is a separate boolean flag, not a group — an owner is allowed everything regardless of grants, the last owner can't be demoted or deleted (`User`'s own validation), and every user-changing service (`Users::Save`/`Destroy`/`UpdatePassword`, via the shared `Users::OwnerProtection` concern) refuses a non-owner touching an owner's account at all, and refuses managing any user whose groups aren't a subset of the actor's own assignable rights (`#outranked?`) — so `users.manage` is bounded by what you could already grant yourself, never a blanket "any admin may manage any user". A password change ends that user's sessions inside the transaction that writes it (`Users::OwnerProtection#end_sessions_after_password_change`, called by `Users::Save` and `Users::UpdatePassword`, never by a controller): all of them, except the acting session of a signed-in user changing their own; the reset flow keeps none. The same bound applies to groups: `AccessControl.can_manage_group?(actor, group)` ("may this actor manage this group as it stands" — every grant it holds is one they could hand out) gates removing members or grants (narrowing a grant counts), deleting a group, and changing a user's membership, in `Users::Save`, `Groups::Save` and `Groups::Destroy`. Only a `User` is ever an owner (`AccessControl.owner?`): an `ApiToken` — even an owner's — is judged on its effective rights (group ∩ user) by `can_grant?`/`can_assign_group?`/`can_manage_group?` and the owner-only rules. A content type that is no longer registered matches nothing, and `AccessControl::LiveGrants` is what reads a group's grants with that in mind. A grant *all* of whose content types are gone is dead: it matches nothing, is shown unticked in the group editor, and is dropped on the next save of that group. A grant that still has a live type keeps the removed name beside it — a `LiveGrants::Entry` with `gone_types` — and the editor carries it (`#carried_attributes`) through every save until somebody presses Remove on it, so an untouched save changes nothing (see "Groups" under the design system for the rule `Groups::Save` reads it by). Either way the name is dormant, not gone: while it is stored, re-registering a content type of that name revives the grant with its old meaning. `can_assign_group?` and `can_manage_group?` judge a group on its *live* grants, so a dormant name can ride along when a user or token is put into the group by someone who couldn't grant that name (a roadmap row).

`AccessControl.allowed?(actor, key, record = nil, channel:)` (`app/models/access_control.rb`, delegating to `AccessControl::Checker`) is the one decision point: a subject key (`posts.*`/`pages.*`) requires `record` (nil raises `ArgumentError` — no scope-free allow by omission), an admin-area key ignores it; a `User` is allowed if any of their groups' grants match, an `ApiToken` only if a grant of the token's own group matches *and* its user is separately allowed — the intersection, so a token narrows but never widens its user's rights; a `nil` actor is allowed on the trusted channels `:setup`, `:console`, `:system` (and no channel at all) and denied on `:admin`/`:mcp`/`:public` (`PublicController` sets `:public`; nothing on the public site calls a service or access control today). The setup wizard creates the founding owner through `Users::Save` as that trusted nil actor on `:setup`, and every later step runs as the signed-in owner (`SetupController#act_as_signed_in_user`), so its events are attributed. `AccessControl.creatable_parents(actor, pages)` answers "under which of these pages may this actor create a page" (`pages.create` asked against a would-be child of each, branches preloaded in one query) for every parent picker — deliberately not `scope(actor, "pages.create", ...)`, which would never offer a branch grant's own root. `.holds?` is the same decision without a record, for nav/buttons only ("does this user hold `posts.edit` anywhere"), never to gate a write. `.scope(actor, key, relation, channel:)` (`AccessControl::Scoping`) narrows a `Post`/`Page`/`ContentBlock` relation to what's readable — used by every CS Studio list, the page tree, link-target/related-post/mind-graph search, `/preview`, and MCP's list/get tools — and `.tree_visibility`/`.preload_branches` exist purely for the page tree's cost profile: ancestors of a readable page are returned separately as `context_only` (greyed out, no actions, so a deep readable page still shows its path to the root), and `preload_branches` loads every listed page's closure-table ancestry in one query so per-row `allowed?` checks in a rendered list cost nothing extra. Everywhere a record could be looked up outside its scope — a CS Studio URL by id, an MCP `get_post`/`update_post`, a preview link — the answer is **not found, not forbidden**: a 404 or tool error, never a 403, so a locked-out record's existence isn't disclosed (one accepted trade-off: the related-posts editor discloses a *count* of hidden relations it can't show, "+N related posts you can't open", without naming them).

Every content, settings, user, group and token write funnels through `ApplicationService` (`app/services/application_service.rb`) — the exceptions are sessions (sign-in/out, audited directly as `session.*` by `Admin::SessionsController`), the `setup_completed_at` marker `Setup.complete!` sets, and derived rows (`public_paths`, closure-table rows) the models maintain themselves: `#authorize!(key, record)` calls `AccessControl.allowed?`; on refusal a service returns `denied(key, record, message: nil)`, which records one `access.denied` audit event (outside the service's own transaction — a rolled-back forged write still leaves exactly one, coalesced, denial) and answers with the fixed message `"You don't have permission to #{permission.label.downcase}"`. `#record_event(action, subject:, field_changes:, metadata:)` is the write side, called inside the transaction so a rollback leaves no trace. `test/services/service_contract_test.rb` enforces this isn't opt-in: it eager-loads every `ApplicationService` subclass and greps the *file* its `#call` is defined in (not the method body alone, comment lines excluded) for both `authorize!(` and `record_event(`, failing loudly on a service that has neither thought about authorization nor about the log. It is a tripwire, not a proof: a service passes by mentioning both anywhere in its file, and the one escape hatch, an explicit `# audit: none (reason)` comment, skips the `authorize!(` check together with the audit one. Behaviour is what `test/services/authorization_matrix_test.rb` and each service's own tests cover. One interim rule worth knowing before touching autosave: **editing an already-published record needs `publish`, not just `edit`**, because CS Studio's autosave writes straight to the live record — this goes away once pending revisions (Phase 3 versioning) exist. The converse holds too: a save that changes *only* the publish state (`published`/`published_at`, nothing else) needs only `publish` (`Posts::Save`/`Pages::Save#publish_only?`), so a read + publish "Publishers" group works.

`Audit.record(action, subject:, field_changes:, snapshot:, metadata:)` (`app/models/audit.rb`) is the single write path for the log (`Audit::Event`, table `audit_events`) — reading actor/channel/request id/IP off `Current` rather than taking them as arguments, so a caller can't forge them. `*.updated` and `access.denied` events coalesce (`Audit::Coalescer`): a burst within `Audit::COALESCE_WINDOW` (exactly 10 minutes, measured from the *previous* event's `last_occurred_at`, not `occurred_at`, so a continuous autosave session keeps extending one row for as long as it runs) merges into the open row instead of one row per keystroke pause; everything else stays discrete. Each event carries `field_changes` (old → new per field, named `field_changes` — never `changes`, which `ActiveRecord::Dirty` already owns) and a full `snapshot` of the subject after the change (`Audit::Snapshot`, the version basis Phase 3 versioning will build on) — both scrubbed of secrets twice over (a `NEVER_STORED` list, then a pass through `Rails.application.config.filter_parameters`), so a password digest, token digest, or raw token can never land in the log even if a snapshot serializer dumped raw `attributes`. The table is append-only twice: `Audit::Event` itself refuses any update outside its coalescing columns (`field_changes`, `snapshot`, `last_occurred_at`, `occurrences`) and any destroy, and the Postgres trigger `db/triggers/audit_events_append_only.sql` refuses the same at the SQL level (covering `delete_all`/`update_all`/raw SQL too — deliberately not `TRUNCATE`, so `db:truncate_all` still works in development) — reapplied after every schema load, not just every migration, via `config/initializers/db_triggers.rb` hooking `ActiveRecord::Tasks::DatabaseTasks.load_schema`, since `db/schema.rb` itself can't carry a trigger and `db:schema:load`/`db:reset`/parallel test workers' own database copies all bypass migrations entirely. After the writing transaction commits, `Audit.record` publishes `ActiveSupport::Notifications.instrument("audit.content_spiel", event:)` — the plugin hook for anything that wants to react to audit events, never before commit, so a rolled-back write triggers nothing.

### Rich text

`Post#body`/`ContentBlock#body` (via `HasRichTextBody`, `app/models/concerns/has_rich_text_body.rb`) store a Tiptap/ProseMirror JSON document per locale, read back as a `RichText::Document` value object (`app/models/rich_text/document.rb`) and written through `#assign_body` rather than the raw Mobility accessor. Node/mark types (built-ins: `doc paragraph heading bulletList orderedList listItem blockquote codeBlock horizontalRule hardBreak text youtube image` / `bold italic strike code link internalLink`) are declared in the `RichText::Schema` registry (`app/models/rich_text/schema.rb`, `built_ins.rb`) — the plugin seam: plugins register prefixed `owner/name` types, duplicates raise. `Document#validate` checks types/attributes are registered and allowed, enforces the editor's own content model (each node's `content` expression and mark `excludes`, mirrored from the vendored Tiptap extensions — `code` can't combine with another mark, no empty text nodes, a `listItem` starts with a paragraph, no empty quotes/lists; the one deliberate difference is that `doc` may be empty), so nothing the server accepts opens read-only in the editor, and that referenced records (internal links, image `Media::Asset`s -- see "Media library" below) exist; existence checks only block references that are new relative to the locale's *stored* document, so a pre-existing dead reference never blocks an unrelated edit, and validation only re-runs on the locales that actually changed in a given save. `#to_html`/`#to_markdown`/`.from_markdown` convert to/from rendered HTML (via `RichText::HtmlRenderer`, always scrubbed by `RichTextScrubber`) and CommonMark (via `RichText::Markdown`, backed by `commonmarker`); the render cache key (`Rails.cache.fetch`) is `["rich_text", digest, RichText::Schema.version, locale, preview, PublicSite.current_content_version, RichText.code_revision]` — `PublicSite.content_version` (`app/models/public_site.rb`) is memoised per request on `Current` and is there because a document's own digest only covers the document, not the world its links and images resolve against. It is much broader than that purpose: fifteen aggregates — the newest `updated_at` and the row count of pages, posts, content blocks, `public_paths` and media assets, the settings row's `updated_at`, the newest `published_at` of published pages and posts (a scheduled record going live writes no row), and the newest id and count of `ActiveStorage::VariantRecord` — so it moves on *any* write to any of those tables, a draft's autosave included, and every cached render and every public ETag goes with it (narrowing it to published output is a roadmap row); `RichText.code_revision` (`KAMAL_VERSION`, else a `REVISION` file, else a value chosen at boot) covers the code, so a renderer or component markup change reaches pages after a deploy instead of Solid Cache serving the old HTML.

MCP (`create_post`/`update_post`/`get_post`) exchanges `body` as Markdown: standard nodes are CommonMark, custom nodes are directives (`::youtube{id="…"}`, `::image{asset="42" alt="…" caption="…"}`) on their own line, and internal links are `[text](cs:page/42)` / `[text](cs:post/7)`. Directives are recognised inside list items and quotes too (`- ::youtube{…}`). Unknown directives are kept as text and reported as warnings, never a hard failure; whatever the Markdown can express but the editor's content model can't (a bold code span, an empty quote) is repaired by `RichText::ContentRepair`, also with a warning. Markdown can't spell an empty paragraph or a trailing hard break, so those two don't survive a round trip; otherwise editor-shaped documents round-trip exactly over `Document#normalized` (which also moves whitespace at the edges of bold/italic/strike runs outside the mark).

The Tiptap editor is vendored under `vendor/javascript` via import maps (`config/importmap.rb`) — no npm, no CDN at runtime. There are two entry points: the public site (and setup/sign-in) imports `application` (Turbo plus the site's own controllers); CS Studio's layout imports `admin` (`app/javascript/admin.js`: `application` plus `controllers/admin/*`). CS Studio's controllers, `rich_text/*`, Tiptap/ProseMirror, SortableJS and D3 are all `preload: "admin"`, so they're modulepreloaded in CS Studio and never on a public page. Re-pinning Tiptap (`bin/importmap pin @tiptap/core @tiptap/starter-kit @tiptap/extension-link ...`) writes the new pins without that option — re-add `preload: "admin"` afterwards (`test/integration/public_javascript_test.rb` catches a miss).

`bin/rails rich_text:migrate_from_action_text` (`lib/tasks/rich_text.rake`) runs `RichText::ActionTextImport`, which orchestrates the conversion of every stored ActionText/Trix body — it never aborts partway and reports counts plus every unmapped fragment — handing each HTML fragment to `RichText::HtmlImport`, the per-fragment HTML → `RichText::Document` converter. The ActionText tables are dropped by a later, guarded migration (`db/migrate/20260928040000_drop_action_text.rb`) that refuses to run while unimported rows remain, unless `FORCE_DROP_ACTION_TEXT=1` overrides the guard.

### Media library

`Media::Asset` (`app/models/media/asset.rb`, table `media_assets` -- Zeitwerk would otherwise demodulize `Media::Asset` down to `assets`, so `self.table_name` is explicit, same as `Media::Usage`/`media_usages` below) is the one place any image enters the app: a `title`, translated `alt`/`caption` (Mobility jsonb, same backend and fallback chain as every other translated attribute), and a `has_one_attached :file` with four named, preprocessed variants (`VARIANT_WIDTHS`: `w480`/`w960`/`w1600`/`w2400`, `resize_to_limit` so none ever upscales, WebP, enqueued right after upload for every allowed type except GIF, which the global rule leaves unresized). `#srcset` only ever lists a variant with a finished `ActiveStorage::VariantRecord` -- never triggers or waits on processing itself -- so a slow, missing or failed transform just means fewer `srcset` entries, never a 500; `<img src>` (`#url`/`#src`) always points at the original regardless, and once there are variants the original is also the widest `srcset` candidate (when its width is known -- a browser never falls back to `src` once `w` descriptors exist). `#alt_text(override:, locale:)`/`#caption_text(override:, locale:)` are the one place the resolution order lives: a rich-text node's single-valued override (a String) wins outright, then this asset's own translation along the fallback chain; a *translated* override (a block's `alt`/`caption`, a page's `hero_alt`) is passed whole as its `{locale => value}` jsonb (`read_attribute`, not `translated(...)`) and interleaved per locale -- the override in a locale, then the asset in that locale, then the next locale -- so an override written in another language never beats the asset's default in this one. A page hero, an image block and a rich-text `image` node all call through these rather than reading `alt`/`caption` directly, and `Media::PictureComponent` (`app/components/media/`) is the one place every image render builds its `<img srcset sizes>` tag from (lazy by default; the page hero passes `loading: "eager", fetchpriority: "high"`). Allowed types are png/jpeg/gif/webp, byte-sniffed against the actual bytes (never a client's Content-Type header or filename), max 10 MB -- SVG stays refused everywhere, and the site logo stays its own separate `SiteSetting` attachment outside the library (moving it in, with the SVG sanitising that would need, is tracked in the roadmap, not built).

Three places reference a library asset -- `pages.hero_media_asset_id`, `content_blocks.media_asset_id` (both plain FKs to `media_assets` -- default NO ACTION, not `on_delete: :restrict`: Postgres 18 reports a RESTRICT violation as SQLSTATE 23001, which Rails doesn't map to `ActiveRecord::InvalidForeignKey`, so every `rescue` of it would miss; `MediaForeignKeysNoAction`) and a rich-text `image` node's `asset_id` (`RichText::BuiltIns`) -- and `Media::Choosing` (shared by `Pages::Save`/`ContentBlocks::Save`) is what lets *choosing* one need `media.upload` and an existing asset id while *clearing* it needs only the ordinary edit right already being checked, refusing a forged or nonexistent id as a validation failure on the field the editor sees rather than letting it reach Postgres as an FK-violation 500 (an asset deleted between that check and the write still hits the FK; `Pages::Save`/`ContentBlocks::Save`/`Posts::Save` rescue `ActiveRecord::InvalidForeignKey` into the same "doesn't exist" failure, `Media::Choosing#vanished_media_failure`). Embedding an image that's already in the library in *rich text* needs no `media.upload` -- it's content editing, covered by the right to edit the post or block, and only the asset's existence is validated (`RichText::BuiltIns`' `image` node); uploading a new image, and browsing the library in the picker, do need `media.upload`. Where an asset is actually used is entirely derived, never hand-maintained: `Media::Usage`/`Media::UsageIndex` (`app/models/media/`, table `media_usages`, unique on `(media_asset_id, owner_type, owner_id, role, locale)` with `nulls_not_distinct: true` so two rows that both have a nil `locale` still collide as "the same usage" instead of silently duplicating) rebuilds one owner's (`Page`, `ContentBlock` or `Post`) *entire* set of rows at once -- delete-then-reinsert, never an incremental diff -- from inside the same save/destroy service transaction that changed it; `bin/rails media:reindex` (`Media::UsageIndex.rebuild_all`) recomputes the whole table any time it's suspected stale (a bug, a direct SQL edit, a restored backup). `Media::Asset#used?`/`#usages_summary` read this table to back the library's "Unused" filter and a detail panel's "Used on" list, and it's the database's own FK -- not this table -- that's the actual guarantee behind "can't delete an asset that's in use" (`Media::Destroy`). Editing or deleting needs `media.manage` (seeded onto Admin and Editor) or, via `Media::Ownership`, being the asset's own uploader with `media.upload` alone -- see "Access control and audit" above for the full permission story, including how a token is judged.

CS Studio's own Media module (`Admin::MediaController`, `Admin::MediaLibrary::ToolbarComponent`/`GridComponent`/`TileComponent`/`PanelComponent`) is the grid/search/multi-file-upload home with one image's autosaving panel beside the grid (`/media?selected=ID`, keeping `q`, `filter`, `page`, `locale`; `GET /media/:id` is a 303 to it, and a trashed or missing id is a 404 either way). The segments All / Unused / Missing alt (default-language alt blank) / Untranslated (`missing` in any target language; hidden with one language) / Mine come with counts from one grouped query (`Media::Search#counts`: respects the search, not the segment, kept images only), and an autosave in the panel streams the tile, the counts and the panel's title back rather than reloading. The panel (`PanelComponent`) is the image's own autosaving form — language tabs, Title, Alt (a warn border while the default-language alt is empty and nothing is typed, `.admin-media-alt-warn`), Caption, "Used on", and "Move to trash…" with its reason and a link to where the image is used while it can't be trashed; a viewer who may not edit the image gets plain text and "Only the uploader or a media manager can edit this image." A tile is a link into `#content` that advances the URL, and `admin--media-panel` moves focus into the panel after a tile was chosen and back to that tile when the panel's × closes it (a plain load moves no focus). The screen carries `turbo-cache-control: no-cache` and `turbo-prefetch: false` in its head, like the editors, so Back never restores a panel with a stale base or stale chips. A missing, trashed or malformed `?selected=` is the 404, never a grid without a panel. The panel is a 340px column beside the grid from 1024px and stacks under it below that; the handoff's panel overlaying the grid between 1024 and 1279px is deliberately not built. It is searched through `Media::Search` (title, alt in any locale, and filename, one bound `:q` reused across all three ILIKEs -- shared with MCP below so both search the library the same way); `Admin::MediaAssetsController` is a separate, narrower upload-only JSON endpoint for `Media::PickerComponent` (`app/components/media/`, the one modal dialog that every hero/image-block field -- via `Admin::Columns::MediaColumnComponent` -- and the Tiptap editor's Image button open) -- two unrelated callers sharing `Media::Upload`, not one feature split across two endpoints. **Uploading** is drop-anywhere on the Media screen (`admin--media-drop`: a file drag, only one carrying `Files`, shows the "Drop images to upload" overlay, counted `dragenter`/`dragleave`, gone on drop, Escape, `dragend` or a stale `dragover`) plus the header's "Upload images"; every file becomes a progress tile at the start of the grid and goes up one at a time (`app/javascript/media/upload_tiles.js`, shared with the picker; XHR for the bar), and the answer (`Admin::MediaUploadResponses`: `id`, `title`, `url`, the finished tile's HTML and the new `counts`) swaps the tile in with nothing reloading, so a finished upload never replaces the panel under a typing editor. A refused file (wrong type, over 10 MB, SVG -- the server decides) keeps its own tile with the reason and Dismiss. The queue is module-level so a tile click (a frame navigation) re-attaches the tiles still going up to the new grid. **The picker** (880 dialog hanging from a fixed top edge, `.admin-media-picker`) is the same toolbar and tiles inside its own frame `media-picker-grid` (`GET /media?picker=1`, `media.upload`-gated, kept images only; every segment but Untranslated), choosing is select-then-use (a click selects, **Use image** confirms, a double click does both; `admin--media-select` holds the choice across searches), its header **Upload** selects the first finished upload, and Escape clears a typed search before a second one closes. New page and New post hang from the same fixed top edge (`Admin::DialogComponent`'s `hang:`). MCP exposes the library read-only as `list_media_tool`/`get_media_tool` (`app/mcp/mcp/tools/`); `list_media_tool` pages 50 per call through a `page:` argument. It is the only MCP list tool that pages: `list_posts_tool` returns every readable post in one answer (without bodies), which is a roadmap row. `db/migrate/20260929050000_move_images_into_media_library.rb` moved every legacy `Page#hero_image`/`ContentBlock#image` Active Storage attachment into this one storage path -- deduping identical files by blob checksum, recording which assets it created in a ledger table (`media_library_migrated_assets`, so its own `down` can roll back cleanly without touching a pre-existing or later-uploaded asset), leaving in place (and reporting, never silently dropping) any attachment whose blob type the library refuses, and adding the `rich_text` usage rows for bodies that already embedded a library image (rich-text uploads and ActionText-imported images predate the index; without those rows such an image reads as "Unused" and can be deleted -- a rich-text reference has no FK). `20260929070000_backfill_rich_text_media_usages.rb` runs that same additive, idempotent SQL for databases that ran the move before it did, and `RichText::ActionTextImport` refreshes each owner it writes. `bin/rails media:orphans` lists (and, with `CONFIRM=1`, purges) blobs with no attachment at all -- duplicates that migration deliberately never deleted, plus ActionText leftovers -- and `bin/rails media:variants` re-enqueues whichever of a non-GIF asset's four named variants still has no `VariantRecord` (a failed or lost job, an asset that predates a width), idempotent since it only ever looks at what's actually processed, never at what's currently queued. Interim state: until a variant has actually been processed, a page serves the original file at full size. `ActiveStorage::VariantRecord`'s own max id/count feed `PublicSite.content_version` (see "Rich text" above) -- a newly processed variant is exactly the kind of change that can make a page's already-cached render worth invalidating.

### Trash

Pages, posts and library images are soft-deleted (spec `docs/superpowers/specs/2026-09-29-trash-design.md`); a single block, a tag, a group, a user or a token is still deleted for good. Columns: `trashed_at` (indexed) and `trashed_by_id` (FK to `users`, `on_delete: :nullify`) on `pages`/`posts`/`media_assets`, plus `pages.trash_root_id` (FK to `pages`, `on_delete: :nullify`) naming the page an editor actually picked, and `site_settings.trash_retention_days` (default 30, `0` = never purge automatically, edited in CS Studio's Settings module). `Trashable` (`app/models/concerns/trashable.rb`) gives `kept`/`trashed` scopes and `#trashed?` -- deliberately **no `default_scope`**, which would silently hide rows from closure_tree, uniqueness checks, associations and the Trash screen itself. Hiding is explicit instead, at the narrowing points: `AccessControl.scope` (kept only unless called with `trashed: true`, which only the Trash screen does -- so every CS Studio list, the tree, pickers, `/preview`, MCP and the "not found, not forbidden" id lookups inherit it), `PublicSite::Resolver` (and its listing-page fallback), `listed_posts`, navigation, internal-link rendering (a link to a trashed page or post renders as plain text), the sitemap, the related-posts editor, the media library/picker/search, `Media::Choosing` and rich-text image validation (a trashed image reads as missing), and MCP's post and media tools. `test/integration/trash_visibility_test.rb` pins every one of them with a kept-vs-trashed pair; a new list, search, picker or public query over pages, posts or images belongs in it. URLs are freed through `PublicSite::Paths` itself, not by any trash code: `compute_path` returns nil for a trashed record and `canonical_page` ignores listing blocks on trashed pages, so saving a changed `trashed_at` deletes (on trash) or rebuilds (on restore) the record's `public_paths` rows -- redirects included, not recreated on restore -- through the ordinary model callbacks, and nothing (`rebuild!`, `sync_posts`, a save elsewhere) can resurrect a trashed record's URL. The public site answers 404 for a trashed page or post, not 410. `Page::TreeRanking` counts kept siblings only, so "move to rank N" means rank N among the pages an editor can see.

Four services (`app/services/trash/`), all `ApplicationService`s, audited as `page|post|media.trashed/restored/purged` and `trash.emptied`. `Trash::Move` trashes a page with its whole kept branch (descendants flagged with `update_all`, one shared timestamp and `trash_root_id`, root saved last so a single `sync_subtree` pass sees them trashed; a descendant already trashed on its own keeps its own root) -- the root saved with `save!(validate: false)`, callbacks still running, so a record that has gone invalid since its last save (an unregistered content type, a reserved slug) can still be cleared away, while `Trash::Restore` keeps full validation -- and refuses an image while a *kept* page or post still uses it (`Media::Asset#used_by_kept_owner?`) -- which is what makes it safe that rich-text image rendering never looks at an asset's trash state. `Trash::Restore` brings back exactly the pages sharing the root's `trash_root_id`; a page trashed as a branch member comes back only with its root, or alone under a new `parent:` (same checks as `Pages::Move`: `pages.move` on the page, `pages.create` under the target, never itself or a descendant; the CS Studio picker is a server-rendered `<select>` of the pages `AccessControl.creatable_parents` offers). The chosen parent is loaded through the read scope: one the actor can't read, a trashed one and an id that names nothing all get the same plain failure (`Trash::Restore::UNKNOWN_PARENT`), never a 403 or an `access.denied`. Slugs were free while in the trash, so a slug taken in the meantime moves to the first free `-2`, `-3`, ... suffix, per locale (taken in `de` but free in `en` changes only `de`). Restoring a page or post also restores every trashed library image its hero, blocks or bodies still reference, each with its own `media.restored` event (metadata `restored_with`), so a restored page never points at a trashed image; a page's own `page.restored` lists the branch members that came back in `restored_page_ids` (mirroring `page.trashed`'s `descendant_ids`). A refusal that names a branch's root names it by title only when the actor may read it (`Trash::ItemPermissions#branch_root_name`), "the page it was moved to the trash with" otherwise. `Trash::Purge` is the permanent delete `Pages::Destroy`/`Posts::Destroy`/`Media::Destroy` used to be: a page takes its whole subtree deepest first (all of it must be trashed), recording one `page.purged` per destroyed page -- the root's listing the rest in `descendant_ids`, each descendant's naming the root in `purged_with` -- and is refused for a member of another page's still-trashed branch -- purge the root instead; an image goes only once no usage row at all points at it (trashed owners included), an FK violation becoming an ordinary failure, the file purged after commit. `Trash::Empty` runs `Purge` over `Trash.roots` (page branches, then posts, then images -- so an image's trashed owners are gone first), each item in its own savepoint, reporting what it skipped -- an exception out of one item's purge is rescued into a skip ("Couldn't be deleted: <class>"), so the rest still go and `trash.emptied` is still recorded; the retention job rescues and logs the same way. Permissions (`Trash::ItemPermissions`): moving, restoring or purging one item needs its ordinary delete right (`pages.delete`/`posts.delete` with their scopes, or for an image `media.manage` / uploader with `media.upload`); `trash.empty` (Admin only) empties everything **and** permits purging any single trashed item, never moving or restoring. `Trash::PurgeExpiredJob` (`app/jobs/trash/`) purges roots older than the retention period via `Trash.each_root(trashed_before:)` (re-finding each root at its turn, so a subpage already swept by an ancestor's branch purge isn't purged twice), as the trusted nil actor on the `:system` channel; it's scheduled in `config/recurring.yml`, which only runs where Solid Queue is the adapter (production -- development and test use the default adapter, so nothing purges on its own there).

CS Studio: `Admin::TrashController` (`/cs-studio/trash`) lists page branch roots ("Includes N subpages: A, B, C and N more", the names only of pages the viewer may read, the count every member a restore brings back; a branch member whose root is gone from the trash is a row of its own with an inline "Restore under"), posts and images newest first, 50 per page (`Pagination` / `Admin::PaginationComponent`, the page in `?page=`), in tabs (`?type=pages|posts|images`, junk means All) whose counts are `TrashController.counts` -- the very numbers the sidebar badge sums -- loaded only through `AccessControl.scope(..., trashed: true)` on the delete right (so an id the viewer can't act on is a 404). A row shows who and when, "<who> · <time ago>": "You" or the user's `display_name` from `trashed_by`; when that is nil (the user was deleted, or the FK nullified it) the newest `*.trashed` audit event stands in, read for the whole page in one query — its user's name, "a deleted user" when that user is gone, with "via <token name>" appended for a change made through a token — and "System" when there is no such event or it has no user or token. a retention tag (`RetentionTagComponent`: IN N DAYS / TODAY / NEVER, calendar days in the site zone, the date as tooltip and screen-reader text), Restore and "Delete now…" (disabled with its reason as visible text while the trash still uses an image). "Empty trash…" in the header (`EmptyTrashComponent`) counts everything `Trash::Empty` deletes, not the viewer's tab counts. Restore, delete and empty sit behind `Admin::ConfirmDialogComponent` where destructive, and come back to the tab they were done from (hidden `tab` field). The editors' delete buttons are "Move to trash" now, and the toast (`flash[:undo]`, see "CS Studio design system") offers Undo. Its components live under `Admin::TrashScreen::`, never `Admin::Trash::` -- see "Key Conventions".

### Translations

Spec `docs/superpowers/specs/2026-10-02-translation-helpers-design.md` (read its §10 Amendments, which override the text above them). The original is always `Locales.default` (`Translations.primary_locale`, read at the time of use, never cached), and every other enabled language is a translation of it (`Translations.target_locales`).

**Tracking.** `Translations::Tracker` (`app/models/concerns/translations/tracker.rb`, `tracks_translations` on `Page`, `Post`, `ContentBlock`, `Media::Asset` and `SiteSetting`) records which version of the original each translation was saved against. `translation_sources` is a jsonb column on each of those tables, `{ field => { locale => entry } }`, where an entry is one of two shapes that stay valid side by side (every reader goes through `Translations::Source.wrap`, so a record holding both never raises): the bare sha256 of the original (everything saved before the design pass: it can answer "current or outdated" but has no text to diff) or `{ "digest", "text", "saved_at", "from" }` — the original's text as it was (a String, or an Array of paragraphs for rich text), when, and in which language. When a target-language value changes, a `before_save` stores the current original's entry for it, or deletes the entry if the value is now blank. The text is what `Translations::SourceDiff` word-diffs the original's current text against; `Source#comparable?` is true only when text is stored *and* `from` is the current primary locale, so after a default-language change the stored text (in the old language) is never diffed against the new original. `SourceDiff` is pure and bounded — `MAX_WORDS` (4,000) per text and one `MAX_CELLS` (4 million) table budget per call, common prefix and suffix trimmed first, paragraphs matched before words — and answers `too_long?` rather than build an expensive table. The other column is `translation_original_changed_at`, `{ field => ISO-8601 }`: when each field's *primary-language* value last changed (by digest, so a whitespace-only edit isn't one; blank → filled counts), written by the Tracker's `before_save` and nothing else; it is what the translations matrix sorts by and the reference card's "CHANGED <time ago>" reads. A change to the original itself never touches `translation_sources`, which is exactly what makes the other languages outdated. Digests come from `Translations.digest`: a stripped string with line endings normalised to LF for plain values (a browser submits CRLF; the changed-value check normalises the same way, so re-submitting an unchanged multi-line value is never an edit), `RichText::Document#normalized` for rich text (so a normalisation-only change isn't an edit), and canonical key-sorted JSON for a schema group field. The tracked fields are derived from the model's own Mobility `translates` names minus `slug`, plus its content or block type's `translated: true` schema fields. Don't list them anywhere a second time. `#translation_state(field, locale)` returns one of:
- `:missing`: blank;
- `:unknown`: present but no digest. This covers everything saved before the feature, and any field whose original is now blank. It never reads `:outdated`, so deploying flags nothing;
- `:outdated`;
- `:current`.

Every read is literal per locale, never through a fallback. The original's digest is memoised per record and field (and a schema reader's per-locale FieldSet per locale), checked against the stored value it came from and dropped on save, reload and confirm, so a status read digests each original once, not once per target language. `translation_sources` and `translation_original_changed_at` are bookkeeping: they're kept out of audit `field_changes` (`Audit::Snapshot::IGNORED_CHANGES`) but stay in the snapshot.

**Status.** `Translations::Status.for(records, locales:)` (`app/models/translations/status.rb`) rolls fields up to one state per record and locale, in this order of precedence:
- `:missing`: a required translated field is blank. That's the title, a required schema field, an image's alt when its original has one, or the site title;
- `:outdated`: any tracked field is outdated;
- `:complete`: neither. `:unknown` counts as complete.

A page's or post's blocks roll into it, loaded in one query per batch.

**The stored states.** Where a record stands is a table, `translation_states` (`Translations::State`; `record_type`, `record_id`, `locale`, `state` = `complete`/`missing`/`outdated`), one row per page, post, library image and the site settings, per target language — so a list can `WHERE`, `COUNT` and page on it instead of working states out per record. `Translations::StateIndex` (`app/models/translations/state_index.rb`) is the only writer and computes through `Translations::Status`, so the two always agree: `refresh(record)` (a block refreshes its *owner*), `remove(record)`, `rebuild_all`, and the readers `states_for(records, locales:)` and `counts_for` (one query; a record, or a locale, with no row reads `:complete`), `joins`, `summary` / `summaries` (grouped SQL per type, however many languages) and `exists_in_any_locale_sql`. It is derived data, like `public_paths` and `media_usages`: never written by hand, refreshed inside the same transaction as every save that can change a state — the save services, a block's save and destroy, `Translations::Confirm`, `Trash::Purge` (`remove`), and a language being enabled, disabled or made the default (`Locales::Enable`/`Disable`/`MakeDefault`, and `Settings::Save` when it is handed a changed `default_locale` or `locales`, as the setup wizard does: `rebuild_all`, **synchronously**, proportional to the site's size; a reorder or a fallback change through `languages:` rebuilds nothing) — so a rolled-back write leaves the rows alone, and a trashed record keeps its rows. `bin/rails translations:reindex` rebuilds everything when it is suspected stale (a bug, a direct SQL edit, a restored backup). `test/services/translation_state_parity_test.rb` is the guard against a write path that forgets it: one scenario per service, after which the stored rows must equal a fresh `Translations::Status`; a new service that changes what a state is computed from belongs in it. Two limits follow from the table being derived: a deploy that adds a required translated field leaves rows stale until `translations:reindex`, and a record created outside the services (a console `create`, a test) has no row, reads complete and is absent from the matrix and the counts until it is next saved or reindexed. Where it shows:
- the language tabs (`Admin::LanguageTabsComponent`), which show missing and outdated as independent markers (`Admin::TranslationChipComponent` draws the same two states in lists, the tree and the matrix);
- each outdated field's reference card (see "Translation pair" above);
- the posts list's Languages column and its Translation filter (`needs` / `outdated` / `complete`, an EXISTS over the target languages);
- the page tree's ↻N / ○N counts;
- the dashboard's "Needs translation" card;
- the **Translations matrix** (`Admin::TranslationsController#index`, `/<admin>/translations`): a summary card per target language ("% done", a bar, "12 missing · 1 outdated"), a type filter (`?type=page|post|media|settings`, only the types the viewer may read), `?language=de` (a summary card's link: only the rows that need work in that language, all columns stay), and a matrix whose rows are the items that need work in *any* target language and whose columns are the languages — each cell that language's chip, linking to the item's editor in it. Rows with an outdated language come first (they are already visible on the site), the most recently changed original first (`StateIndex.original_changed_at_sql`, blocks rolled in), then rows that only miss something in the same order. It lists exactly what the actor may read (pages and posts through `AccessControl.scope`, images only for a `media.upload` holder, the site settings row only for `settings.manage`) and is filtered, counted and paginated in SQL — each type contributes its own ordered window and the page is merged in Ruby, so the cost is proportional to the page, not the site; the settings row tops page 1 and is never paged. A retired `?locale=` is ignored.

`Translations::EditRight` is the one "may edit this record" rule shared by Confirm and `AI::Translate`:
- pages and posts: `edit`, plus `publish` when published;
- blocks: `ContentBlocks::OwnerPermissions`;
- images: `media.manage` or the uploader with `media.upload`;
- the site settings: `settings.manage`.

Confirming records `<page|post|block|media|settings>.translation_confirmed`. **Still correct — mark up to date** streams the card's current variant and, once a language has nothing else outdated, removes the language tab's marker (`Admin::TranslationConfirmationsController`).

**Site title and tagline** are translated: `SiteSetting` `translates :title, :tagline`, jsonb. The title must be present in the default language, and changing the default language copies the title and tagline from the old default when the new one has none. Public readers use `translated(theme_site, :title)` (with fallback). The Settings form holds every enabled language's title and tagline at once (see "Settings" under the design system); `?locale=` only picks the tab shown first (the Translations matrix's `?locale=` is retired). `Settings::Save` takes them through `translations:` only, never `attributes:`.

**AI translation.** `AI::Providers` (`app/models/ai/providers.rb`) is a registry like the others: the built-in `anthropic`, plugins `owner/name`, a duplicate raising `AI::DuplicateProvider`, reset and re-registered in `config/initializers/types.rb`'s `to_prepare`. A provider answers `new(api_key:, model:)`, `#translate(texts:, from:, to:, format: :plain | :markdown)` and `#test_connection`, and raises `AI::Error` with a message fit to show the editor. `AI::Providers::Anthropic` uses the `anthropic` gem with a 25 s timeout, `max_retries: 0` and a pinned `base_url`. `AI.configured?` / `AI.provider` / `AI.model` (default `claude-sonnet-5`) read the `SiteSetting` row's `ai_provider`, `ai_model` and `ai_api_key`, which are configured under Settings → "AI translation" with `settings.manage`. Zeitwerk inflects `ai` → `AI` (`config/initializers/zeitwerk.rb`).

`AI::Translate` (`app/services/ai/translate.rb`) needs `ai.translate` (seeded onto Admin and Editor) **and** the record's edit right (`Translations::EditRight`). It sends the primary-language values of the requested fields (blank ones skipped; rich text as Markdown, back through `RichText::Document.from_markdown`, the MCP round trip), capped at 20 fields and 6,000 characters per request. It returns **suggestions only**: it never saves. It records `ai.translated` with metadata `fields from to provider model characters` and **no snapshot**, so no text reaches the audit log.

**AI requests run inside the web request.** A suggestion request makes at most two provider calls (plain fields, then rich text), each bounded by the 25 s timeout, and holds one Puma thread for as long as it waits (`RAILS_MAX_THREADS`, 3 by default, `config/puma.rb`): a few editors running "Suggest translations for N empty fields" at once can starve the site of threads for that long. In production kamal-proxy sits in front, and its default 30 s response timeout would cut requests off, so `config/deploy.yml` sets `proxy.response_timeout: 75` (`test/models/ai/providers/anthropic_test.rb` keeps it above twice the provider timeout). Keep the timeout, the cap and the proxy setting in step when changing any of them. The long-term route is a background job (Solid Queue) that streams suggestions back over Turbo, tracked in the roadmap.

**The suggestion flow.** In the editor, an *empty* translated field in a non-default language gets a Translate button under its input and an outdated one a **Suggest update** in its reference card (both `Admin::TranslationScreen::TranslateButtonComponent`, `admin--translate`; shown only to a viewer who may edit the record, with AI set up and `ai.translate`), and the header gets "Suggest translations for N empty fields" (`TranslateAllComponent`: idle, running — "Suggesting i of n fields", a bar, Cancel — and ready — "N suggestions ready · Use all · Discard all"). Requests are `fetch`es, never form submissions (the buttons sit inside autosave forms): `POST /<admin>/translations/suggest` (`Admin::TranslationsController#suggest`) answers with Turbo Streams — at any status, a refusal or provider error being a stream too — putting a suggestion box under each requested field, with Use / Discard, or the inline error. The bulk run splits per record and by `AI::Translate::MAX_FIELDS`/`MAX_CHARACTERS` and sends the parts one after another, so each fits the provider's timeout, progress shows and earlier parts survive a later failure or Cancel. While a request is out the field's box holds a pending box (`PendingComponent`, cloned from a `<template>` in the layout): a spinner, the seconds waited, Cancel — and after 25 s (`PendingComponent::TIMEOUT_SECONDS`, the provider's own timeout) "No suggestion after 25 seconds." with Try again; a late answer for a box that timed out is ignored unless Try again was pressed. `mode=update` (Suggest update) additionally shows the field's current translation ("Current: …", read from the record, never sent to the provider) so the editor can compare before pressing Use, which replaces the value; the bulk run skips fields that already have a translation. **Use** is the only write: it fills the input (a rich-text body through a `translate:use` event handled by `admin--rich-text#applySuggestion`) and a bubbling `input` event lets the form's own autosave save it as an ordinary edit, which records a fresh digest and text. **Use all** presses every Use, plain fields first, then rich text, through the write queue. A plain suggestion sits in an editable textarea with no `name`, so it never feeds an autosave until Use.

**The API key** is stored with `encrypts :ai_api_key` and is never rendered, logged (the `_key` parameter filter), or put in an audit snapshot (`Audit::Snapshot::NEVER_STORED`). It is not a field of the Settings form: it has its own Save key and Remove forms and endpoint (`Admin::AiKeysController`, see "The AI translation card" under the design system), Remove asks through `Admin::ConfirmDialogComponent`, and `ai_api_key_saved_at` records when it was saved. `SiteSetting#ai_api_key_set?` checks the stored ciphertext without decrypting it, so lost encryption keys never break the Settings screen. A key that can't be decrypted makes a provider call fail with a message asking for the key to be entered again.

**Active Record encryption keys.** Development and test use fixed, public keys (`config/environments/development.rb`, `test.rb`), so a checkout and CI need nothing. Production must provide `primary_key`, `deterministic_key` and `key_derivation_salt`, in one of two ways:
- in the credentials, as `active_record_encryption.*` (`bin/rails db:encryption:init` prints a fresh set);
- as the env vars `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY`, `ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY` and `ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT` (`config/application.rb`; for Kamal, see the comment in `.kamal/secrets` and add them to `env: secret:` in `config/deploy.yml`).

Precedence is per key: an env var that's set wins over the credentials for that key alone. Setting only some of the env vars therefore mixes two key sets, so keep all three in the same place. Nothing checks for the keys at boot. A server without them runs normally until someone saves an AI key, which then raises. Once keys are set, keep them: losing them makes the stored AI key unreadable, and the fix is to remove it and enter it again.

## Key Conventions

- **No RSpec** — Minitest + fixtures (`test/fixtures/`), not factories.
- **No Devise / no ActiveAdmin** — auth and admin (CS Studio) are both hand-rolled as described above; don't reach for those gems' idioms.
- **No npm/webpack** — JS is import-maps only (`importmap-rails`); CSS is Tailwind via `tailwindcss-rails` (`bin/rails tailwindcss:watch` in dev).
- **Long, load-bearing code comments are the norm in this codebase**, especially in `page.rb`, `content_block.rb`, `post.rb`, and `routes.rb` — they document non-obvious invariants and past incidents (e.g. the Accept-header 500, the two-pages-one-URL collision). Read them before changing the code they annotate, and match that density when adding similarly non-obvious logic; don't strip them out during cleanup.
- **Never define `Admin::Media` or `Admin::Trash`** — either module would shadow the top-level `Media`/`Trash` namespaces (models and services) for every bare `Media::`/`Trash::` reference lexically inside `module Admin`, a `NameError` that has already shipped once mid-task. That's why the media library's admin components are `Admin::MediaLibrary::` and the Trash screen's are `Admin::TrashScreen::`; `test/lib/admin_media_namespace_test.rb` and `test/lib/admin_trash_namespace_test.rb` guard both. The same goes for **`Admin::Translations`, `Admin::AI` and `Admin::Ai`**, which would shadow `Translations::`/`AI::`. The translation screens' components live under `Admin::TranslationScreen::`, and `test/lib/admin_translation_namespace_test.rb` guards it. The same goes for **`Admin::Audit`** (it would shadow `Audit::Event`/`Sentence`/`Filter`): the audit log's components live under `Admin::AuditScreen::`, guarded by `test/lib/admin_audit_namespace_test.rb`. And for **`Admin::Dashboard`** (it would shadow the `Dashboard::` queries): the dashboard's components live under `Admin::DashboardScreen::` (not test-guarded). A screen's components go in a namespace named after the *screen*, never after a domain module: besides those, `Admin::EditorScreen::`, `Admin::PostsScreen::`, `Admin::SettingsScreen::`, `Admin::TokensScreen::`, `Admin::GroupsScreen::`, `Admin::UsersScreen::` and `Admin::Shell::` (none of these is test-guarded; `Settings::`, `Groups::`, `Users::` and `ApiTokens::` are service namespaces a bare `Admin::Settings` and so on would shadow the same way). The Tags screen has no components of its own.
- **Dependency order.** Models, queries (`app/queries`) and services know nothing of components, helpers or controllers. Components may know models and queries; controllers orchestrate services and never write a record themselves. A model or query that needs *wording* returns data and a component renders it: `Audit::Sentence` is the actor as facts, the sentence as parts and the subject as a route *name* with its arguments, and `Admin::AuditScreen::SentenceComponent` turns that into a name, markup and a URL; `Dashboard::Activity` returns rows holding such a sentence and builds no component. Route resolution happens in components and controllers, from a fixed set of route names the lower layer may hand up (`Audit::Sentence::Route`), with the request's own URL options. The reason is the direction of change: a screen is rebuilt far more often than a rule, and a model that renders, or a query that picks a component, has to be rewritten with every screen that shows it — and can't be used from MCP, a job or the console, where there is no view. Among the domains the same direction holds: `RichText` and `ContentModel` at the bottom, then `AccessControl` and `Audit`, the content models, the derived indexes (`PublicSite`, `Translations`, `Media`), services, and controllers and components on top; a lower layer never references a higher one. The inversions that still exist are listed in the roadmap's Technical health section (M1) and are not a pattern to copy.
- **Design docs**: `docs/superpowers/specs/` and `docs/superpowers/plans/` hold the original design specs and implementation plans this app was built from — useful background when a change touches the page tree or content blocks.
