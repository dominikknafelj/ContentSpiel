# Backups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every ContentSpiel site deployed from the site template backs up its primary database and its files volume once a day, encrypted, to an S3-compatible bucket, can be restored by a written runbook (which jumps the content version past its old values), and System status and the alerts say when the newest good backup is too old.

**Architecture:** A plain-Ruby command in the image, `bin/backup` (`ContentSpiel::Backup` in `lib/content_spiel/`, standard library only, no Rails boot), runs `pg_dump` and `restic` through an injectable command runner and writes a status file into the files volume. The web app reads that file (`ContentSpiel::Backup::Status`) for a "Backups" row in `Setup::SystemCheck` and for a new alert kind, `backup_stale`, raised by `Alerts::CheckJob`. The site template gains a commented `backup` accessory running the CMS image at the site's pin; `contentspiel upgrade` prints that block for older sites. `bin/rails public_site:after_restore` closes the roadmap's restore trap.

**Tech Stack:** Ruby 3.4 / Rails 8.1, Minitest, restic (Debian trixie package, 0.18) and `postgresql-client-17` in the image, Kamal accessories, GitHub Actions (`image.yml`).

**Spec:** `docs/superpowers/specs/2026-11-17-backups-design.md` (binding; read it whole before any task).

## Global Constraints

- Generic for every site: no guide-specific name, bucket, provider or path in the CMS or the template; tests use the default theme or `test/fixtures/themes/` (`feedback: CMS changes are generic`).
- Never print a secret: `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `POSTGRES_PASSWORD` never reach stdout, stderr, the status file, a log line, an alert, a mail or a page. `BACKUP_REPOSITORY` is not printed either (it names the destination; System status names "no snapshot id, no destination"). No tool's own message (restic's, pg_dump's) is ever printed or stored by `run`/`schedule`: a failure is one of the fixed reasons `destination_unreachable`, `wrong_password`, `database_unreachable`, `disk_full`, `other`.
- Recovery targets, verbatim: RPO 24 hours; RTO 2 hours; retention `restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune`; integrity `restic check --read-data-subset=n/12` once a month, n the month.
- Status file: `/rails/storage/backup/status.json` (i.e. `<app root>/storage/backup/status.json`), excluded from the backup itself; the command writes nowhere else in the files volume.
- System status: two states only, `:ok` and `:warning`; ok while the newest good backup is younger than **26 hours**. Alert `backup_stale` at **48 hours** or a failed monthly check, one alert per UTC day, no audit-log link. A single failed run alerts nothing.
- `pg_dump` major version ≥ the template's Postgres major (17).
- `BACKUP_HOUR`: 0–23 UTC, default 3. The web container gets none of the backup variables.
- Every admin string is an i18n key (`config/locales/admin/…`); mail strings in `config/locales/mail.en.yml`.
- "No compatibility code before it is needed"; comments state current invariants, never plan steps or history.
- `CHANGELOG.md` `## Unreleased` changes with this work. Alert kinds are a model constant validated in Ruby (`Alerts::Alert::KINDS`, no database enum or check), so **no migration**.
- Any server you start for a manual check listens on port **3212**, never 3100 (`bin/rails server -p 3212`).
- Kamal commands written into docs and output are checked against `bin/kamal help accessory` of the version in `Gemfile.lock` before they are committed.
- Run `bin/rubocop` on touched files before each commit; the full unit suite (`bin/rails test`) before the last.

## Review Focus

1. **Retention that never forgets.** restic groups snapshots by host and paths; a container's random hostname or a random dump folder makes every snapshot its own group, so `forget` keeps all of them and the bucket grows forever. Expected: every snapshot is made with `--host <BACKUP_SITE>` and the same two paths. Test in Task 3: "every snapshot is taken with the site as its host and the same two paths, and forget narrows to that host".
2. **An alert re-mailed every hour.** `Alert.due` mails again an hour after the mail when `last_seen_at` moves; a check job that updates the day's row every minute would remind hourly. Expected: one mail per day while stale. Test in Task 6: "a stale backup seen every minute of a day is one row, mailed once".
3. **A torn or foreign status file.** The web reads the file while the accessory writes it, and a person may edit it. Expected: atomic write (temp + rename), and an unreadable file is a warning row, never a 500 and never an alert storm. Tests in Task 2 ("a write is whole or absent: a temp file and a rename") and Task 5 ("an unreadable status file is a warning that says so").
4. **A missing secret that hangs.** Without `POSTGRES_PASSWORD` pg_dump may prompt; without `RESTIC_PASSWORD` restic may read stdin; the accessory would hang forever. Expected: the command names the missing variable (name only), writes a failed status with the matching reason and exits 1; children get `--no-password` and a closed stdin. Test in Task 3: "a missing secret is named, recorded as its reason, and no tool is started".
5. **A tool that echoes a secret.** restic or pg_dump may print an environment value or a URL in an error. Expected: nothing of a tool's output reaches stdout, stderr or the status file during `run`; `list` and `init` pass restic's stdout through with every secret value replaced by `[hidden]`. Test in Task 3: "a tool's message holding every secret reaches neither the output nor the status file".

## Rulings on the spec

Where the spec contradicts itself or names something that does not exist, the plan rules:

- **Accessory image.** "The site template" says `image: <the site's image>`; "Which image the accessory runs" (dated, with reasons) says the CMS image at the pin. The dated decision wins: `<cms_image>:<pin>`.
- **Two states, not three.** "Tests" says "the System status row's three states"; "System status" decides two (ok, warning). Two.
- **No Dashboard attention list exists** (the Dashboard draws no checks): no Dashboard change; owners are reached by the alert.
- **"The template's `postgres_version`"** is no variable: the image test reads `image: postgres:NN` from `deploy.yml.tt`.
- **restic `local:` in tests.** Neither restic nor pg_dump 17 is on a laptop or a CI runner, and CI installs nothing at test time for this: the unit suite drives a fake runner; the real tools run against a `local:` repository in `image.yml`'s `site-template` job (main, and by hand on a branch).
- **`media:orphans`** walks blob rows and never the disk, so it already skips `storage/backup`; a test pins it, no code changes.
- **No migration:** alert kinds are a Ruby constant.
- **"A link to the guide page":** the guide's URL is not in this repository; the row links `docs/reference/backups.md` at the running version's tag, as the Visitor address row links its reference.
- **Unspecified, decided here:** an uninitialised repository is `destination_unreachable`; a failed monthly check is retried at the next run; the day's alert is inserted once (no hourly reminders); no alert for a site with no status file; `PGUSER` (default `postgres`) because CI's superuser is `content_spiel`; `BACKUP_SITE` names the snapshots' host and tag.
