# ContentSpiel roadmap

Living document (started 2026-09-26, consolidated 2026-10-05). ContentSpiel is a **generic, self-hosted CMS** that non-technical editors enjoy using and developers can extend without forking. Priorities: **Must** (needed before we'd call it a usable generic CMS), **Should**, **Could**. Refactors are judged against this list: they must open the seams these items need and never make one more expensive.

How to read it: **Next** is the agreed order of sub-projects. **Before the first deploy** is everything that must be true before a real site runs on this. **Product backlog (Phase 3)** and **Technical health** are grouped by topic, not ordered. **Known gaps** lists what was knowingly shipped incomplete, each under the item that closes it. What is done is one line under **Shipped**; the history is in git and in the specs.

Sources: product review (`docs/product/2026-09-26-backend-product-review.md`), code-structure review (`docs/architecture/2026-09-26-code-structure-review.md`, findings `#N`, sections `§N`), staff review (`docs/architecture/2026-10-04-staff-review.md`, findings `S`, `M`, `L`, `D`, `C`, `O` plus a number), and the specs under `docs/superpowers/specs/`.

## Version 1: a solid foundation

Decided by the owner on 2026-10-11: the first stable version is the focus, and everything else on this roadmap is sorted after it. Version 1 is five things; the order is the order of meaning, not a schedule.

1. **Editing is safe.** Live editing (shipped, PR #66) and drafts of live content (shipped 2026-10-12, under "Shipped"): two people can work on one page, and nothing typed into a live page reaches visitors by itself.
2. **Theming as a real mechanism.** Shipped 2026-10-12 ("Shipped"): a site keeps a theme folder in its own repository, sets `THEME_PATH`, and is drawn by it, with the default theme behind whatever the folder does not hold and a written contract. The Code block joined the contract on 2026-10-12 ("Shipped"), the first block type to do so after it was written. Still open, each its own work: a published CMS image, and the documentation theme's move from the spike's shape to the contract's (in `contentspiel-docs`; "Next", item 9, has the list).
3. **It can be hosted properly.** The items under "Before the first deploy" move ahead of features, beginning with the gaps the dry run found ("Hosting and the dry run" there). The first of its four parts, "safe on a public address", shipped 2026-10-12 (under "Shipped"); mail, the sitemap and starting up, and the setup wizard follow in that order.
4. **The documentation site runs in public.** `contentspiel-docs` ("Next", item 9) is the first real integration, and is used as the prototype that finds the gaps in 2 and 3.
5. **Pages as nodes in the mind graph** (the owner's decision): the graph shows posts and tags today; pages join it. Designed in two steps (`docs/superpowers/specs/2026-10-12-pages-in-the-mind-graph-design.md`): step one is pages, the tree and what a page lists; step two, links in the text, is under "Dashboard and CS Studio". **Step one is built** (2026-10-13, on the branch `pages-in-graph`; its pull request's number goes here once it has one): it is under "Shipped", and what it left open is under "Known gaps", "Pages in the Mind graph". Step two is the next piece of the graph.

## Decisions already made

| Decision | Detail |
|---|---|
| Our own admin, not Avo | Rails + Hotwire, product design tokens (`--cs-*`). Avo is removed. |
| Admin layout | Three columns: modules, page tree, content. |
| Rich text | Tiptap: one Tiptap/ProseMirror JSON document per locale, rendered to HTML on the server, Markdown for AI and MCP (custom nodes as directives). Node types come from a registry (the plugin seam). |
| Independent CSS | Product UI and public theme are separate Tailwind builds with separate tokens (`--cs-*` and `--th-*`); the demo look is only the default public theme. |
| One PR per body of work | Bugfixes and features of a round ship together; no production exists yet. |
| Two repositories | `ContentSpiel` is the CMS and holds no guide text. `contentspiel-docs` is the documentation site: its content, its theme and its hosting, and the first real integration of the CMS ("Next", item 9). There is no third repository. |

#### Release management: what drafts of live content settled for it, and what it left to it (2026-10-11)

The first learning, in the owner's words (2026-10-11): "we need to remember what good ux is and releasing when people draft or 'doodle' is not good UX". Autosave wrote the live record from 2026-09-27 on; it was written down as interim in the design, on the roadmap and in the editor's own header, and it still stood for two weeks, because it was weighed as a technical trade-off and not from the seat of the person typing. For everything below, and for release management as a whole: what a person does while working (typing, trying, rearranging) and what the public sees are separate, and the step between them is theirs to take, on purpose, with a view of what will change. An interim behaviour that breaks that is not acceptable as interim.

What a release is made of, now that the pieces exist:
- A release is a set of published copies, one per page or post (`published_versions`), that become current together. A copy already carries the time it goes live (`live_at`) and is picked at read time by the clock, so "publish atomically" is several copies sharing one `live_at`; no job has to fire. Today there is at most one future copy per record, and nothing names a group of them: a release is that name, with a way to cancel or move the whole group.
- The overview in the "Publish changes…" dialog (`Publishing::Changes`: blocks changed, added, removed, moved; the record's own fields; languages) is one record's part of a release's contents. A release's screen is that overview across its records.
- Every publish keeps its copy, so "what did the site look like before this release" and rolling a release back are reads of copies that exist. A history screen and restore are not built.

Decisions deferred to release management, each with the reason it was deferred:
- **Who prepares and who approves.** Rights were left as they are (whoever may change a live record may publish its changes; editing a live record still needs the right to publish). The split belongs here: an author prepares, someone with the publish right reviews the overview and approves. The staff review of 2026-10-04 suggests one `AccessControl.edit_keys(record)` to drop the publish-to-edit rule. The guide's writers found the cost of today's rule: the seeded Author can read every post and cannot touch one once it is live.
- **Slug, place in the tree, and whether a record is published at all** stayed immediate actions. In a release they are pending changes like any other: a page moved, renamed or first published together with the pages that link to it. That needs addresses (`public_paths`) derived from copies, redirects for the old address, and the menu and sitemap following the release.
- **Per language.** A record is published in every language at once and missing optional fields fall back silently ("missing" counts required fields only). A release could carry one language of a record, or refuse to go out while a language it names is incomplete.
- **Several records that depend on each other.** A post list's settings are part of the PAGE's copy and a post's tags are part of the POST's copy, so the two can be published at different times and disagree for a while (a list filtered by a tag the post does not publicly have yet). A release publishes both together; so does a tag rename or merge, which today acts at once and can empty a list.
- **Preview of the whole site with the release applied, and a shareable link to it.** Preview shows one record's working rows today; its lists show published posts only.

What step 3 (live editing) adds to it:
- Publishing changes while a colleague holds unsaved text publishes what was saved and says so; discarding is refused while someone holds part of the record. A release should show, per record, who is still editing it, and decide whether it waits for them.
- Bulk publish in the posts list is a small release without a name: it already skips posts someone is editing and reports them.

For the interface to other programs:
- The MCP server's `update_post` leaves a live post with unpublished changes unless called with `publish_changes`; a release needs tools of its own (list what is pending, publish a set).

Costs seen while building drafts that a release will meet again:
- Discarding brings a deleted block back as a new block, without the notes that were on it. Rolling back a release has the same limit unless deletion becomes pending too.
- About 200 tests name publish, live or scheduled; the ones that pinned "an edit of a live record is public at once" were rewritten. A release will touch the same set.
- No test may assert a duration (four did in step 3 and failed on CI); scheduled copies are tested by moving the clock.

What the dry run of drafts of live content adds (2026-10-12):
- **Releasing the whole site as one release is the target shape**: all copies and all addresses switched together, and a scheduled change is a release with a time. `PublicSite::Paths.refresh` then becomes "apply a release".
- **A workflow for a release, not for a record.** The `state_machines` gem is an option to weigh for a RELEASE's workflow (prepared, in review, approved, released). It is not for a record's publishing state: `Publishing::State` derives that from three facts and stores nothing, on purpose.
- **A tag rename marks every carrying post as changed**, and a discard cannot clear that mark until the name is published (a rename of a tag with forty posts is forty marks and no action to publish them together): a release of tag changes is what this wants.
- **A publish that takes another record's address away is announced, not refused** (the publish dialog names the records; the record's own address is the only one that refuses). The owner may want it refused: the rule is one place (`Publishing.keep_address!`).
- **A discard brings a deleted block back without its notes** (already named above); a release's rollback has the same limit.

### The browser scripts: keep Stimulus clean, and say where it ends

Should. Asked for by the owner on 2026-10-11, while live editing was being built: "i want to have the stimulus part clean as possible. And let's be honest about the limitations and if we need to departe for certain functions." Stimulus on server-rendered HTML is how every CS Studio screen is built and stays so. The page editor is where that model is at its limit (several stateful forms, rich text, and now a server that redraws the page under them), and `app/javascript/editing/merge.js` is the price of it, paid once. What to do, in this order:

1. **Controller-to-controller calls: events or a small shared module; outlets not now.** Outlets were the first idea and were put aside after reading upstream (2026-10-11), for three open bugs: `disconnect()` is not called when an outlet is accessed in `connect()` (hotwired/stimulus#763, open since 2024-04), an outlet's connected callback fires before that controller's own `connect` (#738, open since 2023-10), and an outlet is not found from a `visibilitychange` handler (#861, open). That is "not now", not "never": the same reading allowed a guarded outlet for a plain method call, and for #763 there is an unreleased fix and an open pull request. Stimulus has had no release since 3.2.2 on 2023-08-07, so a date for any of it cannot be counted on. Today the editor's controllers call each other through `application.getControllerForElementAndIdentifier` (the hold script calls the autosave's `pause()`, `flush()`, `saveNow()`, `outstanding()`, `clean()` and `unchanged()`, the section's `open()` and the rich-text editor's `lock()` and `unlock()`; the live script asks the autosave the same three questions and reads the rich-text dialog's and the media picker's opener), which is silently nothing when that controller is not connected. Replace those with events that have one written vocabulary, or with a module both import (as `live/state` and `saving/queue` are).
2. **One shared base for "listen on a stream, say how my live part stands, clean up"**, which is written out in notes' live controller, presence's record and list controllers and editing's live controller.
3. **A written map of what state lives where in the editor's scripts** (in `docs/reference`): the DOM's attributes, the autosave's `WeakMap` by form element, the hold script's Maps by subject, the live script's line of reads.
4. **A limits section in `docs/reference`** (`design-system.md` or a new `scripts.md`), saying where the DOM-is-the-state model strains, when to depart from it and how far. What live editing ran into, from the accounts of the two tasks that built the hold script and their reviews:
   - State that must outlive an element: the claims a tab has made (`held`) are needed after a Turbo visit has disconnected the controller, so `disconnect` queues the releases with values read before it went.
   - State kept outside the DOM in collections keyed by subject: `held`, `claiming`, `releasing`, `asking`, `handing`, `lost`, `announcing` and the timers. Four of them (`lost`, `asking`, `announcing` and the strips' timers) end by time, with three lifetimes between them (30 seconds, 10 seconds, "a tick after the strip goes"), each a hand-kept timeout; the others end by an answer or an event. Stimulus has values per element and no state per target, and each of these lives across the server replacing the element that shows it, so "waiting" has to be applied again every time a strip is drawn.
   - The autosave's real state is a `WeakMap` by element outside any controller, and `pause()` writes it from another controller.
   - Controllers talk through custom events with no owner of the picture: the autosave says a form is dirty, the section and the card say they were closed, the live script says a block was deleted or its holder changed. An event cannot return anything, so a controller that needs "the draw is done" passes an array in `detail.waits` for the other to fill with a promise.
   - The live and the hold controller stand on one element and send each other events: one object split in two.
   - A target used as a hook: `stripTargetConnected` stands for "a server answer put a notice here", which Turbo has no event for. It only works inside the controller's element: a strip a stream drew outside the region would not be seen (none is today; a post's notice area is inside its region because the post's form draws the header). Stimulus tells a controller of a target a microtask after the DOM changes and Turbo draws a stream a frame after the answer, which is too late for the queue, so the refused form is stopped by hand in the claim's answer. Targets already in the page are announced before `connect`, so the Maps are made in `initialize`. And `stripTargetDisconnected` needs a `setTimeout 0` to tell "replaced" from "gone", because the two halves of a replacement are reported separately.
   - The hold script vetoes a Turbo Stream it does not own from a document-level `turbo:before-stream-render` listener, by looking into its template (`keepStaleBar`).
   - Polling to wait on another controller's state, four times: a release waits in a 25 ms loop for "nothing left to send", and so does a hand-over, because the autosave has no such event; the live script checks once a second whether a displaced unit's form is no longer unsaved, for the same reason; and the focus that goes back to a rich-text field after a merge polls on each animation frame (up to 3 seconds) until the controller that mounts the editor has done so, because one controller cannot be told that another has finished connecting. Of the first two: the first hand-over borrowed `drained()`, which is about the whole screen, and a person typing in any form never let it finish.
   - No reversible read-only: the tools were `pause()` and `freeze()`, both final (freezing removes Stimulus's own wiring, the `data-action` tokens, and can only be undone by fetching the form again). The light lock for a hand-over needed a new `unlock()` on the rich-text controller, and the discovery that Tiptap's `setEditable` emits an update the autosave then saves as a change.
   - "After this event" cannot be said: a menu closes on a click on an item that is not disabled, and an action runs before that handler, so disabling the pressed item inside the action kept the menu open, which the live script reads as busy; a `setTimeout 0` fixes it.
   - Buttons found by a `data-action` selector instead of as targets, because a menu's item and a strip's button of one subject are in different subtrees of a controller far above them.
   - Wording: every sentence a script shows has to be a `data-*` attribute of the server's markup, so a status with four states is four attributes read by a string key; and a live region that arrives with its text is not always read, so an announcement is written 150 ms later, into a region looked up again.
   - A global `translate:changed` on `document` to nudge a third controller; and a test can make a tab "deaf" only by replacing a method of a controller instance.
   When to depart, and how far: a small state store (nanostores or `@preact/signals-core`; both load from an import map as plain ES modules, the second as one file of about 2 KB, the first as several files that each need a pin, which was not tried) only if the editor's form state keeps growing, the trigger being the publishing workflow; no Stimulus pairing with either has a track record. A self-contained client component, an island, for co-editing (step 4 of collaboration: Tiptap with Yjs). Never a second way to build an ordinary screen.
5. **Not planned, with the reason.** `stimulus-use` (maintained, but little is saved and the code is not ours). Idiomorph in place of the merge: its callbacks could keep a unit that holds unsaved text, but it has no counterpart for a gone unit, a displaced subject or matching by subject, and patching a rich-text editor in place is exactly what the unit rule avoids (Trix and Lexxy both broke under morphs: hotwired/turbo#1142, basecamp/lexxy#263). Turbo's page morphing: the write queue assumes it is off. `Element.moveBefore()` to move a kept unit: tried on 2026-10-11 in Chromium 155 with Stimulus 3.2.2, it disconnects and connects the controller exactly as `insertBefore` does (only the focus of a contenteditable stayed), and Safari has not shipped it, so "a kept unit is never moved" stands. That result has its own limits: one browser (Chromium), a bare contenteditable and not a mounted Tiptap editor. **A middle option that is not ruled out:** `Turbo.morphElements`, which is already in the pinned Turbo bundle, for the leaf cases of the merge (a clean unit with no editor in it, a tile, a strip slot), with `merge.js` keeping the rule and the cases a morph has no word for; not tried.
6. **Candidates for a contribution upstream**, most promising first: a documentation pull request to Rails saying that the commands of one Action Cable connection run on the worker pool and may finish out of order (it is true by the code and stated nowhere; presence's `in_order` exists because of it; the open guide rewrite, rails/rails#58262, is the place to ask first); documentation and tests in idiomorph for editable subtrees (contenteditable and editors owned by a script), where no issue covers it and a change of documentation and tests is the kind that project takes; and reviewing hotwired/turbo#1562 (`data-turbo-refresh-policy="manual"`, a frame an application owns is skipped by a morph refresh) against a contenteditable editor, rather than a design of our own. A "moved" hook in Stimulus for `moveBefore` would be the direct fix for the merge's hardest rule and is the least likely to be taken, given the project's pace.

### Closed by versioning

The first two of these shipped on 2026-10-12 with drafts of live content: a save no longer goes live, and editing a published record needs `publish` because the person who may change it is the person who may publish it (`docs/reference/publishing.md`).

- CS Studio autosave writes straight to the record: edits to a published page or post go live as the editor types (the editor header says so).
- Editing an already-published page, post or block therefore needs `publish`, not only `edit`.

### Presence

Left by the presence sub-project (spec §9; `docs/reference/presence.md`).

- Nothing limits how fast a client may send `report` or `beat` on `Presence::Channel`: each is one indexed update, and a `report` that changes the state also two broadcasts. A minimum interval per subscription would close it. Also `seen_at` is in the record index, so every keep-alive is a non-HOT update (one indexed row per open tab every 30 seconds).
- "Away N min" restarts when a laptop reconnects: an arrival resets `state_at`, so a person who was away for an hour is "away just now" again. Telling a reconnect from a first arrival needs the server to know what the tab last said.
- The presence system tests hold about ten annotated sleeps (`presence_test.rb`, `presence_lists_test.rb`) that conditions could replace, e.g. a counter of the script's readings that a test waits on.
- A full batch of 500 ids makes a 7 to 10 KB URL for `GET presence/here`, which no test sends (the ">500 ids" test shortens `chunk`). Behind a proxy with an 8 KB request-line limit it is refused and the list's markers silently stop updating. A POST, or smaller chunks, would end it.
- Two narrow races in the heal, both corrected within 150 seconds by the stale limit: a `beat` that updated nothing and asks to heal just after its own subscription's leave began can put a row back, and a heal can overwrite a newer subscription's token. `Presence::Channel#heal` is check-then-act.
- A subscription already open is not re-judged when a right is taken away, as for notes (above): the signal says nothing and every fetch it leads to is scoped, and the record's script ends its own subscription when its next read, within a minute, is answered with a 404 or 403 (`Presence::Channel` itself is not asked again).
- A list open with the focus on the button and the pointer away is closed by a real redraw (someone arrived or left), which replaces the group; the next press opens it again. The `restoring` reset in the record script (`turbo:load`) has no test of its own.
- A list reads once about half a second after a full load, on top of what the server rendered, because the script cannot know what was signalled between the render and its subscription being confirmed.
- Checked by hand only, and only in Chrome: Safari; idle detection on a second real machine; reduced motion; a real back/forward-cache restoration; a throttled hidden tab's keep-alives. Everything else has a machine test.

- **A save on the wire at `pagehide` can claim the block back for the tab that is going.** The release at `pagehide` is a `keepalive` request and can be processed before a save that was sent first; that save then claims for the old tab id, and the reloaded page reads "You're editing this in another tab" until the hold lapses (two minutes) or the person presses Take over. Nothing in a page that is going away can order the two. One way out: the server does not claim for a save that carries a mark saying its form was closed.
- **A holder who is typing without a pause in another block sees "Taken over by …" on the handed block only when they pause**: the live script's reads wait for the tab's writes to be quiet. The handed block's fields are locked at once, so nothing is typed into it meanwhile.
- **After a hand-over, if every re-read of the unit fails (three tries), its fields stay locked and no notice shows**: the notice's words come from the server's strip. The next signal or a reload shows it.
- **A holder's tab is not told when the asker withdrew**: its hand-over answers `nothing` and it takes its lock back, after having sent what it held.
- **A drop made while a colleague changed the list is refused** as a stale reorder and the list is redrawn; the drop does not win. Ruled as the design's "the existing refusal covers the rare clash"; a person's drop snaps back when a colleague changed the list in that second.
- **A colleague's publish or unpublish does not refresh the header.** The form is fetched, the header is not, so the status chip and the primary action stay as they were until a reload; someone without `publish` then gets the service's 403 on their next save of a record that went live meanwhile.
- **Renaming, deleting or merging a tag sends no signal.** Each touches the posts that carry the tag, but the event names the tag: an open post form is refused as stale, as before. The fix is a list of post ids in those three events.
- **A clean rich-text field that has the focus loses its caret when its card is replaced** (a colleague saved that very block, or took it): the focus comes back to the field, at its start. An `input` or `textarea` keeps its selection.
- **A catch-up misses what a unit's version does not cover**: a unit that shows something of another record or of the viewer (their rights, a library image's file, a tag's name, an ancestor's slug) is left as it is by the fetch made on connect, until the next signal or a reload.
- **Holds are neither taken nor respected by writes through the MCP server**, or by any request without a tab id. Such a write appears through live refresh, and one that lands on a block someone is changing makes that person's next save stale, as before live editing. With "More tools in the MCP server" ("Next", item 8).
- **No rate limit on claims** (the design's §9): `POST claim`, `release`, `take_over`, `hand_over` and `withdraw` are each one or a few indexed statements and at most one broadcast, and a client may send them as fast as it likes. With presence's `report` and `beat` (above).
- **A take-over can deadlock with the deletion of the requester's user**: the transfer's update checks the user's row, which `Users::Destroy` holds while it waits to nullify the reservation; Postgres aborts one of them. It needs an administrator deleting someone in the seconds they are taking a block over.
- **A subscription already open is not re-judged when a right is taken away**, as for notes and presence (above); and a person whose right to edit was removed keeps a hold until it lapses or someone takes it over, which needs no answer from them.
- **A forged Publish by someone in the read scope without the right is answered "… is editing" while a hold exists, with no `access.denied` event**: the hold is asked before the service's own check. Accepted: they see the strip that names the holder anyway.
- **A deleted block's reservation row stays** until it expires and the sweep takes it; nothing reads it again. And a deleted block's notice can name who deleted it for 7 days; after that it is the plain sentence.
- **A post that becomes held while its "Changed elsewhere" bar is up shows no strip**: the two share the header's notice area and the bar stays, since the form is dead until a reload anyway.
- **A `claimed` signal for a block in which this tab has unsaved text shows nothing at once**: the person learns at their next change or save, by the refusal. With the renewal while typing it takes a tab that was offline or asleep.
- **A write made with a token, or by a job, refreshes the other editors with no "Updated by" mark**: the newest change decides, and it has nobody to name.
- **Duplicating a block is several audit events** (a `block.created` per copy and one `block.reordered`) and so several `structure` signals; the live script coalesces the asks it has not yet sent.
- **Library images are not live**: the Media panel is not refreshed and not held, and keeps "saved, also changed elsewhere".
- **Wording that nobody designed** is in use (the spec's §10 lists each sentence): to put to the design project in one go.
- **A section's layout is saved by an autosave form and so claims the section**, where the design (D4) called it an instant action that holds nothing: someone changing a layout holds the section's settings for two minutes. To decide whether that is wanted.
- **A top-level card that stays expanded has no "close"**: its hold is released by collapsing the card or leaving the editor, and otherwise by the two-minute lapse (the colleague's strip refetches the card then), where a section's panel is released the moment it is closed. A colleague waits or presses Take over, which an awake holder's tab answers at once. A release on blur, or after some seconds without a change, was not designed.
- **A read caused by a `requested` signal can replace a lightly locked, clean card with an unlocked one** for the moment before `handed` arrives (the read and the hand-over race by about 25 ms). What is typed in that moment is refused by the server with the `lost` notice, so nothing is lost or saved twice. The fix is to skip that read for a subject the hold script is handing over.
- **A displaced unit is shown in its old place with no notice**: a block a colleague moved to another container while this tab holds unsaved text in it stays where it was until this tab's save, then takes its place. Nothing says so meanwhile.
- **For a page, a refused settings save can say "Changed elsewhere." where it could name someone**: `Audit::ChangeSince` counts only the page's own events, which is right for the cause and loses the name when the event that moved the base is not one of them.
- **The three rules without a behaviour test have static guards with stated limits** (final review): an id on every ancestor of a unit is held for the markup the server draws, not for what a script does to it afterwards; "every version through `Editing.version`" and "a reservation's statements in autocommit" are source greps (`test/lib/editing_guards_test.rb`), and the second cannot see a transaction opened further up the call stack than the caller's own file. A test that runs a claim on a second connection inside a caller's request would be the real guard.
- **Small things the final review named and left**: `Editing::Reservation::FREE` is a SQL fragment in a plain constant, which the `# sql:` guard neither sees nor lets be marked; `admin--saving--autosave#announce` serialises the whole form on every input event (fine for today's forms, worth knowing for a long rich-text body); `Editing::TakeOver#take` retries a lost race up to three times where the row lock makes a second loss all but impossible; and `holdTurboRequest`'s `before` and `baseIds` options (`saving/queue_core.js`) have no caller since the tree's base forwarding went.
- **What the guide's writer found hard to explain because it is hard to use** (2026-10-12): the first change claims a block but nothing shows the claim to its owner; a claim lapses after two minutes with no sign to either side; whether a take-over saves the other person's text depends on their tab, and the requester cannot tell; "You're editing this in another tab" can stand for two minutes after a reload with one tab open; there are three different rules for what a hold refuses (a save, an instant action, a discard); and one conflict appears in three wordings.
- **The tests that were not written** are in the Tests table under "Technical health" ("Live editing, tests that were not written").

### Safe on a public address

Left by the first part of hosting (spec "As built"; `docs/reference/hosting.md`). The first two are closed by the Mail part.

- **A production site without `PUBLIC_HOST` sends no reset mail, and the request page still says a link was sent.** The mail is not built on purpose (a link taken from the request could be made to point at a stranger's host); the log, System status and the wizard's check say so, the page does not until the Mail part.
- **Saving an AI key on a site without encryption keys is a 500.** The Mail part will say a sentence instead, where its own secret cannot be stored; the AI card should say the same.
- **`config/deploy.yml` holds `PUBLIC_HOST` only as a commented line**: a Kamal deploy from it as it stands answers any host and forces nothing until someone uncomments the line and writes the address, which the file's comment says. The file goes when the real deploy files exist in `contentspiel-docs`.
- **The localised homepage answers at both `/de` and `/de/`.** Its canonical link, `og:url`, `hreflang` and the sitemap all name `/de/`; nothing redirects one to the other. A redirect is a routing change. The default homepage's sitemap `<loc>` is the bare origin while its canonical link ends in a slash: one address, two spellings.
- **The canonical link of a paginated list** is to be page N's own address when pagination exists; there is none today, so a list's canonical link is the page's.
- **A redirect's `Location` follows the request**, not the configured address. With an address a foreign host is refused first; without one the request's host is all there is. Left as it is by a ruling.
- **Only the exact host is answered.** A site that wants `www.` as well has no way to say so (one address, one host); a redirect from the other name is the proxy's to make.
- **The boot's lines are logged at info**: with `RAILS_LOG_LEVEL=warn` none is printed, and a wrong `PUBLIC_HOST` then refuses every request with nothing in the log to say which host is answered; what is left is Rails' own `Blocked hosts: <name>` at error for each refusal. Logging the "Serving …" line at warn would be a one-word change if wanted. The settings and the lines are held by a test that boots production (`test/lib/production_boot_test.rb`); the secret check is not booted for.
- **A wrong `RAILS_MASTER_KEY`** with no `SECRET_KEY_BASE` is told the secret is missing, with the error's class; beside a good `SECRET_KEY_BASE` the boot still stops later, with Rails' own decryption error, wherever else the credentials are read.
- **Resetting a password needs JavaScript**, and a link opened twice, reloaded or come back to says it is incomplete: the token is kept nowhere but the page that received it.
- **The proxy's access log** still holds the token of a reset link mailed before the change, for the fifteen minutes it is good, and whatever a client goes on sending to the old address.
- **At `RAILS_LOG_LEVEL=debug` Rails logs every mail it sends in full**, the reset link and its token included. The boot warns and does not refuse; the Mail part could give production a mailer logger that never goes below info.
- **A mail gateway that rewrites links** (Outlook Safe Links, Proofpoint, Mimecast) may drop what follows the `#` of the reset link, and then nobody behind it can reset a password by mail. Untried: one real mail through such a gateway before a stranger depends on it.
- **`ASSUME_SSL=1` in front of nothing**, or a proxy that claims HTTPS for a plain connection, makes the "HTTPS" check say OK and hides the notice. Nothing in the application can tell.
- **No query string is visible in a trace** (a note's quote travels in one); `http.route` says which address was asked for.
- **A host label or name longer than DNS allows** is accepted by `SiteAddress`; it matches no request.
- **Wording that nobody designed**: the four strings of the incomplete-link page, the notice, the two checks' sentences and the boot's lines (the pull request lists each string and place).

### Theming

Left by theming (spec "As built"; `docs/reference/theming.md`).

- **The public content security policy sets no `script-src` and no `style-src`**: only `frame-src`, `object-src` and `base-uri`. A theme's template can load a script or a stylesheet from any host, and the folder check does not look for `<script`; a second stylesheet link is refused by the check, not by the policy.
- **Development and test share the built stylesheet and its entry** (`app/assets/builds/theme.css`, its stamp, `tmp/theme/entry.css`). A test run builds the default theme's under a running `bin/dev`; System status and the test build's own line say so, and `bin/rails tailwindcss:build` with `THEME_PATH` set or a restart of the watch repairs it. An output per environment needs the test environment to find both stylesheets elsewhere, and is not small.
- **`navigation_pages`, `published_views` and `@page` still hand a theme's template `Page` objects**, from which rows can be read (`@page.children`); the tree helpers hand out values. No guard reads a theme's templates for the walk.
- **A theme's template can still change the head** through `@page.title = …` or `response.status = …`: the layout reads the record and the status after the page template ran. The fix is the controller keeping the head's facts where a view cannot reach them.
- **In the preview of a draft page the tree, the crumbs and previous and next hold published pages only**: the draft has no sidebar entry, nothing is marked current, and a draft directly under the homepage has no section. Whether a preview's tree includes drafts is undecided.
- **A heading's id can equal an id the theme's own frame uses** (`with_heading_ids` sees the article it is handed, not the frame): two elements with one id.
- **A rich text's HTML structure cannot be replaced by a theme** (decision 12). Raised with the owner on 2026-10-12, not objected to, not confirmed.
- **The folder check is a fence, and misses by design**: a name reached through `send`, an alias or `&.`, a read from the tag that binds the same name onward (one before it is refused), a cookie written through a bracket inside a bracket, a tag whose attribute ERB prints at run time, a row walk, a `<script src>`, `response`, the clock (`docs/reference/theming.md`, "Checking a folder").
- **A theme's template can render the CMS's own head partial or write to the title's slot, and nothing refuses it**: `render "pages/seo_meta"` (and `shared/theme_head`, `layouts/public/preview_banner`) prints the CMS's tags a second time, and `content_for :title` does nothing, both without a word. The documentation theme has one of each ("Next", item 9). A refusal for the three renders ("the layout draws this itself now: delete the line") and for the title's slot (pointing at `layouts/public/_title` and `page_found?`) is two patterns in `Theme::Check.written`.
- **What a copied default template asks of a record is not contract**: `@page.root?`, `@page.landing?`, `@page.hero_media_asset`, `@page.children.kept.published`, `post.tags`, `post.fields`, `theme_site.logo`, `Media::PictureComponent`, `ContentTypes::ResumeEntry::ROLE_TYPES`. Every scaffolded theme calls them from its first day, and no image template can draw a picture from listed names alone. Name what a template may ask of a page, a post and an image.
- **The check wrongly refuses an attribute's words inside a string of a tag helper's call** (`tag.meta name: "description", content: "use rel: canonical"`): a tag built by a helper is read with its strings, whole.
- **Nothing reads the CMS's own public templates for a fragment cache**: the check refuses one in a theme's template, because the public page and the preview would share the entry.
- **A controller file added to a theme needs a restart in development**, the first and every later one: importmap-rails sweeps its map for `app/javascript` and `vendor/javascript` only (observed 2026-10-12). Adding the theme's folder to `config.importmap.cache_sweepers` has to happen before that gem's own initializer.
- **The boot reads a theme folder more often than it needs to**: every file is hashed three times in production (`built?`, the boot line, `Theme.load`) and the folder walked about eight times. A few tenths of a second per process start for a theme with 30 MB of fonts and images; hand the fingerprint read for `built?` on.
- **The production boots in the unit suite are not shared**: nine child processes of about three seconds each (seven in `test/lib/production_boot_test.rb`, two in `test/tasks/theme_tasks_test.rb`, one of them new with `theme:new`), each asserting something no other does; two could share a boot.
- **A `Dockerfile` at a theme folder's top is refused as any stranger is, and the sentence does not say where it goes** (beside the folder; `theme:new`'s README and the reference files say so).
- **Wording that nobody designed**: the boot's line and refusals, the check's problem sentences, the "Theme" row's sentences, the watch's lines and the two tasks' lines (the pull request lists each).

### Code block

Left by the Code block (spec "As built"; `docs/reference/content-blocks-and-types.md`, "The Code block"). Each line ends with what would close it or what should make someone look again.

- **A slow lex is cut, not prevented.** One lex has a deadline (`CodeHighlight::LEX_SECONDS`, half a second, checked at every step inside Rouge), a failure is remembered for five minutes (`FAILURE_TTL`) and one request spends two seconds at most on lexing (`REQUEST_SECONDS`): what is left of the page is drawn plain, with nothing remembered, and coloured by the next request. So a page of thirty blocks that each fail costs about eight requests of under three seconds each, every five minutes, where it was one request of up to 45 seconds; three requests at once are three threads for three seconds. What is left: a request that arrives while another is still failing the same block lexes it too (the entry is written when the lex ends), and a visitor who was sent a page with a FAILED block is confirmed that page by a 304 until something is published (only a late block's page loses its ETag). Lexing when the block is saved, not when it is shown, would end both; look again when code can arrive from anyone but an editor (an MCP block tool, an import), or when `CodeHighlight::TooSlow` is seen in a log for code that is not slow (a loaded machine: the deadline is wall time, and a second is the first thing to try).
- **Markdown's fenced blocks are coloured by whatever lexer the fence names**, listed or not, eight lexers deep at most (`MAX_DEPTH`), and a fence that names none by Rouge's guess, which runs outside the steps the deadline checks, as do the three lexers that are no regex lexers (console, plain text, escape). Accepted and bounded by the deadline and the depth; closed by a Markdown lexer of our own whose fence rule looks only in `LANGUAGES`, if a fence is ever seen to be the slow part.
- **The deadline's and the depth's checks are a module prepended to `Rouge::RegexLexer`** (`CodeHighlight::EachStep`, around `step` and `delegate`), the one change this application makes to a gem's class. It does nothing while no lex of ours runs (Lookbook's own highlighting in development passes through it untouched), a Rouge upgrade that renames either method fails a test by name, and in development a change to it needs a restart. Closed when Rouge offers a hook, a time limit or a depth limit of its own.
- **`CodeHighlight`'s helpers are all public** (`module_function`): `coloured`, `plain`, `split_lines`, `role_of`, `within_budget`. Its interface is `lines`, `label`, the constants and, for a test, `budget`, `now` and the two keys.
- **`CodeHighlight::REVISION` is bumped by hand** when `RULES` changes, and nothing fails when it is forgotten: cached blocks keep their old roles until their code changes. Closed by deriving the key from a digest of `RULES`.
- **No line numbers, highlighted lines or diffs**, no wrapping as an option, no colours in the editor's field. Each is a design question first; the documentation site is what would ask.
- **Code inside rich text has no language and is not coloured**, and a Markdown fence in a post stays rich text and does not become a Code block. Two ways to show code; the guide says which is for what. A language on rich text's code block is the rich-text editor's work.
- **The MCP server has no block tools, so no tool reads or writes a Code block** ("Next", item 8). When they are built the settings travel as the plain strings they are, and the first line of this list (a slow lex is cut, not prevented) is what to read first.
- **The four public strings are English only** ("Copy", "Copy code", "Copied", "Not copied"): German and Spanish come with "Next", item 7.
- **`string` is a generic name to have promised to themes** (`Blocks::CodeComponent#string`, on the contract's line because the default template calls it for its words). The owner's call, listed in the pull request; a rename after the first theme outside this repository uses it is a breaking change.
- **A theme's `--th-syn-*` do not reach code inside a strong band**: the band's own declaration is nearer the code. A theme sets them there in a rule of its own for `.content-section--strong` and answers for the contrast. Band-scoped optional tokens (`--th-on-band-strong-syn-*`, falling back to the band's one colour) would let a theme set both in one place.
- **The theme check does not refuse `raw`, `html_safe` or `<%==` in a theme's template** (theming's matter, seen through this block: a theme's own Code template can print the code unescaped, and only the default template is held to text). Closed by a refusal in `Theme::Check` with a sentence that says what to write instead.
- **Three guards read less than they seem to.** The contract's method-call guard (`test/values/theme/contract_test.rb`, "a default component template calls no method of its component that its line does not name") misses a call inside a string's interpolation, a `self.` call and an inherited method; the reference test's reading of a script's `static values` (`test/lib/theming_reference_test.rb`) misses a value declared with a bare type that is not `String`; and the contrast test reads only the first rule of a band. Each is closed in its own test the next time that test is touched.
- **`bin/theme-build-check` asserts nothing about the syntax tokens**: a build that dropped `code.css` from the public stylesheet would pass it. One assertion that the built stylesheet holds `--th-syn-keyword` and `.syn-keyword`.
- **A NUL character in any string field of a block reaches jsonb and is a 500, not a 422** (`PG::UntranslatableCharacter` at the save; the schema's validation passes it). Older than this block and true of every string field the schema casts; closed in `ContentModel::FieldSet#cast` by dropping or refusing the character.
- **The counter counts the field as typed, the server after dropping outer blank lines**, so "N over" can be a line or two high for a paste that ends in blank lines, and a text the counter calls over can be saved. Closed by counting in the script what `cast_code` keeps.
- **A browser without `field-sizing` (Firefox when this was built) gets a fixed twelve-line code field** with the browser's resize handle, not one that grows from six lines to twenty-four. Closed when the browser has it; a script that measures would have to measure again for a hidden form that is shown and for a card a live refresh replaces, which CSS alone does not.
- **A collapsed card shows no line of its block's content, for any type**: the design answer (C7) wants the Code block's line on the collapsed card as on the tile, and only the tile has one. A line on every collapsed card is a change to the shared block card, for all types at once.
- **Shared components, seen through this block and not its own:** a held select loses its arrow (`.admin-held :is(select, input, button):disabled` sets `background` as a shorthand, which takes the arrow's image with it); and the toast of a refused save (a 422) can lie over the field's own message. Both are the design system's.
- **Each audit snapshot of a Code block holds its source**, up to 20,000 characters, once per typing session (one coalesced event), as a post's snapshot holds its bodies; only an event's changes hold digests. Nothing prunes the log. Look again with versioning, which is what the snapshots are kept for.
- **Three places sort a page's children in Ruby by one key written three times** (`Admin::PagesScreen::TreeNodeComponent#children`, `Admin::EditorScreen::NewPageFormComponent#choices`, `PublicSite::Branch#in_tree_order`: by position, a page without one last, then by id). A method of `Page` that all three call would make it one.
- **The Copy button's accessible name stops matching its word for two seconds**: `aria-label="Copy code"` stays while the button reads "Copied" or "Not copied", so the visible word is not in the name (WCAG 2.5.3; speech control by the visible word). The designer's call (final review M1): drop the `aria-label` and name the button by its word and the `aria-describedby` it has, or accept it in writing.
- **Every code block's `pre` is a tab stop with no role and no name** (`tabindex="0"`, set whether the block scrolls or not; thirty blocks, thirty stops), and a screen reader lands on an element that says nothing. `role="region"` named by the file name where there is one needs a fifth public string where there is none, which is a line of the theming contract (final review M2).
- **The cache is read once per block**: a page of thirty code blocks is thirty reads (one `read_multi` of two keys each), as rich text does. One read per page needs the block outline to know its code blocks (final review M4).
- **The file name's id repeats for blocks without an id** (`code--file` for every unsaved block drawn together; a Lookbook preview is saved, so none is seen today). Harmless until two unsaved blocks are drawn on one page (final review M8).
- **Wording that nobody designed beyond the designer's answers**: the limit's message ("is too long (maximum is 20,000 characters)") and the log lines (the pull request lists each).

The design points (looks, wording, what a toggle should move) are not here: they are one list for the design system's owner.

From the measurement of 2026-10-13 (204 pages, 2,005 posts):

- **The 3,000-line rule is the normal case at the size the performance rule names.** The measurement's site holds 6,204 lines (3,162 related, 2,769 shared tags, 203 tree, 70 lists), the posts' own twice the threshold, so it always opens around Home. The threshold was not moved. To decide, by the owner with the designer: whether it should count otherwise (the shared tags' lines are not drawn below 40% zoom anyway), or stay, since the whole graph at that size is one mass at the zoom that fits it.
- **A small graph takes 6.2 s to unfold here, not "about five seconds"**: 300 ticks at one a frame, a tick every 21.5 ms where the canvas spec measured 18 (the worker's 16 ms timer, in headless Chrome 155). The view a large site opens in is such a graph (6.4 to 6.5 s to rest; usable from its first frame, after 30 to 70 ms). Look again if a person calls the opening slow; the cure is the worker's pace for a first layout, which is the owner's motion decision of 2026-10-08.
- **What a page lists still costs 0.29 s of Ruby where 200 pages have 200 different filters** (0.39 s for the graph's data, and as much for a local view at depth 2 and each list read): the criteria are asked once per distinct filter and distinct kind of post, and that site has 836 kinds. An unlikely shape, a third of what it was. Closed by asking the criteria per (type, tag) and not per kind, which needs `BlockTypes::PostList` to say that a filter reads one tag.
- **The search reads the whole site per request**: every readable page's place in the tree and every list block of every readable page, run through `BlockOutline`, only to know which tags a page names. 7 to 23 ms at 204 pages. Closed by collecting the named tags without the outline (the order of blocks does not matter for it); look again past a thousand pages.
- **A legend toggle redraws the whole list**: 28 to 33 ms at 2,202 rows, 208 of them with a canvas for a mark (1.4 to 1.8 ms of it). Nothing is lazy. Look again at several thousand pages, or if a toggle is felt.
- **The whole graph's answer is 844 kB** (55 kB gzipped) at this size, a third more than before pages; nothing to do while production compresses.

Correctness, each small:

- **Two tags whose names differ only in case** (an old row, a write around the model; `tags.name` has a plain unique index, not a lowered one) are listed differently by the application's two listings, and the graph sides with the preview. `BlockTypes::PostList.listed_posts` (through `Tag.named`) and `PostGraph::Listings` take the posts of every twin; `Publishing::Listing` and `ContentBlock#listed_tag_id` take ONE tag per name, the lowest id, and those decide what a visitor sees and a post's address. So a post that carries only the higher twin is listed in the preview and the graph (counted in `listed_count`, absent from "Not listed on any page") and not on the public page. In the graph it can also float loose around a page (its line goes to the lower twin, which it does not carry), `PostGraph::Focus` accepts either twin, and "Open in Posts" names the lower one. Older than this build. Closed by a lowered unique index with a merge of the twins, or by one rule for both listings.
- **A block can be written to a trashed page.** `ContentBlocks::Save` takes the page's row lock and does not read `trashed_at` again under it, and neither do `Destroy`, `Reorder` and `Duplicate` (`app/services/content_blocks/save.rb`; the permission check does not mirror the trash, on purpose). The controller hides a trashed page as a 404, so what is left is trusted code handing one over, and a race: a tab's block save whose page lookup ran just before a colleague moved the page to the trash. The block is written, the trashed page touched, and the block is there when the page is restored; nothing public shows it. Closed by one re-read under the lock.
- **A spent "+N more" pill is hidden, not removed**: nothing of it can be met any more (it is not drawn, takes no press, has no row, and a pin on it is let go), but it stays in the layout as an invisible node and keeps its collision space, and a pill that shrinks keeps its old collision radius. A few pixels. Closed by a `remove` message for the worker.
- **The graph's two fetches need `AbortSignal.any`**, with no fallback: Safari before 17.4 and Firefox before 124 throw there, so the graph says it could not be loaded and the list that it couldn't be, each with a retry that cannot work. Closed by a small helper that joins the two signals by hand, or by saying which browsers CS Studio supports.
- **The measurement's server figures were not kept**: the table in the spec's "As built" was written down from one run of a probe script (in the build's workspace) against a database that is dropped, as query objects in a runner and not as requests, and its "before" column needs the code before the fix. Whoever decides on the 3,000-line rule or on saved positions from those figures takes them again, as requests against a server, and keeps the output.
- **A post added from the list with no line is centred, then drifts**: the layout pushes an unconnected node to the rim, and on a large graph it can end outside the view while it is the selection. Closed by following the selection until the layout rests, or by pinning what was added.
- **Past 200 rows a list read has no paging**: the heading says the whole total ("Posts · 431") over 200 rows, and "Open in Posts" is the way to the rest for a pill only. Closed by paging, or by wording the designer gives.
- **A read of the list has no visible pending state**: the rows' region is `aria-busy` and nothing is said or shown until the answer or the fifteen-second limit. Needs words nobody gave.
- **The swatches are not repainted when the device pixel ratio changes** (a window dragged to another screen); a theme change repaints them.
- **A handed `pending_at` is trusted by `Publishing::State`**: a time at or before `now` on a live record answers "change scheduled". The graph's builder reads the pending copies with the same `now` it hands over, so nothing is wrong today; the rule lives in the method's comment.
- **`theme.radius` reads `--cs-radius` as pixels**: a token given in `rem` would be read as that many pixels, with no error (`mind_graph/theme.js`).

No guard, by name:

- **A post's dot and a tag's square outside the canvas are a second drawing**: in the list's rows, the search's results and a post's or a tag's card they are CSS spans (CS Studio's type dot and tag square), not the renderer's canvases as a page's and a post type's marks are. A change of a post's or a tag's look in `mind_graph/marks.js` leaves them as they were. On purpose (a list can hold two thousand posts); closed by drawing them from the same table, or by a test that holds the two against each other.
- **The server reads a list target's kind by the literal prefix `"tag-"`** in five lines of `PostGraph::Local` and `PostGraph::Builder`, beside `PostGraph.node_id`, which writes it. Closed by a `PostGraph.tag_id_of(target)` those lines call.
- **`PostGraph::Kinds` is a hand-written table**, held equal to what the builders answer by a test on a site built to contain every kind: a new kind of node or line needs a row there, and the test fails only if its site draws that kind.
- **The status key's five names and the chip's are two locale keys** (`status_key.states`, `script.card.status`) that must be changed together.
- **The label rule's `free` set is wired by `app.js` and seen only on a graph with more free nodes than the zoom's budget**: no browser test is big enough. `chooseLabels` has no default for it, so a caller that forgets it throws in every frame.
- **Something new a script writes into the page and `reset()` does not take back** passes every test that waits for `[data-settled]` on the snapshot.

### Block types

Left by block types step 1 (spec "As built"; `docs/reference/content-blocks-and-types.md`, "Block types from outside" and "Adding a block type"). The items that need an outside author are one entry under "Content model and extension".

- **An outside type may claim no capability and use no column beyond `body`, `caption`, `alt` and `image`**: `:container` is bound to the section classes and `BlockOutline`, `:lists_posts` to `BlockTypes::PostList`'s criteria, which decide posts' addresses. Each is opened with a seam of its own when an outside author needs it.
- **An outside type's scripts are not loaded**: neither the public entry point nor CS Studio's registers an engine's controllers, and its import map is not read. A gem's block is markup and styles only until step 2.
- **The stylesheet's stamp is the theme's fingerprint alone** and covers no block type's stylesheet, so production does not refuse a stylesheet built under another set of gems.
- **`theme_css:watch` reads the registered types once, when it starts**: a type added while `bin/dev` runs, or a stylesheet newly declared, needs the watch started again.
- **A registration that raises on a development reload leaves the registries after it empty until the next reload** (development only): the refusal says so on every public page, and the outside types are replayed last so a gem's hook leaves every registry of the CMS filled; a built-in's definition being edited can still empty the content types, the permissions and the AI providers behind it for a reload.
- **A gem's own `BlockTypes.register`, made around the hook, is not refused**: in its engine's `to_prepare` it is wiped by the next reset, and inside the hook's block it passes around the registrar's refusals. The reference says to register through the hook only.
- **The colour guard of an outside stylesheet reads a nested-CSS selector that follows a declaration inside a rule as part of its value** (`color: var(--x); li:has(#bead) { … }`), so a hex-looking id there is refused wrongly; a top-level selector is never read.
- **A built-in's module must be its name camelized** (`post_list` is `BlockTypes::PostList`) for `BlockTypes.built_in_names` to count it; the generator writes it so, and "built-ins are registered" fails for one that is not.

### Contrast and buttons

- **cat-5 sits near the accent in dark** (contrast and buttons spec, Ruling 5): cat-5 moves to `#91acd8` in dark, nearer the dark accent (`#79b0e8`). A type dot is never the only cue (it is beside the type's name) and accent means "unread" only on a count pill, so the closeness is accepted.
- **The native checkbox keeps the browser's outline** (Ruling 10): `.cs-checkbox` is a native control whose box the browser draws (`accent-color` only), so its unchecked border is not measured. A drawn checkbox is a separate change.

### Accepted as they are

- The seeded Author group's `posts.read` and `posts.create` are unscoped, so an Author reads every post (only `posts.edit` is `own`-scoped). Revisit if it surprises in practice.
- A related post the viewer can't read is hidden but disclosed as a count ("+N related posts you can't open").
- The audit log's append-only trigger blocks `DELETE` and `UPDATE` but deliberately not `TRUNCATE`, so `db:truncate_all` works in development.
