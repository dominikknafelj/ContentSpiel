# Settings, languages and the AI translation card

> Describes: `app/controllers/admin/settings_controller.rb`, `app/controllers/admin/languages_controller.rb`, `app/controllers/admin/ai_keys_controller.rb`, `app/components/admin/settings_screen/`, `app/services/settings/`, `app/services/locales/`.

## Settings

**Settings** is one screen (`Admin::SettingsController`, `/<admin>/settings`): an in-page nav of anchors (`#site`, `#languages`, `#publishing`, `#ai`; `Admin::SettingsScreen::NavComponent`), which marks the section in view (`admin--settings--nav`, `aria-current="true"`, drawn in ink with a 2px bar): the last heading whose top is above 40% of the window, the last section on a page scrolled to its end, the first on a page that does not scroll (window scroll and resize listeners, not an `IntersectionObserver`: a tall section never crosses a threshold at the 40% line), a card per section, each in the 760px form column (`--cs-form-max`; the API key input fills its row, and there is no logo "NONE" square) (`SiteCardComponent`, `LanguagesCardComponent`, `PublishingCardComponent`, `AiCardComponent`) (the Publishing card holds one field, "Keep trashed items for N days after an item is trashed", `site_setting[trash_retention_days]`, where 0 keeps trashed items until someone empties the trash) and ONE form, `#settings-form`, on ONE save footer — a plain `PATCH`, never a Turbo Stream: 303 with "Settings saved", the screen re-rendered at 422 with the error summary (`Admin::SettingsScreen::Values` puts the typed values back over the stored ones), or at 409 on a stale base. The module opens for `settings.manage` **or** `languages.manage`; each card and its nav link render only for the right that owns them (Languages: `languages.manage`; Site, Publishing, AI translation: `settings.manage`), and the service enforces the same split: `Settings::Save(site, attributes:, translations:, languages:)` decides from what it is *passed* which rights it needs — a site part needs `settings.manage`, `languages:` needs `languages.manage`, a call with both needs both, checked before anything is assigned — so the controller passes exactly what was posted and a forged field outside the viewer's right is a 403 with one `access.denied`, never silently dropped. `languages:` is the complete ordered list of `{ "code", "fallbacks" }` entries (the form posts one `fallback` per row, and `SettingsController#language_arguments` turns it into the list: a row's stored fallbacks unchanged unless its select changed, a non-scalar value no choice at all), applied inside Save's own transaction through `Locales::Configure#apply` (which checks `languages.manage` itself and records `language.configured` only when something changed), so one Save is all-or-nothing. `Settings::Save` and `Locales::Enable`/`Disable`/`MakeDefault`/`Configure` take a row lock on the settings row first thing inside their transaction (`site.lock!`, which re-reads the row) and decide from the locked row, never from the copy loaded earlier in the request, so a language or settings change made meanwhile is not overwritten; a Save whose stored default makes it a default-language change re-checks `languages.manage` under that lock, and the lock is held until commit, including the synchronous `rebuild_all`. A languages-only call assigns and audits no site field, but the row is still saved — and so validated as a whole — by `Configure#apply`; and when the language part refuses after the site part was written, the rollback is followed by a reload of the site record, so no rolled-back value stays on `Current.site`. The Site card holds every enabled language's title and tagline at once (`site_setting[translations][<code>][title]`, ids `settings-<code>-title`); its language tabs are in-page buttons that only switch which pair is visible (`Admin::Ui::LanguageTabsComponent(mode: :buttons)`, `admin--settings--tabs`; `?locale=` picks the tab shown first, and a refusal on a translated field shows the default language's tab, where the required title lives), so switching never counts as a change or asks to leave. Social links are repeated rows (`admin--settings--repeat-rows`; the list starts as "+ Add link" with no row, and the fieldset posts `site_setting[social_links_present]=1`, so no rows with the marker clears the links, no marker leaves them, and `Values#social_rows` honours the marker so a save refused for another reason keeps an emptied list empty). The form never carries `default_locale`.

## Languages

**Languages** are the Languages card. A language is switched on from the built-in list, `SUPPORTED_LOCALES` in `config/supported_locales.rb` (38 languages; a new site starts with three on, English, German and Spanish); only a language outside that list needs a code change. The card: rows with a drag handle (`admin--settings--sortable-rows`: the same SortableJS options and keyboard path as the block list, writing one tracked `site_setting[language_order]` field so a reorder is one change), the language's own name and path, a "Default" tag on the default language's row and a **Make default** button on every other, and a single "Falls back to" select — order and fallbacks wait for Save. A fallback select stores a one-element list or none; a language stored with several shows the first, and the others are dropped only when that row's fallback is changed and saved. What happens at once is `Admin::LanguagesController`, each a form of its own outside `#settings-form` (reached with `form=`), each a 303 back to `#languages` with a toast, each `languages.manage`: Add language (`Locales::Enable`), Turn off (`Locales::Disable`, behind a dialog; refused for the default) and Make default — `PATCH settings/languages/:id/default`, `Locales::MakeDefault`, event `language.default_changed`, behind "Make <Name> the default?", whose "(N items)" is `Translations::StateIndex.translated_record_count` (kept records holding at least one stored translation). `MakeDefault` assigns the code, clears the *new* default's own fallbacks (its select reads "None (default)" and is disabled, so no screen could clear them), lets the model carry the title and tagline over, and rebuilds the translation states. The default is chosen with buttons, never radios: a radio group changes on every arrow key, which opened a dialog per key press, while a button opens its dialog only when pressed. All three are `admin--saving--pending-lock` controls, and a request that changes nothing (Add for a language that is already on, Make default for the default) redirects without a toast. `GET settings/languages` is a 301 to `settings#languages`; there is no Languages screen.

## The AI translation card

**The AI translation card.** Provider and model are fields of the Settings form. The key is not — it is never rendered, so it can't be a pending change — and has its own controller: `Admin::AiKeysController`, `PATCH` / `DELETE /<admin>/settings/ai_key`, `settings.manage`, writing through `Settings::Save` and answering with Turbo Streams that replace only the key component (`AiKeyComponent`: "● Key saved · added 2 Oct", the year added when it isn't this year, "Key saved" alone for a key older than the column, "No key yet"; Replace or Add key, Remove… behind a dialog; a blank key is a 422 with "Enter the API key first."), its forms, a toast and an empty test result. `site_settings.ai_api_key_saved_at` is set with the key and cleared with it (`SiteSetting#ai_api_key_saved_on` is the day in the site zone); it is bookkeeping, kept out of audit field changes. **The carried base:** a key write moves the settings row's `updated_at`, so the key forms carry the main form's base (`main_base_updated_at`) and the answer moves the main form's `base_updated_at` forward only when the request wrote something *and* the carried base was parseable and still current before the write; otherwise nothing moves and the forms come back carrying what they were given, so a key saved from a stale tab neither unlocks that tab's Save nor cancels its 409. **Test connection** (`SettingsController#test_ai_connection`) tests the *saved* provider, model and key and answers "● CONNECTED · 412 MS" or the provider's message (`AiTestResultComponent`); `admin--settings--ai` disables it while provider or model differ from what is saved ("Save provider and model first. Tests the saved settings."), while anything else is pending, and while a test is running. The hint is per control: the test row and the key row may each show their own. A key typed into the open entry and not yet saved is nothing the main form would send, and the main Save's re-render would drop it without a word: while the entry holds text it carries `data-save-bar-holds`, and the footer's Save is disabled with "Save or cancel the API key first." The other way round the key is never locked out, even when the main form has unsaved changes, so the two can't lock each other: its input stays usable for as long as the entry is open (`data-pending-lock-exempt` — emptied to type another key it is not disabled under the caret), and Save key while the entry holds text; Remove key, Replace and Test connection stay under the pending lock.
