## The one reader: `MailSettings`

`MailSettings.current(site = Current.site, env: ENV, production:, address: SiteAddress.current, stand_in:)` is a value (`app/values`) that answers the effective settings, where each came from, whether they are complete, the state, and the options a send is made with. **Nothing else in `app/`, `lib/` or `config/` reads a `MAIL_*` variable, and nothing decides from a `mail_` column whether or how a mail is sent**: the mailers and the job ask it, the Settings card and the wizard ask it whether a field is the host's, System status and the dashboard ask it the state. The other files that name a column are the model (encryption, normalisation, validations), `Settings::Save` (the one writer), `Audit::Snapshot` (what is never stored) and the two screens' form fields, which show the SITE's own value to edit (`test/lib/mail_guards_test.rb`: "nothing outside MailSettings reads a MAIL_ variable, and nothing configures smtp_settings", "nothing outside MailSettings reads a mail_ column of site_settings for delivery: the other files that name one are the screens' and Settings::Save's", "the delivery path reads no setting itself: the mailers and the job ask MailSettings"; the list of files is `COLUMN_NAMERS`, each with its reason, and an entry that names nothing any more fails).

**Seven fields, two sources.** Server, port, security, username, password, sender name and sender address (`MailSettings::FIELDS`). Each comes from the host's variable when it is set and not blank, else from the site's column (`source(field)`: `:host`, `:site` or `:none`); a variable set to the empty string (a deploy file with `MAIL_SMTP_PASSWORD=`) counts as not set, so it neither blanks the screen's value nor locks the field.

| Variable | Column | Notes |
|---|---|---|
| `MAIL_SMTP_SERVER` | `mail_server` | |
| `MAIL_SMTP_PORT` | `mail_port` (integer) | 1 to 65535; a host value outside that, or not a number, is no port and the settings are incomplete |
| `MAIL_SMTP_SECURITY` | `mail_security` | `starttls` (the default) or `tls`; `none` only from the variable, only without a login |
| `MAIL_SMTP_USERNAME` | `mail_username` (encrypted) | never shown: "Set by the host" |
| `MAIL_SMTP_PASSWORD` | `mail_password` (encrypted) | never shown |
| `MAIL_SENDER_NAME` | `mail_sender_name` | not a delivery setting |
| `MAIL_SENDER_ADDRESS` | `mail_sender_address` | |

`test/test_helper.rb` removes the seven from `ENV` before the application loads, as it does `PUBLIC_HOST`, so the suite does not depend on the shell's.

**Security.** `starttls` is STARTTLS REQUIRED (`enable_starttls: true`, `enable_starttls_auto: false`): net-smtp refuses a server that does not offer it, before the login is sent. "If offered" is never used, because someone on the network can strike the offer and read the login. `tls` is TLS from the first byte. `none` is plain SMTP with both STARTTLS switches off, for a host's own relay; it is taken only from `MAIL_SMTP_SECURITY=none` and only with no login (a login in the clear makes the settings incomplete), and the column's validation refuses it, so no screen offers it. `smtp_options` says all three of the mail gem's switches for every security, because the gem fills in what is not said with STARTTLS `:auto`, which would have made `none` upgrade whenever a server offered it (found on the wire by the stub test: plan ruling T2a). The timeouts are `OPEN_TIMEOUT` 5 s and `READ_TIMEOUT` 10 s: the test mail is sent in the request.

**Complete** (`complete?`): a sender address, a security that is acceptable, and either a server and port or the stand-in (below), and in production a site address (`PUBLIC_HOST`): without one no link could be mailed (`address_missing?`).

**The fingerprint** is an HMAC-SHA256 over the six DELIVERY settings (server, port, security, username, password, sender address, from whichever source each comes; `DELIVERY_FIELDS`), keyed by `Rails.application.key_generator.generate_key("content_spiel mail fingerprint", 32)`. It is one-way and keyed, so the stored value says nothing of the password without the application's secret; it is never shown, logged or audited (`mail_verified_fingerprint` is in `Audit::Snapshot::NEVER_STORED`). The sender NAME is not in it: renaming the sender keeps mail working.

## The state

`MailSettings#state` is derived on every read, never stored:

| State | When | `ready?` |
|---|---|---|
| `:not_set_up` | not complete (or production without an address) | no |
| `:untested` | complete, and nothing verified for THESE settings | no |
| `:working` | `mail_verified_at` with `mail_verified_fingerprint` equal to the fingerprint now, and no failure since | yes |
| `:failed` | verified, and `mail_failed_at` later than `mail_verified_at` | yes |

Because verification is a fingerprint compared on every read, a changed field in Settings and a changed variable at a deploy both make a working site untested with no write at all: nothing has to "clear" anything, and a save that forgot to could not leave mail looking verified. A later failure hides nothing (spec decision 5): one outage must not take the reset link away from everyone. The words are `admin.mail.states.*` (`config/locales/admin/mail.en.yml`), said by one class, `MailStateSentence`, for the Settings card and System status alike; a failure's short reason is `admin.mail.reasons.<key>`.

**The state columns** (`mail_verified_at`, `mail_verified_fingerprint`, `mail_last_sent_at`, `mail_failed_at`, `mail_failure`) are written by `MailSettings.record_success!` and `record_failure!` alone, with `update_columns` and `# version: none (mail's state is not content)`, never through a save of `SiteSetting`: every save of the settings row bumps the public content version (`SiteSetting#reset_cached_state`), and a mail must not empty the site's caches. Neither locks anything: a lost update costs one timestamp. `record_success!` always records the send and marks the settings verified only when the fingerprint it is handed is the current one (`test/lib/mail_guards_test.rb`: "mail's state columns are named by MailSettings alone, which writes them with update_columns, and by the audit's lists"; `test/values/mail_settings_test.rb`: "record_success! and record_failure! write their columns and move neither updated_at nor the public content version", "record_success! with a fingerprint that is not the current one records the send and does not verify"; `test/lib/version_bump_test.rb`).

## Delivery

**A caller queues, and nothing else**: `ApplicationMailer.queue(PasswordsMailer, :reset, user, origin: …)` is `deliver_later` with `params[:fingerprint]`, the fingerprint of the settings as they are when it is queued. `MailDeliveryJob` (the application's `delivery_job`) delivers it and records the outcome; a success verifies the settings only under that fingerprint, so a mail queued under old settings never verifies new ones. A plain `deliver_later` is delivered and recorded but verifies nothing. The test mail is the one mail sent at once, `ApplicationMailer.deliver_now_and_record(SystemMailer.test_mail(user))`, which answers nil (sent) or the `MailFailure`.

**The settings are read in `mail`**, so in the job, at delivery time: From is `MailSettings#sender` (the name quoted by the mail gem); a server that is set is SMTP through `ApplicationMailer::SmtpDelivery` with `smtp_options`, per message, so `config.action_mailer.smtp_settings` is used nowhere and a change in Settings needs no restart; settings that are not complete send nothing (`perform_deliveries = false`) and log one line, `[ContentSpiel] A mail was not sent: outgoing mail is not set up.`, a floor under callers that are meant to ask `ready?` first. Every message raises its delivery errors, so a failure is recorded, never swallowed.

**The stand-in** (plan ruling 1). Outside production, with no server set, the environment's own delivery method stands in for a server (`:test` in test, `:file` into `tmp/mails` in development) and a send through it is a send that succeeded. So in development one "Send test mail" turns resets and invites on without a provider. In production `delivery_method` is `:smtp` and there is no stand-in.

**What is a failure** (ruling T2b). Only an error of the SMTP exchange is a mail failure: `SmtpDelivery#deliver!` marks every error that leaves it (`MailFailure.mark`), and the job and `deliver_now_and_record` record only marked errors. An error raised BEFORE delivery, a record deleted since the mail was queued (`ActiveJob::DeserializationError`), a template or a mailer that raises, is a bug: it is raised on, the job fails as Active Job always does, and nothing is recorded. The first build had a catch-all that recorded everything, which put "Last send failed: the mail could not be sent" on the dashboard for a template error and told the owner to check settings that were fine. One deserialization error is no bug either (ruling T8a): an invite withdrawn before its mail went out leaves the job a user who is gone; the job ends quietly with one info line naming no address. Only the INVITED person's absence: an invite whose inviter is gone still fails.

**Retries.** A connection failure (`MailFailure::CONNECTION_ERRORS`: refused, unreachable, a timeout, an unknown host) is retried three times with polynomial backoff (`attempts: 4`) and recorded once, after the last: one blip the next attempt gets through must not put "Last send failed" on the dashboard. A refused login, a refused sender, a TLS mismatch and anything else of the exchange are recorded at once and not retried. A recorded failure raises nothing, so a failed mail is no failed job and Solid Queue's failed list does not fill with what the dashboard already shows. The `retry_on` is declared after the catch-all `rescue_from` because Active Job tries the last declared first.

**A failure's sentence** (`MailFailure`, `mail.failure.*` in `config/locales/mail.en.yml`):

| Key | What raised it | Sentence |
|---|---|---|
| `login` | `Net::SMTPAuthenticationError` (a 535) | "The server refused the login. Check username and password." |
| `connect` | `CONNECTION_ERRORS` | "Could not reach %{server} on port %{port}. Check server and port." |
| `security` | an SSL error during the handshake, STARTTLS not offered, any reply to STARTTLS | "The server expects a different security setting. Try STARTTLS with port 587, or TLS with port 465." |
| `sender` | a 550 or 553 to MAIL FROM | "The server refused the sender address." |
| `other` | anything else, a 550 to RCPT TO and an SSL error after the handshake included | "The mail could not be sent." |

A Net::SMTP error does not say which command it answered: a 550 is the same class to MAIL FROM and to RCPT TO, so `SmtpDelivery` extends the session to note the command in progress (`starttls authenticate mailfrom rcptto data`) and the error carries it. A server that hangs up mid-mail on a TLS socket raises an SSL "unexpected eof", which is why `security` is a handshake's error only. A net-smtp upgrade that renamed those methods would make a refused sender read as `other`; the stub tests would see it.

**The line and the scrub.** The stored failure is `{ "key", "line" }`: the server's first reply line, or what the connection said, or for any other error its class name only (a bug's message can quote anything). Some servers echo the login in a refusal ("535 Authentication failed for ana@example.org"), and for several providers the username IS a credential (Postmark's server token, SES's access key id), so the effective username and password are replaced by "…" wherever they appear, in any case, with their Base64 forms and AUTH PLAIN's blob, before the line is cut to one line and 300 characters. The error leaves `SmtpDelivery` already scrubbed, with no `cause`, because Action Mailer's log subscriber writes a failed delivery's message at INFO (`Failed delivery … error_message="535 … for <username>"`): found by the log test, not by reading. Telemetry's spans hold the same message, and a test reads them. System status (`system_status.view`) shows the sentence only; the Mail card (`settings.manage`) the sentence and the line in mono.

**Known limits of delivery**, each a minor this build parked (spec "As built"): ECONNRESET, EOFError and EPIPE are not retried; a read timeout after DATA is retried and can send a mail twice; the HELO domain is the mail gem's `localhost.localdomain`, which a strict server may refuse.

## The mails

Three: the reset (`PasswordsMailer#reset`), the invite (`InvitesMailer#invite`) and the test mail (`SystemMailer#test_mail`). Every line is a key under `mail.` in `config/locales/mail.en.yml` (`%{site}`, `%{inviter}`, `%{minutes}`, `%{date}`), read in the default language for now. A plain-text part and an HTML part: one column of at most 560px, system fonts, the site's name as text, the link as one button with the whole address in plain text under it (`mails/_button`), the footer "Sent by %{site} via Content Spiel", no image, no tracking pixel, no rewritten link. The HTML's colours are named CSS colours, because the design rules refuse a hex literal under `app/views` (a design question left open).

**Where a link points** is the reset's rule, written once in `ApplicationMailer#link_origin` and `request_origin_used?` (`docs/reference/hosting.md`, "The reset mail"): the site's address, else in development and test the request's origin, else no mail and one log line. The invite's link is `<origin>/<admin>/invitation#<token>`: like the reset's, the token is the fragment, which a browser sends to no server.

**No credential in a job's arguments.** The job's row and Active Job's log lines hold its arguments, so a mail is handed records (as Global IDs), an origin and the fingerprint, never a setting and never a token: the invite token is made IN the mailer, when the job builds the mail (`user.generate_token_for(:invite)`), as the reset's is (ruling T3a: the plan had passed it in, which put a credential at rest in the queue). `test/lib/mail_guards_test.rb`: "no mail action takes a token or a password: a mailer's arguments are the job's, and a token is made in the mailer"; `test/mailers/invites_mailer_test.rb`: "the queued job holds no token: its arguments are the two users' Global IDs and an origin"; `test/jobs/mail_delivery_job_test.rb`: "the job's arguments hold no setting and no credential".

At `RAILS_LOG_LEVEL=debug` Action Mailer logs every mail whole, a reset or an invite link included; the boot's warning names both (`HostSettings.log_level_warning`).

## Settings → Mail

A card after AI translation (`Admin::SettingsScreen::MailCardComponent`, nav anchor `#mail`), for `settings.manage` only. Server, port, security (a STARTTLS / TLS segmented control; `admin--settings--mail` puts 587 or 465 into Port unless another port was typed), sender name and sender address are fields of the one Settings form and its save bar, written by `Settings::Save` and checked by `SiteSetting`'s validations: a control character in the sender name (a line break would be a header injection; a quote is allowed, because the mail gem quotes the display name: ruling T4a), more than one address in the sender address, a port outside 1 to 65535, a security other than the two.

**The login** is written once and never shown: `MailLoginComponent` and `Admin::MailLoginsController` (`PATCH`/`DELETE settings/mail_login`), on the AI key's pattern, with the carried base shared through `Admin::CarriedBase`. Username and password with one "Save login"; afterwards "Set on 14 Oct 2026" (`mail_login_saved_at`), Replace and Remove…. `Settings::Save#write_mail_login` writes the given halves straight to their columns with `update_columns`, never decrypting what is stored (so a login the current keys cannot read can still be replaced), and audits "Mail login" as "set"/"not set". `mail_username` and `mail_password` are in `Audit::Snapshot::NEVER_STORED` and `mail_username` in `filter_parameters` (the password is filtered by the existing `passw` rule).

**A field the host sets** is a sunken box with its value and "Set by the host" (a login half with "••••••••"), no input and nothing posted; `Settings::Save` refuses a call that names one, whole and before anything is written ("<Field> is set by the host and can't be changed here."). With every field from the host the card says "These settings come from the host's environment."

**Without encryption keys** the first encryption raises `ActiveRecord::Encryption::Errors::Configuration` inside the save's transaction; `Settings::Save` answers one sentence, "This site has no encryption keys, so a password can't be stored. See Hosting: encryption keys.", the transaction is rolled back and nothing is recorded. The same is true of the AI key, which was a 500 before.

**Send test mail** (`POST settings/send_test_mail`) sends to the person pressing it, with the SAVED settings, in the request, and answers in place: "Test mail sent to <address>. Check your inbox.", the warn alert with the sentence and the line, or, for settings that are not complete, the state's own sentence. It is an `admin--saving--pending-lock` control ("Save your changes first") and shows "Sending…" while it runs. `MailTestSending` holds the sending and `MailTestOutcomeComponent` the answer, for this card and the wizard. **One limit for both screens** (ruling P2): `MailTestLimit`, five test mails per person per three minutes, under one `name:` AND one `scope:` (Rails' `rate_limit` keys by the controller's path unless told otherwise, so a shared name alone would have been two buckets), in `Rails.cache`, or a memory store for the process where that is the test environment's `NullStore`, in which a limit never trips.

## The setup wizard's Mail step

An optional step after Site identity (`SetupController::STEPS`, `OPTIONAL_STEPS`): the same fields, a Username and a Password with no Save of their own (left blank on a revisit, a stored login stays), Sender name prefilled from the site's title. "Send test mail" saves and sends through `MailTestSending` and the shared limit; a success redirects back to the step (Turbo refuses a 200 for a form), a failure is a 422 with the alert. A hidden first "Continue" makes Enter mean Continue, never a mail. The security switch is `setup-mail`, a top-level controller because the wizard loads only the `application` entry. The review step says "Mail: not set up. Password resets and invites stay off until mail works. Set it up later in Settings → Mail." when no server was given (by "no server", not by `ready?`, because the stand-in makes a server-less development site complete).

## System status and the dashboard

System status's "Mail" row replaces "Outgoing mail": the state's sentence, OK only for Working; a failure by its short reason, never the server's line; "Open Mail settings →" only for a viewer who holds `settings.manage` (the model hands a symbol, `:mail_settings`, and names no route). **While mail is not ready** (Not set up, Saved not tested) the row carries the console password command to copy, `Setup::SystemCheck::MAIL_FALLBACK_COMMAND` (`docs/reference/hosting.md`, "The reset mail"). Task 6 first took it away, which left a sole owner with no mail and a forgotten password no path on any screen to the one way back in; it came back (ruling T6a). Once mail works the reset link replaces it. The dashboard shows `Admin::Ui::MailFailedNoticeComponent` at its top to `settings.manage` only, and only while the last send failed (ruling P3).

## Sign-in and the reset

"Forgot your password?" shows on sign-in and on Your account only while `MailSettings#ready?`; otherwise sign-in says "Forgot your password? Ask the site's owner to reset it." and Your account shows nothing. Only the request depends on it: `new` and `create` redirect to sign-in unless mail is ready (a bookmarked request page must not pretend to send; a lapsed link met then lands on sign-in with "This reset link has expired. Ask the site's owner to reset your password."), while `edit`, `check` and `update` keep working whatever the state, so a person holding a valid link finishes even if an owner has just changed the settings. The expired page says "This reset link has expired. Ask for a new one." for a lapsed, a used and an invalid link alike.

## Invites and `User.can_sign_in`

**An invited person is a user row that cannot sign in** (plan ruling 2): `invited_at` set, `invite_sent_at`, `invited_by_id` (nullified when the inviter goes), and the digest of a random 32-character password nobody is told, so `password_digest` stays NOT NULL and `has_secure_password`'s validations are untouched. `User.can_sign_in` (`invited_at IS NULL`) and `User.invited` are the scopes. **Every path that signs someone in and every count or list of people who can sign in reads `can_sign_in`**: sign-in (`User.can_sign_in.authenticate_by`), the reset request and the reset token (`Admin::PasswordsController#create`, `#user_for_token`), mention suggestions, notes' deliveries and mention check, the group member picker, `User#other_owner_remains?`, the Users editor's last-owner check and the audit log's people filter. Each has a test of its own that an invited row is not there, and `test/lib/mail_guards_test.rb` ("every User query in a sign-in path names can_sign_in") reads those files for a `User.` line without it, with named exceptions (`PLACES`): `other_owner_remains?` locks EVERY owner row in id order, an invited one included, so two demotions queue rather than deadlock, and counts only the rows whose `invited_at` is nil; the Users screen edits every row; the audit filter keeps a person already chosen. The guard found one: `user_for_token` looked a reset token up among all users, so a reset token of an invited row (one made outside the app, since no reset mail goes to one) would have set a password on it; it reads `can_sign_in` now (`test/controllers/admin/passwords_controller_test.rb`: "a reset token of an invited row is the expired state, sets no password and is a 410 to the check"). Presence and the dashboard's people read users by the ids of people who have done something (a presence row, a message), which an invited row cannot have, and are not places. An invited row is never an owner: `Users::Invite` takes no owner flag and `Users::Save` refuses to make one ("An invited person can't be made an owner until they accept the invite."); one made so by hand can still be demoted and withdrawn, because it counts as no other owner.

**The token** is `generates_token_for(:invite, expires_in: User::INVITE_VALID_FOR) { invite_sent_at }` (seven days; ruling 3). Accepting clears `invited_at` and KEEPS `invite_sent_at`, so a used link still finds its row and the page can say "already been used"; a resend moves `invite_sent_at` and the old link dies; a withdrawal deletes the row and the link finds nothing ("expired"). The block's value goes through `as_json` (millisecond precision), so a token made from an in-memory row verifies against the stored one.

**The services**, each an `ApplicationService` in `EXPECTED_SERVICES` with a factory: `Users::Invite` (`users.manage`; a non-owner may only add groups they could assign; refused while mail is not ready, "Invites need mail."; "Someone with this address already has an account." and "This address is already invited.", the address compared as the model normalises it), `Users::ResendInvite`, `Users::WithdrawInvite` (deletes the row; "There is no open invite for this person." for a row that can sign in, so it never deletes an account) and `Users::AcceptInvite`, whose credential is the token (`# authorize: none`, the contract's `TOKEN_CREDENTIAL` exemption; it is the one exception to "a password changes only through `UpdatePassword` or `Save`"). Invite and Resend queue the mail inside `ActiveRecord.after_all_transactions_commit` (the application does not enqueue after commit by itself): a rollback sends nothing. Audit actions `user.invited`, `user.invite_resent`, `user.invite_withdrawn`, `user.invite_accepted` (the actor is the invited person), each in `Audit::Sentence` and `Editing::Signals::SILENT`.

**On screen.** "Invite person" beside "New user" for `users.manage` while mail is ready, else an owner sees "Invites need mail. Set up mail →". `Admin::InvitesController` (`create`, `resend`, `destroy`; the id is the invited user's) limits create and resend together to ten per person per three minutes, one bucket, so resend cannot be used to mail one address without limit (ruling T9a). The list shows an invited row by its address when it has no name, with "Invited" and "Invited 14 Oct · expires 21 Oct", or "Invite expired"; its menu has "Resend invite" and "Withdraw invite…"; a group's member chips say "Invited"; the editor offers no password for an invited row.

**The accept page**, `InvitationsController` at `<admin>/invitation` (under the admin path, so it shadows no page slug: ruling T3b), is the reset page's design: `show` reads no parameter and no user; `invitation-token` extends `reset-token`'s class and moves the fragment into the form, asks `POST invitation/check` once (200 with the address and name, 409 used, 410 everything else, limited like the reset's check), and the form posts the token in its body. Accepting ends whatever session the browser already had, then signs the person in on the dashboard with "Your account is ready." (ruling T9a). Every answer is `no-store`.

## In tests

- `with_mail_state(state, **columns) { … }` (`test/support/mail_state.rb`) puts the site in `:not_set_up`, `:untested`, `:working` or `:failed` and puts every column back afterwards; `put_mail_state(state)` does the same without restoring, for a factory whose test transaction undoes it. The login is restored as plaintext through its attribute (its raw value is ciphertext, which `update_columns` would encrypt again) and `mail_failure` as a Hash (its raw value is JSON text). The fixture has a sender address, so the suite's default state is `:untested` through the stand-in, not `:not_set_up`; a test of a screen that shows the reset link or invites puts `:working`.
- `with_mail_env(vars) { … }` sets host variables; it goes OUTSIDE `with_mail_state`, because `:working`'s fingerprint is taken under whatever `ENV` holds then.
- **No test reaches the network.** In the test environment `config.x.mail.smtp_loopback_only` dials SMTP only for 127.0.0.1, ::1 and localhost; any other server's mail goes to `:test` and counts as sent, so `with_mail_state(:working)` with `smtp.example.test` delivers into `ActionMailer::Base.deliveries`. The exchange itself is tested against `SmtpStub` (`test/support/smtp_stub.rb`), a `TCPServer` on 127.0.0.1 with scripts (`:success`, `:login_refused` echoing the login, `:sender_refused`, `:starttls_refused`, `:no_starttls`, `:silent`, `:hang_up`), real STARTTLS with a certificate made per process (`SmtpStub.trusted { }`) and the commands it received.
- A job performed inline runs under its own `Current`: read the state after it as `MailSettings.current(SiteSetting.instance.reload).state`.
- `without_encryption_keys { … }` (`test/support/encryption_keys.rb`) takes the three keys away and resets the memoised key provider, so the next encryption raises as production without keys does.
- `with_held_test_mail { |entered, release, calls| … }` (`test/support/held_test_mail.rb`) holds "Send test mail" in flight for a browser test of the busy state.
- `invited_user(email, name:, groups:, sent_at:, invited_by:)` (`test/support/invites.rb`) makes an invited row with neither mail nor an actor.
- `MailTestLimit.store.clear` between tests that count test mails. A token's expiry is travelled by `User::INVITE_VALID_FOR.to_i.seconds`, not `7.days`: a calendar week crossed the US clock change on the machine it was written on.

## What a change can break silently

- **A second reader of a `MAIL_*` variable or a delivery column** disagrees with the screen about where a setting comes from, and with the fingerprint about what was verified. Read `MailSettings` (the guard above).
- **A save of `SiteSetting` for the state** empties the public site's caches at every mail. `update_columns` with its mark.
- **A query of people without `can_sign_in`** in a new place offers, counts or mails an invited row; a new sign-in path that forgets it lets a password nobody knows be the only lock. A new place goes into the guard's `PLACES`.
- **A token or a setting in a mail's arguments** is written to the queue's row and Active Job's log. Hand a record; make the token in the mailer.
- **Recording an error that is not the SMTP exchange's** blames the provider for a bug.
- **A second test-mail limit** with its own name or scope is a second bucket: a person gets ten.
- **Removing the console command from the Mail row** while mail is not ready leaves a locked-out sole owner no path from any screen.
- **A link-rewriting gateway** (click tracking, Safe Links) may drop the `#` of a reset or an invite link; untried, and the guide tells an owner to switch click tracking off.
