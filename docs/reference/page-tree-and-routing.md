# Page tree and public routing

> Describes: `app/models/page.rb`, `app/models/page/`, `app/models/public_site/`, `app/models/public_path.rb`, `app/models/concerns/has_public_paths.rb`, `app/controllers/pages_controller.rb`, `config/routes.rb`, `config/sitemap.rb`, `app/jobs/public_site/`.

## The page tree

`Page` (`app/models/page.rb`) is a `closure_tree` (gem `closure_tree`), backed by a `page_hierarchies` closure table, with exactly one root (the homepage, enforced by `only_one_root_page` and, as a database backstop, the partial unique index `index_pages_on_single_root`). `page_type` is an enum with `validate: true`, so a forged value is an ordinary validation failure on the field, not an `ArgumentError`. Sibling order is the `position` column; closure_tree renumbers it, but reordering to a given rank is implemented on top of that in `remember_requested_position`/`place_among_siblings` because closure_tree's own renumbering doesn't do what a literal "move to rank N" needs. In CS Studio a page is moved in the page tree: by dragging the handle of its row (`Admin::PagesScreen::TreeNodeComponent`, SortableJS in `admin--pages--tree`) or, with the focus on that handle, by the keyboard (Space picks the row up and drops it, the up and down arrows step it among its siblings, the right arrow nests it, the left arrow moves it out, Escape cancels), both sent as `Pages::Move.call(page, parent:, position:)` by `Admin::TreeController` (`test/system/admin/tree_test.rb`: "dragging a page onto another node reparents it and persists"). A move is a write of the moved page (its `updated_at` moves, its URLs are resynced, its new siblings are renumbered with `update_columns`), sent through the write queue like every other write of the screen, but it is **not a change of the page's settings**: `parent_id` and `position` are in `Page::SETTINGS_BASE_IGNORES`, so the page settings form's base (`settings_changed_at`) stays where it was and someone typing in that form, in the mover's tab or a colleague's, goes on saving (`docs/reference/live-editing.md`, "The page settings form's own base"; `test/models/page_test.rb`: "a move in the tree leaves the settings base of the moved page and of its new siblings where it was"; `test/integration/admin/tree_test.rb`: "a settings form held while a colleague moves that page in the tree saves afterwards"). The homepage has no handle, and neither has a page the viewer may not move.

**The page type and the public menu.** `page_type` is `standard` or `landing`. A landing page differs in one place, the public page's header (`app/views/pages/show.html.erb`): it shows the page's subtitle under the title and its hero image; a standard page shows neither. In the page settings form the hero image and its alt text are offered only for a landing page, while the subtitle field is there for every page although only a landing page renders it. The public site's menu is not configured anywhere: it is the homepage's children that are published and not in the trash, in their sibling order (`ThemeHelper#navigation_pages`, drawn by `layouts/public/_header.html.erb`), so every live child of the homepage is in it and no other page can be.

Every public URL is precomputed and stored: the `public_paths` table (`PublicPath`, one row per record per locale, `current: true` for the live URL and `current: false` for the redirects an old URL leaves behind) is derived by `PublicSite::Paths`, never written by hand. The public router (`PagesController#show`) asks `PublicSite::Resolver` for a URL, which is a single indexed lookup in that table plus the visibility rule (`:published`, or `:preview` for signed-in editors) rather than a walk of the tree per request; `PublicSite::Urls` builds links the other way round. Sibling ranking lives in `Page::TreeRanking` (`app/models/page/tree_ranking.rb`).

## One entry point derives addresses

`PublicSite::Paths.refresh(pages:, posts:, everything:, now:)` makes the addresses of everything that depends on the records it is handed what a full rebuild would write, in the caller's transaction, and answers the changes that had to yield (empty when every record got the address it wants). **A caller says what it touched and never which posts that could have moved.** Before this there were eleven places that each worked that out for their own situation, from a before-picture each reconstructed for itself (a block's earlier settings, the copy before, the copy before that, both names of a tag), and every new situation needed every one of them taught; the holes were where one of them had not been.

**The recorded host.** A post's current row carries `listed_on_id`: the page that gives it its address. That is the one fact about an address that cannot be read back from the records afterwards, and it is what makes one function possible: "which posts did this page hold until now" is a query on the derived table, whatever the page listed and however it came to list it. `write_all` writes it with the path, and only then: a post's path begins with its host's and a current path belongs to one page, so the host cannot change under a path that stays. A page's row has none.

**What depends on a touched page**, with S the touched pages and everything below them: its own address and its subtree's (`sync_subtree`, a fixed number of statements however large the subtree); the **hosted** posts, whose row says a page of S gives them their address (the "before"); the **listable** posts, of every content type the list blocks of S name as published now (the "after"; a block that names no type lists every type); and the **unhoused** posts, kept and with no address at all, of the content types some list block of the site names now. A post that had to yield has no row to say where it wanted to be, so it is looked at with every touched page, which is also what gives a yielder its address in the very save in which the page that held it moves away; narrowed to the listed types, because a post no block can list gets no address whatever happens and a site's unlisted posts are not to be read on every page save. A page's rank among the candidates matters only for posts it hosts or can list, so a post outside all three sets keeps the winner it had. A touched post is its own address, and nothing else. Still not healed, and tracked in the roadmap: a post that yielded to another *post* which then moves away, a post that yielded in one language while it has an address in another, and the pages below a page that yielded (`bin/rails public_paths:rebuild` does it).

**Who calls it, and with what.** A page's save that changed one of its URL inputs (`url_inputs_are`: slug, parent, position, publication, trash state; any other save, and a bare `touch`, refreshes nothing) passes itself; so does a post's (its slug, content type, publication or trash state, or its tags, which the association notes), and a `PostTag`'s commit passes its post. A list block saved or destroyed passes its page. `Publishing::Version.take!` passes the record whose copy it has just taken, when that copy is in force at once. `Tags::Rename`, `Tags::Destroy` and `Tags::Merge` pass the pages whose list blocks refer to the tag and the posts that carry it (below). `Locales::Enable` passes `everything: true`, and `rebuild!` is "empty the table, then everything". The trash services pass nothing of their own: the branch root's save is the touch. `refresh` locks no page, post or block row: its callers hold what the lock order asks for (a save its own row, a block service the page's first, `take!` the record's), and inside it only `public_paths` rows are written, pages top-down and then posts by id.

**Guards.** `test/models/public_site/paths_test.rb` has the parity test: after every write path that feeds a URL the live rows, the recorded host included, must equal what `PublicSite::Paths.rebuild!` would write ("every write path leaves public_paths equal to a full rebuild"; a partial oracle: it asks no condition, but works from the same records). `test/lib/public_paths_entry_test.rb` holds that nothing under `app/` or `lib/` calls a function inside the entry point ("outside its own file PublicSite::Paths is asked to refresh, to rebuild, to sweep the window, or to read: nothing calls a function inside the entry point") and that only `PublicSite::Paths` writes a row of the table.

## Addresses follow the published copies

A post's address is not made of its slug and the tree alone: it runs through the page whose list block lists it, and which block lists which post is content, held in the published copies (`docs/superpowers/specs/2026-10-11-drafts-of-live-content-design.md`, §5). So `PublicSite::Paths.canonical_pages` reads both sides as published. The candidates are `Publishing::Listing.blocks`: of a kept page that is published or scheduled and has a copy in force, the list blocks of its current copy; of every other kept page (a draft, whatever copies it kept, and a page written around the services), the blocks of its rows; of a trashed page, none. Each post is judged by the tags of its current copy when it is published or scheduled and has one, by its rows' tags otherwise, and a filter's tag is matched by id. That is the rule the public list itself is drawn by (`Publishing::Listing.posts`), which is the point: a post's address lies under the page whose published list shows it. A list block changed, added or deleted in the rows of a live page, and a tag changed in the rows of a live post, therefore move no address until that record's changes are published (`test/models/public_site/paths_test.rb`: "changing a live page's list block to another type moves no address until the page is published", "a tag changed in a live post's rows moves it to another listing only when the post is published"; `test/integration/public_drafts_test.rb`: "a post whose tag was taken off in the rows keeps its address and the list's link to it until the post is published").

**What stays on the rows, and immediate:** a slug, the place in the tree, publication and scheduling, the trash, a post's content type. The owner of every candidate block is the page's row, and the ranking (live chain, specificity, tree order) reads rows only. The block's own refresh (`ContentBlock#sync_listed_post_paths`) and the join row's (`PostTag`) still run; for a record with a copy they find nothing to move.

**A live record with no copy** (written around the services: a console, a test) is listed and addressed from its rows. That is not enforced away; what keeps it a case of tests and a console is that the application sets a publication time in two places only, each of which takes the copy in the same transaction (`test/lib/publishing_guards_test.rb`: "published_at is assigned only in the two save services").

**The clock, and the settle marker.** A copy taken with a time ("Publish changes" at a time) comes into force with no write. `published_versions.settled_at` says that its coming into force has been acted on: a copy in force at once is marked by `take!` as it is written, and one with a time is **due** from its time until some refresh settles it. Every `refresh` begins with `Publishing::Version.settle!`, which marks the due copies (one statement on a partial index that is normally empty, the rows locked so a second refresh at once finds nothing left) and has their records refreshed like any touched record, in a pass of its own ahead of the caller's. So no derivation acts on a picture the clock has made stale: a page whose scheduled change is in force and which is then renamed, moved, unpublished or trashed gives up what its older copy listed in that same save (`test/models/public_site/paths_test.rb`: the four tests "a page whose scheduled change is in force and not settled, then …: the posts its older copy listed are looked at"), a copy is never too late to be settled ("a copy that came into force long before any sweep is settled all the same, and one of a trashed page is settled and gives no address"), and it is settled once ("a refresh of nothing settles what is due, once: a second run reads the due copies and nothing else"). Until the first refresh after its time the public list is already drawn from the new copy, so a post a new list block lists has no address yet and one a removed block listed keeps an address that answers 404: five minutes in production, where the sweep below is also a refresh, and where nothing sweeps until the next write that refreshes anything.

**The one time window left** is a page going live by the clock: nothing records that a page's `published_at` has passed, so `PublicSite::Paths.sync_went_live(since:)` hands `refresh` every kept page whose time lies in the window, from `PublicSite::SyncWentLiveJob` every five minutes over 24 hours (`config/recurring.yml`, which, like the trash job, runs only where Solid Queue is the adapter). There is no window for copies any more, no reading back through older copies, and no cache key.

**A publish that would take an address away is refused.** Publishing never leaves a live record without an address: not the record that is published, and not another one (a page's new list block can take a live post out of the list it was in and want it at an address a subpage holds). Nobody works out beforehand what a publish would do. `Publishing::PublishChanges`, `Pages::Save` and `Posts::Save` do it inside their transaction and read what the addresses answered (`Publishing::Version#yields`, which is `refresh`'s answer for the copy just taken; a page's own save keeps its answer in `Page#address_yields`), and `Publishing::KeepsAddresses#lost_addresses` says which yields refuse: one of the published record itself, and one of any live record that had an address until this transaction and has none now. Then the service rolls back and answers one sentence per record and address: "The post “Hello” would get the address /topic/hello, which is already taken in EN". The copy, the addresses and the audit event go with the rollback, and the version bump, the `public_paths.changed` announcements and the live signals were all deferred to a commit that does not come; that is what the refusal relies on, and `test/integration/public_drafts_test.rb` holds it ("publishing a page's changes that would take a live post's address away is refused, and nothing is written, announced or signalled", with "the guard of a refused publish can fail: …"). One line stays behind: the log line of the yield that was taken back. A **scheduled change** moves no address until its time, when nobody can be refused any more, so it is asked when it is scheduled, of the site as it is then: taken as if it were published at once inside a savepoint, looked at, rolled back whatever the answer, and then taken with its time ("a scheduled change that is free is asked as if now, rolled back, and taken with its time: one copy, one event, no address moved yet"). A record that was without an address before is not this publish's doing and refuses nothing, and because the due copies are settled in a pass of their own, a publish answers for itself only ("a publish answers for itself only: another record's scheduled change that came into force onto a taken address does not refuse it").

What cannot be refused is the clock: a scheduled copy that comes into force onto an address taken since it was scheduled. `public_paths` equals a full rebuild whatever happens, so the record yields like any other clash and has no address until someone resolves it, and the settle pass reports it through `Rails.error.report` (`PublicSite::Paths::AddressTaken`): once, because a copy is settled once, after the commit, with the copies' ids and per yield the record's type and id, the language and the address it wanted, never content ("a scheduled change of a post's tags that comes into force onto an address taken since leaves the post without an address, and reports the clash once").

**The slug's validation stays outside** (`HasPublicPaths#public_paths_are_available`): a slug typed onto a taken address fails before anything is written, on the slug field of the language it clashes in. It sees what a save can see; what follows from a publish (a tag made by the very save that carries it, a published post's tags about to be published) is the refusal above. A draft is asked by `Posts::Save` only when its tag set really changed: the editor resends every tag chip with every autosave, and a draft that another record's write left without an address goes on saving its text ("a draft post that wants a taken address still autosaves with its tags resent unchanged, and is refused when published").

**Tags.** A list block's filter is a tag's name in its settings. A row is asked by that name, now (`ContentBlock#listed_tag_id`): a draft page's list follows a rename at once. A published copy **records the tag's id when it is taken, and is never asked by name afterwards** (`ContentBlock#tag_recorded?`): a copy taken when no tag had the name recorded none and **lists nothing until its page is published again**, whoever makes a tag of that name later. No publish and no block save ever creates a tag, so a tag that was renamed or deleted cannot come back through a published list, and a tag deleted and made again under the same name is another tag to a copy (`test/queries/publishing/listing_test.rb`: "a filter whose tag did not exist when the copy was taken lists nothing, also once a tag has that name, until the page is published again", "a tag deleted and made again under the same name is another tag to a copy"; `test/integration/public_drafts_test.rb`: "a list for a tag that did not exist when its page was published stays empty, and the first post that carries the tag is not addressed under it, until the page is published again"). In CS Studio the block form's tag field cannot name a tag that does not exist, so this is the case of MCP, a script, and a tag renamed or deleted after the block was set. A rename and a delete change nothing public while both copies hold the tag's id; they show when the page or the post is published again. The three tag services say what they touched through one finder, `Tags::Listings#pages_listing(names:, ids:)`: the owners of the row blocks that filter by one of the names, and the pages one of whose copies recorded one of the ids (`Publishing::Version.listing_tag`, by jsonb containment). `Tags::Rename` passes both names and no id; `Tags::Destroy` the tag's name and id and, as posts, its carriers, read before the destroy; `Tags::Merge` both tags' names and ids and the carriers of both. A **merge is immediate everywhere**, as a slug is: `Tags::Merge` calls `Publishing::Version.repoint_tag!(from:, to:)`, the one write to what a copy refers to after it is taken, which replaces the merged tag's id in every copy's `tag_ids` and in the id a copy's list block recorded, reading only the copies that hold it. A tag's id in a copy is a reference, not content, and the id is about to stop existing; the names a visitor reads in a copy are not touched and change when the record is published. After a merge the lists that held the merged tag's posts still hold them. The two ids are one from then on, so a list that filters by either holds the carriers of both, at once: a post of the *kept* tag that nobody touched can move to a list that filtered by the merged one (`test/lib/publishing_guards_test.rb`: "inside Publishing::Version only take!, repoint_tag! and settle! write a row; only Tags::Merge repoints and only PublicSite::Paths settles"; `test/integration/public_drafts_test.rb`: "merging a tag changes no public list and no address, with no publish, and publishing the page and the posts afterwards changes nothing either", "a merge reaches a pending copy too: a scheduled change keeps its posts when its time comes", "after a merge a list that filtered by the merged tag holds the kept tag's posts too, and one of them moves there").

**The preview** shows the rows, so a post in a list block that is only in a live page's rows has no address there. Its link is that page's preview address plus the post's slug (`PublicSite::Urls#path_for(post, locale, listed_on: page)`, preview only), which the preview's resolver answers with the post drawn on that page (`Resolver#listing_fallback`, `Result#listing_page`); a visitor gets a 404 at the same path. Publicly, a list entry of a post that has no address (a yielder) links to the listing page itself.

## Public routing

Routes: `config/routes.rb`. Two catch-all routes, declared last (named routes like `/cs-studio`, `/mcp`, `/up` must win first; the unprefixed catch-all also skips `/rails/active_storage/...`, whose routes Rails draws after this file): `get ":locale(/*path)"` for an explicit locale prefix (`/de/about`), and `root`/`get "*path"` for no prefix at all (served in `SiteSetting#default_locale`, editable in CS Studio's Settings module, checked per request — not a code-level default). `PagesController#redirect_default_locale_prefix` 302s an explicit prefix that happens to name the *current* default locale to the unprefixed URL, so each page has exactly one canonical address even though the default can change at runtime. `PagesController#show` resolves the path through `PublicSite::Resolver` against `public_paths`, where pages and posts both have rows: a post's URL is its canonical listing page's path plus its own slug (`PublicSite::Paths.canonical_page`) — posts have no page-tree node of their own. An old URL answers a 301 to the current one; a miss, a draft (outside preview) or a trashed record is a 404. `PagesHelper#page_url_path`/`#post_url_path` and `config/sitemap.rb` both mirror the same default-locale-omits-prefix rule when building links — grep for `default_locale` if changing how locales map to URLs.

## SEO / sitemap

`config/sitemap.rb` (gem `sitemap_generator`) walks the published page tree across all locales; built via `rake sitemap:create`, output to `public/sitemap.xml`.
