# Page tree and public routing

> Describes: `app/models/page.rb`, `app/models/page/`, `app/models/public_site/`, `app/models/public_path.rb`, `app/models/concerns/has_public_paths.rb`, `app/controllers/pages_controller.rb`, `config/routes.rb`, `config/sitemap.rb`, `app/jobs/public_site/`.

## The page tree

`Page` (`app/models/page.rb`) is a `closure_tree` (gem `closure_tree`), backed by a `page_hierarchies` closure table, with exactly one root (the homepage, enforced by `only_one_root_page` and, as a database backstop, the partial unique index `index_pages_on_single_root`). `page_type` is an enum with `validate: true`, so a forged value is an ordinary validation failure on the field, not an `ArgumentError`. Sibling order is the `position` column; closure_tree renumbers it, but reordering to a given rank is implemented on top of that in `remember_requested_position`/`place_among_siblings` because closure_tree's own renumbering doesn't do what a literal "move to rank N" needs. In CS Studio a page is moved in the page tree: by dragging the handle of its row (`Admin::PagesScreen::TreeNodeComponent`, SortableJS in `admin--pages--tree`) or, with the focus on that handle, by the keyboard (Space picks the row up and drops it, the up and down arrows step it among its siblings, the right arrow nests it, the left arrow moves it out, Escape cancels), both sent as `Pages::Move.call(page, parent:, position:)` by `Admin::TreeController` (`test/system/admin/tree_test.rb`: "dragging a page onto another node reparents it and persists"). A move is a write of the moved page (its `updated_at` moves, its URLs are resynced, its new siblings are renumbered with `update_columns`), sent through the write queue like every other write of the screen, but it is **not a change of the page's settings**: `parent_id` and `position` are in `Page::SETTINGS_BASE_IGNORES`, so the page settings form's base (`settings_changed_at`) stays where it was and someone typing in that form, in the mover's tab or a colleague's, goes on saving (`docs/reference/live-editing.md`, "The page settings form's own base"; `test/models/page_test.rb`: "a move in the tree leaves the settings base of the moved page and of its new siblings where it was"; `test/integration/admin/tree_test.rb`: "a settings form held while a colleague moves that page in the tree saves afterwards"). The homepage has no handle, and neither has a page the viewer may not move.

**The page type and the public menu.** `page_type` is `standard` or `landing`. A landing page differs in one place, the public page's header (`app/views/pages/show.html.erb`): it shows the page's subtitle under the title and its hero image; a standard page shows neither. In the page settings form the hero image and its alt text are offered only for a landing page, while the subtitle field is there for every page although only a landing page renders it. The public site's menu is not configured anywhere: it is the homepage's children that are published and not in the trash, in their sibling order (`ThemeHelper#navigation_pages`, drawn by `layouts/public/_header.html.erb`), so every live child of the homepage is in it and no other page can be.

Every public URL is precomputed and stored: the `public_paths` table (`PublicPath`, one row per record per locale, `current: true` for the live URL and `current: false` for the redirects an old URL leaves behind) is derived by `PublicSite::Paths`, never written by hand. The public router (`PagesController#show`) asks `PublicSite::Resolver` for a URL, which is a single indexed lookup in that table plus the visibility rule (`:published`, or `:preview` for signed-in editors) rather than a walk of the tree per request; `PublicSite::Urls` builds links the other way round. Sibling ranking lives in `Page::TreeRanking` (`app/models/page/tree_ranking.rb`).

## One entry point derives addresses

`PublicSite::Paths.refresh(pages:, posts:, everything:, now:)` makes the addresses of everything that depends on the records it is handed what a full rebuild would write, in the caller's transaction, and answers the changes that had to yield (empty when every record got the address it wants). **A caller says what it touched and never which posts that could have moved.** Before this there were eleven places that each worked that out for their own situation, from a before-picture each reconstructed for itself (a block's earlier settings, the copy before, the copy before that, both names of a tag), and every new situation needed every one of them taught; the holes were where one of them had not been.

**The recorded host.** A post's current row carries `listed_on_id`: the page that gives it its address. That is the one fact about an address that cannot be read back from the records afterwards, and it is what makes one function possible: "which posts did this page hold until now" is a query on the derived table, whatever the page listed and however it came to list it. `write_all` writes it with the path, and only then: a post's path begins with its host's and a current path belongs to one page, so the host cannot change under a path that stays. A page's row has none.

**What depends on a touched page**, with S the touched pages and everything below them: its own address and its subtree's (`sync_subtree`, a fixed number of statements however large the subtree); the **hosted** posts, whose row says a page of S gives them their address (the "before"); the **listable** posts, of every content type the list blocks of S name as published now (the "after"; a block that names no type lists every type); and the **unhoused** posts, kept and with no address at all, of the content types some list block of the site names now. A post that had to yield has no row to say where it wanted to be, so it is looked at with every touched page, which is also what gives a yielder its address in the very save in which the page that held it moves away; narrowed to the listed types, because a post no block can list gets no address whatever happens and a site's unlisted posts are not to be read on every page save. A page's rank among the candidates matters only for posts it hosts or can list, so a post outside all three sets keeps the winner it had. A touched post is its own address, and nothing else. **Where `public_paths` can still differ from a rebuild**, an interim tracked in the roadmap: a post that yielded to another *post* which then moves away (a post's touch looks at that post only; the next touch of any page heals it); a post that yielded in one language while it has an address in another (it has a row, so it is not among the unhoused); a *page* that yielded; and the pages below a page that yielded. `bin/rails public_paths:rebuild` heals each. A record that stands without an address is looked at by every page's refresh and yields again each time; that writes no row, so it moves no content version and is logged only when the address is lost, not each time it is met (`test/models/public_site/paths_test.rb`: "with a live post that stands without an address, renaming an unrelated draft page leaves the content version where it was and logs nothing; a real change bumps as it does without it"). A redirect carries no host: the column is about current rows.

**Who calls it, and with what.** A page's save that changed one of its URL inputs (`url_inputs_are`: slug, parent, position, publication, trash state; any other save, and a bare `touch`, refreshes nothing) passes itself; so does a post's (its slug, content type, publication or trash state, or its tags, which the association notes), and a `PostTag`'s commit passes its post. A list block saved or destroyed passes its page (not when it is destroyed with its page: the page's own `after_destroy` passes the page's id, and the posts it hosted are found by the host their rows record although the page is gone). `Publishing.keep_address!` passes the record whose copy `Publishing::Version.take!` has just taken, and for `Posts::Save` a draft post whose tag set it has just changed, and reads the answer (below). `Tags::Rename`, `Tags::Destroy` and `Tags::Merge` pass the pages whose list blocks refer to the tag and the posts that carry it (below). `Locales::Enable` passes `everything: true`, and `rebuild!` is "empty the table, then everything". `PublicSite::SyncWentLiveJob` passes nothing: it is there for what every refresh does first (the clock, below). The trash services pass nothing of their own: the branch root's save is the touch. `refresh` locks no page, post or block row: its callers hold what the lock order asks for (a save its own row, a block service the page's first, `take!` the record's), and inside it only `public_paths` rows are written, pages top-down and then posts by id.

**Guards.** `test/models/public_site/paths_test.rb` has the parity test: after every write path that feeds a URL the live rows, the recorded host included, must equal what `PublicSite::Paths.rebuild!` would write ("every write path leaves public_paths equal to a full rebuild"; a partial oracle: it asks no condition, but works from the same records). `test/lib/public_paths_entry_test.rb` holds that nothing under `app/` or `lib/` calls a function inside the entry point ("outside its own file PublicSite::Paths is asked to refresh, to rebuild, or to read: nothing calls a function inside the entry point") and that only `PublicSite::Paths` writes a row of the table.

## Addresses follow the published copies

A post's address is not made of its slug and the tree alone: it runs through the page whose list block lists it, and which block lists which post is content, held in the published copies (`docs/superpowers/specs/2026-10-11-drafts-of-live-content-design.md`, §5). So `PublicSite::Paths.canonical_pages` reads both sides as published. The candidates are `Publishing::Listing.blocks`: of a kept page that is published or scheduled and has a copy in force, the list blocks of its current copy; of every other kept page (a draft, whatever copies it kept, and a page written around the services), the blocks of its rows; of a trashed page, none. Each post is judged by the tags of its current copy when it is published or scheduled and has one, by its rows' tags otherwise, and a filter's tag is matched by id. That is the rule the public list itself is drawn by (`Publishing::Listing.posts`), which is the point: a post's address lies under the page whose published list shows it. A list block changed, added or deleted in the rows of a live page, and a tag changed in the rows of a live post, therefore move no address until that record's changes are published (`test/models/public_site/paths_test.rb`: "changing a live page's list block to another type moves no address until the page is published", "a tag changed in a live post's rows moves it to another listing only when the post is published"; `test/integration/public_drafts_test.rb`: "a post whose tag was taken off in the rows keeps its address and the list's link to it until the post is published").

**What stays on the rows, and immediate:** a slug (a live page's is changed through its own confirmed form, `PATCH pages/:id/slug`, `docs/reference/publishing.md`; a typed slug of a live page is ignored by the autosave), the place in the tree, publication and scheduling, the trash, a post's content type. The owner of every candidate block is the page's row, and the ranking (live chain, specificity, tree order) reads rows only. The block's own refresh (`ContentBlock#sync_listed_post_paths`) and the join row's (`PostTag`) still run; for a record with a copy they find nothing to move.

**A live record with no copy** (written around the services: a console, a test) is listed and addressed from its rows. That is not enforced away; what keeps it a case of tests and a console is that the application sets a publication time in two places only, each of which takes the copy in the same transaction (`test/lib/publishing_guards_test.rb`: "published_at is assigned only in the two save services").

**The clock, and the settle marker.** Two things begin to show with no write: a change published with a time ("Publish changes" at a time), when that time passes, and a scheduled page or post, when its `published_at` passes. Both are one event here, a published copy that is **due**. A copy shows from the later of its own time (`live_at`) and its record's (`published_at`); `published_versions.settled_at` says that its beginning to show has been acted on. `take!` marks a copy that shows at once as it writes it, and leaves every other unsettled: a change with a time, and the copy of a record that is only scheduled (that copy is in force at once and simply not shown yet, so a scheduled record moved to another time, or published now, needs nothing kept in step: its copy is due when the record is live, whenever that is). Every `refresh` begins with `Publishing::Version.settle!`, which takes the copies that are due, marks them (one statement when none is waiting; the due rows locked, so a second refresh at once finds nothing left; a copy of a record that is not published, because its schedule was removed or it was unpublished with a change pending, will never be due and is marked the first time it is met, with no refresh: "a schedule that was removed and a change pending on an unpublished page leave no copy waiting, and a refresh of nothing is one statement again") and has their records refreshed like any touched record, in a pass of its own ahead of the caller's. So no derivation acts on a picture the clock has made stale: a page whose scheduled change is in force and which is then renamed, moved, unpublished or trashed gives up what its older copy listed in that same save (`test/models/public_site/paths_test.rb`: the four tests "a page whose scheduled change is in force and not settled, then …: the posts its older copy listed are looked at"), nothing is ever too late to be settled ("a page that went live long before any refresh is settled all the same", "a copy that came into force long before any sweep is settled all the same, and one of a trashed page is settled and gives no address"), and it is settled once ("posts move to a listing page that went live by the clock when the next refresh settles its copy, once", "a refresh of nothing settles what is due, once: a second run reads the due copies and nothing else"). Until the first refresh after the moment, the public site already shows the new state, so a post a new list block lists has no address yet and one a removed block listed keeps an address that answers 404. `PublicSite::SyncWentLiveJob` keeps that short: every five minutes (`config/recurring.yml`, which, like the trash job, runs only where Solid Queue is the adapter) it calls `refresh` with nothing touched. Where nothing sweeps, the next write that refreshes anything does it.

**There is no time window any more**: no sweep of the pages whose time passed in the last day, none for copies, no reading back through older copies, no cache key. The price, on purpose: a record that is scheduled *around the services* (a console, a test) has no copy to be due, and its going live is acted on only by the next refresh that reaches its posts, or by `bin/rails public_paths:rebuild` ("a page scheduled around the services has no copy, so its going live is acted on by the next refresh that reaches its posts, not by the clock's"). The application has no such writer (`test/lib/publishing_guards_test.rb`: "published_at is assigned only in the two save services").

**Only a record's OWN address refuses its save or its publish.** Two things refuse, and nothing else does. The slug's validation (`HasPublicPaths#public_paths_are_available`) refuses before anything is written wherever it can see the clash: a slug, a content type, a publication time or a tag that would put the record on an address another record holds fails on the slug field of the language it clashes in. What it cannot see follows from the record's own tags: a tag made by the very save that carries it, and the tags a publish makes public (a live post is judged by its copy's). For those there is ONE check, `Publishing.keep_address!`, which is the record's own refresh: it raises `Publishing::AddressTaken` when the record ITSELF had to yield, carrying the yields as data (`lost`: the record, the language, the address it wanted). `Publishing::Version.take!` ends with it for every copy that is in force at once, and `Posts::Save` calls it for a draft whose tag set really changed (a draft has no copy; and only then: the editor resends every tag chip with every autosave, and a draft that another record's write left without an address goes on saving its text, "a draft post that wants a taken address still autosaves with its tags resent unchanged, and is refused when published"). The three services, `Publishing::PublishChanges`, `Pages::Save` and `Posts::Save`, rescue that one error outside their transaction, put the object in memory back to what is stored and answer one sentence (`Publishing::KeepsAddresses#address_taken`, a literal like the validation's message): "The post “Hello” would get the address /topic/hello, which is already taken in EN". The error has rolled the transaction back: the copy, the addresses, the record's own row and the audit event are gone, and the version bump, the `public_paths.changed` announcements, the report and the live signals were all deferred to a commit that does not come (`test/integration/public_drafts_test.rb`: "publishing a post's tags that would put it on an address another record holds is refused, and nothing is written", "a new live post whose brand-new tag would put it on a taken address is refused as before, and so is a draft", "a post published again after an unpublish is refused when the tags it got as a draft would put it on a taken address"; `assert_nothing_happened` is kept honest by "the guard of a refused publish can fail: …"). One thing stays behind: the log line of the yield that was taken back.

*A record that stood without an address already* is not refused its own text. `take!` is told by "Publish changes" that the record was on the site before this copy (`shown: true`; a scheduled record, which never was, is passed the same, and is refused nothing it would have been given), and then only an address the record HAD and lost in this publish refuses; a record that goes live with this copy, and a draft, are refused by any yield of their own ("a live post that stands without an address blocks nobody: the page above it, the homepage, a schedule, an unpublish and publish again, and the post's own text all go through").

**Another record that loses its address refuses nobody.** A publish that changes which page lists other posts (a list block removed, re-typed or re-tagged and published; a page published, scheduled, moved or trashed) can take a live post to an address another record holds. That post **yields**, as it always has: it has no address until the clash is gone, `public_paths` equals a full rebuild, the yield is logged when the address is lost, and a LIVE record that lost its address is reported once through `Rails.error.report` (`Publishing::AddressTaken`, `PublicSite::Paths.report_clash`): after the commit, with the due copies' ids and per yield the record's type and id, the language and the address it wanted, never content. A record met again that stood without an address is neither logged nor reported again, and it blocks nobody: every page above it publishes ("removing a page's list block and publishing drops a live post to no address: named beforehand, not refused, logged and reported once, and the addresses are a rebuild's"; "publishing a page's changes that take a live post to an address a subpage holds is not refused: the post yields and the clash is reported"; "publishing a draft page whose list takes a live post to an address a subpage holds is not refused: the page is live, the post yields and the clash is reported once").

*A copy that does not show yet* moves no address now and is asked nothing: a change with a time, and the copy of a page or post that is only scheduled. At its moment the first refresh settles it, whatever has to yield then yields, also the record's own address, and the clash is reported in the same way, once because a copy is settled once ("a page's scheduled change that will take a live post's address away is taken and moves nothing yet; at its time the post yields and the clash is reported once"; "scheduling a draft page whose list will take a live post's address away is not refused: nothing moves until its time, then the post yields and the clash is reported once"; "a scheduled change of a post's tags that comes into force onto an address taken since leaves the post without an address, and reports the clash once"). The header's Publish on a record that is already scheduled takes no copy (it changes the time only): for a page a clash is the clock's case a little earlier ("a clash that arose after a page was scheduled is not refused when the page is then published now: the post yields and the clash is reported, as the clock would"), and for a post the publication time is a URL input, so the validation sees it ("Publish on a scheduled post that another record's publish left without an address is refused by the slug's validation, which the person sees on the slug field").

**What a publish would take away can be asked beforehand, as information.** `PublicSite::Paths.foresee(record, now:)` answers the addresses live records would lose if the working rows of a published or scheduled record were published at that time, the record's own among them: `[{ record_type:, record_id:, locale:, path: }]`, data and never wording. It tries inside a savepoint (the copy is taken, the addresses follow, the current rows are compared with what they were) and rolls back whatever happened, so it keeps nothing and tells nobody. No service decides anything by it: its one caller is `Publishing::Changes.lost_addresses`, which `Admin::PublishingController#changes` asks (a POST sent through the write queue when the publish dialog opens, never a GET, because the trial takes the record's row lock) to name, in the overview, the live records that would lose their address. It reads every current row twice, so it belongs to that dialog and to no save path; it is asked for now, also when "At a time" is chosen, so a clash that only exists at the later time is not shown.

The migration's first copies are written by its own SQL, not by `take!`. The starter content and the seed go through the services like anyone.

**Tags.** A list block's filter is a tag's name in its settings. A row is asked by that name, now (`ContentBlock#listed_tag_id`): a draft page's list follows a rename at once. A published copy **records the tag's id when it is taken, and is never asked by name afterwards** (`ContentBlock#tag_recorded?`): a copy taken when no tag had the name recorded none and **lists nothing until its page is published again**, whoever makes a tag of that name later. No publish and no block save ever creates a tag, so a tag that was renamed or deleted cannot come back through a published list, and a tag deleted and made again under the same name is another tag to a copy (`test/queries/publishing/listing_test.rb`: "a filter whose tag did not exist when the copy was taken lists nothing, also once a tag has that name, until the page is published again", "a tag deleted and made again under the same name is another tag to a copy"; `test/integration/public_drafts_test.rb`: "a list for a tag that did not exist when its page was published stays empty, and the first post that carries the tag is not addressed under it, until the page is published again"). In CS Studio the block form's tag field cannot name a tag that does not exist, so this is the case of MCP, a script, and a tag renamed or deleted after the block was set. A rename and a delete change nothing public while both copies hold the tag's id; they show when the page or the post is published again. The three tag services say what they touched through one finder, `Tags::Listings#pages_listing(names:, ids:)`: the owners of the row blocks that filter by one of the names, and the pages one of whose copies recorded one of the ids (`Publishing::Version.listing_tag`, by jsonb containment). `Tags::Rename` passes both names and no id; `Tags::Destroy` the tag's name and id and, as posts, its carriers, read before the destroy; `Tags::Merge` both tags' names and ids and the carriers of both. A **merge is immediate everywhere**, as a slug is: `Tags::Merge` calls `Publishing::Version.repoint_tag!(from:, to:)`, the one write to a copy after it is taken, which replaces the merged tag's id in every copy's `tag_ids` and in the id a copy's list block recorded, reading only the copies that hold it. A tag's id in a copy is a reference, not content, and the id is about to stop existing. The id and name a post's copy shows of the tag are rewritten to the kept tag's with it, so no visitor reads the name of a tag that is gone and no post is left with anything to publish (`docs/reference/publishing.md`, "Tags"); the name in a list block's copied settings, which nobody reads, changes when its page is published. After a merge the lists that held the merged tag's posts still hold them. The two ids are one from then on, so a list that filters by either holds the carriers of both, at once: a post of the *kept* tag that nobody touched can move to a list that filtered by the merged one (`test/lib/publishing_guards_test.rb`: "inside Publishing::Version only take!, repoint_tag!, settle! and withdraw_pending! write a row; only Tags::Merge repoints, only PublicSite::Paths settles and only the cancel and the discard withdraw"; `test/integration/public_drafts_test.rb`: "merging a tag changes no public list and no address, with no publish, and publishing the page and the posts afterwards changes nothing either", "a merge reaches a pending copy too: a scheduled change keeps its posts when its time comes", "after a merge a list that filtered by the merged tag holds the kept tag's posts too, and one of them moves there").

**The preview** shows the rows, so a post in a list block that is only in a live page's rows has no address there. Its link is that page's preview address plus the post's slug (`PublicSite::Urls#path_for(post, locale, listed_on: page)`, preview only), which the preview's resolver answers with the post drawn on that page (`Resolver#listing_fallback`, `Result#listing_page`); a visitor gets a 404 at the same path. Publicly, a list entry of a post that has no address (a yielder) links to the listing page itself.

## Public routing

Routes: `config/routes.rb`. Two catch-all routes, declared last (named routes like `/cs-studio`, `/mcp`, `/up` must win first; the unprefixed catch-all also skips `/rails/active_storage/...`, whose routes Rails draws after this file): `get ":locale(/*path)"` for an explicit locale prefix (`/de/about`), and `root`/`get "*path"` for no prefix at all (served in `SiteSetting#default_locale`, editable in CS Studio's Settings module, checked per request — not a code-level default). `PagesController#redirect_default_locale_prefix` 302s an explicit prefix that happens to name the *current* default locale to the unprefixed URL, so each page has exactly one canonical address even though the default can change at runtime. `PagesController#show` resolves the path through `PublicSite::Resolver` against `public_paths`, where pages and posts both have rows: a post's URL is its canonical listing page's path plus its own slug (`PublicSite::Paths.canonical_page`) — posts have no page-tree node of their own. An old URL answers a 301 to the current one; a miss, a draft (outside preview) or a trashed record is a 404. `PagesHelper#page_url_path`/`#post_url_path` and `config/sitemap.rb` both mirror the same default-locale-omits-prefix rule when building links — grep for `default_locale` if changing how locales map to URLs.

## SEO / sitemap

`config/sitemap.rb` (gem `sitemap_generator`) walks the published page tree across all locales; built via `rake sitemap:create`, output to `public/sitemap.xml`. A record's `lastmod` is the date of what the public sees: for a record with a published copy, the later of the newest copy in force's `live_at` and the record's `published_at`; for one with none (written around the services), its `updated_at`. So typing on a live record does not move it, publishing the changes does, and **a slug or a move does not move a copied record's sitemap date** (the roadmap lists it).
