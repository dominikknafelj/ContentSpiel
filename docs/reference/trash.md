# Trash

> Describes: `app/models/concerns/trashable.rb`, `app/services/trash/`, `app/jobs/trash/`, `app/controllers/admin/trash_controller.rb`, `app/components/admin/trash_screen/`.

## Soft deletion

Pages, posts and library images are soft-deleted (spec `docs/superpowers/specs/2026-09-29-trash-design.md`); a single block, a tag, a group, a user or a token is still deleted for good. Columns: `trashed_at` (indexed) and `trashed_by_id` (FK to `users`, `on_delete: :nullify`) on `pages`/`posts`/`media_assets`, plus `pages.trash_root_id` (FK to `pages`, `on_delete: :nullify`) naming the page an editor actually picked, and `site_settings.trash_retention_days` (default 30, `0` = never purge automatically, edited in CS Studio's Settings module). `Trashable` (`app/models/concerns/trashable.rb`) gives `kept`/`trashed` scopes and `#trashed?` -- deliberately **no `default_scope`**, which would silently hide rows from closure_tree, uniqueness checks, associations and the Trash screen itself. Hiding is explicit instead, at the narrowing points: `AccessControl.scope` (kept only unless called with `trashed: true`, which only the Trash screen does -- so every CS Studio list, the tree, pickers, `/preview`, MCP and the "not found, not forbidden" id lookups inherit it), `PublicSite::Resolver` (and its listing-page fallback), `listed_posts`, navigation, internal-link rendering (a link to a trashed page or post renders as plain text), the sitemap, the related-posts editor, the media library/picker/search, `Media::Choosing` and rich-text image validation (a trashed image reads as missing), and MCP's post and media tools. `test/integration/trash_visibility_test.rb` pins every one of them with a kept-vs-trashed pair; a new list, search, picker or public query over pages, posts or images belongs in it. URLs are freed through `PublicSite::Paths` itself, not by any trash code: `compute_path` returns nil for a trashed record and `canonical_page` ignores listing blocks on trashed pages, so saving a changed `trashed_at` deletes (on trash) or rebuilds (on restore) the record's `public_paths` rows -- redirects included, not recreated on restore -- through the ordinary model callbacks, and nothing (`rebuild!`, a `refresh` caused by a save elsewhere) can resurrect a trashed record's URL. The public site answers 404 for a trashed page or post, not 410. `Page::TreeRanking` counts kept siblings only, so "move to rank N" means rank N among the pages an editor can see.

## The services

Four services (`app/services/trash/`), all `ApplicationService`s, audited as `page|post|media.trashed/restored/purged` and `trash.emptied`. `Trash::Move` trashes a page with its whole kept branch (descendants flagged with `update_all`, one shared timestamp and `trash_root_id`, root saved last so a single `sync_subtree` pass sees them trashed; a descendant already trashed on its own keeps its own root) -- the root saved with `save!(validate: false)`, callbacks still running, so a record that has gone invalid since its last save (an unregistered content type, a reserved slug) can still be cleared away, while `Trash::Restore` keeps full validation -- and refuses an image while a *kept* page or post still uses it (`Media::Asset#used_by_kept_owner?`) -- which is what makes it safe that rich-text image rendering never looks at an asset's trash state. `Trash::Restore` brings back exactly the pages sharing the root's `trash_root_id`; a page trashed as a branch member comes back only with its root, or alone under a new `parent:` (same checks as `Pages::Move`: `pages.move` on the page, `pages.create` under the target, never itself or a descendant; the CS Studio picker is a server-rendered `<select>` of the pages `AccessControl.creatable_parents` offers). The chosen parent is loaded through the read scope: one the actor can't read, a trashed one and an id that names nothing all get the same plain failure (`Trash::Restore::UNKNOWN_PARENT`), never a 403 or an `access.denied`. Slugs were free while in the trash, so a slug taken in the meantime moves to the first free `-2`, `-3`, ... suffix, per locale (taken in `de` but free in `en` changes only `de`). Restoring a page or post also restores every trashed library image its hero, blocks or bodies still reference, each with its own `media.restored` event (metadata `restored_with`), so a restored page never points at a trashed image; a page's own `page.restored` lists the branch members that came back in `restored_page_ids` (mirroring `page.trashed`'s `descendant_ids`). A refusal that names a branch's root names it by title only when the actor may read it (`Trash::ItemPermissions#branch_root_name`), "the page it was moved to the trash with" otherwise. `Trash::Purge` is the permanent delete `Pages::Destroy`/`Posts::Destroy`/`Media::Destroy` used to be: a page takes its whole subtree deepest first (all of it must be trashed), recording one `page.purged` per destroyed page -- the root's listing the rest in `descendant_ids`, each descendant's naming the root in `purged_with` -- and is refused for a member of another page's still-trashed branch -- purge the root instead; before anything is destroyed the branch's pages are locked in id order, the page-first order every write to a page's blocks keeps (`docs/reference/content-blocks-and-types.md`, "The lock order"), and a page destroys the blocks in its sections before the sections, which the foreign key from a block to its section requires; an image goes only once no usage row at all points at it (trashed owners included), an FK violation becoming an ordinary failure, the file purged after commit. `Trash::Empty` runs `Purge` over `Trash.roots` (page branches, then posts, then images -- so an image's trashed owners are gone first), each item in its own savepoint, reporting what it skipped -- an exception out of one item's purge is rescued into a skip ("Couldn't be deleted: <class>"), so the rest still go and `trash.emptied` is still recorded; the retention job rescues and logs the same way. Permissions (`Trash::ItemPermissions`): moving, restoring or purging one item needs its ordinary delete right (`pages.delete`/`posts.delete` with their scopes, or for an image `media.manage` / uploader with `media.upload`); `trash.empty` (Admin only) empties everything **and** permits purging any single trashed item, never moving or restoring. `Trash::PurgeExpiredJob` (`app/jobs/trash/`) purges roots older than the retention period via `Trash.each_root(trashed_before:)` (re-finding each root at its turn, so a subpage already swept by an ancestor's branch purge isn't purged twice), as the trusted nil actor on the `:system` channel; it's scheduled in `config/recurring.yml`, which only runs where Solid Queue is the adapter (production -- development and test use the default adapter, so nothing purges on its own there).

**Notes.** A trashed page, post or image keeps its notes (`docs/reference/notes.md`): they are hidden with it, because every read of notes narrows through the read scope, which hides the trash, and they are back with a restore, the inbox rows addressed to people included. A trashed record takes no new note and none of its notes can be changed: every notes service reads its container through `kept` under a row lock and answers "This note is gone…" (so you can't delete your own note on a trashed record until it is restored). `Trash::Purge` deletes them for good by calling `Notes::Remove` once in its transaction, since a note's reference to its record is polymorphic and no foreign key could: for a page **before** anything of the branch is destroyed (for the page, the rest of the branch and all their blocks; `Notes::Remove` asks the purge's own right again, and a branch-scoped `pages.delete` is matched against closure rows the destroy deletes), for a post and an image **after** the destroy, with no lock of its own (a row lock ahead of the destroy reverses the order `Posts::Save` takes a post's row and its `post_tags` rows in, and could deadlock). The files of the removed notes go with them, their rows in the transaction and their stored bytes only once the purge has committed. `notes.removed` is recorded on the purged record with the thread ids, only when there was something to remove. `test/services/trash/purge_test.rb` pins the order, the rights and that a purge costs the same statements with one note as with many.

## CS Studio

CS Studio: `Admin::TrashController` (`/cs-studio/trash`) lists page branch roots ("Includes N subpages: A, B, C and N more", the names only of pages the viewer may read, the count every member a restore brings back), posts and images newest first, 50 per page (`Pagination` / `Admin::Ui::PaginationComponent`, the page in `?page=`), in tabs (`?type=pages|posts|images`, junk means All) whose counts are `TrashController.counts` -- the very numbers the sidebar badge sums -- loaded only through `AccessControl.scope(..., trashed: true)` on the delete right (so an id the viewer can't act on is a 404). A page row is a root exactly as `Trash.roots` defines one (`trash_root_id = id`, the scope `Page.trash_roots`; the pages that went with one are `Page.trash_branch_members`), so the list, the badge, Empty trash and the retention job agree on what is there; a page that is its own root but whose parent is in the trash or gone gets an inline "Restore under" with a parent select in place of the one-click Restore, disabled with "No page you can restore it under." when the viewer has no page to offer. A row shows who and when, "<who> · <time ago>": "You" or the user's `display_name` from `trashed_by`; when that is nil (the user was deleted, and the FK nullified it) the trashing's own `*.trashed` audit event stands in — its user's name, "a deleted user" when that user is gone — and it reads "System" when there is no such event or the event has neither a user nor a token. That event is read for every row of the page, in one query, because only it knows that a token did the trashing: the row then reads "<name> via <token name>", and "You, via <token name>" for the viewer's own token (the audit log's two forms), whether or not `trashed_by` is still there; an event older than the item's `trashed_at` belongs to an earlier trip to the trash and is ignored. Then come a retention tag (`RetentionTagComponent`: IN N DAYS / TODAY / NEVER, calendar days in the site zone; its tooltip and screen-reader text read "Deleted for good on or after <date>", the first day the item can go, since the sweep runs once a day), Restore and "Delete now…" (disabled with its reason as visible text while the trash still uses an image). An empty list reads "The trash is empty" or its tab's line — except for a `trash.empty` holder whose list is empty while the trash does hold that kind: "Nothing here you can restore.", because "The trash is empty" beside an Empty trash dialog that names what it deletes was a contradiction; nobody else is told what the trash holds. "Empty trash…" in the header (`EmptyTrashComponent`) counts everything `Trash::Empty` deletes, not the viewer's tab counts. Restore, delete and empty sit behind `Admin::Ui::ConfirmDialogComponent` where destructive, and come back to the tab they were done from (hidden `tab` field). The editors' delete buttons are "Move to trash" now, and the toast (`flash[:undo]`, see `docs/reference/design-system.md`) offers Undo. Its components live under `Admin::TrashScreen::`, never `Admin::Trash::` -- see "Key Conventions".
