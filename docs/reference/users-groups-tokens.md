# Users, groups and API tokens in CS Studio

> Describes: `app/controllers/admin/users_controller.rb`, `app/controllers/admin/invites_controller.rb`, `app/controllers/concerns/admin/users_list.rb`, `app/controllers/admin/groups_controller.rb`, `app/controllers/admin/api_tokens_controller.rb`, `app/components/admin/users_screen/`, `app/components/admin/groups_screen/`, `app/components/admin/tokens_screen/`, `app/services/users/` (with `leaked_password_rule.rb`), `app/services/groups/`, `app/services/api_tokens/`.

## AI assistant (API tokens)

**AI assistant** (`Admin::ApiTokensController`, `Admin::TokensScreen::CreateStepComponent` / `ConnectStepComponent` / `TableComponent`) is a numbered flow of three cards: 1 · Create a token (a required name, a group from those the viewer may assign with its description under the select — `admin--tokens--group-hint` — and Create token, the page's one primary), 2 · Add it to your assistant (the MCP URL and the client configuration, each a copy box, `Admin::Ui::CopyValueComponent` on `admin--ui--clipboard`), then the Tokens table in `.admin-table-scroll--x` with its Name column sticky: Name, Acts as, Group, Created, Last used, Status, "Revoke…" behind a dialog. Status is the state chip, never a publication's: Active `ok`, Revoked `off` with the time it was revoked as its detail. A revoked token stays listed with no action, its words meta, never dimmed by opacity. A refused create answers the same screen at 422 with each message in its own field's slot: `ApiTokens::Issue` puts its refusals on the token's `:name` and `:group` (`errors.full_messages_for(:name)`), so the screen places them by attribute and never by reading their words. `api_tokens.name` is required, stripped, at most `ApiToken::MAX_NAME_LENGTH` (60) characters and unique per user among that user's *active* tokens, case-insensitively — a validation backed by the partial unique index `index_api_tokens_on_user_and_lower_name_active`. `ApiTokens::Issue.call(user, group:, name:)` treats a nil name as "pick the next free Token N" and any String, a blank one included, as the name to validate; CS Studio and the setup wizard always pass a String, so a missing name is "Name can't be blank". The reveal is the POST's own answer — the same screen with the warn notice in step 1 holding the token's copy box and the token filled into the configuration, both `secret` targets that `admin--tokens--reveal` blanks at `pagehide` (the copy script copies the box's text, so the token stands in no attribute), `no-store`, never a redirect and never in Turbo's cache — and no part of a token is rendered, logged or audited afterwards. The setup wizard's token step (`setup/mcp_token_created`) reveals its token the same way: the same copy box and `secret` target, `no-store`, `turbo-cache-control: no-cache`, on the one wizard page that loads the `admin` entry point. The token's name is what the audit log shows: `Audit.record` writes it to `audit_events.actor_label` once, at insert (it is not a coalescing column), so "via <name>" survives the token row.

## Groups

**Groups.** The list (`Admin::GroupsScreen::ListComponent`) is a table in one card whose row is one link (the name, `.admin-row-link`, with the Built-in badge and the description; Members; Tokens, the active ones; and the verb "Edit"), with member and token counts from two grouped queries; delete is the editor's zone, never a row's. The editor (`admin/groups/_form`) is the Group card (name, description, members) and the permission matrix (`Admin::GroupsScreen::PermissionMatrixComponent` composing the rest) in two card frames, Content permissions and Other permissions. Content permissions is rows, not a grid: eleven `PermissionRowComponent`s (Posts ×5, Pages ×6) under their area's band, each a tick, the short label (a key, `permission_row.short.<action>`) with the key in mono, the scope as badge chips (a type's with its dot as the badge's mark), and "Edit scope" opening a `ScopeEditorComponent` in place — content types as a multi-select (none ticked = all) and an "Own only" toggle for posts, a tri-state branch tree for pages (`BranchTree`, `admin--groups--branch-picker`: chosen, a greyed tick for a page a chosen ancestor already includes, a dash for an ancestor of a chosen page) — then the Other permissions card, `ToggleListComponent`'s bands of switches for the unscoped keys, one more band per plugin area. Open and close are only `hidden`; everything stays in the form, and the scope of an unticked permission is ignored. **A form saved as rendered changes nothing**, which is why some things are carried as hidden inputs: a stored branch root the viewer can't open ("A page you can't open (kept)"), a chosen context-only ancestor, a redundant stored root (a root plus its own descendant; its hidden input is enabled only while the box is disabled as implied), and a *removed content type*. The last is drawn as a warn badge "! <name> · type removed" with **Remove** beside it, on a tracked hidden input, so pressing Remove is a counted change; with no live type left the chips read "All content types" followed by the warn chips, which is what Save stores.

`Groups::Save` reads such a carried name by one narrow rule (the comment above `#live` is the authority; keep this in step with it): a posted grant is read as a stored grant, unchanged, only when the stored grant is a live `LiveGrants` entry with removed types of its own (never a wholly dead grant), the permission is the same, and the posted scope *minus that entry's own removed types* is exactly the entry's live scope (the same live types, the same `own`, the same pages); a group holds one grant per permission and a request listing one twice is refused up front, so a posted grant meets at most one stored entry. Everything else is compared raw, so `can_grant?` sees the removed name and only an actor whose own grant covers it passes. The consequence, on purpose: from a non-owner who couldn't hand out the removed name the service accepts such a grant in one shape only, posted back exactly as it is (a rename of the group) — giving the name up is a removal, which `#removal_refusal` reads from the grants as stored against the grants as posted and refuses for anyone who couldn't manage the group — and the editor shows that viewer the group view-only (below) until an owner, or someone whose own grant covers the name, presses Remove. A removed name is dormant, not meaningless — re-registering a type of that name revives it — so it may stay or shrink, never appear, move or widen unchecked. **View only:** a stored group the viewer can't manage as it stands (`AccessControl.can_manage_group?` false — a grant they couldn't hand out, which includes one that carries a removed content type they couldn't grant and a wholly dead grant that names only such types) gets the notice "This group has permissions you can't hand out, so you can only view it.", the whole form in `<fieldset disabled class="admin-view-only">`, no footer and no delete zone; scopes still open through a link ("View scope"), which a disabled fieldset doesn't disable. The locked tick ("You can't grant this", a greyed disabled box whose scope is carried) is a defensive rendering only: a stored grant the viewer couldn't hand out makes the whole group view-only, and the lock is judged on the same scope `can_manage_group?` reads (a grant still exactly as stored, a removed type's name included), so no stored state reaches it. Members are a chip input (`MembersComponent`, tracked) over `GET /<admin>/users/suggest` (`Admin::UserSuggestionsController`: `groups.manage`, at least two characters, at most eight rows, name or email, prefix matches first, the user ids in `exclude` (the chips already there) left out before the limit, owners never offered — "Owners aren't listed: they already have every permission." — while an owner already stored as a member stays a chip until removed). A group's description is none when blank: `AccessControl::Group` normalises a blank one to nil, since the editor's text field posts "" for a group that has none, so the form saved as rendered writes nothing and audits nothing (`test/models/access_control/group_test.rb`: "a blank description is stored as nil, and a description is stripped"). The delete zone (`DeleteZoneComponent`, the shared `Admin::Ui::ActionZoneComponent` after the form, custom groups only) names the member count and the active tokens that go with the group ("<name> — <user>", ten then "and N more") in its confirm dialog; a built-in group gets a neutral notice instead.

**The Forms rights** (`docs/reference/forms.md`, "Who may do what"). `forms.manage` ("Manage forms") and `form_submissions.view` ("View form submissions") are unscoped keys of their own area, "Forms", drawn as a fourth built-in `ToggleListComponent` card after Content, Administration and Oversight (`ToggleListComponent::CARDS`; where it stands is a placeholder for the Design System). The Admin group holds both: a data migration grants them to an existing site's built-in Admin group (`20261104090300_grant_forms_permissions_to_admin_group`, `find_or_create_by!`, so it runs twice harmlessly), and a new site's Admin group gets them with `grants: :all` (`test/lib/built_in_data_test.rb` lists it among the migrations that grant, `GRANTED_BY_MIGRATION`, and compares what it grants with `Groups::EnsureBuiltIns`). **A permission can be registered ungrantable** (`Permissions.register(..., grantable: false)`): `forms.submit`, the visitor's alone, which the matrix and the toggle cards never offer (`Permissions.grantable` is what they, `Seeds`' `:all` and the grant fixtures read), a `Grant` naming refuses ("can't be granted"), and `AccessControl.can_grant?` answers false for, an owner included. Checking still reads every registered key (`Permissions.all`), so an ungrantable key is checked like any other and held by nobody.

## Users

**Users.** `users.name` is optional; `User#name_or_email` is the one reader (name, else email). The list (`Admin::UsersScreen::ListComponent`) is a table in one card whose row is one link (the name, `.admin-row-link`, and the verb "Edit"; no Delete, which is the editor's zone): the shared avatar (`:own` for the viewer, `:other` for everyone else), the name or email with the email beneath a name, "(you)", the Owner badge, each group a badge or "No groups", and the last sign-in — `Users::LastSignIn.for(users)` (`app/queries/users/last_sign_in.rb`), one grouped `MAX(occurred_at)` over the `session.created` audit events for the whole list, no column on the user; no event reads "Never". The list is not paginated and no index covers `(user_id, action)`, so that one query's cost grows with the audit log, not only with the users. The editor (max 880px) is two cards in Settings' frame, Details and Groups: name and email, the password behind "Set a new password…" (a `<details>`; blank keeps the password, closing it clears what was typed, and a typed password is never rendered back; a password an administrator sets for someone else ends **every** session of that person, so they are signed out everywhere and sign in again with the new one, while a person changing their own password keeps the session they did it in: `Users::OwnerProtection#end_sessions_after_password_change`, called by `Users::Save` and `Users::UpdatePassword`), the groups as tiles (`GroupCardsComponent`: `.admin-tile`, the tile is the label of its checkbox and a ticked one takes the accent outline; a group the viewer can't assign is a locked tile, sunken with "You can't grant this group." and, when ticked, carried by a hidden input), "Save user". Owner rights and deletion are zones after the form, each the shared `Admin::Ui::ActionZoneComponent` with `pending_lock: true`: the **owner zone** (`OwnerZoneComponent`, shown to owners on an existing user) opens "Make owner…" / "Remove owner rights…" dialogs that post `PATCH users/:id/owner` (`owner=1|0`, anything else a 400), which calls `Users::Save` and nothing else — the last owner's button is disabled with the reason; the **sessions zone** (`SessionsZoneComponent`, between the owner and delete zones, owners only) counts the person's live sessions and opens "End all sessions…", which sends `DELETE users/:id/sessions` to `Sessions::EndAll` and nothing else (the owner rule, one `session.ended` event with the count; drawn disabled with its reason at no live session and on your own account, which Your account's "Sign out everywhere else" serves); an owner can't be created in one step, and the ordinary editor form cannot change the flag at all: `user_params` does not permit `owner`, so a forged `user[owner]` is dropped as unpermitted and the rest of the save is an ordinary one (`Users::Save` reads an absent, nil or empty `owner` as no change). The **read-only states** come from one predicate shared with the services, `Users::Manageability.for(actor, user)` → `:editable`, `:owner_protected` ("Only owners can change other owners.") or `:outranked` ("This user has permissions you don't have, so you can't change them."): a neutral notice, a disabled fieldset, no footer and no zones. `Users::OwnerProtection` delegates its predicates to the same class, so the screen and the services can't drift; the view decides nothing — a forged write against a read-only user is still the services' 403 and one `access.denied`. A signed-in user edits their own name on the **Your account** screen (`Admin::AccountsController`, at `<admin>/account`; the page's first address, `account/password`, answers a GET with a 301 to it, the Password card is `#password`, and the two forms post where they always did, `account/password` and `account/profile`, so no non-GET is redirected. After the password form is saved or refused the page is at `…/account#password` with the Password card in view and the focus on the message. The message is in the card, at its top under the sentence about sessions: a refusal is the shared danger alert (`Admin::Ui::ErrorSummaryComponent`, each field keeping its own line; too many tries are said there too), a save the success alert, and no toast is raised. The page's own error summary, above the cards, is the Profile and Notes form's only. the fragment of the redirect never reaches a Turbo visit, so the page drawn as that answer carries `admin--account--password-answer` on the card, which writes the fragment through Turbo's history, scrolls to the card (at once with reduced motion) and focuses the card's alert. The card is the one element with the id `password`; the new-password field is `new_password`; the sidebar's entry and the name block above it both lead there; four cards in Settings' card frame (`Admin::Ui::SettingsCardComponent`, 560px), Profile, Notes, Password and Sessions, the third holding the password form with the promise about sessions under its title, the fourth in neither form): the profile form (`PATCH account/profile`, `Users::UpdateProfile`) above the password form, each with its own footer and one shared Leave prompt. The profile form is headed "Your account" and is two cards of one width, **Profile** (the name) and **Notes** with two switches (`users.notes_sound`, on by default, and `users.notes_desktop`, off by default): one form, one footer, one service call, one `user.updated` event (none, and no write, when the form is saved as rendered: `test/integration/admin/accounts_test.rb`, "Your account saved as rendered writes nothing and audits nothing"), and a refused name writes no switch either (the form comes back with what was sent, the rest of the page from what is stored). Neither Save may throw away what the other form holds. **Save** on the profile form keeps the screen: to Turbo it answers a stream that replaces the sidebar's `Admin::Shell::AccountIdentityComponent` and appends the toast "Settings saved", so typed password fields stay as they are (without Turbo it is a redirect). The notes settings are the signed-in person's own and nobody else's to change (`Users::Save` does not take them; a switch the request does not send is left as it is), they reach the scripts as values on `<body>` (`admin--notes--alert`, which chimes and notifies for a mention: `docs/reference/notes.md`, "Live delivery"), in the saving tab and the person's other tabs of this browser at once (the save's stream replaces `#notes-alert-settings`, and the tab passes the values on), and the lines under the desktop switch are about this *browser's* permission, not the setting (`admin--notes--permission`): shown only while that switch is on, as it stands in the page, saved or not; not asked yet is an accent-toned line with "Allow in this browser", which asks at once, outside the save; allowed shows nothing; blocked is a warn-toned line saying where to change it. **Change password** re-renders the screen, so it waits for the profile form: while the name or a Notes switch is unsaved its button is disabled with "Save or discard your changes first." (`save_bar_form_data(after: "profile-form")`). The current password is not counted by the footer (`data-save-bar-ignore`), or a password manager filling it in on load would make every visit end in "Leave without saving?"; a wrong current password is an error on that field ("That's not your current password."), and the subtitle's promise — you stay signed in here, other sessions end — is the services' own rule.

**A leaked password is refused** wherever a person sets one, with "This password is in a list of leaked passwords, so it isn't safe to use. Choose another one." on the password field (`activerecord.errors.models.user.attributes.password.leaked`), as the model's own rules are: the setup wizard's founding owner and a new user or a typed change in the Users editor (`Users::Save`), Your account and the reset (`Users::UpdatePassword`), and an invitation's acceptance (`Invitations::Accept`, which copies the refusal onto the invitation's field). The three services include `Users::LeakedPasswordRule`; the seeds and a direct write of the model are not checked, while the console's command (`Users::UpdatePassword`) is. **Where the check runs**: only when it is on (production by default, `LEAKED_PASSWORD_CHECK`), and only once the record is otherwise valid, so a blank, short or unconfirmed password is refused by the model first and never leaves the process; and before the service's transaction, so the lookup (up to 5 seconds) holds no row lock others wait on. The one exception is the wizard, whose `Users::Save` runs inside its `LOCK TABLE users` transaction: one person and one row, bounded by the lookup's timeouts. A refusal writes nothing, audits nothing and ends no session; a lookup that could not be made accepts the password (`docs/reference/hosting.md`, "Sign-in on the open internet", for what leaves the process) (`test/services/users/save_test.rb`: "a leaked password is refused on a new user and on a typed change, with the sentence on the password, and nothing is written or audited", "a password too short or unconfirmed is refused by the model first and is never looked up"; `test/services/users/update_password_test.rb`: "a leaked password is refused and the user's sessions all stay"; `test/services/invitations/accept_test.rb`: "a leaked password is refused, the invitation stays open, and the lookup runs before the invitation is locked"; `test/integration/setup_early_steps_test.rb`: "the wizard refuses a leaked password for the founding owner").

**Sessions.** An owner sees a Sessions zone (`Admin::UsersScreen::SessionsZoneComponent`, the shared action zone after the user form, beside the owner zone) on an existing user's editor, and no one else sees it. It offers "End all sessions…", which opens a confirm (not destructive: the person only signs in again) and DELETEs `users/:id/sessions` (`Admin::UsersController#sessions`, `Sessions::EndAll`, which asks the owner rule again on the request). The count in it is the user's LIVE sessions (`Session.live`, a named query the controller loads as `@open_sessions`, not the view's), so a row past its timeout is not "open"; with none the button is disabled with its reason, and on the owner's OWN account it is disabled with its reason too, and Your account's "Sign out everywhere else" is the way, since ending the session the owner acts in would sign them out under the request. The trigger is an `admin--saving--pending-lock` control, as the owner zone's is: an instant action answers by re-rendering the screen, which would throw an unsaved edit away. One `session.ended` (`ended_by_owner`, with the count) is audited per press, none when nothing was open; the rules and the endings are in `docs/reference/access-control-and-audit.md`, "Sessions: their limits and their endings".

**Your account's Sessions card** (`Admin::AccountScreen::SessionsCardComponent`, `Admin::AccountSessionsController`, open to every signed-in user, for their own sessions only) lists the person's live sessions: this one first ("This session", no End), then the others by when they were last seen, each as a device in words (`SessionDevice`), its address, how recently it was active and how the person signed in. A row's End ends that session at once with no confirm (`DELETE account/sessions/:id`, `Sessions::EndOthers` with `only:`) and answers with a Turbo Stream that takes the row away, draws the foot again and toasts; an id that ended nothing is answered with the same stream and words as one that had already ended, so it tells nothing about whose it was, and an End of this session's own id ends nothing. The foot (`Admin::AccountScreen::SessionsFootComponent`) says how many others there are and offers "Sign out everywhere else…" behind a confirm (`DELETE account/sessions`, answered as a redirect back to `#sessions`, since the whole card changes); with no other it says so and offers nothing. That redirect draws the whole screen again, so the trigger waits for both forms: while the name, a Notes switch or a new password is unsaved it is disabled with "Save or discard your changes first." (`admin--saving--pending-lock` on the foot, as the users editor's zones wait), and a row's End, whose stream keeps both forms, is never locked. The card's rows are the controller's (`AccountsController` loads `User#open_sessions` for every answer that draws the screen), never a query of the view's. The card stands outside both of the screen's forms and holds no field, so no save bar counts it and leaving the screen never asks; `admin--account--sessions` hands the focus on when a row goes.

## Invites

**Invites** (mail spec; the whole of it, the model, the token, the accept page and why an invitation is not a user, is `docs/reference/mail.md`, "Invites: an invitation is not a user"). "Invite person" stands beside "New user" for `users.manage`, and only while mail is ready (`MailSettings#ready?`); otherwise an owner sees "Invites need mail. Set up mail →" (to Settings' `#mail`). The dialog, `Admin::UsersScreen::InviteDialogComponent` ("Invite a person": Email, Name, the editor's group cards; "Send invite"), posts `invites` (`Admin::InvitesController#create` → `Invitations::Invite`); a refusal re-renders the Users index with the dialog open (the index is loaded by `Admin::UsersList`, shared by both controllers), each refusal in the error slot of the field it is about (the shared invalid edge on that field), a refusal about no field as the danger notice at the dialog's top (one line per message, never joined into one sentence), and, for "This address is already invited.", a Resend button in the address's slot, of a form of its own. An invitation is an `Invitation`, not a user: the list shows each open one among the users, in the order of the address, by its name or its address as text, with the `:other` avatar, the badge "Invited" and "Invited 14 Oct · expires 21 Oct" (or the badge "Invite expired"), its groups and no editor to open, and its row's ⋯ menu, in place of "Edit" and over the row's cover, has "Resend invite" (`POST invites/:id/resend`, `Invitations::Resend`, a new link and seven more days) and "Withdraw invite…" (`DELETE invites/:id`, `Invitations::Withdraw`, which deletes it). Create and resend share one limit, ten per person per three minutes. Accepting creates the user in the invitation's groups (`Invitations::Accept`; a refused password or name is copied by field onto the unsaved invitation's errors, so the invitation page draws each on its own field, Name or a password, with the refused edge, as the reset page does); until then the person is in no group's members, no picker and no count, and nothing on this screen's users side knows invitations exist.

## Rules a change can break silently

Moved word for word from `CLAUDE.md`, where "above" and "below" meant the list these rules stood in: a rule named that way may now be in another reference file. Each names the test that guards it; a rule or a part of one with no guard is also said in `CLAUDE.md`.

- A new database is built by loading `db/schema.rb`, never by running migrations (`db:prepare`, `db:setup`, `db:schema:load`, and since Rails 8 `db:migrate` on an empty database), so a row a migration inserts reaches no new site. A row every site needs (today the four built-in groups) is made by the block at the top of `db/seeds.rb`, above the line that ends the file outside development, through `Groups::EnsureBuiltIns`, which makes only a group that is missing by name and never adds a grant to one that exists (an owner's edit of a built-in group must survive the next deploy; `AccessControl::Seeds.ensure_built_in_groups!` does add grants and is for the migration alone). The setup wizard calls the same service before every step past the token, for a database built with `db:schema:load` alone, and its token step answers a missing Admin group with a message, never `find_by!`'s 404. A migration that inserts rows is named in `test/lib/built_in_data_test.rb` with what a schema-loaded database gets instead (`test/lib/built_in_data_test.rb`: "every migration that inserts rows is accounted for: built in, derived from rows that were there, or made when first asked", a source grep by method name that takes a `derived:` or `lazy:` reason at its word; "what the built-in migrations inserted, Groups::EnsureBuiltIns makes on a database no migration ran on"; `test/services/groups/ensure_built_ins_test.rb`: "a group that exists is left as it is: a grant an owner took away does not come back, and only the missing group is made"; `test/integration/setup_fresh_database_test.rb`; `test/models/seeds_test.rb`: "outside development the seed makes the built-in groups of a schema-loaded database, no account and no content, and nothing the second time"). `db:prepare` seeds only a database it has just created: a site set up before this runs `bin/rails db:seed` once.
