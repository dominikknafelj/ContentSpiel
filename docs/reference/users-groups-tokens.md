# Users, groups and API tokens in CS Studio

> Describes: `app/controllers/admin/users_controller.rb`, `app/controllers/admin/groups_controller.rb`, `app/controllers/admin/api_tokens_controller.rb`, `app/components/admin/users_screen/`, `app/components/admin/groups_screen/`, `app/components/admin/tokens_screen/`, `app/services/users/`, `app/services/groups/`, `app/services/api_tokens/`.

## AI assistant (API tokens)

**AI assistant** (`Admin::ApiTokensController`, `Admin::TokensScreen::CreateStepComponent` / `ConnectStepComponent` / `TableComponent`) is a numbered flow: 1 · Create a token (a required name, a group from those the viewer may assign with its description under the select — `admin--tokens--group-hint` — and Create token), 2 · Add it to your assistant (the MCP URL and the client configuration, each with Copy), then the tokens table: Name, Acts as, Group, Created, Last used, Status, "Revoke…" behind a dialog; revoked tokens stay listed. `api_tokens.name` is required, stripped, at most `ApiToken::MAX_NAME_LENGTH` (60) characters and unique per user among that user's *active* tokens, case-insensitively — a validation backed by the partial unique index `index_api_tokens_on_user_and_lower_name_active`. `ApiTokens::Issue.call(user, group:, name:)` treats a nil name as "pick the next free Token N" and any String, a blank one included, as the name to validate; CS Studio and the setup wizard always pass a String, so a missing name is "Name can't be blank". The reveal is the POST's own answer — the same screen with the warn box in step 1 and the token filled into the configuration, `no-store`, never a redirect and never in Turbo's cache — and no part of a token is rendered, logged or audited afterwards. The token's name is what the audit log shows: `Audit.record` writes it to `audit_events.actor_label` once, at insert (it is not a coalescing column), so "via <name>" survives the token row.

## Groups

**Groups.** The list (`Admin::GroupsScreen::ListComponent`) is card rows that are links, with member and token counts from two grouped queries. The editor (`admin/groups/_form`, `Admin::GroupsScreen::PermissionMatrixComponent` composing the rest) is rows, not a grid: eleven `PermissionRowComponent`s (Posts ×5, Pages ×6), each a tick, the short label with the key in mono, scope chips, and "Edit scope" opening a `ScopeEditorComponent` in place — content types as a multi-select (none ticked = all) and an "Own only" toggle for posts, a tri-state branch tree for pages (`BranchTree`, `admin--groups--branch-picker`: chosen, a greyed tick for a page a chosen ancestor already includes, a dash for an ancestor of a chosen page) — then `ToggleListComponent` cards for the unscoped keys, one more per plugin area. Open and close are only `hidden`; everything stays in the form, and the scope of an unticked permission is ignored. **A form saved as rendered changes nothing**, which is why some things are carried as hidden inputs: a stored branch root the viewer can't open ("A page you can't open (kept)"), a chosen context-only ancestor, a redundant stored root (a root plus its own descendant; its hidden input is enabled only while the box is disabled as implied), and a *removed content type*. The last is drawn as a warn chip "! <name> · this type no longer exists" with **Remove**, on a tracked hidden input, so pressing Remove is a counted change; with no live type left the chips read "All content types" followed by the warn chips, which is what Save stores.

`Groups::Save` reads such a carried name by one narrow rule (the comment above `#live` is the authority; keep this in step with it): a posted grant is read as a stored grant, unchanged, only when the stored grant is a live `LiveGrants` entry with removed types of its own (never a wholly dead grant), the permission is the same, and the posted scope *minus that entry's own removed types* is exactly the entry's live scope (the same live types, the same `own`, the same pages); a group holds one grant per permission and a request listing one twice is refused up front, so a posted grant meets at most one stored entry. Everything else is compared raw, so `can_grant?` sees the removed name and only an actor whose own grant covers it passes. The consequence, on purpose: from a non-owner who couldn't hand out the removed name the service accepts such a grant in one shape only, posted back exactly as it is (a rename of the group) — giving the name up is a removal, which `#removal_refusal` reads from the grants as stored against the grants as posted and refuses for anyone who couldn't manage the group — and the editor shows that viewer the group view-only (below) until an owner, or someone whose own grant covers the name, presses Remove. A removed name is dormant, not meaningless — re-registering a type of that name revives it — so it may stay or shrink, never appear, move or widen unchecked. **View only:** a stored group the viewer can't manage as it stands (`AccessControl.can_manage_group?` false — a grant they couldn't hand out, which includes one that carries a removed content type they couldn't grant and a wholly dead grant that names only such types) gets the notice "This group has permissions you can't hand out, so you can only view it.", the whole form in `<fieldset disabled class="admin-view-only">`, no footer and no delete zone; scopes still open through a link ("View scope"), which a disabled fieldset doesn't disable. The locked tick ("You can't grant this", a greyed disabled box whose scope is carried) is a defensive rendering only: a stored grant the viewer couldn't hand out makes the whole group view-only, and the lock is judged on the same scope `can_manage_group?` reads (a grant still exactly as stored, a removed type's name included), so no stored state reaches it. Members are a chip input (`MembersComponent`, tracked) over `GET /<admin>/users/suggest` (`Admin::UserSuggestionsController`: `groups.manage`, at least two characters, at most eight rows, name or email, prefix matches first, the user ids in `exclude` (the chips already there) left out before the limit, owners never offered — "Owners aren't listed: they already have every permission." — while an owner already stored as a member stays a chip until removed). The delete zone (`DeleteZoneComponent`, after the form, custom groups only) names the member count and the active tokens that go with the group ("<name> — <user>", ten then "and N more") in its confirm dialog; a built-in group gets a note instead.

## Users

**Users.** `users.name` is optional; `User#display_name` is the one reader (name, else email). The list (`Admin::UsersScreen::ListComponent`) is card rows that are links: an initial, name or email, "(you)", an OWNER tag, group chips or "No groups", and the last sign-in — `Users::LastSignIn.for(users)` (`app/queries/users/last_sign_in.rb`), one grouped `MAX(occurred_at)` over the `session.created` audit events for the whole list, no column on the user; no event reads "Never". The list is not paginated and no index covers `(user_id, action)`, so that one query's cost grows with the audit log, not only with the users. The editor (max 880px): name and email, the password behind "Set a new password…" (a `<details>`; blank keeps the password, closing it clears what was typed, and a typed password is never rendered back), the groups as cards (`GroupCardsComponent`: the card is the label of its checkbox; a group the viewer can't assign is sunken with "You can't grant this group." and, when ticked, carried by a hidden input), "Save user". Owner rights and deletion are zones after the form, both `admin--saving--pending-lock` controls: the **owner zone** (`OwnerZoneComponent`, shown to owners on an existing user) opens "Make owner…" / "Remove owner rights…" dialogs that post `PATCH users/:id/owner` (`owner=1|0`, anything else a 400), which calls `Users::Save` and nothing else — the last owner's button is disabled with the reason; an owner can't be created in one step, and the ordinary editor form cannot change the flag at all: `user_params` does not permit `owner`, so a forged `user[owner]` is dropped as unpermitted and the rest of the save is an ordinary one (`Users::Save` reads an absent, nil or empty `owner` as no change). The **read-only states** come from one predicate shared with the services, `Users::Manageability.for(actor, user)` → `:editable`, `:owner_protected` ("Only owners can change other owners.") or `:outranked` ("This user has permissions you don't have, so you can't change them."): a notice, a disabled fieldset, no footer and no zones. `Users::OwnerProtection` delegates its predicates to the same class, so the screen and the services can't drift; the view decides nothing — a forged write against a read-only user is still the services' 403 and one `access.denied`. A signed-in user edits their own name on the **Your account** screen (`Admin::AccountsController`, at `<admin>/account`; the page's first address, `account/password`, answers a GET with a 301 to it, the Password card is `#password`, and the two forms post where they always did, `account/password` and `account/profile`, so no non-GET is redirected. After the password form is saved or refused the page is at `…/account#password` with the Password card in view and the focus on the message (handoff decisions 42 and 43). The message is in the card, at its top under the sentence about sessions: a refusal is the shared danger alert (`Admin::Ui::ErrorSummaryComponent`, each field keeping its own line; too many tries are said there too), a save the success alert, and no toast is raised. The page's own error summary, above the cards, is the Profile and Notes form's only. the fragment of the redirect never reaches a Turbo visit, so the page drawn as that answer carries `admin--account--password-answer` on the card, which writes the fragment through Turbo's history, scrolls to the card (at once with reduced motion) and focuses the card's alert. The card is the one element with the id `password`; the new-password field is `new_password`; the sidebar's entry and the name block above it both lead there; three cards, Profile, Notes and Password, the last holding the password form with the promise about sessions under its title): the profile form (`PATCH account/profile`, `Users::UpdateProfile`) above the password form, each with its own footer and one shared Leave prompt. The profile form is headed "Your account" and is two cards of one width, **Profile** (the name) and **Notes** with two switches (`users.notes_sound`, on by default, and `users.notes_desktop`, off by default): one form, one footer, one service call, one `user.updated` event, and a refused name writes no switch either (the form comes back with what was sent, the rest of the page from what is stored). Neither Save may throw away what the other form holds. **Save** on the profile form keeps the screen: to Turbo it answers a stream that replaces the sidebar's `Admin::Shell::AccountIdentityComponent` and appends the toast "Settings saved", so typed password fields stay as they are (without Turbo it is a redirect). The notes settings are the signed-in person's own and nobody else's to change (`Users::Save` does not take them; a switch the request does not send is left as it is), they reach the scripts as values on `<body>` (`admin--notes--alert`, which chimes and notifies for a mention: `docs/reference/notes.md`, "Live delivery"), in the saving tab and the person's other tabs of this browser at once (the save's stream replaces `#notes-alert-settings`, and the tab passes the values on), and the lines under the desktop switch are about this *browser's* permission, not the setting (`admin--notes--permission`): shown only while that switch is on, as it stands in the page, saved or not; not asked yet is an accent-toned line with "Allow in this browser", which asks at once, outside the save; allowed shows nothing; blocked is a warn-toned line saying where to change it. **Change password** re-renders the screen, so it waits for the profile form: while the name or a Notes switch is unsaved its button is disabled with "Save or cancel your changes first." (`save_bar_form_data(after: "profile-form")`). The current password is not counted by the footer (`data-save-bar-ignore`), or a password manager filling it in on load would make every visit end in "Leave without saving?"; a wrong current password is an error on that field ("That's not your current password."), and the subtitle's promise — you stay signed in here, other sessions end — is the services' own rule.
