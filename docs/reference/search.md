## What is found

**Only what a visitor sees now.** A result is a page or a post that, at the moment of the request, is kept (not in the trash) and published (`published_at` not after now); is visible (every page above it published: `PublicSite::Resolver.visible_among`, for a post the chain of the page that gives it its address); has a current address in the language searched (a `public_paths` row with `current: true`); and is matched by the words of its **copy in force** (`Publishing.current`, the newest copy whose `live_at` is not after now). Never the rows: words typed into a live record and not published are in no document, and a live record with no copy (written around the services, a console) is not searchable although the site serves it.

**In the visitor's language, with the page's fallback.** Each copy gives one document per **enabled** language, each field read through that language's fallback chain (`Locales.fallback_chain`), so a Spanish visitor finds a page by the English title the Spanish page shows. A search in one language never finds another's document. The chain is a runtime setting, so a change of the languages rebuilds the index ("The automatic build", below).

## The document

`SiteSearch::Documents.for(version, now:)` (`app/models/site_search/documents.rb`) is the one place a published copy becomes words: it rebuilds the copy read-only (`Publishing::Snapshot.rebuild`), reads it with the public readers and answers one `SiteSearch::Document` per enabled language. Every backend is handed the same documents, plain values that need nothing of ContentSpiel's models (`app/values/site_search/document.rb`):

`key` (`"Page:12:345:de"`: record type, record id, copy id, language), `record_type`, `record_id`, `copy_id`, `language`, `url` (the record's address in that language when the document was made: informational, for an engine's own tools; what is drawn is read again from `public_paths`), `live_at` (the copy's), `shown_from` (the later of `live_at` and the record's `published_at`), `shown_until` (the `live_at` of the record's pending copy, or nil), `fields` (`SiteSearch::Field`: `name`, `weight` `:a` to `:d`, `text`) and `text` (the body field's text again, the snippet is cut from it).

| Weight | Field | From |
|---|---|---|
| A | `title` | the record's title |
| A | `tags` | a post's tag names, as its copy shows them |
| B | `summary` | a page's subtitle, meta title and meta description and its slug words; a post's excerpt and its slug words |
| C | `body` | a post's rich-text body and its type's translated `:string` and `:text` fields, then every block's searchable text in the copy's reading order (`t.search_text`) |
| D | `code` | the Code blocks' code |

**The slug words** are the record's own slug in the document's language, as stored and with no fallback, with hyphens as spaces: the parts of `zero-downtime-deploys`, which Postgres's parser would read as one hyphenated compound. The homepage's slug is empty and gives none. Never the address's last segment: an address also moves with writes that are no slug's (a list published after its posts gives them one), which re-index nothing. A slug is immediate and in no copy (`docs/reference/publishing.md`), so every write of one re-indexes its record (`record_changed(record, slug: true)`, below); a page moved, or under a parent whose slug changed, keeps its words. A page whose title changes stays findable by its old slug words for as long as its slug keeps them.

Every text is plain: no markup, whitespace collapsed, control characters and the two characters the snippet marks with (U+E000, U+E001) taken out. A Code block's code keeps its angle brackets and entities as typed (`<div class="note">` is a listing's words, not markup). Every field is cut at `SiteSearch::MAX_TEXT` (200,000 characters, at a word boundary): Postgres refuses a `tsvector` over 1 MB and counts word positions only to 16,383, and a page of tables or Code blocks would pass either inside the publish that indexes it. Words past the cut are not found.

`SiteSearch::Documents::REVISION` (2) is part of the index's fingerprint: bumped by hand when what a document holds for the same copy changes (a field, a reader, a block type's `search_text`), it makes every backend's index stale, and the automatic build rewrites it. Without the bump the index keeps the old words until each record's next copy.

### A block type's text: `t.search_text`

```ruby
t.search_text ->(block, locale:) { [ ::Locales.read(block, :caption, locale: locale) ] }                    # body text, weight C
t.search_text :code, ->(block, locale:) { [ block.settings_object(locale: locale, fallback: true)&.code ] }  # weight D: the Code block's alone
```

The callable takes the block **as the published copy holds it** (a rebuilt, read-only `ContentBlock`) and `locale:`, and answers an Array of plain Strings (blanks dropped): the text the type's public component draws in that language, read with the same fallback-aware readers. It is refused at registration when it does not take the block and `locale:`, and a kind other than `:code` or none is refused. A type that declares none gives nothing. Read by `SiteSearch::Documents` alone. A callable that raises gives no text for that block and is reported (`SiteSearch::BlockTextFailed`, the type's name and the error's class, at most once a minute), and the publish stands: a gem's type never blocks a publish.

| Type | Its text |
|---|---|
| `rich_text` | the body's plain paragraphs (`SiteSearch.paragraphs`: without the placeholders that stand for an image, a video or a rule) |
| `image` | the caption and the block's own alt override; never the library image's alt, which is the asset's, read live and in no copy |
| `code` | file name and caption at C, the code at D, so prose about a thing outranks a listing that mentions it |
| `diagram` | description and caption, never the Mermaid source (syntax, which would match "graph" or "end") |
| `table` | every cell, row by row, and the caption |
| `note` | the title, or the kind's word when untitled, as drawn; and the body |
| `card` | title, text and the image's alt override |
| `section`, `post_list`, `form`, `search` | nothing: a container holds no text of its own (its blocks are read each); the posts are documents of their own; field labels are an interface; the block is a field |

An outside type declares `t.search_text` through the same hook (`ContentSpiel::Plugins.block_types`) with the same signature and refusals, and may not declare `:code` text (refused at registration: D is the Code block's weight). A gem's type that declares nothing is silently unsearchable. `docs/reference/content-blocks-and-types.md`, "Adding a block type", step 2, has the step for a new built-in.

## The backend seam

### The contract

A backend is any object answering `SiteSearch::Backend::METHODS`; the contract is written in `SiteSearch::Backend`'s comment (`app/models/site_search/backend.rb`):

**Indexing**, asked by `SiteSearch::Indexing` alone:

- `index(documents)`: store these documents, each replacing any stored one of the same `key`.
- `remove(record_type:, record_id:, copy_ids: nil, languages: nil)`: forget the record's documents of these copies (nil: of every copy) in these languages (nil: in every language). A copy withdrawn, a record purged, a language switched off.
- `prune_record(record_type:, record_id:, except_copy_ids:)`: forget the record's documents of every copy not in `except_copy_ids` (an empty list: all of them). Sent AFTER `index`, so the documents of a copy withdrawn or superseded go without the record ever standing with none, and an `index` that fails leaves the old ones in place.
- `clear`: forget everything (a backend's own tests, a reset by hand; the build replaces documents in place and never clears).

**Querying**, asked by `SiteSearch.search` alone:

- `search(query, deadline:)` answers `SiteSearch::Results` (`hits`, `total`) for a `SiteSearch::Query` (`text`, `language`, `page`, `per_page`, `now`): the documents of `query.language` only, in view at `query.now` (`shown_from <= now`, and `shown_until` nil or after it), matching every word of `query.text` (never a document by one word of two, since a correction is checked by such a search; contract: "a document is found only when it holds every word of the query") in any field, a title's match ranking above a body's; `per_page` hits from `query.offset`, and `total` counting every match. A `SiteSearch::Hit` is `record_type`, `record_id`, `copy_id`, `language`, `snippet`, `rank` and `close` (default false); its `SiteSearch::Snippet` is plain text with `[start, length]` `marks` on the query's words, **never markup**: an engine's own highlighter writes HTML the site would have to trust, so the ranges are escaped and marked by ContentSpiel (`Blocks::SearchComponent::Result#snippet`). The page draws at most `SiteSearch::SNIPPET_LENGTH` (500) characters of a snippet, cut at a word boundary, and an answer of another shape (a total that is no Integer, a mark that is no pair of Integers) is a failure, scrubbed and reported like a raise.
- **Close matches and a correction**, both optional, every new member with a default (`Query#close_matches` true, `Hit#close` false, `Results#correction` and `Results#close_outcome` nil), so a 0.7.0 backend that builds `Hit.new` and `Results.new` without them passes unchanged. `query.close_matches` is true for a visitor's search, on which a backend **may** add close matches by its own rule and when it judges them due (a word one typo away, Solr's `word~1` on escaped words, a spellcheck), and false for ContentSpiel's verifying search, which it answers with exact and stemmed matches only. A close hit is `close: true` and matches each query word or a close variant of it; **no close hit stands before an exact hit**, and `total` counts both. `Results#correction` is the query with its words corrected, as plain words, at most `Query::MAX_LENGTH` characters, offered only on an answer with no exact hit, or nil. ContentSpiel verifies it whatever the backend ("The request", below), so a correction is never trusted for visibility. `Results#close_outcome` says what a close pass did when it found no close hit: nil (none found, or no close pass), `"timeout"` (out of time, the exact answer standing) or `"skipped"` (it ran none: a language or a query it does not judge), `SiteSearch::BACKEND_CLOSE_OUTCOMES`; anything else is an answer of the wrong shape. **A backend never writes on ContentSpiel's span**: `search.close` is read from the answer ("Telemetry", below).
- **Suggestions while typing**, optional (`SiteSearch::Backend::OPTIONAL_METHODS`, `%i[suggest]`; `METHODS` stays the six, so a 0.7.0 backend passes `Backends.built` unchanged): `suggest(suggest_query, deadline:)` answers `SiteSearch::Suggestions` (`items`) for a `SiteSearch::SuggestQuery` (`text`, `language`, `now`, `limit`): up to `limit` `SiteSearch::Suggestion`s (`record_type`, `record_id`, `copy_id`, `rank`), best first, of the documents of `language` in view at `now` whose title has a word that begins with each word of `text`. The rules of `search` hold: the text is plain words the engine escapes (a prefix query on escaped words or an "as you type" field, never a raw query string with `*` appended), text left with no words answers no items, answered or raised by the deadline, a failure scrubbed, the prefix never logged; an answer of another shape (not `Suggestions`, items that are no Array of `Suggestion`s with Integer ids) is a failure. An item carries no text: it is re-checked and drawn from the copy in force, as a hit is. A backend without `suggest` gives no title suggestions; the tags are ContentSpiel's own and still come, and System status says so (below).
- **The text is a visitor's, as typed.** `query.text` is normalised (`SiteSearch::Query.normalise`: whitespace collapsed, invalid bytes, control characters and the two marker characters taken out) and at most `SiteSearch::Query::MAX_LENGTH` (200) characters, and it is never a query in an engine's own language: ContentSpiel hands over words, nothing else. **An outside engine escapes its own query syntax**: a client that takes a query string (Solr's standard or eDisMax parser, Lucene's `QueryParser`, Elasticsearch's `query_string`) escapes every character its parser reads (`+ - && || ! ( ) { } [ ] ^ " ~ * ? : \ /`, and Solr's local parameters `{!…}`), or sends the words to a parser that reads plain text (`simple_query_string` with its operators off, a `match` query, Meilisearch's `q`). A field name, an operator, a boost, a wildcard or a local parameter in the text is a word to it, never an instruction: `*:*` is no query for every document. **Text left with no words after the engine's own analysis is answered empty** (no hits, a total of 0), never sent as an empty or placeholder query, which some engines answer with every document (Meilisearch's placeholder search). Both rules are in `SiteSearch::Backend`'s comment, and the contract test holds them as far as its queries reach ("a query full of an engine's syntax is words, never an instruction": an engine may raise on a query, which the caller scrubs and reports, but what it answers holds no document that lacks the plain words, and syntax alone finds nothing).

**Health**:

- `health(deadline:)` answers `SiteSearch::Health` (`status`, `detail`). `status` is `:ok`, `:warn` or `:failed` (anything else raises when the value is made). **`detail` is one plain sentence for a person, or nil, and holds no address, no credential and no error's message**: System status shows it to whoever may read System status, as it is handed, cut to its first line, whitespace collapsed, at most 200 characters (`Setup::SystemCheck::DETAIL_LENGTH`). It is shown after "Solr answers: " for an `:ok` and after "Solr reports a problem: " for a `:warn` or a `:failed` (both a warning: nothing in Settings can mend an engine); with no detail the row says "Solr answers." or "Solr reports a problem but says no more. Check the engine itself." A health that raises or does not answer by its deadline is the row's "did not answer in 3 seconds", and the exception is never read.

**The deadline** is a `Process.clock_gettime(Process::CLOCK_MONOTONIC)` Float: by then the backend has answered or raised. An HTTP client's open and read timeouts are set from it; the built-in sets a statement timeout from it. A failure is raised as any `StandardError`; ContentSpiel reports its class alone, never its message, which for an engine may hold the address it asked and so the query. **A backend never logs the query text.**

**One instance per process, shared by every thread.** `Backends.current` builds the backend once and every thread of the process asks that one object, at the same time: Puma's request threads, the job threads (Solid Queue's workers) and System status's health thread. **A backend is thread-safe**: a client it keeps (an HTTP connection pool, a cached schema) is one several threads may use, or one per thread. No test of this repository can hold it; it is the backend's promise, like the rules above.

### The registry, the hook and `SEARCH_BACKEND`

`SiteSearch::Backends` holds the backends by name: `"postgres"` the built-in's, `"owner/name"` a gem's. A gem registers through the sixth plugin hook:

```ruby
ContentSpiel::Plugins.search_backends do |backends|
  backends.register "acme/solr", label: "Solr", backend: -> { Acme::SolrBackend.new(url: ENV.fetch("ACME_SOLR_URL")) }
end
```

The `Registrar` rules apply as for every hook: `owner/name`, an owner named like a top-level constant of the CMS refused (`site_search` among them), one owner per call, an owner one hook's. `label` is the backend's name as System status writes it. `backend:` is a callable (anything else is refused) that builds the backend, called once per process when the backend is first asked for (`Backends.current`), so a gem reads its engine's variables only when the site has chosen it. `inline: true` (written in the caller's transaction) is the built-in's alone: an outside engine's call inside a write would hold the write open on the network. The hook is kept and replayed on every `to_prepare` by `config/initializers/site_search.rb`, after the built-in (`REPLAYED_SEARCH_BACKENDS` for the error's words); a hook that raises stops the boot naming its place, and on a development reload is logged instead (`test/lib/content_spiel/plugins_test.rb`: "a gem registers a search backend through the hook, owner rules applied", "a raising search backends hook names its place"; `test/models/site_search/backends_test.rb`: "postgres is the default and SEARCH_BACKEND chooses", "only the built-in may be inline", "a name taken and a backend that is not a callable are refused", "the backend is built once, after the replay").

**The site chooses by `SEARCH_BACKEND`**, unset or blank meaning `postgres`, never by Settings: a backend is infrastructure, like the database, with its own address and credentials that a gem reads from variables of its own, and a switch an owner could press would empty the site's search until its index was built. A name no backend registered stops the boot naming the registered ones (`Backends.check!`; "a name nobody registered stops the boot naming the registered ones"). The boot prints `[ContentSpiel] Search: Postgres (postgres)` at info ("the boot names the chosen backend"). A new `SEARCH_BACKEND` has no index state row, so the boot's check builds its index; the old backend's row and documents are left, so switching back is a staleness check, not a full build.

### The contract test, and how a gem runs it

`test/support/site_search_backend_contract.rb` (`SiteSearchBackendContract`) is a module of tests every backend's test includes, with a `backend` method and a `contract_document(title:, body:, code:, language:, shown_from:, shown_until:)` that answers a document of a record of its own. A backend that keeps only what it is handed includes `SiteSearchBackendContract::BareDocuments`, which builds the value alone; the built-in defines its own, publishing a real page so the document is of a real copy. It runs against `SiteSearch::Postgres` (`test/models/site_search/postgres_test.rb`) and `SiteSearch::Fake` (`test/models/site_search/fake_test.rb`; `test/support/site_search_fake.rb`, an in-memory backend that obeys the contract and can be told to raise or to sleep, and `installed { … }` makes it the site's backend as a gem's would be). It holds: a document is found by a word of each field; the title outranks the body; `index` with the same key replaces; `remove` by copy, by record and by language; `prune_record` keeps the listed copies and with none forgets the record; `clear`; the time bounds; one language's query never finds another's document; `page` and `per_page` with the total; a snippet's marks fall inside its text on the query's words; a query full of an engine's syntax (`title:albatross AND (glacier OR walrus)^2 ~ * ? "[`, `albatross" OR "1"="1`, Solr's `{!lucene}`, an SQL comment, a long run of `OR`) finds no document that lacks its plain words (or raises, which the caller scrubs), and syntax alone (`*:*`, `*`, `id:*`, `""`, `()`) finds nothing; `search` answers or raises by its deadline; `health` answers a `Health` within its deadline; a close hit never stands before an exact hit, and `close_matches: false` answers no close hit; a correction is plain text no longer than `MAX_LENGTH`, or nil; and, gated by `respond_to?(:suggest)` so a backend without it skips them, suggest finds a title by the start of its words in its language and view only, a prefix full of an engine's syntax is words (`*:*`, `a:* & !b`, `{!lucene}`, `title:al*`, `"`, `\`, an SQL comment; with "Wren" indexed, which holds none of their words, so a prefix read as an instruction shows), syntax alone suggests nothing, and suggest answers or raises by its deadline. The fake finds a close match by one edit (a letter changed, added or dropped, or two neighbours swapped) over the words of its documents in view when nothing matches exactly, and corrects each word no such document holds outside its code (as the built-in's vocabulary leaves code out) by its first close word, so ContentSpiel's own handling is tested against an outside-style backend; `answer_with(results)` and `answer_for(text, results)` make it answer as a test tells it, and `asked` lists the queries it was asked. Its `suggest` matches title words by their start; `SiteSearch::Fake.new(suggests: false)` has no `suggest` at all (`respond_to?(:suggest)` false), as a 0.7.0 gem, and `suggested` lists the suggest queries.

**A gem's test reaches it by path**, from a checkout of the ContentSpiel it is tested against (`CONTENTSPIEL_ROOT`). The file's path under the CMS's root, `test/support/site_search_backend_contract.rb`, is the promise; it needs nothing of this suite's helpers, only the application booted in the test environment and Active Support's test case. `config/boot.rb` sets up the bundle `BUNDLE_GEMFILE` names, the CMS's own `Gemfile` unless it is set, so a gem with its own dependencies brings a test Gemfile that holds the CMS's gems and its own, and points `BUNDLE_GEMFILE` at it:

```ruby
# Gemfile, in the gem's root
eval_gemfile File.join(ENV.fetch("CONTENTSPIEL_ROOT"), "Gemfile")
gemspec
```

```ruby
# the gem's contract test, run with BUNDLE_GEMFILE=<the gem's Gemfile> SEARCH_BACKEND=acme/solr
ENV["RAILS_ENV"] = "test"
require File.join(ENV.fetch("CONTENTSPIEL_ROOT"), "config/environment")
require "active_support/test_case"
require Rails.root.join("test/support/site_search_backend_contract").to_s

class Acme::SolrBackendTest < ActiveSupport::TestCase
  include SiteSearchBackendContract
  include SiteSearchBackendContract::BareDocuments

  def backend = SiteSearch::Backends.current
end
```

The boot's `Bundler.require` loads the gem, whose file calls `ContentSpiel::Plugins.search_backends`, before the registries are filled, as it would in a site; `SEARCH_BACKEND` makes its backend the one `Backends.current` builds. `test/lib/site_search_backend_contract_test.rb` runs exactly this shape in a folder outside `Rails.root`: a throwaway gem `acme_search` (a gemspec, a file that defines `Acme::MemoryBackend` and registers `acme/memory` through the hook), its Gemfile locked by `bundle install --local` from a copy of the CMS's lockfile, and its contract test in a process of its own ("a gem with its own Gemfile and gemspec requires the contract by path and passes it with its hook's backend"). **What it proves**: the Gemfile shape resolves and boots, a gem outside the CMS's folder is loaded by the boot and chosen by `SEARCH_BACKEND`, and the contract needs nothing of this suite. **What it does not**: the throwaway backend hands every call to `SiteSearch::Fake`, so the contract's verdict on matching is the fake's; and its gemspec declares no dependency of its own, since resolving a gem the CMS's bundle does not hold needs the network, which the suite does not use. **The seam is ready, but installing a gem into a site is not built yet**: a site's image is built FROM the CMS's, whose bundle is frozen, so a site cannot add a search engine's gem until that is (`docs/roadmap.md`, "Content model and extension", the row "Block types from outside, step 2" ("How a site adds a gem to its image")).

It stays in `test/support/` and not in `lib/`: `lib/` holds only what the application needs before autoloading or keeps for the life of the process (CLAUDE.md, "Where a class goes"), is autoloaded and eager-loaded in production, and would carry test code into every running site; `test/` ships in the image and in every checkout already. So moving or renaming the file, making it lean on a helper of this suite, or adding a contract test that a backend obeying `SiteSearch::Backend` cannot pass is a breaking change for every gem, named under `### Breaking` in `CHANGELOG.md`.

## Indexing

`SiteSearch::Indexing` (`app/models/site_search/indexing.rb`) is the one entry point of the indexing side and the one caller of a backend's `index`, `remove` and `prune_record` but for the build (`Rebuild`) and the sync job, which it enqueues. One method per event:

| Event | Called from | Asks |
|---|---|---|
| a copy is taken | `Publishing::Version.take!`, last in its transaction | `copy_taken(version)` |
| a pending copy is withdrawn | `Version.withdraw_pending!`, and the pending copy `take!` replaces | `copies_withdrawn(record, copy_ids:)` |
| a copy's content is rewritten | `Version.repoint_tag!` (a merged tag's name in a post's copy) | `copies_rewritten(copy_ids)` |
| a record's time or visibility moves | `Pages::Save` and `Posts::Save` when `published_at` changes with no copy taken, `Pages::Move`, `Trash::Move`, `Trash::Restore` | `record_changed(record)` |
| a record's slug changes | `Pages::Save` and `Posts::Save` when `slug` changes with no copy taken, `Trash::Restore` when it frees a slug to a suffix | `record_changed(record, slug: true)` |
| a record is purged | `Trash::Purge` (and so `Trash::Empty`) | `record_purged(type, id)` |
| the languages change | `Locales::Enable`, `Disable`, `Configure`, `MakeDefault`, when the enabled set or a fallback chain moved | `languages_changed` |

**The built-in is written in the caller's transaction**, so its entries stand or fall with the copy (a rolled-back publish leaves no entry). It needs only the copies: its query reads each record's state, address and clock as it searches, and the foreign key's cascade takes a withdrawn or purged copy's entries with the copy. So it is asked something for a copy taken (indexed; a copy in force at once also deletes the record's older entries, since those copies will never be current again; a pending copy's entries stand beside the current one's) and for a copy rewritten, and for a slug changed (the record's own documents rebuilt from its copy in force and its pending copy, after the address was refreshed), and nothing for the other events.

**An outside backend is never called inside a write**: every event becomes `SiteSearch::SyncJob.perform_later(record_type, record_id)` (for a page's `record_changed`, one for it and one for each page under it), enqueued after the commit of the outermost transaction (`ActiveRecord.after_all_transactions_commit`), so a rolled-back write sends nothing; the trial copy of `PublicSite::Paths.foresee`, taken in a savepoint that is always rolled back, enqueues nothing, since the copy must still stand after the commit. An enqueue that raises is reported, never raised: the write has committed. `SyncJob` is idempotent: it reads the record as it is, sends the documents of its copy in force and its pending copy (`Documents.for_record`; none for a record purged, trashed or neither published nor scheduled), then prunes every other copy's (`prune_record`). **One record is synced in one place**, `SyncJob.sync`, which the job and the build both run, and the copies the prune keeps are read again right before it (the row and its copies, past the query cache, by a fresh clock), never taken from the documents just sent: two syncs of one record that overlap (job A built the old copy's documents, job B ran in full for a new copy, then A sent) end with the new copy's documents whichever finishes last. A backend's failure is retried with the job's backoff (five attempts) and reported after the last; a database error while the record is read (a deadlock, a lost connection) is retried the same way. The site searches the engine's last state, which the re-check keeps honest.

**A scheduled change with an outside engine** needs no job at its time: each document carries its bounds and the engine filters by `shown_from <= now < shown_until`. When a change is scheduled, the pending copy is sent with `shown_from` its `live_at` and the copy in force again with `shown_until` the same moment; withdrawing it re-sends the copy in force with no `shown_until`; a record rescheduled with no copy taken is `record_changed`, which re-sends its documents from the new time.

**Every hit is checked again before it is drawn** (`SiteSearch::Shown.for(results, locale:, now:)`, `app/queries/site_search/shown.rb`), since an outside index can be stale: a hit is kept only when its record is kept, published and visible at the search's `now` (`PublicSite::Resolver.visible_among(records, now:)`), has a current address in the language, and the hit's copy is the record's copy in force. The title, the address, the place and the date are read from that copy and `public_paths`, never from the engine. The check is a constant number of statements for ten hits. A hit it drops is not replaced: the page shows fewer than ten and the total stays the engine's. With the built-in nothing is dropped, since its query asks the same.

## The built-in backend: `SiteSearch::Postgres`

**`search_entries`** (`SiteSearch::Entry`): one row per published copy and language, a fourth derived table beside `public_paths`, `media_usages` and `translation_states`, written only by `SiteSearch::Postgres` in the caller's transaction, never by hand. Columns: `published_version_id` (foreign key `ON DELETE CASCADE`: a withdrawn pending copy and a purged record's copies take their entries with them in the same statement; a cascade, not NO ACTION, on purpose, since nothing ever has to refuse a copy's delete for its entries, unlike a library image's), `record_type`, `record_id`, `locale`, `config` (the text search configuration it was built with), `live_at` (the copy's), `document` (a weighted `tsvector`, GIN-indexed), `text` (the snippet's source), `title` (the title field's plain text, which the suggestions read by its `simple` words through the expression index `index_search_entries_on_title_words`) and `created_at`; unique on (copy, locale), and indexed on (record type, record id, locale, `live_at`). Its writes carry `# version: none` (the index is no part of a page: results are never cached).

**The languages** (`SiteSearch::Postgres::CONFIGS`): every code of `config/supported_locales.rb` to a configuration Postgres 17 and 18 ship, the language's own stemmer for ar, ca, da, de, el, en, es, fi, fr, hi, hu, id, it, lt, nb, nl, pt, ro, ru, sr, sv and tr, `simple` for the rest. Every field of an entry is built with its locale's configuration, the fallback text included (a Spanish entry holding an English title stems it as Spanish), because the query is parsed with the visitor's and the two must agree. **Japanese, Chinese, Thai and Korean** (`LIMITED`, `%w[ja ko th zh]`) are `simple`, which splits on spaces: Japanese, Chinese and Thai write none between words, so the exact pass finds a page only by a whole run of text, and Korean, which spaces its phrases, finds whole phrases; the contains pass (below) finds the text inside them. They get no vocabulary, no close pass and no correction. System status says so while one is switched on.

**The vocabulary** (`search_words`, `SiteSearch::Word`, `SiteSearch::Postgres::Vocabulary`, search 2 spec §3.2): the site's words per language, lowercased as written and never stemmed (a correction is shown to a person), unique on (locale, word) and trigram-indexed (`gin_trgm_ops`, which needs `pg_trgm`: `docs/reference/hosting.md`, "Database requirements"); the close pass and the correction draw their candidates from it. A word is a run of letters, marks and digits (an apostrophe allowed between two), 4 to 32 characters, not digits alone, from the `title`, `tags`, `summary` and `body` fields, never `code`; a `LIMITED` language has none. It is written by `Postgres#index` alone, after the entries and in the same transaction, so every writer of the entries writes the words of what it indexed, and a word is kept only where an entry just written holds it by `document @@ plainto_tsquery(config, word)`, the one rule the prune deletes by, so stopwords and the parts of a host name never enter. It is pruned at the end of every build and by `SiteSearch::PruneWordsJob` after a purge or a withdrawn copy (one per transaction, one per run inside `Indexing.one_prune`); a superseded copy's words stay until the record's next copy or the next prune, which is harmless since a correction is verified before it is shown. A writer takes the transaction advisory lock `Vocabulary::LOCK` shared and a prune takes it exclusive, waiting `LOCK_TIMEOUT` (2 s) at most and retried by the job after, so a prune never deletes a word an entry in flight holds. Its writes carry `# version: none`.

**The query** (`SiteSearch::Postgres::Query`, `app/queries/site_search/postgres/query.rb`), Arel through `SqlNodes`, in up to two passes. The exact pass: `websearch_to_tsquery(config, $q)`, the visitor's words a bind named `q` (`SqlNodes.bound`), never in the statement's text, so a debug SQL log prints `[FILTERED]`; the entries of the language that match and that a visitor sees (`SiteSearch::Postgres::Visible`, `visible.rb`, whose `all` every pass and the close pass's candidates read): of the copy in force (no entry of the same record and locale with a later `live_at` not after now), of a record with a current address in the language, kept and published, under no unpublished page: the clock is in the query, so a scheduled copy is found at its `live_at` with no job. Ranked by `ts_rank_cd('{0.1, 0.2, 0.4, 1.0}', document, query, 1)` (D, C, B, A; normalisation 1 divides by the log of the length, so a long page does not win by size), then by type and id; ten from the page's offset; the snippet by `ts_headline` over the ten rows only (`MaxFragments=2, MaxWords=30, MinWords=12`, marked with U+E000 and U+E001, which the backend takes out and records as `marks`); the total a second statement. Both run in a transaction of their own, each under a `SET LOCAL statement_timeout` of the time left before the deadline (at least 1 ms, since 0 is none; with no time left the database is not asked), rolled back after, so the timeout ends with it. A query of stop words alone matches nothing.

**The close pass** (`SiteSearch::Postgres::Close`, `close.rb`, search 2 spec §3.3) runs when the exact pass found fewer than `CLOSE_BELOW` (1) hits, so only when it found nothing and a page is all exact or all close, for a visitor's search (`close_matches`), in a language that is not `LIMITED`, and for a plain query: no `"`, no word beginning with `-`, no standalone `or` (any case), the operators `websearch_to_tsquery` reads, since correcting an exclusion would invert it; a query that is not plain answers `close_outcome: "skipped"`. The query's words are cut as the vocabulary cuts them (`Vocabulary::WORD`, lowercased); a word is corrected when it is `CLOSE_WORD_LENGTH` (4) characters or more, not digits alone, no stopword of the language (`numnode(plainto_tsquery(config, word)) > 0`) and held by no entry a visitor sees now (the same `EXISTS` as a candidate's, below: never "in `search_words`", which holds a scheduled change's, a trashed record's and a superseded copy's words too, so whether a word is corrected would say whether a hidden copy holds it), one statement over `unnest($q)` for all of them, none at all when no word qualifies (so "the 2026 and" sends no statement that reads `search_words`). The first `MAX_CLOSE_WORDS` (6) each get, in a statement of their own, the `CANDIDATES` (3) words of the language's vocabulary at `similarity` `SIMILARITY` (0.3, `pg_trgm`'s own default, `SET LOCAL pg_trgm.similarity_threshold` so `%` uses the words' trigram index) or more, most similar first, then the smallest difference in length, then alphabetically, each one **held by an entry a visitor sees now** (`EXISTS` an entry of the language with `document @@ plainto_tsquery(config, word)` and `Visible#all`), so a word only a scheduled, pending, trashed or hidden copy holds is never a candidate (ContentSpiel's verification of the correction is the rule for every backend; this keeps the built-in from wasting it). Measured on Postgres 17: deploymnet/deployment 0.47, serch/search 0.44, recieve/receive 0.33, invoice/voice 0.40 (which the exact pass finds first). The close tsquery is `(plainto_tsquery(config, $word) || plainto_tsquery(config, $candidate) || …) && …` over every query word, grouped whole (`@@` and `&&` share a precedence), every word and candidate a bind named `q`; ranked, paged, counted and marked as the exact pass is, every hit `close: true`. The correction is the query's text with each corrected word replaced by its first candidate, or nil when no word has one. No candidate, no further statement: the close answer is empty.

**The contains pass** (`SiteSearch::Postgres::Contains`, `contains.rb`, search 2 spec §3.4) is the real search in a `LIMITED` language and always runs there: an entry a visitor sees whose `title` or `text` (the body) holds every whitespace-separated part of the query (its operators read as the exact pass reads them: a `"` taken out, a part beginning with `-` leaving out what holds the rest of it, a standalone `or` no part, and a query of operators alone finding nothing), `SqlNodes.ilike` with `SqlNodes.like_pattern`, so a typed `%`, `_` or `\` is only itself, each pattern a bind named `q`. Its hits follow the exact pass's in one list, never repeating one (it is handed the exact pass's condition as `exclude:` and its total as `after:`, so a page takes the rest of its rows from it and a later page skips what earlier ones drew), are never close, and rank by a title that holds the first part, then `strpos` of it in the lowercased body, then type and id; the total is both. The snippet is cut by the database around the earliest occurrence of a part (`substr` from `LEAST` of each part's `strpos`), `SNIPPET_BEFORE` (80) characters before it and `SNIPPET_LENGTH` (300) in all, so a hit's text of up to `MAX_TEXT` is never read whole, and only the cut has every occurrence of every part marked (`ts_headline` cannot mark part of a word under `simple`). No trigram index: a query of one or two characters, the common word in these scripts, has none, and a GIN `gin_trgm_ops` index measured twelve times the text; the language's entries are scanned. The summary field is not in it. Its answer's `close_outcome` is `"skipped"`.

**The suggestions** (`SiteSearch::Postgres::Suggest`, `suggest.rb`, search 2 spec §4.3): `to_tsvector('simple', title) @@ to_tsquery('simple', $q)` on `search_entries.title`, which `index_search_entries_on_title_words` serves (`simple`, because a stem is no prefix: "deploym" begins no word of the stem "deploy"), with `Visible#all` and the language. `$q` (`Suggest.tsquery_text`) is the prefix's letters, marks and digits alone, lowercased, each `'word':*`, joined by `&`, so no tsquery operator can be written; a prefix with none sends no statement. Ordered by a title that begins with the prefix (`ILIKE`, `like_pattern(prefix: true)`), then `length(title)`, then type and id; `limit` rows. In a `LIMITED` language the title contains the text (`ILIKE` with `like_pattern`, a scan of one language's titles). One statement, every pattern a bind named `q`, in a rolled-back transaction of its own under `in_time_left`, as `Query`'s.

**The share.** Each second pass runs in a savepoint of its own, rolled back after (its `SET LOCAL`s end with it), with every statement held to the time left of `CLOSE_SHARE` (1 second) from its start or of the search's deadline, whichever is sooner (`Query.share_of`); out of time, `ActiveRecord::QueryCanceled` rolls the savepoint back and the exact answer stands, with `close_outcome: "timeout"` for the close pass (no hits, no correction: no close matches, not unavailable). `health` is `:ok` with no detail; `entry_count` counts the pages and posts in the index, for System status.

## The automatic build

Nobody runs a task after an upgrade, a change of the languages or a new backend.

**The state** (`search_index_states`, `SiteSearch::IndexState`): one row per backend, written by the build alone: `backend`, `fingerprint`, `languages` (what the last finished build indexed), `status` `building` or `ready`, `done`, `total`, `started_at`, `finished_at`. The fingerprint is a SHA-256 of what documents are made from besides the copies: the enabled languages with each one's fallback chain, `Documents::REVISION` and, for the built-in, `Postgres::CONFIGS` and `Postgres::REVISION` (1: moved when what the built-in stores of a document changes for the same document). The index is **empty** when the backend in use has no row and **stale** when its row is not `ready` with today's fingerprint. Copies taken since the build are indexed as they are taken, so they never make it stale.

**The triggers.** The boot (`SiteSearch::BootCheck`, from the initializer's `after_initialize`): in a process that serves (the web server, `bin/jobs`, `bin/rails runner`; not a console, a rake task or the test environment) it enqueues `SiteSearch::IndexCheckJob`, which reads the row and enqueues `SiteSearch::ReindexJob` when the index is empty or stale, and leaves a database alone whose migration has not run; a queue whose table is missing is skipped and an enqueue that raises is logged by its class alone, so a boot never fails for search. The languages: `languages_changed` enqueues `ReindexJob` after the settings' commit (built in the settings transaction, it would hold the row's lock for the length of the build); until it has run, a language just enabled finds nothing and the others answer from their old fallback text. A backend switch: its row is missing, so the boot's check builds it.

**`ReindexJob`** builds one backend at a time: Solid Queue's `limits_concurrency` on `site_search_reindex:<name>`, one, for an hour, discarding a second enqueue while one waits or runs; a job that slips in later finds the row ready and does nothing. A job that built enqueues itself once more ten seconds later (`AGAIN_AFTER`), so a change of the languages discarded while it ran is built then. A job for a backend the site no longer uses does nothing. A build another holds (`Rebuild::Busy`) is retried ten times a minute apart; a backend's failure five times, then reported.

**`SiteSearch::Rebuild`** is the build, for the job and for `bin/rails search:reindex`, which runs it in the foreground for by-hand use (a build that stopped, System status's command) and says when another build holds the backend. It holds a session advisory lock on the backend's name; marks the row `building` with the total; replaces the documents record by record, a hundred at a time (each kept published or scheduled page's and post's copy in force and pending copy, sent, then `prune_record`), writing `done` after every batch. Nothing is cleared first, so search keeps answering from the old documents of the records not reached yet, and a build that stops half way leaves every record with documents. A copy taken during the build is never lost: for the built-in each record is read again `FOR SHARE` in a transaction of its own, which `take!`'s `FOR UPDATE` waits for; for an outside engine the copies to keep are read again right before the prune (`SyncJob.sync`). For an outside engine the records that are not kept and published (trashed, unpublished, drafts) are synced after, a hundred at a time, so whatever a lost or failed job left of them in the engine goes. At the end the documents of the languages switched off since the last finished build go (`remove(…, languages:)`), and the row is marked `ready` with the fingerprint read at the start, so a change made during the build leaves it stale for the next run. A build that dies leaves the row `building`; one left so for over an hour with no job at work reads "stopped" on System status.

## The request

**The block asks; the controller searches once.** `PublicPageRendering#search_answer` (both `PagesController` and `PreviewController`) runs `SiteSearch::Answer.for` the first time a Search block asks and keeps it for the render, so two blocks on a page draw one search and a page with none never searches. A request asks a search when `q` is a String with words left once normalised (`search_requested?`); an Array or Hash `q` and one of spaces or control characters alone are no search. `q` arrives as bytes (`param_encoding … Encoding::BINARY`), so a query that is no UTF-8 is scrubbed rather than refused into a logged 400. `SiteSearch::Answer`'s `state` is `:empty`, `:results`, `:none`, `:too_long` (over 200 characters, never sent to a backend; the field keeps the text as typed), `:limited` or `:unavailable`, with `results` (`SiteSearch::Shown::Item`s), `total`, `pagination` (`Pagination`, ten to a page, the page parsed before the total is known, so a page past the last stays as asked and draws `:past_end`) and `live_note`.

**`SiteSearch.search(query)`** is the one caller of a backend's `search`: it hands a deadline `SiteSearch::TIMEOUT` (3 seconds) from now, treats an answer handed back after the deadline as a failure, and so an answer of the wrong shape (not `SiteSearch::Results`, a total that is no Integer from 0 below 2**53 (`SiteSearch::MAX_TOTAL`), hits that are no Array of `SiteSearch::Hit`s with Integer ids, a hit's `close` that is not `true` or `false`, a correction that is neither nil nor a String, a close outcome that is neither nil, `"skipped"` nor `"timeout"`, a snippet whose text is no String or whose marks are no pairs of Integers: a `TypeError`, scrubbed like any failure), cuts every snippet to `SiteSearch::SNIPPET_LENGTH` (500) characters at a word boundary, dropping the marks past the cut, verifies the correction (below), and rescues every `StandardError`, answering `:unavailable`: the block says search is unavailable and the page is drawn as any page, with status 200. A failure is scrubbed to `SiteSearch::Unavailable` (the backend's name and the error's class, no cause, no message) before any span, log line or report meets it, and reported through `Rails.error.report` **at most once a minute per site**: the minute is a key in `CounterStore.current`, Solid Cache in production, which every process and container of the site shares (`SiteSearch::Reports`; a block type's raising `search_text` has a minute of its own). A report never raises: with the store unreachable it is made unthrottled. The scrubbed error keeps the backend's backtrace, which names files and lines and never the message. A gem's backend that does not answer every method of `SiteSearch::Backend::METHODS` raises `SiteSearch::Backends::NotABackend` naming the missing ones when it is first built.

**The correction is verified, whatever the backend** (`SiteSearch.verified`). An outside engine's spellcheck builds from its whole index, scheduled copies included, and the built-in's vocabulary keeps a word a pending or purged copy held, so a correction is drawn only when a search for it finds a page a visitor sees now. It and the close-matches sentence are decided on page 1: a correction is weighed only on an answer with no match at all (`total` 0, on any page) or on a page 1 whose first hit is close (no close hit stands before an exact one, so that page holds none), never on a later page nor on an empty page past the end of exact hits; it is normalised as typed text is (`Query.normalise`) and dropped, unasked, when it is blank, longer than `MAX_LENGTH`, the query again ignoring case, or made of syntax (no letter or digit: `*:*`); it is dropped unasked when the deadline has passed, since **one deadline**, `TIMEOUT` from the moment `search` asks, holds the search and its verification. Otherwise one more search runs: the correction's text in the query's language and view, `page: 1`, `per_page: 1`, `close_matches: false`, and the correction is kept only when that search answers an exact hit `SiteSearch::Shown` keeps. The verifying search is part of the visitor's one request and counts toward no limit; its total is not the answer's. One that fails is scrubbed and reported like any failure, and drops the correction while the answer stands. `SiteSearch::Answer` carries the verified `correction` and `close_matches?`, true on page 1 alone when its first hit is close (read from the backend's hits before the re-check), so a later page of close matches does not say the sentence again.

**Caching.** Every answer to a request with `q`, on a page with a Search block or not, the 404, the default language's redirect and the 429 included, is `Cache-Control: private, no-store`, with no ETag and no `stale?`: rendered every time (`answer_search_privately`). A public response is keyed by its URL in a shared cache, `?q=` included, so a CDN would keep the query for as long as it kept the page; free text has almost no repeat hits, and one search is two indexed statements. Nothing of a search goes into `Rails.cache`. Such answers also carry `X-Robots-Tag: noindex` and `Referrer-Policy: origin` (the next page a visitor opens is told only this site's origin). Without `q` a page answers as every page does, and a Search block then draws only its field. Search stays a GET: a results page can be bookmarked and shared, Back works, no script is needed.

**The limits** (`SiteSearch::QueryLimit`, a concern of both controllers): 20 searches per visitor in a minute, keyed by `VisitorAddress.key(request.remote_ip, purpose: "content_spiel search visitor")` (an HMAC, an IPv6 visitor by their /64; the store holds no address), and 600 a minute across the site, the flood limit, whose cost is that during a flood a real search is refused with the rest. Only a search counts, on any page with `q`; the preview's searches count in the same counters. Over either, nothing halts: the page is drawn with status 429 and the block in `:limited`, and no backend is asked. Who the visitor is rests on `request.remote_ip`, right only behind trusted proxies (`docs/reference/hosting.md`, "The visitor's address behind a proxy").

**The query is never logged, audited or kept by the CMS.** `filter_parameters` holds `/\Aq\z/`, the whole name (a bare `:q` matches by substring and would mask `quote`, and `Audit::Snapshot.scrub` drops every key the list matches), which reaches "Started GET", "Redirected to" and Active Record's filtered binds; the database is handed it as the bind `q`; spans carry no query string (`Telemetry::PathScrubber`) and the search's span none; no audit event, table, cache entry or error report holds it. The default language's redirect (`/en/…` to `/…`) keeps the query string, rebuilt from the query parameters, to a path on the request's own host, with the path's leading slashes and backslashes taken off and each segment percent-encoded again: `/en/%2Fevil.com` decodes to "/evil.com", and a location of `//evil.com` would be another host; a decoded space, tab, quote, brace, line break or letter outside ASCII (`/en/caf%C3%A9`) is a location Rails cannot parse; Rails refuses both with an error whose message holds the query. Encoded, the path names the same page ("a path with characters no location may hold redirects encoded on the site's own host, never a 500 that carries the query", "an accented slug under the default language's prefix redirects to its page"). **The front servers' access logs keep the query**, as they keep the address of any page visit: kamal-proxy's access log, Thruster's request log in the container's output and a CDN's or load balancer's logs write the request line with its query string, and Rails' `filter_parameters` reaches none of them. Those logs are the site operator's, not the CMS's (`docs/reference/hosting.md`, "A search's words in the front servers' logs").

**In the preview** (`/<ADMIN_PATH>/preview`) a Search block searches the live site, never the rows the preview draws, and says so above its outcome ("Results come from the live site.", `live_note?`).

**`SiteSearch.suggest(text:, language:, now:)`** is the one caller of a backend's `suggest` and answers a `SiteSearch::SuggestAnswer` (`state` `:ok` or `:unavailable`, `items` of `SuggestAnswer::Item`: `kind` `:page`, `:post` or `:tag`, `label`, `where` (a page's place joined by " › ", a post's date as `post_date` writes it, nil for a tag), `url` and `marks`, `[start, length]` on the label). The prefix normalised (`Query.normalise`) to under `MIN_PREFIX` (2), over `MAX_PREFIX` (100) or nothing answers `:ok` with no items and asks nothing. Otherwise, under one deadline of `SUGGEST_TIMEOUT` (0.3 s): the backend's `suggest`, when it has one, for `SUGGEST_LIMIT` (8) titles with a deadline of `SUGGEST_BACKEND_SHARE` (0.2 s), scrubbed by `Unavailable.scrubbing`, its shape checked and an answer after its deadline a failure; then, in one transaction rolled back after with `SET LOCAL statement_timeout` of what is left (`SuggestAnswer.build`), the titles through `Shown` (as hits with no snippet: label, place and address from the copy in force), the tags (`SiteSearch::TagSuggestions`), and a tag's address: its listing page (`TagPage`), else its name as `?q=` on the site's search page (`SearchPage`), a tag with neither left out. Up to `TITLE_SUGGESTIONS` (5) titles, then up to `TAG_SUGGESTIONS` (3) tags, each kind filling the other's gap up to 8. The marks are ContentSpiel's (`SuggestAnswer.marks_of`): where a prefix word begins a word of the label, case-folded; in a `LIMITED` language, every place the label contains the prefix. Any failure answers `:unavailable` and is reported through `Reports.report_suggest`, a minute of its own. The statements are a constant number whatever the count of titles and tags, at most 28 (`SUGGEST_STATEMENTS`): the two `SET LOCAL`s, the backend's title query, `Shown`'s check (at most its 16), the tags, one pass that finds the tags' listing pages and the search page together (`TagPage.with_search_page`: the copies holding either, then one `FirstHolder` and one read of the copies found) and the addresses; the limit's two counters come on top (`test/models/site_search/suggest_test.rb`, "the statements are at most SUGGEST_STATEMENTS, the same for four suggestions as for eight, and the prefix is a bind").

**`SiteSearch::TagSuggestions`** (`app/queries/site_search/tag_suggestions.rb`), whatever the backend: `Tag.name_starting` (the prefix a bind named `q`, a typed `%` or `_` only itself), `EXISTS` a copy in force (the greatest `(live_at, id)` whose time has come, the order `Postgres::Visible#in_force` compares) of a kept, published post that carries the tag (`tag_ids @> ARRAY[tags.id]`, `SqlNodes.array_contains_column`, which `index_published_versions_on_tag_ids` can serve) with a current address in the language under a listing page with no unpublished page above; by name, `limit` of them; one statement. So a tag only a draft, a scheduled post, a trashed post or an unpublished change carries is never offered, and a renamed tag is offered by its current name. A tag is no publishable record: its name is not held back with a post's change, and a rename is offered at once while the posts' pages draw the old name until each is published again, so a tag renamed to a name that must not be seen yet is seen in the suggestions (a known limit; the name an editor types for a tag is read as public).

**`search_page`** (`ThemeHelper`, `SiteSearch::SearchPage`): the page that holds the site's first Search block in reading order, as published, or nil, for a theme's own header search box. Read from the copies in force of visible pages with an address in the language, memoised for the render; everything it reads moves the content version, so a page's ETag follows a Search block published or taken away (`docs/reference/theming.md`, "Helpers").

## Suggestions

**`POST /search/suggestions`** (`SiteSearch::SuggestionsController`, `app/controllers/site_search/`; the route `search_suggestions` in `HostRouteConstraint::Site`, beside the form sends, before the catch-alls, `format: false` and JSON by default): a JSON body `{"suggest": "<prefix>", "language": "de"}`, answered by `SiteSearch.suggest` (above) as `{"state", "status", "suggestions": [{"kind", "kind_label", "label", "where", "url", "marks"}]}`. Every route of the page tree is a GET, so a page whose slug is `search` keeps its address and a GET of `/search/suggestions` is the page tree's (its child, or a 404). With `ADMIN_HOST` set it answers on the public host alone, as the form sends do. The language is the body's `language` when it is a switched-on language (`Locales.enabled?`), otherwise the default, so `SiteSearch.suggest` is never handed one the site does not have; the path names no language and no page is resolved.

| `state` | Status | When |
|---|---|---|
| `ok` | 200 | answered: `status` is `suggestions` (counted) or `no_suggestions` |
| `unavailable` | 200 | the backend failed or was late (`suggestions_unavailable`) |
| `limited` | 429 | over a limit, nothing asked (`suggestions_limited`) |
| `refused` | 403 | `Sec-Fetch-Site` present and not `same-origin`; else `Origin` present and not `request.base_url`; or a type that is not `application/json` |
| `refused` | 400 | the body did not parse, is no JSON object, or its `suggest` is missing or no String |
| `refused` | 413 | the body is over 1,024 bytes, with or without a length (answered by the gate) |

A refusal's `status` is empty and its `suggestions` none. `status` is the one sentence a screen reader hears, in the language asked: the words `suggestions`, `no_suggestions`, `suggestions_limited` and `suggestions_unavailable`, and `kind_label` the words `kind_page`, `kind_post` and `kind_tag`, under `public.blocks.search` (`PublicStrings.read`). Those but `suggestions_unavailable` are the endpoint's and not the Search block's `words:` (`Blocks::SearchComponent`'s contract), since the block's template does not read them; the template reads `suggestions_unavailable` (the script's words for a failure), `suggestions_loading` and `suggestions_label`. The JSON is encoded with `<`, `>` and `&` escaped (`answer_with`): `render json:` with an object skips that escape under Rails 8.1's defaults (`escape_json_responses`).

**The gate, `ContentSpiel::SuggestGate`** (`lib/content_spiel/suggest_gate.rb`, inserted after `Rails::Rack::Logger`): Rails parses a JSON body the moment the parameters are asked for, which the controller's instrumentation does before any callback (the "Parameters:" line), and a parse error's message quotes the body. So for `POST` of this path alone (compared after the router's `normalize_path`, so a trailing or doubled slash is gated too; not on the admin host, which the router answers 404) the gate reads the body first: a `Content-Length` over `MAX_BODY` (1,024) is a 413 with nothing read, a body with no length is read through `MAX_BODY + 1` bytes and over the cap is a 413, answered by the gate with the refused JSON, `private, no-store` and `noindex`. The cap is on what Rails parses and logs: Puma has read the whole body before any middleware, as for every route, and a cap on a request body's size is the front proxy's (Thruster's `MAX_REQUEST_BODY`, a CDN's rule). Otherwise it parses the bytes when they are UTF-8 (`JSON.parse`, the error rescued unread) into `env["content_spiel.suggest.body"]`, or `:malformed` (bytes that are no UTF-8, or JSON that does not parse), and hands Rails an EMPTY body, length 0, whatever the body and its type, with the content type kept: Rails parses no parameter of it, so no key, nested value, form field or multipart part of the visitor's is in the "Parameters:" line (there is none; `wrap_parameters false`), and no parse error quotes one. `JSON.parse` takes a byte that is no UTF-8 inside a string as it is, and Rails would refuse it with `BadRequest` "Invalid encoding for parameter: …", quoting it at info. What Rack kept of a form body it parsed before the gate (`Rack::MethodOverride` reads a form POST for `_method`), its failed parse's error included, is forgotten (`SuggestGate::FORM_CACHE`), since Rack raises that error again at Rails' next read. The type check still answers first, and the 400 comes from the flag. The controller reads the gate's value and never `params`. It also takes Rack's ETag off the answer.

**No token, and the wall.** `include Cookieless` comes FIRST, as in `FormSendsController`, and `skip_forgery_protection`: a public page carries no token, and this request reads no session, runs as no one, writes nothing and answers only what the public site shows. Its one side effect is a count, which another site's pages could spend through their visitors' browsers: the 403 above refuses those, and a cross-site `fetch` of `application/json` needs a preflight nothing here answers. A request with neither header (curl, a script) is answered and counted. Every answer, a refusal included, is `Cache-Control: private, no-store`, with no ETag, `X-Robots-Tag: noindex` and nothing in `Vary`.

**The limits** (`SiteSearch::SuggestLimit`, `app/controllers/concerns/site_search/suggest_limit.rb`): 120 a minute per visitor and 3,000 a minute across the site, on counters of their own (`suggest_visitor`, `suggest_site`, scope `site_search_suggest`), never the search's, so typing two queries does not spend the twenty searches a minute; the visitor key is the search's (`VisitorAddress.key` under `QueryLimit::KEY_PURPOSE`). The concern is included after the refusals, so a 403, 400 or 413 counts nothing. A third bound is the suggestions in flight: at most `IN_FLIGHT` (2) answered at once per process (`SuggestLimit::SLOTS`, a semaphore its threads share, below Puma's default of three threads), so a flood the counters let through (50 a second, each holding a thread and a connection up to 0.3 s) never takes every thread from the pages and CS Studio; a request that finds both slots taken is answered at once, never queued, and its slot is given back on every path, a raise included (`SuggestLimit.in_a_slot`). Over any of the three: 429, `limited` (the request span's `search.outcome`), no backend asked (`test/controllers/site_search/suggestions_controller_test.rb`: "with every slot in flight a suggestion answers limited at once, and no backend is asked", "a suggestion that raises gives its slot back"; `test/controllers/concerns/site_search/suggest_limit_test.rb`).

**The prefix is personal data**, as a query is: `filter_parameters` holds `/\Asuggest\z/`, the whole name, though Rails is handed none of the body; it reaches the database only as binds; `search.suggest` carries no prefix; and no log line, span, audit event, table, cache entry or error report holds it. A refused or limited request has no `search.suggest` span: its outcome is the request span's `search.outcome` (`refused` or `limited`). Being a POST body, the prefix is not in the front servers' access logs either, which write the request line alone (`docs/reference/hosting.md`, "A search's words in the front servers' logs").

**The script, `search-suggest`** (`app/javascript/controllers/search_suggest_controller.js`; spec §4.5; the SiteSearchSuggest card). A controller of the site's own that a visitor's page alone registers: `PUBLIC_ONLY` in `controllers/index.js` keeps it out of the site's own registration, and `site.js` registers it, so no CS Studio screen, sign-in or setup imports it. It is still modulepreloaded with the rest of `controllers/` everywhere: importmap gives a `pin_all_from` directory one preload, and the directory overrides a pin of one of its files, so only the import is held (`test/integration/public_javascript_test.rb`: "search_suggest is registered by site.js and imported on no CS Studio screen"). Its markup is a contract line (`docs/reference/theming.md`, "Scripts"). With no `url` value it does nothing, and without it the form is the plain GET.

- **The combobox.** At `connect` the field gets `role="combobox"`, `aria-autocomplete="list"`, `aria-expanded`, `aria-controls` and `autocomplete="off"` (its own values kept to put back), and the list `role="listbox"`. `aria-expanded` is "true" only while the shown listbox holds options; a message row (none, limited, unavailable) stands in the popup outside the listbox and is no option. Down opens the list and moves to the next option (round to the first), Up to the previous (from the field to the last); the active option is `aria-activedescendant` on the field and `aria-selected="true"`, and the caret stays in the field. Enter on an active option goes to it; with none active the form is sent. Escape closes an open list, and is the browser's when it is closed. Tab closes it and chooses nothing. The pointer over an option makes it active, a press goes to it (`mousedown` on the list is cancelled, so the field keeps its focus), a press outside closes the list. The focus leaving the field any other way closes the list too. Going is `Turbo.visit`, or `location.assign` without Turbo, and a suggestion whose address does not parse or is not this site's is not drawn.
- **Asking.** From two characters, 150 ms after the last input, with the prefix sliced to 100 characters and the language the page's `<html lang>`, `credentials: "omit"` and `referrerPolicy: "no-referrer"`. A newer input aborts the request in flight (`AbortController`), and an answer is drawn only when it is the newest asked and the field still holds its prefix. The last 20 `ok` answers are kept in memory, never in storage. After `limited` nothing is asked for 60 seconds. The listbox is `aria-busy` from an input that will be answered until its answer is drawn. `loading` is written only after 300 ms without an answer: the last rows stay, dimmed, and the loading word shows at the field's end.
- **Drawing.** Each option is a clone of the `option` template; its parts are filled with `textContent` and each mark is a `<mark>` made with `document.createElement`, from the `[start, length]` ranges in characters. The script names no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `DOMParser` or `document.write` (`test/lib/public_script_guards_test.rb`: "search_suggest writes no HTML from text"). The first tag after a title is ruled off (`search-suggest__option--first-tag`). The server's `status` goes into the live region and, for none and limited, into the message row; a network failure, an answer that is not the endpoint's JSON, `refused` and `unavailable` draw the `unavailable` value, the template's own words.
- **Taken back.** At `turbo:before-cache` and at `disconnect`: every attribute it wrote, the options, the message, the live region, the loading word and the state, so Back never brings an open list from Turbo's copy. A page that is not left (an anchor of it) keeps the script connected, and the field is a combobox again the moment it is focused or typed into. Browser tests: `test/system/search_suggestions_test.rb`.

**Where it is asked**: `ThemeHelper#search_suggest_url`, the route's path, or nil in the preview (its suggestions would be the live site's and lead out of it) and on a site with no search page; the one rule, which `Blocks::SearchComponent#suggest_url` reads too (`docs/reference/theming.md`, "Helpers").

## Telemetry

`search.query` (internal, under the request's span): `search.backend`, `search.page`, `search.outcome` (`results`, `none` or `unavailable`), `search.results` (the total), `search.close` (`SiteSearch::CLOSE_OUTCOMES`, read from the verified answer after it: `skipped` for a query with `close_matches: false`, `found` when any hit is close, the backend's `close_outcome` otherwise, else `none`; a backend never writes on the span) and `search.correction` (whether a verified correction is drawn); never the query or the correction, its length or a digest of it, and a failed search's span holds neither the query nor the engine's message. `search.suggest` (internal, `SiteSearch.suggest`): `search.backend`, `search.outcome` (`ok` or `unavailable`) and `search.suggestions` (the count), and nothing else: never the prefix, its length or a digest. A suggestion request refused (403, 400, 413) or limited (429) starts no `search.suggest`, and writes `search.outcome` (`refused` or `limited`) on the request's own span. `search.index` (`SyncJob`): `search.backend` and `search.documents`, the count. Both are in `Telemetry::SPANS`, their attributes in `ATTRIBUTES`.

## System status

The "Search" row (`Setup::SystemCheck#search`, from `SiteSearch::Status.read`, on System status and in the wizard's check), its words under `admin.system_status.search`: while the index is built, a warning with the progress ("Building the search index: 340 of 1,200 records."), no command, and the backend not asked; a build left `building` for over an hour with no reindex job waiting or running, a warning with `bin/rails search:reindex` to copy ("stopped"); no row and no job, "isn't built yet" with the command; a ready row of another fingerprint and no job, "out of date" with the command; ready, the built-in's count of the pages and posts in the index, "Search finds 1,234 pages and posts (built-in)." (a record counts once, and the count includes a trashed record's entries, kept with its copies until it is purged, and a record whose only copy is pending), or an outside backend's "Solr answers." (with its detail, above); a `:warn` or `:failed` health, a warning with its detail; no answer in 3 seconds (or a raise), "Solr did not answer in 3 seconds. Visitors see “Search isn't available right now.”". The backend's `health` is asked in a thread waited for three seconds and no longer, never killed, so a backend that ignores its deadline holds neither System status nor the wizard (a thread is left behind per visit while it hangs, a leak bounded by how often the page is opened, accepted). With the built-in, while Japanese, Chinese, Thai or Korean is switched on, a note under the row names them ("Search in Japanese and Korean finds the text a page contains, with no stemming and no correction."); a note, not a warning. With an outside backend that answers no `suggest` (`Status#tags_only`), the note is "Suggestions while typing offer tags only: Solr offers no title suggestions." (`tags_only`); the two never meet, since the limited languages' note is the built-in's.

**No guard**

- The close pass's page is the query's own page because `CLOSE_BELOW` is 1, so it runs only when the exact pass found nothing; raising it would need the close hits paged after the exact ones, as the contains pass's are (`after:`), and no test fails until then.
- `SiteSearch::Documents::REVISION` is bumped by hand when the extraction or a type's `search_text` changes; without the bump the index keeps the old words until each record's next copy.
- A live record with no copy (written around the services) is not searchable although the site serves it.
- With an outside backend a page can show fewer than ten results when the re-check drops a stale hit, and the total is the engine's.
- The front servers' access logs (kamal-proxy, Thruster, a CDN) hold a GET's query, as for any page visit; Rails' filter does not reach them.
- A gem's block type that declares no `search_text` is silently unsearchable.
- The gate gates only the path it names: a second route to `SiteSearch::SuggestionsController`, or a new JSON endpoint, is parsed by Rails before any callback, and its parse error quotes the body.
- That a backend is thread-safe, one instance shared by every thread of the process, is its promise; the contract test calls it from one thread.
- That an outside engine escapes its own query syntax is held only as far as the contract test's queries reach, and only when the gem runs the contract; that a backend never logs the query, and that its `Health` detail holds no address or credential, is its promise, which no test of this repository can read.
- A language enabled and switched off again between two builds can leave its documents behind; no visitor reads them, since a search is in an enabled language.
- A new run of purges that each commit on their own (a loop of `Trash::Purge` outside one transaction) enqueues a prune per purge unless it is wrapped in `SiteSearch::Indexing.one_prune`: no guard finds such a loop.
- N (`MAX_CLOSE_WORDS`, `CANDIDATES`), the similarity threshold (`SIMILARITY`) and the time share (`CLOSE_SHARE`) are tuned against the fixture list (`test/fixtures/files/search_typos.yml`) only, since no query is ever kept.
- That the requirement probe (`show_trgm('éé')`) still tells a usable character type from an unusable one on a future Postgres or a new locale provider: measured on 17 only.
- `matched?` (`Blocks::SearchComponent.matched_tag?`) mirrors prefixes, not each engine's stemming.
- A theme's own Search template or header box that writes the listbox without the live region, or fills options with `innerHTML` in a controller of its own: the theme check reads templates, not a theme's scripts.
- An outside engine's close-match rule and correction are its own. Only the ordering rule, the shape, and ContentSpiel's verification are held.
- The contains pass's cost grows with a limited language's text. It is bounded by the time share, not by an index.
- No test races a prune of the vocabulary against a publish on two connections: the writer's shared and the prune's exclusive transaction advisory lock (`SiteSearch::Postgres::Vocabulary::LOCK`) are held by their modes only (`test/models/site_search/postgres/vocabulary_test.rb`: "a write takes the vocabulary's lock shared and a prune takes it exclusive, each to the transaction's end").
