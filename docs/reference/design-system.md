# CS Studio design system

> Describes: `app/components/admin/ui/` (the shared building blocks; a screen's own components are in its screen folder and described by that screen's reference), `app/views/admin/`, `app/views/layouts/`, `app/javascript/controllers/admin/ui/` and `app/javascript/controllers/` (the site's own controllers), `app/assets/tailwind/`, `test/lib/admin_design_rules_test.rb`, `test/lib/admin_contrast_test.rb`, `test/lib/inline_handlers_test.rb`.

## The design pass

The design pass (spec `docs/superpowers/specs/2026-10-03-cs-studio-design-pass-design.md`, the design package in `docs/design/`) rebuilt CS Studio's shared parts. Where the spec and the package disagree, the spec wins; from the package's CSS only `--cs-chrome` and `--cs-cat-1…6` (with their `--color-*` mappings in `app/assets/tailwind/content-spiel.tailwind.css`) were taken, everything else keeps the repo's own tokens. `test/lib/admin_design_rules_test.rb` pins the rules that are easy to break one innocent edit at a time: no raw colour literal (hex of any length, `rgb()`/`hsl()`) and no `dark:` variant other than `dark:scheme-dark` in `app/views/{admin,layouts,setup}`, `app/components/{admin,media,public}` or `app/javascript/{controllers,media,autosave,search,rich_text}` (a colour is a token, and tokens already switch with the theme; the test also fails when one of those directories has no sources, so a rename can't take it out of the rules unnoticed); translation chips and language tabs never mention `danger` (translation states are never red; red is for destruction and failure only); and the replaced components (and `Translations::CachedStatus`) stay deleted, with `danger_outline` appearing nowhere under `app/`. The namespaces that would shadow top-level modules stay forbidden (see "Key Conventions"). **Contrast and buttons** (spec `docs/superpowers/specs/2026-10-15-contrast-and-buttons-design.md`, Claude Design's answers of 2026-10-15) added `--cs-field-line` (with its `border-field-line` utility) and moved the values of lines, strong lines, sunken, meta, dim and dark mode's four grounds. The rule is: a pressable or typed-into element is outlined in `border-field-line` (3:1 on paper, surface and sunken), never `border-line-strong`, which only groups (two named exceptions); and no text is under 11px (a label is the sans `text-label`, a count `text-count`; "One type voice" below). `test/lib/admin_contrast_test.rb` measures CS Studio's token pairs in both schemes (text at 4.5:1, every state mark and outline at 3:1), so a changed token value that breaks a pair fails there; `test/lib/admin_design_rules_test.rb` holds the two rules above and reads a line's classes, so it does not see a control whose line says no hover, focus or pointer (a segmented group's frame, the drop zone).

## E4: the redesign's first stage

CS Studio's redesign (E4; spec `docs/superpowers/specs/2026-11-06-studio-e4-design.md`, plan `docs/superpowers/plans/2026-11-06-studio-e4-stage-1.md`) restyled the shared parts in place and added the tokens, the surfaces and the guards below. Stage 1 changed no structure: the editor's rail, the notes tab and the rest are later stages, and a few places named here as "stage N" are waiting on them. **The public site keeps its look**: a theme's pages draw as they did before, so a value that differs between CS Studio and a visitor's page is scoped to CS Studio and never changed for both. The form-send pages (`layouts/form_send.html.erb`: Check your answers, the thanks, 404, 429 and 503 pages a form's send answers without JavaScript) are the visitor-facing pages that change, because they are CMS-drawn in CS Studio's tokens and are neutral: their accent (the button, the focus ring, the checkbox, the back link) is ink instead of the old blue, and their grounds, lines and words take E4's values of those tokens.

**Surfaces.** `<html data-surface>` says what a page is. `studio` is on the admin, product (sign-in, password reset, invitations) and setup layouts, which are CS Studio's own pages even where no editor is signed in (the wizard and sign-in follow E4's violet). `html[data-surface="studio"]` in `content-spiel.css` is the one scope for a value that applies only there. It wins on specificity: (0,1,1) beats `:root`'s (0,1,0) in any order, so no later `:root` rule can undo it. It is written after every `:root` block that sets the same property as a convention, so the file reads in the order the cascade settles it; the guard holds the selector and that place. Today it holds one value, `--cs-t-label: 12px`. `data-surface="plain"` is on the form-send pages (`layouts/form_send.html.erb`), which are a visitor's, stay neutral and re-value the accent family to ink on paper in both schemes (`--cs-accent` and `--cs-accent-hover` to ink, `--cs-accent-tint` to sunken, `--cs-on-accent` to paper) with `var()` only, after both theme blocks; the public pages carry neither mark. The form-send button's classes are frozen: `FormSendsHelper::FORM_SEND_BUTTON_CLASS` is its own constant, not `ButtonComponent`'s and not the setup helper's, so a restyle of CS Studio's buttons cannot reach a visitor (its colours are tokens, and take the plain surface's ink) (`test/helpers/form_sends_helper_test.rb`: "the form-send page's button is its own frozen string, whatever CS Studio's buttons do", "no form-send view or layout takes a class from the setup helper or the button component"; `test/integration/form_sends_test.rb`: "the admin layout's html is not the plain surface"; `test/lib/admin_contrast_test.rb`: "the plain surface re-values every accent token and nothing else", "the plain block wins over both theme blocks: after them, or by a heavier selector"; the thanks, 404, 429 and 503 pages assert the plain surface in `test/integration/form_sends_test.rb` and `form_send_limits_test.rb`).

**Tokens by role** (`app/assets/tailwind/content-spiel.css`, both schemes; the utilities are mapped in `content-spiel.tailwind.css`). *Grounds*, lowest first: `--cs-paper`, `--cs-surface` (a card), `--cs-rail` (elevation 2: a rail or panel), `--cs-popover` (elevation 3: a popover, menu, dialog, a dragged card), with `--cs-sunken` for a recessed fill, `--cs-chrome` for the sidebar and the tree column and `--cs-field-fill` for a text field's well. In dark each elevation is a lighter ground than the one below it. *Lines*: `--cs-line` and `--cs-line-strong` only group and sit under 3:1 on purpose; `--cs-field-line` is the edge of anything pressed or typed into. *Accent*: `--cs-accent`, `--cs-accent-hover`, `--cs-accent-tint`, `--cs-accent-press` (a secondary's and a tertiary's fill under the pointer) and `--cs-on-accent`. *Status*: `--cs-live` with `--cs-on-live` and `--cs-scheduled` with `--cs-on-scheduled` (the solid chips), `--cs-ok`, `--cs-warn` and `--cs-danger`, each with `-ink` and `-tint`, `--cs-danger-press` (a danger text button's fill under the pointer), `--cs-danger-hover` (the danger confirm's) and `--cs-on-danger` (white in light, dark in dark, where white would measure 3.11:1). *Heads and sections*: `--cs-head-action`, `--cs-head-cool` and `--cs-head-warm` with their `-ink`, `--cs-type-chip` and `--cs-structure` with its tint and ink. *Icon hues*: `--cs-ic-<family>` and `--cs-ic-<family>-bg` for `text`, `media`, `code`, `form`, `lists`, `structure` and `people`; `--cs-tag-usage` is `--cs-ic-structure` under a name of its own, the Tags usage bar's fill. *Depth*: `--cs-shadow-1` to `-4`, and no other shadow token. *Shape*: the radii below. A pair is measured, not judged (`test/lib/admin_contrast_test.rb`: a state mark 3:1 on the surface, the tree's chrome and the rail; text 4.5:1; the accent focus ring 3:1 on every ground; each family's icon 3:1 on its chip and on surface, rail, chrome and popover; the people hue's initials 4.5:1; a Draft chip's words and outline; "a line that only groups stays a hairline"; "the grounds step apart").

**Elevations.** Four levels, always a token (`shadow-1` to `shadow-4`, or `var(--cs-shadow-n)` in a stylesheet), never a Tailwind shadow: 1 is a card and the tree column; 2 is the primary button at rest and the hover lift of a secondary, a danger text and a danger confirm button (a tertiary does not rise); 3 is a menu, popover, dialog, toast, the ⌘K palette, the media picker, the floating save bar and the primary's hover; 4 is what is above everything in a list, the dragged tile (`.admin-drag-chosen`, `.admin-drag-fallback`). Light lifts with a cast shadow, dark with a lighter ground and a one-pixel top highlight, so there the shadow is the weaker cue. A card is told apart by its shadow and has no border of its own; an alert keeps its tinted edge and the drop zone its dashes (`CARD_BORDER_ALLOWED`). A menu's row under the keyboard and the ⌘K palette's selected row carry a 2px accent bar inside their left edge besides the sunken fill, which is 1.13:1 on the dark popover and so no cue on its own (`.admin-menu-panel`, `.admin-palette`; `test/lib/admin_contrast_test.rb`: "a menu's keyboard row and the palette's selected row carry an accent bar, 3:1 on the popover, where their sunken fill is not"). `shadow-menu` is gone from CS Studio (the public language switcher keeps its own).

**Radii.** `rounded-cs` (`--cs-radius`, 2px) stays the radius of small marks: a status, translation or channel chip, a badge, the tooltip, a menu row's hover. The rest are tokens: `rounded-field` (6px; a text field's top corners, its bottom edge is straight), `rounded-button` (8px) and `rounded-button-sm` (7px), `rounded-chip` (7px, the icon chip), `rounded-tile` (12px), `rounded-card` (14px), `rounded-frame` (16px) and `rounded-rail` (18px); `rounded-full` is a pill or a circle. A Tailwind size (`rounded-md`, `rounded-[3px]`) is refused (`test/lib/admin_design_rules_test.rb`: "a shadow is an elevation token", "a radius is a radius token").

**One type voice.** A label is the sans at `text-label` (weight 500) in sentence case, never capitals with letterspacing; the label is **12px under `data-surface="studio"` and 11px for a visitor**, which is why the size is a token that the surface re-values and not a class. A **count** (a tab's number, a row's marker, the posts and Media toolbars' counts) is `text-count`, 11px for both surfaces, and is never a `text-label`: it is a figure in a pill and does not grow with the label. Body text is the sans at 15px and `text-small` is 13px. **Mono is for code and for a value a person copies or compares exactly**: a `<code>` or `<pre>`, a token or key, an audit event's action key, a permission key and the save status line (and the AI test result), the mono-capitals lines that stay; everything else (counts, times, addresses, ⌘K, a field error's "!", language codes, initials, badges, the sidebar's numbers) is the sans. In the stylesheets mono is drawn only for code, an embed and the form-send pages. The one tracked-capitals text is the product wordmark. Guards: `test/lib/admin_design_rules_test.rb`, "one type voice: no capitals with tracking in the sources but the wordmark", "the label is 11px for a visitor and 12px under CS Studio's surface", "the stylesheets set no label in capitals" (only a `.form-send-page` selector is let through, never a CS Studio selector in the same list: "the capitals check lets through a form-send selector and nothing beside it"), "mono is for code, a token's or key's value and the save status line only", "every mono allowance names a file that still writes mono", "the stylesheets draw mono only for code, an embed and the form-send pages", "the token --text-small is mapped to 13px, and --text-count is 11px for studio and visitor alike", "a count is text-count, not the 12px label" (any line of CS Studio's that draws a count, a tab's count, a total, the graph legend's or the presence marker's count, with `text-label`; `COUNT_LABEL_ALLOWED` names the one place a number stands inside words, the inbox card's "3 new"), "the count pattern matches a count helper, a tab's count, a total and the markers, and not text-count or a word". The scans read CS Studio's own sources, the invitation page (`app/views/invitations`) included, and leave out the visitor's two layouts, `application` and `form_send` ("the visitor's two layouts are there, and out of the type-voice and elevation scans"). The allowances (`UPPER_TRACKED_ALLOWED`, `MONO_ALLOWED`, `COUNT_LABEL_ALLOWED`) each name the file or line and why; the second test of each pair fails on an allowance that does not match, so the lists can only shrink.

**Accent: a marker, a selection and a button.** In a *marker* accent means "unread and addressed to you" and nothing else (the notes paragraph below). The selected page-tree row's bar is **a selection, not a marker**: it is the one place a row says "this is open", it is drawn in accent (`.admin-tree-row--selected`, a 3px inset shadow so the title does not move; 3:1 on its sunken ground and on the chrome, `test/lib/admin_contrast_test.rb`: "the selected row's accent bar is 3:1 or better on its sunken ground and on the chrome") and does not make accent a marker colour; a row's unread dot stays the marker. Beside the selection stand **the unsaved marks** and **the wizard's place**, which say "this is yours, not yet saved" and "you are here": the save bar's 8px dot, a changed field's 2px edge inside its well and its 8px dot after a label or legend (drawn by the stylesheet from `data-save-bar-changed`, no utility; 3:1 or better on the field's fill and the card, "the changed mark is 3:1 or better on the field's fill and on the card, in both schemes"), the wizard's current step (a 1.5px accent ring round its accent number, no fill, on the accent tint: "the current step's words are 4.5:1 on the accent tint, and its number in the accent", accent on its tint measuring 5.68:1 in light and 6.25:1 in dark) and its progress fill (a graphic, 3:1 against its sunken track: "the wizard's progress fill is 3:1 or better against its sunken track, in both schemes"); Settings' current nav link is the accent tint in ink, a selection like the tree's. None of them is a marker of something addressed to you. A thing that is not pressable never wears a button's look: the accent fill (`bg-accent`) is only a button (`button_component.rb`, `rich_text/popover.js`'s script-built button, New post's split half in `admin/posts/index.html.erb`), the checkbox, a count pill (the sidebar's Dashboard pill, the notes header's unread count), the unread bubble (the thread and inbox rows, `notes/inbox_controller.js`, `mind_graph/card_notes.js`), the NEW divider (`notes/merge.js`), a progress bar (Translate all's, the upload tiles', the wizard's `setup/_steps.html.erb`) and the save bar's unsaved dot (`save_bar_component.html.erb`) (`ACCENT_FILL_ALLOWED`, each entry with its reason), and the tint with accent words (`bg-accent-tint text-accent`) is only the secondary button, a chip, your own mention and the current sidebar module's row (`TINT_PAIR_ALLOWED`); the tint with the text's own ink is a find's match in a tree ("Tree" below), a rule of the tree block and not a utility (`test/lib/admin_design_rules_test.rb`: "only a button, the checkbox, a count pill, the unread bubble, a progress bar and the unsaved marks carry the accent fill", "the tint with accent words is a secondary button's, a chip's, your own mention or the current module's row, and nothing else", and for each list "every … allowance is still used"). No Tailwind palette colour and no `white` or `black` utility appears in CS Studio ("no Tailwind palette colour or white/black utility in CS Studio").

**Fields are a well.** Every text field in CS Studio, a select, the chip input, the prefix input and the rich-text box are a filled well (`--cs-field-fill`) with a `--cs-field-line` bottom edge, `rounded-field` on the top corners and a 2px accent outline on focus; the rich-text toolbar and its editor are one control with one ring around both. A field takes the well from its wrapper (`.admin-column`, `.admin-field`, a list's filter bar `.admin-filter-bar`, the rich-text popover and the AI suggestion box) or, outside those, from `.admin-well` on itself (the tree's find field, the mind graph's card's note field, a section's anchor; the notes composer's wrapper, round a bare textarea), and `setup_input_class` draws the same with utilities. There is no compact field of another look: a filter bar's controls keep the bar's 38px because the well sets no height. A checkbox and a toggle keep a full outline. An invalid field's edge follows `--cs-field-invalid-border`. A held or view-only form is one box (the prefix and chip wrappers do not nest a second). `test/lib/admin_design_rules_test.rb`: "a control is identified by a field-line edge or a fill of its own, never border-line-strong", "a text field is a well: the field fill and a field-line bottom edge, the accent outline on focus; a checkbox and a toggle keep a full outline", "a filter bar resets the invalid edge, as every wrapper of wells does", "no text input in CS Studio is the old outlined box", "setup_input_class draws the well: the field fill and a bottom edge".

**Status chips and the people hue.** Status is real colour with its word (`Admin::Ui::StatusChipComponent`): Live a solid green chip with a dot and "Live" (`bg-live text-on-live`), a scheduled date a solid amber block, Draft an outlined "○ Draft" in `border-field-line` and dim words. Translation states keep their words and glyphs and are never red; the unpublished-changes chip is outlined like Draft. `bg-live` and `bg-scheduled` (and `on-`) are drawn by the status chip and the scheduled date and nowhere else ("the live and scheduled fills are drawn only by the status chip and the scheduled date"). **A system's state is `Admin::Ui::StateChipComponent`**, never `StatusChipComponent`, whose fills belong to publishing: the state of mail, the AI key, Test connection's result, a system check and the rail's rows ("E4: Settings and the wizard"). The `bg-ok`, `bg-warn` and `bg-danger` fills (and tints) are held to a list of the files that draw one, `STATUS_FILL_FILES`, **a ratchet that may only shrink**, but for a status component, which stands in it only in place of the screens' fills it takes over (`state_chip_component.rb` draws what the Mail state and the system check rows drew), and the wizard's `setup/_steps.html.erb` draws a done step's check on the ok tint, never the Live fill, since a finished step is no publication. A new status fill goes in a status component, not in a screen ("the ok, warn and danger fills are in no file beyond today's: a new one goes in a status component", "the status-fill list holds only files that still draw a status fill"). The people hue (`--cs-ic-people`, a rose) is for people: it is drawn by `IconChipComponent` and the people's own components (the avatar, the notes marker and row pill, the presence marker, the hold strip), never by a button or a type, and the avatars, the note bubble, the presence stack, the hold strip and the people outline draw it ("E4: working together"; "the people hue is drawn only where `PEOPLE_HUE_ALLOWED` says, never by a button").

**Browser tests.** A browser test begins on `visit_editor(record, locale: nil)` or `visit_screen(path)` (`test/application_system_test_case.rb`), each a visit plus `await_admin_controllers`; both fail after a short deadline (`wait:`) naming the controllers that never connected. The rules a browser test keeps (waits, no sleeps, clicks, frame links, JavaScript errors, the shared browser, two people) are in `test/system/README.md`, which `CLAUDE.md` points to; `docs/reference/writing-tests.md` keeps how the suites run.

## E4: the editor's canvas

Stage 2 of E4 (plan `docs/superpowers/plans/2026-11-06-studio-e4-stage-2.md`) redrew the block editor on the stage 1 tokens, with no change to what is saved. The four roles are the rail's ground, the canvas (the paper the list stands on), the raised tile (`--cs-tile-raised`, a card or tile under the pointer or open: `#ffffff` in light, `#1f2a3d` in dark) and the frame (a section). The blocks list is `gap-5.5` (22px).

**A card's state is an edge, and an edge is an outline.** A block card is `rounded-card bg-surface shadow-1` with no border and no rule under its head. Its states are drawn by the stylesheet from `data-card-edge` on the wrapper (`held`, `unavailable`; `BlockCardComponent#card_edge` and `SectionCardComponent#card_edge`, unavailable first) and `data-notes-active` as a 2px outline inside the card (`outline-offset: -2px`), so nothing changes size and no shadow is overwritten:

| State | Mark | Edge | Contrast (light/dark on the card) |
|---|---|---|---|
| held by someone else | `data-card-edge="held"` | `--cs-people` | 8.59 / 10.13 |
| thread open | `data-notes-active` (not on a section) | `--cs-people` (the same outline) | 8.59 / 10.13 |
| type gone | `data-card-edge="unavailable"` | `--cs-danger` | 5.83 / 5.23 |

The people frame, the unavailable edge and the chosen section stand in that order in `content-spiel.tailwind.css` and at one weight, so the later wins; the notes rule is `.admin-block-card:where(:not(.admin-section-card))[data-notes-active]`, because a plain `:not()` would weigh (0,3,0) and beat the unavailable edge. A reader of a held card gets no edge. `editing/freeze.js` writes the held edge on a card whose form it freezes in the browser.

**A tile's states are elevations.** `.admin-block-tile` rests at `shadow-1` on the surface, takes `shadow-2` on the tile-raised ground under the pointer (it does not move or lift by a transform), `shadow-3` plus a 2px accent ring (`0 0 0 2px`) when its face is open or has the keyboard focus, and an open thread is the 2px accent outline inside. These rules are wrapped in `:where()` so each weighs (0,1,0) and the drag rules after them win: the drop place `.admin-drag-ghost` (a 1.5px dashed `--cs-field-line` edge, `box-shadow: none`, the one rule that gives the tile, card, tree row and Settings row their place; 3.28:1 on the paper) and the lifted tile `.admin-drag-chosen` and `.admin-drag-fallback` (popover ground, `shadow-4`). A tile shows its type (chip and name), then its preview: a heading at `text-base` (the 17px heading, one line) and up to three lines of text in `text-dim`, mono for code (`docs/reference/content-blocks-and-types.md`, step 8); the face keeps `focus-visible:outline-hidden` so forced-colours mode keeps an outline where the ring is a shadow.

**A section is a frame.** `.admin-section-card` has no ground, a 1.5px `--cs-structure` edge (danger when its type is gone) and the frame radius; its head is `--cs-structure-tint` in `--cs-structure-ink`, and its words are buttons in the head's ink (13px, a 12% mix under the pointer or the focus, an accent focus ring). Its settings are in one region under the head, on the rail's cool ground (`bg-rail`), `#section-<id>-settings`, which the page editor's rail takes when the section is chosen ("E4: the right rail", below). A held section draws the people outline outside the frame (2px, `outline-offset: 2px`), from the server's `data-card-edge` or from its frozen settings form.

**One add action.** The list ends with one primary "+ Add block" that opens a three-column menu (`Admin::Ui::MenuComponent` with `columns: 3` and an `aria-hidden` `heading:`), and each section column ends with a tertiary "+ Add". `BlockPickerComponent` builds no button of its own: its classes come from `ButtonComponent.classes`. Left and Right do nothing in the three-column menu: ArrowDown and ArrowUp step through the items in reading order.

**The tree's bar and markers.** The selected row's bar is accent (see "Accent" above); the translation markers rest hidden by `sr-only` and show on hover, on focus within the row, for a coarse pointer and always on the selected row. A marker is never `hidden` or `aria-hidden`, so a screen reader reads it at rest. The notes pill stays visible at rest because it asks for action.

## E4: the right rail

Stage 3 of E4 (plan `docs/superpowers/plans/2026-11-06-studio-e4-stage-3.md`) gives the editors a right rail where the editor has the room: the page editor's Page and Section panels, the post editor's Post panel, and on both the Notes tab, which notes register at the panel slot `editor.rail.tabs` (`docs/reference/slots.md`). Nothing is saved differently.

**The container, not the window.** `#editing` (`LiveRegionComponent`) is `.admin-editor-area`, `container: admin-editor / inline-size`, and the rail docks under `@container admin-editor (min-width: 1200px)`, so what decides is the room the editor has: a folded tree changes it while the window stays the same, and the notes, which take no room of their own, do not. No `@media` rule names the rail. A translation tab docks it at the same threshold as the default tab (`test/system/admin/editor_rail_test.rb`: "a translation tab docks the rail at 1200px of the editor"); there the Section tab shows a section's settings read only (`docs/reference/content-blocks-and-types.md`, "The translation tab"). A scrollbar is not one of the things that change that room: CS Studio's document is its scroller and keeps its gutter (`scrollbar-gutter: stable` on `html[data-surface="studio"]`, `content-spiel.css`), so a classic scrollbar that appears as the page grows taller (a colleague's list merge, the person's typing) never undocks the rail near the threshold and moves a section's settings under the person (`test/lib/admin_design_rules_test.rb`: "CS Studio's document keeps its scrollbar gutter, so a scrollbar takes no width from the editor area").

**The grid.** `.admin-rail-grid` (`#editor-grid`) is one column below the threshold. Docked it is `minmax(0, 1fr) var(--cs-rail-width)` with `column-gap: var(--cs-rail-gap)` and `max-width: var(--cs-content-max)`, and `margin-inline: auto`, so the blocks column takes what the rail leaves, the whole grows to 1680px and no further, and its auto margins, 0 below the cap, keep it at the content's left edge there and split the spare width evenly either side past it (the one rule for spare width, which the dashboard and the lists' rail follow too, each inside its docked rule only: undocked, nothing centres; `test/lib/admin_design_rules_test.rb`: "every docked composition and its head row centre past --cs-content-max"). The editor's header row is held to the same box while the rail is docked: each of the header's rows stops at `--cs-content-max` and is centred, so past the cap Publish stands over the rail's right edge, while the header's own line and ground keep the window's width; the page's header stands outside `#editing`, so this reads the grid's `data-rail-docked` (`.admin-editor-header:has(~ .admin-editor-area [data-rail-docked]) > *`, and the post's, inside the area, `.admin-editor-area:has([data-rail-docked]) .admin-editor-header > *`); its rows are `auto auto 1fr`, the tabs, the one current panel and an empty row that takes the rest of the blocks column's height. Three tokens, beside `--cs-form-max` in `content-spiel.css`: `--cs-rail-width` (360px), `--cs-rail-gap` (28px) and `--cs-content-max` (1680px, the widest composition: a main column of 1292px, the gap and the rail); the blocks column is no token of its own, and `.admin-form-column` takes its track whole while docked (`max-width: none`). **The measure:** inside the grown column a field of running text keeps a measure, not the column: the field's wrapper (`.admin-column`, `.admin-field`: its label, well, help, Translate box and error lines together) is at most `--cs-text-measure` (72ch, about 650px in Archivo at 16px), the Code field (`.admin-code-input`, `Admin::Fields::CodeField#input_class`) `--cs-code-measure` (100ch, about 920px at the wrapper's font), and what is wide takes the column: the image field and its preview (`[data-controller~="admin--media--field"]`), a body that holds a table (`.admin-rich-text-table`), a group's rows (`.admin-groups-field`, whose own fields keep the measure); the block card, its head, a section's frame and lanes and the add menu are no field and carry none. On a translation tab a field holding a pair takes the column and each half of the pair keeps the text measure. A section's settings region in the rail keeps none of the room it takes under its head, keyed on `[data-editing-away]`. ## E4: the dashboard

Stage 4 of E4 (plan `docs/superpowers/plans/2026-11-06-studio-e4-stage-4.md`) redraws the dashboard on the same tokens; what each panel holds is in `docs/reference/cs-studio-shell-and-dashboard.md`.

**A panel is headed by its job, and tinted by its kind.** `Admin::DashboardScreen::PanelComponent` takes `kind:` (`:action`, `:shortcuts`, `:information`; any other is refused), and the head's ground and ink follow it: `--cs-head-action` with `--cs-head-action-ink`, `--cs-head-cool` with its ink, `--cs-head-warm` with its ink. The tints are unlayered stylesheet rules on `.admin-dashboard-panel--<kind> .admin-dashboard-panel__head` (`content-spiel.tailwind.css`), not utilities, so a later rule changes them by cascade: the docked rail takes the band away with a rule of higher specificity (0,3,0 against 0,2,0). The heading and the line take the head's ink; nothing in the head sets its own colour but a badge. The panel is elevation 1 on `--cs-surface` with `--cs-radius-card`, and the head's top corners take that radius rather than an `overflow: hidden` that would clip a focus ring.

**`text-h3`.** The panel's heading and a draft tile's title are `text-h3`, the existing `--cs-t-h3` mapped to a utility in `@theme` (`--text-h3`, weight 600), beside `text-h1` and `text-h2` (`test/lib/admin_design_rules_test.rb`: "each heading size token has its utility").

**The scheduled date is a status component.** `Admin::Ui::ScheduledDateComponent` draws a scheduled row's date as a block on the scheduled fill (`bg-scheduled text-on-scheduled rounded-chip size-10`: the month as `text-label`, the day as `text-h2 font-semibold`), hidden from a screen reader because the row's `<time>` says it in words. It stands in `admin/ui/` although only the dashboard draws it, because it is one of the two places the live and scheduled fills may be drawn (`LIVE_SCHEDULED_FILES`, with the status chip).

**What is counted, and what is accent.** Waiting for you's count beside its heading is `text-count` in meta, never accent, and its pill is the read-only notes marker: both count everybody's work. A row's or a tile's closing verb (`.admin-row-verb`, `--cs-t-small`) is `--cs-dim` at rest and `--cs-accent` only while its row or tile is hovered or holds the focus, so accent on a row at rest still means "unread and addressed to you" alone. A draft tile is `rounded-tile`, elevation 1 at rest and 2 on hover, and its stretched link's `::after` carries the focus ring.

**The rail without cards.** Docked (1200px of the dashboard's own width, the editors' threshold), the information panels stand on one rail: `--cs-rail` with `--cs-shadow-2` and `--cs-radius-rail`, the rail's tokens (`--cs-rail-width`, `--cs-rail-gap`), the main column taking the rest up to `--cs-content-max`, and the draft tiles four a row from 64rem of the main column. On it a panel has no ground, no shadow and no tinted band, its heading keeps the warm ink, and its rows, empty line and footer start at the rail's padding. Below the threshold the same panels are cards with their warm heads. Each kind's head words are 4.5:1 on their tint and on the rail's ground, and the scheduled date's words on its block, in both schemes (`test/lib/admin_contrast_test.rb`: "Live, a scheduled date, a panel head's words, a section head's words and the type chip's words are 4.5:1 or better", "an information panel's heading and line read on the rail's ground", "the scheduled date's words read on its block").

The same stage gives the shell three things of its own: one scale of layers, a fade between light and dark, and a colour for every sidebar module.

**THE LAYERS.** Every z-index in CS Studio is one of fourteen tokens, `--cs-z-*`, written once in `:root` of `content-spiel.css` beside the comment that says what each is for, and read as `z-index: var(--cs-z-…)` or the utility `z-(--cs-z-…)`; `auto` is no layer and stays allowed. Three are *local* layers, for raising a thing over its neighbours: `lift` (1, a focused table-strip button, and the canvas over a rail panel that follows it), `raised` (10, a row's second link over its stretched one, a matrix cell's link, a strip entry and its "+", the mind graph's card and tooltip, and an editor's rail panel over a canvas that follows it) and `raised-top` (20, the matrix's sticky title cell, an open or focused strip entry). Eleven are *page* layers, lowest first: `sticky` (15, the save bar), `slide-over` (20, the notes below the rail's threshold), `header` (21, the editor's sticky header, which keeps its menus' z-index inside it), `sheet` (22, the notes under 640px), `divider` (23, the tree's), `top-bar` (25), `popover` (30: a menu, the tooltip, a listbox, the composer's emoji and mention panels, the rich-text popover), `drop` (32, the media library's whole-window drop overlay), `scrim` (35, over an open popover, so a drawer opened with a menu up hides it), `drawer` (40, the sidebar's and the tree's) and `toast` (50). A dialog opens with `showModal()` in the top layer and takes none. Not every user of `lift` and `raised` makes a stacking context of its own, so both stay under the lowest page layer (`raised` < `sticky`); `raised-top` is used only inside a component's own stacking context (the matrix's `isolate`, the canvas). The canvas, `.admin-rail__main`, is a stacking context at `--cs-z-lift` at every width (`isolation: isolate`; its z-index takes without a `position` because it is always a grid or flex item): what it raises, a popover included, stays inside it, so the slide-over and the editor's header, which stand outside it, cover all of it, and a canvas menu scrolls under the header and the top bar. The rail's panels other than the notes' are each a context of their own, under every page layer, so a settings popover (a tag suggestion, a related post) stays under the slide-over; the notes' panel is left out because it holds the slide-over, which a panel's context would trap. Below the threshold, and on a translation tab at every width, a panel and the canvas stand one above the other, and whichever comes first in the document drops its popovers onto the other, so it is the higher: a panel before the canvas (the page editor's) is at `--cs-z-raised`, over the canvas, and a panel after it (the post editor's Post panel and the panels after the post form) is `isolation: isolate` at level 0, under the canvas, so the body's Insert menu, its Link popover or a table strip's menu that hangs over the Excerpt field stays over the field. Docked, the two stand side by side and nothing either raises reaches the other.

**The theme fade.** Pressing Light, Dark or Auto, the public footer's toggle, and an OS change while the choice is Auto all go through `theme_controller.js`'s `apply`, which writes `data-theme-choice` and `aria-checked` at once (the pressed button keeps the focus) and then writes `data-theme` inside `document.startViewTransition`. The callback reads the choice on `<html>` when it runs, so the last press wins whichever callback runs last. The fade is two tokens, `--cs-theme-fade-duration` (250ms) and `--cs-theme-fade-easing` (`ease-out`), each written once in `content-spiel.css`, read by the one rule `html[data-surface="studio"]::view-transition-old(root), ::view-transition-new(root)`, which sets the duration and the timing function and never the `animation` shorthand, so the browser's own keyframes stay. The pseudo-elements are drawn over the whole document, top layer included, and take no layer. The theme changes with no fade where the API is missing, under `prefers-reduced-motion: reduce`, when the call throws, and on first paint (`connect` and `shared/_theme_head` never fade). A visitor's page reads its theme's stylesheet, not this one, so the public toggle takes the browser's default fade. While the fade runs, Chrome sends every press to the document element whatever the pseudo-elements' `pointer-events`, so a press during the 250ms is lost; that is accepted.

**Every sidebar module has a family.** `StudioModules.register` requires `family:`, one of `text media code form lists structure people`; the map and the refusals are in `docs/reference/cs-studio-shell-and-dashboard.md`, "Shell". The current module's row is the accent tint in accent words and its chip keeps its family's colours, so the icon chip has no `accent` family. What is measured is the icon, the chip's meaningful mark: 3:1 on its chip, and on `--cs-chrome` and `--cs-accent-tint` in both schemes; the chip's fill is decoration and unmeasured.

## E4: the mind graph

Stage 5a of E4 (plan `docs/superpowers/plans/2026-11-07-studio-e4-stage-5a.md`) draws the mind graph on E4's tokens; what each mark, line and state is, and the guards by name, are in `docs/reference/cs-studio-shell-and-dashboard.md`, "Mind graph".

**The list stands in the tree column.** The list is not in the graph's box: it is the shell's tree column on the left, the subject `mind_graph` (`Admin::Shell::TreeSubjects`), with the Pages tree's width, divider, fold and drawer and their words in the list's ("Hide list", "Show list", "List width", "List ▾"), and the box is one column at every width (a view's bar, the legend's row, the canvas). The whole site's results replace the tree in the list's region: "Back to the list" first (tertiary small, which takes the focus), the heading "Whole site: “…”" (`text-sm font-semibold`), the groups headed as the tree's are (the chip and the label in `text-label` meta) but no tree items and with no hover, and links on the tree row's geometry (28px, the mark box, the title in `text-sm`, a page's path under it in `text-small` meta), hover sunken, the 2px ring at -2px; nothing found is one dim line, a failure `--cs-danger-ink` in a `role="alert"`. ## E4: the lists' rail

Stage 5b of E4 (plan `docs/superpowers/plans/2026-11-07-studio-e4-stage-5b.md`) gives a list screen a rail beside the list. The posts list's filters stand on it; what the list holds is in `docs/reference/editors-and-translation-pair.md`, "The posts list".

**`.admin-list-rail` is a third layout** (`content-spiel.tailwind.css`). It is `container: admin-list / inline-size` and docks in the one block `@container admin-list (min-width: 1200px)`: 1200px of the list's own width, the editors' and the dashboard's threshold, so a 1279px window, whose sidebar is a drawer, docks it and a 1280px one does not. It is neither the editors' grid nor the dashboard's: `.admin-rail-grid` serves several tabbed panels beside a canvas (`admin--ui--rail`'s docked state, the canvas's stacking contexts), and the dashboard's rules reach into `.admin-dashboard-panel`; a list has one panel and no canvas, so it takes the dashboard's grid and ground under a name of its own. **The rail is first in the document.** The grid holds, in document order, what stands above the list, the rail, then the list, at every width; only the grid places them and no script moves anything, so the focus goes heading row, bar, rail, list, and a choice made in a narrow window is seen above the list (`test/system/admin/posts_list_test.rb`: "the focus goes New post, search, the segments, the rail's Type, Tag and Translation, then the list, and a Type chosen from the keyboard keeps the focus on Type").

**One form, `display: contents`.** The posts list's bar and filter panel are one `form#posts-filters`: `FilterHelper#filter_form_options(url, bar: false)` gives the form the class `contents`, and the caller draws the bar itself with `FilterHelper::BAR_CLASS`. So the panel's `change` reaches the form's `admin--ui--auto-submit`, its focus is restored by id, the no-JS Filter button submits the panel's values too, and `contents` makes the bar and the panel two items of the grid. A `form=` attribute would leave the panel's events outside the form, where the controller listens. The form has no accessible name, so drawing it `contents` drops no landmark. `.admin-list-rail__rail` is therefore matched anywhere in the grid, never only as its child.

**The filter panel's two looks.** `.admin-filter-panel` is a fieldset. Below the threshold it is a wrapping row under the bar, each select under its visible label (`text-label text-meta`), its legend "Filters" for a screen reader only; docked it is a column on the rail's ground, one select under the other, under the legend. The docked legend is floated, so it is the column's first item inside the rail's padding, not the rendered legend the browser draws in the top border. The blank option is "All" (Type) or "Any" (Tag, Translation), since the label names the filter. The panel is a wrapper of wells, so its selects are wells and it resets the invalid edge as the others do, and they are the bar's 38px in both looks ("Control heights", below).

**The tag detail's two looks.** `.admin-tag-detail` is the Tags screen's rail, one tag's detail. Below the threshold it is a card above the list (`--cs-surface`, `--cs-shadow-1`, card radius) and takes no room while it holds only the empty line; docked, inside the one `@container admin-list` block, it is the rail's ground with the empty line shown again. With no tags (`#tags-list` holds the empty state) it is `display: none` at every width. The rail comes before the list in the document at both looks. A record's state in a list is drawn by `Admin::Ui::ListStateComponent` (the shared status chip, Live hidden, and the unpublished chip; it draws nothing for a live record without changes) in the posts table's Status cell and in the tag detail's post rows.

**The Notes screen's open threads.** `.admin-notes-threads` (`Admin::NotesScreen::OpenThreadsComponent`) is an information rail: it says something about the records and acts on nothing in the list, so it follows the list in the document where a filter or a detail rail stands before it, and the grid docks it in the second column from row 1 at 1200px of the screen's own width, with no script moving it. ## E4: working together

Stage 6 of E4 (plan `docs/superpowers/plans/2026-11-09-studio-e4-stage-6.md`) draws the people in CS Studio in one hue: who is here, who wrote, who is holding a block and how many notes wait.

## Shared components

**Shared components** (each has a Lookbook preview in `test/components/previews/admin/` and a test in `test/components/admin/`), and what each replaced:
- `Admin::Ui::StatusChipComponent` (Draft / Scheduled / Live chip, each with its word, Live and Draft with a glyph, and an `aria-label`; Live draws no chip in the page tree; the looks are under "Status chips and the people hue") replaced `StatusBadgeComponent`; `Admin::Ui::TranslationChipComponent` replaced `TranslationScreen::StateBadgeComponent`; `Admin::Ui::LanguageTabsComponent` replaced `LanguageSwitcherComponent`. Colour is never the only cue.
- `Admin::Ui::ContentTypeDotComponent` marks a content type with a dot (indexes 1–6 filled, 7–12 rings, then cycling) next to its name; the index is `colour_index` on `ContentModel::ContentTypeDefinition`, defaulted by `Registry#register` to the smallest unused one.
- `Admin::Ui::DialogComponent` / `Admin::Ui::ConfirmDialogComponent(destructive:)` and `Admin::DialogHelper#dialog_trigger` replaced the old confirm dialog and every inline `onclick`. The `admin--ui--dialog` controller lives on `<body>`: a `mousedown` handler (`remember`) records where a press began and a `click` handler (`backdrop`) closes only when it began *and* ended on the backdrop, so a text selection dragged out of a dialog doesn't close it. Beside it, `admin--shell--drawer` and `admin--shell--command-palette`, two more controllers live on `<body>` for every screen. `admin--shell--fragment-links` handles every same-page `#fragment` link in CS Studio — an error summary's links to its fields, Settings' in-page nav, the media panel's "See where it's used", a ⌘K row for a section of the screen that is showing: such a link never navigates (Turbo and the browser are both kept out), the focus is moved to the target by hand, no history entry is added, a link inside an open dialog whose target is outside it closes the dialog first, and a target that isn't there moves nothing and is named in the console; a link to the very URL that is showing (a footer's Cancel on a screen that cancels to itself, the current tab or tile) is followed as a `replace`, so a reload adds no second history entry. `admin--shell--file-drop-guard` refuses a file dropped anywhere that takes none, where the browser would navigate to the file; file drop zones, file inputs, anything `contenteditable` and the whole Media screen are left alone, and a drag that carries no files is never touched. Dialog forms and the media picker live once in the layout, outside `#content` (forms can't nest). There are no inline event handlers: `test/lib/inline_handlers_test.rb` fails on any `on…=` attribute inside a tag, whatever the event, in a view, a component, a helper or a script's markup, and on a tag helper handed an `on<event>:` key (there the name must be `on` plus a real DOM event, since Ruby has ordinary keywords like `only:`) — wire behaviour through `data-action`. That test is the whole enforcement. The app's CSP (`config/initializers/content_security_policy.rb`) sets only `frame-src` (self and youtube-nocookie.com), `object-src 'none'` and `base-uri 'self'`; there is no `script-src` and no nonce, so the browser itself refuses no script (a script CSP is a roadmap row). `Admin::Ui::DialogComponent`'s `hang: true` hangs a dialog from a fixed top edge instead of centring it, for one whose height changes while it is open (New page, New post; the media picker does the same through `.admin-media-picker`), so nothing moves under the pointer when its content arrives. A dialog whose content arrives after it opens keeps its frame: `hang:` keeps the top edge (the New page and New post dialogs), `steady:` the whole frame, for one whose footer button is aimed at (the publish dialog: 36rem high, 85vh at most, the body scrolling).
- `Admin::Ui::ButtonComponent` variants: `primary` (one per screen; a solid accent fill raised to `shadow-2`, hovered `accent-hover` and `shadow-3`, pressed 1px down), `secondary` (`bg-accent-tint text-accent` inside an edge, hovered to `--cs-accent-press` and `shadow-2`), `tertiary` (accent words, no fill, hovered to the `--cs-accent-press` fill and an underline, and no lift; small, it is underlined at rest, 3px under its words, and its line thickens to 2px under the pointer; `ghost` is no variant and raises `ArgumentError`; a dialog's Cancel is accent words; "Discard changes…", which throws work away, is `danger_text`, set at its call in `publishing_state_component.html.erb` (`test/components/admin/editor_screen/header_component_test.rb`: "Discard changes… throws work away, so it is the danger_text button")), `danger` (solid red with `text-on-danger`, hovered to `--cs-danger-hover` and `shadow-2`: a dialog's destructive confirm only) and `danger_text` (`bg-sunken text-danger-ink` inside an edge, hovered to `--cs-danger-press` and `shadow-2`: the trigger of a destructive action outside a dialog; red words on the violet tint would fight). **The edge** (the owner's decision, 2026-11-07): a secondary's tint and a danger text's sunken fill measure 1.00 to 1.26:1 on every ground, no shape at all on a rail, so both draw a 1px edge at rest everywhere, `border-field-line` regular (3.17:1 or better on the rail, the surface, the paper and the popover) and the variant's own ink small (`border-accent`, `border-danger`), where a 28px button has less fill to see; the other variants keep `border-transparent`. **The hover** is a stronger fill and a neutral lift and never accent around the button, because an accent ring, glow or shadow is what the focus ring is, and two buttons would look focused at once; the edge does not change on hover, and every hover stands under `@media (hover: hover)` (Tailwind's `hover:`), so a touch screen keeps no stuck hover. Each press fill steps 1.2:1 or more from its rest and keeps its words at 4.5:1 (`test/lib/admin_contrast_test.rb`: "a secondary's and a danger text's edge is 3:1 or better on every ground in both schemes, and a small one's is the variant's ink", "a hover fill moves 1.2:1 or more from its rest and keeps its words at 4.5:1"; `button_component_test.rb`: "secondary and danger_text draw their edge, small ones in the variant's ink", "no hover draws the accent outline or an accent shadow, and no hover changes the edge"; `test/lib/admin_design_rules_test.rb`: "a button's hover is under @media (hover: hover)"). The fill and the lift change over 120ms on `--cs-ease` (`transition-[background-color,box-shadow] duration-120 ease-(--cs-ease)`), at once under reduced motion (`motion-reduce:transition-none`), where the primary's press does not move either (`motion-reduce:not-disabled:active:translate-y-0`, as heavy as the press and later in the build, so it wins) and is told by its shadow going ("every variant drops its transition and the press's movement under reduced motion"). ## Tree

A tree of pages is one row, drawn once (`Admin::Ui::TreeItemComponent`, `app/components/admin/ui/tree_item_component.rb`; Design System card StudioTree). The Pages tree renders it; the mind graph's list builds the same row in `mind_graph/node_list.js` from its classes, which the view hands over as `data-tree-classes`, and from the tree's glyphs cloned from `Admin::MindGraphScreen::PartsComponent` (`tree-disclosure`, `tree-page-mark`, `tree-home-mark`), never copying a class (`test/lib/mind_graph_guards_test.rb`: "the graph's list writes no class of its own for a row: every row class is read from data-tree-classes", with `LIST_LAYOUT_LITERALS` naming what it lays out that is no row, and "every data-tree-classes key the graph reads is one of CLASSES"). A browser measures the two rows against each other: height, the step, the mark's box, the title's type, the selected look and each row's left edge from `#tree-column`, with the graph's checkbox at the Pages heading's disclosure (`test/system/admin/tree_item_parity_test.rb`: "the Pages tree and the mind graph's list draw one row"); it first shows that its comparison finds a 1px difference. **The graph's half.** `node_list.js` draws each node as a treeitem whose row is `classes.row` (`row_flat` for a post and a pill) holding `classes.disclosure` (the `tree-disclosure` part where a branch folds, else an empty box), `classes.mark` (the page glyph, the house for Home, a post's dot, a tag's square, a post type's canvas), `classes.title`, and `classes.trailing` with `classes.count`, shown at rest; a branch is `classes.children` with `role="group"`, so a level steps in as Pages' does; the selected node's row takes `classes.row_selected`. The `classes.<key>` it reads are `CLASSES`' keys ("every data-tree-classes key the graph reads is one of CLASSES", which also refuses a computed `classes[...]`). Its group headings are rows of the same geometry, the kind's icon chip in the mark box. The rows stand at Pages' x, inside the column's padding with no gutter of their own, and the lines that are no row at `px-1`, where a row's disclosure column starts; a cut title ends in an ellipsis, and the whole title is its tooltip and its item's name. The find's `noun: :nodes` is the graph's find. The nesting around a row (`<ul>` and `<li>` in Pages) is its screen's; the row, its parts and its look are the component's and the `.admin-tree` block of `content-spiel.tailwind.css`, which is one block (`test/lib/admin_design_rules_test.rb`: "the tree's rules are one block").

**The row and its slots.** From the left: the drag handle in the gutter (`handle`, outside the row's box), a 20px disclosure column, a 16px mark box (`mark`: the page glyph, the home glyph on the root), 8px, the title (`title`: the screen's link, wrapped in the title's box, clipped to it with an ellipsis), the state dot (`state`, 6px after the title), then the `trailings` in order (translation markers, presence, the child count; `renders_many :trailings`, the plural being ViewComponent's) and, last, the "+" (`with_add`: its name, its address and its hooks, never a class). A parent draws its disclosure, a button that says whether its branch is open (`aria-expanded`) and names the list it folds (`controls:`; a parent without one raises), a leaf keeps the column's empty box so the marks line up, and `flat:` draws neither. `CLASSES` is the one list of the block's class names (`tree`, `row`, `row_selected`, `row_context_only`, `row_flat`, `disclosure`, `mark`, `title`, `state`, `trailing`, `count`, `reveal`, `add`, `handle`, `children`, `drop_target`); a value is a class of the block and never a utility, and a screen hands the row no class of its own (`data:` with a `class` key is refused). The row's glyphs are `admin/shared/_tree_glyph`: 12px chevron, 14px page and home glyphs, all silent to a screen reader.

**Four lengths and a step**, on `:root` in `content-spiel.css` and written nowhere else: `--cs-tree-row` 28px, `--cs-tree-disclosure` 20px, `--cs-tree-mark` 16px and `--cs-tree-step` 20px. A level steps in by the children list's 13px margin, its 1px `--cs-line-strong` guide and 6px padding, which are the step (`admin_design_rules_test.rb`: "a tree's geometry is its four tokens, written once" holds that the three add up to the step and that no tree file sets an indent of its own). The guide is a hairline (`admin_contrast_test.rb`: "a tree's guide stays a hairline"); the disclosure, mark and count are 4.5:1 on the chrome and on sunken.

**A parent is never bolder.** The weight says nothing about a page's children; it says "this is open". The selected row is the only weight: a sunken ground, a 600 title, the mark in ink and a 3px inset accent bar (a selection, not a marker: "Accent" above). At rest it reveals only the markers (the translation markers and an open parent's count); the handle and the "+" show on it as on any row, by hover, by focus within and for a coarse pointer, and never by the selection ("no tree rule reveals the handle or the + from the selected row"). A context-only row is greyed text with no actions. A folded parent shows its child count at rest, since the count is the only sign of what is folded.

**One focus ring, on the focused control.** A row draws no outline of its own (`.admin-tree-row:has(:focus-visible)` draws nothing: "no tree row draws an outline from :has(:focus-visible)"); the disclosure, the title's link, the handle and the "+" each draw the shared 2px accent ring at an offset of -2px inside their own box. Never two rings at once; the selected row's inset bar may sit beside one (`test/system/admin/tree_test.rb`: "a focused control in a Pages row draws one ring, its own, and the row none").

**The match is the tint's use in a tree.** A find's match is a `<mark>` in the row's title: `.admin-tree mark`, the accent tint as the ground with the title's own ink (`color: inherit`), a rule of the tree block and nothing a screen writes ("the match's tint is the tree's own rule, with the title's ink"). It is not the tint-with-accent-words pair of `TINT_PAIR_ALLOWED` (it keeps ink), so the allowances of `TINT_PAIR_ALLOWED` (the secondary button, a chip, your own mention and the current module's row) are unchanged.

**Two semantics, each the screen's.** Pages keeps nested lists with a disclosure button on every parent and links for titles, and is never `role="tree"`: its rows are links and buttons that a Tab visits one by one, its drag and keyboard moves are on the handle, and an ARIA tree would ask for a roving focus and arrow keys that those controls already use (Left and Right nest and unnest a picked-up page). The mind graph's list is an APG tree (`ul#mind-graph-tree[role="tree"]`), one Tab stop with a roving `tabindex`, because its rows are choices of one thing and have no controls of their own: its group headings are items at the first level, never selected, and its disclosure is a part hidden from a screen reader, since the item says `aria-expanded` itself; the ring of a focused item is drawn on its own row (`.admin-tree [role="treeitem"]:focus-visible > .admin-tree-row`), and the item itself draws none, since it holds its children's group and a ring round it would round the whole branch (the one rule that takes a ring away, named in "no tree row draws an outline from :has(:focus-visible)"); there is no type-ahead, since the find is the way to a row by its name. Neither is "unified" into the other; the row looks the same and the markup around it does not.

**Folding and the open set.** Which branches are folded is the open set: the cookie `cs_tree_open`, read by `TreeOpenSet` (`app/values/tree_open_set.rb`) and written by `app/javascript/tree/open_set.js` alone ("the open set has one writer": under `app/`, `lib/` and `config/` nothing but `open_set.js` assigns `document.cookie` or names `cs_tree_open` in a script, and in Ruby and ERB only `TreeOpenSet` names the cookie and nothing writes or deletes it; the controllers call `setOpen`, `setFolded` and `forgetFolds`). The format, the limits and the one rule for open or folded (the path to the selected page, then a folded entry, then the root, then an opened entry) are in `TreeOpenSet`'s comment and `docs/reference/cs-studio-shell-and-dashboard.md`, "Folding, the open set and find"; the open set is never written on `<html>`, where the tree's width and fold have their own two writers (`CLAUDE.md`, "Page tree's width"). **The path to the open page is a view state**: it is open whatever the cookie says, the scripts forget the folds on it as a page is opened, and a fold or an open on it is stored against the default it has there (`data-tree-on-path`). A disclosure's turn is 120ms, none under reduced motion. A drag over a folded parent opens it after 600ms with the pointer resting in the middle half of its row; the opened parent is marked with `CLASSES[:drop_target]` (sunken ground and a 1.5px `--cs-field-line` inset edge).

**Find** (`Admin::Ui::TreeFindComponent`, card StudioTree). A search field with the "/" hint, Clear, and a status line (`role="status"`, `aria-live="polite"`) under it. It narrows the drawn tree to the matches and their ancestors, marks the matched text, opens the branches that hold a match without writing the open set, and gives the person's folds back when the field empties. The count is said once, 300ms after the last keystroke, and only when it changed. While the tree is narrowed it is not a place to move pages: dragging is off, the handles are not drawn, the keyboard pick-up is refused, and the line says "Clear the search to move pages". "/" focuses the field except from a text-entry control; Escape clears a non-empty field and is left to the drawer in an empty one. **Where find would move.** It runs on the client over the rows the tree drew, because the tree draws every readable page. Above about 2,000 pages, the cost of drawing the tree at all, a find would ask the server instead: a read-scoped endpoint on `Admin::TreeController`, trashed pages hidden, answering ids and their ancestors. It is not built, because no site is near that size, and no constant holds the figure.

**The column.** From 1024px the tree's column scrolls on its own, window-high and sticky under the top bar, so the window does not move with a long tree; a selected row out of view is brought in by the column's own `scrollTop`, never by `scrollIntoView` (`docs/reference/cs-studio-shell-and-dashboard.md`).

## Component contract

A component that is shared declares what it promises, once, on its class, and tests read the declaration against the code. Nothing at run time asks for it (`test/lib/admin_i18n_test.rb`: "nothing under app/ reads a component's contract at run time"): a component's markup, classes and methods are what they were, and the declaration is a statement a test can fail.

**Two modules over one declaration.** `ComponentContract` (`app/components/component_contract.rb`) is the part both sides share: `accessibility:` (one sentence: the role, the name and the keyboard), `motion:` (`:none`, or `:reduced`: it moves, and holds still under `prefers-reduced-motion`; it describes everything the component renders, its children included, so a component that draws a Button's classes is `:reduced`), `content_edges:` (a list of `long short none many missing`), `widths:` (one of `:from_container`, `:fluid`, `:fixed_width`), `interface:` (the Symbols a caller hands it) and `limits:` (at least one sentence of what it does not do). A declaration it cannot read is refused when the class loads, naming the class and the keyword, and a second declaration raises. `Admin::Ui::Contract` (`app/components/admin/ui/contract.rb`) is what a shared CS Studio component includes; it adds `states:`, `script_states:`, `keys:`, `slots:`, `controller:` and `keyboard:`. `Blocks::Contract` (`app/components/blocks/contract.rb`) is a visitor's page's: it adds `words:` only ("The public side", below). The two share only the common declaration and a class includes one of them, never both (`test/values/theme/component_contract_test.rb`: "the Studio and the public contract share only the common declaration"). The reason for two modules is the Design System's: a Studio component and a component a theme may replace are held to different things (tokens, words, who may replace the template, caching), and a base class would make one carry the other's keywords.

No word of a declaration may be a Tailwind utility, because the stylesheets scan a component's file as they scan any source: a sentence saying "container" or "filter" adds a rule to a built stylesheet. This is why `widths:` is `:from_container`, `:fluid` or `:fixed_width` and not `:container` or `:fixed`. `test/components/component_contract_test.rb`: "a declaration adds no utility to a stylesheet: each word Tailwind builds from it is its file's already" runs Tailwind on the text of every `contract(...)` call and fails for a word it builds that the file's own code and templates do not hold; "the utility guard can fail: a declaration's container, hidden and filter are built and named" holds the guard itself. No declaration changes the public stylesheet, and CS Studio's gains only Button's reduced-motion press reset (`motion-reduce:not-disabled:active:translate-y-0`).

**`Admin::Ui::Contract`'s keywords.**
- `states:` the states a static render draws. Each one but the pointer and keyboard ones (`Admin::Ui::Contract::STATES_NOT_PREVIEWED`: `hover focus pressed`) has a preview example of the same name.
- `script_states:` a state only a script reaches (a dialog's `open`, a menu's open list) or one a static render draws invisibly (a tooltip's hidden bubble), each mapped to the `[file, test name]` of the browser test that holds it. A state is in `states:` or in `script_states:`, never both (refused when the class loads), and one in `script_states:` has no preview example, because a render shows nothing of it. A state no browser test holds (a Toast's dismiss and timeout, a FileDrop's dragging) is in neither and is said in the component's `limits:`.
- `keys:` the key paths it owns under `admin.components.ui.<name>`, a plural being one.
- `slots:` its ViewComponent slots.
- `controller:` the Stimulus identifier the component attaches itself in its own markup (`data-controller` or a `controller:` data key), or nil. A component that is only a target or an action of a controller someone else attaches (RailTab, SaveBar, Tooltip's bubble) declares nil and says whose controller it serves in its `limits:`.
- `keyboard:` the `[file, test name]` of its keyboard browser test, or nil.

**The shared test** (`test/components/admin/ui/contract_test.rb`, on `UiContract` in `test/support/ui_contract.rb`) holds every `Admin::Ui` component, found from the files, so a new one is in it the day its file is written: "every Admin::Ui component includes the contract and declares it"; "the contract's interface is the component's keywords"; "the contract's slots are the component's slots"; "the contract's keys are the leaves the component owns in ui.en.yml"; "the contract's controller exists and is named in the component's own source" (the check reads the component's Ruby and templates around the declaration and comments, so a controller named only in the declaration fails); "a script-held state names a browser test that is there"; "the contract can fail". The declaration's sentences are not English copy to `admin_i18n_test.rb`, which skips a `contract(...)` call in the file of a class that declares one.

**The three part guards** (`test/lib/component_parts_test.rb`) hold what a component has beside its declaration: "every Admin::Ui component has a component test" (`test/components/admin/ui/<name>_test.rb`); "every Admin::Ui component's preview has an example for each previewable state it declares" (`test/components/previews/admin/ui/`, an example per `states:` entry but the pointer and keyboard ones, and a preview at all); "every Admin::Ui component has a Design System entry, or is listed with the reason it has none". "the entries' lists name only components and entries" fails on a stale entry, and "each part guard can fail" runs every matcher over samples. A matcher that lists its list's stale names is the way each list only shrinks.

**The Design System entries are a copy.** `test/support/design_system_entries.rb` is a hand copy of the Design System artifact's list of cards (`ENTRIES`, the folder names of `project/components/`) with the artifact's version it was read from (`VERSION`; it is a stamp of the copy, and the next person to read the artifact bumps it). A component's card is its own name less `Component`, or the card named in `COVERED_BY` whose "Code" section names it (`ChannelChip` and `StatusChip` are drawn by `Badge`), or the component is in `NOT_YET` with the reason it has no card. The design agent changes the artifact and its changes reach this file by hand, as the theme contract's reach `test/support/contract_ledger.rb`: a card added, renamed or removed there is an edit here. A component with no card yet (`ActorAvatar`, `PrefixInput`, `Slot`, `UserName`) is in `NOT_YET`, and the design agent draws its entry; a component that appears in several cards is mapped to the one that describes it, a choice the design agent confirms (`TimeAgo` and `ContentTypeDot` to `StudioListTable`, `LanguageTabs` to `StudioTranslationPair`).

**`MADE_BEFORE_CONTRACT`, `KEYBOARD_NOT_YET` and the keyboard rule.** A shared component made after the contract names its keyboard browser test in `keyboard:` (the test begins on `visit_screen` or `visit_editor`), and the test must be there ("a shared component made after the contract names its keyboard browser test, and the test is there"). `UiContract::MADE_BEFORE_CONTRACT` (40 names) is the components that existed before it and may declare `keyboard: nil`; a component leaves the list when it declares its keyboard test (Menu, RailTabs, ChipInput and Tooltip name theirs) and nothing is ever added. `UiContract::KEYBOARD_NOT_YET` (empty) is a new component whose keyboard test comes in a later task of the same pull request, mapped to the reason, and is empty again at merge. Both can only shrink: `LIST_LIMITS` in the guard holds their sizes, lowered by hand and never raised ("the made-before and keyboard not-yet lists never grow"), and "the keyboard not-yet list names only components that declare no keyboard test" and "the made-before list names only components" fail on a name that matches nothing or has since declared its test.

**A component that more than one screen uses moves to `ui/` when a stage touches it.** A component used by more than one screen that a stage touches moves to `app/components/admin/ui/` and takes the full `Admin::Ui::Contract`: its states with previews, its keys, a Design System entry, and a keyboard browser test, or the test that holds that the keyboard passes over it when it takes no focus (as `StateChipComponent` does). Being moved, it is not on `MADE_BEFORE_CONTRACT`. A feature's slot entry stays in the feature's folder and renders the shared part: the entry keeps its name, its loader and its words (so a core screen still draws the slot and never names the feature, `docs/reference/slots.md`), and the shared look moves, knowing no feature and told only what it draws. Stage 6 moved three. `Admin::Ui::NoteMarkerComponent` is the note bubble that `NotesScreen::RowPillComponent` (the lists' pills), the media tile and Waiting for you's row draw; `Admin::Ui::PresenceMarkerComponent` is the stack that `PresenceScreen::RowMarkerComponent` loads and words; `Admin::Ui::BlockIconComponent` is a block type's chip, which the editor's cards and the Notes screen's rows both draw (`place: :row` is the row's). The block's own button (`NotesScreen::MarkerComponent`) and the holder's avatar stay with the editor, whose only users they are, and share only the stylesheet's look and `AvatarComponent`. Whether a component has a second user is a judgement at review, and nothing finds a one-screen component that a second screen has begun to draw.

**What a static render and a preview cannot show.** `ConfirmDialogComponent` takes `open_on_load:` and passes it to the dialog it draws (a closed dialog has no `rest` to preview, and neither has Dialog itself, whose `open_on_load` is the same), so ConfirmDialog's `rest` and `destructive` examples and Dialog's `rest` are marked to open as the page appears. They open only where the admin's script runs: the Lookbook layout is the public one and loads `site.js`, not `admin--ui--dialog`, so in Lookbook those previews show a closed dialog. They are drawn and rendered by `previews_test`, which holds the markup, and a person opens one from the console. A Tooltip's bubble is a `script_state` (it is hidden in a render), and RailPanel's `docked_only` is a static state shown by a wide preview, since the docking is a container query.

**The public side.** A component a visitor's page is drawn with (`app/components/blocks/`, `app/components/posts/`, a gem's block type) includes `Blocks::Contract`: the common declaration and `words:`, the `public.*` keys the component's own Ruby and default template read, a read with an interpolated key declared as a prefix and `*` (`public.blocks.note.kinds.*`). Its `interface:` is its line of `Theme::Contract.components`, the names a template may call, and the declaration restates it, never widens it. What a theme sees does not change, and `Theme::Contract` is untouched. It is the theming reference's: "Block and post templates: `Theme#component_for`" (`docs/reference/theming.md`).

**Review checklist** (what a test cannot hold; the Design System's "Component contract" entry, `FoundationComponentContract`):
- One primary button per area.
- A state is told by more than colour: a word, a shape or a mark beside it.
- Long German text and a phone width were looked at, not assumed.
- The focus order matches the visual order.
- A live announcement says what changed once, not on every keystroke.
- Reduced motion was tried.
- Whatever the script writes into the page is taken back at Turbo's snapshot, and Back shows no stale state.
- The entry's "can't" list is honest: nothing the component half-does is listed as a "can".
- A design question the spec does not settle went to the owner, not decided at review.

**What the contract found and left, as limits.** A declaration is true or the test fails, so a gap is said as a limit. In CS Studio the words that are literals in a component and not keys: `ChannelChip` ("MCP", "Channel: …"), `FileDrop` ("Drop an image here or", "Choose file"), `PasswordField` (and its script), `SystemCheckRow` ("Copy", "Copy command for", "Learn more →"; "Copied" in its clipboard script; OK and Warning are keys), `ThemeSwitch` ("Theme", "Light", "Dark", "Auto"), `UserName` ("a deleted user", "System") and `WordDiff` ("Removed: ", "Added: "). A Toast's dismiss and timeout, and FileDrop's `dragging`, are held by no browser test. Each is a stage's fix, tagged in the Design System entry's "Gaps".

## Form placement

**Control heights.** Controls in one row share one height: forms are 42px, a filter bar and a list's filter panel are 38px, set by the bar and the panel and never by a control. `Admin::FilterHelper#filter_form_options` gives every filter form `admin-filter-bar` (the posts list, Media and its picker, the audit log, Translations), and `.admin-filter-bar` in `content-spiel.tailwind.css` sets `min-height: var(--cs-control-compact)` (`--cs-control-compact: 2.375rem`, written once in `content-spiel.css`, 38px at a root font size of 16px) with `padding-block: 0` on its inputs, selects, "Clear" link, buttons and the audit log's subject chip, and two pixels less on a segment inside its group's 1px frame. A list's filter panel (`.admin-filter-panel`, "E4: the lists' rail") is part of its bar's form, so `.admin-filter-panel select` takes the same minimum in both of the panel's looks, docked in the rail or a row under the bar. It is a minimum, never a height: Media's segments wrap in a narrow window and the group grows with them (the posts list's group is `flex-wrap` too), where a group height would clip the second row. The rule is unlayered, like `.cs-select`, so it beats the `py-*` written beside a control (which is dead inside a bar); text sizes (16px and 14px) and focus rings are untouched, and a segmented control outside a bar (a Trash tab, a field's segments) stays 34px. The filter bar is CS Studio's only: the public stylesheet imports neither the token nor the rule. `test/system/admin/filter_bar_test.rb` measures every control of the bar at 38px on Posts (the bar and the filter panel measured as one form: "the posts list's bar and its filter panel: search, segments, Clear and the three selects are one height"), Media, the media picker, the audit log (with its subject chip and with Custom's dates) and Translations (its segments and "Clear", which is a link in the form like the others and submits nothing), and that a wrapped segment row shows every segment inside its frame; `test/lib/admin_design_rules_test.rb` holds the token to one place and the panel's selects to it ("the filter bar's height is a token written once, and the bar sets it as a minimum, never a group height").

**Form placement.** A form is centred only when it is the whole screen (sign-in, password reset, the setup wizard) or sits in a dialog; inside the shell every form starts at the left edge of the content area, under the page heading, however narrow it is. Width is capped, not position: about 420px for single fields, 560px for a simple form, up to 880–1000px for a form with grids or a matrix. The editors' and Settings' form column is the token `--cs-form-max` (760px) — the post form, the page settings, the block list and Settings' cards, left-aligned — and an editor's translation tab where its rail does not dock is `--cs-form-max-pair` (1144px), both read through `.admin-form-column` (`Admin::EditorScreen::FormColumn.classes`), a class on the elements that are there; where an editor's rail docks, on either tab, the blocks column takes what the rail leaves, up to `--cs-content-max` for the whole and centred past it, and its fields of running text keep `--cs-text-measure` ("E4: the right rail"). Centring past the cap is the docked compositions' alone, written in their docked rules: an undocked screen (Users, Trash, Audit, a form at `--cs-form-max`, an editor below 1200px) stays at the left. The save bar floats at the foot of the form's column: sticky at `--cs-sp-3` above the window's edge over the fields while a long form scrolls, and under them at the form's end, always at elevation 3 on the popover's ground, so it has no stuck state and no observer ("E4: Settings and the wizard"); a card's own footer (`contained: true`) stands inside the card and does not stick. The reference card's summary is an `.admin-disclosure` whose triangle shows only where the card is stacked. The 403 and 404 messages are the only centred things inside the shell, and `test/lib/admin_design_rules_test.rb` fails on any other `mx-auto` under `app/views/admin`, `app/components/admin` or `app/components/media`.

## Theme

**Theme.** Three-way: Light, Dark, Auto. `Admin::Ui::ThemeSwitchComponent` writes the choice to `localStorage["cs-theme"]` and the `theme_controller.js` sets `<html data-theme data-theme-choice>` — `data-theme` is the resolved light/dark the tokens switch on, `data-theme-choice` is what the switch marks as chosen — before first paint. The public site's footer keeps its own two-state toggle (`layouts/public/_theme_toggle.html.erb`); there is no shared toggle partial any more. A change after first paint cross-fades ("E4: the dashboard", "The theme fade").

**Screen slots.** A screen that a feature draws in, but must not name, draws `Admin::Ui::SlotComponent.new(name:, record:, viewer:, **context)` at the place, and the feature registers a component for the name in `config/initializers/admin_slots.rb` (`Admin::Slots`, in `app/components/admin/slots.rb`: it holds component classes, so it is not a model). The names are `Admin::Slots::NAMES`: `editor.header.people` (first in the editors' action row) and `editor.header.actions` (before Preview), `media.panel.header` (the panel's file-name row, between the name and the "×") and `media.panel.sections` (below "Used on"), `tree.row.markers`, `posts.row.markers` `posts.row.title` (the posts list's title line, inside the row's link, so nothing registered there may be interactive) and `editor.block.markers` (a block card's header and a section's tile: the holder's avatar on a tile, then the notes marker). A slot component is built `new(record:, viewer:, data:, **context)`; `data` is what a list slot's loader answered for that row (a loader is called once per render with every row), nil for a single-record slot, whose component asks its own question; `context` is the host's `locale:` and `url_options:` and, for the editors, whatever the view hands through `slot_context:` because it has already read it. `render?` decides whether it draws, and a slot with nothing registered draws nothing, not even a wrapper. The host does not say the feature's name (`test/lib/notes_boundary_test.rb` keeps the header and the media panel clear of the word, comments included, and lists the places that still name notes directly with the trigger that would make each a slot). A registration may carry options (`register(name, component, loader: nil, **options)`, e.g. `size: :panel`, `joined: true`), which are merged after the host's context and so win, and the names `record`, `viewer`, `data` and `component` are refused as options; **every slot component must accept `**`**, because a host may hand through more than one feature needs. A test that changes a slot does it through `Admin::Slots.with`, which puts the registry back. Presence is the second user of the seam, with the registry of record kinds and the live core; `docs/reference/presence.md`, "The seams", says what each is, and what was left out of it with the trigger that would extract it. The posts table's Notes column *header* stays in the table, a named exception in the boundary test (a column mechanism for lists is more than two features justify).

**The shared tooltip** (`Admin::Ui::TooltipComponent`, `admin--ui--tooltip`) is a short text under its host while the pointer is on it (after 300ms) or the keyboard's focus is (at once), the inverted toast's look: `bg-ink text-paper`, `rounded-cs`, 12px, at most 240px wide, no shadow, no arrow, 6px below its host and centred unless that would cross an edge of the window or of the box that clips it, in which case it lines up with the host's edge; Escape and a press on the host dismiss it, one shows at a time, and a host whose button has its list open shows none. The bubble is hidden from a screen reader, so a focusable host carries the same words as its `aria-label`; the one exception is the page tree's divider, a `separator` whose name is "Page tree width" and whose value is the width, so a screen reader hears the figure from the role and not the tooltip's sentence, and gets no hint of the arrow keys beyond what a window splitter implies. A host that is much taller than a control (the page tree's divider, as tall as the page) hangs the bubble from a small sticky box inside it (`.admin-tree-divider__tip`), since "under the host" would be below the last row; and a host whose text changes writes the bubble's text itself, from the same key the server rendered. It is new with presence; CS Studio's existing icon buttons still use `title`, which a keyboard does not reach, and move to it in a sweep of their own. **The menu component's list panel** (`Admin::Ui::MenuComponent`, `list: true, list_label:`) is a panel that lists and offers nothing to pick: a `role="list"` of plain-text rows that takes the focus when its button is pressed, closes with Escape (the focus goes back to the button) and when neither pointer nor focus is on it, and may be shown by hovering something inside the button (`reveal`); `panel_id:` gives the panel an id and the button its `aria-controls`.

## Tags

**Tags** (`Admin::TagsController`, `admin/tags/index`): a card table of names that are inputs, text until hovered or focused, autosaving a rename through `Tags::Rename`. Each row has the name, a post count linking to the posts list filtered by that tag (kept posts the viewer may read; "—" without `posts.read`), under the count a usage bar, and a Details link. There is no ⋯ menu. **The usage bar** (`.admin-tag-usage`, 4px, on the paper ground, pill radius, with `.admin-tag-usage__bar` filled by `bg-tag-usage`) is the row's readable count over the largest on the screen (`--usage`, 0 to 1, `TagsHelper#tag_usage`), drawn only under `posts.read`, `aria-hidden`: the count beside it is what is read. `--cs-tag-usage` aliases the structure hue (`--cs-ic-structure`), the hue of a tag in the mind graph, and is measured on surface and paper in both schemes (`test/lib/admin_contrast_test.rb`). **Details** (`a#tag-<id>-details`, tertiary, small, `data-turbo-frame="tag-detail"`, `data-turbo-prefetch="false"`, `aria-label` "Details of “name”") opens `GET <admin>/tags/:id` into the rail's frame `#tag-detail`. The route answers only that frame (a request that is not the frame's is a 303 to the list; an unknown id is a 404), and `show` is a route line of its own, `get "tags/:id"` with `id: /\d+/`, because a constraint on the whole resource would reach the `__ID__` URL templates the dialogs fill in. **The detail** (`Admin::TagsScreen::DetailComponent`, root `div#tag-detail-<id>`) is the tag's name as the heading (`h2`, focusable, `overflow-wrap: anywhere`), its count, its eight most recently changed readable kept posts (`Posts::List#rows(limit: 8)`, each with `Admin::Ui::ListStateComponent`), "Show all" when there are more, and the two triggers: Merge into… `secondary` and Delete tag… `danger_text`. Tags draws no primary outside its dialogs (`test/integration/admin/tags_test.rb`: "the Tags screen draws no primary button outside its dialogs"). Close is the last child, so the focus order ends on it, and is drawn at the top right. Without `posts.read` the detail has no count and no post and the dialogs read the neutral sentences. **The frame is redrawn by stream.** A saved rename answers `replace tag-detail-<id>` with the detail, the row's Details link (`_details_link`, `tag-<id>-details`) and the name's screen-reader label (`_name_label`, `tag-<id>-name-label`), and never the input; a delete answers the empty detail (`#tag-detail-empty`, `EmptyDetailComponent`) and, for the last tag, replaces `#tags-list` with `_empty`, the empty state the screen also draws. `admin--tags--detail` marks the chosen row (`aria-current`), clears it on Close and returns the focus to the row's link by its id; it never calls `reload()`. Its `hold` action pauses a GET into the frame while the queue is busy (a write queued or in flight, or a form's edit still to send) and resumes it once `quiet()` (`saving/queue`) resolves, so a Details pressed during its tag's rename draws the new name. With no tags the rail takes no room at any width. Its two looks are in "E4: the lists' rail". There is one Merge and one Delete dialog for the whole list, outside every form, filled from the pressed tag (`admin--tags--dialogs`; the dialogs read the name from the row's input, because a trigger's `data-tag-*` are redrawn only when the rename's answer arrives); their sentences count *every* post carrying the tag, trashed ones included, because that is what the action touches and what the event records — and when that is more than the Posts column beside it shows, the sentence says the others are in the trash or out of the viewer's reach, never how many of each. `Tags::Merge.call(source, into:)` (`tags.manage`) runs in one transaction with both tag rows locked in id order: every post carrying the source gets the target (no duplicate join rows), the carriers are touched (so an open post form is refused as stale), every listing block whose `tag` setting names the source — on trashed pages too — is repointed (re-read under a row lock first, so a setting another editor saved in between survives) and its page touched, the source is deleted, and one `tag.merged` event is recorded on the target (metadata `merged`, `posts`); after the commit `PublicSite::Paths.refresh` is handed the pages whose list blocks refer to either tag and the posts that carry either (`Tags::Listings#pages_listing`), since a post's canonical page depends on tags only through those blocks. No undo, no per-post event. `Tags::Listings` holds what Rename, Destroy and Merge share. A tag in use is never refused on delete: `Tags::Destroy` removes it from every post that carries it (touching them, so an open post form is refused as stale) and records `tag.deleted`. A Post list block that filters on a tag holds the tag's *name* as a plain string in its settings, which neither `Tags::Rename` nor `Tags::Destroy` rewrites, so after a rename or a delete such a block lists nothing until its Tag field is edited; only Merge repoints the blocks. None of the three sends a live-editing signal: the event names the tag, not the posts (`docs/reference/live-editing.md`, "What is not built").

## Rules a change can break silently

Moved word for word from `CLAUDE.md`, where "above" and "below" meant the list these rules stood in: a rule named that way may now be in another reference file. Each names the test that guards it; a rule or a part of one with no guard is also said in `CLAUDE.md`.

- No inline event handlers in a view, a component, a helper or a script's markup: wire behaviour through `data-action` (`test/lib/inline_handlers_test.rb`).
