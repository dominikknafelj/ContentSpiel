## What a theme is

A folder in the site's own repository, named by one variable, `THEME_PATH`. Whatever the folder does not hold comes from the default theme, which is the CMS's own templates where Rails and ViewComponent put them (`app/views`, beside each component) and the styles under `app/assets/tailwind/themes/default/`.

```
<theme>/
  views/layouts/public/   _frame, _head, _title, _icons, _header, _footer, _language_switcher, _theme_toggle
  views/pages/            show, not_found
  views/theme/            the theme's own partials, any names, at any depth: render "theme/name"
  components/             a contract component's template, by the component's path:
                          components/blocks/image_component.html.erb
  assets/stylesheets/theme.css
  assets/images/          png jpg jpeg gif svg webp avif ico
  assets/fonts/           woff2 woff ttf otf
  javascript/controllers/ **/*_controller.js
```

At the top the folder holds those four folders and nothing else; dot files, dot folders (`.git`, `.github`) and a `README` or `README.<anything>` are passed over there (`README.md`; a `README-old.md` is a stranger and stops the boot). An empty folder is a theme that replaces nothing.

**No Ruby** (decision 8): no helper, no component class, no initializer, no `lib`. What a template needs to compute is a CMS helper. Autoloading a theme's `lib/` was rejected because every internal class of the CMS would become something a theme can depend on. "No Ruby" is a statement about what the CMS promises to keep working, not a sandbox: a theme's templates are ERB with the application's whole reach, and a theme is **trusted exactly as the deployment is**. It comes only from the image, and is never uploaded, edited in CS Studio or read from the database.

**A theme brings no block types and no settings** (decision 5): a block type is data, and a switched theme could leave blocks nothing renders.

## THEME_PATH

`ThemeFolder` (`lib/theme_folder.rb`) is plain Ruby with nothing of Rails in it, required by `config/application.rb` itself as `site_address` is, because the boot's initializer and `config/importmap.rb` read it before any application class is loaded. `ThemeFolder.current` is `from_env(ENV)`, memoised for the life of the process (the file is not reloaded in development: an edit of it needs a restart). A blank value is the default theme. A relative value is relative to the directory the process was started in.

**The test environment ignores the variable** (`from_env` answers the default folder when `RAILS_ENV` is `test`), and `test/test_helper.rb` deletes it before the application loads, so a developer's shell never changes a test run and a child process a test starts gets the theme the test names. See "In tests".

Everything that must agree about which theme draws the site starts at `ThemeFolder.current`: the view path, the component templates, the stylesheet's build, the asset path, the import map, the ETag, the boot line and System status. Nothing else reads the variable (`lib/tasks/theme.rake` reads it through `from_env`).

A folder answers `configured?`, `path`, `name` (the base name), `files` (every file, relative, sorted; walked, not globbed), `templates` (the `.erb` files under `views/` and `components/`), `hidden_templates`, `fingerprint`, `glance` (names, sizes and times, no file read), `read(relative)`, `stylesheet`, `controllers_path`, `asset_paths`, `pins` and `built?(root)`. Nothing is memoised but `current`: `files` and `fingerprint` read the disk each time, so a development reload sees the folder as it is now, and `Theme` keeps the fingerprint it was loaded with.

### The fingerprint

SHA-256 over the relative path and the content of every file, in order, each path and each content closed with a NUL (so bytes cannot move from one file's end into the next file's name and keep the digest), read file by file through `Digest#file` so a font is never held in memory whole. Without a folder it is the word `default`. Two folders with the same files have the same fingerprint wherever they are, which is why the fingerprint computed on a laptop equals the stamp inside the image. It is used in three places: the public ETag, the stylesheet's stamp, and (its first eight characters) the boot line and System status.

### The folder is checked in two places

Because the contract is application code and the folder is read before any is loaded.

1. **`ThemeFolder.new`, while the application is configured** (the `content_spiel.host_announcement` initializer reads `ThemeFolder.current` in every environment). It refuses, with `ThemeFolder::Invalid`: a path that is no directory; anything at the top that is not one of the four folders (every such entry in one refusal, a line each); a file or folder that cannot be read (never a bare `Errno::EACCES` from somewhere in the boot: `Dir.glob` would have skipped an unreadable folder in silence and the site would have been drawn without the templates in it); a link whose target is outside the folder, a link to nothing, and a link to a folder it is itself in (a theme reaches a container as one copied folder and must be whole; a link that stays inside is the file it names); and a dot directory below the top (what is in `views/theme/.drafts/` would be outside the check and the fingerprint and still be there to render). The whole folder is walked once here, so these stop the boot where the variable is read and not at the first question somebody asks later. Unlike `SiteAddress`, the message repeats the value: it is a path, and the path is what the person has to go and look at.
2. **`Theme.load`, last in the `to_prepare` of `config/initializers/types.rb`**, after the types it is checked against (the contract's block lines are read from them), whose first run is the boot. It runs `Theme::Check.problems(folder)` at its plain depth and raises `ThemeFolder::Invalid` with every problem, one line each. This is the check against `Theme::Contract` ("Checking a folder", below).

A folder problem (1) stops the boot before the boot's lines are printed; a contract problem (2) after them.

### What the boot says

One line, logged at info in production beside the address's lines and in development too (where a theme is written), never in test, by `ThemeFolder.announcement`:

- `[ContentSpiel] Theme: the default theme (THEME_PATH is not set)`
- `[ContentSpiel] Theme: /rails/site-theme (14 templates, fingerprint 3fa9c1d2)`
- `[ContentSpiel] Theme: /rails/site-theme holds no file of a theme and replaces nothing: the default theme draws the site (fingerprint 3fa9c1d2)`

With `RAILS_LOG_LEVEL=warn` none is printed. The refusals are in `docs/reference/hosting.md` ("The theme"), word for word.

### System status

`Setup::SystemCheck` has a "Theme" row after the address and HTTPS (`theme:` defaults to `Theme.current`, `stylesheet_probe:` to `Setup::SystemCheck.stylesheet_probe(theme)`, which reads the build's stamp: one small file). It names the folder's **base name, never its path**, the number of templates and eight characters of the fingerprint: the page is shown to anyone who may view it, and where a server keeps its files is nobody's business there. The probe has three answers, and the row a sentence for each:

- **true** (the stamp is the theme's fingerprint): OK, "The theme “site-theme” draws the site (14 templates, fingerprint 3fa9c1d2)." or "The default theme draws the site (THEME_PATH is not set)."
- **false** (the stamp is another theme's, or an earlier state's of this one): a warning that the site is drawn with the wrong styles. In production it says to build the site's image again and carries no command (the boot already refuses such a stylesheet, so it is seen only in a process started with `SECRET_KEY_BASE_DUMMY`). Everywhere else nothing refuses, so this row is the one place that says it, and it names the usual cause: a test run builds the default theme's stylesheet into the same place. It carries the command `bin/rails tailwindcss:build` (`Setup::SystemCheck::STYLESHEET_COMMAND`, a fixed string).
- **nil** (no stamp at all): "has not been built, or its last build failed", with the same command outside production. Nothing "was built for another theme" in a fresh checkout or after a failed build.

A probe that raises is the "false" warning and its message is never shown.

**A theme refused on a development reload** (below) is asked first, before the probe, and is a warning of its own: "The theme folder was refused when it was last read, and the public site answers with the reason until the folder is corrected. bin/rails theme:check says what is wrong with it." Such a theme has no path (it brings nothing), so without that branch the row said "The default theme draws the site (THEME_PATH is not set)", OK, while every public page raised. Neither the folder's path nor the refusal's words are shown: the refusal names the server's path.

`test/models/setup/system_check_test.rb` ("without a theme folder the row says the default theme draws the site", "with a theme folder the row names it, its templates and the start of its fingerprint, and not its path", "in production a stylesheet built for another theme is a warning that says to build again", "outside production a stylesheet built for another theme is a warning with the command that builds it", "with no stamp at all the row says the stylesheet was not built or its build failed, for either theme, with the command", "a probe that raises is a stylesheet that was not built for the theme, and never a path", "a theme that was refused when it was last read is a warning that says so, and never the folder's path or the reason's words"); `test/integration/admin/system_status_test.rb` ("the theme row names the theme that draws the site and no path of the server, and warns when the stylesheet is another theme's").

## `Theme`, the runtime side

`Theme` (`app/values/theme.rb`) is what the application asks. `Theme.current` is built in `to_prepare`, as every registry is, and answers `configured?`, `path`, `name`, `fingerprint`, `template_count`, `views_path`, `views_directory`, `component_for(definition, role)`, `template_for(component)` and `refusal`. Without a folder every question is answered with the CMS's own.

- **`Theme.load(folder)` is the one door** from a folder to a theme: it checks. `Theme.new(path:)` checks nothing, has the fingerprint `default` and counts no templates, and nothing in the application calls it for a folder (`test/lib/theme_guards_test.rb`: "the application makes a theme of a folder through Theme.load only, so no folder goes unchecked").
- **`Theme.prepare(folder, reload:)` is what the initializer calls.** At boot it is `load` and raises, and the application does not start. **On a development reload it does not raise.** The theme is prepared last in the types' block (`config/initializers/types.rb`), after the types it is checked against, and an exception in a reload's prepare chain still stops the chain where it is raised: a block after it would not run, the reloader would count the reload as done, and `Theme.current` would stay the Theme built before the reload, over the classes the reload threw away. (While the theme had a block of its own that ran before the types', the registries were such a block and stayed empty.) So a refusal is kept: the answer is a theme that brings nothing and carries `refusal`, the initializer logs it at error (`[ContentSpiel] ` and the check's message), and `PublicPageRendering#look_in_the_theme_first` raises it on every public and preview request until a reload finds the folder sound. CS Studio is untouched. Whatever else the check raises on a reload, a fault of its own included, is kept the same way, as a refusal that says what was raised (`StandardError`; at boot it is raised as it is: "In development"). A registration of the types' block that raises on a reload (a definition being edited) is kept the same way: the block rescues it and hands it to `Theme.prepare(folder, reload:, unregistered:)`, whose refusal says what was raised, so every public page says it rather than `Theme.current` staying the last reload's; the registries after the one that raised are empty until the next reload, and at boot it is raised (`test/integration/theme_pages_test.rb`: "a type whose registration raises on a reload leaves a theme that says why on every public page, and the next reload clears it"). Boot is told from reload by `ThemeFolder.booted?`, state of `ThemeFolder` (in `lib/`, not reloaded) with no writer: `config/initializers/theme.rb` calls `ThemeFolder.follow_boot` once, which registers the `after_initialize` hook that sets it and refuses a second call (`test/integration/theme_pages_test.rb`: "a theme refused on a reload leaves the registries prepared and CS Studio working, and every public page says why until it is corrected"; `test/values/theme_test.rb`: "prepare is load at boot, and on a reload a refused folder is a theme that remembers why and brings nothing").
- **`Theme.with(theme) { … }` and `Theme.current=` are for tests and the initializer's one assignment, and nothing else.** `current` is one variable of the PROCESS, not of a request or a thread: a swap made while a request is answered draws every other request of the process with the other theme and puts its fingerprint into their ETags. That is what a test wants (a system test's server runs in the test's process and must see the swap) and what the application must never do (`test/lib/theme_guards_test.rb`: "nothing in the application swaps the theme: Theme.with and Theme.current= are the tests' and the initializer's", with "the guard can fail: a swap in a controller, a view, a job or a second one in the initializer is named with its line").

`config.watchable_dirs` gains the folder (`erb css js`) when one is configured, so a change under it reloads the application in development as a change under `app/` does: `to_prepare` then builds a new `Theme` with the folder's new fingerprint and new subclasses of the freshly loaded components.

## The four seams

Each has one place that knows it.

### Page templates: the view path

`PublicPageRendering#look_in_the_theme_first`, a `before_action` of the concern `PagesController` and `PreviewController` include, prepends `Theme.current.views_directory` to the view path **of that request's controller instance**, so `Theme.current` can differ between two requests of one process. Only those two controllers do it: no CS Studio controller, not sign-in, not setup, no mailer. `views_directory` asks the filesystem once per `Theme` (it is asked on every public request).

What the path lets a theme replace is not "any template": the folder is checked against `Theme::Contract::TEMPLATES` when the application starts, and one that holds the layout, `pages/_seo_meta`, `shared/_theme_head` or the preview bar does not start.

A template the theme does not hold is the default theme's, silently and by design. **A theme's template that raises is an error that names the theme's file, never a fallback** (decision 14): rescuing it with the default template would draw a page half of one theme and half of another, and hide a bug nobody sees (`test/integration/theme_pages_test.rb`: "a theme's page template that raises is an error that names the theme's file, not a fallback"; `test/values/theme_test.rb`: "a theme's block template that raises names the theme's file").

### Block and post templates: `Theme#component_for`

ViewComponent finds a template beside its class file and never asks the view path, so putting the folder on a path does not reach `components/blocks/image_component.html.erb`. `Theme#component_for(definition, role = :component)` is already where the public site gets a block's, a post list's and a post's component from (`ThemeHelper#render_block`, `Blocks::PostListComponent#list_component`; the roles are `:component`, `:list_component` and `:detail_component`). For a component whose template the folder holds it answers a **subclass generated once per theme**: `Class.new(component)` whose `sidecar_files` answers the theme's file for `erb` and the component's own otherwise. The template is therefore compiled into a class of the theme's own, calls everything the default template calls (private readers included, as any subclass may), and the CMS's class keeps its own template, so one process can hold two themes and a test can draw both.

Three things the subclass has to say because it is anonymous, each read from view_component 4.15.0:

- `name`: `ViewComponent::Template#safe_method_name` calls `@component.name.underscore`, and an anonymous class has none. It answers the CMS component's name, so anything keyed on the name (the contract's lookup, a log line) sees the CMS's component, and `name.constantize` is the parent, not the subclass;
- `virtual_path`: `ViewComponent::Base.inherited` derives it from the name at a moment the class has none yet;
- `identifier`: `inherited` takes it from the call stack, which is `theme.rb`; with the component's own, every question but the template's is answered as the component's. One consequence: with `annotate_rendered_view_with_filenames` on, the comment around a themed block names the CMS's `.rb` file, not the theme's template (read from the gem, not observed).

**The rejected way** is the spike's: an override of `ApplicationComponent.sidecar_files`, which compiles the theme's template into the CMS's own class, so a process holds one theme and no test draws two. The spec kept it as the fallback had the gem refused the subclass; it did not. `test/values/theme_test.rb` is the proof ("the same block is drawn by two themes and by the default in one process, in any order", "the component's own class keeps its own template after a theme's class was drawn", "a template the theme does not hold is the definition's own class, and a held one is a class of its own", "the other roles go through the same seam: a post list's and a post's component"), and it is the guard of a ViewComponent upgrade: it fails on the day the gem changes how a class finds its template.

The subclasses live as long as their `Theme` does (`@components`, a `Concurrent::Map`); a reload builds a new `Theme`. ViewComponent's `CompileCache` holds every compiled class strongly, which is nothing for one theme per process and leaves a class behind for each `plain_theme` a test draws with.

So the replaceable components are exactly those the type registries hand out, each one line of `Theme::Contract.components`. `Media::PictureComponent` is called by templates and is not replaceable; `RichText::ImageComponent` and `RichText::YoutubeComponent` are rich text ("Rich text", below). An outside type's component (a type registered under a name with a slash) is replaceable when its definition declares `theme_methods`, and its line is its gem's promise, not the CMS's: it is in no table here and not in the ledger.

### The stylesheet: `ThemeCss`

**One public stylesheet, `app/assets/builds/theme.css`, built once, for one theme** (decision 11), from an entry file `ThemeCss.write_entry` writes to `tmp/theme/entry.css`:

```
@import "<default theme>/theme.css";              tokens, base, prose, sections, the default templates' utilities
@import "<a type's stylesheet>";                  each registered block type's, in registration order
@import "<theme>/assets/stylesheets/theme.css";   the theme's own styles
@source "<default theme>";                        for the watch alone
@source "<a type's component folder>";            only for a component outside app/components/blocks
@source "<theme>/assets/stylesheets";             for the watch alone
@source "<theme>/views";                          so utilities in the theme's templates are built
@source "<theme>/components";
@source "<theme>/javascript";                     so a utility only a controller writes is built too
```

Without a theme only the first and the fourth line are there (a type's own lines are there for each type that declares a stylesheet). A line is left out for what the theme does not have.

**The types' stylesheets, and their order.** The default theme's own stylesheets (`theme.css` with the tokens, base, prose and sections it imports) come FIRST by a fixed rule of the entry, whatever the registration order (the owner's answer 4); then each registered type's stylesheet once, in registration order; then the theme's, so a theme still re-colours a block by declaring its token again. `lib/theme_css.rb` loads before the application and reads no registry: `BlockTypes.theme_css_blocks` hands it a list of `ThemeCss::Block` (`stylesheet:`, an absolute path or nil, and `source:`, the folder of the type's component when that is not `app/components/blocks`, which the default theme's own `@source` line scans, so utilities in an engine's template are built). `ThemeCss.build`, `watch`, `sources_glance` and `entry` take it as `blocks:`; the watch reads the types once when it starts, so a new type's stylesheet needs it restarted. A stylesheet a type declares is watched like the default theme's (its folder is a `@source`, and `sources_glance` lists its file). **The `@theme inline` mapping stays hand-written for the shared tokens**: a type's tokens are not utilities, and one that wants a utility writes its own `@theme inline` in its stylesheet. Both imports come before the `@source` lines: an `@import` after another rule is not an import. What follows from the order:

- **A theme changes a token by declaring it again, and copies nothing.**
- **A template the theme does not replace is still styled**, because the default theme's styles are always in the build. That is what makes the fallback real, and why the preview bar keeps its look under any theme. A build that left them out would unstyle every template a theme does not replace.
- A theme may write plain CSS or Tailwind utilities in its templates: both go through the same executable, and the theme's templates are scanned.
- The cost is the default templates' utilities in every site's stylesheet, a few kilobytes a site does not use.

Three things about the cascade that a theme's author meets, none of them enforced:

- **A token declared only under `:root` also replaces the DARK value.** The default tokens are unlayered, `:root, [data-theme="light"] { … }` then `[data-theme="dark"] { … }`, and a theme's `:root { --th-accent: … }` comes later at equal specificity. A theme declares a themed token under both selectors, as `theme:new`'s stylesheet comment shows.
- **A theme's unlayered CSS beats utilities.** Tailwind's utilities are in `@layer utilities`; the theme's `theme.css` is imported unlayered, and an unlayered rule wins over a layered one whatever their order. A class of the theme's own on the same element as a utility wins.
- **`--th-` is the CMS's prefix.** A theme's own custom properties take another (`--plain-gap` in the second theme). Nothing checks a theme's stylesheet for it.

**The two `@source` lines that name a folder of stylesheets add nothing to the build** (Tailwind reads no class name out of a `.css` file: the output with them is byte for byte the output without, compared for both themes) and are there for `theme_css:watch`. Tailwind's watcher watches the folder the entry file is in and the folders its `@source` lines name, and not the folder of a file the entry imports. While the entry WAS the default theme's `theme.css`, that folder was watched for being the entry's own; with the entry in `tmp/theme`, a change to `tokens.css`, `prose.css` or a theme's `theme.css` was built by nobody, with no word in the log. So every folder a stylesheet is imported from is a source too (`test/lib/theme_css_test.rb`: "every folder a stylesheet is imported from is watched: it is a source too").

**Paths are relative to the entry file**, so the entry reads the same on a laptop and in an image, and the theme is named by where it REALLY is (`realpath`): the watcher reports a changed file by its real path, so a theme reached through a link (on macOS every temporary folder is: `/var` is a link to `/private/var`) was built once and a changed template of it never again. **A double quote or a backslash in the theme's path breaks the entry**, whose paths are written between double quotes with no escaping; nothing refuses such a path.

**When: at image build, never at boot.** `assets:precompile` runs `tailwindcss:build`, which is enhanced to run `theme_css:build` (`lib/tasks/theme_css.rake`), with `THEME_PATH` set by the site's Dockerfile. `ThemeCss.build(folder, root:, executable:)` is the one build both tasks run: the fingerprint is read, **the stamp is taken away**, the entry is written, the executable runs, and the stamp is written with the fingerprint read BEFORE the build. A build that fails leaves no stamp, an earlier build's included; a file of the theme changed while the executable ran may or may not be in the output, so the folder then no longer matches its stamp. Outside `ThemeCss` nothing runs the executable on this entry or writes the stamp (the watch's keeper, below, is the one other writer): a build made around it would leave a stylesheet nobody vouches for.

**The stamp** is `app/assets/builds/.theme.stamp` (`ThemeFolder::STAMP`): the fingerprint of the theme the stylesheet was built for, beside the stylesheet it vouches for, so it is in the image with it and ignored by git and by the Docker context as that folder is. **A dot file, and not the spec's `theme.stamp`**: `app/assets/builds` is on Propshaft's load path, where every file is an asset, copied to `public/assets` by `assets:precompile`, listed in `public/assets/.manifest.json` (itself a static file, so the digested name need not be guessed) and served. The first build's stamp was exactly that: the asset list held `theme.stamp` and the manifest `theme-a099327b.stamp`. Propshaft leaves dot files out (`Propshaft::LoadPath#without_dotfiles`, read in 1.3.2), so under this name the stamp is read by the application and by nobody else (`test/lib/theme_css_test.rb`: "the stamp is a dot file beside the stylesheet, and no asset: not found, not listed, not served"). **The stamp is the theme's fingerprint and nothing else**: it covers no block type's stylesheet, so a stylesheet built under one set of gems is not refused under another (the block types spec's step 2; a known gap on the roadmap).

**Production does not start under a stylesheet stamped for another theme** (`ThemeFolder#built?`, asked in the `content_spiel.host_announcement` initializer of `config/application.rb`): the right templates drawn with the wrong styles, and nobody told, is worse than not starting. Both ways round, a theme over a stylesheet built without it and no theme over one built with it, and with no stamp at all (a sentence of its own). **It is not asked under `SECRET_KEY_BASE_DUMMY`**, as the secret is not: that is the image build's own `assets:precompile`, which starts production BEFORE the stylesheet it is about to build exists. The check applies to every production process, a console, a runner, `db:prepare` and the job process included; in an image the stamp is always there. Development and test refuse nothing; System status says it (`test/lib/production_boot_test.rb`: "production under a theme whose stylesheet was not built for it does not start, and says how to build"; `test/lib/theme_css_test.rb`: "the build's stamp is the theme's fingerprint, and a folder is built when the stamp is its own", "a build stamps after the executable succeeded; a failed one leaves no stamp, an earlier one's included", "the stamp is the fingerprint read before the build: a file changed while it ran is not vouched for", "the refusal says which way round it is and how to build", "with no stamp the refusal says the stylesheet was not built, for a theme and for none, and how to build").

**In development: `theme_css:watch`**, one of the three processes of `bin/dev` (`Procfile.dev`), is `ThemeCss.watch`: a loop of one whole build, stamped when it succeeded, then Tailwind's watcher on the same entry.

- **It does not end because the stylesheet does not build.** Foreman stops every process of `bin/dev` when one ends, so a watch that raised at its first build took the web server with it, and a person with a half-written `@import` could not start the application they were writing the theme in. Tailwind's own watcher does not stay either: started on an entry that does not build it prints the error and exits (seen with 4.3.3; one already running when the stylesheet breaks reports and stays). So a failure is said in one line under Tailwind's own words for it, and the watch waits until a file of the theme or of the default theme's styles has changed (`sources_glance`: names, sizes, times), then tries again from the whole build. The watcher ending well ends the watch.
- **A folder that cannot be listed** (renamed, deleted, a file made unreadable, a link to nothing) is waited out a turn at a time: nothing is built, the watch says it once by the error's class and without a path, and looks again every second. Every wait sleeps BEFORE it looks: a wait that compared first, with a look that could never equal the last, went round thousands of times a second and printed its line each time.
- **The keeper** (`ThemeCss.keep_stamped`) is a thread that runs only beside Tailwind's watcher, and only for a theme folder (the default theme's fingerprint never changes). Tailwind's watcher rebuilds on a change by itself, but nobody hears whether that build succeeded, and the folder's fingerprint changes with every edit, so a stamp written once at the watch's start would make System status warn after the first edit about a stylesheet that is right. Every second the keeper glances at the folder and reads the stamp, and hashes the folder only when one of the two changed. On a change, while the stamp is still its own, it writes the entry again if it is no longer the folder's (a theme that gained its stylesheet or its `components` folder), **builds once itself**, quietly, and stamps the fingerprint it read; a build that fails takes the stamp away. The price is one extra build of about 50 ms per change. A stamp somebody else wrote since (a test run) is left as it is, because the stylesheet is then theirs too; when the stamp is the folder's fingerprint again the keeper takes it for its own. An error of any kind in a turn is said once, by its class and without a path, and the turn is tried again. **A turn remembers the stamp it judged, or the one it wrote, never a second reading**, and the stamp is put in place whole (`ThemeCss.stamp!` writes a dot file beside it, under a random name so that two containers sharing the folder never write one file, renames it, and leaves none behind when the write fails: "the file a stamp is written to beside it has a name of its own each time, a dot file there, and is gone afterwards, also when the write fails"): a plain write empties the file first, a keeper that read it then read an empty stamp, judged that, and remembered the full one it read at the turn's end as seen, so it never took the other build's stamp for its own and built nothing from then on. The first CI run of the branch stopped there (`test/lib/theme_css_test.rb`: "a stamp another build writes in the middle of a keeper's turn is judged at the next turn, and the theme is kept from there", "a stamp is put in place whole: a reader never meets an empty one, and nothing is left beside it"). The keeper's thread counts the turns it has ended (`thread_variable_get(:turns)`), which the watch does not read: the tests wait for two ended turns (`let_it_ask`) where they once slept a third of a second.

`test/lib/theme_css_test.rb` holds all of it with a stand-in executable ("the watch goes on when the stylesheet does not build: it says so, and builds, stamps and watches once the file is mended", "while the theme folder cannot be listed the watch waits a turn at a time and says so once, and goes on when the folder is back", "while it is kept stamped, a changed theme is built and stamped with its new fingerprint; the default theme needs no keeping", "the keeper stamps the fingerprint it read, and so still knows its own stamp at the next change", "an error of any kind in a turn is said once, without a path, and the keeper goes on"). No test runs the real build: `bin/theme-build-check` does ("Deployment").

**Development and test share the output and the entry.** `bin/rails test` builds the default theme's stylesheet into the same `app/assets/builds`, from the same `tmp/theme/entry.css`, also while a watch runs for a theme: the site in development is then drawn with the default stylesheet until `bin/rails tailwindcss:build` is run with `THEME_PATH` set, or the watch is started again. System status says so, and so does the test build itself, on stderr, when it replaces a stamp that was not `default`. An output per environment is not built (the roadmap has the row).

### Assets and scripts: the load path and the `site` entry point

**Images and fonts.** `config/initializers/theme.rb` appends `ThemeFolder#asset_paths` (the theme's `assets/images`, `assets/fonts` and `javascript`, those that exist at boot) to Propshaft's load path. A theme names an image or a font **by its bare file name**, in its stylesheet (`url("mark.svg")`) and in its templates (`image_path("mark.svg")`): Tailwind leaves the `url()` as written and Propshaft writes the digested address when the stylesheet is served (`url("/assets/mark-<digest>.svg")`). Never a relative path into the folder. The CMS's two font families reach a theme through `--th-font` and `--th-mono`, not through their file names.

**By extension, and nothing else** (`Theme::Check::ASSET_EXTENSIONS`): a folder on the load path is published whole under `/assets`, so a `.rb`, an `.erb`, a second stylesheet or a script put under `assets/images` would be served as it is. `assets/images` takes `png jpg jpeg gif svg webp avif ico`, `assets/fonts` takes `woff2 woff ttf otf`, case ignored, at any depth. A PDF or a video cannot be a theme's asset today; that is a contract change.

**A theme adds assets, it does not replace one.** A file that would be served under the same name as one of the CMS's own stops the boot (`Theme::Check.shadowing`): the CMS's roots inside the application (`CMS_ASSET_ROOTS`: `app/assets/images`, `app/assets/fonts`, `app/assets/stylesheets`, `app/javascript`, `vendor/javascript`) and the gems' roots on the configured load path (Turbo, Stimulus, Action Cable): every root outside the application, and every root INSIDE it that is under the folder of a gem Bundler has activated (`Theme::Check.gem_folders`), since Bundler's path may be `vendor/bundle` (`bundle install --deployment`, every CI runner with a cached bundle). Told by being outside alone, a gem's root in that layout was dropped: a theme's file named like one of Turbo's scripts was let through there, and the first CI run of the branch failed two tests that were green on a laptop (`test/values/theme/check_test.rb`: "a gem installed inside the application (vendor/bundle) is still a gem: its asset folder is asked, by its real path too"). `app/assets/builds` is on the load path and deliberately not asked: its content depends on whether a build has run, and a check must say the same in a fresh checkout as after one. **The theme's own folders are never among the roots**: the initializer puts them on the load path before the check runs, and a real site's theme is outside the application, so, taken for a gem's, each of its own three folders "held" every file of the theme and every image, font and controller was refused. For one round no site with a theme outside the application started, and everything was green because the fixture theme is inside it. The folders of the theme the application STARTED with are left out too (`started:`), so `theme:check` of a second copy of the running theme does not find each asset in the running theme's folders (`test/values/theme/check_test.rb`: "a theme outside the application whose own asset folders are on the load path shadows nothing: an image, a font, a controller", "every root of the asset load path is one the check asks, or is named here with its reason", "what the check says of an asset does not depend on whether a build has run").

**Scripts.** A theme's Stimulus controllers are pinned by `config/importmap.rb` from `ThemeFolder#pins`: every file under `javascript/controllers` as `controllers/theme/<name>`, served as `controllers/<name>.js` from the theme's `javascript` folder, `preload: "site"`. So `copy_controller.js` is the identifier `theme` joined to `copy` by two hyphens and cannot be one of the CMS's; one in a subfolder (`docs/copy_controller.js`) carries the folder as a further part. A theme adds no pin of its own and no third-party script, so `@hotwired/stimulus` is the one import that resolves in a theme's controller. That is what works, not what is checked: nothing reads a controller's content (the check asks its name only).

They are registered by a third entry point, **`site`** (`app/javascript/site.js`: `application` plus `controllers/theme/*`), which the public layout alone loads, as CS Studio's layout alone loads `admin`. `controllers/index.js`, imported by `application`, registers everything under `controllers/` EXCEPT `controllers/admin/*` and `controllers/theme/*`. `application` could not carry a theme's controllers itself because sign-in and setup load it too. So a theme's script is never imported on a CS Studio screen, on sign-in or in setup (`test/integration/public_javascript_test.rb`: "only the public layout loads the site entry point, and with it the theme's controllers", "the site's own registration leaves CS Studio's and a theme's controllers to their entry points", "a theme adds pins under controllers/theme/ and nowhere else, and changes no pin of the CMS's", "the site entry point is named by the public layout and by no other layout or view", "no script of the CMS's imports the site entry point or a theme's controller"; `test/system/theme_script_test.rb`: "a theme's controller connects on a public page under the theme", "the sign-in page registers the site's controllers and not the theme's").

**One place a theme's script does run inside a signed-in session: the preview.** `PreviewController` draws through the public layout, so the theme's controllers are loaded in CS Studio's preview of a page, in the editor's session. That is consistent with the trust above and worth knowing before a theme's script reads the document.

## The head

`layouts/application.html.erb` is the CMS's and no theme replaces it (decision 10): a folder that holds it does not start. **The head is split by who answers for a tag.** The rejected way was the spike's, replacing the layout whole, which made the theme copy the CSP tag, the light/dark script, hreflang and the import map, and lose every tag the CMS adds later.

The CMS writes these, each a line of the layout, each **once and before the theme's**:

1. the `<title>` element (its text is the theme's pattern, below);
2. `<meta name="viewport">`;
3. the content security policy's tag (`csp_meta_tag`);
4. the script that picks light or dark before the first paint (`shared/_theme_head`);
5. the description and the Open Graph tags (`pages/_seo_meta`), when a page is found;
6. the canonical link and the language links (`hreflang`, `x-default`), when a page is found;
7. then the theme's `_icons` and `_head`;
8. the stylesheet link (`theme`) and the import map with the `site` entry point.

And as a decision and not a tag: **no CSRF token on a public page** ("The public site commits no session", below).

The theme has four partials under `views/layouts/public/`, each with the default theme's as the fallback:

- **`_title`, the pattern of the page title.** Locals `page_title` (the page's or the post's own title; nil on the homepage and on a 404) and `site_title`. What it prints, squeezed to one line (`PagesHelper#themed_title`: a theme's author never has to write the pattern on one line), is the text of `<title>`; it is escaped once. The default prints "Page – Site", and the site's title alone without a page title. Two things stay the CMS's: **a meta title an editor typed for a page is taken as written and the pattern is not asked** (`PagesHelper#document_title`), and the Open Graph title is the page's own without the site's name. A 404's title is the site's title through the pattern, where the layout once printed the literal "ContentSpiel".
- **`_icons`**: the favicon and the touch icon. A theme links its own from `assets/images` with `image_path`.
- **`_head`**: every other tag of the theme's own: fonts to preload, `<meta name="theme-color">`, a verification tag. It is rendered with `@page` and `@post` available and receives no locals. The default holds the three "installable app" metas (`application-name` among them), so a site whose theme brings its own `_head` no longer announces itself as "ContentSpiel".
- **`_frame`**: everything inside `<body>` but the preview bar; `yield` is the page. It is a partial layout (`render layout: "layouts/public/frame"`), so the page template has already been rendered when the frame runs.

**The layout reads no slot.** `content_for(:title)` and `content_for(:head)` are not read on the public side: `content_for` appends, the page template is rendered before the layout, and a theme's template that wrote to either slot had its text put in front of the page's ("HijackAbout – Site") or its tags among the CMS's, ahead of the description. The layout asks `document_title` itself and renders `pages/_seo_meta` in place (`test/integration/theme_pages_test.rb`: "a theme's template that writes to the title's slot changes no title: on a page, on a 404 and with a meta title", "a theme's template that writes to the head's slot puts nothing into the head: on a page, in a block and on a 404").

**`pages/show` holds no CMS line any more.** It carried two (the head tags of `pages/_seo_meta` and the preview bar); both moved into the layout, so a theme that replaces the page template cannot lose them ("a theme that replaces the page template still gets the description, the Open Graph tags and the preview bar"). While `pages/show` rendered the tags, not rendering `pages/show` was what kept them off a 404. That guard went with the move, and **a 404 can have a record in hand**: `assign_record` assigns the page and the post before it finds that no block lists the post, and the preview answers 404 for a post whose listing page the editor may not read. Such a 404 had the post's title in `<title>` and, as its description, the listing page's meta description, of a page the editor may not read. So the layout decides by the response's status, never by `@page` (`page_found?`): a 404 has the site's title, no description, no Open Graph tag, no canonical link and no language link ("a 404 that had a record in hand describes none: the site's title and no description or Open Graph tag", "a 404 that had a record in hand names no canonical address and no other language's, in the preview and in public").

**What a theme cannot do, and what it still can.** It cannot remove or replace a CMS tag: each is a line of the layout. The renderer does not stop a theme's `_head` printing MORE markup, a tag of the same name included; the folder check refuses the ones that contradict the CMS's ("Checking a folder"), and what holds for a spelling the check does not see is that the CMS's own are there once, unchanged and first ("every tag the CMS writes into the head is there exactly once under both themes, ahead of the theme's own", "a theme whose head prints a canonical link, a CSP tag and a CSRF tag of its own takes none of the CMS's away: each is there once, unchanged and first"). **And one thing is not held at all**: the layout decides the title, the description, the links and the preview bar from `@page`, `@post`, `@preview_record` and the response's status, after the page template ran in the same view. An assignment to an instance variable is refused by the check; a record changed in memory (`@page.title = …`) and a status set on the response (`response.status = …`) are not seen, and either changes the CMS's head. The stronger fix (the controller keeps the head's facts where a view cannot reach them) is not built; the roadmap has the row.

**Scripts and styles from another host are not held by the content security policy.** `config/initializers/content_security_policy.rb` sets `frame-src`, `object-src` and `base-uri` only: no `script-src`, no `style-src`. A second stylesheet link is refused by the folder check because of decision 11 (one stylesheet), not by the policy; a `<script src>` or an `@import` from another host is held by nothing, and the check does not look for `<script`. The spec's sentence that "the content security policy is the CMS's" promises more than exists (the roadmap has the row).

The body's classes are the default theme's and read tokens only, so a theme changes the page's ground and type by its tokens, or by a `body` rule of its own. The preview bar is product UI on a public page: the layout renders it and no theme replaces it.

## The public site commits no session, mints no token and sets no cookie

`PublicController` always answered the same cookie-less response to every visitor, and that was a convention while every public template was the CMS's own. A theme's templates are not, and there are two ways one sets a cookie on a response that says `Cache-Control: public` (which a shared cache may keep and hand to the next visitor). Both did, in the tests that now pin this.

**The session and the token.** A `form_with` or a `button_to` in a theme's footer, `csrf_meta_tags` in its head or a `form_authenticity_token` anywhere asks Rails for the token, and Rails reads the session to mint it. Three lines:

- the session of a public request is never committed (`request.session_options[:skip] = true`, which the session middleware asks before it writes the cookie), whatever a template read or wrote in it. A write to the flash is a write to the session and goes with it;
- `protect_against_forgery?` answers false, which is what `csrf_meta_tags` and every form helper ask before they print a token;
- `form_authenticity_token`, which mints one without asking, answers nil.

**The cookie jar, which is not the session.** `cookies[:seen] = "1"` in a template (a consent banner, an A/B flag: honest mistakes), `cookies.signed`, `.encrypted` and `.permanent`, and `cookies.delete` are kept in the request's jar and written into the response by `ActionDispatch::Cookies`, a middleware of its own that never asks the session's `:skip`. So `PublicController#leave_no_cookie`, an `around_action` declared first in the class and therefore around every callback and action of it and of its subclasses (one that answers early included), does two things once the action and its templates are done:

- the request gets a NEW jar, built from the cookies the browser sent and holding no write and no delete, which is the one the middleware then finds and writes nothing from (actionpack 8.1.4, `ActionDispatch::Cookies#call`). Nothing is sent to delete a cookie either;
- a `Set-Cookie` put on the response by hand (`response.set_cookie`, `response.headers["Set-Cookie"] = …`) is taken off.

**What is promised, exactly: no `Set-Cookie` leaves a response of `PublicController` or of a subclass, whatever a theme's template calls in the view, and a signed-in editor's cookies are neither changed nor taken away by reading a public page.** What is not: an action that raises is answered by the exceptions application, outside this controller (the cookie middleware writes nothing then, being passed by the exception), and a cookie a script sets in the browser (`document.cookie`) is the browser's and never this response's.

The overrides and the callback are private, so none is an action. Nothing public needs any of it: every public route is a GET to `pages#show` and no action reads the session. A theme's GET form (a search box) works, and a plain `<form method="post">` to another service posts without a token of this application, which that service could not have checked anyway. **`PreviewController` is not a `PublicController` and keeps all three** (session, token, cookies): it is signed in, private and never cached.

`Theme::Check` refuses the same words when the application starts, with a sentence that says why (below, "The plain depth"); the wall is what holds for a spelling the check does not see.

**A later feature that wants a cookie, a session value or a form that posts to this application from a public page meets this wall first**, and needs its own design: such a response is no longer the same for every visitor, so it also has to leave `Cache-Control: public` and the ETag's assumptions behind, most simply in a controller that is not a `PublicController`, as the preview is.

`test/integration/theme_pages_test.rb`: "a public page drawn under a theme sets no cookie and carries no token: a form, the CSRF tags, a token asked for, and a write to the session, the flash, the cookie jar and the header" (with forgery protection switched ON as production has it, on a page and on a 404), "a signed-in editor reads a public page under a grasping theme and is still signed in: no cookie set, none changed, none taken away" (the grasping head also deletes the session's cookie), "the preview, which is private and signed in, keeps its token and its cookies: the wall is the public controller's alone"; `test/integration/public_caching_test.rb`: "public pages set no cookies and are publicly cacheable".

## Rich text

**How a text looks is entirely the theme's** (decision 12). A rendered body is plain elements under a wrapper, and the theme styles every one of them, three ways, and may use all three:

- the tokens the default rules read (`--th-ink`, `--th-accent`, `--th-mono`, `--th-sunken`, `--th-radius`, the type sizes), which restyle a text without a rule;
- its own CSS under its own wrapper: the Rich text block's template and the post's are the theme's (`blocks/rich_text_component`, `posts/detail_component`), so the wrapper's element and class are too, and a theme that does not write `cs-prose` on it gets none of the default rules and starts from bare elements;
- rules under `.cs-prose`, which come after the default theme's in the one stylesheet and so win.

**The one limit: a theme does not replace the HTML structure a text is rendered to.** It cannot turn a heading into another element, add a class or an attribute to one, add a node, or bring its own template for the image and the video inside a text. The reason is that a body is rendered once and used in three places: it is cached by its document's digest (the cache key holds no theme and no component class) and is the same HTML in CS Studio's preview, in the MCP server's Markdown round trip and on the site, so a theme inside that render would be a theme inside the editor, and every theme change would have to empty the render cache. **The limit was raised with the owner on 2026-10-12, was not objected to, and is not confirmed.** If it goes, the way in is a hook on the renderer that a theme's template fills, with the theme's fingerprint in the render cache's key; nothing here closes it. Heading ids (`with_heading_ids`) are put on a copy of the rendered page for the same reason and never into the cached render.

**Struck text reaches the page since this work.** The editor's `strike` mark renders `<s>`, and `RichTextScrubber` started from Rails' safe list, which has `del` and no `s`: a struck text was shown struck in the editor and arrived plain on the site. The contract's own test found it; `s` is on the scrubber's list now and in `Theme::Contract::RICH_TEXT` (`test/values/theme/contract_test.rb`: "a rendered text is the elements the contract lists, under no class of its own").

## The contract

`Theme::Contract` (`app/values/theme/contract.rb`) is **the one list**, read by all of: the check when the application starts and `bin/rails theme:check` (`Theme::Check`), `bin/rails theme:new` (`Theme::Scaffold`), the tests (`test/values/theme/contract_test.rb`) and this file, which `test/lib/theming_reference_test.rb` holds to it both ways (a name added to the contract fails until its row is here; a row the contract does not hold fails too). The lists are data and name no class: a component is written as its path, which is also where a theme puts its template, so this value knows no component. **The block types' lines and tokens are read from their declarations** (`t.theme_methods`, `t.tokens`) by `Theme::Contract.components`, `.themed_tokens` and `.fixed_tokens`, on every call; the built-in types' part is held by the ledger (`test/support/contract_ledger.rb`, held to the code by `test/values/theme/contract_ledger_test.rb`), and the tables below are written by hand and held to the ledger by `test/lib/theming_reference_test.rb`.

**What is on these lists is stable, and a change is said in the release notes.** Everything that is not may change freely, and a theme that uses it is on its own. The list is kept short on purpose: every name on it is one the CMS can no longer rename quietly.

**What a copied default template asks of a RECORD is not yet contract.** The templates `theme:new` writes call `@page.root?`, `@page.landing?`, `@page.hero_media_asset`, `@page.children.kept.published`, `post.tags`, `post.fields`, `theme_site.logo`, `Media::PictureComponent` and `ContentTypes::ResumeEntry::ROLE_TYPES`, none of which is on a list, so every scaffolded theme is "on its own" for those lines from its first day, and no image template can draw a picture from listed names alone. Naming what a template may ask of a page, a post and an image is on the roadmap; until then a change to one of those calls is made in the default template and said in the release notes like a contract change.

**A block type added later joins by its declarations** (decision 18; block types spec, decisions 4 and 5): `t.theme_methods`, the methods its template may call, which makes its line in `Theme::Contract.components`, its template replaceable and `theme:new` copy it, and `t.tokens`, its lines in `.themed_tokens` or `.fixed_tokens`. Nothing else in the mechanism names a block, and the type cannot be added without them: a block type that declares no `theme_methods` is refused at registration (`test/values/theme/contract_test.rb`: "a block type registered without theme methods is refused at registration, and the message says what to declare"), and the contract test fails for a `--th-` token that `tokens.css` defines and no type declares ("every declared token is defined, a themed one for light and for dark, and no --th- name is undeclared"). A built-in's names are then lines of the ledger too, written with the release note, and the ledger's test is red until they are (`test/values/theme/contract_ledger_test.rb`: "the built-in types' part of the contract is the ledger: a name added, renamed or removed is a release note"). The post components are not a type's declaration and stay a constant (`Theme::Contract::POST_COMPONENTS`), as do the shared tokens, the two shared lists of `Theme::Contract` that belong to no type. **The Code block is the first that joined** ("The Code block", below): one line of the components, seven of the themed tokens, and nothing else in the mechanism was changed for it. It declares both in `app/models/block_types/code.rb` (`t.theme_methods`, `t.tokens themed:`), beside its stylesheet.

**An outside type's lines** (block types spec, decision 5) are as binding for the site that installs its gem as a built-in's, and they are the gem's promise, not the CMS's. A type registered through `ContentSpiel::Plugins.block_types` (`lib/content_spiel/plugins.rb`; `docs/reference/content-blocks-and-types.md`, "Block types from outside") joins `Theme::Contract.components` and `.themed_tokens` / `.fixed_tokens` by the same declarations, so while it is registered the check lets a theme replace its template, exactly at its path (`components/gallery/album_component.html.erb` for `Gallery::AlbumComponent`), `theme:new` copies that template from beside the gem's component (`BlockTypeDefinition#component_template`) and names its tokens in the stylesheet it writes, and the build imports the gem's stylesheet and scans its component's folder (`BlockTypes.theme_css_blocks`, by their real paths). The tables below are the built-ins' and stay held to the ledger; a gem documents its own lines. An outside type's tokens start with its owner (`--th-gallery-frame`) and are defined in its own stylesheet from the theme's base tokens only, as `var()` or `color-mix()` of them: a colour literal in a declaration's value there is refused at registration (`BlockTypeDefinition.colour_literal?`), so a theme that re-colours its base re-colours the gem's block, and may still give its token a value of its own. When the gem is removed, a theme that still replaces the type's template is refused by the check, by name, with the type it was for and what to do (the owner's answer 3): the check runs at the image's build, so it stops the build, not a running site.

**A block's colours follow the look of where it is drawn** (block types spec, decision 3; the owner's answer 1, 2026-10-13: "for the backend it follows the backend, for the frontend it should follow the theme"). In CS Studio a block type brings no colour of its own: its card, tile and inputs are CS Studio's components on CS Studio's tokens, as every type's are. On the site a block's tokens are defined IN TERMS OF the theme's base tokens (`--th-accent`, `--th-accent-tint`, `--th-ink`, `--th-line`, `--th-surface`, …), never as colour literals, so a theme that re-colours its base re-colours every block, built-in or from a gem, and a theme may still give any block token a value of its own. A built-in's defaults are written in `tokens.css`, the one place a colour literal is written, where a built-in token may keep a literal where no base token is right (the seven syntax colours do), and the strong band's re-values stay in `sections.css`. An outside type writes its tokens' defaults in its own stylesheet, as `var()` or `color-mix()` of base tokens only, under the same selectors (`:root, [data-theme="light"]`, `[data-theme="dark"]`, and `.content-section--strong` where it re-values for the band); its stylesheet is refused at registration when it holds a colour literal (`test/models/content_model/block_type_definition_test.rb`: "an outside type's token names start with its owner, and its stylesheet is an absolute path that holds no colour literal", "the colour guard reads declaration values: every kind of literal is refused, a selector, a comment and a string are not"). **An outside type's template uses the theme's colour utilities only** (`text-ink`, `bg-surface`, `border-line` and the rest of the `@theme inline` mapping of the shared tokens), never Tailwind's own palette. That is a promise without a guard in step 1: the gem's component folder is scanned by the build, so `text-red-600` in its template is built from Tailwind's whole palette and nothing refuses it (a guard is a roadmap item of step 2). Contrast of an outside type's pairs is the gem's to test; the CMS computes its own built-ins' (`test/integration/design_tokens_test.rb`).

### Tokens

Declared in `app/assets/tailwind/themes/default/tokens.css`, which imports nothing and names no block. A theme changes one by declaring it again in its own stylesheet. The first group (`Theme::Contract.themed_tokens`, `--th-paper` to `--th-note-warning-border`) has a value for the light scheme and one for the dark, and is declared again under both `:root, [data-theme="light"]` and `[data-theme="dark"]`; the rest (`.fixed_tokens`) have one value.

| Token | What it is |
|---|---|
| `--th-paper` | the page's ground |
| `--th-surface` | a raised surface: a menu, a card |
| `--th-sunken` | a sunken surface: a code block, a tinted band |
| `--th-ink` | body text |
| `--th-dim` | secondary text |
| `--th-meta` | labels, dates, captions: 4.5:1 on the page and on the tinted band at 11px; also the outline of a control on the site (3:1) |
| `--th-line` | a hairline |
| `--th-line-strong` | a stronger line: a quote's rule |
| `--th-accent` | links and the one accent colour |
| `--th-accent-hover` | the accent under the pointer |
| `--th-accent-tint` | a ground tinted with the accent |
| `--th-on-accent` | text on the accent (inside a strong band it is the band's own colour: "The Code block", below) |

### The Code block

The first block type that joined the contract after it was written (code block spec §5; the block itself is in `docs/reference/content-blocks-and-types.md`). What a theme can do with it, from the least work to the most:

1. **Re-colour it: declare the seven `--th-syn-*` tokens again**, under both selectors, as any themed token. `code.css` colours each span by its token and by nothing else (`.syn-keyword { color: var(--th-syn-keyword) }`), and holds no colour of its own. It is the type's stylesheet (`t.stylesheet "code.css"` in `app/models/block_types/code.rb`), imported by the generated entry right after the default theme's `theme.css` and before a theme's own, as every type's is ("The types' stylesheets, and their order" above), and no longer by `theme.css` itself: the built stylesheet is the same bytes. The ground is `--th-sunken`, plain code `--th-ink`, the lines `--th-line`, the face `--th-mono`, the head strip `--th-dim`, Copy `--th-accent`.
2. **Restyle it: rules of its own** under `.content-block--code`, which come after the default's in the one stylesheet. The default template's class names (`code-head`, `code-file`, `code-language`, `code-status`, `syn-<role>`) are the default theme's own, as a section's are: not on a list, and a theme that styles them follows the default template through upgrades.
3. **Replace its template**: `components/blocks/code_component.html.erb`.

**What the template is handed** (`Theme::Contract.components`, the row above). The component draws nothing for a block without code (`render?`), so a template never meets one, and each method answers for an empty block all the same.

| Method | What it answers |
|---|---|
| `block` | the block: a published view on the site, the rows in a preview. `block.id` is what tells two code blocks of a page apart (an `id` for `aria-describedby`) |
| `page` | the page the block is drawn on |
| `lines` | the code, cut into lines and coloured on the server: an Array with one Array per line of `[role, text]` pairs. `role` is nil for plain text and otherwise one of `comment`, `keyword`, `string`, `constant`, `tag`, `attribute`, `embed`: a String, and the part of the token's name after `--th-syn-`. Neighbours of one role are one pair; an empty line is `[]`; the line break is in no pair. `[]` without code |
| `code` | the source as stored, a String or nil: for a template that wants it whole (its length, a download link) |
| `language` | the language's tag as stored (`"ruby"`), or nil |
| `language_label` | what a person reads for it (`"Ruby"`), or nil: without a language, and for a stored tag that is no longer on the list (such code is drawn plain) |
| `filename` | the file name an editor typed, or blank |
| `caption` | the caption in the language shown, with the site's fallback, or blank |
| `string(key)` | one of the copy button's four words (the table below, and no other key) in the language shown, in English where that language has no `config/locales/public.<locale>.yml` |

**The code is text.** A template prints each `text`, the file name and the caption through ERB's own escaping (`<%= text %>`, `tag.span(text, …)`) and never marks one safe: no `raw`, no `html_safe`, no `<%==`. What an editor pastes as code is then characters on the page whatever it looks like. No check reads a theme's template for this (the default's own is held by `test/components/blocks/code_component_test.rb`: "nothing in the component, its template or the highlighter marks a string as safe, and only the highlighter names Rouge"). And between the tags of the element that holds the code a template writes nothing but each text and ONE line break between two lines, none before the first and none after the last, which is why the default's `pre` is on one line: what is between those tags is what a visitor copies.

**What `string` is asked for:**

`string` answers these four keys and no other (`Blocks::CodeComponent::STRINGS`), as a Symbol or a String. **Any other key is a mistake in the template and never a word on the page**: in development and test it raises (`ArgumentError`, naming the four), so the first render of the theme says so; in production it answers an empty string, and the log has one line for that key for the life of the process. `theme:check` does not see it: the check reads names, not arguments.

| Word | What it is |
|---|---|
| `string(:copy)` | the button's word at rest: "Copy" |
| `string(:copy_code)` | the button's accessible name: "Copy code" |
| `string(:copied)` | what the button says after a press that worked: "Copied" |
| `string(:failed)` | what it says when the browser refused the clipboard: "Not copied" |

**The copy script's markup.** The Copy button is the CMS's script, `code-copy` (`app/javascript/controllers/code_copy_controller.js`), registered on every public page as the `theme` controller is. A template that wants the button writes this, and one that wants no button leaves all of it out:

| Markup | Where, and what the script does with it |
|---|---|
| `data-controller="code-copy"` | on an element around everything below |
| `data-code-copy-target="button"` | the button, **rendered `hidden`**. The script shows it only where the browser has a clipboard to write to, so a page without JavaScript, or on plain HTTP, has no button that does nothing. Its whole text is its word: the script writes the answer into it and the word back. Required: without it the script raises when it connects |
| `data-action="code-copy#copy"` | on the button |
| `data-code-copy-target="source"` | the element whose text is the code. Its `textContent` is what is copied: no markup, and every character between its tags. Required at a press: without it the press is an error in the console and the visitor is told nothing |
| `data-code-copy-target="status"` | optional: an element with `role="status"`, empty. The answer is written into it too, for a screen reader (the button's accessible name does not change), and taken out when the word goes back. The default hides it from sight by a rule of its own class |
| `data-code-copy-target="strip"` | optional: an element that holds nothing a visitor reads but the button, **rendered `hidden`**. The script shows and hides it with the button, so nobody sees an empty bar. The default's head strip is this target when the block has no file name and no language, and is not when it has one |
| `data-code-copy-label-value` | the button's word at rest (`string(:copy)`). Left out or empty, the script keeps the word the template wrote into the button |
| `data-code-copy-copied-value` | what the button says after a press that worked (`string(:copied)`) |
| `data-code-copy-failed-value` | what it says when the browser refused (`string(:failed)`) |
| `data-code-copy-restore-value` | optional: how long the answer stays, in milliseconds. 2000 without it |

What the script writes into the page it takes back itself, and a template does nothing for that; when and how is the script's own business and not part of this table. A theme that wants another behaviour writes a controller of its own (`controllers/theme/…`) and leaves this markup out; the script's file says the rest.

**The row is the spec's eight names and `string`.** Nothing else of the component is a theme's to call, and the default template calls nothing else of it: no default component template calls a method of its component that its row does not name (`test/values/theme/contract_test.rb`: "a default component template calls no method of its component that its line does not name"), so the copy `theme:new` writes is made of promised names only. Two things the default template once asked the component for are written out in it instead, because they are ITS layout and a theme's is another: which bar is hidden until the script shows it, and the `id` of the file name's element (`code-<%= block.id %>-file`, from `block`, for the button's `aria-describedby`). A method that answered "hide the bar" for a block with no file name and no language would hide a theme's bar that also holds the caption, on every page without JavaScript.

**A block with neither a file name nor a language** is the case to write for, and the one an author tries last. The code still has its Copy button, so something has to hold the button; and where the script does not run, or the browser has no clipboard (plain HTTP), the button stays hidden and that something would be an empty box. So the element that holds the button and NOTHING ELSE A VISITOR READS is sent `hidden` by the server and marked as the script's `strip` target, and the script shows it together with the button. Whether that is so is the template's to say, for its own markup. The default's head strip holds the file name, the language and the button, and says it in two lines:

```erb
<% bare = filename.blank? && language_label.nil? %>
<%= tag.div class: "code-head", hidden: bare, data: { code_copy_target: ("strip" if bare) } do %>
```

(Rails leaves out `hidden` when it is false and a `data` entry that is nil.) A theme whose bar also holds the caption adds `&& caption.blank?`; one whose button stands alone in an element of its own writes that element `hidden` with the target always; one whose button sits in something that is always worth showing writes no `strip` target at all. Left out by mistake, the result is an empty bar on pages without the script; written on a bar that holds something to read, that something is hidden there.

**On a section's bands** (`sections.css`), which re-value tokens for everything inside them:

- **Tinted**: the band is the sunken ground, so code in it stands on `--th-surface`. The seven are not touched.
- **Strong re-values `--th-on-accent` too**, to the band's own colour (`--th-band-strong`), as it re-values the accent: what is written ON the accent inside the band is to the band's accent what the band is to it (9.9:1 light, about 7.0:1 dark). In the default theme one rule reads the token, selected code; a theme's own `bg-accent text-on-accent` button in a strong band follows it.
- **Strong is a raised dark ground in a dark page**: `--th-band-strong` is `#34353a` there, between 1.4 and 2:1 against the page, with its three text tokens re-valued to read on it. A code block in a strong band is therefore `color-scheme: dark` in both schemes (the light page's band is the inverted page, dark as well), so its scrollbar and selection follow the band and not the page.
- **Strong: the code is one colour** (code block spec, decision 8). The band sets six of the seven to `--th-on-band-strong` and the comment to `--th-on-band-strong-dim`, and the code's ground is the band's text colour at 12%. The band turns the page's colours round, and a second set of seven for it would be fourteen more values to keep readable. **So a theme's `--th-syn-*` do not reach code in a strong band**: the band's declaration is on an element nearer the code than the root's. A theme that wants colours there declares them in a rule of its own for `.content-section--strong`, for both schemes, and answers for their contrast itself.

**Contrast is computed, for the default theme's values only.** `test/integration/design_tokens_test.rb` reads `tokens.css` and the two bands' values from `sections.css` and holds, in both schemes and on each of the three grounds (the page's sunken, the surface in a tinted band, the strong band's sunken): every one of the seven at 4.5:1 ("every syntax colour is readable on every ground a code block has: the page, a tinted band and a strong band, in both themes": 42 pairs, the lowest the comment in a dark strong band at 4.84:1), plain code, the head strip and Copy's word at 4.5:1, and both focus rings at 3:1, Copy's on the code's ground and the code's own on what is around the block ("plain code, the head strip and Copy are readable on every ground a code block has, and both focus rings stand out, in both themes"). The same file measures the site's other values: "faint text is 4.5:1 on the page and on the tinted band, an outline in it is 3:1, and a line stays a hairline, in both themes", "the bands step from the page: tinted at 1.15:1 or more, the light strong band the inverted page, the dark one a raised ground", "the site's controls: the theme button is outlined in the faint text colour and 28px high, …" and "in a strong band the ink on the accent is the band's colour, readable on the band's accent, and a code block is dark in both schemes". It measures a token as the band values it, and "the measuring can fail: a colour too close to its ground is under 4.5, and a token is measured as the band values it" shows it awake. **Nothing measures a theme's values**: a theme that changes a `--th-syn-*`, `--th-sunken`, `--th-surface`, `--th-accent` or a band's colour has changed a pair, and its author checks it.

The third theme (`test/fixtures/themes/code`, "In tests") is a template written from this section alone, and its tests are what holds the section to the code: `test/integration/theme_pages_test.rb` ("a theme replaces the Code block's template from the contract's names alone, and a theme that does not is drawn the default one", "the third theme is sound, checked deeply too: a Code template of the contract's names and a stylesheet of the seven tokens for both schemes"), `test/system/code_block_test.rb` ("under a theme's own template the Copy button is shown, copies the stored code and says so, with nothing but the documented markup", "a theme's stylesheet that declares the seven tokens again re-colours the code in both schemes, and in a strong band the code stays the band's one colour"), `test/values/theme/contract_test.rb` ("the Code block is in the contract: its template is replaceable with the methods it may call, and its seven syntax tokens are themed tokens in the highlighter's order", "each method the Code block's template may call answers for a block with no settings, and its four words are never missing"), `test/components/blocks/code_component_test.rb` ("string answers the four words and nothing else: another key raises with the four where a theme is written, and in production is empty and logged once", "lines is read once however often a template asks") and `test/lib/theming_reference_test.rb` ("the Code block's tables name exactly the methods of its entry, the four words and what the copy script reads").

### The Note block

A highlighted note in the flow of a page: a kind (Note, Tip, Important, Warning), an optional title of the editor's own and a short rich text (note block spec; the block itself is in `docs/reference/content-blocks-and-types.md`, "The Note block"). What a theme can do with it, from the least work to the most:

1. **Re-colour it: re-colour the base tokens**, or declare the sixteen `--th-note-*` again under both selectors. Each is defined from the base in the default theme (Note is neutral, a 4% tint of `--th-ink` with a `--th-line-strong` rule; Tip is `--th-ok`, Important `--th-accent`, Warning `--th-warn`; none is `--th-danger`, which is kept for errors), so a theme that changes its base changes its notes. The text is `--th-ink`, its links `--th-accent`, inline code `--th-surface` with a `--th-line` frame. Each of the four kinds (`note`, `tip`, `important`, `warning`) has a ground, a rule, an ink and a border: `--th-note-note-ground`, `--th-note-note-line`, `--th-note-note-ink`, `--th-note-note-border`, `--th-note-tip-ground`, `--th-note-tip-line`, `--th-note-tip-ink`, `--th-note-tip-border`, `--th-note-important-ground`, `--th-note-important-line`, `--th-note-important-ink`, `--th-note-important-border`, `--th-note-warning-ground`, `--th-note-warning-line`, `--th-note-warning-ink`, `--th-note-warning-border`.
2. **Restyle it: rules of its own** under `.content-block--note`. The default template's class names (`content-block--note-<kind>`, `note-head`, `note-icon`, `note-kind`, `note-body`) are the default theme's own, not on a list.
3. **Replace its template**: `components/blocks/note_component.html.erb`.

**What the template is handed** (`Theme::Contract.components`). The component draws nothing for a note without text in the language shown or along the site's fallback (`render?`), so a template never meets one, and each method answers for an empty block all the same.

| Method | What it answers |
|---|---|
| `block` | the block: a published view on the site, the rows in a preview. `block.id` tells two notes of a page apart (an `id` for `aria-labelledby`) |
| `page` | the page the block is drawn on |
| `kind` | `"note"`, `"tip"`, `"important"` or `"warning"`; a kind stored and not on the list is `"note"` |
| `heading` | the editor's title in the language shown, with the site's fallback; without one (or with one that is only the kind's word), the CMS's word for the kind ("Tip") |
| `titled?` | whether `heading` is the editor's title |
| `word` | the CMS's word for the kind ("Tip"), titled or not, in the language shown where `config/locales/public.<locale>.yml` has it and in English otherwise |
| `icon` | the kind's Lucide name: `info`, `lightbulb`, `circle-alert` or `triangle-alert` |
| `body` | the text, rendered (the same HTML `rich_text(block)` answers) |

**What a template should keep.** The default draws an `aside` named by its heading (`aria-labelledby`), an `h3`, and never `role="alert"`: a note is part of the page, not an event. The icon is decoration (`aria-hidden`), since the heading says the kind. **Under an editor's title the kind is still said**: when `titled?`, the default puts `word` and a colon first inside the heading, visually hidden, so a screen reader hears "Tip: Before you publish", in a list of headings too; without a title it adds nothing, because `heading` is then the word and "Tip" would be heard twice. A theme's template should do the same. Print `heading` and `word` through ERB's escaping (`<%= heading %>`) and never mark them safe: the title is what an editor typed.

**On a section's bands** (`sections.css`): a tinted band changes nothing of a note. **On a strong band a note shares the band's ground and each kind keeps its colour** (spec decision 10): every ground is `--th-band-strong`, every frame the band's `--th-line`, the text the band's text, and each kind's rule and ink (its word and icon) a colour of its own that reads on the band: Note the band's dim and text, Important the band's accent (`--th-on-band-strong-accent`), Tip and Warning their hue mixed 60% with the band's text (`color-mix(in srgb, var(--th-ok) 60%, var(--th-on-band-strong))`). The band is a dark ground in both schemes, so these are light inks in both. A theme's own `--th-note-*` therefore do not reach a note in a strong band; a theme that wants other colours there, or that draws its strong band light, declares them in a rule of its own for `.content-section--strong` and answers for their contrast.

**Contrast is computed, for the default theme's values only.** `test/integration/design_tokens_test.rb` holds 72 pairs at 4.5:1 or better: `--th-ink`, `--th-accent` and the kind's ink on each kind's ground, on the page, in a tinted band and in a strong band, in both schemes ("every note's text, link and word are readable on its ground..."); and 16 at 3:1 or better: each kind's rule and ink against a strong band, in both schemes ("on a strong band a note shares the band's ground and each kind keeps its colour..."). Nothing measures a theme's values.

The fourth theme (`test/fixtures/themes/note`, "In tests") is a template written from this section alone: `test/integration/theme_pages_test.rb` ("a theme replaces the Note block's template from the contract's names alone, and a theme that does not is drawn the default one", "the fourth theme is sound, checked deeply too: a Note template of the contract's names").

### The default theme's captions, subpages list and tags

How the default theme draws three things, for a theme author who copies it (all by value and class: no token, template path or component method changed).

- **Captions** (the Code block's, the Image block's and a rich-text figure's) are text: `--th-font` at `--th-t-small` (13px, the `text-small` utility, whose `--text-small` is `theme.css`'s alias of that token), sentence case as typed (no `text-transform`, no tracking), in `--th-meta`. ## What a template may ask

The helpers of the page tree and the article (`ThemeHelper`, theming spec §7). Each is read-only and memoised for the render, answers only what the public sees, and reads none of `params`, `request`, `cookies` or `session`: "the shown page" is the page the controller resolved (`@page`), never the request's path.

**What a template gets is a node, never a page.** A `Page` in a template's hand, even one rebuilt from its copy, answers `.children`, `.parent` and `.content_blocks` from the ROWS, and no guard reads a theme's templates for that walk. The first version of these helpers answered pages; the review sent it back.

**None raises, and a 404 is nowhere.** With no page (`nil`), and on every answer that says "not found", each answers empty: no pages above, no section, no tree, no neighbours. So a frame may ask for the section on every page without a condition of its own. One consequence: a theme cannot draw a section's tree on its "not found" page with these helpers; `navigation_pages` still works there.

| Helper | Answers |
|---|---|
| `page_found?` | `true` when there is a page and the answer is not a 404. What a frame asks before it prints something OF `@page` (its title in a bar). |
| `page_ancestors(page)` | Array of `Node`, the homepage first, the parent last. `[]` for the homepage, for `nil` and on a 404. A page above that is not published or is in the trash is left out (only a preview can show a page under one). |
| `page_section(page)` | The `Node` of the page's section (the page whose parent is the homepage; a page directly under the homepage is its own) WITH ITS WHOLE TREE and `page` marked current. `nil` for the homepage, for `nil`, on a 404, and when the section or the homepage is not shown. |
| `page_tree(top, current: <the shown page>)` | `Node` or `nil`. `top` is a node or a page. `nil` for `nil`, on a 404, and when `top` is not shown or has no address in this language. `page_tree(page_section(@page))` is the same object as `page_section(@page)` and reads nothing. |
| `pages_in_reading_order(node)` | Array of `Node`: a page, then its subpages, each followed by its own. `[]` for `nil`. |
| `neighbouring_pages(tree, skip: nil)` | `[previous, next]`, each a `Node` or `nil`; `[nil, nil]` for `nil` or a tree with no current page. `skip` is a callable `(node) -> true/false` naming pages the walk passes over (a theme hands in "the pages that only group others"); the shown page is never skipped. |
| `with_heading_ids(html, levels: 2..3)` | `[html, headings]`: the html (html-safe) with an `id` on each heading of the levels, and an Array of `ThemeHelper::Heading`. `["", []]` for `nil`. |

`page` and `current` are `@page` or a node, and nothing else (`PublicSite::Branch.in_the_tree?`): handed anything that is neither, a post included, a helper answers empty (no pages above, no section, no tree) and marks nothing as the shown page. `page_ancestors(@post || @page)`, which is how `language_links` is called, answered the crumbs of the page with the post's number before: the answers are remembered by an id (`test/helpers/theme_helper_test.rb`: "a helper handed a post answers empty, never the crumbs, the section or the mark of the page with its id"; `test/queries/public_site/branch_test.rb`: "what is neither a page nor a node is nowhere and no branch's top, and marks nothing as the shown page: a post with a page's id").

**`PublicSite::Branch::Node`** (a `Data`; `app/queries/public_site/branch.rb`):

| Method | Value |
|---|---|
| `id` | Integer, the page's id: what tells two nodes apart (`node.id == other.id`), and what `page_tree` takes a top by. |
| `title` | String, as published, in the language shown, falling back as the site does. |
| `subtitle` | String or nil, as published, same fallback. |
| `slug` | String: the last part of the page's stored address in this language; `""` for the homepage. |
| `path` | String: the address, with the language's prefix and, in the preview, `/preview`. |
| `depth` | Integer: 0 for the homepage, 1 for a page directly under it. |
| `children` | Array of `Node`, in the tree's order, frozen (a node is remembered for the render). **Empty for a node that was not read as part of a branch**: the homepage in `page_ancestors` (its branch is the whole site, so `leaf?` is true of it there), and, in a preview only, a page above that the section's tree does not hold. |
| `current?` | this is the shown page. |
| `open?` | the shown page is somewhere below (false for the shown page itself; true for every node of `page_ancestors`, also in the preview of a draft, which the tree itself does not hold: "every page above the shown one is open, also in the preview of a draft that the tree does not hold"). |
| `leaf?` | no children. |
| `reading_order` | Array of `Node`: itself, then its subpages, each followed by its own. |

Because it is a `Data` it also answers `current` and `open` (the same without the question mark), `to_h` and `==` by value. Nothing else: no `parent`, `content_blocks`, `attributes`, `ancestors`, `descendants`, `page`, `record`, `published_at`, `reload` or `save`, and every field but `children` is a String, an Integer, nil or a boolean (`test/queries/public_site/branch_test.rb`: "a node is a value: it answers what is documented and no way to a record or its rows"). A node is not a page: `node.title` and `node.path`, never `translated(node, :title)`. There is no `summary`: a summary field is outside this work (decision 7).

**`ThemeHelper::Heading`** (a `Data`): `id` (String), `text` (the heading's words: markup removed, a space for a line break, white space squished), `level` (Integer, 2 for `h2`).

### `PublicSite::Branch`

It answers data and knows no helper, no view and no theme. **Which pages are in a branch and in what order is the rows' to say** (the tree is not in a copy): kept and published pages only, the rule of every public listing; a page with no address in the language shown is left out with everything under it, because there is nowhere to link it; a published page under an unpublished one is in no branch. **A title is content, and content of a published page comes from its copy** (`Publishing.published_all`), never from its rows: the spike this replaces read the rows, and a sidebar would have shown a title nobody had published. In a preview the rows are what is shown, as for `published_views`. The order is the tree's own: by position, a page without one last, then by id, as the menu, the subpage list and CS Studio's tree have it.

**The statements, whatever the branch's size** (counted at 4 pages and at 30):

- `page_tree(top)`: **four** (the pages above the top, which say how deep the branch sits; the branch's pages; their stored addresses, through `PublicSite::Paths.current_paths`, one of the reads the entry guard allows; their copies). **Three when the top is the homepage.** One more when `top` is handed over as a node other than the section already read (its row is looked up).
- `page_section` and `page_ancestors` together: **four** for a page in a section, from one read, with none per page above; one for the homepage; three when the section is not shown.
- **A page that draws its tree, its crumbs and previous and next: four in all.**

The spec said three for a branch and one more for the ancestors; `depth` counts from the homepage, which is the fourth.

`test/queries/public_site/branch_test.rb` ("a branch costs four statements at 4 pages and at 30, the homepage's three, and what is around a page four with none per page above", "titles are the published ones, and in a preview the rows'", "an unpublished page leaves with its branch", "a page in the trash is in no branch and above no page, although its address is still stored", "pages are in the tree's own order, one without a position last: as the menu's and CS Studio's tree"); `test/helpers/theme_helper_test.rb` ("page_tree, page_section and page_ancestors read a branch once per render, as published, and answer nodes", "with no page every helper answers empty and none raises", "on a 404 that has a page in hand the page is not found, and nothing of it is answered"). The default theme draws none of this, so the public canary and the trash test ask the site under the second theme (`test/integration/public_canary_test.rb`: "under a theme that draws the page tree, the crumbs and previous and next, rows overwritten without publishing reach none of them"; `test/integration/trash_visibility_test.rb`: "a theme's page tree and previous and next leave out a trashed page whose address is still stored, publicly and in preview", "a theme's crumbs leave out a trashed page above, publicly and in preview"). A trashed page loses its address, and a page with no address is left out anyway, so the first trash tests could not fail for a missing `.kept`; these two trash the page around the callbacks and assert that its address row is still there.

**In the preview of a draft page the tree, the crumbs and the neighbours hold published pages only**, as the menu does: the draft has no entry in the sidebar, nothing is marked current, there is no previous or next, and a draft directly under the homepage has no section at all. Whether a preview's tree should include drafts was not decided (the roadmap has the row).

**What still hands a template a page.** `navigation_pages`, `published_views` and `@page` itself answer `Page` objects, as they did before this work, and a template can read rows from them (`@page.children`, `@page.parent.root?`). `test/lib/public_readers_test.rb` does not scan a theme's templates and the folder check does not look for the walk; the canary under the second theme is what holds for the fixture (the roadmap has the row).

### Heading ids

`with_heading_ids(html, levels: 2..3)` is handed the rendered blocks of a page, as a `capture` of them, and gives each heading of the levels an `id` and lists them: what a table of contents and a link to a heading need.

- **Made on the RENDERED page, from each heading's words, not stored in the document** (decision 17): an id must be unique on the whole page, and a page's text is several blocks, each rendered and cached alone. **Rewording a heading changes its id**, and a link to it from elsewhere then opens the page at its top. Accepted with that consequence; the later alternative is an anchor stored on the heading, which is rich-text work (the roadmap has it).
- **Letters of any script are kept** (`ThemeHelper::Heading.id_from`). For Latin text the id is what `parameterize` answers ("Über uns" is `uber-uns`). `parameterize` alone answers nothing for Greek, Arabic, Cyrillic, Japanese or Hindi, and a page in one of them would have got `section`, `section-2`, …: ids that follow a heading's PLACE and move when a heading is added above, which is a worse consequence than the one accepted. So for every other script the id is the words themselves, lower case, with a hyphen for each run of anything that is not a letter, a mark or a digit (`εγκατάσταση-και-ρύθμιση`, `インストール-手順`). A Latin letter the transliteration does not know loses its marks and stays a letter (`huong-dan-cai-dat`, where `parameterize` puts a hyphen into the word). Only a letter that is not ASCII is asked of the transliteration, which follows `I18n.locale` as `parameterize` does.
- **Invisible characters are dropped**: format characters (a zero-width joiner or space, a soft hyphen), the variation selectors and the marks that combine with a symbol, and a mark that follows no letter or digit. So an id never starts with a character nobody can see or type: "⚠️ Warning" is `warning`.
- **A heading with no letter and no digit is `section`**, numbered like any other.
- **Duplicates are numbered**: `intro`, `intro-2`. An id a heading already has is kept and never given to another.
- **Which headings are the article's.** The article is what the template hands in, less the pieces that list or link OTHER content or are the page's furniture: a heading inside `nav`, `aside`, `header`, `footer` or a link (`a`) is neither listed nor given an id (`ThemeHelper::NOT_THE_ARTICLE`): a card that is one link. Nor is a heading inside a list item (`li`) that A TEMPLATE wrote: a post list's titles. **A heading an author wrote inside a list item of a rendered text is listed and gets its id** (a list item of a text holds blocks, and spec §7 gives each heading of the text an id). A rendered text has no wrapper of the CMS's (the element and class around it are the theme's), so a text's list item is known by what `rich_text` answered during this render: an item of the article is the text's own when it is, tag for tag, an item of one of those texts (`ThemeHelper#template_item?`). A template's item is taken for a text's only when it is the same markup as an item an author wrote on that page, heading included; a text that did not come through `rich_text` in this render is not known, and its items are a template's. A post's own text, which its template wraps in `article`, and a text in a section's column are listed. No default component draws an `h2` or `h3` of its own today.
- **What comes in is made safe first.** Rendered blocks (a `capture`) are html-safe and pass as they are; anything else is escaped, or the helper would be the way to print a typed title as markup. A text with no heading of the levels comes back as the same object, unparsed where it holds no heading at all.
- **After the render cache, never in it**: the ids are put on a copy of what `rich_text` answered ("heading ids are on the page a theme draws and not in the cached render of the text").
- **The cost** is one more parse of the article for a request that is not a 304, paid only by a template that calls the helper. The page is written out again by Nokogiri's HTML5 serialiser, which normalises markup as a browser would (`allowfullscreen` becomes `allowfullscreen=""`, a `table` without `tbody` gains one).
- **An id may hold non-ASCII letters.** `href="#<%= heading.id %>"` works as written; a theme's script that builds a CSS selector from an id uses `CSS.escape` or `getElementById`. **And an id can equal an id the theme's own frame uses** (`taken` is collected from what the helper was handed, which is the article, not the frame): a heading "Menu" under a frame with `id="menu"` is two elements with one id. Nothing guards it (the roadmap has the row).

`test/helpers/theme_helper_test.rb` ("with_heading_ids gives each heading of the levels asked for an id made from its words, and lists them", "two headings alike, an empty one, one in another script and one with markup each get an id of their own", "a heading in another script keeps its letters: its id is its words, not its place on the page", "an emoji leaves nothing in an id: no selector, no joiner, no keycap, and a heading of emoji alone is section", "only the article's own headings are listed and given an id: not a list's titles, a card's, or the furniture's", "a heading an author wrote inside a list item of a text is listed and given an id; the same heading in a template's own list item is not", "a string that is not markup comes back escaped: with_heading_ids is no way to print a title as markup").

## The render cache and the ETag

The public ETag and the rich-text render cache are keyed on `RichText.code_revision` (`KAMAL_VERSION`, else a `REVISION` file, else a value chosen at boot). A site's image rebuilt on the same CMS image with a changed theme moves none of the three in a way that is promised. So **`Theme.current.fingerprint` is one of the ETag's keys** in `PagesController#show`: a changed theme is never answered 304 (`test/integration/public_caching_test.rb`: "another theme, and the same theme with one byte changed, answer 200 where the same theme answers 304", in both directions). That is the whole change: the stylesheet's and the scripts' addresses are digested and printed in the page, and the rich-text cache needs nothing, because a theme styles a rendered body and does not change its HTML.

A page's ETag also moves when another page of its tree is published under a new title (the content version), so a sidebar is never confirmed stale (`test/integration/theme_pages_test.rb`: "a page a visitor has is asked for again when another page of its tree is published under a new title").

**What the ETag cannot see is what a template reads beyond the contract.** A public page is one cookie-less answer for every visitor, so a theme's template reads the page, the tree, the site and the language, and never `params`, `request`, `cookies`, `session`, `flash` or the clock. `theme:check` refuses a template that names one of the first five where it is written by name ("The deep depth" lists the spellings it does not see); the clock and a query of a template's own it cannot see, and a theme that reads what the ETag does not cover serves stale pages to returning visitors.

## Checking a folder

`Theme::Check.problems(folder, deep: false)` answers sentences; an empty answer is a sound folder. Each starts with the file, says what is wrong and ends with what to do: it is read in a boot log, or in a build's log, by whoever started it.

**Strict on purpose** (decision 14). A file the contract does not name is a problem, not something to ignore: a misspelt `pages/shwo.html.erb` would otherwise silently never be used, and a theme that holds `layouts/application.html.erb` would replace the CMS's head, since the view path finds whatever is there.

**THIS IS A FENCE AGAINST MISTAKES, NOT A SANDBOX.** The reading of a template's source looks for names and literal tags, so a tag built from a string at run time, or a name reached another way, is not seen, and nothing here is meant to stop an author who wants to get past it. It is for the honest mistake: a `_head` copied from another project with its canonical link and its `csrf_meta_tags` still in it. What holds whatever a theme writes is elsewhere and narrower: the CMS's head tags are lines of the layout, and the public site commits no session and lets no cookie leave.

### The plain depth: at boot, and on every development reload

1. **A stranger at the folder's top**: whatever is there NOW and is none of the four folders, each as ONE problem with the folder's own sentence ("`<name>` is not part of a theme. A theme folder holds the folders views, components, assets and javascript, and nothing else (dot files and a README are ignored). Move it out of the folder or delete it."), whatever it is and whatever is in it: a file, a folder (a `lib` with thirty files is one line), an empty folder, a folder named like a file, a FILE named `views`. Nothing else is asked about a file under one. `ThemeFolder` refuses the same entries when the folder object is made (`check_shape!`), which is once per process; this is the reading that meets a note saved beside the templates while a development server runs (`ThemeFolder#strangers`).
2. **A file with no place** (`misplaced`): under `views`, anything but a template of `TEMPLATES` or a `.html.erb` under `views/theme/`; under `components`, anything but `<a component of Theme::Contract.components>.html.erb` (a `.html.erb` there that no registered type hands out is said as such, with the type and what to do: "… replaces the template of <path>, which no registered type hands out: the block type "<type>" it is named for is not installed. Remove the template from the theme, or install the type.", the owner's answer 3 of the block types spec, for a gem removed from a site whose theme still replaces its block. The type is read from the path, `blocks/<type>_component` or `<owner>/<name>_component`; for another path the sentence says "which no registered block or content type hands out: the type it belongs to is not installed"; and a template of one of the CMS's own components that is not replaceable, such as `media/picture_component`, keeps the generic sentence, since no type of it is missing: `test/values/theme/check_test.rb`, "a template of a component no registered type hands out is refused by name, and the message names the type and says to remove it or install the type", "a template of one of the CMS's own components that is not replaceable is not part of the contract, and no type is said to be missing"); under `assets`, anything but `stylesheets/theme.css` and an image or font by its extension; under `javascript`, anything but `controllers/**/*_controller.js`. Such a file is ONE problem, and nothing else is said of it: whether its name is also one of the CMS's, and what it says inside, is nothing its author can use before it has a place.
3. **A hidden template**: a dot file that is an `.erb` under `views/` or `components/`. The folder passes dot files over (`.DS_Store`, `.keep`), and a template is on the view path all the same, unchecked and outside the fingerprint.
4. **An asset named like one of the CMS's own** ("Assets and scripts", above).
5. **A template that is not UTF-8**: one problem, and nothing else is said of that file.
6. **What a template's source says** (`written`). **Code and markup are read, and nothing else**: not a comment (ERB's `<%# %>`, Ruby's `#`, HTML's `<!-- -->`), not the words of a string, not the template's text. A helper's name is asked of each ERB tag's code, as the lexer reads it ("How a template is read", below). An attribute that makes a tag what it is (`rel="canonical"`, `property="og:url"`, `name="csrf-token"`) is asked only of a tag: a `<link>`, `<meta>` or `<script>` written out in the template's text, up to its own `>` (an ERB tag inside it is a blank there), or one built by a helper inside one ERB tag (`tag.link`, `tag.meta`, `tag.script`, `tag(:link, …)`, `content_tag("meta", …)`, `javascript_tag`), which is read with its strings (`Theme::Check.markup_of`). The first site with a theme documents this CMS, and "We set og:url for you" in a paragraph stopped its boot with "prints the og:url tag" while these patterns were asked of the whole source.
   - one of the CMS's head tags, in ANY template of the theme (a partial is rendered from anywhere): a canonical link (`rel` canonical); a language link, which is a `<link>` with `rel="alternate"` AND `hreflang`; the `og:url` tag (`property` or `name`); the CSP tag (`csp_meta_tag`, a `meta` named `csp-nonce` or with `http-equiv` `Content-Security-Policy`); the import map (`javascript_importmap_tags`, `javascript_inline_importmap_tag`, a script of `type` importmap); a stylesheet link (`stylesheet_link_tag`, `rel` stylesheet, whatever it links). An attribute is seen in every spelling (`rel="canonical"`, `rel: :canonical`, `:rel => "canonical"`, and among other values);
   - the CSRF token asked for (`csrf_meta_tags`, `form_authenticity_token`, a `meta` named `csrf-token` or `csrf-param`);
   - a form that is sent with a token: `form_with`, `form_tag`, `form_for` or `button_to`, unless the same ERB tag says `method: :get`;
   - **a cookie written**: an assignment through `cookies[…]` (also through `.signed`, `.encrypted` and `.permanent`), `session[…]` or `flash[…]`, `cookies.delete`, `reset_session`, and the response's `set_cookie` and `delete_cookie`. The wall takes every cookie off a public response, so the write is lost; this is the sentence that tells the author when the application starts, not a visitor's forgotten consent. Reading one of them is the deep depth's. Not refused for a name the template bound itself (a loop over `|session|`);
   - **a cache of the theme's own**: `cache`, `cache_if`, `cache_unless` (bare, or asked of `helpers.`, `controller.`, `self.`) and `Rails.cache`. The public page and the preview draw the SAME template of a theme, and Rails keys a fragment by the template's path, its digest and the name it was given: nothing in the key says which of the two is drawing, and the preview draws rows nobody has published. A sidebar wrapped in `cache "sidebar"` is filled by whichever comes first; filled by an editor's preview, it is served to every visitor until it expires, and no publish changes it. It is the obvious optimisation and not an evasion, which is why it is refused at this depth and not only at the build. Nothing is lost: a public page is already answered whole by its ETag. Not a Hash key (`data: { cache: "1" }`), not `cache_key`, not a local the template assigned;
   - a write to the head's slot (`content_for :head`, `provide :head`, the name as a symbol or a string);
   - an assignment to an instance variable, in any form (`@page = …`, `||=`, `+=`, `<<=`, `instance_variable_set`);
   - a `_frame` that never prints the page: no printing tag (`<%=`, `<%==`) holds `yield` without a name after it;
   - a `_title` that prints nothing.

**Let through on purpose**: `hreflang` and `rel="alternate"` on an `<a>` (`link_to name, path, hreflang: code, rel: "alternate"` is how a language switcher in the page is written, and the default one has it); `rel="canonical"` on anything that is not a `link`, `meta` or `script` tag; a feed's `<link rel="alternate">`; `rel="preload"`; a second `<title>`, a viewport, a description and the other `og:` tags (extra markup after the CMS's, not refused); a GET form and a plain `<form>` tag; a frame that hands `yield` on (`<%= tag.main yield %>`, `<%= render "theme/body", content: yield %>`); and every one of these words where it is no tag and no call: in a sentence of the page, in a string (`link_to "About csrf-token", …`), in a comment of any of the three kinds, in an escaped sample (`&lt;%= csrf_meta_tags %&gt;`).

**Still not seen** (a fence): a tag whose attribute is printed by ERB at run time (`<link rel="<%= kind %>">`); an attribute's words inside a string of a tag helper's call (`tag.meta name: "description", content: "use rel: canonical"` is refused, wrongly, for the words after `content:`); a cookie written through a bracket inside a bracket (`cookies[keys[0]] = …`) or by a script in the browser; a cache reached through another name; `render "pages/seo_meta"`, `render "shared/theme_head"` and `content_for :title` in a theme's template, which print the CMS's tags a second time or do nothing, and which nothing refuses (the roadmap has both).

### The deep depth: `theme:check`, the build's gate

`deep: true` does the above and two things more:

- **It compiles every template**, inside a method as Action View does (a frame yields, and `yield` at the top level is a syntax error), so a syntax error is found at the build and not by a visitor. The message is one sentence worded from Prism's first error: the line and what Ruby found there; a block that is never closed, said as that and not as a line after the template's last; one `<% end %>` too many, said as that with its own line.
- **It reads each template for `params`, `request`, `cookies`, `session` and `flash`**: the bare name, and the name asked of `helpers.`, `controller.` and `self.`. Not a method of something else (`text.request_id`), not a symbol, not a Hash key.

**How a template is read.** The Ruby of a template is read by Ruby's own lexer (`Ripper.lex`), **one ERB tag at a time**, and the fences ask their patterns of a tag's CODE: what is left when its comments and the words of its strings are taken away. Telling the three apart is the lexer's work and not a pattern's. An earlier reading took comments away first ("a space, a hash, to the line's end") and strings second, so `style: "color: #123456"` lost its closing quote, the quote left over paired with the opening quote of the NEXT string, and from there to the template's end words were read as code and code as words: `link_to "Our cookies", "/cookies"` was refused at a site's build as "reads cookies", and a real `@page = nil` between two such strings was not seen. Not read: comments, the words of every string form (quotes, `%q`, `%Q`, `%w`, `%i`, heredocs, regular expressions, a character). Read: everything else, and what a string interpolates, at any depth. Per tag, because a tag is where ERB itself cuts and a tag is a fragment (`end`, `}`, `items.each do |item|`), which the lexer reads.

**The deep check gates a site's build, so where it is unsure it lets through.** A wrong refusal blocks a deploy. What it therefore misses, all of it known:

- a name reached by `send`, through a local alias (`r = controller; r.request`), with `&.` (`helpers&.request`), by a keyword's shorthand (`render "theme/x", params:`), or through a helper of another name;
- **a fenced name the template binds itself, from the tag that binds it onward** (`bound_in`, `bound_through`): a block's parameter (`sessions.each do |session|`), a lambda's, or a local that is assigned. From that tag on the name is the theme's own variable, and a template that lists a conference's sessions is not told to "take session out". **A read BEFORE the binding is refused** (a `request.remote_ip` at a template's top with a loop over `|request|` at its bottom is the mistake the fence is for; the exemption once covered the whole template). The price that is left: from the binding tag to the template's end no read of the view's method of that name is seen, in the binding tag itself (`request = request.path`) and after the block has closed, and a default value in a parameter list binds what it names (`|a, b = params|`);
- a read written after one of three spellings Ruby reads by whether the name in front is a local, which one tag does not know (`width /2, "/cookies"`, `ok ?"cookies" : "session"`, `list <<name`): the tag is read both ways and a fence speaks only when both readings hold what it looks for (`reads?`);
- `response` and `headers`, which are not fenced at all (the status is not "per visitor", so the fence's sentence would not be true of it);
- an `end` too many FOLLOWED by a block never closed, which compiles (the two cancel out inside the wrapper);
- a walk of rows from a page (`@page.children`), a `<script src>` from another host, the clock, and a query of the template's own.

`test/values/theme/check_test.rb` holds each rule and each thing let through (among them "a file the contract does not name is refused by name: a misspelt template, a backup file, a layout", "a file with no place in a theme is one problem, whatever it holds and whatever it is named like", "a template that prints one of the CMS's own head tags is refused, by its file and by the tag", "the reading is not fooled: a comment, a word in text, a language link in the page, a feed link, another slot", "a string that holds a hash sign, or a quote inside quotes or a regex, does not turn the reading of what follows inside out", "a block parameter, a lambda's parameter and a local named like a fenced word are the theme's own, in every tag after", "a fenced word read BEFORE the template binds it is still refused: a block parameter or a local further down exempts the tags from there on", "a head tag's, the token's and the head slot's words are no tag: in a sentence, in a string, in a Ruby or an HTML comment, in an escaped sample", "a real tag beside its word in a comment is still refused, once, and a tag built by a helper is read with its strings", "a template that writes a cookie, the session or the flash is refused when the application starts, and the message says the write is lost", "a template that caches a fragment or asks the application's cache is refused when the application starts, and the message says why and what to do", "whatever appears at a folder's top after it was read is one problem each, with the folder's own sentence, and never an exception", "a tag that is a fragment of Ruby is read like any other: the words of its strings are not"); the boot is `test/lib/production_boot_test.rb` ("production with a theme folder that holds a file the contract does not name does not start, and names the file": the one proof that the contract is checked when the application starts).

## `theme:new` and `theme:check`

The path is a rake argument, so the shell needs the quotes:

```sh
bin/rails 'theme:new[../my-site/theme]'
bin/rails 'theme:check[../my-site/theme]'     # or, with THEME_PATH set:  bin/rails theme:check
```

A space in the path is carried by those quotes. **A comma is not**: rake cuts a task's arguments at every comma and trims around them, so what was between the pieces cannot be put back. A path that arrives in pieces is refused with that sentence, never used by its first piece, and is given in a variable instead: **`THEME_NEW_PATH`** for `theme:new` (read when the bracket is empty, and by nothing else), `THEME_PATH` for `theme:check`.

**`theme:new`** (`Theme::Scaffold.write`) writes the default theme into a folder of a theme's shape (decision 15: the default theme's templates stay where Rails and ViewComponent put them, and this copy is how they are "the example to copy"). **What is copied is the contract**: every template of `TEMPLATES` and every component template of `Theme::Contract.components` (an outside type's from beside its component, `Theme::Contract.template_for`), so a line added to either is copied from that day on and nothing the contract does not name can be; plus `assets/stylesheets/theme.css` (a comment that names every token and declares nothing), a `.keep` in each folder a theme may fill, and a `README.md`. A site under the written folder is drawn byte for byte as before; its author then deletes what they do not want to own, because a file the folder does not hold comes from the default theme and follows it through upgrades. It writes into a new folder or an empty one, and a folder is empty when everything at its top is what a theme folder passes over (a repository, dot files, a README, which is kept and ours not written). A path taken from `THEME_NEW_PATH` is said BEFORE anything is written ("The path is THEME_NEW_PATH's: <path>"): a variable left in a shell from the last run names a folder nobody is thinking of. It prints how many files it wrote and the next step with the path quoted as a shell needs it, so the line pastes; the next step is `THEME_PATH=<path> bin/dev`, the command that also builds the stylesheet as a file is saved (with `bin/rails server` the templates would be the theme's and the stylesheet whatever was built last, said only in System status). **It is not `=> :environment` either**: an integrator exports `THEME_PATH` once, for the folder this command is about to make, and the application does not start under a path that names no directory, so a `THEME_PATH` that names none is taken out of that process before the application starts, with the line "THEME_PATH names no folder yet and is not read by this command." (`test/tasks/theme_tasks_test.rb`: "theme:new says, before it writes, that the path is THEME_NEW_PATH's, and says nothing of it for a path in the brackets", "theme:new runs under a THEME_PATH that names the folder it is about to make"; `test/values/theme/scaffold_test.rb`: "the folder it writes has no problem, checked deeply, and loads", "a site under the folder it writes is drawn byte for byte as under the default theme: every block type, a section, the three lists, a post of each type, a 404, two more languages and a sample of every type" (a page that every copied component draws, each shown to be the copy's, and a page of every registered type's sample, the outside `gallery/album` included), "its README says how to run it while writing, where the folder goes and that the templates are code", "a folder that holds only a repository, dot files and a README is empty: it is written into, and the README is kept").

**`theme:check`** runs the deep check and says every problem as one numbered line on stderr, then `<path>: N problems.`, and ends 1; a sound folder is one line, `<path>: N templates, no problems.`, and 0. Never an exception's trace for a folder that is refused: this output is read in a build's log. It needs no stylesheet, no database and no secret outside production, or in production with `SECRET_KEY_BASE_DUMMY=1`, which is how a site's Dockerfile runs it (a production boot without it asks for the secret and for the stylesheet's stamp, `config/application.rb`).

**It is not `=> :environment`: the task starts the application itself, inside `ThemeFolder.checking { … }`.** Under a `THEME_PATH` whose folder the contract refuses the application does not start, so as a prerequisite the boot ended the command before the task's body ran, with rake's "aborted!", a trace and the boot's half of the list only, and the deep half (a template that does not compile) came to light one build later. Inside `checking` the initializer keeps a refusal as it does on a reload and does not log it, and the task says the whole list. It is the one boot of a refused theme that does not raise.

What still ends it before the list, each as one sentence with no trace and exit 1: a path that is no directory, something at the folder's top that is no part of a theme (all of them together), a file that cannot be read, a link out of the folder, a hidden folder inside the theme (`ThemeFolder::Invalid`: the folder cannot be read as a theme at all, so there is no list to make; these three come one at a time, since the walk stops where it cannot go on), and in production with a real secret a stylesheet built for another theme. And when a path is checked while `THEME_PATH` names ANOTHER folder that is refused, the task says so after its own report and ends 1: saying nothing would end 0 in a process whose every public page raises. Not when the path asked about IS that folder (`theme:check[x]` with `THEME_PATH=x`, compared by where each really is): it was checked, and its list is above (`test/tasks/theme_tasks_test.rb`: "theme:check of the very folder the application started under does not say that another folder was not checked", "theme:check names every problem, the deep ones too, and exits 1", "theme:check under a THEME_PATH the application does not start under names every problem, the deep ones too, with no trace", "theme:check of a path while the theme the application started under is refused says so and ends 1", "a path with a comma is refused in the brackets with the way to give it, and taken from THEME_NEW_PATH").

## Deployment

**A theme reaches a container as an image layer on the CMS image, never as a mounted volume** (decision 16). The stylesheet, the digested images and fonts and the import map's pins are all made at build time; a volume could change without a build. For a person: **changing the theme of a running site is a build and a deploy**, and in development you edit a file in the folder and reload the page.

A site's `Dockerfile`, as built and run by hand for this work (`docs/reference/hosting.md`, "How a site's image is built", has each line's reason):

```dockerfile
FROM <the CMS image>
ENV THEME_PATH=/rails/site-theme
COPY --chown=1000:1000 theme/ /rails/site-theme/
RUN SECRET_KEY_BASE_DUMMY=1 ./bin/rails theme:check && \
    SECRET_KEY_BASE_DUMMY=1 ./bin/rails assets:clobber assets:precompile
```

**The theme is a folder of the site's repository (`theme/`), with the `Dockerfile` beside it and not in it.** A theme folder's top holds the four folders and nothing else, so a `Dockerfile` at the root of a repository that IS the theme is refused as a stranger; the README `theme:new` writes says the same.

**`theme:check` goes BEFORE `assets:precompile`**, where the spec had it after: `assets:precompile` starts the application, which does not start under a refused folder, so with the precompile first a refused theme ended the build in rake's trace with the boot's half of the list, and `theme:check` was reached only for a folder the application starts under. Check first, the build's log is the numbered list.

**`bin/theme-build-check`** is the two halves of "a site's image on top of the CMS's" that are the CMS's own, tried with the second theme **copied to a folder outside the application** with an image, a font and a controller in it. That is what every real site's theme is, and a check that only ever saw the fixture inside the application was green while no such site started. It builds the stylesheet with `THEME_PATH` set and finds in it the default theme's tokens, a default utility, the theme's accent and own rule, a utility used only in the theme's templates and the theme's image by its bare name; starts production under the theme with a real secret and requires the boot line, the stamp, the theme's controller in the import map, its image and font on the load path, the image at its digested address in the served stylesheet and the stamp being no asset; and runs the **deep check** under production, and then shows it awake (a copy with one broken template must be refused). CI runs it as a step of the `test` job after the unit tests. **It is not in the test suite and is never run while tests or a watch run**: it writes `app/assets/builds`, which every other test reads. On its way out it builds the DEFAULT stylesheet again, whatever `THEME_PATH` the shell has, and ends non-zero when that rebuild fails.

**CI builds no image** (a run is billed, and there is no Docker job). The image on top was built once by hand, and "As built" in the spec records what it proved, down to a public page drawn by the site image under its theme.

**No CMS image is published yet**, and publishing one is its own work. Until then a site builds the CMS image itself from the revision it pins and builds its own on top.

## In development

A change to a file of the theme reloads the application at the next request, as a change under `app/` does (`watchable_dirs`), and `theme_css:watch` rebuilds the stylesheet. What needs more than a reload:

- **A template FILE added to or removed from the theme is seen by the next request.** The watched folder has changed, the reload builds a new `Theme`, and the new theme answers the new file's subclass (or the CMS's class again). Observed with a development runner: a component template added under a running theme made the reloader report a change, and the theme built by that reload held it. `Theme` remembers per component whether the folder has its template (`@components`), which is why it is a new `Theme`, and never the old one, that sees the file; in the test environment nothing reloads, so a test that adds a file builds a new theme ("In tests").
- **A new controller file needs a restart, the first one and every one after it.** The import map is drawn when the application starts (`ThemeFolder#pins` is nil without a `javascript/controllers` folder), and importmap-rails sweeps its cached map only for `app/javascript` and `vendor/javascript`, not for a theme's folder. Observed with a development runner: a controller file added to a folder that held one at boot was in no map after everything a request does before its action (both sweepers, the reloader). A CHANGED controller file is served as it is now. `config/importmap.rb` says the same.
- **An asset folder that did not exist at boot** (`assets/images`, `assets/fonts`, `javascript`) is not on the load path until a restart: the paths are appended once.
- **Something new at the folder's TOP, put there while the process runs, is a refusal on the next reload**, like any other problem of the folder: one line in the list, the public pages answer with it, CS Studio works, and deleting the entry and saving a file clears it. `ThemeFolder.current` checks the top once, when the process starts, so `Theme::Check` asks it again each time (`ThemeFolder#strangers`). It was an exception out of the reloader's prepare (a `KeyError` for `notes.txt`, a `NoMethodError` for a file named `views`), which left the type registries empty.
- **Nothing leaves a reload's prepare.** `Theme.prepare` on a reload keeps whatever the check raises, a fault of its own included, as a refusal that says what was raised ("THEME_PATH (…) could not be checked: KeyError: …"); at boot a fault is raised as it is. `StandardError` and not a list of what the check raises today, because that list was the thing that was wrong (`test/values/theme_test.rb`: "on a reload prepare keeps whatever the check raises as the refusal, with what was raised in the message; at boot it is raised as it is"; `test/integration/theme_pages_test.rb`: "a file that appears at a theme folder's top is a refusal on the next reload, not an exception: the registries are prepared and the public page names the file").
- **A refused folder is said on every public page** until it is corrected, and CS Studio keeps working.

## In tests

- **The test environment ignores `THEME_PATH`**, and `test/test_helper.rb` deletes it. No test sets `ENV["THEME_PATH"]` in its own process; a test of a child process hands it to the child (`test/lib/production_boot_test.rb`, `test/tasks/theme_tasks_test.rb`).
- **`with_plain_theme { … }`** (`test/support/theme_test_helper.rb`, included in every test case) is the one way a test is drawn by a theme: `Theme.with(plain_theme, &block)`, where `plain_theme` is `Theme.load(ThemeFolder.new(PLAIN))`. A system test's server runs in the test's process, so the swap reaches it. `Theme.with` is process-wide: two tests in one process must not run under different themes at once (the suite's parallelism is by process).
- **`with_theme_copy { |dir| … }`** yields a copy of the second theme in a directory of its own, for a test that adds, changes or removes a file. Load it with `Theme.load(ThemeFolder.new(dir))`: a theme made with `Theme.new(path:)` is unchecked and has the fingerprint `default`, so the ETag does not tell it from the default theme. **One `Theme` does not re-read a changed template in the test environment** (ViewComponent compiles once, and Action View caches a template by its path): a test that edits a file builds a new theme, in a copy of its own.
- **The third theme, `test/fixtures/themes/code`**, and `with_code_theme { … }`: two files, a template for the Code block written from the contract's nine names and the copy script's markup (it draws a `div.plain-code`, never the default's `figure`), and a stylesheet that declares the seven syntax tokens again for both schemes. Neither its assets nor a controller are on the test environment's paths: it has no image, font or script, and the suite's built stylesheet is the default theme's, so the browser test that shows its tokens at work puts the file's text into the page after the built stylesheet, which is where the build puts a theme's.
- **A fourth theme, `test/fixtures/themes/note`** (`with_note_theme`), is a Note template written from "The Note block" alone and a stylesheet for it.
- **The second theme, `test/fixtures/themes/plain`**: plain CSS, no utilities but one. It replaces `_frame`, `_title`, `_icons`, `_head`, `pages/show`, the Rich text block's template and one post list (`posts/blog_list_component`); it changes `--th-accent` for both schemes; it brings two partials under `views/theme/`, one controller (`hello_controller.js`) and one image. Its frame and page draw the section's tree, the crumbs, a table of contents and previous and next on every page, which is why the canary and the trash test can ask it. **It deliberately does not replace the header, the footer, the Image block, the Code block or the 404**, so every test of it is also a test of the fallback. Any file added to it changes its fingerprint; no test pins the value.
- **The second theme's assets and controller are on the test environment's paths from the start** (`config/environments/test.rb`, `test/fixtures/themes/importmap.rb`): Propshaft's load path and the import map are fixed when the application starts and the suite swaps themes in-process. So `image_path("plain-mark.svg")` resolves under the default theme too, and "the default theme has no theme controller in its map" cannot be shown in the suite; the browser test shows the other half, that it is not REGISTERED off the public site.
- **The suite's stylesheet is the default theme's.** System status' Theme row therefore WARNS under `with_plain_theme` (the stamp is `default`): a test that wants the OK row under a theme hands `stylesheet_probe: -> { true }` to `Setup::SystemCheck`.
- **Never run a build while tests run.** A build takes the stamp away for its duration (`ThemeCss.build`), and two tests read the working tree's stamp (`test/models/setup/system_check_test.rb`: "the row's own probe reads the build's stamp: this suite's stylesheet is the default theme's"; `test/integration/admin/system_status_test.rb`: "the theme row names the theme that draws the site and no path of the server, and warns when the stylesheet is another theme's"); every public integration test needs `app/assets/builds/theme.css`, which a fresh worktree does not have until `bin/rails tailwindcss:build` (or the full `bin/rails test`) has run. `bin/rails tailwindcss:build`, `bin/dev`'s watch and `bin/theme-build-check` are all builds.
- **Development and test share the built stylesheet and its entry**: a test run leaves the default theme's behind, also under a running `bin/dev` (above).
- The unreadable-file tests of `test/lib/theme_folder_test.rb` skip when run as root, who reads everything.

## What is not built

New blocks beyond the Code block (Note and Table are the catalogue's). Syntax colours of their own on a strong band (the code is one colour there). A check of a theme's own colours for contrast. A theme's own HTML for rich text. Stored heading ids, list variants, a language on code blocks, tables in rich text. Search. A summary field, a navigation title or "show in menus" on a page. A group heading that is not a page. A link in the menu that leaves the site. The frame option on images. The product's version in a template. A template per page type. The content width as a token from which image `sizes` are made (a theme with another width passes its own `sizes` to `Media::PictureComponent`). Appearance settings in CS Studio. Several themes in one site, or a theme chosen per page or language. A published CMS image. A stylesheet per environment. A `script-src` or `style-src` in the public content security policy. A preview tree that holds drafts. A content API.

## What a change can break silently

- **A name on `Theme::Contract` renamed or removed as a cleanup** breaks themes that live outside this repository. It is a release-note change. The lists are held to the code (`test/values/theme/contract_test.rb`: "every component a type registry hands out is on the list, and the list holds nothing else", "every listed component has its default template and every method its template may call", "every listed template has its default under app/views, and says what it is", "every listed helper is one a template can call", "every declared token is defined, a themed one for light and for dark, and no --th- name is undeclared", "a block type registered without theme methods is refused at registration, and the message says what to declare") and to this file (`test/lib/theming_reference_test.rb`: "the helpers table names exactly the contract's helpers" and its four siblings, one per table).
- **A built-in block type's name dropped, renamed or added in its declarations.** The block lines and tokens are derived from `theme_methods` and `tokens`, so a method taken off a type's line, a token renamed or a type deleted changes the contract with nothing else red: the ledger is the brake, the built-ins' part of the contract written out by hand and changed only with a release note (`test/support/contract_ledger.rb`; `test/values/theme/contract_ledger_test.rb`: "the built-in types' part of the contract is the ledger: a name added, renamed or removed is a release note", "the ledger can fail: a method dropped from a built-in's line, and a token renamed, are each named"). The tables of this file are held to the ledger, not to the derived lists, so a gem's lines never reach them.
- **An outside type's lines** are the site's contract while its gem is installed: the check lets a theme replace its template, `theme:new` copies it and names its tokens, the build imports its stylesheet and scans its folder (`test/lib/content_spiel/plugins_test.rb`: "a type registered through the hook survives a reload, after the built-ins, and the theme check still knows its template", "theme:new copies an outside type's template and names its token; the build imports its stylesheet and scans its folder"). Once the gem is removed, a theme that still replaces its template is refused by name, and the block is dormant ("a block of an outside type that is no longer registered is dormant: the page answers, the editor names it, the copy stays, and a theme's template of it is refused by name"; `test/values/theme/check_test.rb`: "a template of a component no registered type hands out is refused by name, and the message names the type and says to remove it or install the type"). **No guard** for an outside template's Tailwind colours (above), nor for the set of outside types in the public ETag: an image rebuilt with a gem added or removed on the same CMS revision has a 304 confirm a page drawn with the old set.
- **A target, a value or the action of `code-copy` renamed**, or a class the script now needs on an element: a theme's own Code template keeps the old markup and its button is dead or its press an error in a visitor's console, with nothing failing here once the default template is changed with the script. It is a contract change (`test/lib/theming_reference_test.rb`: "the Code block's tables name exactly the methods of its entry, the four words and what the copy script reads", which reads the script's `targets` and `values`; `test/system/code_block_test.rb`: "under a theme's own template the Copy button is shown, copies the stored code and says so, with nothing but the documented markup"). **No guard** for a role added to `CodeHighlight::ROLES` reaching a theme: its token is then missing from every theme's stylesheet, which is harmless (the default's value is in the build), and a theme's own template that maps roles to its own classes draws the new role plain.
- **A `--th-syn-*` given a value in a band, or a band's ground changed**, moves a pair nobody looks at: `test/integration/design_tokens_test.rb` computes all of them from the files ("every syntax colour is readable on every ground a code block has: the page, a tinted band and a strong band, in both themes"). A colour written in `code.css` or `sections.css` instead of a token is refused (`test/values/theme/contract_test.rb`: "the default theme's styles and templates hold no colour literal: tokens.css is the one place").
- **A second place that puts the theme's views on a path**, or `prepend_view_path` in `ApplicationController`, lets a theme's file named like an admin view be drawn in CS Studio (`test/integration/theme_pages_test.rb`: "nothing of a theme reaches sign-in: a theme's file named as the product layout or the sign-in view is never drawn", "nothing of a theme reaches CS Studio: a theme's file named as the admin layout or the dashboard is never drawn", "nothing of a theme reaches setup: a theme's file named as the setup layout or a step is never drawn", "nothing of a theme reaches the password pages or a mail: a theme's file named as either's view or layout is never drawn"; `test/integration/public_javascript_test.rb`: "only the public layout loads the site entry point, and with it the theme's controllers"; `test/system/theme_script_test.rb`: "the sign-in page registers the site's controllers and not the theme's"). **No guard** for a job that renders through the theme's path: none does.
- **A tag a site breaks without, moved into a theme's partial**, is lost by every theme that replaces the partial; **a tag that is look or voice, written into the layout**, cannot be changed by any (`test/values/theme/contract_test.rb`: "what the layout renders of the theme's is on the list, and what is the CMS's is not").
- **A `content_for` slot read by the public layout** is a way for any theme template to write among the CMS's head tags (`content_for` appends, and the page is rendered first); and **a head decided by `@page` and not by the response's status** describes a record on a 404 that has one in hand (`test/integration/theme_pages_test.rb`: "every tag the CMS writes into the head is there exactly once under both themes, ahead of the theme's own", "a theme's template that writes to the head's slot puts nothing into the head: on a page, in a block and on a 404", "a 404 that had a record in hand describes none: the site's title and no description or Open Graph tag"). **No guard** for a theme's template that changes the record in memory (`@page.title = …`) or the response's status: the layout reads both after the page template ran.
- **`Theme::Check` loosened to "ignore what it does not know"**, or a theme's failing template rescued with the default one (`test/values/theme/check_test.rb`: "a file the contract does not name is refused by name: a misspelt template, a backup file, a layout"; `test/integration/theme_pages_test.rb`: "a theme's page template that raises is an error that names the theme's file, not a fallback"). - **A second place that names ViewComponent's `sidecar_files`**, or the theme's template compiled into the CMS's own class: one process then holds one theme (`test/values/theme_test.rb`: "the same block is drawn by two themes and by the default in one process, in any order", which is also the guard of a ViewComponent upgrade).

- **A build that leaves the default theme's styles out, or imports the theme's first**, unstyles every template a theme does not replace, the preview bar included (`test/lib/theme_css_test.rb`: "with a theme the entry imports the default first, then the theme's stylesheet, and scans the theme's templates and scripts").

- **A public helper that reads a page's rows**: `page.children`, `page.ancestors` or `self_and_descendants` in a helper, where `PublicSite::Branch` reads the copies; or one that hands a template a `Page` where it handed a `Node` (`test/integration/public_canary_test.rb`: "under a theme that draws the page tree, the crumbs and previous and next, rows overwritten without publishing reach none of them"; `test/integration/trash_visibility_test.rb`: "a theme's page tree and previous and next leave out a trashed page whose address is still stored, publicly and in preview", "a theme's crumbs leave out a trashed page above, publicly and in preview"; `test/queries/public_site/branch_test.rb`: "a node is a value: it answers what is documented and no way to a record or its rows"). **No guard** reads a theme's own templates for a row walk, and `navigation_pages`, `published_views` and `@page` still hand one a `Page`.

- **A fragment cache in a public template, the CMS's own included**, is shared by the public page and the preview unless its key says which is drawing: `Theme::Check` refuses one in a theme's template, and nothing reads the default templates for it (`test/integration/theme_pages_test.rb`: "a fragment a theme's template caches is shared by the preview and the public page: an unpublished title reaches a visitor, which is why the check refuses it", which shows the leak with a real store and passes while it is there).
- **A pattern of `Theme::Check` asked of a template's whole source** refuses a word in a sentence or a comment and stops a site's boot for it: a helper's name is asked of a tag's code, an attribute of a tag ("a head tag's, the token's and the head slot's words are no tag: in a sentence, in a string, in a Ruby or an HTML comment, in an escaped sample").
- **An exception out of `Theme.prepare` on a reload** ends the reload's prepare chain: the reloader counts the reload as done and `Theme.current` stays the Theme built before it, over classes the reload threw away (while the theme had a `to_prepare` of its own that ran before the types', it left the type registries empty) ("on a reload prepare keeps whatever the check raises as the refusal, with what was raised in the message; at boot it is raised as it is"). **A registration of the types' block that raises on a reload** is kept the same way and said on every public page (`test/integration/theme_pages_test.rb`: "a type whose registration raises on a reload leaves a theme that says why on every public page, and the next reload clears it"); the registries after the one that raised stay empty until the next reload, which is development only.
