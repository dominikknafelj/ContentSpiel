# The media library

> Describes: `app/models/media/`, `app/services/media/`, `app/controllers/admin/media_controller.rb`, `app/controllers/admin/media_assets_controller.rb`, `app/components/admin/media_library/`, `app/components/media/`, `app/jobs/media/`, `app/values/media/`, `app/queries/media/`, `app/controllers/admin/media_originals_controller.rb`, `app/controllers/concerns/active_storage_*.rb`, `config/initializers/active_storage_access.rb`, `app/mcp/mcp/tools/`, `lib/tasks/media.rake`.

## The asset

`Media::Asset` (`app/models/media/asset.rb`, table `media_assets` -- Zeitwerk would otherwise demodulize `Media::Asset` down to `assets`, so `self.table_name` is explicit, same as `Media::Usage`/`media_usages` below) is the one place any image enters the app: a `title`, translated `alt`/`caption` (Mobility jsonb, same backend and fallback chain as every other translated attribute), and a `has_one_attached :file` that is never served to the public: the public gets only the re-encoded widths this app makes from it ("Widths and the generation" and "Delivery", below). `Media::Decoding` (`app/values/media/decoding.rb`) reads the file once, at validation, and everything the row knows about the pixels comes from that one decode: `width` and `height` as shown (after the camera's rotation; an animated image's first frame), a ~24px WebP `preview` made from the oriented pixels with all metadata stripped, and `has_alpha`. A file is refused, with a message of its own (`activerecord.errors.models.media/asset.attributes.file.*` in `config/locales/en.yml`, because `Media::Asset` is below CS Studio and MCP and the import read the same messages), when it is over the largest upload (`:too_large`), when libvips cannot read it or reads it as another format than its sniffed type (`:unreadable`), or when it describes more than `Decoding::MAX_PIXELS` (100 megapixels, `:too_many_pixels`, judged from the header before a pixel is decoded: a few kilobytes of one-colour PNG can describe a canvas of gigabytes), or when an animation's frame times its frames is more than `Decoding::MAX_ANIMATION_PIXELS` (500 megapixels, `:too_many_frames`, from the header too: every width decodes and encodes every frame on the one images thread, and a long screen recording is under the byte limit). The upload waits for that decode and nothing else: the widths are made afterwards (`test/models/media/asset_test.rb`, `test/values/media/decoding_test.rb`). `#alt_text(override:, locale:)`/`#caption_text(override:, locale:)` are the one place the resolution order lives: a rich-text node's single-valued override (a String) wins outright, then this asset's own translation along the fallback chain; a *translated* override (a block's `alt`/`caption`, a page's `hero_alt`) is passed whole as its `{locale => value}` jsonb (`read_attribute`, not `translated(...)`) and interleaved per locale -- the override in a locale, then the asset in that locale, then the next locale -- so an override written in another language never beats the asset's default in this one. A page hero, an image block and a rich-text `image` node all call through these rather than reading `alt`/`caption` directly, and `Media::PictureComponent` (`app/components/media/`) is the one place every image render builds its `<img>` from (lazy by default; the page hero passes `loading: "eager", fetchpriority: "high"`); what the tag carries is in "What a page draws" below. Allowed types are png/jpeg/gif/webp, byte-sniffed against the actual bytes (never a client's Content-Type header or filename), largest upload from Settings → Images (default 10 MB, 1 to 50) -- SVG stays refused everywhere, and the site logo stays its own separate `SiteSetting` attachment outside the library (moving it in, with the SVG sanitising that would need, is tracked in the roadmap, not built).

## Widths and the generation

The widths of an image are made by `Media::RenditionJob` (`app/jobs/media/rendition_job.rb`), once per image, on the queue `images`. The settings (`ImageSettings`, the five `image_*` columns of `site_settings`: format `webp` by default or opt-in `avif`, a quality per format at libvips' own defaults of 75 and 50, 1 to 6 distinct widths of 160 to 4,000 pixels, default 480, 960, 1600 and 2400, and the largest upload) are read when the job RUNS, never taken from its arguments, so a format saved between the enqueue and the run, or a Regenerate that queued an image twice, makes the image once with the newest settings; an image already made with them is left alone. The widths of an image are every configured width below its own width plus one at the smaller of its own width and the largest configured (`Media::Renditions.widths_for`): an image narrower than the smallest width gets one WebP of its own, and the widest candidate is a re-encoded file, never the original. An animated GIF or WebP is loaded with all its frames and becomes an animated WebP at each width, whatever the format setting, at the WebP quality (`Media::Renditions.format_for`): libvips writes an animation's AVIF as a still image collection, which a browser shows as its first frame, so under AVIF the job reads the header of a GIF or WebP for its frame count, a still one is made in AVIF, and the fingerprint holds the WebP quality too (`test/jobs/media/rendition_job_test.rb`). Its preview is its first frame. Each width is Active Storage's own `variant(...).processed` (a variant record and one download of the original per width, which on the Disk service is a local copy), with `strip: true`, so the public files carry no camera data, GPS included.

What was made is recorded on the row, not found by asking Active Storage: `media_assets.renditions` holds `{ "current", "previous" }`, each a generation `{ "fingerprint", "files": [{ "width", "key", "digest" }] }` (`Media::Generation`, the one reader). The key is the signed variation key an address is built from and the digest is what the 404 concern and the cleanup compare; `renditions_fingerprint` repeats the current fingerprint as a column of its own, so the progress counts, Regenerate and the backfill select with hash conditions. The fingerprint is a SHA-256 of the format, quality and widths. The generation is written in ONE statement after the last width, so a page never lists a width before every width exists, and a job that dies half way leaves the image as it was: the next run finds the variants already made. The generation before the current one is kept as `previous`, so a page cached under it still finds its files, and the one before that is deleted; a change of format never sends a page back to the preview while the remake runs, because the page switches only when the next generation is complete. A failure is retried twice and then recorded as `renditions_failed_at` and the error's class (never its message, which can quote a path); a file libvips cannot read is recorded at once; the image keeps its preview either way, and System status counts it. A vanished image's job is discarded, not retried.

**Queues.** `config/queue.yml` has two workers: `default` (three threads, `JOB_CONCURRENCY` processes) and `images` (ONE thread, one process, polling every 2 seconds), so a batch of uploads takes one core of a small host and mail is never behind an image. `Media::RenditionJob`, `Media::BackfillJob`, Active Storage's analysis and transform jobs are on `images` (`config/application.rb`); purge and mirror and every other job stay on `default` (`test/lib/job_queues_test.rb`). A library upload queues no analysis at all: its blob is marked analyzed with the decode's size when the asset is saved (`Media::Asset#mark_blob_analyzed`), because the analysis would read the whole file again and then touch the asset, moving the media panel's autosave base under an editor typing the alt text (`test/models/media/asset_test.rb`). The plain job has priority 0; `Media::BackfillRenditionJob` has priority 10 and is limited to one per image at a time, so an upload's widths and a Regenerate's never wait behind a backfill.

**Existing images.** `20261031120000_adopt_existing_image_variants.rb` records the variants the old preprocessing made as each image's first generation, under the fingerprint `"adopted"` (`Media::Generation::ADOPTED`). Those were made without `strip` and carry a JPEG's camera data, and the public gets only widths without it, so an adopted generation is served only until the image is made again: it is never kept as `previous`, it is deleted when the new generation is recorded (its addresses then answer 404, and a page cached before the remake shows a broken image until it is reloaded), and a remake that fails withdraws it (the page shows the preview or the box). `Media::BackfillJob` (every ten minutes, `config/recurring.yml`) queues at most 300 images per run, the oldest first, and selects an adopted image explicitly; on a site with nothing due it is one `exists?` answered by a partial index. A purged image's widths stop being served at once (the allow-list below); a TRASHED image's made widths stay public until it is purged, because the trash is restorable and its screen shows them; they carry no camera data.

**Telemetry.** The job's span is a consumer root and is kept (`Telemetry::WorkSampler`); it carries `image.queue_latency_ms`, `image.width.<w>.ms`, `image.bytes_in` and `image.bytes_out`, and no file name or path.

## What a page draws

`Media::PictureComponent` draws one `<img>` and never a wrapper, a `<picture>` or a script (`test/components/media/picture_component_test.rb`; the rich-text scrubber keeps only the preview style on an `img`, `test/sanitizers/rich_text_scrubber_test.rb`). It has three states, always with `width` and `height`, and never the original:

- **Widths made:** `src` is the middle width, `srcset` lists exactly the widths of the current generation, and the preview is the image's own `style` background (`background:url("data:image/webp;base64,...") center/cover no-repeat`), so the browser paints the sharp image over it as it arrives. There is no fade and no attribute for one. An image with an alpha channel gets no background, or the preview would show through its transparent parts for ever.
- **No width yet** (just uploaded, a failed generation, an image waiting for the backfill): `src` is the preview itself and `data-image-preview` lets the stylesheet blur it to its box (`app/assets/tailwind/themes/default/images.css`).
- **Neither:** no `src`, a box of the image's size with its alt, `data-image-empty`, on `--th-sunken`. The box carries the Design System's image mark, 28px at its centre, as a centred non-repeating CSS background of the same `<img>` (`images.css`), so the component keeps no wrapper and no script. A data-URI SVG cannot read a token, so the mark's stroke is `--th-meta` written out once per scheme (`#6c6d72` light, `#8e8f95` dark, under `[data-theme="dark"]`), and `test/integration/design_tokens_test.rb` ("the empty image's mark ...") reads `--th-meta` from `tokens.css` and holds both to it. **A theme that overrides `--th-meta` is not followed**: the mark keeps the default theme's colour until the theme restyles `img[data-image-empty]` itself; **no guard** for that.

The public content security policy sets no `img-src` or `style-src`, which is what lets a `data:` URL stand as a `src` and a background. The scrubber keeps an `img`'s `src` only as exactly the WebP preview data URL, and its `style` only as exactly the preview background, each judged as a browser reads it; `data-image-preview` and `data-image-empty` are the only other attributes it adds. CS Studio draws the same rule through `Admin::Ui::LibraryImageComponent` and `Media::Asset#display_url`: the smallest width that covers the tile, else the preview, else the box.

## Delivery

Every attachment is addressed through Active Storage's PROXY routes (`config.active_storage.resolve_model_to_route = :rails_storage_proxy`, `config/application.rb`): one request, no redirect, answered `Cache-Control: max-age=3155695200, public, immutable` (Rails' own `http_cache_forever`). The address names its bytes for ever, since a signed id carries no expiry and a variation key is a digest of the transformation, so an image is fetched once per browser and once per cache in front of the site, and the headers are what a CDN or a proxy caches by (`docs/reference/hosting.md`, "What a host sets", the paragraph "Images and the proxies in front of the site"). Nothing is configured for a CDN.

What the public routes refuse is an allow-list that fails closed (`ActiveStoragePublicFiles`, applied by `config/initializers/active_storage_access.rb`), shown by `test/integration/image_delivery_test.rb`:

- **No library original, to anyone.** The blob routes (redirect, proxy and the disk route) serve an original only of the site logo. A blob attached to nothing, which is what a purged image's is until `purge_later` has run while its signed id is in every srcset ever published, is refused like the rest; a refusal decided by the attachment row would have served it for a hundred years.
- **No request makes a width.** The representation routes serve a width only when the asset's recorded generation (current or previous) lists its digest and its variant record exists. Rails' own `set_representation` processes the variant inline, and the variation keys of the configured widths are predictable, so a request for a width not made would run a 2,400px transform on a Puma thread; the concern overrides the callback instead of following it (`ActiveStorageMadeVariantsOnly`). Only the logo's variants are made on request, as Rails makes them.
- A refusal is a bare 404 before `http_cache_forever` runs, so it carries no `Cache-Control: public`.
- A note's file stays refused by `ActiveStorageNoteFilesRefusal`; no MCP answer, public route or srcset carries a library original.

**Download original.** Signed-in editors download the original from the media panel through `Admin::MediaOriginalsController` (`GET media/:id/original`, `media.upload`, a kept image; a 403 before anything is looked up). It is not the blob proxy because Active Storage's proxy controllers take no session and cannot tell an editor from a visitor. It streams the original's bytes as an attachment, `private, no-store` (`test/controllers/admin/media_originals_controller_test.rb`). The panel's link is a plain text link with one small line under it, "Only editors can download the original." (`admin.components.media_library.panel.download_hint`).

## The content version

A rendered page bakes in an image's address, alt, caption and dimensions, so a change to an image moves the public content version, but only when a live page can show it (`test/models/media/asset_version_test.rb`). `Media::Asset`'s own commit bumps only when `Media::Usage.shown_publicly` holds for it: a usage row whose owner (through its block, for a block's row) is kept and published or scheduled, or a row of role `published`; a question that fails answers yes, because a needless bump costs a cache and a missed one a stale page. `Media::RenditionJob` bumps ONCE per image, when it records the generation (and when it fails after writing the size and preview, since a cached page holds neither), and the variant records it makes do not bump, so an upload no longer empties the site's caches four times. The logo's variants still bump. Every `update_columns` on `media_assets` says `# version: none (reason)` or bumps (`test/lib/version_bump_test.rb`). Left alone, and not images': re-keying the rich-text render cache on what it reads.

## In tests

`make_renditions!(asset)` (`test/support/media_renditions.rb`) gives an asset a generation: with no arguments the real job runs inline and the files are made; with `widths:` or `fingerprint:` a generation is written without making any file, its keys and digests the real variation ones, so the addresses have the real shape and the public routes answer them 404 (nothing was made). The test environment's queue adapter is `:test`, so a job is enqueued and not run unless the test performs it. A test that wants the public routes to serve a width makes it with the job.

## Measured

The figures that matter are the documentation site's, and its server is behind Cloudflare Access and was not reachable from the session that built this: **the site's figures are the owner's to take and write here.** The procedure, for before (the revision before this work) and after on the same page:

1. A page with a hero image, in Chrome with the network throttled to a mid-tier phone profile (Slow 4G, 4x CPU slowdown) and the cache disabled; record the transfer size of the page and its images, which file the hero is, and the time of the Largest Contentful Paint.
2. Upload a 10 MB photo: time from the request to the answer (the decode and the preview are inside it) and the time until the widths are recorded (`image.queue_latency_ms` and the job's duration in telemetry, or `renditions_fingerprint` appearing on the row).
3. One generation per image for a still WebP and an animated GIF, from the job's span.

Local figures, from libvips on a development laptop (Apple silicon), the pipeline the job runs (`resize_to_limit`, WebP quality 75, `strip`), on synthetic images. They are an order of magnitude, not a promise: noise compresses unlike a photograph.

| What | Figure |
|---|---|
| Decode and preview of a 4000x3000 JPEG of 5.9 MB (`Media::Decoding.read`), the work the upload waits for | about 40 ms |
| The preview of a 2880x1800 PNG | 62 bytes (83 as base64 in the page) |
| Widths of a 4000x3000 JPEG: 480, 960, 1600, 2400 and its own 4000 | 81, 85, 176, 353 and 929 ms, about 1.6 s in all |
| Widths of a 2880x1800 PNG (1.99 MB original) | 21, 35, 67, 126 and 166 ms, about 0.4 s in all; the 480 width is 508 bytes and the widest 15.8 KB |
| An animated GIF of 800x600 and 20 frames (11.9 MB): the 480 and 800 widths | 256 and 647 ms, 206 KB and 1.78 MB as animated WebP |

Add the downloads (a local copy on the Disk service) and the database writes; the job is one thread, so a burst of N images takes N times the per-image figure, which is why the queue exists. The backfill's bound of 300 images per run is about what that queue makes in ten minutes.

## References and usages

Three places reference a library asset -- `pages.hero_media_asset_id`, `content_blocks.media_asset_id` (both plain FKs to `media_assets` -- default NO ACTION, not `on_delete: :restrict`: Postgres 18 reports a RESTRICT violation as SQLSTATE 23001, which Rails doesn't map to `ActiveRecord::InvalidForeignKey`, so every `rescue` of it would miss; `MediaForeignKeysNoAction`) and a rich-text `image` node's `asset_id` (`RichText::BuiltIns`) -- and `Media::Choosing` (shared by `Pages::Save`/`ContentBlocks::Save`) is what lets *choosing* one need `media.upload` and an existing asset id while *clearing* it needs only the ordinary edit right already being checked, refusing a forged or nonexistent id as a validation failure on the field the editor sees rather than letting it reach Postgres as an FK-violation 500 (an asset deleted between that check and the write still hits the FK; `Pages::Save`/`ContentBlocks::Save`/`Posts::Save` rescue `ActiveRecord::InvalidForeignKey` into the same "doesn't exist" failure, `Media::Choosing#vanished_media_failure`). Embedding an image that's already in the library in *rich text* needs no `media.upload` -- it's content editing, covered by the right to edit the post or block, and only the asset's existence is validated (`RichText::BuiltIns`' `image` node); uploading a new image, and browsing the library in the picker, do need `media.upload`. Where an asset is actually used is entirely derived, never hand-maintained: `Media::Usage`/`Media::UsageIndex` (`app/models/media/`, table `media_usages`, unique on `(media_asset_id, owner_type, owner_id, role, locale)` with `nulls_not_distinct: true` so two rows that both have a nil `locale` still collide as "the same usage" instead of silently duplicating) rebuilds one owner's (`Page`, `ContentBlock` or `Post`) *entire* set of rows at once -- delete-then-reinsert, never an incremental diff -- from inside the same save/destroy service transaction that changed it; The images a record's published copies show (its current copy and the one waiting for its time) are rows of role `published` on the page or post (`Media::UsageIndex.refresh_published`, in the transaction that takes a copy; `refresh` leaves them alone unless the owner is destroyed), so an image dropped from the rows but still on the site stays "used" until the changes are published; those rows exist only while the record is live or scheduled (an unpublish releases them in the same transaction, publishing again writes them from the copy then taken); a trashed record keeps them, since restoring it makes the same copy public again; "Used on" and MCP's `usage_count` count a page or post once (`Media::Asset#usages_summary`, `.usage_places_for`), and show `published` alone only when nothing in the rows shows the image any more; the copy a pending one replaces by the clock keeps its rows until the next copy is taken (more protection than needed, never less). `bin/rails media:reindex` (`Media::UsageIndex.rebuild_all`) recomputes the whole table any time it's suspected stale (a bug, a direct SQL edit, a restored backup). `Media::Asset#used?`/`#usages_summary` read this table to back the library's "Unused" filter and a detail panel's "Used on" list, and it's the database's own FK -- not this table -- that's the actual guarantee behind "can't delete an asset that's in use" (`Trash::Purge`, which turns the violation into an ordinary failure). Editing or deleting needs `media.manage` (seeded onto Admin and Editor) or, via `Media::Ownership`, being the asset's own uploader with `media.upload` alone -- see `docs/reference/access-control-and-audit.md` for the full permission story, including how a token is judged.

## CS Studio's Media module

CS Studio's own Media module (`Admin::MediaController`, `Admin::MediaLibrary::ToolbarComponent`/`GridComponent`/`TileComponent`/`PanelComponent`) is the grid/search/multi-file-upload home with one image's autosaving panel beside the grid (`/media?selected=ID`, keeping `q`, `filter`, `page`, `locale`; `GET /media/:id` is a 303 to it, and a trashed or missing id is a 404 either way). Every action sits behind a gate that runs before any image is looked up: `index`, `show` and `create` need `media.upload`, `update` and `destroy` need `media.upload` or `media.manage` (the controller's 403, with no `access.denied`, like every module gate — so to someone with no media right an id that names nothing and one that exists answer alike); which image a holder may then edit or delete is still the services' decision. The segments All / Unused / Missing alt (default-language alt blank or only whitespace) / Untranslated (`missing` in any target language; hidden with one language) / Mine come with counts from one grouped query (`Media::Search#counts`: respects the search, not the segment, kept images only), and an autosave in the panel streams the tile, the counts and the panel's title back rather than reloading. The panel (`PanelComponent`) is the image's own autosaving form — language tabs, Title, Alt (a warn border while the default-language alt is empty and nothing is typed, `.admin-media-alt-warn`), Caption, "Used on", and "Move to trash…" (which comes back to the grid with its `q`, `filter` and `page` kept) with its reason and a link to where the image is used while it can't be trashed; a viewer who may not edit the image gets plain text and "Only the uploader or a media manager can edit this image." A tile is a link into `#content` that advances the URL, and `admin--media--panel` moves focus into the panel after a tile was chosen and back to that tile when the panel's × closes it (a plain load moves no focus). The screen carries `turbo-cache-control: no-cache` and `turbo-prefetch: false` in its head, like the editors, so Back never restores a panel with a stale base or stale chips. A missing, trashed or malformed `?selected=` is the 404, never a grid without a panel; its link is "Back to Media" with the search and segment kept. The panel is a 340px column beside the grid from 1024px and stacks under it below that; the handoff's panel overlaying the grid between 1024 and 1279px is deliberately not built. It is searched through `Media::Search` (title, alt in any locale, and filename, one escaped pattern for all three ILIKEs, built as Arel nodes through `SqlNodes` -- shared with MCP below so both search the library the same way); `Admin::MediaAssetsController` is a separate, narrower upload-only JSON endpoint for `Media::PickerComponent` (`app/components/media/`, the one modal dialog that every hero/image-block field -- via `Admin::Columns::MediaColumnComponent` -- and the Tiptap editor's Image button open) -- two unrelated callers sharing `Media::Upload`, not one feature split across two endpoints. **Uploading** is drop-anywhere on the Media screen. The big drop zone is the empty library's invitation only: its wrapper (`[data-media-drop-zone]`) is `hidden` once `Media::Search#any_images?` says the library holds a kept image (a library of trashed images is empty), while the file input inside it stays the upload target, and "Upload images" and the window-wide drop remain. The drop is `admin--media--drop` (a file drag, only one carrying `Files`, shows the "Drop images to upload" overlay, counted `dragenter`/`dragleave`, gone on drop, Escape, `dragend` or a stale `dragover`; a drag that began inside the page — an image dragged off the grid — is the page's own and is left alone) plus the header's "Upload images"; every file becomes a progress tile at the start of the grid and goes up one at a time (`app/javascript/media/upload_tiles.js`, shared with the picker; XHR for the bar), and the answer (`Admin::MediaUploadResponses`: `id`, `title`, `url`, the finished tile's HTML and the new `counts`) swaps the tile in with nothing reloading, so a finished upload never replaces the panel under a typing editor. A refused file (wrong type, over the largest upload, unreadable, SVG -- the server decides) keeps its own tile with the reason and Dismiss. The queue is module-level so a tile click (a frame navigation) re-attaches the tiles still going up to the new grid. **The picker** (880 dialog hanging from a fixed top edge, `.admin-media-picker`) is the same toolbar and tiles inside its own frame `media-picker-grid` (`GET /media?picker=1`, `media.upload`-gated, kept images only; every segment but Untranslated), choosing is select-then-use (a click selects, **Use image** confirms, a double click does both; `admin--media--select` holds the choice across searches), its header **Upload** selects the first finished upload, and Escape clears a typed search before a second one closes. New page and New post hang from the same fixed top edge (`Admin::Ui::DialogComponent`'s `hang:`). MCP exposes the library read-only as `list_media_tool`/`get_media_tool` (`app/mcp/mcp/tools/`); `list_media_tool` pages 50 per call through a `page:` argument. It is the only MCP list tool that pages: `list_posts_tool` returns every readable post in one answer (without bodies), which is a roadmap row. `db/migrate/20260929050000_move_images_into_media_library.rb` moved every legacy `Page#hero_image`/`ContentBlock#image` Active Storage attachment into this one storage path -- deduping identical files by blob checksum, recording which assets it created in a ledger table (`media_library_migrated_assets`, so its own `down` can roll back cleanly without touching a pre-existing or later-uploaded asset), leaving in place (and reporting, never silently dropping) any attachment whose blob type the library refuses, and adding the `rich_text` usage rows for bodies that already embedded a library image (rich-text uploads predate the index; without those rows such an image reads as "Unused" and can be deleted -- a rich-text reference has no FK). `20260929070000_backfill_rich_text_media_usages.rb` runs that same additive, idempotent SQL for databases that ran the move before it did. `bin/rails media:orphans` lists (and, with `CONFIRM=1`, purges) blobs with no attachment at all -- duplicates that migration deliberately never deleted, plus ActionText leftovers; never a blob of the notes' storage service, which the notes services remove themselves -- and `bin/rails media:regenerate` queues `Media::RenditionJob` for every kept image not made with the current image settings (`Media::Asset.not_made_with`), idempotent since it only ever looks at what is recorded as made, never at what is queued. An existing site's images keep their widths through the deploy and get their previews from the backfill ("Widths and the generation", above).

## Notes on an image

A library image takes notes like a page or a post (`docs/reference/notes.md`). There is no drawer on the Media screen: the panel has a **Notes** section below "Used on" (`#media-notes`, headed "NOTES · N OPEN"; `Admin::NotesScreen::MediaSectionComponent`, which `Admin::MediaLibrary::PanelComponent` draws through the slot `media.panel.sections` without naming it), which embeds the same `turbo-frame#notes` as the editors' Notes tab with `view=media`, outside the panel's autosave form: a note is no field of the image, and inside an `admin--saving--autosave` form a note's field would be saved as one. A thread opens in place in the panel. Anyone who may open the panel may read and write notes there (`media.upload`), whether or not the image is theirs to edit; deleting someone else's note and pinning need `media.manage` or being the image's uploader. A tile with open threads shows a count chip on the image, top right, on the surface background so that it stays readable over a photo, accent while something on that image is unread for the viewer (`Admin::NoteCountsHelper#media_note_marks`: one grouped query for the page of the grid and one beside it, only for a `media.upload` holder); the picker's tiles show none, since choosing an image is not reading about it. `?selected=ID&thread=N` opens the panel at a thread, which is where an inbox row for an image leads. **A note's files are not library images**: they are attachments of the message on a storage service of their own (`notes` in `config/storage.yml`), with no `Media::Asset`, no usage row and no variant, read only through `Admin::NoteFilesController` and refused by Active Storage's public read routes. A purged image takes its notes with it (`Trash::Purge` calls `Notes::Remove`); a trashed one keeps them, hidden.

## Who else has an image open

The panel's file-name row also draws the slot `media.panel.header`, between the name and the "×": presence's people (`Admin::PresenceScreen::PeopleComponent`, `size: :panel`), 20px circles, two and then "+N" at every width, with the "×" rightmost. The file name is `flex-1 min-w-0` and is cut with an ellipsis on one line (the full name stays in a `title` and in the fields below); the people never give way, since a group that vanished on long names would be unreliable. It is a part of the panel, so closing the panel ends its subscription. Who is shown is decided in `docs/reference/presence.md`; an image is a record kind with no per-image read right (`RecordKinds`, `scoped: false`), so a user without `media.upload` gets the 403 of the media screen, and the grid's tiles show no presence (not built).

## Rules a change can break silently

Moved word for word from `CLAUDE.md`, where "above" and "below" meant the list these rules stood in: a rule named that way may now be in another reference file. Each names the test that guards it; a rule or a part of one with no guard is also said in `CLAUDE.md`.

- An image a current or pending copy shows is in use (role `published`, released on unpublish) (`test/models/media/usage_index_test.rb`: "an image only the published copy shows cannot be moved to the trash or deleted, and can once the changes are published").
- No public route, page, `srcset`, rich-text image or MCP answer gives a library image's original, and no request makes a width: Active Storage's public routes serve an allow-list (the logo, and the widths the asset's recorded generation lists whose variant record exists), a purged image's blob included in the refusal, and Rails' `set_representation` is overridden, not followed, because it transforms inline; editors download the original through `Admin::MediaOriginalsController` (`test/integration/image_delivery_test.rb`).
- An image moves the public content version only when `Media::Usage.shown_publicly` holds for it, and the library's widths once per generation from `Media::RenditionJob`, never one bump per variant record; a write around the callbacks on `media_assets` says `# version:` (`test/models/media/asset_version_test.rb`).
- An asset's `width`, `height`, `has_alpha` and preview come from `Media::Decoding` at validation, on every path that makes an asset (`Media::Upload`, the import, a test's `create!`), and nothing reads the file again to learn them (`test/models/media/asset_test.rb`).
- Image jobs (`Media::RenditionJob`, `Media::BackfillRenditionJob`, `Media::BackfillJob`, Active Storage's analysis and transform) are on the `images` queue, served by one thread, and every other job stays on `default`: a new job names its queue (`test/lib/job_queues_test.rb`).
- `Media::PictureComponent` stays one `<img>` with no wrapper and no script, and `RichTextScrubber` keeps on an `img` only the exact preview `src` and `style` and the two `data-image-*` attributes (`test/components/media/picture_component_test.rb`, `test/sanitizers/rich_text_scrubber_test.rb`).
