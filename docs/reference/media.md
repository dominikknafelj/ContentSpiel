# The media library

> Describes: `app/models/media/`, `app/services/media/`, `app/controllers/admin/media_controller.rb`, `app/controllers/admin/media_assets_controller.rb`, `app/components/admin/media_library/`, `app/components/media/`, `app/mcp/mcp/tools/`, `lib/tasks/media.rake`.

## The asset

`Media::Asset` (`app/models/media/asset.rb`, table `media_assets` -- Zeitwerk would otherwise demodulize `Media::Asset` down to `assets`, so `self.table_name` is explicit, same as `Media::Usage`/`media_usages` below) is the one place any image enters the app: a `title`, translated `alt`/`caption` (Mobility jsonb, same backend and fallback chain as every other translated attribute), and a `has_one_attached :file` with four named, preprocessed variants (`VARIANT_WIDTHS`: `w480`/`w960`/`w1600`/`w2400`, `resize_to_limit` so none ever upscales, WebP, enqueued right after upload for every allowed type except GIF, which the global rule leaves unresized). `#srcset` only ever lists a variant with a finished `ActiveStorage::VariantRecord` -- never triggers or waits on processing itself -- so a slow, missing or failed transform just means fewer `srcset` entries, never a 500; `<img src>` (`#url`/`#src`) always points at the original regardless, and once there are variants the original is also the widest `srcset` candidate (when its width is known -- a browser never falls back to `src` once `w` descriptors exist). `#alt_text(override:, locale:)`/`#caption_text(override:, locale:)` are the one place the resolution order lives: a rich-text node's single-valued override (a String) wins outright, then this asset's own translation along the fallback chain; a *translated* override (a block's `alt`/`caption`, a page's `hero_alt`) is passed whole as its `{locale => value}` jsonb (`read_attribute`, not `translated(...)`) and interleaved per locale -- the override in a locale, then the asset in that locale, then the next locale -- so an override written in another language never beats the asset's default in this one. A page hero, an image block and a rich-text `image` node all call through these rather than reading `alt`/`caption` directly, and `Media::PictureComponent` (`app/components/media/`) is the one place every image render builds its `<img srcset sizes>` tag from (lazy by default; the page hero passes `loading: "eager", fetchpriority: "high"`). Allowed types are png/jpeg/gif/webp, byte-sniffed against the actual bytes (never a client's Content-Type header or filename), max 10 MB -- SVG stays refused everywhere, and the site logo stays its own separate `SiteSetting` attachment outside the library (moving it in, with the SVG sanitising that would need, is tracked in the roadmap, not built).

## References and usages

Three places reference a library asset -- `pages.hero_media_asset_id`, `content_blocks.media_asset_id` (both plain FKs to `media_assets` -- default NO ACTION, not `on_delete: :restrict`: Postgres 18 reports a RESTRICT violation as SQLSTATE 23001, which Rails doesn't map to `ActiveRecord::InvalidForeignKey`, so every `rescue` of it would miss; `MediaForeignKeysNoAction`) and a rich-text `image` node's `asset_id` (`RichText::BuiltIns`) -- and `Media::Choosing` (shared by `Pages::Save`/`ContentBlocks::Save`) is what lets *choosing* one need `media.upload` and an existing asset id while *clearing* it needs only the ordinary edit right already being checked, refusing a forged or nonexistent id as a validation failure on the field the editor sees rather than letting it reach Postgres as an FK-violation 500 (an asset deleted between that check and the write still hits the FK; `Pages::Save`/`ContentBlocks::Save`/`Posts::Save` rescue `ActiveRecord::InvalidForeignKey` into the same "doesn't exist" failure, `Media::Choosing#vanished_media_failure`). Embedding an image that's already in the library in *rich text* needs no `media.upload` -- it's content editing, covered by the right to edit the post or block, and only the asset's existence is validated (`RichText::BuiltIns`' `image` node); uploading a new image, and browsing the library in the picker, do need `media.upload`. Where an asset is actually used is entirely derived, never hand-maintained: `Media::Usage`/`Media::UsageIndex` (`app/models/media/`, table `media_usages`, unique on `(media_asset_id, owner_type, owner_id, role, locale)` with `nulls_not_distinct: true` so two rows that both have a nil `locale` still collide as "the same usage" instead of silently duplicating) rebuilds one owner's (`Page`, `ContentBlock` or `Post`) *entire* set of rows at once -- delete-then-reinsert, never an incremental diff -- from inside the same save/destroy service transaction that changed it; `bin/rails media:reindex` (`Media::UsageIndex.rebuild_all`) recomputes the whole table any time it's suspected stale (a bug, a direct SQL edit, a restored backup). `Media::Asset#used?`/`#usages_summary` read this table to back the library's "Unused" filter and a detail panel's "Used on" list, and it's the database's own FK -- not this table -- that's the actual guarantee behind "can't delete an asset that's in use" (`Trash::Purge`, which turns the violation into an ordinary failure). Editing or deleting needs `media.manage` (seeded onto Admin and Editor) or, via `Media::Ownership`, being the asset's own uploader with `media.upload` alone -- see `docs/reference/access-control-and-audit.md` for the full permission story, including how a token is judged.

## CS Studio's Media module

CS Studio's own Media module (`Admin::MediaController`, `Admin::MediaLibrary::ToolbarComponent`/`GridComponent`/`TileComponent`/`PanelComponent`) is the grid/search/multi-file-upload home with one image's autosaving panel beside the grid (`/media?selected=ID`, keeping `q`, `filter`, `page`, `locale`; `GET /media/:id` is a 303 to it, and a trashed or missing id is a 404 either way). Every action sits behind a gate that runs before any image is looked up: `index`, `show` and `create` need `media.upload`, `update` and `destroy` need `media.upload` or `media.manage` (the controller's 403, with no `access.denied`, like every module gate — so to someone with no media right an id that names nothing and one that exists answer alike); which image a holder may then edit or delete is still the services' decision. The segments All / Unused / Missing alt (default-language alt blank or only whitespace) / Untranslated (`missing` in any target language; hidden with one language) / Mine come with counts from one grouped query (`Media::Search#counts`: respects the search, not the segment, kept images only), and an autosave in the panel streams the tile, the counts and the panel's title back rather than reloading. The panel (`PanelComponent`) is the image's own autosaving form — language tabs, Title, Alt (a warn border while the default-language alt is empty and nothing is typed, `.admin-media-alt-warn`), Caption, "Used on", and "Move to trash…" (which comes back to the grid with its `q`, `filter` and `page` kept) with its reason and a link to where the image is used while it can't be trashed; a viewer who may not edit the image gets plain text and "Only the uploader or a media manager can edit this image." A tile is a link into `#content` that advances the URL, and `admin--media-panel` moves focus into the panel after a tile was chosen and back to that tile when the panel's × closes it (a plain load moves no focus). The screen carries `turbo-cache-control: no-cache` and `turbo-prefetch: false` in its head, like the editors, so Back never restores a panel with a stale base or stale chips. A missing, trashed or malformed `?selected=` is the 404, never a grid without a panel; its link is "Back to Media" with the search and segment kept. The panel is a 340px column beside the grid from 1024px and stacks under it below that; the handoff's panel overlaying the grid between 1024 and 1279px is deliberately not built. It is searched through `Media::Search` (title, alt in any locale, and filename, one escaped pattern for all three ILIKEs, built as Arel nodes through `SqlNodes` -- shared with MCP below so both search the library the same way); `Admin::MediaAssetsController` is a separate, narrower upload-only JSON endpoint for `Media::PickerComponent` (`app/components/media/`, the one modal dialog that every hero/image-block field -- via `Admin::Columns::MediaColumnComponent` -- and the Tiptap editor's Image button open) -- two unrelated callers sharing `Media::Upload`, not one feature split across two endpoints. **Uploading** is drop-anywhere on the Media screen (`admin--media-drop`: a file drag, only one carrying `Files`, shows the "Drop images to upload" overlay, counted `dragenter`/`dragleave`, gone on drop, Escape, `dragend` or a stale `dragover`; a drag that began inside the page — an image dragged off the grid — is the page's own and is left alone) plus the header's "Upload images"; every file becomes a progress tile at the start of the grid and goes up one at a time (`app/javascript/media/upload_tiles.js`, shared with the picker; XHR for the bar), and the answer (`Admin::MediaUploadResponses`: `id`, `title`, `url`, the finished tile's HTML and the new `counts`) swaps the tile in with nothing reloading, so a finished upload never replaces the panel under a typing editor. A refused file (wrong type, over 10 MB, SVG -- the server decides) keeps its own tile with the reason and Dismiss. The queue is module-level so a tile click (a frame navigation) re-attaches the tiles still going up to the new grid. **The picker** (880 dialog hanging from a fixed top edge, `.admin-media-picker`) is the same toolbar and tiles inside its own frame `media-picker-grid` (`GET /media?picker=1`, `media.upload`-gated, kept images only; every segment but Untranslated), choosing is select-then-use (a click selects, **Use image** confirms, a double click does both; `admin--media-select` holds the choice across searches), its header **Upload** selects the first finished upload, and Escape clears a typed search before a second one closes. New page and New post hang from the same fixed top edge (`Admin::Ui::DialogComponent`'s `hang:`). MCP exposes the library read-only as `list_media_tool`/`get_media_tool` (`app/mcp/mcp/tools/`); `list_media_tool` pages 50 per call through a `page:` argument. It is the only MCP list tool that pages: `list_posts_tool` returns every readable post in one answer (without bodies), which is a roadmap row. `db/migrate/20260929050000_move_images_into_media_library.rb` moved every legacy `Page#hero_image`/`ContentBlock#image` Active Storage attachment into this one storage path -- deduping identical files by blob checksum, recording which assets it created in a ledger table (`media_library_migrated_assets`, so its own `down` can roll back cleanly without touching a pre-existing or later-uploaded asset), leaving in place (and reporting, never silently dropping) any attachment whose blob type the library refuses, and adding the `rich_text` usage rows for bodies that already embedded a library image (rich-text uploads and ActionText-imported images predate the index; without those rows such an image reads as "Unused" and can be deleted -- a rich-text reference has no FK). `20260929070000_backfill_rich_text_media_usages.rb` runs that same additive, idempotent SQL for databases that ran the move before it did, and `RichText::ActionTextImport` refreshes each owner it writes. `bin/rails media:orphans` lists (and, with `CONFIRM=1`, purges) blobs with no attachment at all -- duplicates that migration deliberately never deleted, plus ActionText leftovers; never a blob of the notes' storage service, which the notes services remove themselves -- and `bin/rails media:variants` re-enqueues whichever of a non-GIF asset's four named variants still has no `VariantRecord` (a failed or lost job, an asset that predates a width), idempotent since it only ever looks at what's actually processed, never at what's currently queued. Interim state: until a variant has actually been processed, a page serves the original file at full size. Every `ActiveStorage::VariantRecord` commit bumps the public content version (`config/initializers/public_site_version.rb`; see `docs/reference/rich-text.md`) -- a newly processed variant is exactly the kind of change that can make a page's already-cached render worth invalidating.

## Notes on an image

A library image takes notes like a page or a post (`docs/reference/notes.md`). There is no drawer on the Media screen: the panel has a **Notes** section below "Used on" (`#media-notes` in `Admin::MediaLibrary::PanelComponent`, headed "NOTES · N OPEN"), which embeds the same `turbo-frame#notes` as the editors' drawer with `view=media`, outside the panel's autosave form: a note is no field of the image, and inside an `admin--autosave` form a note's field would be saved as one. A thread opens in place in the panel. Anyone who may open the panel may read and write notes there (`media.upload`), whether or not the image is theirs to edit; deleting someone else's note and pinning need `media.manage` or being the image's uploader. A tile with open threads shows a count chip on the image, top right, on the surface background so that it stays readable over a photo, accent while something on that image is unread for the viewer (`Admin::NoteCountsHelper#media_note_marks`: one grouped query for the page of the grid and one beside it, only for a `media.upload` holder); the picker's tiles show none, since choosing an image is not reading about it. `?selected=ID&thread=N` opens the panel at a thread, which is where an inbox row for an image leads. **A note's files are not library images**: they are attachments of the message on a storage service of their own (`notes` in `config/storage.yml`), with no `Media::Asset`, no usage row and no variant, read only through `Admin::NoteFilesController` and refused by Active Storage's public read routes. A purged image takes its notes with it (`Trash::Purge` calls `Notes::Remove`); a trashed one keeps them, hidden.
