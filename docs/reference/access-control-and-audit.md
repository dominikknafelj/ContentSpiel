## Auth

Custom session-based auth (`app/controllers/concerns/authentication.rb`), not Devise — `has_secure_password` on `User`, signed cookie holds a `Session` id, `Current.session`/`Current.user` per-request. `ApplicationController` requires authentication by default; `PagesController` (the public site) opts out with `allow_unauthenticated_access`. `ApiToken` is a separate token model (revocable, named — see `docs/reference/users-groups-tokens.md`): a token is 256 random bits, the row stores only `lookup_digest` (its SHA-256 hex, unique index) and `ApiToken.authenticate` is one indexed lookup on it, so no password hash is computed per request; the tokens issued before that change were revoked (their `lookup_digest` is the placeholder `revoked:<id>`), and `lookup_digest` is in `Audit::Snapshot::NEVER_STORED` and in `filter_parameters` for non-session API access, bound to one `AccessControl::Group` (`group_id`, not null) that bounds what it may do regardless of its user's own rights — see "Access control and audit" below for what being signed in or holding a token actually permits. Active Storage's own write endpoints (`POST /rails/active_storage/direct_uploads`, the Disk service's `PUT`) require a signed-in session too (`config/initializers/active_storage_access.rb`, 401 otherwise) — the app never uses direct uploads; every upload goes through a CS Studio controller.

**Signing in** is decided by `SignIn` (`app/models/sign_in.rb`, `app/models/sign_in/`), a layer below the controllers that knows no session, cookie, route or mail: `SignIn::PasswordAttempt` asks the bot check when it is due (`SignIn::BotCheck`, Cloudflare Turnstile), reserves the attempt in the buckets (`SignIn::Throttle#reserve`) BEFORE the password is checked, then checks it through `User.authenticate_by`, and answers a `SignIn::Outcome` (one of `SignIn::OUTCOMES`: `ok`, `refused`, `locked`, `bot_check_required`, `bot_check_failed`, and `second_factor_required` for a right password of an account that owes a second proof, "Passkeys, recovery codes and the second step" below; with the buckets the attempt closed). `Admin::SessionsController` signs the account in, audits and answers. Three buckets: the address's (Rails' `rate_limit`, 10 POSTs in 3 minutes, every POST counted), the email's (the 5th attempt closes it for 1 minute, doubling to 1 hour; counted whether or not an account has the email) and the address's wide one (50 attempts in an hour, whatever emails). Every refusal is one redirect with one sentence, the same for a known and an unknown email: "Try another email address or password.", "Try again in a few minutes." while the email's bucket is closed, "Try again later." while an address's is, "Complete the check, then sign in again." for the bot check. A password a person sets is also checked against the list of leaked passwords (`SignIn::LeakedPassword`, `docs/reference/users-groups-tokens.md`). The figures, the bot check, the leaked check, Cloudflare's own rule and the spans are in `docs/reference/hosting.md`, "Sign-in on the open internet". `scope:` on `SignIn::Throttle` and `accounts:` on `PasswordAttempt` are the seam for a second kind of sign-in (members'), which counts apart.

## Permissions, groups and grants

`AccessControl::Permissions` (`app/models/access_control/permissions.rb`) is a registry like `ContentModel::Registry`/`RichText::Schema`: built-in keys are unprefixed (`posts.read/create/edit/publish/delete`, `pages.read/create/edit/publish/move/delete`, `tags.manage`, `media.upload`, `media.manage`, `settings.manage`, `languages.manage`, `users.manage`, `groups.manage`, `tokens.manage`, `system_status.view`, `audit.view`, `trash.empty`, `ai.translate` — see `AccessControl::BuiltIns`), an outside key must be `owner/name`, and a duplicate raises `AccessControl::DuplicatePermission`; registration happens in `config/initializers/types.rb`'s `to_prepare`, alongside the block/content-type/rich-text registries, reset-then-register so a dev reload doesn't double-register. No hook replays an outside permission after that reset, so a gem cannot register one yet (`lib/content_spiel/plugins.rb`). `AccessControl::Group`/`Membership`/`Grant` (tables `access_control_groups`, `access_control_memberships`, `access_control_grants`) carry the actual rights: a group's grants each name a permission key plus a jsonb `scope` limited to `content_types` (array), `page_ids` (array, matched via `page_hierarchies` so a branch grant covers descendants), and `own` (boolean, matched against `Post#author_id`) — a group holds at most one grant per permission (unique index on `group_id, permission`; `Groups::Save` refuses a request that lists one twice as an invalid request, not a denial), grants combine with OR across a user's groups, and every scope key set on one grant must match (AND) for that grant to apply. Four groups are built in, by name (`AccessControl::Seeds::BUILT_IN`). A new database is built by loading `db/schema.rb`, which holds no rows, so they are made by `Groups::EnsureBuiltIns`: from the top of `db/seeds.rb` in every environment (`db:prepare` and `db:setup` run it after the schema load; `bin/rails db:seed` by hand on a site set up before the service existed) and by the setup wizard before every step past the token (a database built with `db:schema:load` alone ran no seed). It makes only a group that is missing by name, with the grants below, records `group.created` for each, and never touches a group that exists, so an owner's change to a built-in group's grants survives a deploy; the `SeedAccessControlGroups` data migration's own `ensure_built_in_groups!`, which also adds a missing grant to an existing group, is for databases that were migrated across that change and is called by nothing else. The groups: Admin (every registered permission, unscoped), Editor, Author (`posts.edit` scoped `own: true` — note its `posts.read`/`posts.create` are unscoped by design, so a seeded Author can still read every post, not just their own), Read only. Library images have no scopes: `media.upload` uploads, browses and chooses them (pointing a hero or image block at one needs it plus an existing asset, `Media::Choosing`, while clearing needs only the edit right), `media.manage` (Admin and Editor, added to already-seeded groups by `GrantMediaManageToBuiltInGroups`) edits or deletes any of them, and an image's uploader (`created_by_id`) may edit or delete their own with `media.upload` alone (`Media::Ownership` — a token still needs its group to hold `media.upload`). `users.owner` is a separate boolean flag, not a group — an owner is allowed everything regardless of grants, the last owner can't be demoted or deleted (`User`'s own validation), and every user-changing service (`Users::Save`/`Destroy`/`UpdatePassword`, via the shared `Users::OwnerProtection` concern) refuses a non-owner touching an owner's account at all, and refuses managing any user whose groups aren't a subset of the actor's own assignable rights (`#outranked?`) — so `users.manage` is bounded by what you could already grant yourself, never a blanket "any admin may manage any user". A password change ends that user's sessions inside the transaction that writes it (`Users::OwnerProtection#end_sessions_after_password_change`, called by `Users::Save` and `Users::UpdatePassword`, never by a controller): all of them, except the acting session of a signed-in user changing their own; the reset flow keeps none. The same bound applies to groups: `AccessControl.can_manage_group?(actor, group)` ("may this actor manage this group as it stands" — every grant it holds is one they could hand out) gates removing members or grants (narrowing a grant counts), deleting a group, and changing a user's membership, in `Users::Save`, `Groups::Save` and `Groups::Destroy`. Only a `User` is ever an owner (`AccessControl.owner?`): an `ApiToken` — even an owner's — is judged on its effective rights (group ∩ user) by `can_grant?`/`can_assign_group?`/`can_manage_group?` and the owner-only rules. A content type that is no longer registered matches nothing, and that is enforced at the decision point, not left to the data: `AccessControl::Scoping::Condition`, the one matcher behind both `allowed?` and `scope`, reads a grant's `content_types` intersected with the registered ones (`Permissions.content_type_choices`), so a grant naming a gone type — alone or beside a live one — doesn't reach posts that still carry that type; only an unscoped grant and an owner reach those. `AccessControl::LiveGrants` reads a group's grants with the same reader for the editor. A grant *all* of whose content types are gone is dead: it matches nothing, is shown unticked in the group editor, and is dropped on the next save of that group's form — a removal that takes someone who could grant those types, so the row's note says so ("Limited to a content type that no longer exists (<name>). Saving removes it; until then only someone who could grant that type can manage this group.") and, for a viewer who may manage the group, Save is enabled with nothing touched (`save_bar_form_data(always:)`). A grant that still has a live type keeps the removed name beside it — a `LiveGrants::Entry` with `gone_types` — and the editor carries it (`#carried_attributes`) through every save until somebody presses Remove on it, so an untouched save changes nothing (see `docs/reference/users-groups-tokens.md` for the rule `Groups::Save` reads it by). Either way the name is dormant, not gone: it grants nothing while its type is unregistered, and comes back to life, with its old meaning, only if a content type of that name is registered again while the name is still stored. So whoever hands a group on is judged on its grants *as stored* (`LiveGrants#as_stored`: the carried names, and a dead grant that such a re-registration would revive; a deleted page id is left out, it can't come back): `can_assign_group?`, `can_manage_group?` and the added-member check in `Groups::Save` all refuse an actor whose own grant doesn't cover the dormant name, so a `{blog}` holder can't put a user or a token into a group storing `{blog, retired}` or `{retired}`, nor take a member out of it, nor delete it — and the group editor shows them that group view-only.

## The decision point

`AccessControl.allowed?(actor, key, record = nil, channel:)` (`app/models/access_control.rb`, delegating to `AccessControl::Checker`) is the one decision point: a subject key (`posts.*`/`pages.*`) requires `record` (nil raises `ArgumentError` — no scope-free allow by omission), an admin-area key ignores it; a `User` is allowed if any of their groups' grants match, an `ApiToken` only if a grant of the token's own group matches *and* its user is separately allowed — the intersection, so a token narrows but never widens its user's rights; a `nil` actor is allowed on the trusted channels `:setup`, `:console`, `:system` (and no channel at all) and denied on `:admin`/`:mcp`/`:public` (`PublicController` sets `:public`). **The one bent rule is the visitor** (forms plan, decision 8): `AccessControl::VISITOR`, the one instance of `AccessControl::Visitor` (a value with nothing in it; `new` and `[]` are private, and the checker asks for that very instance by `equal?`, so a copy is no visitor), is allowed exactly `forms.submit` on `:public` and nothing else on any channel; `forms.submit` is registered `grantable: false`, so no group, token, matrix or seed can hold it (`Permissions.grantable`, which the group matrix, `AccessControl::Seeds`' `grants: :all` and `Grant`'s validation read, and `AccessControl.can_grant?`, false for it whoever asks). Only `FormSendsController` sets the visitor, for a visitor's send of a form, the one service the public site calls (`docs/reference/forms.md`, "Who may do what"; `test/models/access_control/visitor_test.rb`, `test/lib/visitor_actor_test.rb`). An owner passes every check, `forms.submit` too, which is harmless: only the endpoint calls `Forms::Submit`. The setup wizard creates the founding owner through `Users::Save` as that trusted nil actor on `:setup`, and every later step runs as the signed-in owner (`SetupController#act_as_signed_in_user`), so its events are attributed. `AccessControl.creatable_parents(actor, pages)` answers "under which of these pages may this actor create a page" (`pages.create` asked against a would-be child of each, branches preloaded in one query) for every parent picker — deliberately not `scope(actor, "pages.create", ...)`, which would never offer a branch grant's own root. `.holds?` is the same decision without a record, for nav/buttons only ("does this user hold `posts.edit` anywhere"), never to gate a write. The one other reader is `Passkeys::Policy#covers?`, which asks it of the *subject*, never the actor: whether a person counts as an admin for the passkey policy (an admin-area key, which no record narrows). That classifies who must hold a passkey; what may be written is still decided by each service's own rule (`Passkeys::Remove` lets the actor act on their own passkeys alone, and the policy only says whether the last one may go); with no record to match, any grant for the key counts except one whose scope names content types of which none is registered (`Scoping::Condition#dormant?`), so such a holder gets no Posts entry at all. `.scope(actor, key, relation, channel:)` (`AccessControl::Scoping`) narrows a `Post`/`Page`/`ContentBlock` relation to what's readable — used by every CS Studio list, the page tree, link-target/related-post/mind-graph search, `/preview`, and MCP's list/get tools — and `.tree_visibility`/`.preload_branches` exist purely for the page tree's cost profile: ancestors of a readable page are returned separately as `context_only` (greyed out, no actions, so a deep readable page still shows its path to the root), and `preload_branches` loads every listed page's closure-table ancestry in one query so per-row `allowed?` checks in a rendered list cost nothing extra. Everywhere a record could be looked up outside its scope — a CS Studio URL by id, an MCP `get_post`/`update_post`, a preview link — the answer is **not found, not forbidden**: a 404 or tool error, never a 403, so a locked-out record's existence isn't disclosed (one accepted trade-off: the related-posts editor discloses a *count* of hidden relations it can't show, "+N related posts you can't open", without naming them).

## Services

Every content, settings, user, group and token write funnels through `ApplicationService` (`app/services/application_service.rb`) — the exceptions are sessions (sign-in/out, audited directly as `session.*` by `Admin::SessionsController`, and `session.created` by `SetupController#update_admin` for the founding owner the wizard signs in), the `setup_completed_at` marker `Setup.complete!` sets, derived rows (`public_paths`, closure-table rows) the models maintain themselves, and a form delivery's state (`Forms::Delivery#record_attempt!`, `#record_sent!`, `#record_failed!`, `#resend!`: one statement each, from `Forms::DeliveryJob` and `Forms::Resend`, because a delivery's state is a job's, as mail's state columns are, and auditing every attempt would bury the log; what an editor asks for, Send again or a delete, is a service that audits; **no guard** for another writer, `docs/reference/forms.md`, "The services"): `#authorize!(key, record)` calls `AccessControl.allowed?`; on refusal a service returns `denied(key, record, message: nil)`, which records one `access.denied` audit event (outside the service's own transaction — a rolled-back forged write still leaves exactly one, coalesced, denial) and answers with the fixed message `"You don't have permission to #{permission.label.downcase}"`. `#record_event(action, subject:, field_changes:, metadata:)` is the write side, called inside the transaction so a rollback leaves no trace. Two tests enforce that this isn't opt-in. `test/services/service_contract_test.rb` is the grep tripwire: it eager-loads every `ApplicationService` subclass and reads the source of the class's own body (not the file, so a second service in the same file is not exempted by the first; comment lines excluded) for both `authorize!(` and `record_event(`, failing loudly on a service that has neither thought about authorization nor about the log; each check has its own escape hatch, `# authorize: none (reason)` and `# audit: none (reason)`, matched inside the class body and naming a reason a reviewer can check. A source check is satisfied by a service that calls `authorize!(` and ignores the answer, so the proof is behaviour: `test/services/service_behaviour_contract_test.rb`, with `test/support/service_calls.rb` (a factory per service naming its `permission:` and the record it acts `on:`), never reads source: it calls every service as a user with no memberships on `:admin` (and, where MCP reaches the service, as that user's API token on `:mcp`) and asserts a refusal (not a validation failure or an exception), exactly one `access.denied` event attributed to that actor and channel, and an unchanged digest of every table but the audit log; a control run of the same call, allowed, in a rolled-back savepoint must answer ok and change something, so "changes nothing" cannot be true of a call that would have changed nothing anyway. The trusted nil actor is never used for the refusal run. Its `EXPECTED_SERVICES` list is exact (a new service is added there and given a factory), `SELF_SERVICE` names the services open to any signed-in user for their own record and `OWN_RESULT` the bulk services that answer with their own result because the single-record services they run authorize and audit. A service that says `# audit: none (reason)` names the reason in its factory too, as `control_unaudited: "<reason>"`, and its allowed control run must then record **no** event at all, where every other allowed call must record one: today `Notes::React`, `Notes::MarkRead` and `Notes::SetFollowing` (a reaction, a read mark and a follow are not changes to content). The twelve `Notes::` services are ordinary entries of the list: a note needs the read right of the record it is on (`pages.read`, `posts.read`, or `media.upload` for an image), moderation its edit right, and "only the author edits a note" is a refusal logged against the read key with its own sentence, not a `SELF_SERVICE` (`docs/reference/notes.md`, "Who may do what"). The branches of each rule (publish-only saves, scoped grants, escalation) belong to `test/services/authorization_matrix_test.rb`, and each service's own tests cover the rest. One interim rule worth knowing before touching autosave: **editing an already-published record needs `publish`, not just `edit`**, because CS Studio's autosave writes straight to the live record — this goes away once pending revisions (Phase 3 versioning) exist. The converse holds too: a save that changes *only* the publish state (`published`/`published_at`, nothing else) needs only `publish` (`Posts::Save`/`Pages::Save#publish_only?`), so a read + publish "Publishers" group works.

## The audit log

`Audit.record(action, subject:, field_changes:, snapshot:, metadata:, coalesce: true)` (`app/models/audit.rb`) is the single write path for the log (`Audit::Event`, table `audit_events`) — reading actor/channel/request id/IP off `Current` rather than taking them as arguments, so a caller can't forge them. `*.updated` and `access.denied` events coalesce (`Audit::Coalescer`): a burst within `Audit::COALESCE_WINDOW` (exactly 10 minutes, measured from the *previous* event's `last_occurred_at`, not `occurred_at`, so a continuous autosave session keeps extending one row for as long as it runs) merges into the open row instead of one row per keystroke pause; everything else stays discrete. A coalesced extension never writes `metadata` (it is outside the append-only allow-list), so an `*.updated` event whose point is its metadata is recorded with `coalesce: false` (`record_event` passes it on) and is a row of its own: a section's fold with its `folded_block_ids` (`ContentBlocks::Save`). A later event may still extend that row and leaves its metadata as written. Each event carries `field_changes` (old → new per field, named `field_changes` — never `changes`, which `ActiveRecord::Dirty` already owns) and a full `snapshot` of the subject after the change (`Audit::Snapshot`, the version basis Phase 3 versioning will build on). One kind of value is summarised in `field_changes` as a rich-text body is: a `:code` field of a type's schema (the Code block's source, and any block or post type's field of that type, one level into a field group) is `{ "settings code" => { "digest_before", "digest_after", "length_before", "length_after" } }` there (the column and the field in one key, only when the code changed; the column's other keys stay `"settings" => [old, new]` without the code), while the snapshot holds the source whole, as it holds a body, because it is the version basis. The source is a key of `settings`, a plain column, so before this a changes row held the settings' whole old and whole new hash beside the snapshot: three copies. What that costs is counted per typing session and not per save, because `*.updated` events coalesce into one row that each save rewrites: for a 20,000-character source about 60 KB a session and block then, about 20.5 KB now (the one copy in the snapshot; a post's snapshot already holds every language's whole body, with no cap). It is decided by the field's type in the record's definition (`Audit::Snapshot.typed_changes`), never by a type's name or a key called "code", so a record whose type is no longer registered is recorded as stored. The audit screen reads such a row as "Changed", as it reads a body's, and a burst folds into the first `…_before` and the last `…_after` (`Audit::Coalescer.merge`) (`test/models/audit/snapshot_test.rb`: "one save of a 20,000-character source writes small changes that hold none of it, and a snapshot that holds it once", "the digest of a code field differs when the source differs, and the other settings are recorded as before", "a block type without a code field is recorded exactly as before, a key called code included", "a post type's code field gets the same treatment in the changes, by its type, and so does one inside a field group", "a burst of saves folds into one event: the first digest and length before, the last after"). Both are scrubbed of secrets twice over (a `NEVER_STORED` list, then a pass through `Rails.application.config.filter_parameters`), so a password digest, token digest, or raw token can never land in the log even if a snapshot serializer dumped raw `attributes`. The table is append-only twice: `Audit::Event` itself refuses any update outside its coalescing columns (`field_changes`, `snapshot`, `last_occurred_at`, `occurrences`) and any destroy, and the Postgres trigger `db/triggers/audit_events_append_only.sql` refuses the same at the SQL level (covering `delete_all`/`update_all`/raw SQL too — deliberately not `TRUNCATE`, so `db:truncate_all` still works in development) — reapplied after every schema load, not just every migration, via `config/initializers/db_triggers.rb` hooking `ActiveRecord::Tasks::DatabaseTasks.load_schema`, since `db/schema.rb` itself can't carry a trigger and `db:schema:load`/`db:reset`/parallel test workers' own database copies all bypass migrations entirely. After the writing transaction commits, `Audit.record` publishes `ActiveSupport::Notifications.instrument("audit.content_spiel", event:)` — the plugin hook for anything that wants to react to audit events, never before commit, so a rolled-back write triggers nothing. Live editing is its first listener inside the app: `Editing::Signals.heard` maps an event's action to the signal an open editor fetches on (`config/initializers/editing.rb`; every action in `Audit::Sentence::ACTIONS` must be placed in `Editing::Signals::MAP` or `SILENT`, `docs/reference/live-editing.md`). `session.failed` has no user to name, so its `metadata` holds the email address that was tried (`email_address`, cut to 254 characters, and only when the value contains an `@`, so a password typed into the email box by mistake is not kept), never the password (`Admin::SessionsController#email_metadata`). Only an attempt whose password was checked is `session.failed`: one a closed bucket or the bot check refused checked none and records nothing, or a bot's run would bury the log. **`session.locked`** is one event per bucket a failed attempt closed, with no actor and no subject, for the same reason as `session.failed`: naming the account would take a lookup in the request, and a refusal for a known email would then cost more than for an unknown one (equal timing is the rule; the subject is not). Its metadata is `bucket` (`account`, `device` for a browser that signed in to the account before and is counted apart, `docs/reference/hosting.md`, "Sign-in on the open internet", or `address_wide`), `seconds` (how long it is closed), and for the account's and a device's also `email_address` (as `session.failed` keeps it) and `level` (the back-off: 0 for the first minute); the address is the event's own `ip`. Its sentence is "Sign-in to one account paused after repeated failures", "Sign-in to one account from one browser paused after repeated failures" or "Sign-in from one address paused after repeated failures", and it is a Security event (`Audit::Sentence::NO_ACTOR`, `SECURITY_ACTIONS`; `test/integration/sign_in_throttles_test.rb`: "the fifth failure records one session.locked with the bucket, level and seconds, and the sixth attempt in that minute records nothing", "the fiftieth failure from an address answers Try again later and records session.locked for address_wide").

**In CS Studio** the log is one card of day sections under sticky day headings, each event one row of its time, who did it (the small actor avatar), its sentence, its channel and, for a security event, a warn "Security" state chip in words, never red; the event page shows its facts in one card and its changes as word diffs whose removed words are struck through, not red. How it is read, filtered and drawn is in `docs/reference/cs-studio-shell-and-dashboard.md`, "The audit log".

**Publishing events and the rule's reason.** `Publishing::PublishChanges`, `Publishing::DiscardChanges` and `Publishing::CancelScheduledChange` are `ApplicationService`s in `EXPECTED_SERVICES`, audited as `page|post.changes_published` (number, `live_at`, whether scheduled), `changes_discarded` (the number returned to and the withdrawn one) and `scheduled_change_cancelled`, on the content record, never coalesced, with `snapshot: nil`; `Audit::Sentence` tells them as "published changes to Pricing", "scheduled changes to Pricing for 12 Oct" (a publish with a time), "discarded the unpublished changes to Pricing" and "cancelled the scheduled changes to Pricing". Publishing needs `<owner>.publish`; a discard needs what editing the record needs (`AccessControl::OwnerRule`). That rule, `edit` and, once the owner has a `published_at`, `publish`, no longer means that a save is public (it is not: the site shows the published copy, `docs/reference/publishing.md`) but that the person who may change a published record is the person who may publish it (drafts spec D5), until preparing and approving are two rights; `OwnerRule`'s comment, `Translations::EditRight`'s and `Admin::EditorScreen::HeaderComponent#view_only_hint`'s say so (`test/models/audit/sentence_test.rb`; `test/services/service_behaviour_contract_test.rb`).

**Note events.** `note.started`, `note.replied`, `note.edited`, `note.deleted`, `note.resolved`, `note.reopened`, `note.pinned`, `note.unpinned` and `notes.removed` take the **content record** as their subject (the page, post, block or image the thread is on), so they appear in that record's Activity and are read-scoped like it; a refusal's `access.denied` names the container, the record whose right was missing. They are recorded with `snapshot: nil` and metadata that holds ids only (`thread_id`, `message_id`; `thread_ids` for a removal): a note's text, its quote and its files' names never reach `Audit.record`, because the log is append-only and would keep a deleted note's words for ever. `Audit::Sentence::NOTE_VERBS` words them, and `Dashboard::Feed::NOT_A_CHANGE` (`access.denied`, the three `…taken_over` actions and those keys) keeps them out of "Mine" and out of `Audit::ChangeSince`'s "Changed by": a note is not a change to the record. The same text is kept out of the request log by `config/initializers/filter_parameter_logging.rb`, which filters `body` and `quote` only for a request to a notes controller, because `Audit::Snapshot.scrub` drops every snapshot key that list matches and a bare `:body` would have taken a post's and a block's body out of their snapshots.

**Take-over events.** `page.taken_over`, `post.taken_over` and `block.taken_over` (`Editing::TakeOver`, the one audited write of live editing) are recorded when an edit reservation passes from the tab that held it to someone who asked for it. The subject is the content record (the page, the post or the block), `snapshot: nil`, never coalesced, and the metadata is two ids and a flag: `from_user_id`, `to_user_id`, `answered`. No name and no text. The actor is whoever called the service, so `Audit::Sentence` has two verbs for the one action (`#handed_over?`): "handed over editing" when the holder's tab answered (`answered: true`) and "took over editing" when the requester passed over a tab that did not (`answered: false`); for a block the sentence is "… editing a block on “Pricing”". The other person is in the metadata's ids, never in the sentence. They are in `Dashboard::Feed::NOT_A_CHANGE`: a take-over writes no content row, so "Mine", "Changed by" and the editors' "Updated by" skip it, and `Dashboard::Activity` does not list it. Claiming, renewing, releasing and withdrawing a reservation are not audited at all (`test/models/audit/sentence_test.rb`: "a take-over reads as having taken over editing, of a block on its page, of a page, of a post", "an answered take-over reads as the actor having handed editing over, an unanswered one as having taken it"; `test/components/admin/ui/audit_sentence_component_test.rb`: "an answered take-over reads handed over, an unanswered one took over, and neither names a second person").

**Invitation events.** `invitation.created`, `invitation.resent` and `invitation.withdrawn` (`Invitations::Invite`, `Resend`, `Withdraw`, `users.manage`) are on the `Invitation` (labelled by its address, its snapshot the address, name, inviter, dates, account and group ids; the audit log's Type filter lists "Invitation"); `Audit::Sentence` words them "invited <person>", "sent a new invite to <person>" and "withdrew the invite to <person>" (`OTHER_VERBS`). `invitation.accepted` (`Invitations::Accept`) is recorded on the USER that accepting creates, as its ACTOR and its subject at once, whoever else is signed in in that browser, since the invitation's token is the credential (the service says `# authorize: none` with that reason, and the service contract exempts it as `TOKEN_CREDENTIAL`); its sentence is "accepted the invite" (`SPECIAL_ACTIONS`), its changes the new account's fields and `group_ids`, its metadata the invitation's id. Nothing of the token is in any of them. All four are in `Editing::Signals::SILENT`. A bad token records nothing, as the reset's does: nobody was refused a permission. A withdrawal's event is written before the row is deleted. **Mail settings in the log**: a save of Settings → Mail is a `settings.updated` like any other; the login is "Mail login" "set"/"not set", never a value (`mail_username`, `mail_password` and `mail_verified_fingerprint` are in `Audit::Snapshot::NEVER_STORED`), and the state's columns (`mail_verified_at`, `mail_last_sent_at`, `mail_failed_at`, `mail_failure`, `mail_login_saved_at`) are in `IGNORED_CHANGES`: a send is not a change of the settings, and a test mail records no event (`docs/reference/mail.md`).

**Form events.** `form.created`, `form.updated`, `form.trashed`, `form.restored` and `form.purged` are on the form (`Forms::Form`, labelled by its name; the audit log's Type filter lists "Form"; its snapshot is its columns and its destinations, a destination's secrets by name only, and `secrets` is in `Audit::Snapshot::NEVER_STORED`), worded in `OTHER_VERBS` ("created the form “Contact”", "moved the form “Contact” to the trash"). The three submission events take the FORM as their subject and carry ids, a count, a reason and a kind, never an answer, a label, a language or an address: `form_submission.received` (`Forms::Submit`, recorded as the visitor: no actor row, `actor_label` "visitor" (`Audit::VISITOR_LABEL`), no IP whatever `Current.ip_address` holds, never coalesced; its sentence reads "A visitor sent the form “Contact”"), `form_submission.resent` (`Forms::Resend`, "sent a submission of “Contact” again") and `form_submissions.deleted` (`Forms::DeleteSubmissions`, with the count, the reason and, for 50 or fewer, the ids; "deleted 3 submissions of “Contact”" and, for the jobs' reasons, "at the end of their keeping time", "after they were delivered", "that couldn't be delivered in 30 days"). They are `Audit::Sentence::SUBMISSION_ACTIONS`, which `Dashboard::Feed::NOT_A_CHANGE` reads, and every form event is in `Editing::Signals::SILENT` (`docs/reference/forms.md`).

**Counted sentences.** `Audit::Sentence::COUNTED` (`block.created`, `block.updated`, `media.uploaded`) are the actions with a counted form, which `Dashboard::Activity` collapses a run into: `Audit::Sentence.build(…, count:, mixed:, at_least:)` tells "added 4 Code blocks to “…”", "edited 3 blocks on “…”" (`mixed` names no type) and "uploaded 12 images", the last with a `:collection` part (a counted set of records, linked to the library by `Audit::Sentence.library_route` and never quoted). A count above 1 for any other action, or with no target, raises; `at_least:` ("60 or more") is for a run the dashboard's read cut off. Only the dashboard passes a count: the audit log tells every event on its own and does not collapse.

**What "Changed by" counts for a page.** `Audit::ChangeSince` names who made a refused save stale. For a post it counts the post's own events and those of the blocks it owns. For a page it counts the page's own events only: the page settings form's base is `pages.settings_changed_at`, which a block's save does not move, so only an event about the page itself can have made it stale (`test/queries/audit/change_since_test.rb`: "a block saved after a page's settings change is not named as the cause of a refused settings save").

## Sessions: their limits and their endings

A `Session` (`app/models/session.rb`) is one signed-in browser: the signed `session_id` cookie names its row. Every session is made through `Session.start(user:, method:, user_agent:, ip_address:, enrolment_due: false)` (`Authentication#start_new_session_for(user, method: "password")`, which passes `enrolment_due` from the passkey policy, below), which writes `confirmed_at` (now: the sign-in proved its person, for Confirm it's you), `enrolment_due`, `last_seen_at` (now), `expires_at` (now plus `Session::ABSOLUTE_TIMEOUT`, 14 days) and `authenticated_with` (one of `Session::METHODS`: `password`, `passkey`, `sso`, `recovery_code`; any other is refused). The cookie is not permanent: its `expires` is the session's `expires_at`, so it never outlives the row. Two timeouts end a session: **idle** (`Session::IDLE_TIMEOUT`, about 12 hours without a request or a cable connection that met it: it counts from `last_seen_at`, which lags the last request by up to `SEEN_EVERY`, so it can end a session up to 5 minutes early) and **absolute** (`ABSOLUTE_TIMEOUT`, whatever is done with it). When both hold, the absolute one is the reason, since it is the one the cookie carries (`Session#expiry`). `last_seen_at` is written at most every `Session::SEEN_EVERY` (5 minutes) through `update_column`, so two tabs racing the write both write, neither raises, and `updated_at` and the callbacks never move.

**One lookup.** `Session.from_cookies` is the only way a request or a cable connection finds its session (`Authentication` and `ApplicationCable::Connection` both call it), so the two can never authenticate by different rules. It answers only a LIVE session (and marks it seen), and a session it finds past either timeout it ENDS there, at the first request or connection that meets it (`Sessions::End`, reason `expired_idle` or `expired_absolute`, no actor; inside a request's span an `auth.session` span is drawn around it, and at the cable's connect, which runs outside any request's span, none is: `Telemetry.in_child_span`), and answers nil. A request that gets nil from a cookie that named a session is told so, once, in that browser only: `Authentication#forget_ended_session` clears the cookie and flashes `session_ended`, which the sign-in page words "Your session ended. Sign in again." (the notice is `data-turbo-temporary`, so a cached preview of the page never says it again). Only a page the person asked for does that (a GET or HEAD for HTML that is no XHR): a write or a script's fetch (an autosave, a stream, JSON) that meets the gone session first follows its redirect inside the fetch, where the flash would be spent unseen, so it leaves the cookie and the flash alone and the person's next page says it. Turbo's own GET (a Drive visit, a frame's load, a hover's prefetch: `X-Turbo-Request-Id`) and a script's GET for a frame (`Turbo-Frame`) are not redirected at all (`Authentication#turbo_get?`): the fetch would draw the sign-in page and spend the notice, and where the sign-in page asks to be loaded whole (`turbo-visit-control`, on a site with the bot check's keys) Turbo would then load it again without it. They are answered with a page Turbo may not draw, so Turbo loads the address it asked for whole, and that load is told (`test/system/admin/session_ended_test.rb`: a sidebar link, a link in `#content` and a full visit, with and without the keys). A script's plain GET for HTML (the live editing refresh) cannot be told from a visit and counts as a page. A browser with no cookie or a forged one (`cookies.signed` reads nil) is told nothing, and the sentence names no account, so it says nothing about whose session it was. `Session.live(at)` is the scope for what a person is SHOWN as signed in (an expired row stands until a request meets it or the sweep runs); a count of "open" sessions reads it (`User#open_sessions`, `open_session_count`). A socket already open is judged again at every subscription by the same rule (`ApplicationCable::Channel#subscriber` reads `Session.live`), so one whose session passed a timeout before any request met it subscribes to nothing.

**The endings.** Every ending destroys the row through the model's callbacks, never `delete_all`, because `after_destroy_commit :disconnect_cable` is what takes the user's open WebSockets with the session. A relation of sessions is ended through `Session.destroy_each_locked` (each row read under its lock and destroyed, answering how many; a row another request ended first is not counted), called inside the transaction that records the ending. `disconnect_cable` is per user, not per session (Action Cable names a connection by its user), so every row ended, the sweep's stale ones included, disconnects all of its user's sockets: a tab whose own session still stands reconnects in a moment, harmlessly, and the hourly sweep adds that churn once per swept row of someone still at work.

| Ending | Where | `session.ended` reason | Actor |
|---|---|---|---|
| Sign-out | `Authentication#terminate_session` | none: still `session.destroyed` | the person |
| An expiry met by a request or connection | `Session.from_cookies` -> `Sessions::End` | `expired_idle`, `expired_absolute` | none, subject the user |
| The hourly sweep | `Sessions::SweepJob` | `expired_absolute`, then `expired_idle` | none, no subject |
| "Sign out everywhere else", a row's End (Your account) | `Sessions::EndOthers` | `ended_by_self` | the person |
| An owner's "End all sessions" (user editor) | `Sessions::EndAll` | `ended_by_owner` | the owner |
| A changed password | `Users::OwnerProtection#end_sessions_after_password_change` | `password_changed` | whoever changed it |

`Session::END_REASONS` lists the five reasons, and `Sessions::End` refuses any other. The rules the table holds:

- **Sign-out stays `session.destroyed`.** The append-only log already holds `session.destroyed` rows whose sentence reads "signed out", and `Users::LastSignIn` reads `session.created`; a second name for the same act would split the audit filter. Every other ending is `session.ended`, in the Security filter's set (`Audit::Sentence::SECURITY_ACTIONS`).
- **One audit event per act, never per row.** "Sign out everywhere else", "End all sessions" and a password change record ONE `session.ended` with `metadata["count"]` and the user as subject, however many rows ended, and none when nothing ended. The sweep records at most one per reason per run, with a count and no subject. A request that meets its own expired session records one, the user its subject. No snapshot: the user did not change (a password change's own record is the service's `user.updated`).
- **`Sessions::EndOthers` ends only the actor's own sessions**, and never the one it is told to keep (`keep:`, the session the request is made in, so the person stays signed in on the answer). With `only:` the id is looked up among the user's own sessions: another user's id, one already ended, one that never was and the kept session itself all end nothing, record nothing and answer ok with 0, the same answer as for a session of theirs that had already ended ("That session had already ended."), so an id tells the caller nothing about whose it is. A token never ends sessions; it is denied.
- **`Sessions::EndAll` is the owner's, for another user.** It is not offered on the owner's own account and refuses it ("End your own sessions from Your account.", the service's own key `admin.users.sessions.own`; the zone's reason is `reason_own`, the same words): ending every session would end the one the owner acts in, which is Your account's "Sign out everywhere else". Like the other owner zone actions it asks `Users::Manageability.actor_owner?` in `#call`, since no permission says "owner".
- **A password change ends the changed user's sessions but the acting one.** A person changing their own password keeps the session they changed it in; an owner changing another user's ends ALL of that user's (the acting session is not theirs). One `password_changed` event with the count, in the same transaction, and none when no other session was open.
- **The expiry span is drawn only when a request ends a session for expiry** (`auth.session`), never on a live request: a span on every signed-in request would be noise the WorkSampler keeps. A cable connection's expiry is audited and not traced, since its span would be a root the sampler drops (`docs/reference/hosting.md`, "Telemetry").

**The sweep.** `Sessions::SweepJob` runs hourly (`config/recurring.yml`, `sessions_sweep`, minute 40, in every environment) and ends what no browser came back to meet. It sweeps the absolute timeout first, so the idle read after it holds only sessions that are idle alone and each is counted under one reason; rows go in batches of `BATCH` (500), each batch in its own transaction through `destroy_each_locked`. A reason's event is recorded after its batches, in an `ensure`, so a batch that raises after others committed still leaves one event with their count before the error reaches the job. It runs inside an `auth.session_sweep` span carrying the total.

**Words.** `Audit::Sentence` tells `session.ended` by its reason and its count, and an expiry by the timeout its event stored (`metadata["after_hours"]` for `expired_idle`, `["after_days"]` for `expired_absolute`, written by `Session.timeout_metadata`), so an old event keeps its words when a timeout changes: "Session of “Bo” ended after 12 hours unused", "3 sessions ended 14 days after sign-in" (the sweep, no subject), "ended 2 of your other sessions" / "of their other sessions", "ended every session of “Bo” (3)", "2 sessions of “Bo” ended by a password change". Only `ended_by_self` and `ended_by_owner` name an actor (`SESSION_ENDED_BY`); an expiry and a password change's sentence are about the sessions and are told with none, as `NO_ACTOR`'s are, whoever the event's actor was. An unknown reason reads "N sessions of “Bo” ended", or "N sessions ended" with no subject.

**A session's device.** Your account shows a session as a person's words, from its stored `user_agent`: `SessionDevice` (`app/values/session_device.rb`, the `useragent` gem, which sits outside the Hotwire group) answers a browser's name and a system's ("Firefox on macOS"; "Edge", which the gem reads as Chrome or Safari, by its token). A user agent is what a client chose to send, so it is untrusted: one over `MAX_LENGTH` (512) is not parsed, a bot or a product that is not a browser has no browser name, a system the gem names its own way is reduced to a short name or to none, and nothing raises. The screens are in `docs/reference/users-groups-tokens.md`.

## Passkeys, recovery codes and the second step

Spec: `docs/superpowers/specs/2026-11-10-studio-sign-in-design.md` §3; the screens and their words are `docs/superpowers/specs/2026-11-11-passkeys-screens.md`. A person may sign in with a passkey alone, or with their password followed by a passkey or a recovery code; an owner decides who must hold a passkey.

**What a person holds.** A `Passkey` (`passkeys`) is a WebAuthn credential of one account: `external_id` (the credential id, base64url, unique), `public_key` (COSE, base64url), `sign_count`, a `name` its person typed (at most `Passkey::NAME_LIMIT`, 60), `transports` and `last_used_at`. A `RecoveryCode` (`recovery_codes`) is one of a set of `RecoveryCode::COUNT` (10) codes of eight characters of Crockford's base32 shown as `XXXX-XXXX`, of which only an HMAC-SHA256 is stored (`RecoveryCode.digest`, under `Rails.application.key_generator` with the purpose `"content_spiel recovery code"`, unique per account; the key is derived from `secret_key_base`, so **rotating `SECRET_KEY_BASE` voids every recovery code**: no stored digest matches again, a right code is told "That code didn't work.", and each person makes a new set with Regenerate… on Your account after a rotation, before they need one; `docs/reference/hosting.md`, "What a host sets"), read however it was typed (small letters, spaces and the hyphen dropped, O as 0, I and L as 1); a code is used by one `UPDATE … WHERE used_at IS NULL` through `user.recovery_codes.redeem(text)`, the association's extension and the only way, so two tabs cannot both use one and no caller redeems a code by its digest without its account. `User#webauthn_handle!` is the random handle (`users.webauthn_id`) an authenticator keeps in place of the email, made at the first ask and kept, written only where the row has none so two first asks agree. Both tables are `dependent: :delete_all` from `User`. **`User#second_factor?`**, a passkey or an unused code, is the account's rule: such an account is never signed in by its password alone. Nothing of the material reaches a page, a span, a log line or the audit log: `Audit::Snapshot` draws a passkey as its id, owner, name and dates and a code as its id, owner and dates, and `external_id`, `public_key` and `digest` are in `NEVER_STORED`; `filter_parameters` holds `/\Acredential\z/` (the WebAuthn JSON a script posts, the exact name, since a bare `:credential` would drop a user's and a destination's `credentials` from the audit log) and `:recovery_code` (`test/models/audit/snapshot_test.rb`; `test/integration/passkey_telemetry_test.rb`).

**The ceremonies** are plain objects of `SignIn` over the `webauthn` gem, knowing no session, cookie, route or mail. `SignIn::RelyingParty.for(address:, request_origin:, name:)` is the one place that decides which domain a passkey belongs to: with `PUBLIC_HOST`, the registrable domain of its host (`PublicSuffix.domain`, private section included) or the host itself, and the address's origin as the one allowed origin; with none (development, test), the request's host and origin; at an IP host, `nil`, since WebAuthn refuses an IP as an id. A browser binds a credential to that id for good, so a change of what it answers orphans every passkey made ("Sign-in on the open internet" in `docs/reference/hosting.md` says what a domain move costs). With no relying party no passkey button is drawn, every passkey endpoint answers 404, the enrolment guard holds nobody and the wizard's step goes on (`test/models/sign_in/relying_party_test.rb`; `test/integration/passkey_sign_in_test.rb`: "with an IP request host there is no passkey button and both endpoints answer 404"). `SignIn::PasskeyRegistration` asks for a discoverable credential with user verification and no attestation, excluding the person's own; `SignIn::PasskeyCheck#verify(json, challenge:, credentials:, ceremony:)` (`CEREMONIES`: `sign_in`, `second_factor`, `confirm`) finds the passkey among `credentials` only (every passkey for a passkey sign-in, the account's own for a second proof), asks for user verification, refuses a sign count that goes backwards (a synced passkey's stays 0 and passes) and a user handle that is not the stored one, and records the use (`Passkey#used!`). Each verification is one `auth.passkey` span. The browser's half is one plain module, `app/javascript/passkeys/ceremony.js` (pinned with `preload: false`, so no public page loads it), used by `passkey-sign-in` (the product layout's sign-in and second step, which imports it in `connect()`), `admin--passkeys--register` and `admin--passkeys--confirm`. WebKit runs the browser's prompt only inside a press, so the options are fetched before the press that opens it (on connect for sign-in and the second step, when the Add dialog or the confirm dialog opens), and the press calls the API at once.

**The challenges** (`PasskeyChallenges`, a controller concern with `issue_passkey_challenge(purpose, challenge)` and `take_passkey_challenge(purpose)`; `PURPOSES`: `sign_in`, `second_factor`, `confirm`, `register`) are kept in a cookie of their own per purpose, `cs_passkey_<purpose>` (encrypted, HttpOnly, SameSite Strict, path `/`, a browser-session cookie with no `Expires`: the lifetime is the server's check of `at`, and a date of the browser's own would drop the cookie at once on a machine whose clock runs five minutes ahead), never in the Rails session: the cookie store writes the whole session back on every request that loads it, so any request sent with the cookie from before the options (a favicon, a prefetch, a live refresh) would put the session back without the challenge. Only the options answer writes the cookie and only the take deletes it. One older than `PasskeyChallenges::LIFETIME` (5 minutes), or issued for another purpose, is no challenge and the answer is a wrong passkey. So every script that holds options for a press (sign-in's button, the second step's, Confirm it's you, adding a passkey on Your account, on enrolment and in the wizard) holds them through `passkeys/held_options` (`HeldOptions`), which replaces them four minutes after they arrived while the tab is shown, and whenever the tab is shown again, so the tab in use holds the latest challenge when a second tab has fetched its own; a press on a set older than four and a half minutes waits for a fresh one first (`test/integration/passkey_sign_in_test.rb`: "the challenge's cookie lasts the browser's session, and the server alone refuses it after five minutes"; `test/system/admin/passkey_sign_in_test.rb`: "a tab shown again fetches fresh options, so a page left open past five minutes still signs in", "a press on options too old to use fetches fresh ones first and signs in"). **A challenge is taken once, on the server**: the take spends it in `SignIn::SpentChallenge` (table `sign_in_spent_challenges`: an HMAC of the purpose and the challenge, unique, and `expires_at`, a second past the challenge's own), by one `INSERT … ON CONFLICT DO NOTHING` judged by the row it returned, so of any number of sends of one challenge, at the same moment too, exactly one is let through; a failed statement or a lost connection (`ActiveRecord::StatementInvalid`, `ActiveRecord::ConnectionNotEstablished`) is no spend and refuses, logging the error's class alone, and any other error is the code's own and is raised. Deleting the cookie only asks the browser to drop it, and a copied cookie with a captured assertion would otherwise pass again (a synced passkey's counter does not stop it). The hourly `Sessions::SweepJob` deletes the expired rows (`SpentChallenge.sweep`) (`test/models/sign_in/spent_challenge_test.rb`: "of several spends of one digest at the same moment exactly one wins", "a database error is not rescued: it is no spend"; `test/integration/passkey_sign_in_test.rb`: "an assertion sent twice, one after five minutes and one made for another purpose's challenge are refused, and the second press works with a fresh challenge", "a database error while a challenge is spent refuses the passkey, signs nobody in and logs the error's class alone", "an error of the code's own while a challenge is spent is not taken for the database's"). Signing out deletes every challenge's cookie (`Authentication#terminate_session`, `PasskeyChallenges.cookie_names`): a challenge is the signed-out person's ceremony, never the next person's on the same browser (`test/integration/sessions_test.rb`: "signing out deletes every passkey challenge's cookie").

**Signing in with a passkey** (`Admin::SessionsController#passkey_options`, `#passkey`) names no account until the assertion is verified, so it counts in the address's wide bucket alone (`SignIn::Throttle#reserve_address`; a verified passkey takes its count back, `#release_address`), and no account's lock refuses it: a passkey cannot be guessed, and a bot naming a credential must not lock its owner out; it never asks for the bot check. The answer is 200 JSON `{ "location" }` whatever happened, so a script cannot tell one refusal from another: CS Studio (or the page the person was sent from), or the sign-in page with "That passkey didn't work. Try again, or sign in with your password." ("Try again later." past the wide bucket or the rate limit, which `create` and `passkey` share). The options have a per-address rate limit of their own, on sign-in, the second step and Confirm it's you alike (`name: "options"`, 30 a minute, looser than the proofs' because options write nothing on the server and an office behind one address must keep its passkey button): past it the answer is a bare 429, which the scripts take as no passkey to offer, and no challenge is kept (`test/integration/passkey_sign_in_test.rb`: "the options are limited per address on a count of their own: the thirty-first in a minute is a bare 429 that keeps no challenge"). A refused passkey names no account and records nothing of its own; the wide bucket it closed is one `session.locked` (`test/integration/passkey_sign_in_test.rb`: "a passkey signs in an account whose email bucket a bot holds closed").

**The second step** (`Admin::SecondFactorsController`, `<admin>/sign-in/second-step`, on the product layout). A right password for an account with a second factor is `:second_factor_required`: nobody is signed in and no known device is written; the account is held in `cs_second_factor` (`SECOND_FACTOR_COOKIE`: `{ "user_id", "at" }`, encrypted, HttpOnly, SameSite Lax, never the password), a browser-session cookie whose `SignIn::SECOND_STEP_LIFETIME` (5 minutes) is held by the server's check of `at` alone, and the person goes to the step, on its code view when the account has no passkey; the code view of an account with a passkey links back to the passkey view ("Use your passkey", beside Start over). A late cookie, or one naming no account, is the sign-in page with "That took too long. Sign in again."; Start over deletes it. One of the account's own passkeys or one of its unused codes finishes the sign-in; a wrong code and a used one are one sentence; a code's success lands on Your account's passkeys, which says how many are left, records `recovery_code.used` and mails the account (`docs/reference/mail.md`, "The two account mails"), and forgets the page the person was sent from (`return_to_after_authenticating`), which the other sign-ins take. A refused proof that closes the account's, the device's or the address's bucket says the pause ("Try again in a few minutes.", the address's "Try again later.") on that refusal, as sign-in and Confirm it's you do. (`test/integration/second_factor_test.rb`.)

**A second proof counts where the password counted** (`SignIn::Proof`, `account:`, `identifier:`, `address:`, `span:`, `device:`; `#recovery_code`, `#password`, `#passkey`). The password step's count in the account's bucket (or the known device's) stands until the second proof succeeds, and its address counts are taken back at once, with any lock the reservation wrote (`Throttle#await_second_proof`), so one whole sign-in costs the address one count, as a password-only sign-in does, and a right password never locks its own account. The lock taken back is the one the reservation's trip names, never one read from the `device:` handed in, and a take-back that goes below 0 adds back its own 1 and no more, so take-backs at once of more than was counted settle at 0 (`test/models/sign_in/throttle_test.rb`: "take-backs at once of more than was counted leave the count at 0", "await_second_proof takes back the lock its reservation's trip names, whatever device it is handed"). Each proof reserves in the account's (or device's) bucket again BEFORE it checks anything: a closed bucket is `:locked` and nothing is checked (no code used, no passkey verified, no password hashed), a wrong proof counts as a wrong password does and the run closes the account as wrong passwords do, and only a right proof forgets the run (`Throttle#record_success`). So a stolen password earns no session, no known device and no fresh guesses (`test/models/sign_in/proof_test.rb`; `test/integration/second_factor_test.rb`: "a right password then five wrong codes closes the account, mails its person, and no session or known-device cookie was ever written", "after a whole sign-in the account's run is clear and the address's wide count is one"). A closed bucket at the second step or in Confirm it's you is audited and mailed as at the password step (`Admin::SignInLocks`, which both share with sign-in: one `session.locked` per trip, the account's pause mail at most once an hour). **A bot can still delay a covered person**: one that polls an email's bucket closed at every lock's end keeps the password step, and with it the second step, refused on a browser the person never signed in with, as it does for an account with a password alone; their known device (its own bucket) and a passkey sign-in (no account's bucket) answer it. **No guard** measures it.

**A whole sign-in** is `Admin::SignInCompletion#complete_sign_in(user, method:)`, however its person proved it (a password with no second factor, a passkey, the second step): the session (`start_new_session_for`), the known-device cookie `cs_known_device` (`DEVICE_COOKIE`), `session.created` with `{ "method" }` when it is not `password`, and forgetting the bot check's flag. **The known-device cookie is written there and nowhere else**, so a password step that still owes its second proof earns none: otherwise a stolen password would earn its own device bucket beside the account's lock (`test/integration/second_factor_test.rb`: "a right password for an account with a passkey goes to the second step and starts no session").

**Confirm it's you.** `sessions.confirmed_at` is set by `Session.start` and by `Session#confirm!`; `Session#confirmed_recently?` is within `Session::CONFIRM_WINDOW` (10 minutes). Four actions change how a person signs in and are gated on the server by `Admin::RecentConfirmation` (`require_recent_confirmation only: […]`): the registration options and the add (`Admin::PasskeysController#options`, `#create`), the remove (`#destroy`) and making codes (`Admin::RecoveryCodesController#create`). A gated request outside the window writes nothing: JSON is 403 `{ "confirm": true }`, a Turbo Stream is 403 with a stream that appends a `request` target to the dialog's requests (`ConfirmIdentityDialogComponent::REQUESTS_ID`), anything else a 303 to Your account's passkeys; both 403s carry the header `X-Confirm-Identity` (`RecentConfirmation::CONFIRM_HEADER`), so the script tells the gate's refusal from any other 403 without reading the body. `admin--passkeys--confirm` opens the dialog (`Admin::Ui::ConfirmIdentityDialogComponent`, `#confirm-identity`: "Use your passkey" first for a person who holds one, else the password) and then makes the call again, or sends again the one form the gate refused (a form marked `data-confirm-identity`, known by the header at `turbo:submit-end`); a cancelled confirmation sends nothing later. For Add the confirmation comes when "Add a passkey…" is pressed, before the Name dialog, which then opens by itself; for Remove and the codes it comes after their own confirm. `Admin::ConfirmationsController` (`POST account/confirmation`, `/options`, `/passkey`) checks the password or one of the person's own passkeys through `SignIn::Proof` under `auth.confirmation`, in the account's bucket: a wrong password counts as one at sign-in, the bucket-closing fifth answers 429 with "limited" and records `session.locked` and the pause mail, and a closed bucket checks nothing. A right proof confirms this session only and records nothing; a checked proof that failed is `session.confirmation_failed`. Rename and ending a session are not gated (`test/controllers/admin/confirmations_controller_test.rb`; `test/controllers/admin/passkeys_controller_test.rb`, `recovery_codes_controller_test.rb`, which hold the gate through the four actions). **No guard** for a fifth action that changes how a person signs in and is not declared behind the gate.

**Codes and passkeys together.** `Passkeys::Add` stores the passkey and, when the person holds no unused code (their first passkey, or every code used), ten new codes in the same transaction under the account's row lock, shown once; it clears `enrolment_due` on every session of the person and records `passkey.added` (and `recovery_codes.generated`), then mails `passkey_added` after the commit. `Passkeys::Remove` refuses the last passkey of a person the policy covers (read under the row lock, so two removals at once cannot both pass for the last two) and takes the codes with the last passkey of anyone else, so "you'll sign in with your password again" is true (`test/services/passkeys/remove_test.rb`). `RecoveryCodes::Generate` replaces every code the person held, and refuses a person with no passkey (read under the row lock), since codes are a backup for passkeys and alone would be asked for and spent at every sign-in; Your account's card offers neither Generate… nor Regenerate… to them, and enrolment and the wizard make codes only with a passkey (`test/services/recovery_codes/generate_test.rb`: "a person with no passkey is refused, and nothing is written or recorded"). All four services (`Passkeys::Rename` too) act on the actor's own account only, never a token's, and the codes reach no event, log line or attribute: they are the copy box's text in `Admin::Ui::RecoveryCodesComponent` and nothing else, which its script forgets at `turbo:before-cache` and `pagehide`, on a page marked `turbo-cache-control: no-cache` (`Admin::AccountRecoveryCodes` on Your account, where the dialog opens by itself on connect and the mark carries the id `recovery-codes-no-cache`, so a second set's replaces the first's and the head holds one; the enrolment page and the wizard draw `frame: :page` with Done to where the person was going).

**The policy** (`Passkeys::Policy`, `SiteSetting#effective_passkey_policy`, `site_settings.passkey_policy`): `nobody`, `owners_and_admins` (the owners and whoever holds `users.manage`, `groups.manage` or `tokens.manage`, `ADMIN_PERMISSIONS`) or `everyone`; unset, `owners_and_admins` in production and `nobody` in development and test, so a site made before the policy needs no value and follows the default until an owner chooses. Only an owner sets it (`docs/reference/settings-languages-ai.md`, "The Sign-in card"). **It is read once per session, at sign-in**: `start_new_session_for` passes `Passkeys::Policy.current.enrolment_due?(user)` (covered and holding no passkey) to `Session.start`, so a policy changed later reaches a person at their next sign-in and an open session carries on as it was, a held one included until sign-out (`test/integration/passkey_enrolment_test.rb`: "a policy saved while a covered person is signed in leaves that session alone; their next sign-in is sent to enrolment"). `Passkeys::Policy.current` defaults its site to `Current.site || SiteSetting.instance`, since the console, jobs and model tests have no request's site.

**Enrolment.** `Admin::PasskeyEnrolment#require_passkey_enrolment`, a `before_action` of `Admin::BaseController` and `PreviewController`, holds a session marked `enrolment_due` (where the request has a relying party): a page (a GET or HEAD for HTML, no XHR) is redirected to `admin_enrolment_path` with its address kept as the return address; Turbo's own GET or a frame's gets the page Turbo may not draw, so it is loaded whole and meets the redirect; anything else is 403 with nothing done. It skips `Admin::EnrolmentsController` (the page, on the product layout, which asks for `content_for :entry_point, "admin"` so the layout loads CS Studio's entry point and its controllers), `Admin::PasskeysController#options` and `#create` (the add the page sends, `from: "enrolment"`; rename and remove stay held) and `Admin::ConfirmationsController` (the add asks for it once the sign-in is more than ten minutes old). Sign out is `Admin::SessionsController`, outside the base. Action Cable subscribes a held session to nothing (`ApplicationCable::Channel#subscriber` reads `enrolment_due: false`). Once the passkey is added the codes stand in place of the page, Done going where the person was going; a person who still held codes goes straight on (`test/integration/passkey_enrolment_test.rb`: "a covered person without a passkey is sent to enrolment from every CS Studio page and the preview, and Sign out still works", "a Turbo visit while enrolment is due is answered with a page Turbo loads whole"). **No guard** for a CS Studio door outside `Admin::BaseController` and `PreviewController` (a new controller on `ApplicationController`, Active Storage's direct uploads) that a held session reaches.

**The wizard's passkey step.** The setup wizard has ten steps (`SetupController::STEPS`: token, system check, admin, passkey, site, mail, languages, MCP token, starter content, review); `passkey` follows the admin step and is not gated by Confirm it's you, since the session was made by the password just set; that reason covers a first passkey alone, so an owner who holds one is sent on from the step and its options and PATCH answer 404 (`test/integration/setup_passkey_step_test.rb`: "an owner who holds a passkey gets no options and no add from the step"). It uses its own endpoints under `/setup` (`setup_passkey_options`, the step's PATCH through `admin--passkeys--register` with `method: "patch"` and no confirm outlet), adds through `Passkeys::Add`, and draws the codes in place of its body. While the policy covers the founding owner (production's default does) and they hold none, every later step, the MCP token's included, is sent back to it and there is no Skip; with `nobody` it is optional; a browser that cannot make passkeys is told so in words (open the wizard in one that can); at an IP address it says why and goes on. `Setup::RedirectConstraint` sends only a page load (a GET or HEAD asking for HTML, no prefetch, a document or a script's fetch) into the wizard while setup is pending, and answers any other request (a write, an icon, DevTools' file, a prefetch, a non-HTML client) with a bare 404 that loads no session: a redirect would load the session and write it back over what a parallel request had just kept (`test/integration/setup_redirect_test.rb`: "a write is answered 404, and loads no session", "an icon, DevTools' file and a prefetch are answered 404 and write no cookie"; `test/integration/setup_passkey_step_test.rb`).

**The console** is the way back for a person who lost every passkey and every code: `Users::UpdatePassword.call(user, …, remove_passkeys: true)` deletes the account's passkeys and codes in the password's transaction, records one `passkey.removed` (`{ "count", "recovery_codes_removed", "reason" => "console" }`, no actor) and ends every session as any password change does. Only the trusted nil actor may ask it: from anyone signed in, an owner included, it is refused whole as `denied("users.manage", user)`, since a second factor someone else could clear protects nothing; the user editor has no such action (`test/services/users/update_password_test.rb`: "remove_passkeys from the console removes passkeys and codes, ends every session and records one passkey.removed", "remove_passkeys from a signed-in actor is denied and changes nothing"). The command is in `docs/reference/hosting.md`, "The reset mail".

**The events** (`Audit::Sentence`), all but `passkey.renamed` Security events (`SECURITY_ACTIONS`), and in the audit log's Action filter under "Sign-in" with the sessions' (`Admin::AuditScreen::ToolbarComponent::GROUP_OF`):

| Action | Subject, actor | Metadata | Sentence |
|---|---|---|---|
| `passkey.added` | the passkey, its person | `{ "name" }` | "added the passkey “MacBook”" |
| `passkey.renamed` | the passkey, its person | `field_changes` name | "renamed the passkey “Old” to “New”" |
| `passkey.removed` | the passkey, its person; the console's: the user, no actor | `{ "name", "recovery_codes_removed" }`; the console's `{ "count", "recovery_codes_removed", "reason" => "console" }` | "removed the passkey “MacBook”"; "2 passkeys of “Bo” removed from the console" |
| `recovery_codes.generated` | the user, the person | `{ "count" => 10, "replaced" }` | "made new recovery codes" |
| `recovery_code.used` | the user, the person | `{ "left" }` | "signed in with a recovery code (9 left)" |
| `session.second_factor_failed` | the user, no actor (`NO_ACTOR`: the password before it signed nobody in) | `{ "method" }` | "Failed second sign-in step for “Bo”" |
| `session.confirmation_failed` | the user, the person | `{ "method" }` | "didn't confirm it was you before a sign-in change" |

`session.created` carries `{ "method" }` for a passkey or a code and reads "signed in with a passkey" or "signed in with a recovery code"; a password's reads "signed in". No event holds a code, a digest, a credential id, a key or a challenge (`test/models/audit/sentence_test.rb`).

**The spans** are `auth.passkey`, `auth.recovery_code`, `auth.second_factor`, `auth.confirmation` and `auth.account_mail`, with `auth.policy` on the request's span of a sign-in that started a session (`docs/reference/hosting.md`, "Telemetry"; `test/integration/passkey_telemetry_test.rb`).

## Presence, and the registry of record kinds

**Presence is one of the two feature writes that are not an `ApplicationService`** (the other is an edit reservation, below), beside the exceptions the Services section lists. `Presence::Channel` writes and deletes its own `presence_marks` rows through `Presence::Mark`, with no `authorize!` and no `record_event`: a presence is not content, nobody asks for it by name, and a row is ignored by every read after `Presence::STALE_AFTER` (150 seconds). It is never audited and never touches the record it is on, so it appears in no record's Activity; a presence write says `# version: none (presence is not content)` on its line for `test/lib/version_bump_test.rb`. What stands in for the service's `authorize!` is the read scope at each door: you may be on, and see who is on, what you may read (`docs/reference/presence.md`, "The exception to the service rule").

**An edit reservation is the other.** `Editing::Reservation`'s statements (claim, release, request, withdraw, hand over, pass over) write only their own `edit_reservations` row, each as one statement, with no `record_event`: a reservation is not content and is gone in two minutes. What stands in for `authorize!` is `Editing::Rights.missing(actor, record)` at each door, which asks **`AccessControl::OwnerRule`** (`app/models/access_control/owner_rule.rb`): the rule every write to a page's or post's content shares, `<owner>.edit` and, once the owner has a `published_at`, `<owner>.publish` too. The rule was `ContentBlocks::OwnerPermissions`' own; it moved to the model layer so the services (which still reach it through `OwnerPermissions#owner_refusal`) and the reservations ask the same rule, since a model may not reach up into the services. Taking a reservation over is a service, `Editing::TakeOver`, in `EXPECTED_SERVICES` like any other (`docs/reference/live-editing.md`; `test/models/editing/rights_test.rb`: "it agrees with what the save services refuse, for the fixtures' actors").

**`RecordKinds`** (`app/models/record_kinds.rb`) is where "which records can a feature attach to, and who may read each" is written down once: `page`, `post` and `media`, each with its read right, its moderate right and `scoped`. A scoped kind (pages, posts) finds a record through `AccessControl.scope`, so a record outside the user's grants is not found, never forbidden; an unscoped kind (the library image, whose single right `media.upload` opens every kept image) answers 403 to a user without that right, as `Admin::MediaController`'s gate does. `Kind#readable(user, channel:)` is the one relation, and `find` and `readable_ids` come from it. Notes (`Notes.readable_threads`, `Admin::NoteContainer`, `Notes::RecordChannel`) and presence (`Admin::RecordOfKind`, `Presence::Channel`) find their records through it, and `AccessControl.holds?` stays for navigation only. A subscription asks it at subscribe time for the user as they are then (`ApplicationCable::Channel#subscriber`); a right taken away later is not re-judged for a stream already open, which is harmless because a signal says nothing and every fetch it leads to is scoped.

## Rules a change can break silently

Moved word for word from `CLAUDE.md`, where "above" and "below" meant the list these rules stood in: a rule named that way may now be in another reference file. Each names the test that guards it; a rule or a part of one with no guard is also said in `CLAUDE.md`.

- Every content, settings, user, group and token write goes through an `ApplicationService` that calls `authorize!(` and `record_event(`, and a controller never writes a record itself (`test/services/service_contract_test.rb`, `test/services/service_behaviour_contract_test.rb`).
- A new `ApplicationService` needs its entry in `EXPECTED_SERVICES` and a factory in `test/support/service_calls.rb` (`test/services/service_behaviour_contract_test.rb`).
- The visitor (`AccessControl::VISITOR`, one instance) is allowed exactly `forms.submit` on `:public` and nothing else on any channel, `forms.submit` is no group's, token's or user's to be granted, only `FormSendsController` sets the visitor, and its event has no actor row and no IP (`test/models/access_control/visitor_test.rb`: "a visitor is allowed forms.submit on :public and nothing else: every registered key on every channel", "a user, an owner's token and a group can't be given forms.submit"; `test/lib/visitor_actor_test.rb`; `test/services/forms/submit_test.rb`: "the event is the form's, names the submission by id, holds no answer, no actor row, no IP, and its channel is public").
- An account that holds a passkey or an unused recovery code is never signed in by its password alone, a second proof counts in the account's (or the known device's) bucket before it checks anything, and the known-device cookie is written by a whole sign-in only (`Admin::SignInCompletion#complete_sign_in`), never after the password step (`test/integration/second_factor_test.rb`: "a right password for an account with a passkey goes to the second step and starts no session", "a right password then five wrong codes closes the account, mails its person, and no session or known-device cookie was ever written"; `test/models/sign_in/proof_test.rb`: "a proof's failures count in the account's bucket: the fifth wrong code closes it and the right code is then refused as locked").
- A passkey challenge lives in its own cookie per purpose, never the session, and is taken once on the server through `SignIn::SpentChallenge`'s one atomic insert, a failed statement or a lost connection refusing (`test/models/sign_in/spent_challenge_test.rb`: "of several spends of one digest at the same moment exactly one wins", "a database error is not rescued: it is no spend"; `test/integration/passkey_sign_in_test.rb`: "an assertion sent twice, one after five minutes and one made for another purpose's challenge are refused, and the second press works with a fresh challenge", "an error of the code's own while a challenge is spent is not taken for the database's").
- The audit log keeps a passkey's name (`passkey.added`'s and `passkey.removed`'s `{ "name" }`, `passkey.renamed`'s change, a passkey's label in a snapshot and the sentences: "added the passkey “MacBook”") and never its credential id, its public key, a challenge, an assertion or any recovery code. No span holds any of them, the name included, nor the email or the password: the `auth.*` spans write only the listed keys with listed words (`test/integration/passkey_telemetry_test.rb`: "no span or event holds the email, the password, the code typed, the credential id, the challenge or the passkey's name", which plants every one of them, a refused stranger's credential id among them, and searches the password step's request too; `test/models/audit/snapshot_test.rb`). A request's log line holds the passkey's name with its parameters, as any field typed, and none of the others: the email, the password, `credential` and `recovery_code` are filtered (`filter_parameters`), and a challenge is never a parameter. **No guard** reads the log for a passkey's material.
