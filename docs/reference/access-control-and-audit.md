# Auth, access control and the audit log

> Describes: `app/controllers/concerns/authentication.rb`, `app/models/access_control/`, `app/models/access_control.rb`, `app/models/audit.rb`, `app/models/audit/`, `app/services/application_service.rb`, `app/models/api_token.rb`.

## Auth

Custom session-based auth (`app/controllers/concerns/authentication.rb`), not Devise — `has_secure_password` on `User`, signed cookie holds a `Session` id, `Current.session`/`Current.user` per-request. `ApplicationController` requires authentication by default; `PagesController` (the public site) opts out with `allow_unauthenticated_access`. `ApiToken` is a separate token model (revocable, named — see `docs/reference/users-groups-tokens.md`): a token is 256 random bits, the row stores only `lookup_digest` (its SHA-256 hex, unique index) and `ApiToken.authenticate` is one indexed lookup on it, so no password hash is computed per request; the tokens issued before that change were revoked (their `lookup_digest` is the placeholder `revoked:<id>`), and `lookup_digest` is in `Audit::Snapshot::NEVER_STORED` and in `filter_parameters` for non-session API access, bound to one `AccessControl::Group` (`group_id`, not null) that bounds what it may do regardless of its user's own rights — see "Access control and audit" below for what being signed in or holding a token actually permits. Active Storage's own write endpoints (`POST /rails/active_storage/direct_uploads`, the Disk service's `PUT`) require a signed-in session too (`config/initializers/active_storage_access.rb`, 401 otherwise) — the app never uses direct uploads; every upload goes through a CS Studio controller.

## Permissions, groups and grants

`AccessControl::Permissions` (`app/models/access_control/permissions.rb`) is a registry like `ContentModel::Registry`/`RichText::Schema`: built-in keys are unprefixed (`posts.read/create/edit/publish/delete`, `pages.read/create/edit/publish/move/delete`, `tags.manage`, `media.upload`, `media.manage`, `settings.manage`, `languages.manage`, `users.manage`, `groups.manage`, `tokens.manage`, `system_status.view`, `audit.view`, `trash.empty`, `ai.translate` — see `AccessControl::BuiltIns`), plugin keys must be `owner/name`, and a duplicate raises `AccessControl::DuplicatePermission`; registration happens in `config/initializers/types.rb`'s `to_prepare`, alongside the block/content-type/rich-text registries, reset-then-register so a dev reload doesn't double-register. `AccessControl::Group`/`Membership`/`Grant` (tables `access_control_groups`, `access_control_memberships`, `access_control_grants`) carry the actual rights: a group's grants each name a permission key plus a jsonb `scope` limited to `content_types` (array), `page_ids` (array, matched via `page_hierarchies` so a branch grant covers descendants), and `own` (boolean, matched against `Post#author_id`) — a group holds at most one grant per permission (unique index on `group_id, permission`; `Groups::Save` refuses a request that lists one twice as an invalid request, not a denial), grants combine with OR across a user's groups, and every scope key set on one grant must match (AND) for that grant to apply. Four groups are built in, by name (`AccessControl::Seeds::BUILT_IN`). A new database is built by loading `db/schema.rb`, which holds no rows, so they are made by `Groups::EnsureBuiltIns`: from the top of `db/seeds.rb` in every environment (`db:prepare` and `db:setup` run it after the schema load; `bin/rails db:seed` by hand on a site set up before the service existed) and by the setup wizard before every step past the token (a database built with `db:schema:load` alone ran no seed). It makes only a group that is missing by name, with the grants below, records `group.created` for each, and never touches a group that exists, so an owner's change to a built-in group's grants survives a deploy; the `SeedAccessControlGroups` data migration's own `ensure_built_in_groups!`, which also adds a missing grant to an existing group, is for databases that were migrated across that change and is called by nothing else. The groups: Admin (every registered permission, unscoped), Editor, Author (`posts.edit` scoped `own: true` — note its `posts.read`/`posts.create` are unscoped by design, so a seeded Author can still read every post, not just their own), Read only. Library images have no scopes: `media.upload` uploads, browses and chooses them (pointing a hero or image block at one needs it plus an existing asset, `Media::Choosing`, while clearing needs only the edit right), `media.manage` (Admin and Editor, added to already-seeded groups by `GrantMediaManageToBuiltInGroups`) edits or deletes any of them, and an image's uploader (`created_by_id`) may edit or delete their own with `media.upload` alone (`Media::Ownership` — a token still needs its group to hold `media.upload`). `users.owner` is a separate boolean flag, not a group — an owner is allowed everything regardless of grants, the last owner can't be demoted or deleted (`User`'s own validation), and every user-changing service (`Users::Save`/`Destroy`/`UpdatePassword`, via the shared `Users::OwnerProtection` concern) refuses a non-owner touching an owner's account at all, and refuses managing any user whose groups aren't a subset of the actor's own assignable rights (`#outranked?`) — so `users.manage` is bounded by what you could already grant yourself, never a blanket "any admin may manage any user". A password change ends that user's sessions inside the transaction that writes it (`Users::OwnerProtection#end_sessions_after_password_change`, called by `Users::Save` and `Users::UpdatePassword`, never by a controller): all of them, except the acting session of a signed-in user changing their own; the reset flow keeps none. The same bound applies to groups: `AccessControl.can_manage_group?(actor, group)` ("may this actor manage this group as it stands" — every grant it holds is one they could hand out) gates removing members or grants (narrowing a grant counts), deleting a group, and changing a user's membership, in `Users::Save`, `Groups::Save` and `Groups::Destroy`. Only a `User` is ever an owner (`AccessControl.owner?`): an `ApiToken` — even an owner's — is judged on its effective rights (group ∩ user) by `can_grant?`/`can_assign_group?`/`can_manage_group?` and the owner-only rules. A content type that is no longer registered matches nothing, and that is enforced at the decision point, not left to the data: `AccessControl::Scoping::Condition`, the one matcher behind both `allowed?` and `scope`, reads a grant's `content_types` intersected with the registered ones (`Permissions.content_type_choices`), so a grant naming a gone type — alone or beside a live one — doesn't reach posts that still carry that type; only an unscoped grant and an owner reach those. `AccessControl::LiveGrants` reads a group's grants with the same reader for the editor. A grant *all* of whose content types are gone is dead: it matches nothing, is shown unticked in the group editor, and is dropped on the next save of that group's form — a removal that takes someone who could grant those types, so the row's note says so ("Limited to a content type that no longer exists (<name>). Saving removes it; until then only someone who could grant that type can manage this group.") and, for a viewer who may manage the group, Save is enabled with nothing touched (`save_bar_form_data(always:)`). A grant that still has a live type keeps the removed name beside it — a `LiveGrants::Entry` with `gone_types` — and the editor carries it (`#carried_attributes`) through every save until somebody presses Remove on it, so an untouched save changes nothing (see `docs/reference/users-groups-tokens.md` for the rule `Groups::Save` reads it by). Either way the name is dormant, not gone: it grants nothing while its type is unregistered, and comes back to life, with its old meaning, only if a content type of that name is registered again while the name is still stored. So whoever hands a group on is judged on its grants *as stored* (`LiveGrants#as_stored`: the carried names, and a dead grant that such a re-registration would revive; a deleted page id is left out, it can't come back): `can_assign_group?`, `can_manage_group?` and the added-member check in `Groups::Save` all refuse an actor whose own grant doesn't cover the dormant name, so a `{blog}` holder can't put a user or a token into a group storing `{blog, retired}` or `{retired}`, nor take a member out of it, nor delete it — and the group editor shows them that group view-only.

## The decision point

`AccessControl.allowed?(actor, key, record = nil, channel:)` (`app/models/access_control.rb`, delegating to `AccessControl::Checker`) is the one decision point: a subject key (`posts.*`/`pages.*`) requires `record` (nil raises `ArgumentError` — no scope-free allow by omission), an admin-area key ignores it; a `User` is allowed if any of their groups' grants match, an `ApiToken` only if a grant of the token's own group matches *and* its user is separately allowed — the intersection, so a token narrows but never widens its user's rights; a `nil` actor is allowed on the trusted channels `:setup`, `:console`, `:system` (and no channel at all) and denied on `:admin`/`:mcp`/`:public` (`PublicController` sets `:public`; nothing on the public site calls a service or access control today). The setup wizard creates the founding owner through `Users::Save` as that trusted nil actor on `:setup`, and every later step runs as the signed-in owner (`SetupController#act_as_signed_in_user`), so its events are attributed. `AccessControl.creatable_parents(actor, pages)` answers "under which of these pages may this actor create a page" (`pages.create` asked against a would-be child of each, branches preloaded in one query) for every parent picker — deliberately not `scope(actor, "pages.create", ...)`, which would never offer a branch grant's own root. `.holds?` is the same decision without a record, for nav/buttons only ("does this user hold `posts.edit` anywhere"), never to gate a write; with no record to match, any grant for the key counts except one whose scope names content types of which none is registered (`Scoping::Condition#dormant?`), so such a holder gets no Posts entry at all. `.scope(actor, key, relation, channel:)` (`AccessControl::Scoping`) narrows a `Post`/`Page`/`ContentBlock` relation to what's readable — used by every CS Studio list, the page tree, link-target/related-post/mind-graph search, `/preview`, and MCP's list/get tools — and `.tree_visibility`/`.preload_branches` exist purely for the page tree's cost profile: ancestors of a readable page are returned separately as `context_only` (greyed out, no actions, so a deep readable page still shows its path to the root), and `preload_branches` loads every listed page's closure-table ancestry in one query so per-row `allowed?` checks in a rendered list cost nothing extra. Everywhere a record could be looked up outside its scope — a CS Studio URL by id, an MCP `get_post`/`update_post`, a preview link — the answer is **not found, not forbidden**: a 404 or tool error, never a 403, so a locked-out record's existence isn't disclosed (one accepted trade-off: the related-posts editor discloses a *count* of hidden relations it can't show, "+N related posts you can't open", without naming them).

## Services

Every content, settings, user, group and token write funnels through `ApplicationService` (`app/services/application_service.rb`) — the exceptions are sessions (sign-in/out, audited directly as `session.*` by `Admin::SessionsController`, and `session.created` by `SetupController#update_admin` for the founding owner the wizard signs in), the `setup_completed_at` marker `Setup.complete!` sets, and derived rows (`public_paths`, closure-table rows) the models maintain themselves: `#authorize!(key, record)` calls `AccessControl.allowed?`; on refusal a service returns `denied(key, record, message: nil)`, which records one `access.denied` audit event (outside the service's own transaction — a rolled-back forged write still leaves exactly one, coalesced, denial) and answers with the fixed message `"You don't have permission to #{permission.label.downcase}"`. `#record_event(action, subject:, field_changes:, metadata:)` is the write side, called inside the transaction so a rollback leaves no trace. Two tests enforce that this isn't opt-in. `test/services/service_contract_test.rb` is the grep tripwire: it eager-loads every `ApplicationService` subclass and reads the source of the class's own body (not the file, so a second service in the same file is not exempted by the first; comment lines excluded) for both `authorize!(` and `record_event(`, failing loudly on a service that has neither thought about authorization nor about the log; each check has its own escape hatch, `# authorize: none (reason)` and `# audit: none (reason)`, matched inside the class body and naming a reason a reviewer can check. A source check is satisfied by a service that calls `authorize!(` and ignores the answer, so the proof is behaviour: `test/services/service_behaviour_contract_test.rb`, with `test/support/service_calls.rb` (a factory per service naming its `permission:` and the record it acts `on:`), never reads source: it calls every service as a user with no memberships on `:admin` (and, where MCP reaches the service, as that user's API token on `:mcp`) and asserts a refusal (not a validation failure or an exception), exactly one `access.denied` event attributed to that actor and channel, and an unchanged digest of every table but the audit log; a control run of the same call, allowed, in a rolled-back savepoint must answer ok and change something, so "changes nothing" cannot be true of a call that would have changed nothing anyway. The trusted nil actor is never used for the refusal run. Its `EXPECTED_SERVICES` list is exact (a new service is added there and given a factory), `SELF_SERVICE` names the services open to any signed-in user for their own record and `OWN_RESULT` the bulk services that answer with their own result because the single-record services they run authorize and audit. A service that says `# audit: none (reason)` names the reason in its factory too, as `control_unaudited: "<reason>"`, and its allowed control run must then record **no** event at all, where every other allowed call must record one: today `Notes::React`, `Notes::MarkRead` and `Notes::SetFollowing` (a reaction, a read mark and a follow are not changes to content). The twelve `Notes::` services are ordinary entries of the list: a note needs the read right of the record it is on (`pages.read`, `posts.read`, or `media.upload` for an image), moderation its edit right, and "only the author edits a note" is a refusal logged against the read key with its own sentence, not a `SELF_SERVICE` (`docs/reference/notes.md`, "Who may do what"). The branches of each rule (publish-only saves, scoped grants, escalation) belong to `test/services/authorization_matrix_test.rb`, and each service's own tests cover the rest. One interim rule worth knowing before touching autosave: **editing an already-published record needs `publish`, not just `edit`**, because CS Studio's autosave writes straight to the live record — this goes away once pending revisions (Phase 3 versioning) exist. The converse holds too: a save that changes *only* the publish state (`published`/`published_at`, nothing else) needs only `publish` (`Posts::Save`/`Pages::Save#publish_only?`), so a read + publish "Publishers" group works.

## The audit log

`Audit.record(action, subject:, field_changes:, snapshot:, metadata:, coalesce: true)` (`app/models/audit.rb`) is the single write path for the log (`Audit::Event`, table `audit_events`) — reading actor/channel/request id/IP off `Current` rather than taking them as arguments, so a caller can't forge them. `*.updated` and `access.denied` events coalesce (`Audit::Coalescer`): a burst within `Audit::COALESCE_WINDOW` (exactly 10 minutes, measured from the *previous* event's `last_occurred_at`, not `occurred_at`, so a continuous autosave session keeps extending one row for as long as it runs) merges into the open row instead of one row per keystroke pause; everything else stays discrete. A coalesced extension never writes `metadata` (it is outside the append-only allow-list), so an `*.updated` event whose point is its metadata is recorded with `coalesce: false` (`record_event` passes it on) and is a row of its own: a section's fold with its `folded_block_ids` (`ContentBlocks::Save`). A later event may still extend that row and leaves its metadata as written. Each event carries `field_changes` (old → new per field, named `field_changes` — never `changes`, which `ActiveRecord::Dirty` already owns) and a full `snapshot` of the subject after the change (`Audit::Snapshot`, the version basis Phase 3 versioning will build on). One kind of value is summarised in `field_changes` as a rich-text body is: a `:code` field of a type's schema (the Code block's source, and any block or post type's field of that type, one level into a field group) is `{ "settings code" => { "digest_before", "digest_after", "length_before", "length_after" } }` there (the column and the field in one key, only when the code changed; the column's other keys stay `"settings" => [old, new]` without the code), while the snapshot holds the source whole, as it holds a body, because it is the version basis. The source is a key of `settings`, a plain column, so before this a changes row held the settings' whole old and whole new hash beside the snapshot: three copies. What that costs is counted per typing session and not per save, because `*.updated` events coalesce into one row that each save rewrites: for a 20,000-character source about 60 KB a session and block then, about 20.5 KB now (the one copy in the snapshot; a post's snapshot already holds every language's whole body, with no cap). It is decided by the field's type in the record's definition (`Audit::Snapshot.typed_changes`), never by a type's name or a key called "code", so a record whose type is no longer registered is recorded as stored. The audit screen reads such a row as "Changed", as it reads a body's, and a burst folds into the first `…_before` and the last `…_after` (`Audit::Coalescer.merge`) (`test/models/audit/snapshot_test.rb`: "one save of a 20,000-character source writes small changes that hold none of it, and a snapshot that holds it once", "the digest of a code field differs when the source differs, and the other settings are recorded as before", "a block type without a code field is recorded exactly as before, a key called code included", "a post type's code field gets the same treatment in the changes, by its type, and so does one inside a field group", "a burst of saves folds into one event: the first digest and length before, the last after"). Both are scrubbed of secrets twice over (a `NEVER_STORED` list, then a pass through `Rails.application.config.filter_parameters`), so a password digest, token digest, or raw token can never land in the log even if a snapshot serializer dumped raw `attributes`. The table is append-only twice: `Audit::Event` itself refuses any update outside its coalescing columns (`field_changes`, `snapshot`, `last_occurred_at`, `occurrences`) and any destroy, and the Postgres trigger `db/triggers/audit_events_append_only.sql` refuses the same at the SQL level (covering `delete_all`/`update_all`/raw SQL too — deliberately not `TRUNCATE`, so `db:truncate_all` still works in development) — reapplied after every schema load, not just every migration, via `config/initializers/db_triggers.rb` hooking `ActiveRecord::Tasks::DatabaseTasks.load_schema`, since `db/schema.rb` itself can't carry a trigger and `db:schema:load`/`db:reset`/parallel test workers' own database copies all bypass migrations entirely. After the writing transaction commits, `Audit.record` publishes `ActiveSupport::Notifications.instrument("audit.content_spiel", event:)` — the plugin hook for anything that wants to react to audit events, never before commit, so a rolled-back write triggers nothing. Live editing is its first listener inside the app: `Editing::Signals.heard` maps an event's action to the signal an open editor fetches on (`config/initializers/editing.rb`; every action in `Audit::Sentence::ACTIONS` must be placed in `Editing::Signals::MAP` or `SILENT`, `docs/reference/live-editing.md`). `session.failed` has no user to name, so its `metadata` holds the email address that was tried (`email_address`, cut to 254 characters, and only when the value contains an `@`, so a password typed into the email box by mistake is not kept), never the password (`Admin::SessionsController#failed_sign_in_metadata`).

**Publishing events and the rule's reason.** `Publishing::PublishChanges`, `Publishing::DiscardChanges` and `Publishing::CancelScheduledChange` are `ApplicationService`s in `EXPECTED_SERVICES`, audited as `page|post.changes_published` (number, `live_at`, whether scheduled), `changes_discarded` (the number returned to and the withdrawn one) and `scheduled_change_cancelled`, on the content record, never coalesced, with `snapshot: nil`; `Audit::Sentence` tells them as "published changes to Pricing", "scheduled changes to Pricing for 12 Oct" (a publish with a time), "discarded the unpublished changes to Pricing" and "cancelled the scheduled changes to Pricing". Publishing needs `<owner>.publish`; a discard needs what editing the record needs (`AccessControl::OwnerRule`). That rule, `edit` and, once the owner has a `published_at`, `publish`, no longer means that a save is public (it is not: the site shows the published copy, `docs/reference/publishing.md`) but that the person who may change a published record is the person who may publish it (drafts spec D5), until preparing and approving are two rights; `OwnerRule`'s comment, `Translations::EditRight`'s and `Admin::EditorScreen::HeaderComponent#view_only_hint`'s say so (`test/models/audit/sentence_test.rb`; `test/services/service_behaviour_contract_test.rb`).

**Note events.** `note.started`, `note.replied`, `note.edited`, `note.deleted`, `note.resolved`, `note.reopened`, `note.pinned`, `note.unpinned` and `notes.removed` take the **content record** as their subject (the page, post, block or image the thread is on), so they appear in that record's Activity and are read-scoped like it; a refusal's `access.denied` names the container, the record whose right was missing. They are recorded with `snapshot: nil` and metadata that holds ids only (`thread_id`, `message_id`; `thread_ids` for a removal): a note's text, its quote and its files' names never reach `Audit.record`, because the log is append-only and would keep a deleted note's words for ever. `Audit::Sentence::NOTE_VERBS` words them, and `Dashboard::Feed::NOT_A_CHANGE` (`access.denied`, the three `…taken_over` actions and those keys) keeps them out of "Mine" and out of `Audit::ChangeSince`'s "Changed by": a note is not a change to the record. The same text is kept out of the request log by `config/initializers/filter_parameter_logging.rb`, which filters `body` and `quote` only for a request to a notes controller, because `Audit::Snapshot.scrub` drops every snapshot key that list matches and a bare `:body` would have taken a post's and a block's body out of their snapshots.

**Take-over events.** `page.taken_over`, `post.taken_over` and `block.taken_over` (`Editing::TakeOver`, the one audited write of live editing) are recorded when an edit reservation passes from the tab that held it to someone who asked for it. The subject is the content record (the page, the post or the block), `snapshot: nil`, never coalesced, and the metadata is two ids and a flag: `from_user_id`, `to_user_id`, `answered`. No name and no text. The actor is whoever called the service, so `Audit::Sentence` has two verbs for the one action (`#handed_over?`): "handed over editing" when the holder's tab answered (`answered: true`) and "took over editing" when the requester passed over a tab that did not (`answered: false`); for a block the sentence is "… editing a block on “Pricing”". The other person is in the metadata's ids, never in the sentence. They are in `Dashboard::Feed::NOT_A_CHANGE`: a take-over writes no content row, so "Mine", "Changed by" and the editors' "Updated by" skip it, and `Dashboard::Activity` does not list it. Claiming, renewing, releasing and withdrawing a reservation are not audited at all (`test/models/audit/sentence_test.rb`: "a take-over reads as having taken over editing, of a block on its page, of a page, of a post", "an answered take-over reads as the actor having handed editing over, an unanswered one as having taken it"; `test/components/admin/audit_screen/sentence_component_test.rb`: "an answered take-over reads handed over, an unanswered one took over, and neither names a second person").

**Invitation events.** `invitation.created`, `invitation.resent` and `invitation.withdrawn` (`Invitations::Invite`, `Resend`, `Withdraw`, `users.manage`) are on the `Invitation` (labelled by its address, its snapshot the address, name, inviter, dates, account and group ids; the audit log's Type filter lists "Invitation"); `Audit::Sentence` words them "invited <person>", "sent a new invite to <person>" and "withdrew the invite to <person>" (`OTHER_VERBS`). `invitation.accepted` (`Invitations::Accept`) is recorded on the USER that accepting creates, as its ACTOR and its subject at once, whoever else is signed in in that browser, since the invitation's token is the credential (the service says `# authorize: none` with that reason, and the service contract exempts it as `TOKEN_CREDENTIAL`); its sentence is "accepted the invite" (`SPECIAL_ACTIONS`), its changes the new account's fields and `group_ids`, its metadata the invitation's id. Nothing of the token is in any of them. All four are in `Editing::Signals::SILENT`. A bad token records nothing, as the reset's does: nobody was refused a permission. A withdrawal's event is written before the row is deleted. **Mail settings in the log**: a save of Settings → Mail is a `settings.updated` like any other; the login is "Mail login" "set"/"not set", never a value (`mail_username`, `mail_password` and `mail_verified_fingerprint` are in `Audit::Snapshot::NEVER_STORED`), and the state's columns (`mail_verified_at`, `mail_last_sent_at`, `mail_failed_at`, `mail_failure`, `mail_login_saved_at`) are in `IGNORED_CHANGES`: a send is not a change of the settings, and a test mail records no event (`docs/reference/mail.md`).

**Counted sentences.** `Audit::Sentence::COUNTED` (`block.created`, `block.updated`, `media.uploaded`) are the actions with a counted form, which `Dashboard::Activity` collapses a run into: `Audit::Sentence.build(…, count:, mixed:, at_least:)` tells "added 4 Code blocks to “…”", "edited 3 blocks on “…”" (`mixed` names no type) and "uploaded 12 images", the last with a `:collection` part (a counted set of records, linked to the library by `Audit::Sentence.library_route` and never quoted). A count above 1 for any other action, or with no target, raises; `at_least:` ("60 or more") is for a run the dashboard's read cut off. Only the dashboard passes a count: the audit log tells every event on its own and does not collapse.

**What "Changed by" counts for a page.** `Audit::ChangeSince` names who made a refused save stale. For a post it counts the post's own events and those of the blocks it owns. For a page it counts the page's own events only: the page settings form's base is `pages.settings_changed_at`, which a block's save does not move, so only an event about the page itself can have made it stale (`test/queries/audit/change_since_test.rb`: "a block saved after a page's settings change is not named as the cause of a refused settings save").

## Presence, and the registry of record kinds

**Presence is one of the two feature writes that are not an `ApplicationService`** (the other is an edit reservation, below), beside the exceptions the Services section lists. `Presence::Channel` writes and deletes its own `presence_marks` rows through `Presence::Mark`, with no `authorize!` and no `record_event`: a presence is not content, nobody asks for it by name, and a row is ignored by every read after `Presence::STALE_AFTER` (150 seconds). It is never audited and never touches the record it is on, so it appears in no record's Activity; a presence write says `# version: none (presence is not content)` on its line for `test/lib/version_bump_test.rb`. What stands in for the service's `authorize!` is the read scope at each door: you may be on, and see who is on, what you may read (`docs/reference/presence.md`, "The exception to the service rule").

**An edit reservation is the other.** `Editing::Reservation`'s statements (claim, release, request, withdraw, hand over, pass over) write only their own `edit_reservations` row, each as one statement, with no `record_event`: a reservation is not content and is gone in two minutes. What stands in for `authorize!` is `Editing::Rights.missing(actor, record)` at each door, which asks **`AccessControl::OwnerRule`** (`app/models/access_control/owner_rule.rb`): the rule every write to a page's or post's content shares, `<owner>.edit` and, once the owner has a `published_at`, `<owner>.publish` too. The rule was `ContentBlocks::OwnerPermissions`' own; it moved to the model layer so the services (which still reach it through `OwnerPermissions#owner_refusal`) and the reservations ask the same rule, since a model may not reach up into the services. Taking a reservation over is a service, `Editing::TakeOver`, in `EXPECTED_SERVICES` like any other (`docs/reference/live-editing.md`; `test/models/editing/rights_test.rb`: "it agrees with what the save services refuse, for the fixtures' actors").

**`RecordKinds`** (`app/models/record_kinds.rb`) is where "which records can a feature attach to, and who may read each" is written down once: `page`, `post` and `media`, each with its read right, its moderate right and `scoped`. A scoped kind (pages, posts) finds a record through `AccessControl.scope`, so a record outside the user's grants is not found, never forbidden; an unscoped kind (the library image, whose single right `media.upload` opens every kept image) answers 403 to a user without that right, as `Admin::MediaController`'s gate does. `Kind#readable(user, channel:)` is the one relation, and `find` and `readable_ids` come from it. Notes (`Notes.readable_threads`, `Admin::NoteContainer`, `Notes::RecordChannel`) and presence (`Admin::RecordOfKind`, `Presence::Channel`) find their records through it, and `AccessControl.holds?` stays for navigation only. A subscription asks it at subscribe time for the user as they are then (`ApplicationCable::Channel#subscriber`); a right taken away later is not re-judged for a stream already open, which is harmless because a signal says nothing and every fetch it leads to is scoped.
