# Auth, access control and the audit log

> Describes: `app/controllers/concerns/authentication.rb`, `app/models/access_control/`, `app/models/access_control.rb`, `app/models/audit.rb`, `app/models/audit/`, `app/services/application_service.rb`, `app/models/api_token.rb`.

## Auth

Custom session-based auth (`app/controllers/concerns/authentication.rb`), not Devise — `has_secure_password` on `User`, signed cookie holds a `Session` id, `Current.session`/`Current.user` per-request. `ApplicationController` requires authentication by default; `PagesController` (the public site) opts out with `allow_unauthenticated_access`. `ApiToken` is a separate token model (revocable, named — see `docs/reference/users-groups-tokens.md`): a token is 256 random bits, the row stores only `lookup_digest` (its SHA-256 hex, unique index) and `ApiToken.authenticate` is one indexed lookup on it, so no password hash is computed per request; the tokens issued before that change were revoked (their `lookup_digest` is the placeholder `revoked:<id>`), and `lookup_digest` is in `Audit::Snapshot::NEVER_STORED` and in `filter_parameters` for non-session API access, bound to one `AccessControl::Group` (`group_id`, not null) that bounds what it may do regardless of its user's own rights — see "Access control and audit" below for what being signed in or holding a token actually permits. Active Storage's own write endpoints (`POST /rails/active_storage/direct_uploads`, the Disk service's `PUT`) require a signed-in session too (`config/initializers/active_storage_access.rb`, 401 otherwise) — the app never uses direct uploads; every upload goes through a CS Studio controller.

## Permissions, groups and grants

`AccessControl::Permissions` (`app/models/access_control/permissions.rb`) is a registry like `ContentModel::Registry`/`RichText::Schema`: built-in keys are unprefixed (`posts.read/create/edit/publish/delete`, `pages.read/create/edit/publish/move/delete`, `tags.manage`, `media.upload`, `media.manage`, `settings.manage`, `languages.manage`, `users.manage`, `groups.manage`, `tokens.manage`, `system_status.view`, `audit.view`, `trash.empty`, `ai.translate` — see `AccessControl::BuiltIns`), plugin keys must be `owner/name`, and a duplicate raises `AccessControl::DuplicatePermission`; registration happens in `config/initializers/types.rb`'s `to_prepare`, alongside the block/content-type/rich-text registries, reset-then-register so a dev reload doesn't double-register. `AccessControl::Group`/`Membership`/`Grant` (tables `access_control_groups`, `access_control_memberships`, `access_control_grants`) carry the actual rights: a group's grants each name a permission key plus a jsonb `scope` limited to `content_types` (array), `page_ids` (array, matched via `page_hierarchies` so a branch grant covers descendants), and `own` (boolean, matched against `Post#author_id`) — a group holds at most one grant per permission (unique index on `group_id, permission`; `Groups::Save` refuses a request that lists one twice as an invalid request, not a denial), grants combine with OR across a user's groups, and every scope key set on one grant must match (AND) for that grant to apply. Four groups are seeded by name (`AccessControl::Seeds::BUILT_IN`, applied by the `SeedAccessControlGroups` data migration and by `db/seeds.rb`'s `ensure_built_in_groups!`): Admin (every registered permission, unscoped), Editor, Author (`posts.edit` scoped `own: true` — note its `posts.read`/`posts.create` are unscoped by design, so a seeded Author can still read every post, not just their own), Read only. Library images have no scopes: `media.upload` uploads, browses and chooses them (pointing a hero or image block at one needs it plus an existing asset, `Media::Choosing`, while clearing needs only the edit right), `media.manage` (Admin and Editor, added to already-seeded groups by `GrantMediaManageToBuiltInGroups`) edits or deletes any of them, and an image's uploader (`created_by_id`) may edit or delete their own with `media.upload` alone (`Media::Ownership` — a token still needs its group to hold `media.upload`). `users.owner` is a separate boolean flag, not a group — an owner is allowed everything regardless of grants, the last owner can't be demoted or deleted (`User`'s own validation), and every user-changing service (`Users::Save`/`Destroy`/`UpdatePassword`, via the shared `Users::OwnerProtection` concern) refuses a non-owner touching an owner's account at all, and refuses managing any user whose groups aren't a subset of the actor's own assignable rights (`#outranked?`) — so `users.manage` is bounded by what you could already grant yourself, never a blanket "any admin may manage any user". A password change ends that user's sessions inside the transaction that writes it (`Users::OwnerProtection#end_sessions_after_password_change`, called by `Users::Save` and `Users::UpdatePassword`, never by a controller): all of them, except the acting session of a signed-in user changing their own; the reset flow keeps none. The same bound applies to groups: `AccessControl.can_manage_group?(actor, group)` ("may this actor manage this group as it stands" — every grant it holds is one they could hand out) gates removing members or grants (narrowing a grant counts), deleting a group, and changing a user's membership, in `Users::Save`, `Groups::Save` and `Groups::Destroy`. Only a `User` is ever an owner (`AccessControl.owner?`): an `ApiToken` — even an owner's — is judged on its effective rights (group ∩ user) by `can_grant?`/`can_assign_group?`/`can_manage_group?` and the owner-only rules. A content type that is no longer registered matches nothing, and that is enforced at the decision point, not left to the data: `AccessControl::Scoping::Condition`, the one matcher behind both `allowed?` and `scope`, reads a grant's `content_types` intersected with the registered ones (`Permissions.content_type_choices`), so a grant naming a gone type — alone or beside a live one — doesn't reach posts that still carry that type; only an unscoped grant and an owner reach those. `AccessControl::LiveGrants` reads a group's grants with the same reader for the editor. A grant *all* of whose content types are gone is dead: it matches nothing, is shown unticked in the group editor, and is dropped on the next save of that group's form — a removal that takes someone who could grant those types, so the row's note says so ("Limited to a content type that no longer exists (<name>). Saving removes it; until then only someone who could grant that type can manage this group.") and, for a viewer who may manage the group, Save is enabled with nothing touched (`save_bar_form_data(always:)`). A grant that still has a live type keeps the removed name beside it — a `LiveGrants::Entry` with `gone_types` — and the editor carries it (`#carried_attributes`) through every save until somebody presses Remove on it, so an untouched save changes nothing (see `docs/reference/users-groups-tokens.md` for the rule `Groups::Save` reads it by). Either way the name is dormant, not gone: it grants nothing while its type is unregistered, and comes back to life, with its old meaning, only if a content type of that name is registered again while the name is still stored. So whoever hands a group on is judged on its grants *as stored* (`LiveGrants#as_stored`: the carried names, and a dead grant that such a re-registration would revive; a deleted page id is left out, it can't come back): `can_assign_group?`, `can_manage_group?` and the added-member check in `Groups::Save` all refuse an actor whose own grant doesn't cover the dormant name, so a `{blog}` holder can't put a user or a token into a group storing `{blog, retired}` or `{retired}`, nor take a member out of it, nor delete it — and the group editor shows them that group view-only.

## The decision point

`AccessControl.allowed?(actor, key, record = nil, channel:)` (`app/models/access_control.rb`, delegating to `AccessControl::Checker`) is the one decision point: a subject key (`posts.*`/`pages.*`) requires `record` (nil raises `ArgumentError` — no scope-free allow by omission), an admin-area key ignores it; a `User` is allowed if any of their groups' grants match, an `ApiToken` only if a grant of the token's own group matches *and* its user is separately allowed — the intersection, so a token narrows but never widens its user's rights; a `nil` actor is allowed on the trusted channels `:setup`, `:console`, `:system` (and no channel at all) and denied on `:admin`/`:mcp`/`:public` (`PublicController` sets `:public`; nothing on the public site calls a service or access control today). The setup wizard creates the founding owner through `Users::Save` as that trusted nil actor on `:setup`, and every later step runs as the signed-in owner (`SetupController#act_as_signed_in_user`), so its events are attributed. `AccessControl.creatable_parents(actor, pages)` answers "under which of these pages may this actor create a page" (`pages.create` asked against a would-be child of each, branches preloaded in one query) for every parent picker — deliberately not `scope(actor, "pages.create", ...)`, which would never offer a branch grant's own root. `.holds?` is the same decision without a record, for nav/buttons only ("does this user hold `posts.edit` anywhere"), never to gate a write; with no record to match, any grant for the key counts except one whose scope names content types of which none is registered (`Scoping::Condition#dormant?`), so such a holder gets no Posts entry at all. `.scope(actor, key, relation, channel:)` (`AccessControl::Scoping`) narrows a `Post`/`Page`/`ContentBlock` relation to what's readable — used by every CS Studio list, the page tree, link-target/related-post/mind-graph search, `/preview`, and MCP's list/get tools — and `.tree_visibility`/`.preload_branches` exist purely for the page tree's cost profile: ancestors of a readable page are returned separately as `context_only` (greyed out, no actions, so a deep readable page still shows its path to the root), and `preload_branches` loads every listed page's closure-table ancestry in one query so per-row `allowed?` checks in a rendered list cost nothing extra. Everywhere a record could be looked up outside its scope — a CS Studio URL by id, an MCP `get_post`/`update_post`, a preview link — the answer is **not found, not forbidden**: a 404 or tool error, never a 403, so a locked-out record's existence isn't disclosed (one accepted trade-off: the related-posts editor discloses a *count* of hidden relations it can't show, "+N related posts you can't open", without naming them).

## Services

Every content, settings, user, group and token write funnels through `ApplicationService` (`app/services/application_service.rb`) — the exceptions are sessions (sign-in/out, audited directly as `session.*` by `Admin::SessionsController`, and `session.created` by `SetupController#update_admin` for the founding owner the wizard signs in), the `setup_completed_at` marker `Setup.complete!` sets, and derived rows (`public_paths`, closure-table rows) the models maintain themselves: `#authorize!(key, record)` calls `AccessControl.allowed?`; on refusal a service returns `denied(key, record, message: nil)`, which records one `access.denied` audit event (outside the service's own transaction — a rolled-back forged write still leaves exactly one, coalesced, denial) and answers with the fixed message `"You don't have permission to #{permission.label.downcase}"`. `#record_event(action, subject:, field_changes:, metadata:)` is the write side, called inside the transaction so a rollback leaves no trace. Two tests enforce that this isn't opt-in. `test/services/service_contract_test.rb` is the grep tripwire: it eager-loads every `ApplicationService` subclass and reads the source of the class's own body (not the file, so a second service in the same file is not exempted by the first; comment lines excluded) for both `authorize!(` and `record_event(`, failing loudly on a service that has neither thought about authorization nor about the log; each check has its own escape hatch, `# authorize: none (reason)` and `# audit: none (reason)`, matched inside the class body and naming a reason a reviewer can check. A source check is satisfied by a service that calls `authorize!(` and ignores the answer, so the proof is behaviour: `test/services/service_behaviour_contract_test.rb`, with `test/support/service_calls.rb` (a factory per service naming its `permission:` and the record it acts `on:`), never reads source: it calls every service as a user with no memberships on `:admin` (and, where MCP reaches the service, as that user's API token on `:mcp`) and asserts a refusal (not a validation failure or an exception), exactly one `access.denied` event attributed to that actor and channel, and an unchanged digest of every table but the audit log; a control run of the same call, allowed, in a rolled-back savepoint must answer ok and change something, so "changes nothing" cannot be true of a call that would have changed nothing anyway. The trusted nil actor is never used for the refusal run. Its `EXPECTED_SERVICES` list is exact (a new service is added there and given a factory), `SELF_SERVICE` names the services open to any signed-in user for their own record and `OWN_RESULT` the bulk services that answer with their own result because the single-record services they run authorize and audit. The branches of each rule (publish-only saves, scoped grants, escalation) belong to `test/services/authorization_matrix_test.rb`, and each service's own tests cover the rest. One interim rule worth knowing before touching autosave: **editing an already-published record needs `publish`, not just `edit`**, because CS Studio's autosave writes straight to the live record — this goes away once pending revisions (Phase 3 versioning) exist. The converse holds too: a save that changes *only* the publish state (`published`/`published_at`, nothing else) needs only `publish` (`Posts::Save`/`Pages::Save#publish_only?`), so a read + publish "Publishers" group works.

## The audit log

`Audit.record(action, subject:, field_changes:, snapshot:, metadata:, coalesce: true)` (`app/models/audit.rb`) is the single write path for the log (`Audit::Event`, table `audit_events`) — reading actor/channel/request id/IP off `Current` rather than taking them as arguments, so a caller can't forge them. `*.updated` and `access.denied` events coalesce (`Audit::Coalescer`): a burst within `Audit::COALESCE_WINDOW` (exactly 10 minutes, measured from the *previous* event's `last_occurred_at`, not `occurred_at`, so a continuous autosave session keeps extending one row for as long as it runs) merges into the open row instead of one row per keystroke pause; everything else stays discrete. A coalesced extension never writes `metadata` (it is outside the append-only allow-list), so an `*.updated` event whose point is its metadata is recorded with `coalesce: false` (`record_event` passes it on) and is a row of its own: a section's fold with its `folded_block_ids` (`ContentBlocks::Save`). A later event may still extend that row and leaves its metadata as written. Each event carries `field_changes` (old → new per field, named `field_changes` — never `changes`, which `ActiveRecord::Dirty` already owns) and a full `snapshot` of the subject after the change (`Audit::Snapshot`, the version basis Phase 3 versioning will build on) — both scrubbed of secrets twice over (a `NEVER_STORED` list, then a pass through `Rails.application.config.filter_parameters`), so a password digest, token digest, or raw token can never land in the log even if a snapshot serializer dumped raw `attributes`. The table is append-only twice: `Audit::Event` itself refuses any update outside its coalescing columns (`field_changes`, `snapshot`, `last_occurred_at`, `occurrences`) and any destroy, and the Postgres trigger `db/triggers/audit_events_append_only.sql` refuses the same at the SQL level (covering `delete_all`/`update_all`/raw SQL too — deliberately not `TRUNCATE`, so `db:truncate_all` still works in development) — reapplied after every schema load, not just every migration, via `config/initializers/db_triggers.rb` hooking `ActiveRecord::Tasks::DatabaseTasks.load_schema`, since `db/schema.rb` itself can't carry a trigger and `db:schema:load`/`db:reset`/parallel test workers' own database copies all bypass migrations entirely. After the writing transaction commits, `Audit.record` publishes `ActiveSupport::Notifications.instrument("audit.content_spiel", event:)` — the plugin hook for anything that wants to react to audit events, never before commit, so a rolled-back write triggers nothing.
