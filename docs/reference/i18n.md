# CS Studio's i18n key scheme

Every string a person reads in CS Studio comes from a locale file, never from
the source. This is the scheme, and the shared components and the admin layout are
converted to it (`test/lib/admin_i18n_test.rb` lists the files that are). The
German UI sub-project converts the other screens; new admin work uses keys from
the start.

## Files

```
config/locales/en.yml                  Rails' own (validation messages) and the named date/time formats
config/locales/admin/components.en.yml the shared components, and the layout (`admin.layout`)
config/locales/admin/<screen>.en.yml   one file per screen (`tags.en.yml`), all under the top-level key `admin`
```

Rails loads `config/locales/**/*.yml`, so a new file is picked up. A second
language is `components.de.yml` beside it, with the same keys.

A value with a leading or trailing space, a `%{...}`, a `:` or a glyph that
could open a YAML token is double-quoted; check what loads with `I18n.t` in a
test rather than trusting the file (`"NOT SAVED · "` keeps its trailing space).

## The rules

**A view's keys mirror its path.** `t(".title")` in
`app/views/admin/tags/index.html.erb` reads `admin.tags.index.title` (Rails'
lazy lookup). The admin layout is the exception to this: lazy lookup in
`layouts/admin.html.erb` would read `layouts.admin.*`, outside the `admin` tree, so the
layout writes its keys in full under `admin.layout`:

```erb
<%= render Admin::DialogComponent.new(id: "leave-dialog", title: t("admin.layout.leave_dialog.title")) %>
```

**A component's keys live under `admin.components.<its scope>`.** The scope is the
class name without `Admin::` and `Component`, underscored, one segment per
namespace: `Admin::ConfirmDialogComponent` is `confirm_dialog`,
`Admin::EditorScreen::HeaderComponent` is `editor_screen.header`. A component
writes `t(".cancel")` and `Admin::AdminComponent#translate` reads
`admin.components.confirm_dialog.cancel`; any key that does not start with a dot
is passed on untouched (ViewComponent's own lookup would have read
`admin.confirm_dialog_component.cancel`). `_html` keys, `count` and
interpolation behave as in a view, and a missing key raises in the test
environment (`config.i18n.raise_on_missing_translations`).

```ruby
# app/components/admin/confirm_dialog_component.rb
def cancel_label = @cancel_label || t(".cancel")   # admin.components.confirm_dialog.cancel
```

A default argument cannot ask `t`: nothing is rendering when `initialize` runs
(`TranslateCalledBeforeRenderError`). Take `nil` and fall back in a method, as
above. A string the *caller* passes into a component (a button's label, an empty
state's title, a menu's label) belongs to the calling screen, never to the
component.

A component that is not under `Admin::AdminComponent` has no `t(".key")`; its
base class is changed when its screen is converted.

**A string a script shows comes from the server.** The element a controller lives
on (or `<body>`, for what every screen's scripts share) carries
`data-messages`, made by `messages_data(scope, *keys)`; the script reads it
through `i18n/messages.js`. There is no English in a `.js` file.

```erb
<%# app/components/admin/chip_input_component.html.erb %>
data-messages="<%= messages %>"   <%# messages_data("admin.components", "chip_input.remove", "chip_input.results", ...) %>
```
```js
// app/javascript/controllers/admin/chip_input_controller.js
this.announce(messages(this.element).t("chip_input.added", { label: item.label }))
```

`messages(element)` reads the nearest `data-messages` at or above the element,
else `<body>`'s (`Admin::MessagesHelper::SCRIPT_MESSAGES`: the autosave status
line, the save footer, the leave dialog, the toasts a failed drop raises). A
missing key, a plural asked for without a `count` and a placeholder without a
value all throw, so a test fails on a `JsErrorCollector` error instead of showing
"undefined". Insert the result with `textContent` or an attribute, never `innerHTML`.
`messages_data` looks keys up with `raise: true`, so a missing key fails at render.

**One key, server and script.** A text the server renders and a script also writes
is one key: the autosave status line is `admin.components.save_status.*`, rendered
by `Admin::SaveStatusComponent` and written by `autosave_controller.js` from the
same keys.

**Counts use pluralisation, never a hand-built "1 post / 2 posts".**

```yaml
save_bar:
  changes:
    one: "%{count} unsaved change"
    other: "%{count} unsaved changes"
```
```ruby
t(".error", count: count)                                   # server
```
```js
messages(this.element).t("components.save_bar.changes", { count })   // script
```

In the script the category is chosen by `Intl.PluralRules` for the `@locale` the
server sends in the payload, so a language that needs `few`/`many` defines them in
its file and no script changes. English is `one` for 1, `other` otherwise, as in
Rails. (A Rails rule that is not CLDR's, or a count that a language treats
specially like `zero`, would need the server to send the category; none exists
today.)

**A string with a name or number in it is one key with interpolation**, never a
sentence glued from parts, so a translator can reorder it:

```yaml
translation_chip:
  aria_label:
    missing: "%{language}: not translated"
```
```ruby
t(".aria_label.#{@state}", language: ::Locales.name(@locale, native: true))
```

**Flash and toast texts set in a controller use the same files**, under a key
named for what the screen says, with the absolute key (a controller has no view
path to resolve a dot from): `Admin::TagsController#merge` writes
`flash[:notice] = t("admin.tags.toasts.merged", source: source.name, into: into.name)`,
which reads `admin.tags.toasts.merged` in `config/locales/admin/tags.en.yml`, and
`toast_stream(t("admin.tags.toasts.deleted", name: tag.name))` answers a delete. A
service's own refusals are looked up the same way with `I18n.t` (a service may
call `I18n`, never a helper or component): `Tags::Merge`'s three messages are
`admin.tags.merge.*`, still reachable as the constants `Tags::Merge::GONE` and
friends, which `const_missing` resolves at each reference so a later locale
switch applies. A missing key raises like every other lookup.

A helper that chooses between whole sentences (`Admin::TagsHelper`) does the same
with absolute keys, one pluralised key per shape of the sentence.

**A date or a time goes through `I18n.l` with a named format**, defined in
`config/locales/en.yml` under `date.formats.admin` / `time.formats.admin` (`short`
`"%-d %b"`, `short_with_year`, `time` `"%H:%M"`, `datetime`, `short_datetime`):

```ruby
I18n.l(at, format: :"admin.datetime")   # "5 Sep 2026, 09:07" (Admin::StatusChipComponent#title)
```

Relative times ("just now", "5m ago") are keys with `count` and interpolation
(`admin.components.time_ago.*`).

## The guard

`test/lib/admin_i18n_test.rb` holds `CONVERTED`, the files that must hold no English.
A listed file that does not exist fails. Its rules are written at the top of the test
and pinned against small positive and negative samples: ERB text nodes and the
`aria-label`, `title`, `placeholder`, `alt` and button `value` attributes; Ruby
string literals that read as copy (a capitalised word, a word in capitals, a
sentence); JavaScript literals that read as a sentence. Add a file to the list as you
convert it. A literal that is not copy but looks like it ends its line with
`# i18n-ok: <reason>`.

## Out of scope, named

- **Sentences built in Ruby.** `Audit::Sentence`, `Post.human_attribute_name` /
  `ContentBlock.human_attribute_name` (the typed-field names) and the denial message in
  `ApplicationService` stay English. When they are converted each becomes one key
  per whole sentence with interpolation; none is glued from parts. Also still glued
  in the shared layer: `Admin::ErrorSummaryComponent#sentence_for` (a field name and a
  model's message), and the Translations matrix's cell label.
- **How CS Studio chooses its own UI language.** Nothing sets `I18n.locale` for the admin
  today (only the public site does); it runs in the default `:en`. The editing
  language (`?locale=`, `admin_locale`) is the content's, not the interface's, and the
  layout's `<html lang>` carries it. The German UI sub-project decides how the
  interface language is picked; `messages_data` already sends `I18n.locale` as
  `@locale`, so the scripts follow whatever it decides.
