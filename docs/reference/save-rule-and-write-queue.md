# The save rule, the leave guard, stale autosaves and the write queue

> Describes: `app/javascript/saving/`, `app/javascript/controllers/admin/saving/` (the autosave controller, the save bar, the pending lock, the queue hold), `app/components/admin/ui/save_bar_component.rb`, `app/controllers/concerns/admin/` (autosave responses, stale form).

## The save rule

**The save rule.** Content autosaves (`admin--saving--autosave`, the status line "SAVED 10:42", or "SAVED TO SITE 10:42" for a live record, whose edits go straight to the site): the page and post editors, block cards, the Media panel, a tag's name. Configuration is saved explicitly — Settings (every card of it, Languages included), Groups, Users, Your account — through `Admin::Ui::SaveBarComponent` with `admin--saving--save-bar`: a form footer that is always visible, in the form's own column under the fields and sticky at the bottom of the window ("Save · Cancel · N unsaved changes"; Save is disabled, and the footer reads "No unsaved changes", while an existing record has nothing to save; `Admin::SaveBarHelper#save_bar_form_data(dirty:, always:, after:)` — `dirty` re-renders with the typed invalid values still counted, `always` keeps Save enabled from the start for a new record, and `after` names another form whose unsaved changes lock this one's Save, with "Save or cancel your changes first." and an Enter submit refused: the account screen's password form waits for the profile form, the name and the Notes switches, that way). Something typed *beside* a form that its Save would drop locks Save the same way: the element holding it carries `data-save-bar-holds="<sentence>"` while it does (Settings' API key entry, "Save or cancel the API key first."). A successful submit whose answer keeps the form on screen (a Turbo Stream) makes what was sent the new baseline. A successful save stays on the screen it was made on with a toast: Settings 303s to itself ("Settings saved"), a group and a user to their own editor ("Group saved", "User saved"; a new user to the new user's editor, "User created"); only a delete leaves for the list. Single actions (publish, trash, restore, revoke, a language added, turned off or made the default, the AI key, an owner change) are instant, behind a confirm dialog where they destroy or re-point something. Drag has a keyboard path (Space, arrows, Space; a tile in a section's lane is the exception — its grip is for the pointer only and its ⋯ menu holds every move a drag makes) and its own styling (`.admin-drag-ghost`, `.admin-drag-chosen`, `.admin-drag-fallback`); the Sortables run with `forceFallback` (SortableJS's own pointer-driven drag, a clone on `<body>`), because the handles are `<button>`s and Firefox can't start a native drag from one.

## How the footer counts

**How the footer counts.** `admin--saving--save-bar` compares what the form would *submit* now against a snapshot taken on connect (a disabled control and an unticked box are absent), so it doesn't depend on the order nested controllers connect in, and a value typed back is no change. One key per control: a radio group is one key, a checkbox is `name=value` while ticked, a tracked hidden input whose name ends in `[]` is `name=value` too, present while it holds a value — the members of a *set* (a chip input's chips, the scope editor's carried content types), where order means nothing, so removing the first of ten chips is one change and a chip removed and added back is none (the blank sentinel ahead of the chips is no member) — and anything else is its name plus its *position* among the controls of that name (`name#0`, `name#1`, …), so the rows of a list that share one name (`site_setting[languages][][fallback]`, one select per language row) count separately. A control marked `data-save-bar-ignore` is not counted at all (the account screen's current password: nothing to save by itself, and what a password manager fills in on load). A hidden input is ignored unless it carries `data-save-bar-track` — the real control behind a widget (a member chip, the language order, a removed content type's carrier), whose script dispatches a bubbling `input` or `change` on it when it sets the value; `Admin::Ui::ChipInputComponent`'s `track:` marks its inputs that way. For every key but a checkbox's, an absent key and an empty string are the same value, so a blank row added to a list is not yet a change. The count is announced for the whole page as `admin--saving--save-bar:state` on `document` (`detail: { unsaved, count }`; a late listener asks with `admin--saving--save-bar:query`), and `admin--saving--pending-lock` is its listener: while anything is unsaved it disables its `control` targets (a link gets `aria-disabled` and its click swallowed) and shows its `hint`, "Save or cancel your changes first." — the instant actions beside a form answer by reloading the screen, which would throw the pending changes away. A *named* control of the explicit-save form itself is never locked (disabled, it would drop out of what the form submits and count as a change that keeps the lock on), so an instant action's fields belong to a form of their own through `form=`.

## The leave guard

**The leave guard** ("Leave without saving?" · "You have N unsaved changes on this screen." · **Keep editing**, which has the focus, / **Discard changes**; the `leave-dialog` in the layout) is page-level, one prompt however many forms a screen has, and covers four ways out: a Turbo visit (`turbo:before-visit`); a *link* that navigates the `#content` frame, stopped at `turbo:click` before Turbo has started anything; Back and Forward within the document (a `popstate` listener put ahead of Turbo's own, the traversal undone with `history.go`); and a page unload (`beforeunload`, the browser's own prompt — which is also all that Back to an entry from before a full page load gets). It does **not** cover a GET *form* submitted into `#content` or a script setting the frame's `src`: no explicit-save screen has either, and one that adds a filter form beside its save form must revisit this first. The footer's Cancel never asks; a same-page `#fragment` link is no way out at all (`admin--shell--fragment-links`, see `docs/reference/design-system.md`: the focus moves by hand, no history entry, and the guard stands back from it); the visit a `#content` frame navigation is promoted to is let through once. A screen with one of these forms is never restored from Turbo's page cache (`save_bar_form_data` adds `turbo-cache-control: no-cache` to the head). The Back and frame-link guards read Turbo internals (`Turbo.session.history`'s `onPopState` and `currentIndex`, `history.state.turbo.restorationIndex`, the order of `turbo:click` and the frames' link interceptors), listed in the header of `save_bar_controller.js`; `turbo-rails` is pinned (`Gemfile`) for them and for the write queue, and an upgrade means re-reading both files against the new source. Where an internal is missing the guard stands back and only `beforeunload` remains.

## A stale autosave is refused

**A stale autosave is refused, not saved.** The three record editors (the page settings form, a block card, the post form) carry a base as it loaded (`base_updated_at`, iso8601 with microseconds): the record's `updated_at`, except the page settings form, whose base is the page's own `settings_changed_at` (`Admin::AutosaveResponses#autosave_base`). `settings_changed_at` moves in a page's `before_save` whenever a column the settings form can change is about to change (every column but those in `Page::SETTINGS_BASE_IGNORES`: `updated_at`, itself, and `parent_id` and `position`, which a move in the tree writes), and never on `touch`, `update_columns` or `update_all`, so neither a colleague's block save (which only touches the page) nor a colleague's move of the page in the tree makes the settings form stale. Descendants that `Trash::Move#trash_descendants` and `Trash::Restore#restore_branch_members` change with `update_all` keep their `settings_changed_at` (the branch root's moves); harmless, since no settings value changes. A save whose base is older than the record as just loaded is answered 409 by `Admin::AutosaveResponses#refuse_stale_autosave` before any service is called: the record is untouched, nothing is audited, the status line reads "● CHANGED ELSEWHERE" and `Admin::EditorScreen::ChangedElsewhereComponent` fills the header's `#editor-notice` — "Changed by <name> <time ago>. Your text is still here so you can copy it; reloading shows the latest version." and Reload, a full-page visit that discards the typed text. The name comes from the audit log bounded by the refused save's own base (`Audit::ChangeSince`, `app/queries/audit/change_since.rb`: only later events can have made it stale, and for a page only events about the page itself, never its blocks'; the newest change by someone else is preferred; a change by the viewer's own other tab says so; with no event at all it says "Changed elsewhere."). The answer carries no new base, so every later save of that form is refused too until Reload. A blank or unparseable base is not stale (non-JS and scripted clients never send one). The check and the save are not atomic: two saves on the same base within one request's length can both pass. The Media panel and the tag rows still save on a stale base and warn afterwards (`:saved_over`, "SAVED · ALSO CHANGED ELSEWHERE — RELOAD TO SEE THE LATEST", deliberately not the refusal's wording: that save went through and overwrote the other change, where "● CHANGED ELSEWHERE" is a save that was refused and wrote nothing). The Settings form is refused like the editors, as a page rather than a stream: it carries `base_updated_at`, and a Save on a stale base re-renders the screen at 409 with "Settings were changed elsewhere since you opened this screen. Reload to see the latest — your changes are still in the form." and the typed values kept. A group's and a user's editor are refused the same way (`Admin::StaleForm`, 409 with the banner and the typed values kept). All three banners name who changed the record and when by the editors' own rule (`Audit::ChangeSince`): "This group was changed by <name> <time ago>. Reload to see the latest — your changes are still in the form.", "… in another tab or window <time ago>." for the viewer's own change, and the plain "changed elsewhere since you opened this screen" sentence when no event after the base names that record — which includes a group made stale from a user's editor and the reverse, whose event is the other record's. The stale check stands back for a record the viewer can't change: a group that is view-only for them (`AccessControl.can_manage_group?` false) and a user who is not `:editable` (`Users::Manageability`) skip it, so a forged write gets the service's 403 and its one `access.denied`, never a 409 that records nothing. The services move the other side's `updated_at` when a membership changes (`Groups::Save`/`Destroy` touch the members, `Users::Save`/`Destroy` the groups), so a member added on a group form makes that user's open form stale. A block write `touch`es its page but does not move the settings base, so a block's answer carries no page base: the forwarding the block side had (`Admin::ContentBlocksController#page_base_streams`, the autosave script's `pageBaseId` value, the header `X-Page-Base-Updated-At` on `admin--editor--blocks`' requests) was removed with `settings_changed_at`. The page tree's move kept its own forwarding one step longer, because `Pages::Move` saves the page's `parent_id` and `position` and that moved the base; it only ever helped the mover's own tab, and a colleague's drag of the page still refused whoever held its settings form with a final 409. Since a move is not a change of the page's settings, both columns are ignored by the base now, and the tree's forwarding (the header on `admin--pages--tree`'s move and on its Undo toast, `Admin::TreeController#page_base_streams`) is gone too: **no request carries one form's base for another form, and the header no longer exists.** The move and its Undo are still writes of the page and still take their turn in the queue (`test/integration/admin/tree_test.rb`: "a settings form held while a colleague moves that page in the tree saves afterwards", "a move answers no base of the page settings form, whatever a client sends"; `test/system/admin/tree_test.rb`: "moving the page that is open, and undoing it, leaves its editor able to save"). A post's tags are covered the other way round: `Tags::Rename`, `Tags::Destroy` and `Tags::Merge` touch every post carrying the tag, so a post form that was open (it resends every tag chip on every autosave) is refused as stale instead of re-creating a deleted tag or putting the old name back. A 403 answer (a save refused for want of permission) is a rendered answer, not a failure to retry: the status line reads "Not saved — you don't have permission to change this", an error toast says so, and the form stays unclean. The page and post editors are never restored from Turbo's page cache (`turbo-cache-control: no-cache` in their `<head>`), so Back never shows a form with a stale base; they also carry `turbo-prefetch: false`, so a hover-prefetched answer older than a save is never used for a click from an editor.

## The write queue

**The write queue.** That only holds together if one screen's writes are serialised, so `app/javascript/saving/queue.js` (the one specifier everybody imports, a façade over `queue_core.js`, the queue itself; `frame_hold.js`, what waits on it; `promotion_hold.js`; and `queue_state.js`, the page generations and the state they share — the façade's header has the module map and the order their listeners are registered in) runs every `admin--saving--autosave` form's save, block reorder, Turbo block form (add, duplicate, delete, Undo) and tree move (with its Undo) one at a time: a request is sent only after the previous answer has been received, its new bases written into the hidden fields and — for a Turbo Stream answer — the answer's own streams applied, recognised by their markup (`holdTurboRequest` releases its slot only then), and each reads the freshest base at send time. An unchanged form sends nothing. Nothing that replaces the page starts until the queue is empty and every form has sent what it holds (`drained()`, bounded by `DRAIN_LIMIT_MS`), and three things replace a page: a Turbo **visit** waits in `turbo:before-visit`; a **frame navigation** inside `#content` has its REQUEST held (the same `turbo:before-fetch-request` listener holds a GET carrying `Turbo-Frame: content`), and its render waits again only when a write was queued since the request went out (`writeCount()`, every write queued, counted, compared with the count noted as the request went out, or a busy queue) -- the answer is then older than that save, so the frame's URL is fetched again after the drain and that is rendered instead; and **any non-GET Turbo form submission** made while a save is outstanding waits in `turbo:before-fetch-request`, whichever form it is (Still correct — mark up to date, Save key, tag delete, the header's actions; Sign out is not a Turbo submission and is not held). The redirect a Turbo form submission ends in, and the visit a `#content` frame navigation is promoted to, are never held (they arrive with the answer Turbo already fetched; each such note expires after 2 s, `VISIT_NOTE_LIMIT_MS`). **The promotion hold** is a fourth hold, and it is about that promoted visit: `#content` carries `data-turbo-action="advance"`, so a link into it renders the frame and is then promoted to a page visit, and Turbo's navigator, starting a visit, stops whatever navigator-level form submission is under way — the write is done, its answer is dropped. So from the moment a `#content` frame GET goes out until the promoted visit's `turbo:load`, a capturing `submit` listener on `window` holds every *navigator-level* submission — a non-GET, non-`dialog` Turbo form that says `data-turbo-frame="_top"` (itself or its submitter) or sits outside every `<turbo-frame>` (Turbo's own rule, `navigatorLevel` in `promotion_hold.js`: a form outside every frame that names an enabled frame is that frame's, and one inside a frame whose `target` is `_top` or that is disabled is the navigator's): a Trash row's Restore, the header's actions, an Undo toast — and submits it once afterwards, its submitter showing its busy state while held. A frame-level form inside `#content` (the block picker, a block's delete, Duplicate, the account screen's profile form, a note's forms in `turbo-frame#notes`) is never held: the navigator doesn't stop those. The hold ends early on `turbo:fetch-request-error` or `turbo:frame-missing` for the frame, and has two limits: `PROMOTION_FETCH_LIMIT_MS` (10 s) for the fetch and `PROMOTION_LIMIT_MS` (500 ms) from the frame's render to the visit. A held form whose screen was replaced meanwhile is dropped and nothing is sent, and the editor is told with one error toast, "That didn't go through — the screen changed. Try again." (also when the resubmit itself throws) — except a form that opted in with `data-promotion-stand-in` (only the Trash rows' restore and purge forms), which is submitted through its counterpart in the new content when exactly one form there has the same action and the same full payload (every named control, hidden ones and `_method` included, minus the CSRF token and fields marked `data-hold-ignore`). A press that came from a confirm dialog is forgotten when that dialog is closed (Cancel, Escape) before the release, so a cancelled action is never sent. A GET form, `method="dialog"` and a form Turbo doesn't drive (`data-turbo="false"`) are never held. Still open: a `_top` *link* clicked during the frame fetch loses to the promoted visit (a roadmap row). The header's page-replacing actions (Publish, Unpublish, Schedule, Move to trash) additionally drain at `submit` through `admin--saving--queue-hold`, which declines to run when a form ended unclean (refused, invalid, offline) because its redirect would throw away the text a 409 bar promised to keep. One block action carries the same controller, a section's "Remove section, keep blocks": it is no visit, but its Turbo Stream answer replaces the forms of the blocks that stay with new cards, which is the same loss for what those forms hold. Its press drains first and is sent once, after the drain, through `admin--editor--blocks`'s `holdTurboRequest` like any block delete (waiting only for its turn there would let it go ahead of the follow-up of a save still on the wire), and it is not sent at all after an unclean drain (`test/system/admin/sections_test.rb`, "Remove section, keep blocks does not run while a form holds text that was refused, and says so" and "… waits for an edit typed while the block's save was on the wire"). A task belongs to the page generation its form was rendered on: a generation is the `<body>` element plus the count of `#content` frame renders (`isCurrentGeneration`), and a body Turbo is about to replace is retired at `turbo:before-render` (read from `Turbo.navigator.currentVisit.willRender`, a Turbo internal); a task that outlives its page is still sent but renders nothing into the new document. `drained()` never rejects (a form whose flush throws is skipped, so a link that waited is never stranded). A form's save state (what it last saved, what it last sent, whether it is paused by a 409 or failed) lives in a `WeakMap` keyed by the form element, so a block card moved by drag keeps its paused or failed state and is not sent again as it is; after Duplicate, focus goes to the copy's drag handle. A block reorder and a tree move are hand-built `fetch`es inside the queue; `app/javascript/saving/order_request.js` judges their answer: only a Turbo Stream is rendered, and a redirect to sign-in, any other answer or no answer puts the card or row back where it was and raises an error toast (cloned from `#toast-error-template` in the layout) — a reorder the server refuses goes back too. **A block's move** — along the page's list, along a section's lane, between lanes, into a section or out of one — is that same hand-built `fetch`, and `admin--editor--blocks#move` is its one sender, for a drop, a menu item and the handle's keyboard path alike (`docs/reference/content-blocks-and-types.md`, "Moves"). Four things about it belong to the queue. (1) A move between containers is answered with the block redrawn in its new shape, the one time a form is replaced while its block stays, so as any move that names a section or changes containers is queued, every autosave form of the block list is told to send what it holds (`sendHeldEdits`), which puts those saves ahead of it; at its turn a block whose own form did not end clean (paused by a 409, refused, invalid, offline) is not moved and everything is put back with a toast, and one whose edit is still queued behind the move makes the move stand back once — the form is told to send, the move is queued again behind it. (2) For such a move the queue slot is released only when the answer's streams are in the page (`streamsApplied` in `order_request.js`: Turbo performs a stream after the next repaint, and `holdTurboRequest` settles the same thing for a Turbo form), so the next write is never sent from elements the answer is about to replace; a queued move whose element is no longer where that move put it is dropped, and the moved element and its panel are `inert` from the drop until then. (3) What goes back after a failure is `restoreTo`, each container's order as the server last took it, kept per container. (4) A refused structural move is answered with the whole block list, which would replace every form on the screen, so the browser draws that list only when no autosave form there holds text the server does not have (not clean, outstanding, or changed: the questions `settled()` asks); otherwise the list's stream is stopped, the block is put back, the alert gains "Something on this page changed elsewhere. Reload once your unsaved text is safe." and nothing else changes — the 409 bar's promise that typed text stays outranks a current list. A block in a section has its form in a hidden panel under the section's lanes (`admin--editor--section`): the form is rendered with the page and is only shown or hidden, **never fetched and never removed**, because everything above is about forms that are in the document — a hidden form keeps its registration, its debounce, its place in the queue and its paused or failed state, and closing one tells it to send what it holds at once. Closing or reloading the tab is the one way out the queue can't hold: while the screen is not `settled()` (something queued, debounced or retrying, or a form paused or failed) a `beforeunload` listener, present only while an autosave form is registered, asks for the browser's own prompt.

## Notes beside the queue

**Notes are not content and are not in the queue** (`docs/reference/notes.md`). A note's forms are ordinary Turbo forms inside `<turbo-frame id="notes">`, which is rendered outside every autosave form: none is an `admin--saving--autosave` form, none carries a `base_updated_at`, and none replaces an editor form. A notes service never writes the record the note is on (no `touch`, no `updated_at`, no content version), so a note can't make a base stale and a stale base can't refuse a note. What the queue does to a note's form is what it does to any non-GET Turbo submission: while a save is outstanding the request waits in `turbo:before-fetch-request` until `drained()`, and is then sent once. `test/system/admin/notes_flow_test.rb` ("a note sent while an autosave is on the wire goes after it, once, and moves no base") holds a block's PATCH, sends a note, and asserts that the note's POST does not reach `fetch` until the save has been answered, that it is sent exactly once, that the block's and the page's `base_updated_at` are what the save made them, and that the next edit of the block is saved rather than refused. Unsent note text is no unsaved change: it is a draft in `sessionStorage`, it does not make the screen un-`settled()`, the unload guard does not ask for it and the "Leave without saving?" dialog is not raised for it (same file, "leaving an editor with a half-typed note asks nothing, and an unsaved edit of the page still asks"). Live delivery refreshes the notes parts with the notes controller's own `fetch`, part by part, which is no Turbo request and is neither held by the queue nor counted by it; it touches nothing outside the notes frame, the markers and the counts. That is the same reason Turbo's morphing page refresh stays off: no `turbo_refreshes_with`, no `broadcast_refresh`, no `<meta name="turbo-refresh-method">`, each refused by `test/lib/notes_guards_test.rb` ("nothing in the app turns on Turbo's page refresh or morphing, or broadcasts one"). While a note is held here its field is read-only (`admin--notes--composer#sending`, on the form's `submit` as well as on `turbo:submit-start`, which comes only after the hold): what is typed after Send would be in neither the request nor the emptied field.

## Live editing beside the queue

**What live editing adds to the queue, and what it keeps out of it** (`docs/reference/live-editing.md`).

**A save refused by a hold.** Before the stale check, each of the three autosave actions claims the edit reservation of what it saves for the request's tab (`Admin::EditingClaims`). When another tab holds it, the save is answered 409 like a stale one, so `admin--saving--autosave` pauses the form the same way and its later saves send nothing; nothing is written and nothing audited. The status line reads "● NOT SAVED · DANA WEISS IS EDITING" (the state `:held`; "● NOT SAVED · OPEN IN YOUR OTHER TAB" for the person's own other tab), and instead of the "Changed elsewhere" bar the answer puts the `lost` notice into the form's strip slot, with "Copy my text" and "Discard". The answer carries no new base. A request with no tab id (`X-Notes-Tab`) is neither refused nor does it claim, so a scripted client saves as before. Every write an editor sends now carries that header: Turbo's requests from one listener in `app/javascript/editing/requests.js`, the three hand-built ones (the autosave, the block reorder, the tree move) themselves (`test/lib/editing_tab_header_test.rb`).

**Claims and releases are writes in the queue.** `admin--editing--hold` puts `POST claim`, `POST release`, `POST take_over`, `POST hand_over` and `POST withdraw` into the queue with `enqueue`, each a `fetch` with a 10-second timeout, because a request that never answers would hold every save of the screen. The claim is queued when a form says it changed, which is before its debounce starts, so it is answered before that form's first save is sent. A release is queued only once none of the subject's forms has anything `outstanding()`; it waits for that outside the queue, or it would go ahead of the follow-up of a save still on the wire. The one exception to "everything through the queue" is `pagehide`, where nothing can wait: the release of what the tab holds and the withdrawal of a request it made are each a `fetch` with `keepalive`. A test that counts or scripts an editor's writes passes a request to `/cs-studio/editing/` through.

**Three things the autosave controller learned.** (1) `announce()`: `queue()` and `saveNow()` dispatch `admin--saving--autosave:dirty` with the form's `data-editing-subject` when the form differs from what it last saved, except for text that is exactly what is on the wire now (`inFlight`): the `focusout` of a card that was just collapsed is not typing. (2) `pause()` ends a form's saves as a 409 does, without a request: `paused` and `failed` are set, the debounce is cancelled, and a retry waiting out its backoff is cancelled with `busy` cleared, or the form would count as outstanding for good and every read and every visit would wait for a save that is never coming. The hold script calls it when a claim is refused, before the form has sent anything. (3) A save whose form was paused while it waited its turn sends nothing: the queue's task answers `"skipped"`.

**`quiet()` and `writeCount()`, for a reader.** `quiet()` (`queue_core.js`) resolves once the queue is idle: nothing queued or in flight and no form with an edit still to send. Unlike `drained()` it takes no turn, is counted as no write and tells no form to send early, so a reader never changes what the writers do. `writeCount()` (`queue_state.js`) is the number of writes ever queued, which `frame_hold.js` already compared across a frame's request. The editor's live refresh uses both: a read waits for `quiet()`, and an answer during whose flight the count moved is dropped and asked for again, because it was read before this tab's own write (`test/system/admin/editing_live_test.rb`: "an answer fetched before this tab's own write was queued is not drawn").

**The live reads are not in the queue.** They are plain `fetch`es, no Turbo request: the queue neither holds nor counts them, and nothing that listens to Turbo's events hears them ("live refresh uses no Turbo request: no visit, no frame load, no stream"). What they fetch is merged by `app/javascript/editing/merge.js`, whose one rule is the queue's own promise seen from the other side: a form that holds unsaved changes (not `clean()`, something `outstanding()`, or not `unchanged()`) is never replaced, removed or moved. The queue still assumes Turbo's morphing page refresh stays off.
