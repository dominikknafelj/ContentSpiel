# The save rule, the leave guard, stale autosaves and the write queue

> Describes: `app/javascript/autosave/`, `app/javascript/controllers/admin/save_bar_controller.js`, `app/components/admin/save_bar_component.rb`, `app/controllers/concerns/admin/` (autosave responses, stale form).

## The save rule

**The save rule.** Content autosaves (`admin--autosave`, the status line "SAVED 10:42", or "SAVED TO SITE 10:42" for a live record, whose edits go straight to the site): the page and post editors, block cards, the Media panel, a tag's name. Configuration is saved explicitly — Settings (every card of it, Languages included), Groups, Users, Change password — through `Admin::SaveBarComponent` with `admin--save-bar`: a form footer that is always visible, in the form's own column under the fields and sticky at the bottom of the window ("Save · Cancel · N unsaved changes"; Save is disabled, and the footer reads "No unsaved changes", while an existing record has nothing to save; `Admin::SaveBarHelper#save_bar_form_data(dirty:, always:, after:)` — `dirty` re-renders with the typed invalid values still counted, `always` keeps Save enabled from the start for a new record, and `after` names another form whose unsaved changes lock this one's Save, with "Save or cancel your changes first." and an Enter submit refused: the account screen's password form waits for the name form and the Notes switches that way). Something typed *beside* a form that its Save would drop locks Save the same way: the element holding it carries `data-save-bar-holds="<sentence>"` while it does (Settings' API key entry, "Save or cancel the API key first."). A successful submit whose answer keeps the form on screen (a Turbo Stream) makes what was sent the new baseline. A successful save stays on the screen it was made on with a toast: Settings 303s to itself ("Settings saved"), a group and a user to their own editor ("Group saved", "User saved"; a new user to the new user's editor, "User created"); only a delete leaves for the list. Single actions (publish, trash, restore, revoke, a language added, turned off or made the default, the AI key, an owner change) are instant, behind a confirm dialog where they destroy or re-point something. Drag has a keyboard path (Space, arrows, Space; a tile in a section's lane is the exception — its grip is for the pointer only and its ⋯ menu holds every move a drag makes) and its own styling (`.admin-drag-ghost`, `.admin-drag-chosen`, `.admin-drag-fallback`); the Sortables run with `forceFallback` (SortableJS's own pointer-driven drag, a clone on `<body>`), because the handles are `<button>`s and Firefox can't start a native drag from one.

## How the footer counts

**How the footer counts.** `admin--save-bar` compares what the form would *submit* now against a snapshot taken on connect (a disabled control and an unticked box are absent), so it doesn't depend on the order nested controllers connect in, and a value typed back is no change. One key per control: a radio group is one key, a checkbox is `name=value` while ticked, a tracked hidden input whose name ends in `[]` is `name=value` too, present while it holds a value — the members of a *set* (a chip input's chips, the scope editor's carried content types), where order means nothing, so removing the first of ten chips is one change and a chip removed and added back is none (the blank sentinel ahead of the chips is no member) — and anything else is its name plus its *position* among the controls of that name (`name#0`, `name#1`, …), so the rows of a list that share one name (`site_setting[languages][][fallback]`, one select per language row) count separately. A control marked `data-save-bar-ignore` is not counted at all (the account screen's current password: nothing to save by itself, and what a password manager fills in on load). A hidden input is ignored unless it carries `data-save-bar-track` — the real control behind a widget (a member chip, the language order, a removed content type's carrier), whose script dispatches a bubbling `input` or `change` on it when it sets the value; `Admin::ChipInputComponent`'s `track:` marks its inputs that way. For every key but a checkbox's, an absent key and an empty string are the same value, so a blank row added to a list is not yet a change. The count is announced for the whole page as `admin--save-bar:state` on `document` (`detail: { unsaved, count }`; a late listener asks with `admin--save-bar:query`), and `admin--pending-lock` is its listener: while anything is unsaved it disables its `control` targets (a link gets `aria-disabled` and its click swallowed) and shows its `hint`, "Save or cancel your changes first." — the instant actions beside a form answer by reloading the screen, which would throw the pending changes away. A *named* control of the explicit-save form itself is never locked (disabled, it would drop out of what the form submits and count as a change that keeps the lock on), so an instant action's fields belong to a form of their own through `form=`.

## The leave guard

**The leave guard** ("Leave without saving?" · "You have N unsaved changes on this screen." · **Keep editing**, which has the focus, / **Discard changes**; the `leave-dialog` in the layout) is page-level, one prompt however many forms a screen has, and covers four ways out: a Turbo visit (`turbo:before-visit`); a *link* that navigates the `#content` frame, stopped at `turbo:click` before Turbo has started anything; Back and Forward within the document (a `popstate` listener put ahead of Turbo's own, the traversal undone with `history.go`); and a page unload (`beforeunload`, the browser's own prompt — which is also all that Back to an entry from before a full page load gets). It does **not** cover a GET *form* submitted into `#content` or a script setting the frame's `src`: no explicit-save screen has either, and one that adds a filter form beside its save form must revisit this first. The footer's Cancel never asks; a same-page `#fragment` link is no way out at all (`admin--fragment-links`, see `docs/reference/design-system.md`: the focus moves by hand, no history entry, and the guard stands back from it); the visit a `#content` frame navigation is promoted to is let through once. A screen with one of these forms is never restored from Turbo's page cache (`save_bar_form_data` adds `turbo-cache-control: no-cache` to the head). The Back and frame-link guards read Turbo internals (`Turbo.session.history`'s `onPopState` and `currentIndex`, `history.state.turbo.restorationIndex`, the order of `turbo:click` and the frames' link interceptors), listed in the header of `save_bar_controller.js`; `turbo-rails` is pinned (`Gemfile`) for them and for the write queue, and an upgrade means re-reading both files against the new source. Where an internal is missing the guard stands back and only `beforeunload` remains.

## A stale autosave is refused

**A stale autosave is refused, not saved.** The three record editors (the page settings form, a block card, the post form) carry the record's `updated_at` as it loaded (`base_updated_at`, iso8601 with microseconds). A save whose base is older than the record as just loaded is answered 409 by `Admin::AutosaveResponses#refuse_stale_autosave` before any service is called: the record is untouched, nothing is audited, the status line reads "● CHANGED ELSEWHERE" and `Admin::EditorScreen::ChangedElsewhereComponent` fills the header's `#editor-notice` — "Changed by <name> <time ago>. Your text is still here so you can copy it; reloading shows the latest version." and Reload, a full-page visit that discards the typed text. The name comes from the audit log bounded by the refused save's own base (`Audit::ChangeSince`, `app/queries/audit/change_since.rb`: only later events can have made it stale; the newest change by someone else is preferred; a change by the viewer's own other tab says so; with no event at all it says "Changed elsewhere."). The answer carries no new base, so every later save of that form is refused too until Reload. A blank or unparseable base is not stale (non-JS and scripted clients never send one). The check and the save are not atomic: two saves on the same base within one request's length can both pass. The Media panel and the tag rows still save on a stale base and warn afterwards (`:saved_over`, "SAVED · ALSO CHANGED ELSEWHERE — RELOAD TO SEE THE LATEST", deliberately not the refusal's wording). The Settings form is refused like the editors, as a page rather than a stream: it carries `base_updated_at`, and a Save on a stale base re-renders the screen at 409 with "Settings were changed elsewhere since you opened this screen. Reload to see the latest — your changes are still in the form." and the typed values kept. A group's and a user's editor are refused the same way (`Admin::StaleForm`, 409 with the banner and the typed values kept). All three banners name who changed the record and when by the editors' own rule (`Audit::ChangeSince`): "This group was changed by <name> <time ago>. Reload to see the latest — your changes are still in the form.", "… in another tab or window <time ago>." for the viewer's own change, and the plain "changed elsewhere since you opened this screen" sentence when no event after the base names that record — which includes a group made stale from a user's editor and the reverse, whose event is the other record's. The stale check stands back for a record the viewer can't change: a group that is view-only for them (`AccessControl.can_manage_group?` false) and a user who is not `:editable` (`Users::Manageability`) skip it, so a forged write gets the service's 403 and its one `access.denied`, never a 409 that records nothing. The services move the other side's `updated_at` when a membership changes (`Groups::Save`/`Destroy` touch the members, `Users::Save`/`Destroy` the groups), so a member added on a group form makes that user's open form stale. Because every block write `touch`es its page, a block's answer moves the page settings form's `base_updated_at` forward to the touched page's — only when the base that request carried (`X-Page-Base-Updated-At`) was still current before the write. The page tree's move (and its Undo toast) sends the same header, but only when the moved page is the one open in the editor, since `Pages::Move` saves that page and so moves its `updated_at` (`Admin::TreeController#page_base_streams`). A post's tags are covered the other way round: `Tags::Rename`, `Tags::Destroy` and `Tags::Merge` touch every post carrying the tag, so a post form that was open (it resends every tag chip on every autosave) is refused as stale instead of re-creating a deleted tag or putting the old name back. A 403 answer (a save refused for want of permission) is a rendered answer, not a failure to retry: the status line reads "Not saved — you don't have permission to change this", an error toast says so, and the form stays unclean. The page and post editors are never restored from Turbo's page cache (`turbo-cache-control: no-cache` in their `<head>`), so Back never shows a form with a stale base; they also carry `turbo-prefetch: false`, so a hover-prefetched answer older than a save is never used for a click from an editor.

## The write queue

**The write queue.** That only holds together if one screen's writes are serialised, so `app/javascript/autosave/queue.js` (the one specifier everybody imports, a façade over `queue_core.js`, the queue itself; `frame_hold.js`, what waits on it; `promotion_hold.js`; and `queue_state.js`, the page generations and the state they share — the façade's header has the module map and the order their listeners are registered in) runs every `admin--autosave` form's save, block reorder, Turbo block form (add, duplicate, delete, Undo) and tree move (with its Undo) one at a time: a request is sent only after the previous answer has been received, its new bases written into the hidden fields and — for a Turbo Stream answer — the answer's own streams applied, recognised by their markup (`holdTurboRequest` releases its slot only then), and each reads the freshest base at send time. An unchanged form sends nothing. Nothing that replaces the page starts until the queue is empty and every form has sent what it holds (`drained()`, bounded by `DRAIN_LIMIT_MS`), and three things replace a page: a Turbo **visit** waits in `turbo:before-visit`; a **frame navigation** inside `#content` has its REQUEST held (the same `turbo:before-fetch-request` listener holds a GET carrying `Turbo-Frame: content`), and its render waits again only when a write was queued since the request went out (`writeCount()`, every write queued, counted, compared with the count noted as the request went out, or a busy queue) -- the answer is then older than that save, so the frame's URL is fetched again after the drain and that is rendered instead; and **any non-GET Turbo form submission** made while a save is outstanding waits in `turbo:before-fetch-request`, whichever form it is (Still correct — mark up to date, Save key, tag delete, the header's actions; Sign out is not a Turbo submission and is not held). The redirect a Turbo form submission ends in, and the visit a `#content` frame navigation is promoted to, are never held (they arrive with the answer Turbo already fetched; each such note expires after 2 s, `VISIT_NOTE_LIMIT_MS`). **The promotion hold** is a fourth hold, and it is about that promoted visit: `#content` carries `data-turbo-action="advance"`, so a link into it renders the frame and is then promoted to a page visit, and Turbo's navigator, starting a visit, stops whatever navigator-level form submission is under way — the write is done, its answer is dropped. So from the moment a `#content` frame GET goes out until the promoted visit's `turbo:load`, a capturing `submit` listener on `window` holds every *navigator-level* submission — a non-GET, non-`dialog` Turbo form that says `data-turbo-frame="_top"` (itself or its submitter) or sits outside every `<turbo-frame>` (Turbo's own rule, `navigatorLevel` in `promotion_hold.js`: a form outside every frame that names an enabled frame is that frame's, and one inside a frame whose `target` is `_top` or that is disabled is the navigator's): a Trash row's Restore, the header's actions, an Undo toast — and submits it once afterwards, its submitter showing its busy state while held. A frame-level form inside `#content` (the block picker, a block's delete, Duplicate, the account screen's name form) is never held: the navigator doesn't stop those. The hold ends early on `turbo:fetch-request-error` or `turbo:frame-missing` for the frame, and has two limits: `PROMOTION_FETCH_LIMIT_MS` (10 s) for the fetch and `PROMOTION_LIMIT_MS` (500 ms) from the frame's render to the visit. A held form whose screen was replaced meanwhile is dropped and nothing is sent, and the editor is told with one error toast, "That didn't go through — the screen changed. Try again." (also when the resubmit itself throws) — except a form that opted in with `data-promotion-stand-in` (only the Trash rows' restore and purge forms), which is submitted through its counterpart in the new content when exactly one form there has the same action and the same full payload (every named control, hidden ones and `_method` included, minus the CSRF token and fields marked `data-hold-ignore`). A press that came from a confirm dialog is forgotten when that dialog is closed (Cancel, Escape) before the release, so a cancelled action is never sent. A GET form, `method="dialog"` and a form Turbo doesn't drive (`data-turbo="false"`) are never held. Still open: a `_top` *link* clicked during the frame fetch loses to the promoted visit (a roadmap row). The header's page-replacing actions (Publish, Unpublish, Schedule, Move to trash) additionally drain at `submit` through `admin--queue-hold`, which declines to run when a form ended unclean (refused, invalid, offline) because its redirect would throw away the text a 409 bar promised to keep. One block action carries the same controller, a section's "Remove section, keep blocks": it is no visit, but its Turbo Stream answer replaces the forms of the blocks that stay with new cards, which is the same loss for what those forms hold. Its press drains first and is sent once, after the drain, through `admin--blocks`'s `holdTurboRequest` like any block delete (waiting only for its turn there would let it go ahead of the follow-up of a save still on the wire), and it is not sent at all after an unclean drain (`test/system/admin/sections_test.rb`, "Remove section, keep blocks does not run while a form holds text that was refused, and says so" and "… waits for an edit typed while the block's save was on the wire"). A task belongs to the page generation its form was rendered on: a generation is the `<body>` element plus the count of `#content` frame renders (`isCurrentGeneration`), and a body Turbo is about to replace is retired at `turbo:before-render` (read from `Turbo.navigator.currentVisit.willRender`, a Turbo internal); a task that outlives its page is still sent but renders nothing into the new document. `drained()` never rejects (a form whose flush throws is skipped, so a link that waited is never stranded). A form's save state (what it last saved, what it last sent, whether it is paused by a 409 or failed) lives in a `WeakMap` keyed by the form element, so a block card moved by drag keeps its paused or failed state and is not sent again as it is; after Duplicate, focus goes to the copy's drag handle. A block reorder and a tree move are hand-built `fetch`es inside the queue; `app/javascript/autosave/order_request.js` judges their answer: only a Turbo Stream is rendered, and a redirect to sign-in, any other answer or no answer puts the card or row back where it was and raises an error toast (cloned from `#toast-error-template` in the layout) — a reorder the server refuses goes back too. **A block's move** — along the page's list, along a section's lane, between lanes, into a section or out of one — is that same hand-built `fetch`, and `admin--blocks#move` is its one sender, for a drop, a menu item and the handle's keyboard path alike (`docs/reference/content-blocks-and-types.md`, "Moves"). Four things about it belong to the queue. (1) A move between containers is answered with the block redrawn in its new shape, the one time a form is replaced while its block stays, so as any move that names a section or changes containers is queued, every autosave form of the block list is told to send what it holds (`sendHeldEdits`), which puts those saves ahead of it; at its turn a block whose own form did not end clean (paused by a 409, refused, invalid, offline) is not moved and everything is put back with a toast, and one whose edit is still queued behind the move makes the move stand back once — the form is told to send, the move is queued again behind it. (2) For such a move the queue slot is released only when the answer's streams are in the page (`streamsApplied` in `order_request.js`: Turbo performs a stream after the next repaint, and `holdTurboRequest` settles the same thing for a Turbo form), so the next write is never sent from elements the answer is about to replace; a queued move whose element is no longer where that move put it is dropped, and the moved element and its panel are `inert` from the drop until then. (3) What goes back after a failure is `restoreTo`, each container's order as the server last took it, kept per container. (4) A refused structural move is answered with the whole block list, which would replace every form on the screen, so the browser draws that list only when no autosave form there holds text the server does not have (not clean, outstanding, or changed: the questions `settled()` asks); otherwise the list's stream is stopped, the block is put back, the alert gains "Something on this page changed elsewhere. Reload once your unsaved text is safe." and nothing else changes — the 409 bar's promise that typed text stays outranks a current list. A block in a section has its form in a hidden panel under the section's lanes (`admin--section`): the form is rendered with the page and is only shown or hidden, **never fetched and never removed**, because everything above is about forms that are in the document — a hidden form keeps its registration, its debounce, its place in the queue and its paused or failed state, and closing one tells it to send what it holds at once. Closing or reloading the tab is the one way out the queue can't hold: while the screen is not `settled()` (something queued, debounced or retrying, or a form paused or failed) a `beforeunload` listener, present only while an autosave form is registered, asks for the browser's own prompt.
