# Translations: tracking, status, matrix and AI translation

> Describes: `app/models/translations/`, `app/models/concerns/translations/`, `app/models/ai/`, `app/services/ai/`, `app/services/translations/`, `app/controllers/admin/translations_controller.rb`, `app/components/admin/translation_screen/`.

## Translations

Spec `docs/superpowers/specs/2026-10-02-translation-helpers-design.md` (read its §10 Amendments, which override the text above them). The original is always `Locales.default` (`Translations.primary_locale`, read at the time of use, never cached), and every other enabled language is a translation of it (`Translations.target_locales`).

**Tracking.** `Translations::Tracker` (`app/models/concerns/translations/tracker.rb`, `tracks_translations` on `Page`, `Post`, `ContentBlock`, `Media::Asset` and `SiteSetting`) records which version of the original each translation was saved against. `translation_sources` is a jsonb column on each of those tables, `{ field => { locale => entry } }`, where an entry is one of two shapes that stay valid side by side (every reader goes through `Translations::Source.wrap`, so a record holding both never raises): the bare sha256 of the original (everything saved before the design pass: it can answer "current or outdated" but has no text to diff) or `{ "digest", "text", "saved_at", "from" }` — the original's text as it was (a String, or an Array of paragraphs for rich text), when, and in which language. When a target-language value changes, a `before_save` stores the current original's entry for it, or deletes the entry if the value is now blank. The text is what `Translations::SourceDiff` word-diffs the original's current text against; `Source#comparable?` is true only when text is stored *and* `from` is the current primary locale, so after a default-language change the stored text (in the old language) is never diffed against the new original. `SourceDiff` is pure and bounded — `MAX_WORDS` (4,000) per text and one `MAX_CELLS` (4 million) table budget per call, common prefix and suffix trimmed first, paragraphs matched before words — and answers `too_long?` rather than build an expensive table. The other column is `translation_original_changed_at`, `{ field => ISO-8601 }`: when each field's *primary-language* value last changed (by digest, so a whitespace-only edit isn't one; blank → filled counts), written by the Tracker's `before_save` and nothing else; it is what the translations matrix sorts by and the reference card's "CHANGED <time ago>" reads. A change to the original itself never touches `translation_sources`, which is exactly what makes the other languages outdated. Digests come from `Translations.digest`: a stripped string with line endings normalised to LF for plain values (a browser submits CRLF; the changed-value check normalises the same way, so re-submitting an unchanged multi-line value is never an edit), `RichText::Document#normalized` for rich text (so a normalisation-only change isn't an edit), and canonical key-sorted JSON for a schema group field. The tracked fields are derived from the model's own Mobility `translates` names minus `slug`, plus its content or block type's `translated: true` schema fields. Don't list them anywhere a second time. `#translation_state(field, locale)` returns one of:
- `:missing`: blank;
- `:unknown`: present but no digest. This covers everything saved before the feature, and any field whose original is now blank. It never reads `:outdated`, so deploying flags nothing;
- `:outdated`;
- `:current`.

Every read is literal per locale, never through a fallback. The original's digest is memoised per record and field (and a schema reader's per-locale FieldSet per locale), checked against the stored value it came from and dropped on save, reload and confirm, so a status read digests each original once, not once per target language. `translation_sources` and `translation_original_changed_at` are bookkeeping: they're kept out of audit `field_changes` (`Audit::Snapshot::IGNORED_CHANGES`) but stay in the snapshot.

A block type's translated schema field (`translated: true`, stored in `translated_settings`) is tracked, translated by AI as plain text (`Admin::Ui::FieldComponent::TRANSLATABLE_TYPES` lists `:string`) and copied like a column; the Note block's title is the first built-in one (`test/services/translation_state_parity_test.rb`: "a note's title is tracked like a caption: never missing, outdated when the original changes, and a change of the kind changes no state"; `test/services/ai/translate_test.rb`: "a note's title goes to the provider as plain text and its text as Markdown, and its kind is not offered"; `test/integration/public_blocks_test.rb`: "a note on a live page is read from its published copy: its kind, its title in each language and its text change only when published"; `test/models/audit/snapshot_test.rb`: "a note's translated title is in the snapshot per language, and its change is the column's old and new value").

**Status.** `Translations::Status.for(records, locales:)` (`app/models/translations/status.rb`) rolls fields up to one state per record and locale, in this order of precedence:
- `:missing`: a **required** translated field is blank. That's the title, a required schema field, an image's alt when its original has one, or the site title. An optional field left blank in a language (a subtitle, an excerpt, a caption, a body) is a choice, not a gap: it does not make the record missing there, marks no language tab, adds nothing to a "○N" count and is not on the Translations screen;
- `:outdated`: any tracked field is outdated;
- `:complete`: neither. `:unknown` counts as complete.

A page's or post's blocks roll into it, loaded in one query per batch.

**The stored states.** Where a record stands is a table, `translation_states` (`Translations::State`; `record_type`, `record_id`, `locale`, `state` = `complete`/`missing`/`outdated`), one row per page, post, library image and the site settings, per target language — so a list can `WHERE`, `COUNT` and page on it instead of working states out per record. `Translations::StateIndex` (`app/models/translations/state_index.rb`) is the only writer and computes through `Translations::Status`, so the two always agree: `refresh(record)` (a block refreshes its *owner*), `remove(record)`, `rebuild_all`, and the readers `states_for(records, locales:)` and `counts_for` (one query; a record, or a locale, with no row reads `:complete`), `joins`, `summary` / `summaries` (grouped SQL per type, however many languages) and `exists_in_any_locale_sql` (an Arel condition for a `where`, a `where.not` or a `FILTER`, despite its name; the index builds no SQL text). It is derived data, like `public_paths` and `media_usages`: never written by hand, refreshed inside the same transaction as every save that can change a state — the save services, a block's save and destroy, `Translations::Confirm`, `Trash::Purge` (`remove`), and a language being enabled, disabled or made the default (`Locales::Enable`/`Disable`/`MakeDefault`, and `Settings::Save` when it is handed a changed `default_locale` or `locales`, as the setup wizard does: `rebuild_all`, **synchronously**, proportional to the site's size; a reorder or a fallback change through `languages:` rebuilds nothing) — so a rolled-back write leaves the rows alone, and a trashed record keeps its rows. `bin/rails translations:reindex` rebuilds everything when it is suspected stale (a bug, a direct SQL edit, a restored backup). `test/services/translation_state_parity_test.rb` is the guard against a write path that forgets it: one scenario per service, after which the stored rows must equal a fresh `Translations::Status`; a new service that changes what a state is computed from belongs in it. Two limits follow from the table being derived: a deploy that adds a required translated field leaves rows stale until `translations:reindex`, and a record created outside the services (a console `create`, a test) has no row, reads complete and is absent from the matrix and the counts until it is next saved or reindexed. Where it shows:
- the language tabs (`Admin::Ui::LanguageTabsComponent`), which show missing and outdated as independent markers, in one vocabulary — Missing, Outdated, Translated — that the chip, the tabs' screen-reader words and the matrix share (`Admin::Ui::TranslationChipComponent` draws the same two states in lists, the tree and the matrix);
- each outdated field's reference card (see `docs/reference/editors-and-translation-pair.md`);
- the posts list's Languages column and its Translation filter (`needs` / `outdated` / `complete`, an EXISTS over the target languages);
- the page tree's ↻N / ○N counts;
- the dashboard's "Needs translation" card;
- the **Translations matrix** (`Admin::TranslationsController#index`, `/<admin>/translations`): a summary card per target language ("% done", a bar, "12 missing · 1 outdated"), a type filter (`?type=page|post|media|settings`, only the types the viewer may read), `?language=de` (a summary card's link: only the rows that need work in that language, all columns stay), and a matrix whose rows are the items that need work in *any* target language and whose columns are the languages — each cell that language's state as a mark and a word (`Admin::TranslationScreen::StateCellComponent`: ○ Missing, ↻ Outdated, ● Translated), linking to the item's editor in it. The whole row opens the item in the first language that needs work: a stretched link sits in the action cell (an `aria-hidden`, untabbable `<a>`; the title cell is `z-20` and the matrix's scroll wrapper is `isolate`, so the sticky titles stay under the shell's top bar), the row has one tab stop (the title link, named for the action: "Translate: About us"), and the action word ("Translate →", or "Review changes →" when any state is outdated) is shown by `opacity` on hover or focus. Rows with an outdated language come first (they are already visible on the site), the most recently changed original first (`StateIndex.original_changed_at_sql`, blocks rolled in), then rows that only miss something in the same order. It lists exactly what the actor may read (pages and posts through `AccessControl.scope`, images only for a `media.upload` holder, the site settings row only for `settings.manage`) and is filtered, counted and paginated in SQL — each type contributes its own ordered window and the page is merged in Ruby, so the cost is proportional to the page, not the site; the settings row tops page 1 and is never paged. A retired `?locale=` is ignored.

`Translations::EditRight` is the one "may edit this record" rule shared by Confirm and `AI::Translate`:
- pages and posts: `edit`, plus `publish` when published;
- blocks: `ContentBlocks::OwnerPermissions`;
- images: `media.manage` or the uploader with `media.upload`;
- the site settings: `settings.manage`.

Confirming records `<page|post|block|media|settings>.translation_confirmed`. **Still correct — mark up to date** streams the card's current variant and, once a language has nothing else outdated, removes the language tab's marker (`Admin::TranslationConfirmationsController`).

**Site title and tagline** are translated: `SiteSetting` `translates :title, :tagline`, jsonb. The title must be present in the default language, and changing the default language copies the title and tagline from the old default when the new one has none. Public readers use `translated(theme_site, :title)` (with fallback). The Settings form holds every enabled language's title and tagline at once (see `docs/reference/settings-languages-ai.md`); `?locale=` only picks the tab shown first (the Translations matrix's `?locale=` is retired). `Settings::Save` takes them through `translations:` only, never `attributes:`.

**AI translation.** `AI::Providers` (`app/models/ai/providers.rb`) is a registry like the others: the built-in `anthropic`, plugins `owner/name`, a duplicate raising `AI::DuplicateProvider`, reset and re-registered in `config/initializers/types.rb`'s `to_prepare`. A provider answers `new(api_key:, model:)`, `#translate(texts:, from:, to:, format: :plain | :markdown)` and `#test_connection`, and raises `AI::Error` with a message fit to show the editor. `AI::Providers::Anthropic` uses the `anthropic` gem with a 25 s timeout, `max_retries: 0` and a pinned `base_url`. `AI.configured?` / `AI.provider` / `AI.model` (default `claude-sonnet-5`) read the `SiteSetting` row's `ai_provider`, `ai_model` and `ai_api_key`, which are configured under Settings → "AI translation" with `settings.manage`. Zeitwerk inflects `ai` → `AI` (`config/initializers/zeitwerk.rb`).

`AI::Translate` (`app/services/ai/translate.rb`) needs `ai.translate` (seeded onto Admin and Editor) **and** the record's edit right (`Translations::EditRight`). It sends the primary-language values of the requested fields (blank ones skipped; rich text as Markdown, back through `RichText::Document.from_markdown`, the MCP round trip), capped at 20 fields and 6,000 characters per request. It returns **suggestions only**: it never saves. It records `ai.translated` with metadata `fields from to provider model characters` and **no snapshot**, so no text reaches the audit log.

**AI requests run inside the web request.** A suggestion request makes at most two provider calls (plain fields, then rich text), each bounded by the 25 s timeout, and holds one Puma thread for as long as it waits (`RAILS_MAX_THREADS`, 3 by default, `config/puma.rb`): a few editors running "Suggest translations for N empty fields" at once can starve the site of threads for that long. In production kamal-proxy sits in front, and its default 30 s response timeout would cut requests off, so `config/deploy.yml` sets `proxy.response_timeout: 75` (`test/models/ai/providers/anthropic_test.rb` keeps it above twice the provider timeout). The long-term route is a background job (Solid Queue) that streams suggestions back over Turbo, tracked in the roadmap.

**The suggestion flow.** In the editor, an *empty* translated field in a non-default language gets a Translate button under its input and an outdated one a **Suggest update** in its reference card (both `Admin::TranslationScreen::TranslateButtonComponent`, `admin--translation--translate`; shown only to a viewer who may edit the record, with AI set up and `ai.translate`), and the header gets "Suggest translations for N empty fields" (`TranslateAllComponent`: idle, running — "Suggesting i of n fields", a bar, Cancel — and ready — "N suggestions ready · Use all · Discard all"). Requests are `fetch`es, never form submissions (the buttons sit inside autosave forms): `POST /<admin>/translations/suggest` (`Admin::TranslationsController#suggest`) answers with Turbo Streams — at any status, a refusal or provider error being a stream too — putting a suggestion box under each requested field, with Use / Discard, or the inline error. The bulk run splits per record and by `AI::Translate::MAX_FIELDS`/`MAX_CHARACTERS` and sends the parts one after another, so each fits the provider's timeout, progress shows and earlier parts survive a later failure or Cancel. While a request is out the field's box holds a pending box (`PendingComponent`, cloned from a `<template>` in the layout): a spinner, the seconds waited, Cancel — and after 25 s (`PendingComponent::TIMEOUT_SECONDS`, the provider's own timeout) "No suggestion after 25 seconds." with Try again; a late answer for a box that timed out is ignored unless Try again was pressed. `mode=update` (Suggest update) additionally shows the field's current translation ("Current: …", read from the record, never sent to the provider) so the editor can compare before pressing Use, which replaces the value; the bulk run skips fields that already have a translation. **Use** is the only write: it fills the input (a rich-text body through a `translate:use` event handled by `admin--rich-text--editor#applySuggestion`) and a bubbling `input` event lets the form's own autosave save it as an ordinary edit, which records a fresh digest and text. **Use all** presses every Use, plain fields first, then rich text, through the write queue. A plain suggestion sits in an editable textarea with no `name`, so it never feeds an autosave until Use.

**A Table block's table is per language** (`docs/reference/content-blocks-and-types.md`, "The Table block"; table block spec, decisions 1 and 8 to 10, whose "As built" says where the build left them). The table is the block's `body`, so its tracking, state and AI flow are a body's and nothing about it was taught anew; only these differ.
- **The source's table is the starting content, not the stored value.** On a translation tab, an editable table-mode column whose document has no top-level node, beside an original that is a table, shows the source's table (shape, alignment, header kinds, words) as the editor's `startingContent` (`RichTextColumnComponent#starting_content`, `source_copy?`), while the form's body field stays EMPTY. Only the translator's first real change writes the field, so a click on the grid saves nothing, live refresh sees a clean form and replaces it, and the existing rules hold: the field is empty, so the state is Missing and **Translate** is offered. Until a change is saved the site shows the default language's table (the fallback). "No table" is the script's own rule (no top-level node), not `blank?`, so a stored table of empty cells is the language's own. A held or read-only column is never given the copy, and the caption is not copied (it is a plain translated field). The control switches are drawn from the copy (a source without a header row starts the switch off). A copy saved untouched would have read as Translated with English words in it, and one written into the field by a script would have counted as an edit, which is why it is not written (`test/components/admin/columns/rich_text_column_component_test.rb`: "on a translation tab a language with no table starts from the source's table, with the field empty, Translate offered and the mark Missing", "a read-only column is never given the source's copy"; `test/system/admin/table_block_test.rb`: "the copied grid saves nothing until a cell is changed; then the language is Translated and the site shows it", "the translation tab's own grid has all the controls").
- **The diff is cell by cell.** `RichText::Document#plain_paragraphs` descends into a table and answers one entry per cell, row by row, empty cells dropped, so the Outdated reference card's word diff names only the changed cell's words, and a table's `plain_paragraphs.first` is its first non-empty cell. The digest is unchanged, so a stored state is not disturbed. **Still correct** clears it without editing (`test/system/admin/table_block_test.rb`: "a changed source cell makes the table Outdated, the reference card names the cell's words, and Still correct clears it"). The reference card draws the source's table read-only, in the card's plain rich-text styles.
- **AI translates the cells and keeps the shape.** A table goes out as a GFM table and comes back through `RichText::Document.from_markdown` with `tables: true` (the only caller that passes it). A suggestion is offered only when it is exactly ONE table with the source's shape now (`document.table?`, rows and columns equal), else the whole call fails with `AI::Translate::DIFFERENT_TABLE` (a constant, as the service's other messages are, not a locale key) and nothing is offered; prose beside the table fails it too. The failure is the whole request's, not the table's: `DIFFERENT_TABLE` is raised as an `AI::Error`, so every suggestion that request would have made is dropped with the table's, the block's caption's included, as the spec decided. The suggestion's cells take their kind (`tableHeader` or `tableCell`) and alignment from the source's cell at the same position (`with_source_cells`), because Markdown cannot spell a header column or the absence of a header row. **Suggest update** translates the source as it is now, and **Use** replaces this language's table with it whatever shape that had; the translator sees it first, and AI never saves by itself. A table whose text is over `AI::Translate::MAX_CHARACTERS` (6,000 characters: far below the hard limits, so a table of a few hundred short cells is enough) gets no suggestion at all, the request answering `TOO_MUCH` as it does for a long body, so such a table is translated by hand (`test/services/ai/translate_test.rb`: "a table body goes out as GFM and its suggestion comes back as a table of the source's shape", "a suggestion keeps the source's cell kinds and alignment: a header column, and no header row", "a suggestion with prose beside the table fails the whole call", "a suggestion whose table has another shape fails the whole call and offers nothing"; `test/system/admin/table_block_test.rb`: "Suggest update offers a table of the source's shape and Use puts it in the grid"). The system test registers its own provider (`TableProvider`, once, never `reloader.prepare!`) because `GatedProvider` prefixes the whole text and breaks a table's first line.
- **A page's status does not count a table**, as it does not count any block's body (`Translations::Status#block_missing_count` counts a block's required settings only): an untranslated table does not make the page read Missing in the matrix or the switcher.

**The API key** is stored with `encrypts :ai_api_key` and is never rendered, logged (the `_key` parameter filter), or put in an audit snapshot (`Audit::Snapshot::NEVER_STORED`). It is not a field of the Settings form: it has its own Save key and Remove forms and endpoint (`Admin::AiKeysController`, see `docs/reference/settings-languages-ai.md`), Remove asks through `Admin::Ui::ConfirmDialogComponent`, and `ai_api_key_saved_at` records when it was saved. `SiteSetting#ai_api_key_set?` checks the stored ciphertext without decrypting it, so lost encryption keys never break the Settings screen. A key that can't be decrypted makes a provider call fail with a message asking for the key to be entered again.

**Active Record encryption keys.** Development and test use fixed, public keys (`config/environments/development.rb`, `test.rb`), so a checkout and CI need nothing. Production must provide `primary_key`, `deterministic_key` and `key_derivation_salt`, in one of two ways:
- in the credentials, as `active_record_encryption.*` (`bin/rails db:encryption:init` prints a fresh set);
- as the env vars `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY`, `ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY` and `ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT` (`config/application.rb`; for Kamal, see the comment in `.kamal/secrets` and add them to `env: secret:` in `config/deploy.yml`).

Precedence is per key: an env var that's set wins over the credentials for that key alone. Nothing checks for the keys at boot. A server without them runs normally until someone saves an AI key, which then raises.
