# Hosting: the site's address, HTTPS, telemetry and the reset link

> Describes: `lib/site_address.rb`, `lib/host_settings.rb`, `lib/telemetry.rb`, `lib/telemetry/path_scrubber.rb`, `lib/old_reset_address.rb`, `config/environments/production.rb`, `config/application.rb` (the `content_spiel.host_announcement` initializer and the middleware), `config/initializers/opentelemetry.rb`, `config/initializers/setup_token.rb`, `app/models/setup/token.rb`, `app/models/setup/system_check.rb`, `app/mailers/passwords_mailer.rb`, `app/controllers/admin/passwords_controller.rb`, `app/javascript/controllers/reset_token_controller.js`, `app/controllers/public_controller.rb` (`public_urls`, `origin_etag_key`), `app/components/admin/ui/insecure_notice_component.rb`.

Spec: `docs/superpowers/specs/2026-10-12-safe-on-a-public-address-design.md` (its last section, "As built", lists where the code departed from it). This is the first of four parts that make a site a stranger can put on a public address; mail, the sitemap and starting up, and the setup wizard follow (`docs/roadmap.md`).

## What a host sets

Seven variables. None is required for the application to start outside production; in production `SECRET_KEY_BASE` (or a secret in the credentials) is.

| Variable | What it does | Without it |
|---|---|---|
| `PUBLIC_HOST` | The site's address with its scheme, `https://docs.example.org`. Everything in "The site's address" and "HTTPS" below follows from it. | Any host name is answered, nothing is forced to HTTPS, addresses in pages follow the request, and outside development and test no password reset mail is sent. System status and the wizard's system check say so as a warning. |
| `ASSUME_SSL` | `1`, and no other value, makes every request count as HTTPS (`config.assume_ssl`). Only for a proxy that ends TLS and does not send `X-Forwarded-Proto`. | The proxy's `X-Forwarded-Proto` is believed. Kamal's proxy sends it and Thruster passes it on. |
| `SECRET_KEY_BASE` | Signs sessions and tokens. | Production does not start, unless the credentials file that `RAILS_MASTER_KEY` opens holds a `secret_key_base`. |
| `SETUP_TOKEN` | The one-time code `/setup` asks for, chosen by the host. | It is derived from `secret_key_base` and printed to the boot log while setup is not complete. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Where spans are sent (OTLP, batched). | No telemetry at all, unless one of the two below is set. |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | The traces' own endpoint, which the exporter reads ahead of the general one. It counts as an endpoint by itself. | As above. |
| `OTEL_CONSOLE` | `1`, and no other value, prints every span to the terminal. An endpoint wins over it. | Nothing is printed, in development too. |

`SITEMAP_HOST` is the old name of `PUBLIC_HOST` and is read when `PUBLIC_HOST` is not set or blank; by itself it turns on everything `PUBLIC_HOST` does (host authorisation and HTTPS included), which was accepted because it is the same fact under an older name and no production site exists that set it for the sitemap alone. `config/deploy.yml` sets no `PUBLIC_HOST`: a Kamal deploy from it as it stands forces nothing until someone adds the variable (its comment says so; the roadmap lists it).

**Why the address is a variable and not a setting.** Which hosts are refused and whether HTTPS is forced are decided while the application starts, before the database is read, and a wrong value typed into a Settings screen would refuse every request with no screen left to correct it on. A wrong variable is corrected where it was set, and the boot stops on a value that is not an address. The wizard (part four) will show the value read-only and say where it comes from.

## The site's address: `SiteAddress`

`SiteAddress` (`lib/site_address.rb`) parses the variable once. `SiteAddress.current` is the first non-blank of `SiteAddress::VARIABLES` (`PUBLIC_HOST`, `SITEMAP_HOST`), memoised for the life of the process; `SiteAddress.parse(value, source:)` is the same for a value handed in. An address answers `configured?`, `origin` (`https://docs.example.org`, `http://localhost:3030`; no path, no trailing slash, no default port; nil when not configured), `host`, `port`, `https?` and `url_options` (for `url_for`; `{}` when not configured, and the protocol is the address's own, so an http address gives http links). It is frozen. `PublicSite::Urls.configured_host` is `SiteAddress.current.origin`, and nothing else in the application reads either variable.

The file lives in `lib/` and uses nothing of Rails, and `config/application.rb` requires it explicitly although `lib/` is autoloaded (`config.autoload_lib`): `config/environments/production.rb` runs before any autoloading is set up. The spec put it in `app/values`; the environment file cannot reach a class there.

**Accepted and normalised.** A blank value is "not configured", never an error (a checkout has none). Blanks around the value are stripped (a trailing newline from a file is not an error). The scheme and the host are lower-cased, a path, query and fragment are dropped, the scheme's default port is dropped, ONE trailing dot of the host is dropped (no request's `Host` would match it), and an IPv6 literal keeps its brackets, as `config.hosts` and `url_for` want it.

**Refused**, with `SiteAddress::Invalid`: a value with no `http` or `https` scheme or no host; user info, also an empty one (`https://@host`: an origin has none, and dropping it silently would leave a password in the environment unnoticed); a port outside 1..65535; any whitespace or control character inside the value (a newline would also break the log line); a host that is not ASCII (write it in its `xn--` form; nothing is converted); and a host that is not a host name. The grammar is dot-separated labels of letters, digits and inner hyphens, none empty (an IPv4 address is that too), or brackets holding what `IPAddr` reads as IPv6. It is not pedantry: Rails reads a `config.hosts` entry that starts with a dot as "every subdomain", so `https://.example.org` would open what the boot line calls refused, and `a..b`, `*.example.org` or `%41.example` match no request at all, which locks everyone out. An underscore in a host name is refused; a label of digits is not range-checked (`999.1.1.1` parses).

**The refusal never repeats the value, and carries no cause.** The message is `<VARIABLE> must be the site's address with its scheme, for example https://www.example.org`, naming the variable the value came from. It goes to the boot log, and a value someone typed as `https://user:password@…` would put the password there (Task 1's review found exactly that in the first version, which printed `got: "…"`). Ruby prints the causes of an uncaught error, and `URI::InvalidURIError`'s and `IPAddr`'s messages are the raw value, so `Invalid` is never raised from inside a `rescue`: a rescue in that file answers nil or false and the raise comes after it (`test/lib/site_address_test.rb`: "the message names the variable the value came from and never repeats the value", "the refusal carries no cause: an uncaught one prints nothing of the value").

**In tests** `with_site_address(value) { … }` (`test/support/site_address_helper.rb`, included in every test case) is the one way to set the address: it sets `PUBLIC_HOST` (nil for "not configured"), clears `SITEMAP_HOST` so the older name cannot answer instead, calls `SiteAddress.reset!` on both sides and puts both variables back, also when the block raises. A test that sets `ENV` itself leaves its address, memoised, to every test that runs after it in the same worker.

## What production does with it: `HostSettings`

`config/environments/production.rb` decides nothing about hosts, HTTPS or the address in mailed links itself: it calls `HostSettings.apply(config)` (`lib/host_settings.rb`) and that is all. Development and test never call it, so they answer any host. `apply(config, address: SiteAddress.current, env: ENV)` takes its two inputs as parameters so a test hands in its own, and sets:

- **`config.hosts`** to the address's host when one is configured; without one it is left as it is (empty in production: any host is answered), never emptied. **The match is exact**: an address of `example.org` refuses `www.example.org`, any other subdomain and a look-alike suffix; case and a port in the request's `Host` do not matter. A forwarded host that is not the site's is refused although the `Host` is right.
- **`config.host_authorization`** and the redirect's exclusion to `HostSettings::HEALTH_CHECK`: the path `/up` exactly (`/up?x=1` is the health check; `/up/`, `/UP`, `/up.json` and `/up/x` are ordinary requests). The proxy asks it by IP and over plain HTTP, so it is left out of both the refusal and the redirect, and gets no `Secure` cookie.
- **`config.force_ssl`** to the address's own scheme: there is no `FORCE_SSL` variable, one fact has one place. An https address gives the redirect (a GET with 301, any other method with 308, keeping its method), the `Secure` cookie and HSTS; an http address (a private network, a trial on localhost) is served as it is, with none of the three, also for a request that did arrive over HTTPS.
- **HSTS** to `HostSettings::HSTS`, which is exactly `max-age=31536000`: one year, no `includeSubDomains`, no `preload`, written out and not left to Rails' default, which is two years with subdomains (the spec's sentence that "Rails' defaults" were one year without subdomains was wrong about Rails; its values stand). `includeSubDomains` would force HTTPS, in every visitor's browser and for as long as the header says, on whatever else the host runs under the same name (mail, an old intranet on plain HTTP), and a server cannot take that back once a browser has seen it. The cost is weaker HSTS for a site that wants its subdomains covered.
- **`config.assume_ssl`** to `ASSUME_SSL == "1"`: `true`, `0`, an empty value and `" 1"` are all no. A proxy that ends TLS and sends no `X-Forwarded-Proto` makes every request look plain, so under an https address every request is redirected to the address it already asked for, forever, unless `ASSUME_SSL=1`. `ASSUME_SSL=1` does not open the door to another host: host authorisation stands ahead of it.
- **`config.action_mailer.default_url_options`** to the address's `url_options` (`{}` without one). The literal `example.com` is gone.

The middleware order is Rails' own (`HostAuthorization`, then `AssumeSSL`, then `SSL`), which is why plain HTTP for a foreign host is a 403 with no `Location` and never a redirect to that host: there is no open redirect. `test/lib/host_settings_test.rb` holds the configuration and `test/integration/host_settings_test.rb` the behaviour, through a stack built in Rails' order ("plain HTTP for another host is refused, never redirected to that host", "under an https address another host is refused, www. and a subdomain included", "behind a proxy that does not say so, a plain request is redirected unless ASSUME_SSL=1", "the health check is answered over plain HTTP by IP: no redirect, no refusal, no Secure cookie", "under an https address its own host is answered, with HSTS of one year and nothing more").

**What the boot says.** A wrong `PUBLIC_HOST` refuses every request with a 403 that says nothing in production, so the boot log is where a person reads which address is answered. The initializer `content_spiel.host_announcement` in `config/application.rb` runs in production only and logs each line of `HostSettings.announcement(address, env)` (an Array of lines, not one string) at info:

- `[ContentSpiel] Serving https://docs.example.org. Other host names are refused; plain HTTP is redirected.`
- or `[ContentSpiel] Serving http://localhost:3030. Other host names are refused. The connection is not encrypted.`
- then `[ContentSpiel] Only the exact host name docs.example.org is answered: not www.docs.example.org, not any other subdomain.`, or for a name nobody puts `www.` in front of (an IP address, `localhost`, any single label) `[ContentSpiel] Only the exact host name localhost is answered.`
- without an address, the one line `[ContentSpiel] PUBLIC_HOST is not set. Any host name is accepted and nothing is forced to HTTPS.`
- with `ASSUME_SSL=1`, configured or not, `[ContentSpiel] ASSUME_SSL=1: every request is taken as HTTPS, whatever the proxy says.`
- and with `ASSUME_SSL=1` and an http address one more, which says that the two contradict: `[ContentSpiel] ASSUME_SSL=1 contradicts the http address in PUBLIC_HOST: nothing is redirected to HTTPS and no HSTS is sent, yet every request counts as encrypted, so redirects point to https and System status reports HTTPS. Set PUBLIC_HOST to the https address, or remove ASSUME_SSL.`

With `RAILS_LOG_LEVEL=warn` none of these is printed. The initializer runs for every production process, `bin/rails runner`, a console and a rake task included. It has no automated test (it runs in production only); the lines are tested as `announcement`'s return value, and the boots that proved the wiring are in the build's reports.

**The secret check.** The same initializer calls `HostSettings.require_secret!(ENV, credentials: Rails.application.credentials)` first, unless `SECRET_KEY_BASE_DUMMY` is set (the Dockerfile's asset precompilation, which has no secret and needs none). Rails' own error for a missing secret sends the reader to `bin/rails credentials:edit`, which a container has no key for; `HostSettings::MissingSecret` names the variable and `bin/rails secret`, and never holds a value. It decides as Rails does, in Rails' order:

- the variable holds a secret: accepted, and the credentials are NOT read, so a broken credentials file cannot stop a boot that needs nothing from it;
- the variable is set but blank (a compose file's `SECRET_KEY_BASE=${SECRET_KEY_BASE}` with nothing behind it): refused as "set but empty", also when the credentials hold a secret, because Rails would take the blank value for the secret and fail on it with its own message;
- the variable is not set: the credentials' `secret_key_base` decides. The spec asked for the variable alone; a secret in the credentials is accepted too because the Kamal boilerplate this repository ships (`config/deploy.yml`: `RAILS_MASTER_KEY`) supplies it exactly that way.

Credentials that cannot be read (a master key that does not open the file, a key of the wrong length, a file that is not YAML) are "could not be read": the message adds the error's class, never its text, and says to check `RAILS_MASTER_KEY`; `MissingSecret` has no cause. The rescue is every `StandardError` around the one call `credentials.secret_key_base`, which keeps `lib/` free of Rails' error classes and fails closed: its outcome is always a refusal. The cost is a vaguer message for someone whose master key is what is wrong.

The initializer is `after: :initialize_logger, before: :initialize_cache`. `after:` alone does not place it early (an application's own initializers are sorted after every engine's unless a `before:` pulls them forward), and Rails first reads `secret_key_base` at the very end of boot today, but any initializer or gem that asked for a key generator earlier would raise Rails' message first. The environment file, which parses `PUBLIC_HOST`, loads before `initialize_logger`, so a value that is not an address stops the boot earlier still.

## Addresses a public page prints

`og:url`, every `hreflang` alternate and `<link rel="canonical">` are built by `PublicSite::Urls`, whose host `PublicController#public_urls` sets to the configured origin, so they carry the site's address whatever `Host` (or `X-Forwarded-Host`, which wins over `Host` in Rails) a request named. A public response is the same for everyone and cacheable: a host written into it from the request is served to the next visitor too. With no address configured they fall back to the request's origin, as CS Studio's "Copy address" does. The canonical link is the page's or post's own address in the language shown, without a query string; a page that is not found has none, and a preview has none and keeps the request's origin and its `/preview` addresses (`PreviewController` is untouched) (`test/integration/public_head_address_test.rb`: "under a foreign Host, og:url, every hreflang and the canonical link carry the configured address", "the canonical link is the page's own address in the language shown, without the query", "a page that is not found has no canonical link, and names no foreign host", "a preview keeps the request's origin and its /preview addresses, and has no canonical link").

**The guard** is `test/lib/public_address_guard_test.rb`: no public view, component, helper or controller asks the request where it was sent (`request.base_url`, `request.host`, `request.original_url` and the rest of that family, the Host headers by name) or calls a `..._url` helper. What it scans is derived, as `test/lib/public_readers_test.rb` derives it: `PublicController`, the controllers that descend from it and the concerns they include, their view folders, the public layout, `layouts/public`, `views/shared`, every helper outside `admin/` and every component outside `app/components/admin`. Two lines are allowed, each by its file and its text with the reason, and an entry that matches no line fails: the `request.base_url` fallback in `PublicController#public_urls`, and the `request.original_url` fallback of `og:url`, reached only by a preview post that no published copy lists.

**What the guard does not cover.** It is a source grep: an address handed in from elsewhere, `url_for(..., only_path: false)` and a `PublicSite::Urls` made with another host are invisible to it, and the integration test is the guard that really holds. And it looks at what a page prints, not at response headers: **a redirect's `Location` follows the request** (`redirect_to` in `PagesController`: the default language's redundant prefix, a moved record). That was left as it is by a ruling: with an address configured a foreign `Host` is refused before any redirect is made, so the request's host IS the address's, and without one the request's host is all there is.

**The ETag.** With no address configured the public ETag includes the request's origin (`PublicController#origin_etag_key`, read from the `public_urls` instance so the guard's allow-list stays at one `request.base_url` line): the fallback writes that origin into the head, and without it a 304 could confirm a body printed under another host. With an address configured the key is not added at all, so the ETag is the same under every host and is built from exactly the keys it had (`test/integration/public_head_address_test.rb`: "with no address configured an ETag obtained under one Host is not confirmed under another, and is under the same one", "with no address configured the scheme and the port are part of it too", "with an address configured the ETag is the same under every Host, and a 304 is given under any").

**The homepage.** The localised homepage's canonical link, `og:url` and `hreflang` are `/de/`, with the slash, and that is also the sitemap's `<loc>`; `/de` answers 200 with the same page as well, and only the canonical link says which of the two is the address. No redirect and no loop; a redirect from one to the other would be a routing change and is on the roadmap. The default language's homepage is `/` in the link and the bare origin in the sitemap's `<loc>` (`sitemap_generator` joins "/" onto the host): one address, two spellings ("the homepage in another language: the three agree on /de/, and that address answers 200 with the same page, as /de does", "the sitemap lists the homepage in each language at the address its canonical link names").

## The reset mail

`PasswordsMailer.reset(user, origin: nil)` builds its link in one place, the private `reset_url`, which both parts of the mail call (memoised: every call of `password_reset_token` signs a new token, and the two parts used to carry two different links). Where the link points:

- the site's configured address whenever there is one, whatever `origin` says;
- otherwise, **in development and test only**, the origin of the request that asked (`Admin::PasswordsController#create` hands over `request.base_url` as a String, because a job delivers the mail), parsed by `SiteAddress.parse` and used for its origin and nothing else; a value that is not an origin is no origin;
- otherwise **no mail**: `mail` is not called, Action Mailer delivers nothing, and the log says `[ContentSpiel] A password reset mail was not sent: no site address is known. Set PUBLIC_HOST.`, a line that names no person and holds no token. The request page answers with the same words either way: it must not reveal anything, so an owner learns of it from the log, from System status ("Site address", "Outgoing mail") or from the missing mail. The Mail part will make the page say so; until then the console fallback of the "Outgoing mail" check is the way in.

**Why the request's origin is used nowhere else.** It is whatever `Host` the request named, and a site with no address configured refuses no host. Anyone could ask for a reset of an address they know under a host of their own, and the account's owner would be mailed a valid token on a link to that host (password-reset poisoning). The spec had the request's origin as the fallback in every environment; Task 4's implementer named the hole and it was closed before the review. `PasswordsMailer.request_origin_used?` is the one place the decision is made and both the mailer and the controller ask it; it is `env.local?`, an ALLOW-list, never `!env.production?`: a staging, preview or demo environment is exactly the kind that sits on a public address without `PUBLIC_HOST`, and host authorisation is set up from `production.rb` alone, so an environment nobody named must fail closed. With an address configured, and in production without one, the origin is not put into the job's arguments at all.

Three things that are easy to miss. **The address is read in the process that performs the job**: a job container separate from the web container needs `PUBLIC_HOST` too, or it builds no mail. **Active Job logs a job's arguments**, so in development and test the origin is in the job's own lines and in the queue's row: an address, never a token. And `reset_url` passes `port: nil` ahead of the address's options, because `url_for` merges what it is given over `default_url_options` and an address without a port would otherwise inherit the environment's (development's 3000) (`test/mailers/passwords_mailer_test.rb`: "in production with no address configured no mail is built, whatever origin is handed over, and the log says why", "the request's origin is used in development and in test, and in no other environment", "nothing of the environment's default url options reaches the link", "an origin that is not an origin is no origin: no mail, the same line, and the value is not repeated"; `test/controllers/admin/passwords_controller_test.rb`: "create with a site address configured hands the mailer no origin, whatever Host the request named", "create in production with no address configured hands over no origin, sends no mail and answers the same").

## The reset link: the token is in no address

The mailed link is `<origin>/<admin>/password/edit#<token>`. A browser sends what follows the `#` to no server, so the token is in no request line, no span and no proxy's access log; the proxy's log is the one this application could never have filtered, which is why masking the old path was not enough.

- **`GET <admin>/password/edit`** (`admin_edit_password`, `Admin::PasswordsController#edit`) draws the same page for everyone: no lookup, no parameter read, and a `token` handed to it as a query parameter is ignored, since that would be a token in an address. The form is drawn `hidden` by the server and its hidden `token` field empty, so nothing flashes before the script runs and without JavaScript a form that can only fail is not shown beside the `<noscript>` line.
- **The script** is the top-level Stimulus controller `reset-token` (`app/javascript/controllers/reset_token_controller.js`), not an admin one: the `product` layout loads only the `application` entry point, and `controllers/index.js` registers everything except `controllers/admin/*`, so an admin controller would never connect on this page. It moves `location.hash` into the field, removes the fragment from the address with `history.replaceState`, shows the form and focuses its field; with no token it shows "This link is incomplete…" with a way to a new link. A fragment is not sent, so nothing on the server can tell a truncated link from a missing one, and the message covers both. The token is not percent-decoded: a token is URL-safe, and a link a mail program has spoilt fails verification and gets the expired state.
- **The token is kept nowhere but the field, and not past the page.** Writing a hidden input's `value` writes its attribute, so a copy of the document holds it: Turbo's snapshot (the `product` layout does use Turbo Drive; the token was seen there before this was closed) and the browser's back/forward cache. The field is emptied on `turbo:before-cache` (the field only, since the page is still on screen while the next one is drawn) and on `pagehide` (the field and the message, because the browser's own cache restores a page without connecting anything again). Neither comes before the form's own request has been built. A page come back to has no token and says the link is incomplete, which is true of it.
- **`PATCH <admin>/password`** (`admin_update_password`, `#update`) reads the token from the body, where `filter_parameters` (`:token`) masks it in the log. Tampered, lapsed, used, blank, missing, or a list or a hash where a string belongs: one answer, the "expired" state of the request page, nothing written. So whether a link is good is answered when the form is sent, not when it is opened. A refused password is a 422 of the form itself, with the token in the hidden field of that one response: rendered, not redirected, because a redirect could carry the token only in an address or in the session.
- **`Cache-Control: no-store`** on `edit`, `legacy` and `update`: the empty page and the refused form share an address in the address bar, and neither may be answered from a copy of the other.
- **The old link**, `GET <admin>/password/<token>/edit`, is `#legacy`: a 302 to the page WITHOUT the token. A server cannot hand a browser a fragment it was never sent and must not repeat the token in another address; the page then says the link is incomplete. Tokens live fifteen minutes, so the loss is the mails on their way during one deploy. The old `PATCH <admin>/password/<token>` has no route and is a 404.
- **`OldResetAddress`** (`lib/old_reset_address.rb`), a Rack middleware inserted at position 0 in `config/application.rb`, is why the old addresses log no token. A route that only redirects does not keep a path out of the log: Rails writes the first line of every request (`Started GET "…"`) before the router is asked, and for the old form's address, which has no route, the `RoutingError` line as well; neither is a parameter, so `filter_parameters` reaches neither. The middleware replaces the segment in `PATH_INFO`, `ORIGINAL_FULLPATH`, `REQUEST_URI` and `REQUEST_PATH` by `Telemetry::PathScrubber.scrub`, the same rule that masks it in a span, before anything of Rails has read the request; the router still takes `<admin>/password/[FILTERED]/edit` for the old link. Not covered and not coverable from the application: the proxy's access log, which has the old path as the client sent it. Where telemetry is on, OpenTelemetry's Rack middleware puts itself ahead of it and reads the path as it came; its spans are scrubbed on their way out.

The rate limit (on `create` only), the audit event (`user.updated`, the user as actor) and the ending of every session (`Users::UpdatePassword`, `keep_acting_session: false`) are as they were. The cost of the whole design: resetting a password needs JavaScript, which CS Studio needs everywhere else.

Tests: `test/controllers/admin/passwords_controller_test.rb` ("edit reads no user: the page is the same with no account at all behind it", "edit ignores a token handed to it as a parameter: it reaches neither the form nor a redirect", "the old address redirects to the page with no token in the Location, whatever stood in its place", "the form's page is kept by no cache: the empty one, the refused one and the redirects", "nothing logged for the form's requests holds the token: accepted, refused, and with a bad password", "nothing logged for a request to the old addresses holds the token"), `test/mailers/passwords_mailer_test.rb` ("the token is the link's fragment: the address a server is asked for holds none"), `test/lib/old_reset_address_test.rb` ("it stands ahead of every middleware of Rails, the request logger and the error pages among them") and the browser's side in `test/system/admin/password_reset_test.rb` ("the mailed link opens the form, the token leaves the address, and the new password signs in", "the token does not outlive the page: not in Turbo's snapshot, and not after Back"; the snapshot assertion reads a Turbo internal, `Turbo.session.view.snapshotCache`, and fails loudly if its shape changes). A log test swaps the loggers through `LogCapture` (`test/support/log_capture.rb`): `REQUEST_LOGGERS` includes `action_dispatch.logger`, an entry of the application's memoised Rack environment and not a class's logger, which is where the `RoutingError` line goes; swapping `Rails.logger` alone sees neither it nor the controller's lines.

## Telemetry

`config/initializers/opentelemetry.rb` asks `Telemetry.exporter_kind(env, rails_env)` (`lib/telemetry.rb`) where the spans go, first match first:

1. `:memory` in the test environment, whatever is set (`Rails.application.config.x.otel_test_exporter`, the exporter inside the scrubber's wrapper, so what a test reads is what a backend would be sent);
2. `:otlp` when either `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` or `OTEL_EXPORTER_OTLP_ENDPOINT` is not blank (`Telemetry::ENDPOINTS`), batched;
3. `:console` when `OTEL_CONSOLE` is exactly `1` (`true`, `yes` and `" 1"` are not), printed at once;
4. `:none` otherwise, development and production alike: `OpenTelemetry::SDK.configure` is not called, no instrumentation is installed, no span is made, and `OpenTelemetry.tracer_provider` stays the API's own no-op.

Case 4 used to be the console. A production container with no endpoint printed every span to its log: about 49,000 lines for 60 requests, with the path of every request in them, a password-reset token included. Hence the default is nothing, and printing is asked for by its own variable and one value, so that no environment prints because something else was left unset. `bin/dev` and `bin/rails server` print no span unless started with `OTEL_CONSOLE=1`.

**The scrubber** (`Telemetry::PathScrubber`, `lib/telemetry/path_scrubber.rb`) has two rules for the attributes that hold a request's address (`url.path`, `url.query`, `http.target`, `url.full`, `http.url`):

- **The token segment of the old reset routes** is replaced by `[FILTERED]`. The rule is wider than the two routes, because a path is recorded before the router has said whether it is one of ours: the segment after `<admin>/password/` is filtered wherever something follows it, and as a last segment unless it is exactly `new` or `edit`. So a link a mail program has spoilt (a bracket taken into it, a slash doubled, which the router squeezes) is filtered too. The pattern is built from `ContentSpiel::ADMIN_PATH`, read when a path is scrubbed, not when the file loads.
- **No query string leaves in a span**, whatever its parameters are called: `url.query` is replaced whole when it is not empty, and an address is cut at its first `?`. The Action Pack instrumentation does put `filter_parameters` over the query, but only once a controller has the request: one answered before any controller (a redirect in the routes, a throttle, a refusal in a middleware) keeps the query as it was sent, and with the older attribute names `http.target` is never rewritten at all. A note's quote travels in a query string as `note_quote`, and a note's text reaches no log line (`docs/reference/notes.md`), so none of it is kept. The cost: a tracing backend shows no query string at all; `http.route` still says which address was asked for. `scrub` itself, the path's rule, keeps a query, because `OldResetAddress` uses it on the request line, where the router needs the query.

**Why it is `on_start` plus a wrapped exporter.** `PathScrubber::Processor` is added first and scrubs the attributes a span starts with (all the Rack instrumentation writes), before any other processor has seen them. It can do nothing for an attribute set later: the SDK (1.13) freezes a span's attributes before it calls `on_finish`, and its `on_finishing` hook is called while the span holds its own mutex, where `set_attribute`, which takes the same mutex, raises. So `PathScrubber::Exporter` wraps whichever exporter is used and scrubs the same attributes in the copy that is exported. Each half has its own test (`test/lib/telemetry/path_scrubber_test.rb`: "an attribute a span starts with is scrubbed, on the span itself and in what is exported", "an attribute set after the start is scrubbed in what is exported, each of the five"; `test/integration/opentelemetry_test.rb`: "no span of a request to a reset address carries the token", "no span carries a query string, of a request answered before a controller or by one"; `test/lib/telemetry_exporter_test.rb`: "with neither variable there is no telemetry, in production and in development", "a development boot with neither variable configures no SDK and prints no span, and OTEL_CONSOLE=1 prints it", which boots development twice in a subprocess, because the table alone would not notice an initializer that ignored `:none`).

Not scrubbed: a span's name (not the path with today's defaults) and an exception event's message. A `RoutingError`'s message quotes the path; the old form's address raises one, but `OldResetAddress` has replaced the segment by then, and the end-to-end test reads events as well as attributes.

`lib/telemetry.rb` and the scrubber are required from `config/application.rb` for a different reason than `site_address`: the initializer hands the scrubber's objects to the SDK for the life of the process, and a file loaded before the autoloader is set up is not unloaded and redefined on a development reload.

## The setup token's log line

While setup is not complete the boot logs `Setup::Token.log_line` (`config/initializers/setup_token.rb`). The derived token can be read nowhere but that log, so the line holds it: `[ContentSpiel] Setup is not complete. Open /setup and enter this setup token: <token>`. A token the host set in `SETUP_TOKEN` is not repeated, since they have it already and a log is kept, shipped and read by more people than the environment is: `[ContentSpiel] Setup is not complete. Open /setup and enter the setup token you set in SETUP_TOKEN.` A blank `SETUP_TOKEN` is no token of the host's (`test/models/setup/token_test.rb`: "with SETUP_TOKEN set the boot's line names the variable and holds no token").

## What a person is told

**System status and the wizard's system check** (`Setup::SystemCheck`, `docs/reference/cs-studio-shell-and-dashboard.md`) begin with two checks. `Setup::SystemCheck.new(address: SiteAddress.current, request_ssl: nil, production: Rails.env.production?, reset_link_from_request: false)`; both screens hand over `request_ssl: request.ssl?` and `reset_link_from_request: PasswordsMailer.request_origin_used?`, a boolean, so the model knows no mailer.

- **Site address**: OK with the origin, or a warning with `PUBLIC_HOST=https://www.example.org` to copy. The warning has two wordings and shows the one that is true where it is read: where a reset mail takes its link from the request (development and test) it says addresses in pages and in reset mails follow the request; everywhere else, and when nobody said (the console), that reset mails are not sent until it is set.
- **HTTPS**: in production only, and only when the caller said how the request came. "Reached over an encrypted connection" is what `request.ssl?` says, and the application sees no connection but the proxy's: it is true when the proxy said so or when `ASSUME_SSL=1` says it for every request, and a proxy that claims HTTPS for a plain connection makes the row say OK about a connection that is not encrypted. Nothing in the application can tell.
- **Outgoing mail** counts as configured only with a host for mailed links, which in production is the site's address: a site with a mail server and no address is told that the address is what is missing, in one sentence ahead of the console fallback (`Setup::SystemCheck::MAIL_NEEDS_ADDRESS`). The Mail part replaces this check.

**The plain-HTTP notice** (`Admin::Ui::InsecureNoticeComponent`): in production, on a request that is not `request.ssl?`, "This connection is not encrypted. Passwords and sessions can be read on the way. Set PUBLIC_HOST to an https address." It can only show where the address is an http one or missing, since an https address redirects plain HTTP before it reaches the application. Three layouts draw it: `product` (sign-in and the password pages) and `setup` (every wizard page; the spec did not ask for the wizard, which takes the setup token and the first account's password) for everyone, and `admin` at the top of `<main>`, outside `#content`, for someone who holds `settings.manage` or `system_status.view`, each of which is enough alone (`Admin::BaseController::INSECURE_NOTICE_PERMISSIONS`; `test/integration/admin/insecure_notice_test.rb`: "in the shell settings.manage alone is enough to be told", "in the shell system_status.view alone is enough to be told", "in the shell someone who holds neither right is told nothing").

## What a change can break silently

- **A `..._url` helper or `request.base_url` in a public view** prints the host the client sent into a cacheable page. The guard refuses the line; it does not see an address handed in from a controller outside the scanned set or a `PublicSite::Urls` built with another host.
- **A host or HTTPS setting written into `production.rb`** (or a `config.hosts <<` in an initializer) is not seen by `HostSettings`' tests, which hand in their own config, and can contradict the boot lines, which are computed from the address and not from the configuration. Add it to `HostSettings.apply`.
- **A new route with a credential in its path or query** is logged by Rails' first request line, by the proxy and, for a path, by every span; `filter_parameters` masks a query parameter in Rails' own log only. Nothing fails. A credential travels in a fragment, a form's body or a header.
- **A new mail** that builds its link from `default_url_options` has no host to build it from on a site without an address (production's are `{}` then); one that takes the request's origin outside development and test reopens reset poisoning. Build a mailed link the way `PasswordsMailer#reset_url` does.
- **A reader of `PUBLIC_HOST` beside `SiteAddress`** gets the raw value: not normalised, possibly with user info, and not refused.
- **A test that sets `ENV["PUBLIC_HOST"]` without `with_site_address`** passes alone and changes the tests after it in the same worker, since the address is memoised.
- **A new span attribute that holds an address** (an instrumentation's own, under another name) is not in `PathScrubber::ATTRIBUTES` and leaves with its query string.
- **Moving `OldResetAddress` down the middleware stack**, or inserting another middleware that logs ahead of it, puts the old link's token back into a log line. `test/lib/old_reset_address_test.rb` holds that nothing but OpenTelemetry's `Rack::Events` stands before it.
- **A second job or web container without `PUBLIC_HOST`** sends no reset mail and says so only in its own log.
- **`includeSubDomains` or `preload` added to HSTS** cannot be taken back for a browser that has seen it.
