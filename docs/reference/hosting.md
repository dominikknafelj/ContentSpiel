## What a host sets

The variables below say what the site is and where it is; outgoing mail takes seven more, and the encryption keys, the database's password and the log level are in "Every variable the code reads", below, which lists every variable the code reads with who sets it, its default and whether it is a secret. None is required for the application to start outside production; in production `SECRET_KEY_BASE` (or a secret in the credentials) is.

| Variable | What it does | Without it |
|---|---|---|
| `PUBLIC_HOST` | The site's address with its scheme, `https://docs.example.org`. Everything in "The site's address" and "HTTPS" below follows from it. | Any host name is answered, nothing is forced to HTTPS, addresses in pages follow the request, and outside development and test no password reset mail is sent. System status and the wizard's system check say so as a warning. |
| `ADMIN_HOST` | Optional, for a backend behind a DMZ: the address, with its scheme, of a host that serves CS Studio alone (`https://studio.example.internal`). | `ASSUME_SSL` | `1`, and no other value, makes every request count as HTTPS (`config.assume_ssl`). Only for a proxy that ends TLS and does not send `X-Forwarded-Proto`. | The proxy's `X-Forwarded-Proto` is believed. Kamal's proxy sends it and Thruster passes it on. |
| `THEME_PATH` | The site's theme folder (`docs/reference/theming.md`). Read when the application starts; a path that is no folder, a folder with anything at its top but `views`, `components`, `assets` and `javascript`, or a folder that holds a file the theme contract does not name, stops the boot with a message that names the variable and the file ("The theme", below). **Jobs and images.** Two variables decide where the background jobs run, and images depend on both, because an image's widths are made by a job (`docs/reference/media.md`, "Widths and the generation"). `SOLID_QUEUE_IN_PUMA` (any value) starts Solid Queue's supervisor inside the web server's Puma process (`config/puma.rb`); `config/deploy.yml` sets it. Without it nothing performs a job unless `bin/jobs` runs somewhere else, so an uploaded image keeps its preview and never gets a width, mail is never sent and the sweeps never run; a host that runs `bin/jobs` apart from the web process needs no `SOLID_QUEUE_IN_PUMA` and starts the same two workers from `config/queue.yml`. `JOB_CONCURRENCY` (default 1) is the number of processes of the `default` worker (three threads each: mail, sweeps, notes, the trash); it does not change the `images` worker, which is always ONE process with ONE thread, polling every 2 seconds, so a batch of uploads takes a single core and queues behind itself, never in front of mail. There is no variable for the images worker; its two jobs are the widths (`Media::RenditionJob`) and the backfill that queues the widths of images from before this existed, at most 300 images every ten minutes. On a host with several cores and many uploads, raise nothing: a second `images` process would make libvips run twice at once, which a small machine does not want. An idle site pays one more poll every two seconds for the `images` worker. A job that cannot run leaves the image on its preview and System status counts it ("Images"). AVIF needs an encoder libvips does not bring by itself: the `Dockerfile` installs `libheif-plugin-aomenc` beside `libvips` (Debian's package is decoders only, and without it writing AVIF fails with "heifsave: Unsupported compression"); a host built another way without it shows AVIF as unavailable in Settings → Images, which is `ImageSettings`' own probe, and stays on WebP.

**Images and the proxies in front of the site.** The largest upload is a setting (Settings → Images, 1 to 50 MB, default 10), so the proxy must let a 50 MB request body through: Thruster's `MAX_REQUEST_BODY` defaults to 0, no limit, and kamal-proxy buffers a request body up to 1 GB by default (`proxy.buffering.max_request_body` in `config/deploy.yml` lowers it, and `config/deploy.yml` sets none); a proxy or load balancer of the host's own (nginx's `client_max_body_size` is 1 MB) must be raised to match the largest upload set. A library image is served as `Cache-Control: public, immutable` for a hundred years at an address that never changes (`docs/reference/media.md`, "Delivery"), so **a CDN is optional and needs no setting**: any cache in front of the site caches an image by those headers, and a purge is never needed for an image, because an address names one file for ever. Thruster's own HTTP cache already honours them (64 MB, `CACHE_SIZE`, and no single item over 1 MB, `MAX_CACHE_ITEM_SIZE`, so the widest widths are served by Rails each time unless that is raised); it is worth raising only for a site with no CDN and a busy image gallery. Thruster's `X_SENDFILE_ENABLED` is on already and does nothing for images: Active Storage's proxy controllers stream through Rack and do not send the header, and the Disk service is a local read. An original is never public, so there is no private file for a CDN to be kept from.

**Outgoing mail** takes seven more, all optional: `MAIL_SMTP_SERVER`, `MAIL_SMTP_PORT`, `MAIL_SMTP_SECURITY` (`starttls`, `tls`, or `none` for a host's own relay without a login), `MAIL_SMTP_USERNAME`, `MAIL_SMTP_PASSWORD`, `MAIL_SENDER_NAME` and `MAIL_SENDER_ADDRESS`. Each overrides its field of Settings → Mail alone, a variable set but blank counts as not set, a value is never printed, logged or rendered, and `MailSettings` is their one reader (`docs/reference/mail.md`, "The one reader"). Without them the settings are the site's own, typed in the wizard or in Settings. A variable changed at a deploy makes mail "Saved, not tested" until a send succeeds with it, because verification is a fingerprint of the settings in effect. In production mail also needs `PUBLIC_HOST`: without an address it is "Not set up", since no link could be mailed.

`config/deploy.yml` holds `PUBLIC_HOST` as a commented line under `env.clear`, with a placeholder address, and the comment at its proxy section says to uncomment it: a Kamal deploy from the file as it stands still answers any host and forces nothing (the final review found the comment pointing at an entry that was not there; the roadmap lists what is left).

**Why the address is a variable and not a setting.** Which hosts are refused and whether HTTPS is forced are decided while the application starts, before the database is read, and a wrong value typed into a Settings screen would refuse every request with no screen left to correct it on. A wrong variable is corrected where it was set, and the boot stops on a value that is not an address. The wizard (part four) will show the value read-only and say where it comes from.

## The site's address: `SiteAddress`

`SiteAddress` (`lib/site_address.rb`) parses the variable once. `SiteAddress.current` is `PUBLIC_HOST` (`SiteAddress::VARIABLES`; blank is not configured), memoised for the life of the process; `SiteAddress.parse(value, source:)` is the same for a value handed in. An address answers `configured?`, `origin` (`https://docs.example.org`, `http://localhost:3030`; no path, no trailing slash, no default port; nil when not configured), `host`, `port`, `https?` and `url_options` (for `url_for`; `{}` when not configured, and the protocol is the address's own, so an http address gives http links). It is frozen. `PublicSite::Urls.configured_host` is `SiteAddress.current.origin`, and nothing else in the application reads `PUBLIC_HOST`.

`SiteAddress.admin` is the second address, CS Studio's own, parsed from `ADMIN_HOST` by the same `parse` (`source: "ADMIN_HOST"`, so a refusal names that variable), memoised beside `current` and dropped with it by `reset!`. Unset or blank it is not configured, and everything behaves as with one host. `SiteAddress` is its one reader; the places that ask it are `HostSettings` (the hosts, the refusals, the boot line), `HostRouteConstraint` (per request), `ApplicationMailer#link_origin`, `Admin::ApiTokensController#mcp_url`, `SignIn::RelyingParty`, `PublicSite::Urls.studio_link` and `Setup::SystemCheck` ("Behind a DMZ").

The file lives in `lib/` and uses nothing of Rails, and `config/application.rb` requires it explicitly although `lib/` is autoloaded (`config.autoload_lib`): `config/environments/production.rb` runs before any autoloading is set up. The spec put it in `app/values`; the environment file cannot reach a class there.

**Accepted and normalised.** A blank value is "not configured", never an error (a checkout has none). Blanks around the value are stripped (a trailing newline from a file is not an error). The scheme and the host are lower-cased, a path, query and fragment are dropped, the scheme's default port is dropped, ONE trailing dot of the host is dropped (no request's `Host` would match it), and an IPv6 literal keeps its brackets, as `config.hosts` and `url_for` want it.

**Refused**, with `SiteAddress::Invalid`: a value with no `http` or `https` scheme or no host; user info, also an empty one (`https://@host`: an origin has none, and dropping it silently would leave a password in the environment unnoticed); a port outside 1..65535; any whitespace or control character inside the value (a newline would also break the log line); a host that is not ASCII (write it in its `xn--` form; nothing is converted); and a host that is not a host name. The grammar is dot-separated labels of letters, digits and inner hyphens, none empty (an IPv4 address is that too), or brackets holding what `IPAddr` reads as IPv6. It is not pedantry: Rails reads a `config.hosts` entry that starts with a dot as "every subdomain", so `https://.example.org` would open what the boot line calls refused, and `a..b`, `*.example.org` or `%41.example` match no request at all, which locks everyone out. An underscore in a host name is refused; a label of digits is not range-checked (`999.1.1.1` parses).

**The refusal never repeats the value, and carries no cause.** The message is `<VARIABLE> must be the site's address with its scheme, for example https://www.example.org`, naming the variable the value came from. It goes to the boot log, and a value someone typed as `https://user:password@…` would put the password there (the first version did exactly that: it printed `got: "…"`). Ruby prints the causes of an uncaught error, and `URI::InvalidURIError`'s and `IPAddr`'s messages are the raw value, so `Invalid` is never raised from inside a `rescue`: a rescue in that file answers nil or false and the raise comes after it (`test/lib/site_address_test.rb`: "the message names the variable the value came from and never repeats the value", "the refusal carries no cause: an uncaught one prints nothing of the value").

**In tests** `with_site_address(value) { … }` (`test/support/site_address_helper.rb`, included in every test case) is the one way to set the address: it sets `PUBLIC_HOST` (nil for "not configured"), calls `SiteAddress.reset!` on both sides and puts the variable back, also when the block raises. `with_admin_address(value) { … }` does the same for `ADMIN_HOST` and leaves `PUBLIC_HOST` as it is, so it nests inside `with_site_address` (`test/lib/site_address_test.rb`: "with_admin_address puts the variable and the memo back, also when the block raises"). A test that sets `ENV` itself leaves its address, memoised, to every test that runs after it in the same worker. And the suite does not depend on the shell: `test/test_helper.rb` removes `PUBLIC_HOST` and `ADMIN_HOST` from `ENV` before the application is loaded and resets the memo, once, ahead of the parallel workers' fork, because five tests that expect "no address" failed for whoever had `PUBLIC_HOST` exported, and an exported `ADMIN_HOST` would turn the host constraints on for every test.

## What production does with it: `HostSettings`

`config/environments/production.rb` decides nothing about hosts, HTTPS or the address in mailed links itself: it calls `HostSettings.apply(config)` (`lib/host_settings.rb`) and that is all. Development and test never call it: test answers any host, and development keeps Rails' own list (`.localhost`, `.test` and every IP address), so a made-up name is refused there too. `apply(config, address: SiteAddress.current, admin: SiteAddress.admin, env: ENV)` takes its inputs as parameters so a test hands in its own. With an admin address it first refuses, before anything is set, a pair that cannot work, with `SiteAddress::Invalid` (which stops the boot, and names the variables, never a value):

- `ADMIN_HOST needs PUBLIC_HOST: set the site's public address too.` `config.hosts` is set only from a public address, so the admin host alone would be answered nowhere it is meant to be.
- `ADMIN_HOST must be another host name than PUBLIC_HOST's.` On one name every public route would be a 404.
- `ADMIN_HOST and PUBLIC_HOST must both be https, or both http.` `force_ssl` is one setting for the process: an http admin host beside an https public one would be redirected to an https address it does not serve.

Then it sets:

- **`config.hosts`** to the address's host when one is configured, and the admin address's host beside it when there is one; without one it is left as it is (empty in production: any host is answered), never emptied. **The match is exact**: an address of `example.org` refuses `www.example.org`, any other subdomain and a look-alike suffix; case and a port in the request's `Host` do not matter. A forwarded host that is not the site's is refused although the `Host` is right.
- **`config.host_authorization`** and the redirect's exclusion to `HostSettings::HEALTH_CHECK`: the path `/up` exactly (`/up?x=1` is the health check; `/up/`, `/UP`, `/up.json` and `/up/x` are ordinary requests). The proxy asks it by IP and over plain HTTP, so it is left out of both the refusal and the redirect, and gets no `Secure` cookie.
- **`config.force_ssl`** to the address's own scheme: there is no `FORCE_SSL` variable, one fact has one place. An https address gives the redirect (a GET with 301, any other method with 308, keeping its method), the `Secure` cookie and HSTS; an http address (a private network, a trial on localhost) is served as it is, with none of the three, also for a request that did arrive over HTTPS.
- **HSTS** to `HostSettings::HSTS`, which is exactly `max-age=31536000`: one year, no `includeSubDomains`, no `preload`, written out and not left to Rails' default, which is two years with subdomains (the spec's sentence that "Rails' defaults" were one year without subdomains was wrong about Rails; its values stand). `includeSubDomains` would force HTTPS, in every visitor's browser and for as long as the header says, on whatever else the host runs under the same name (mail, an old intranet on plain HTTP), and a server cannot take that back once a browser has seen it. The cost is weaker HSTS for a site that wants its subdomains covered.
- **`config.assume_ssl`** to `ASSUME_SSL == "1"`: `true`, `0`, an empty value and `" 1"` are all no. A proxy that ends TLS and sends no `X-Forwarded-Proto` makes every request look plain, so under an https address every request is redirected to the address it already asked for, forever, unless `ASSUME_SSL=1`. `ASSUME_SSL=1` does not open the door to another host: host authorisation stands ahead of it.
- **`config.action_mailer.default_url_options`** to the address's `url_options` (`{}` without one). The literal `example.com` is gone.

The middleware order is Rails' own (`HostAuthorization`, then `AssumeSSL`, then `SSL`), which is why plain HTTP for a foreign host is a 403 with no `Location` and never a redirect to that host: there is no open redirect. `test/lib/host_settings_test.rb` holds the configuration and `test/integration/host_settings_test.rb` the behaviour, through a stack built in Rails' order ("plain HTTP for another host is refused, never redirected to that host", "under an https address another host is refused, www. and a subdomain included", "behind a proxy that does not say so, a plain request is redirected unless ASSUME_SSL=1", "the health check is answered over plain HTTP by IP: no redirect, no refusal, no Secure cookie", "under an https address its own host is answered, with HSTS of one year and nothing more").

**What the boot says.** A wrong `PUBLIC_HOST` refuses every request with a 403 whose page says nothing in production, so the log is where a person finds out: the boot's lines say which address is answered, and for each refusal Rails itself logs `Blocked hosts: <name>` at error, which is what is left to read when the boot's lines are not printed. The initializer `content_spiel.host_announcement` in `config/application.rb` logs, in production only, each line of `HostSettings.announcement(address, env)` (an Array of lines, not one string) at info (the same initializer reads the theme folder in every environment and logs the theme's line outside test, "The theme" below):

- `[ContentSpiel] Serving https://docs.example.org. Other host names are refused; plain HTTP is redirected.`
- or `[ContentSpiel] Serving http://localhost:3030. Other host names are refused. The connection is not encrypted.`
- then `[ContentSpiel] Only the exact host name docs.example.org is answered: not www.docs.example.org, not any other subdomain.`, or for a name nobody puts `www.` in front of (an IP address, `localhost`, any single label) `[ContentSpiel] Only the exact host name localhost is answered.`
- then, under an https address without `ASSUME_SSL=1`, `[ContentSpiel] If every request is redirected to itself, the proxy in front ends TLS and does not say so (no X-Forwarded-Proto: https): set ASSUME_SSL=1.` That loop is the likeliest way to lock everyone out with a RIGHT address, no screen can be reached in it, and the log is all the person has.
- without an address, the one line `[ContentSpiel] PUBLIC_HOST is not set. Any host name is accepted and nothing is forced to HTTPS.`
- with `ADMIN_HOST`, after the address's lines, `[ContentSpiel] CS Studio is served on https://studio.example.internal alone; https://docs.example.org answers no CS Studio address.`
- with `ASSUME_SSL=1`, configured or not, `[ContentSpiel] ASSUME_SSL=1: every request is taken as HTTPS, whatever the proxy says.`
- and with `ASSUME_SSL=1` and an http address one more, which says that the two contradict: `[ContentSpiel] ASSUME_SSL=1 contradicts the http address in PUBLIC_HOST: nothing is redirected to HTTPS and no HSTS is sent, yet every request counts as encrypted, so redirects point to https and System status reports HTTPS. Set PUBLIC_HOST to the https address, or remove ASSUME_SSL.`

With `RAILS_LOG_LEVEL=warn` none of these is printed. One line is logged at warn, when `RAILS_LOG_LEVEL` is `debug` (`HostSettings.log_level_warning`): `[ContentSpiel] RAILS_LOG_LEVEL=debug: Rails logs every mail it sends in full, a password reset link or an invite link and its token included. Use info or above on a site other people use.` ("The reset link", below, says why.) The initializer runs for every production process, `bin/rails runner`, a console and a rake task included.

**The wiring is tested by booting production.** Every other test of hosts, HTTPS and HSTS hands `HostSettings.apply` a config of its own or builds its own middleware stack, so the one line of `production.rb` that calls it and the initializer that prints the lines could both be deleted with all of them green, and the site would answer any host over plain HTTP while its log, computed from the address, said otherwise. `test/lib/production_boot_test.rb` boots production in a child process ten times (about three seconds each; `SECRET_KEY_BASE_DUMMY=1` in all but one, no database, `DATABASE_URL` taken away; four of the ten are the theme's, "The theme" below, and one a gem's hook). The address's three (and two more for `ADMIN_HOST`: "production with an ADMIN_HOST answers both hosts and names the admin origin at boot", "production with an ADMIN_HOST on the public host name does not start and says why"): with an https address ("production with an https address answers that host alone, forces HTTPS, mails the address and says so at boot"), with none and a debug log level ("production with no address refuses and forces nothing, says so, and warns about a debug log level"), and with a value that is no address ("production with a PUBLIC_HOST that is no address does not start, and says which variable without repeating it"). It fails when `HostSettings.apply(config)` is removed from `production.rb`, when a `config.force_ssl = false` is written under it, and when either line of the initializer is removed (each tried). The secret check is not booted for: its tests are `require_secret!`'s.

**The secret check.** The same initializer calls `HostSettings.require_secret!(ENV, credentials: Rails.application.credentials)` first, unless `SECRET_KEY_BASE_DUMMY` is set (the Dockerfile's asset precompilation, which has no secret and needs none). Rails' own error for a missing secret sends the reader to `bin/rails credentials:edit`, which a container has no key for; `HostSettings::MissingSecret` names the variable and `bin/rails secret`, and never holds a value. It decides as Rails does, in Rails' order:

- the variable holds a secret: accepted, and the credentials are NOT read, so a broken credentials file cannot stop a boot that needs nothing from it;
- the variable is set but blank (a compose file's `SECRET_KEY_BASE=${SECRET_KEY_BASE}` with nothing behind it): refused as "set but empty", also when the credentials hold a secret, because Rails would take the blank value for the secret and fail on it with its own message;
- the variable is not set: the credentials' `secret_key_base` decides. The spec asked for the variable alone; a secret in the credentials is accepted too because the Kamal boilerplate this repository ships (`config/deploy.yml`: `RAILS_MASTER_KEY`) supplies it exactly that way.

Credentials that cannot be read (a master key that does not open the file, a key of the wrong length, a file that is not YAML) are "could not be read": the message adds the error's class, never its text, and says to check `RAILS_MASTER_KEY`; `MissingSecret` has no cause. The rescue is every `StandardError` around the one call `credentials.secret_key_base`, which keeps `lib/` free of Rails' error classes and fails closed: its outcome is always a refusal. The cost is a vaguer message for someone whose master key is what is wrong.

The initializer is `after: :initialize_logger, before: :initialize_cache`. `after:` alone does not place it early (an application's own initializers are sorted after every engine's unless a `before:` pulls them forward), and Rails first reads `secret_key_base` at the very end of boot today, but any initializer or gem that asked for a key generator earlier would raise Rails' message first. The environment file, which parses `PUBLIC_HOST`, loads before `initialize_logger`, so a value that is not an address stops the boot earlier still.

## The theme

`THEME_PATH` names the folder a site is drawn with; what a theme is and how each part works is `docs/reference/theming.md`. This section is what a host meets: what the boot says, what stops it, and how a site's image is built.

**Why a variable and not a setting**, as for the address: the stylesheet, the digested assets and the import map are made when the image is built, for one theme, and a theme chosen in a Settings screen could not have been built for.

**What the boot says.** One line, at info, in production after the address's lines and in development too (`ThemeFolder.announcement`, logged by the same initializer, `content_spiel.host_announcement`):

- `[ContentSpiel] Theme: the default theme (THEME_PATH is not set)`
- `[ContentSpiel] Theme: /rails/site-theme (14 templates, fingerprint 3fa9c1d2)`
- `[ContentSpiel] Theme: /rails/site-theme holds no file of a theme and replaces nothing: the default theme draws the site (fingerprint 3fa9c1d2)`

With `RAILS_LOG_LEVEL=warn` it is not printed; System status' "Theme" row says the same fact with the folder's name in place of its path.

**What stops the boot**, each a `ThemeFolder::Invalid`. Unlike `PUBLIC_HOST`'s refusal these repeat the value: it is a path, and the path is what the person has to go and look at. `<path>` is the variable's value made absolute.

While the application is configured, before any of the boot's lines (`lib/theme_folder.rb`):

- `THEME_PATH names no directory: <path>. Set THEME_PATH to the folder that holds the site's theme (its views, components, assets and javascript folders), or unset it to draw the site with the default theme.`
- `THEME_PATH: <path>/<entry> is not part of a theme. A theme folder holds the folders views, components, assets and javascript, and nothing else (dot files and a README are ignored). Move it out of the folder or delete it.` One such line for every entry at the top that is no part of a theme, in one refusal.
- `THEME_PATH: <file> cannot be read (<the system's reason>). The user the application runs as must be able to read every file and folder of the theme: correct the permissions of the folder, or of the step that copies it into the image.`
- `THEME_PATH: <file> is a link to <target>, which is outside the theme folder. A theme is copied into the site's image as one folder and must be whole. Copy what it links to into the theme in place of the link.`
- `THEME_PATH: <file> is a link to nothing. Delete the link, or put the file it should name into the theme.`
- `THEME_PATH: <file> is a link to a folder it is in (<target>). A theme is copied into the site's image as one folder and must be whole. Copy what it links to into the theme in place of the link.`
- `THEME_PATH: <folder> is a hidden folder inside the theme. What is in it would be left out of the check and of the theme's fingerprint, and could still be rendered or served. Move it out of the theme, or rename it without the dot.`

In production with a real secret, in the same initializer (not asked under `SECRET_KEY_BASE_DUMMY`):

- `THEME_PATH: the stylesheet was built for another theme: run assets:precompile with THEME_PATH set (SECRET_KEY_BASE_DUMMY=1 ./bin/rails assets:precompile). The build's stamp is <fingerprint>, this theme's fingerprint is <fingerprint>.` ("without THEME_PATH" when no theme is set over a stylesheet built with one.)
- `THEME_PATH: the public stylesheet was not built, or its build failed: there is no stamp of a build (app/assets/builds/.theme.stamp). Run assets:precompile with THEME_PATH set (SECRET_KEY_BASE_DUMMY=1 ./bin/rails assets:precompile) when the image is built, and keep app/assets/builds in the image.` The last clause is for a site that builds in a stage of its own and copies only `public/assets` into its last stage: the stamp is not under `public`.

When the application is prepared, after the boot's lines (`Theme.load`, against the theme contract):

```
THEME_PATH (<path>) is not a theme this version can draw:
  - <problem>
  - <problem>
Correct the folder, or unset THEME_PATH to start with the default theme. bin/rails theme:check says these and what only it reads for: a template that does not compile, and one that reads the request.
```

**These sentences come from a reading that finds mistakes; it is not a sandbox.** A theme is code the server runs: its templates are ERB, they call whatever a view can call, and a theme is trusted exactly as the deployment that put it into the image is. An operator who did not write the theme reads a refusal here as "the author made a mistake the CMS knows", and a start with no refusal as "none of those mistakes", never as "this theme can do no harm". What holds whatever a theme's template calls is narrower and elsewhere: the CMS's head tags are the layout's own lines, and no session, token or cookie leaves a public page (`docs/reference/theming.md`, "The public site commits no session, mints no token and sets no cookie").

where each problem is one sentence of `Theme::Check`, with `<file>` relative to the folder:

- `<entry> is not part of a theme. A theme folder holds the folders views, components, assets and javascript, and nothing else (dot files and a README are ignored). Move it out of the folder or delete it.` The sentence of a stranger at the folder's top, with its name alone: at boot the folder itself refuses these first (above), so this line is met on a development reload, for something put there while the process ran.
- `<file> is not part of the theme contract (<what that folder holds>). Rename it to a name the contract has, or take it out of the folder.` The parenthesis is one of `views holds the templates Theme::Contract::TEMPLATES names and the theme's own partials under views/theme/`, `components holds <component path>.html.erb for the components Theme::Contract.components names`, `assets holds stylesheets/theme.css, images/ (png, jpg, jpeg, gif, svg, webp, avif, ico) and fonts/ (woff2, woff, ttf, otf)`, `javascript holds controllers/**/*_controller.js`.
- `components/<path>.html.erb replaces the template of <path>, which no registered type hands out: the block type "<type>" it is named for is not installed. Remove the template from the theme, or install the type.` A component template the contract does not name: a misspelt one, or the template of a type whose gem the site no longer has. The type is named where the path says it (`blocks/<type>_component`, `<owner>/<name>_component`); otherwise the sentence says `which no registered block or content type hands out: the type it belongs to is not installed`. A template of one of the CMS's own components that is not a theme's to replace (`media/picture_component`, `rich_text/image_component`) gets the sentence above instead.
- `<file> is a hidden file and a template: it is left out of the check and of the theme's fingerprint, and a render that names it would still find it. Rename it without the dot, or take it out of the folder.`
- `<file> is named like an asset of the CMS's own (<root>/<name>): a theme adds assets, it does not replace one. Give it a name of its own.`
- `<file> is not UTF-8 text, so it cannot be read or drawn. Save the file as UTF-8.`
- `<file> prints <tag>: that tag is the CMS's own, it is in the head of every public page already, and a second one contradicts it. Delete it from the template.` The tag is one of `a canonical link`, `a language link (rel="alternate" with hreflang)`, `the og:url tag`, `the content security policy's tag`, `the import map`, `a stylesheet link`.
- `<file> asks for the CSRF token: a public page is one answer for every visitor and carries none, because asking for the token starts a session and sets a cookie on a page a cache may keep. Delete it from the template.`
- ``<file> has a form that is sent with a CSRF token (form_with, form_tag, form_for or button_to without `method: :get`): a public page is one answer for every visitor and is given no token, so the form would be sent without one. Write a search form with `method: :get`, and a form that posts to another service as a plain <form> tag.``
- `<file> sets or deletes a cookie (a write to cookies, to the session or to the flash): a public page is one answer for every visitor and a cache may keep it, so no cookie leaves with it and the write is lost. Take it out of the template; what differs from one visitor to the next is kept in the browser, by a script.`
- `<file> caches what it draws (cache, cache_if, cache_unless or Rails.cache): the public page and the preview draw the same template and would share the entry, so a visitor could be served what only an editor may see. Take the cache out and put nothing in its place: a public page is already answered whole by its ETag.`
- `<file> writes to the head's slot (content_for :head): the head of a public page is the CMS's and reads no slot, so the tag would never be printed. Put the tag into views/layouts/public/_head.html.erb, which is the theme's part of the head.`
- ``<file> assigns an instance variable: a template is rendered before the layout, which reads the page, the post and the preview from instance variables to write the title and the head's tags. Use a local variable (`name = …`), or pass the value to a partial as a local.``
- ``views/layouts/public/_frame.html.erb never prints the page: `yield` is the page, and without it every address of the site shows the frame alone. Add <%= yield %> where the page goes.``
- ``views/layouts/public/_title.html.erb prints nothing: what it prints is the text of every page's <title>. Print the title from its two locals, `page_title` and `site_title`, or delete the file to get the default pattern.``

A word of one of these in a sentence of the page, in a string or in a comment is not refused: a helper's name is asked of a tag's code and an attribute of a tag (`docs/reference/theming.md`, "The plain depth").

`bin/rails theme:check` says the same sentences and three kinds more (a template that does not compile, one that reads the request, and its own lines); they are in `docs/reference/theming.md` ("`theme:new` and `theme:check`") and are seen in a build's log, never at boot. It needs no database, no stylesheet and no secret outside production, or in production with `SECRET_KEY_BASE_DUMMY=1`, as the Dockerfile below runs it.

On a development reload a refusal does not raise: it is kept, logged at error and said on every public page until the folder is corrected, and so is anything else the check raises there ("THEME_PATH (<path>) could not be checked: <error>. The folder may have changed while it was read: save a file of the theme to have it read again. If this is said again, it is a fault of the check and not of the folder.").

The theme's four boots in `test/lib/production_boot_test.rb`: "production under a theme folder outside the application says which at boot, and the application's theme is that folder", "production with a THEME_PATH that names no folder does not start, and says which variable and which path", "production with a theme folder that holds a file the contract does not name does not start, and names the file", and, the one boot with a real secret, "production under a theme whose stylesheet was not built for it does not start, and says how to build".

### How a site's image is built

**Where the CMS image comes from.** `.github/workflows/image.yml` builds it on every push to `main` (and by hand for any branch) and pushes it to the GitHub container registry as `ghcr.io/<owner>/content_spiel:<the full commit id>`, with `:main` for the newest build of main. A site built before releases pins the commit id; a site now pins a release number, whose image `release.yml` makes from the same commit image ("Releases", "A site's version", below). There is no `latest`, which would change a site under its owner at the next deploy. Before 2026-10-13 the image was built by hand on a laptop, under emulation, from a second folder, and the first deploys' mistakes were all in that step. The repository is public and so is the package (`ghcr.io/<owner>/content_spiel`): a site's build pulls it without a token.

A theme reaches a container as an image layer on the CMS image, never as a mounted volume: changing the theme of a running site is a build and a deploy. A site's `Dockerfile`, as built and run by hand on 2026-10-12 (the comment above `assets:precompile` in the CMS's own `Dockerfile` prints the same lines):

```dockerfile
FROM <the CMS image>
ENV THEME_PATH=/rails/site-theme
COPY --chown=1000:1000 theme/ /rails/site-theme/
RUN SECRET_KEY_BASE_DUMMY=1 ./bin/rails theme:check && \
    SECRET_KEY_BASE_DUMMY=1 ./bin/rails assets:clobber assets:precompile
```

- **No `USER` line.** The CMS image ends as uid 1000 and `/rails` is that user's; the `RUN` writes `tmp/theme/entry.css`, `app/assets/builds/theme.css`, `app/assets/builds/.theme.stamp` and `public/assets`. `--chown=1000:1000` on the `COPY` is what makes the theme readable by it; without it the boot's "cannot be read" sentence is what the build prints.
- **`theme:check` BEFORE `assets:precompile`.** The precompile starts the application, which does not start under a folder the contract refuses, so with the precompile first a refused theme ends the build in rake's "aborted!", a trace and the boot's half of the problems. `theme:check` starts the application itself, without stopping at a refusal, and prints every problem as a numbered line, then `<path>: N problems.`, exit 1; a sound folder is `<path>: N templates, no problems.`, exit 0. It needs no stylesheet and no database, and no secret outside production, or in production with `SECRET_KEY_BASE_DUMMY=1`, which is how the lines above run it (a production boot without it asks for the secret and for the stylesheet's stamp).
- **`SECRET_KEY_BASE_DUMMY=1` on both commands.** Each starts production, and a build has no secret. It is also what lets the precompile start production before the stylesheet it is about to build is stamped: the stamp is not asked under it.
- **`theme/` is a folder of the site's repository, and the `Dockerfile` is beside it, not in it.** A theme folder's top holds the four folders and nothing else (dot files and a README are passed over), so a `Dockerfile` inside the theme is refused as a stranger.
- **`assets:clobber` first.** The base image's `public/assets` holds the default theme's digested `theme-….css`, which would otherwise stay beside the new one.
- A theme names its images and fonts in `theme.css` by bare file name (`url("mark.svg")`); the served stylesheet has `url("/assets/mark-<digest>.svg")`.
- The result is the CMS image plus two small layers (the theme, and the build's output) and builds in seconds once the base exists. The CMS image is published: `.github/workflows/image.yml` pushes it to the registry on every push to `main` ("Where the CMS image comes from", above), and a site's `FROM` line pins a commit's tag; the result is that image plus the two small layers.

**A production build with a real secret, outside the Dockerfile, is refused by the stamp check.** On a host that is not an image build (a buildpack, a plain server: `RAILS_ENV=production bin/rails assets:precompile` with `SECRET_KEY_BASE` in the environment) the first build of a fresh checkout has no stamp, and a rebuild after `THEME_PATH` changed has another theme's, so production does not start to run the task that would write the stamp. Run the build as the refusal's own sentence says, `SECRET_KEY_BASE_DUMMY=1 ./bin/rails assets:precompile`: the stamp is not asked under that variable. No other production command is affected once the stylesheet is built.

**What was proven by hand, and how** (CI builds no image; the spec's "As built" has the detail): the site image, built from those five lines on the CMS image, started under its own entrypoint and command against a throwaway Postgres on a private Docker network, drew the homepage with the theme's frame, page template and block template and the CMS's head, linked its stylesheet by a digested name with the theme's image and font at digested addresses inside it, served the theme's image, font and controller, answered a second request 304, `/up` 200, a missing page 404 inside the theme's frame, and a foreign `Host` 403; and it refused to start with the stamp removed and with `THEME_PATH` emptied over the theme's stylesheet.

**The image reaches its four databases only through libpq's `PGHOST` today.** `config/database.yml`'s production block names four databases (primary, cache, queue, cable), a user and a password from `CONTENT_SPIEL_DATABASE_PASSWORD`, and no host for any of them; `DATABASE_URL` moves the primary alone and leaves the other three on a local socket, so `PGHOST`, which libpq reads because the file names no host, is the one thing that moves all four. That it works is an accident of the file, not a documented way: giving the four databases an address is part three of hosting (`docs/roadmap.md`, "Hosting and the dry run").

## Addresses a public page prints

`og:url`, every `hreflang` alternate and `<link rel="canonical">` are built by `PublicSite::Urls`, whose host `PublicController#public_urls` sets to the configured origin, so they carry the site's address whatever `Host` (or `X-Forwarded-Host`, which wins over `Host` in Rails) a request named. A public response is the same for everyone and cacheable: a host written into it from the request is served to the next visitor too. With no address configured they fall back to the request's origin, as CS Studio's "Copy address" does. The canonical link is the page's or post's own address in the language shown, without a query string; a page that is not found has none, and a preview has none and keeps the request's origin and its `/<ADMIN_PATH>/preview` addresses (`PreviewController` is untouched) (`test/integration/public_head_address_test.rb`: "under a foreign Host, og:url, every hreflang and the canonical link carry the configured address", "the canonical link is the page's own address in the language shown, without the query", "a page that is not found has no canonical link, and names no foreign host", "a preview keeps the request's origin and its /<ADMIN_PATH>/preview addresses, and has no canonical link").

**The guard** is `test/lib/public_address_guard_test.rb`: no public view, component, helper or controller asks the request where it was sent (`request.base_url`, `request.host`, `request.original_url` and the rest of that family, the Host headers by name) or calls a `..._url` helper. What it scans is derived, as `test/lib/public_readers_test.rb` derives it: `PublicController`, the controllers that descend from it and the concerns they include, their view folders, the public layout, `layouts/public`, `views/shared`, every helper outside `admin/` and every component outside `app/components/admin`. Two lines are allowed, each by its file and its text with the reason, and an entry that matches no line fails: the `request.base_url` fallback in `PublicController#public_urls`, and the `request.original_url` fallback of `og:url`, reached only by a preview post that no published copy lists.

**What the guard does not cover.** It is a source grep: an address handed in from elsewhere, `url_for(..., only_path: false)` and a `PublicSite::Urls` made with another host are invisible to it, and the integration test is the guard that really holds. And it looks at what a page prints, not at response headers: **a redirect's `Location` follows the request** (`redirect_to` in `PagesController`: the default language's redundant prefix, a moved record). That was left as it is by a ruling: with an address configured a foreign `Host` is refused before any redirect is made, so the request's host IS the address's, and without one the request's host is all there is.

**The ETag.** With no address configured the public ETag includes the request's origin (`PublicController#origin_etag_key`, read from the `public_urls` instance so the guard's allow-list stays at one `request.base_url` line): the fallback writes that origin into the head, and without it a 304 could confirm a body printed under another host. With an address configured the key is not added at all, so the ETag is the same under every host and is built from exactly the keys it had (`test/integration/public_head_address_test.rb`: "with no address configured an ETag obtained under one Host is not confirmed under another, and is under the same one", "with no address configured the scheme and the port are part of it too", "with an address configured the ETag is the same under every Host, and a 304 is given under any").

**The homepage.** The localised homepage's canonical link, `og:url` and `hreflang` are `/de/`, with the slash, and that is also the sitemap's `<loc>`; `/de` answers 200 with the same page as well, and only the canonical link says which of the two is the address. No redirect and no loop; a redirect from one to the other would be a routing change and is on the roadmap. The default language's homepage is `/` in the link and the bare origin in the sitemap's `<loc>` (`sitemap_generator` joins "/" onto the host): one address, two spellings ("the homepage in another language: the three agree on /de/, and that address answers 200 with the same page, as /de does", "the sitemap lists the homepage in each language at the address its canonical link names").

## The reset mail

`PasswordsMailer.reset(user, origin: nil)` builds its link in one place, the private `reset_url`, which both parts of the mail call (memoised: every call of `password_reset_token` signs a new token, and the two parts used to carry two different links). Where the link points:

- the admin address (`ADMIN_HOST`) when there is one, since the link opens a CS Studio page and CS Studio answers on that host alone ("Behind a DMZ");
- otherwise the site's configured address whenever there is one, whatever `origin` says;
- otherwise, **in development and test only**, the origin of the request that asked (`Admin::PasswordsController#create` hands `request.base_url` through `Admin::MailLinkOrigin` to `PasswordResetRequestJob` as a String, because a job finds the account and delivers the mail; the request looks nobody up, `docs/reference/mail.md`, "Sign-in and the reset"), parsed by `SiteAddress.parse` and used for its origin and nothing else; a value that is not an origin is no origin;
- otherwise **no mail**: `mail` is not called, Action Mailer delivers nothing, and the log says `[ContentSpiel] A password reset mail was not sent: no site address is known. Set PUBLIC_HOST.`, a line that names no person and holds no token. The request page answers with the same words either way: it must not reveal anything about an account. **The request page exists only while mail works** (`MailSettings#ready?`, `docs/reference/mail.md`): in production without an address mail is "Not set up", so sign-in shows "Forgot your password? Ask the site's owner to reset it." in place of the link and `new` and `create` redirect to sign-in; `edit`, `check` and `update` keep working whatever the state, so a link already mailed is finished. A site with no working mail has one way in that needs none, a password set from the server (the command is a fixed string, audited, and it ends that user's sessions): `bin/rails runner 'p Users::UpdatePassword.call(User.find_by!(email_address: "you@example.com"), password: "a new password", password_confirmation: "a new password").ok?'`, with the account's address and a new password (at least 12 characters, no quotes in it) in place of the placeholders; it prints `true` when the password was changed and `false` when it was refused (too short, or the two do not match). System status's Mail row carries it, copyable, while mail is not ready (Not set up, Saved not tested; `Setup::SystemCheck::MAIL_FALLBACK_COMMAND`, the same string); once mail works the row has no command, and the reset link on sign-in is the way back. **A person who lost every passkey and every recovery code** is let back in by the same command with `, remove_passkeys: true` after the confirmation: `bin/rails runner 'p Users::UpdatePassword.call(User.find_by!(email_address: "you@example.com"), password: "a new password", password_confirmation: "a new password", remove_passkeys: true).ok?'`, which also deletes the account's passkeys and codes in the password's transaction and records one `passkey.removed` with no actor (`reason: "console"`); the person then signs in with the new password alone and adds a new passkey, at enrolment when the policy covers them. Only the console may ask it: from anyone signed in it is refused whole, so it is the one way a lost device is cleared, and the user editor offers none. A reset by mail sets a password and leaves the passkeys and codes, so a covered person still needs a second proof after it. `MAIL_FALLBACK_COMMAND` is the command without the keyword. The row is the one place on any screen that leads a locked-out sole owner to it: it was taken off once while mail was built and put back (`docs/reference/mail.md`, "System status and the dashboard").

**Who must sign in with a passkey is set from the console too**, for an owner held at enrolment with no way to make one (no browser of theirs can, and Settings → Sign-in is behind the hold): `bin/rails runner 'p Settings::Save.call(SiteSetting.instance, attributes: { passkey_policy: "nobody" }).ok?'`, with `"nobody"`, `"owners_and_admins"` or `"everyone"`, prints `true` when it was saved and records `settings.updated` with no actor. A session's hold is decided when it starts, so the person signs out and in again. A production site that never chose has no stored value and asks owners and admins (`SiteSetting#effective_passkey_policy`), so after an upgrade to the release with passkeys every owner and admin is sent to enrolment at their next sign-in; the command, or Settings → Sign-in before that sign-in, chooses otherwise (`test/services/settings/save_test.rb`: "the console command in hosting.md sets the policy to nobody, with no actor, and records it").

**Why the request's origin is used nowhere else.** It is whatever `Host` the request named, and a site with no address configured refuses no host. Anyone could ask for a reset of an address they know under a host of their own, and the account's owner would be mailed a valid token on a link to that host (password-reset poisoning). The spec had the request's origin as the fallback in every environment; the hole was named and closed while it was built. `PasswordsMailer.request_origin_used?` is the one place the decision is made and both the mailer and the controller ask it; it is `env.local?`, an ALLOW-list, never `!env.production?`: a staging, preview or demo environment is exactly the kind that sits on a public address without `PUBLIC_HOST`, and host authorisation is set up from `production.rb` alone, so an environment nobody named must fail closed. With an address configured, and in production without one, the origin is not put into the job's arguments at all.

Three things that are easy to miss. **The address is read in the process that performs the job**: a job container separate from the web container needs `PUBLIC_HOST` too, or it builds no mail. **Active Job logs a job's arguments**, so in development and test the origin is in the job's own lines and in the queue's row: an address, never a token. And `reset_url` passes `port: nil` ahead of the address's options, because `url_for` merges what it is given over `default_url_options` and an address without a port would otherwise inherit the environment's (development's 3000) (`test/mailers/passwords_mailer_test.rb`: "in production with no address configured no mail is built, whatever origin is handed over, and the log says why", "the request's origin is used in development and in test, and in no other environment", "nothing of the environment's default url options reaches the link", "an origin that is not an origin is no origin: no mail, the same line, and the value is not repeated"; `test/controllers/admin/passwords_controller_test.rb`: "create with a site address configured hands the mailer no origin, whatever Host the request named", "create in production with no address configured hands over no origin, sends no mail and answers the same").

## The reset link: the token is in no address

The mailed link is `<origin>/<admin>/password/edit#<token>`. A browser sends what follows the `#` to no server, so the token is in no request line, no span and no proxy's access log; the proxy's log is the one this application could never have filtered, which is why masking the old path was not enough. One log does hold the whole mail, link and token: Rails' own at `RAILS_LOG_LEVEL=debug`, where Action Mailer writes every delivered mail in full; production runs at info, and the boot warns when it does not ("What a change can break silently").

- **`GET <admin>/password/edit`** (`admin_edit_password`, `Admin::PasswordsController#edit`) draws the same page for everyone: no lookup, no parameter read, and a `token` handed to it as a query parameter is ignored, since that would be a token in an address. The form is drawn `hidden` by the server and its hidden `token` field empty, so nothing flashes before the script runs and without JavaScript a form that can only fail is not shown beside the `<noscript>` line.
- **The script** is the top-level Stimulus controller `reset-token` (`app/javascript/controllers/reset_token_controller.js`), not an admin one: the `product` layout loads only the `application` entry point, and `controllers/index.js` registers everything except `controllers/admin/*`, so an admin controller would never connect on this page. It moves `location.hash` into the field, removes the fragment from the address with `history.replaceState`, shows the form and, once the link is known to be good (below), focuses its field; with no token it shows "This link is incomplete…" with a way to a new link. A fragment is not sent, so nothing on the server can tell a truncated link from a missing one, and the message covers both. The token is not percent-decoded: a token is URL-safe, and a link a mail program has spoilt fails verification and gets the expired state. What `replaceState` clears is the address bar and the entry Turbo and the page see; whether the browser's own record of the visit (its history list, a synced history) keeps the fragment differs by browser and is not this page's to change. That is no worse than the token in the path was, and a used or lapsed token is worth nothing.
- **The token is kept nowhere but the field, and not past the page.** Writing a hidden input's `value` writes its attribute, so a copy of the document holds it: Turbo's snapshot (the `product` layout does use Turbo Drive; the token was seen there before this was closed) and the browser's back/forward cache. The field is emptied on `turbo:before-cache` (the field only, since the page is still on screen while the next one is drawn) and on `pagehide` (the field and the message, because the browser's own cache restores a page without connecting anything again). Neither comes before the form's own request has been built. A page come back to has no token and says the link is incomplete, which is true of it.
- **The early check.** The page is drawn without the token, so it cannot know whether its link is good, and the form's own request says so only after a password was typed twice. So the script asks once, when the token came from the address: **`POST <admin>/password/check`** (`admin_check_password`, `#check`), a `fetch` with the token in the body and the CSRF token from the page's meta tag. The answer is a status and nothing else: 204 for a token `update` would take now, 410 for every other. It writes nothing (no session key, no audit event, no change to the user, and a good token is as good afterwards), it says no more than `update` would, and it has the request form's rate limit (ten in three minutes), counted on its own (`name: "check"`); past it the answer is a bare 429. On 410 the script empties the field and replaces the page with the request page's "expired" state (`location.replace` to `<admin>/password/new?expired=1`, an address that names no token; replaced, so Back does not lead to a form that cannot work). On anything else (204, a 429, a 422 for a lost CSRF token, an error, no network) it shows the form: the check is advice, and a check that could not be made must not cost a good link. Until the answer is there the fields are read-only and the form is `aria-busy`, so nothing is typed into a form that is about to go; an answer that arrives after the page was left moves nothing. The form of a refused password (the 422 below) comes with its token from the server and is not asked about again.
- **`PATCH <admin>/password`** (`admin_update_password`, `#update`) reads the token from the body, where `filter_parameters` (`:token`) masks it in the log. Tampered, lapsed, used, blank, missing, a list or a hash where a string belongs, or a good token of a user deleted since (Active Record raises `RecordNotFound` for that one, which was a 404): one answer (`user_for_token`, which `check` shares), the "expired" state of the request page, nothing written. This is the rule, whatever the early check said: a token can lapse while a password is typed. A refused password is a 422 of the form itself, with the token in the hidden field of that one response: rendered, not redirected, because a redirect could carry the token only in an address or in the session.
- **`Cache-Control: no-store`** on `edit`, `check` and `update`: the empty page and the refused form share an address in the address bar, and neither may be answered from a copy of the other.

The reset's own rate limit (on `create`; `update` has none, as before), the audit event (`user.updated`, the user as actor) and the ending of every session (`Users::UpdatePassword`, `keep_acting_session: false`) are as they were. The cost of the whole design: resetting a password needs JavaScript, which CS Studio needs everywhere else.

Tests: `test/controllers/admin/passwords_controller_test.rb` ("edit reads no user: the page is the same with no account at all behind it", "edit ignores a token handed to it as a parameter: it reaches neither the form nor a redirect", "the form's page is kept by no cache: the empty one, the refused one and the redirects", "nothing logged for the form's requests holds the token: accepted, refused, and with a bad password", "check answers 410 for every token that is no good: tampered, lapsed, used, blank, missing, no string, of a deleted user", "check writes nothing: no user, no session, no audit event, no cookie, and the token still sets the password", "check is limited like the request form: the eleventh in three minutes is a bare 429, whatever the token", "nothing logged for a check holds the token, good or bad", "a good token of a user deleted since is the expired state, not a 404", "with forgery protection on, the form and the check are refused without the page's token and taken with it"), `test/mailers/passwords_mailer_test.rb` ("the token is the link's fragment: the address a server is asked for holds none") and the browser's side in `test/system/admin/password_reset_test.rb` ("the mailed link opens the form, the token leaves the address, and the new password signs in", "a lapsed link shows the expired state at once, with nothing typed, and its token is in no address", "while the link is being asked about the fields are read-only, and they open when it is answered good", "a check that fails, is refused or is limited leaves the form open, and the form still sets the password", "an answer that arrives after the page was left moves nothing", "the token does not outlive the page: not in Turbo's snapshot, and not after Back", "a page the browser puts away keeps no token: the field is emptied and the message shown at pagehide"; ## Telemetry

`config/initializers/opentelemetry.rb` asks `Telemetry.exporter_kind(env, rails_env)` (`lib/telemetry.rb`) where the spans go, first match first:

1. `:memory` in the test environment, whatever is set (`Rails.application.config.x.otel_test_exporter`, the exporter inside the scrubber's wrapper, so what a test reads is what a backend would be sent);
2. `:otlp` when either `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` or `OTEL_EXPORTER_OTLP_ENDPOINT` is not blank (`Telemetry::ENDPOINTS`), batched;
3. `:console` when `OTEL_CONSOLE` is exactly `1` (`true`, `yes` and `" 1"` are not), printed at once;
4. `:none` otherwise, development and production alike: `OpenTelemetry::SDK.configure` is not called, no instrumentation is installed, no span is made, and `OpenTelemetry.tracer_provider` stays the API's own no-op.

Case 4 used to be the console. A production container with no endpoint printed every span to its log: about 49,000 lines for 60 requests, with the path of every request in them, a password-reset token included. Hence the default is nothing, and printing is asked for by its own variable and one value, so that no environment prints because something else was left unset. `bin/dev` and `bin/rails server` print no span unless started with `OTEL_CONSOLE=1`.

**What is sent: a request's work and a job's, never the background's polling.** Production runs Solid Cable on Postgres and Solid Queue inside Puma, and both poll their tables from threads of their own: Solid Cable's listener asks for new messages every 0.25 seconds (`polling_interval`, `config/cable.yml`; a broadcast reaches a subscriber within one interval, and notes, presence and editing signals are read by a person, so a quarter second is not seen), Solid Queue's worker asks for ready jobs and its processes write heartbeats. The Active Record instrumentation (0.13) makes a span for every one of those statements whether or not anything is being traced, and each was the root of a trace of its own. On 2026-10-13 a small, almost idle site sent about 820,000 spans in a day (`SolidCable::Message query` 697,000, `ActiveRecord.transaction` 183,000, the rest Solid Queue's claims and heartbeats) for a few hundred page requests: Honeycomb's free plan (20 million events a month) would have been gone in three weeks, and the requests were hard to find.

So the provider's sampler is `Telemetry::WorkSampler.sampler` (`lib/telemetry/work_sampler.rb`), assigned at the end of the initializer, in all three configured cases alike (a test records, and the console prints, what a backend would be sent). It is the SDK's own `ParentBased` sampler with a root sampler of ours: `ParentBased` asks it only about a span with no parent, and every other span follows its parent, so a dropped root drops its whole trace and a kept root keeps all of it, its database spans included. The root sampler decides by the root's KIND, never by its name:

| Root kind | What begins with it | |
|---|---|---|
| `:server` | a request (the Rack instrumentation's span) | kept |
| `:consumer` | a job being performed (`<queue> process`: the Active Job instrumentation starts it with `start_root_span`, so it is a root of its own even when Solid Queue's worker posted it from inside a dropped claim, and it links to the request that enqueued it) | kept |
| `:internal` | Active Record's spans with no request or job around them: Solid Cable's polls, Solid Queue's claims, heartbeats and its bookkeeping after a job | dropped |
| `:client`, `:producer` | an outgoing call or an enqueue with no request or job around it: Solid Queue's scheduler enqueuing a recurring task (its perform is kept, as its own trace) | dropped |

A dropped span is a non-recording span: no processor sees it and nothing exports it, so the scrubber is still the first processor of everything that is sent. A span whose parent came in a request's `traceparent` header follows that header's sampled flag, the SDK's default, as before; `OTEL_TRACES_SAMPLER` is overridden. Why a sampler and not a list of names: the names are the instrumentation's and change with a gem or a model, and a list would also drop a request's query that shares a poll's name. Why not an instrumentation option: Active Record's has none that tells a poll from a request's query, and turning it off would take the database spans out of the requests too.

What is dropped with the polling, because it begins no trace of its own with the installed gems (there is no Action Cable instrumentation): **a channel action** (a presence `beat` or `report`, a subscription's `subscribed`), whose statements are INTERNAL roots on Action Cable's worker threads (`Presence::Mark.update_all` was about 500 a day), and **Solid Cable's INSERT of a broadcast**, which its writer thread (`SolidCable::BatchedBroadcaster`) makes apart from the request or job that broadcast (`SolidCable::Message.insert_all`, about 400 a day). The request or job that broadcast is still sent; the connection's own request (`GET /<ADMIN_PATH>/cable`) is a SERVER span and is sent. **This is a known gap, accepted with this change**: a person's live notes, presence and editing work over the socket is not traced. What would close it is a CONSUMER root started for `perform_action.action_cable` (an `ActiveSupport::Notifications` subscriber that starts and finishes the span and attaches its context, as the Active Job instrumentation does for `perform.active_job`), so the action's statements follow it; never a list of span names to keep. A presence `beat` every few seconds per open tab would then be a trace each.

Recurring jobs (`config/recurring.yml`: the five-minute sweeps and `public_paths_sync_went_live`, the hourly clean-up) are performs and stay recorded, about 870 traces a day: they are real work, and a sweep that fails must be seen.

Tests: `test/lib/telemetry/work_sampler_test.rb` ("a root of each dropped kind is dropped with its whole trace, while a server and a consumer root are kept with theirs", "a span started with no kind and no parent, as a poll's query is, is dropped", "a consumer root started inside a dropped trace is a root of its own and is kept", "the provider's sampler is the SDK's ParentBased with the work sampler at its root"); `test/integration/opentelemetry_test.rb` ("a request is recorded with its database spans, in one trace under the request's server span", "a job's perform is recorded with its database spans, in one trace under the job's consumer span", "a query outside any request or job, as a poll's is, records nothing"); and the development boot in `test/lib/telemetry_exporter_test.rb` prints a request's span and not a poll's. A test that starts a span of its own to see it exported starts it as `kind: :server` (`test/lib/telemetry/path_scrubber_test.rb`): an INTERNAL root is dropped.

**The scrubber** (`Telemetry::PathScrubber`, `lib/telemetry/path_scrubber.rb`) has one rule for the attributes that hold a request's address (`url.path`, `url.query`, `http.target`, `url.full`, `http.url`):

- **No query string leaves in a span**, whatever its parameters are called: `url.query` is replaced whole when it is not empty, and an address is cut at its first `?`. The Action Pack instrumentation does put `filter_parameters` over the query, but only once a controller has the request: one answered before any controller (a redirect in the routes, a throttle, a refusal in a middleware) keeps the query as it was sent, and with the older attribute names `http.target` is never rewritten at all. A note's quote travels in a query string as `note_quote`, and a note's text reaches no log line (`docs/reference/notes.md`), so none of it is kept. The cost: a tracing backend shows no query string at all; `http.route` still says which address was asked for. `scrub` itself, the path's rule, keeps a query: cutting it is the attributes' rule (`scrub_attributes`), one step above.

**Why it is `on_start` plus a wrapped exporter.** `PathScrubber::Processor` is added first and scrubs the attributes a span starts with (all the Rack instrumentation writes), before any other processor has seen them. It can do nothing for an attribute set later: the SDK (1.13) freezes a span's attributes before it calls `on_finish`, and its `on_finishing` hook is called while the span holds its own mutex, where `set_attribute`, which takes the same mutex, raises. So `PathScrubber::Exporter` wraps whichever exporter is used and scrubs the same attributes in the copy that is exported. Each half has its own test (`test/lib/telemetry/path_scrubber_test.rb`: "an attribute a span starts with is scrubbed, on the span itself and in what is exported", "an attribute set after the start is scrubbed in what is exported, each of the five"; `test/integration/opentelemetry_test.rb`: "no span of a request to a reset address carries a token handed in its query", "no span carries a query string, of a request answered before a controller or by one"; `test/lib/telemetry_exporter_test.rb`: "with neither variable there is no telemetry, in production and in development", "a development boot with neither variable configures no SDK and prints no span, and OTEL_CONSOLE=1 prints it", which boots development twice in a subprocess, because the table alone would not notice an initializer that ignored `:none`).

Not scrubbed: a span's name (not the path with today's defaults) and an exception event's message, which may quote a path (a `RoutingError`'s does). No route takes a token in its path, so such a message holds none; the end-to-end test hands a token to the reset page and to the check in a query and a body and reads every span's name, attributes and events, and fails if an instrumentation starts to record it somewhere new.

**The CMS's own spans.** Beside the instrumentations' spans the CMS starts a few of its own, for sign-in and sessions: `Telemetry::SPANS` and `Telemetry::ATTRIBUTES` (`lib/telemetry.rb`) list every name and attribute key, `Telemetry.in_span` and `Telemetry.record` refuse anything else, and no file but `lib/telemetry.rb` starts a span (`test/lib/telemetry_spans_test.rb`: "no file but lib/telemetry.rb starts a span", "every span name and attribute key is auth., server., http. or error."). None is a root: each is a child of the request's SERVER span (the sweep's, of its job's CONSUMER span), so the work sampler keeps it with its trace; started anywhere else it would be a root and dropped. `auth.session` is started through `Telemetry.in_child_span`, which starts no span when nothing records around it: the cable's connect runs on Action Cable's worker pool outside any request's span, so an expiry met there is audited (`session.ended`) and not traced.

`auth.sign_in` also carries `auth.second_factor.required` (`true`) when a right password owes a second proof, its outcome then `second_factor_required`. **`auth.policy`** (`nobody`, `owners_and_admins`, `everyone`) is the passkey policy a session was started under, written by `start_new_session_for` on the request's SERVER span, not on `auth.sign_in`: a passkey sign-in has no `auth.sign_in`, and a password's has closed by then. A request that starts no session (a refusal, a password step owing its second proof) has none.

**Never in a span**: the email, the password, any part of its hash, the Turnstile token or its secret, a recovery code, a passkey's name, its credential id or public key, or a challenge. The values are fixed words, numbers and Booleans; `test/integration/sign_in_telemetry_test.rb` plants an email, a password and its SHA-1 (prefix and suffix, both cases, URL-encoded too) and searches every exported span's name, attributes, status, links and events for them ("no span of those sign-ins holds the email, the password or a part of its SHA-1"), and `test/integration/passkey_telemetry_test.rb` does the same for the passkey sign-in, the second step by code and by passkey, Confirm it's you, a passkey added on Your account and the jobs they queue, planting the codes, the passkey's name and its credential, and keeping every challenge it was handed ("no span or event holds the email, the password, the code typed, the credential id, the challenge or the passkey's name"), and holds each new span to its parent and every `auth.*` key to `Telemetry::ATTRIBUTES` and its listed words ("a passkey sign-in, refused and accepted, exports auth.passkey under auth.sign_in's request with only listed words", "the second step by code, wrong, right and locked, exports auth.second_factor and auth.recovery_code with only listed words", "a refused confirmation exports auth.confirmation"). The two outside calls run `untraced` (`SignIn::OutsideCall`), because the Net::HTTP instrumentation's own span would record the range's path, five characters of the hash, and `PathScrubber` cuts queries, not paths; each records its own CLIENT span with the words above instead (`test/models/sign_in/leaked_password_test.rb`: "range runs untraced: no span holds the prefix"; `bot_check_test.rb`: "siteverify runs untraced: no span of the HTTP instrumentation is recorded for it").

**In Honeycomb** (or any backend that queries spans), four queries over the last 24 hours:

- a credential-stuffing run: `WHERE name = auth.throttle AND auth.tripped = true`, `GROUP BY auth.bucket`, `COUNT`, as a time series: a wall of `address_wide` is one address trying many emails, of `account` many addresses trying one, and of `address` one client hammering the form;
- the refusals: `WHERE name = auth.sign_in AND auth.outcome != ok`, `GROUP BY auth.outcome`, `COUNT` (`second_factor_required` is no refusal: a right password going on to its second step);
- the second step's failures by outcome over time: `WHERE name = auth.second_factor AND auth.outcome != ok`, `GROUP BY auth.outcome, auth.method`, `COUNT`, as a time series: a run of `refused` by `recovery_code` is someone with the password guessing codes, `locked` the account's bucket closed under them; the same over `auth.confirmation` is a session left open on someone else's screen;
- the sessions a request ended by expiry, by reason (a cable connection's are in the audit log only): `WHERE name = auth.session`, `GROUP BY auth.session.reason`, `COUNT`, as a time series: idle endings are people who left, absolute ones people who stayed signed in 14 days; and, for the ones nobody came back to meet, `WHERE name = auth.session_sweep`, `SUM(auth.session.count)` (the sweep's span carries the total, not the reasons, which the audit log's `session.ended` events hold, one per reason per run). The endings a person asked for (Your account, an owner's End all sessions, a password change) are audit events, not spans.

`lib/telemetry.rb`, the scrubber and the sampler are required from `config/application.rb` for a different reason than `site_address`: the initializer hands the scrubber's and the sampler's objects to the SDK for the life of the process, and a file loaded before the autoloader is set up is not unloaded and redefined on a development reload.

## What a person is told

**System status and the wizard's system check** (`Setup::SystemCheck`, `docs/reference/cs-studio-shell-and-dashboard.md`; System status is one card of rows, the wizard a ruled list, both through `setup/_system_check_results` and its `list_class:`) begin with two checks about the address, and a third about the theme. `Setup::SystemCheck.new(address: SiteAddress.current, request_ssl: nil, production: Rails.env.production?, reset_link_from_request: false)`; both screens hand over `request_ssl: request.ssl?` and `reset_link_from_request: PasswordsMailer.request_origin_used?`, a boolean, so the model knows no mailer.

- **Site address**: OK with the origin, or a warning with `PUBLIC_HOST=https://www.example.org` to copy. With no address the warning has two wordings and shows the one that is true where it is read: where a reset mail takes its link from the request (development and test) it says addresses in pages and in reset mails follow the request, and nothing of hosts, since development refuses a made-up name by Rails' own list; everywhere else, and when nobody said (the console), that any host name is accepted and reset mails are not sent until it is set. And an http address on a page that was reached over HTTPS is a warning as well, "This site answers at http://…. The address is http but this page was reached over HTTPS: set PUBLIC_HOST to the https address.": a proxy ends TLS and nobody changed the variable, so everything built from the address is still http (canonical links, the sitemap, the reset mail), no cookie is `Secure` and no HSTS is sent, and the row would otherwise say OK beside an "HTTPS" row that says OK too (`test/models/setup/system_check_test.rb`: "an http address reached over HTTPS is a warning that says which to change, and names the address").
- **HTTPS**: in production only, and only when the caller said how the request came. "Reached over an encrypted connection" is what `request.ssl?` says, and the application sees no connection but the proxy's: it is true when the proxy said so or when `ASSUME_SSL=1` says it for every request, and a proxy that claims HTTPS for a plain connection makes the row say OK about a connection that is not encrypted. Nothing in the application can tell.
- **Theme**, after those two: which theme draws the site, by the folder's name and never its path, and a warning when the public stylesheet was built for another theme or not at all, with the command that builds it outside production; and, in development, a warning when the theme folder was refused at its last reload, without its path (`docs/reference/theming.md`, "System status").
- **Mail**: `MailSettings#state` in the state's own words (`MailStateSentence`, the Settings card's sentence): OK only for Working, a warning for Not set up, Saved not tested and Last send failed. In production without a site address mail is Not set up and the sentence says the address (`PUBLIC_HOST`) is what is missing. While mail is not ready (Not set up, Saved not tested) the row also carries the console password command to copy (`Setup::SystemCheck::MAIL_FALLBACK_COMMAND`); Working and Last send failed carry none. A failure is said by its short reason and never the server's line (System status is open to `system_status.view`, the line to `settings.manage`). The row links to the Mail card ("Open Mail settings →") only for a viewer who holds `settings.manage`: the caller hands `mail_settings_link: can?("settings.manage")`, the result carries the symbol `:mail_settings` and the row's component resolves it, since the model names no route.

**The plain-HTTP notice** (`Admin::Ui::InsecureNoticeComponent`, drawn through the compact warn `Admin::Ui::NoticeComponent`, an alert): in production, on a request that is not `request.ssl?`, "This connection is not encrypted. Passwords and sessions can be read on the way. Set PUBLIC_HOST to an https address." It can only show where the address is an http one or missing, since an https address redirects plain HTTP before it reaches the application. Three layouts draw it: `product` (sign-in, the password pages and the invitation, above the panel) and `setup` (every wizard page; the spec did not ask for the wizard, which takes the setup token and the first account's password) for everyone, and `admin` at the top of `<main>`, outside `#content`, for someone who holds `settings.manage` or `system_status.view`, each of which is enough alone (`Admin::BaseController::INSECURE_NOTICE_PERMISSIONS`; `test/integration/admin/insecure_notice_test.rb`: "in the shell settings.manage alone is enough to be told", "in the shell system_status.view alone is enough to be told", "in the shell someone who holds neither right is told nothing").

## The first start's database

`bin/docker-entrypoint` runs `bin/rails db:prepare` before the server. On an empty database that creates it, loads `db/schema.rb` (tables, indexes and keys; no rows) and then runs `db/seeds.rb`; on a database that exists it runs the pending migrations and no seed (`ActiveRecord::Tasks::DatabaseTasks.prepare_all`: the seed is loaded only when a database was initialized by this very run). No way of building a new database runs the migrations' data steps: `db:setup` and `db:schema:load` load the schema too, and since Rails 8 so does `db:migrate` on an empty database.

What a schema load leaves out, and where it comes from instead:

- **The audit log's append-only trigger**: reapplied after every schema load by `config/initializers/db_triggers.rb`.
- **The four built-in groups** (Admin, Editor, Author, Read only) with their grants: made by `Groups::EnsureBuiltIns`, called at the top of `db/seeds.rb` in every environment and by the setup wizard before every step past the token (so a database built with `db:schema:load` alone, which runs no seed, gets them when the first account is made). Only a group that is missing by name is made; a group that exists is never changed. The two are independent, and the wizard's call is what production relies on when the seed never ran: the seed runs on the FIRST start only, in the run that creates the primary database, so a first start that stopped between loading the primary's schema and seeding (the role may not create the cache, queue or cable database, say) is not seeded by the next one, which finds the primary initialized. The wizard then makes the groups at its first step past the token.
- **The settings row** and **the content version's row**: made by the application the first time they are needed (`SiteSetting.instance`, `PublicSite.bump_version!`).
- Everything else a migration ever inserted was computed from content that existed (usage rows, translation states, first published copies), and a new site has none.

Outside development the seed file does nothing else: no account, no content. The first account is the setup wizard's.

**A site that was set up before the groups were made this way** (its Groups screen is empty, or a built-in group is missing): run `bin/rails db:seed` once on the server (with Kamal: `bin/kamal app exec "bin/rails db:seed"`). It makes the missing built-in groups and nothing else, and running it again writes nothing. `db:prepare` will not do it: the database exists, so it is not seeded.

## Sign-in on the open internet

Spec: `docs/superpowers/specs/2026-11-10-studio-sign-in-design.md` (§1, §6, §7). CS Studio's sign-in is meant to stand on a public address with nothing in front of it. What decides an attempt is `SignIn` (`app/models/sign_in.rb`, `app/models/sign_in/`): plain objects that know no session, cookie, route or mail. `Admin::SessionsController` asks, answers, signs in and audits; a job mails. The order of one attempt is `SignIn::PasswordAttempt`'s: the bot check when it is due, then the reservation in the buckets, then the password (`User.authenticate_by`, which hashes a password for an unknown address too), so a refused attempt takes the same work whoever exists (`test/integration/sign_in_throttles_test.rb`: "a refused sign-in answers the same for a known and an unknown address: status, location, flash, page, cookie names, statements and one password hash each").

**The buckets.** Each counts in `SignIn.store` (`CounterStore.current`: Solid Cache in production, so every process counts in one place; a memory store in tests, so a limit trips there too), under keys that hold an HMAC of the email or the address and never either (`VisitorAddress`; an IPv6 address counts by its /64), the rate limit's included (`Admin::SessionsController::RATE_LIMIT_PURPOSE`; `test/integration/sign_in_known_device_test.rb`: "the rate limit counts an IPv6 visitor by their /64, and the store holds no address").

| Bucket | Counts | Closes | Answer |
|---|---|---|---|
| The address (Rails' `rate_limit`) | every POST to sign-in from one address, a success included | the 11th in 3 minutes, until the 3 minutes end | "Try again later." |
| The passkey options (Rails' `rate_limit`, `name: "options"`) | every POST for a passkey's options from one address (sign-in, the second step, Confirm it's you), apart from the proofs: options write nothing on the server | the 31st in a minute, until the minute ends | a bare 429: no passkey is offered |
| The account (`SignIn::Throttle`, by the email typed) | every attempt with that email, whether or not an account has it, reserved BEFORE its password is checked | the 5th attempt goes on and closes the email for 1 minute; each later one doubles it, up to 1 hour from the 11th. A run is forgotten 24 hours after its first attempt; a right password clears it | "Try again in a few minutes.", for a known and an unknown email alike, the right password included while the lock stands |
| A known device (`SignIn::Throttle`, by the email and the browser's `cs_known_device` cookie) | every attempt from a browser that has signed in to that account before, in place of the account's bucket | as the account's: the 5th closes that browser for that account for 1 minute, doubling to 1 hour; a right password clears it | "Try again in a few minutes." |
| The address, wide (`SignIn::Throttle`) | every attempt that went on from one address, whatever emails it tried; a success takes back its own count only | the 50th in an hour from the first, until that hour ends | "Try again later." |

An attempt one of the throttle's buckets refuses (the account's, a known device's, the wide one) checks no password, counts nothing in them (a bot trying through a lock does not lengthen it) and records nothing in the audit log; its spans carry it. The rate limit is Rails' and counts every POST before anything else is asked, a refused one included. Counting before the check is what bounds attempts made at once: a parallel run gets no more guesses per lock than a serial one (`test/models/sign_in/throttle_test.rb`: "attempts at once on one account let exactly five through before the lock", "attempts at once from one address let exactly fifty through"; `SignIn.store`'s comment names the one moment Solid Cache can lose a count, a key's first write). A count the store cannot make (a cache outage) opens the bucket and never answers 500.
Each bucket that a failed attempt closed is one `session.locked` event (`docs/reference/access-control-and-audit.md`, "The audit log"), and an account's lock queues the lock-out mail at most once an hour per email (`SignIn::LockoutMailJob`, `docs/reference/mail.md`, "The mails").

**A bot cannot keep a person out for good, and this is how.** A bot that knows an email can try once at each lock's end, about 30 requests a day from any addresses, and keep the account's bucket closed nearly all the time: a lock ends, and the first attempt after it closes the next. Three things keep the person in. Their own browser: a whole sign-in (a right password for an account with no second factor, a passkey, or the second step finished; `Admin::SignInCompletion#complete_sign_in`, never a password step that still owes its second proof) writes the encrypted cookie `cs_known_device` (OWASP's "device cookie"; HttpOnly, SameSite Lax, Secure over HTTPS, 90 days from the last sign-in; a random id and the HMACs of up to five accounts, never an email, `SignIn::KnownDevice`), and an attempt for an account the cookie names counts in that device's own bucket, which the account's closing does not touch (a bot never holds the cookie, which is written only by a whole sign-in; a cookie that does not open, or names another account, is no cookie). The address buckets and the bot check apply to it as to anyone, and a device's own lock closes that browser alone; a success on it clears the device's run and leaves the account's, so the bot gets no fresh run from it. A new password: `Users::UpdatePassword` (the reset, Your account, the console's command) and `Users::Save` (the wizard's owner, a password a manager types in the Users editor) clear the account's run and lock and every known device's (`Throttle#clear`: a device's keys name the account's generation, which it replaces), after the commit, so with the new password the person signs in at once from any browser, the one whose own failures closed it included. And the lock is never permanent. (`test/integration/sign_in_known_device_test.rb`: "a bot that closes the account at every lock's end for a day does not keep the person out of the browser they signed in with", "a forged, a tampered and another account's cookie are no known device", "a reset of the password opens the account to every browser", "a reset opens the browser whose own failures closed it, at once, with the new password", "a password a manager sets in the user editor opens the account to every browser", "the console's password command opens the account".)


**Passkeys and the second step** (`docs/reference/access-control-and-audit.md`, "Passkeys, recovery codes and the second step"). An account that holds a passkey or unused recovery codes is not signed in by its password alone: a right password is held five minutes for a passkey or a code, and that second proof counts in the account's bucket (or the known device's) as a password does, so a stolen password gets no more guesses and no device bucket of its own. A passkey sign-in names no account until it is verified and counts in the address's wide bucket alone, so a bot holding an account's bucket closed does not keep out a person who signs in with a passkey; nor does it keep out their known device. On a browser they never signed in with, a person whose password needs a second proof can still be delayed by a bot that closes the account's bucket at every lock's end, as a password-only account can: **no guard** measures it.

**The relying party, and a change of the site's domain.** A passkey belongs to the relying party `SignIn::RelyingParty` decides, and a browser binds it to that id for good. Its address is `ADMIN_HOST` when CS Studio has one (every passkey ceremony is under `/<ADMIN_PATH>/`, which then answers on that host alone; "Behind a DMZ"), otherwise `PUBLIC_HOST`; the id is the registrable domain of that address's host (`cms.example.org` and `example.org` both give `example.org`; a host on a public-suffix service such as `foo.github.io` stays itself, and a host with no registrable domain, such as `cms`, is its own id), and the address's origin is the only one a passkey is accepted from; with neither, the request's host. An IP address has no relying party (WebAuthn refuses one), so a site whose `PUBLIC_HOST` is an IP, or development reached at 127.0.0.1, offers no passkey: no button, every passkey endpoint 404, nobody held at enrolment, and the wizard's step goes on. Moving a site (or, with `ADMIN_HOST`, CS Studio) to another registrable domain therefore orphans every passkey made under the old one, and changing only the subdomain keeps them; turning `ADMIN_HOST` on or off, or changing it, is such a move unless the old and the new host share a registrable domain. After such a move a person signs in with their password and a recovery code (the second step's "Use a recovery code"), adds a new passkey in Your account, and removes the old one; one with no code left is cleared from the console ("The reset mail", below). The old passkeys stay listed on Your account until removed; no browser offers them on the new domain.

**The bot check** is Cloudflare Turnstile, verified on the server (`SignIn::BotCheck`), and on only with both `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`; one alone is no check, and production's boot says which is missing (`[ContentSpiel] The bot check is off: TURNSTILE_SECRET_KEY is not set.`, `config/initializers/sign_in.rb`). It is due after 3 attempts that went on from the address, or with the email, in 15 minutes, and asked before the reservation, so an attempt without a token costs the account nothing and checks no password ("Complete the check, then sign in again."). The widget is drawn only while it is due. A widget that cannot load (a privacy extension blocking Cloudflare's script, the site's host missing from the widget's hostnames) sends no token, so the attempt is refused as a check left unanswered; the page says "The check couldn't load. Reload the page to try again.", and when it still does not load the check stops being due 15 minutes after the first of the attempts that made it due; wait that long, or sign in from where the widget loads. A token passes when Cloudflare says `success` for this site's host (the request's) and the widget's action `sign_in`; a token minted on another host with the same key, or by another widget, fails. Make the keys in Cloudflare's dashboard (Turnstile → Add widget), with the site's host name under its hostnames.

- **The page's policy.** A browser takes a page's Content-Security-Policy from the response that loaded the document, never from what Turbo fetches into it, so on a site with both keys every answer of the sign-in page carries the site's policy with `https://challenges.cloudflare.com` added to `frame-src` (and to `script-src` and `default-src` where the site sets them), the page asks Turbo to load it whole (`<meta name="turbo-visit-control" content="reload">`), and Sign in sends the form without Turbo. Without the keys the page is the site's policy and a Turbo form.
- **Failing open.** Cloudflare unreachable, an answer other than 200, a body that is no JSON object, or a refusal for a reason of the site's (`internal-error`, a mistyped or missing secret: every code but `invalid-input-response` and `timeout-or-duplicate`) is `unavailable`: the attempt goes on as if the check passed, and one line says why, `[ContentSpiel] The bot check could not be verified: <class, status or code>`. An outage or a wrong key must not lock an owner out of their own site, and the buckets stand without the check. Siteverify is given 2 seconds to connect and 3 to answer, 5 in all.
- **In development** no key is set and no check is drawn. Cloudflare's test keys (site key `1x00000000000000000000AA`, secret `1x0000000000000000000000000000000AA`, on any host, `localhost` included) draw a widget that always passes, but a test secret's siteverify answers with the host `example.com` and no action, which this check refuses as a token of another site: with them the widget shows and every check fails. They are good for seeing the widget and the refusal; the passing path needs a real widget with `localhost` among its hostnames.

**The leaked-password check** (`SignIn::LeakedPassword`, `Users::LeakedPasswordRule`) refuses a password a person sets when Have I Been Pwned lists it ("This password is in a list of leaked passwords, so it isn't safe to use. Choose another one."), in the setup wizard, an invitation's acceptance, the reset, Your account and the Users editor (`docs/reference/users-groups-tokens.md`, "Users"). **What leaves the process** is five hex characters, the start of the password's upper-case SHA-1, in the path of `https://api.pwnedpasswords.com/range/<prefix>`, with `Add-Padding: true` so the answer's size says nothing either; the other 35 characters are compared here. It is on in production and off in development and test, so the seeded password and the suite ask no network; `LEAKED_PASSWORD_CHECK=off` turns it off and `on` on, anywhere, and any other value is on. It **fails open**: a status other than 200, a network error, or a body that is not the range's lines (a captive portal's page) accepts the password with one line, `[ContentSpiel] The leaked-password check could not be made: <class or status>`; a person must be able to set a password while the service is down. 2 seconds to connect, 3 to answer, 5 in all. The console's `Users::UpdatePassword` (the command in "The reset mail", above) asks it too, and prints `false` for a leaked password; the seeds and a direct write of the model do not.

**Cloudflare's rate limit, set by hand.** A site behind Cloudflare can add a fence in front of the app's buckets, at Cloudflare's edge, before a request costs the server anything. It is a first fence only: the buckets stand without it, and it knows no account. In the zone: Security → WAF → Rate limiting rules (Security rules → Create rule → Rate limiting rule on the newer dashboard), one rule:

- **Expression**: on Business and above, `(http.request.uri.path eq "/<ADMIN_PATH>/sign-in" and http.request.method eq "POST")`, with the admin path as `ADMIN_PATH` sets it (`/cs-studio/sign-in` by default). The Free and Pro plans offer no method field in a rate limiting rule, so there the expression is the path alone, `(http.request.uri.path eq "/cs-studio/sign-in")`, which counts the page's GETs too: one attempt is a POST and the GET its redirect lands on.
- **Counted by** IP (the only choice below Business).
- **Rate**: on Free the period and the timeout are fixed at 10 seconds, and the action is Block, so 10 requests in 10 seconds (five attempts) blocks the address for 10 seconds; on Pro and above a longer period (Pro up to 1 minute) and Managed Challenge, which a person passes, for example 10 requests in 1 minute.
- **Action**: Managed Challenge, or Block (Free). A challenge needs an HTML answer, which a full-page form gets.

The figures are Cloudflare's availability table as of 2026-11-10 (https://developers.cloudflare.com/waf/rate-limiting-rules/#availability); check it when setting the rule. **Cloudflare Access** in front of `/<ADMIN_PATH>` may stay as an extra layer, and one policy on that path alone now covers the whole backend (the screens, sign-in, the preview, the setup wizard, MCP and Action Cable): the app's buckets and checks do not assume it is there or gone.

**Cloudflare Access and MCP, and invitations.** Access's login is interactive, which an MCP client cannot complete, so a client of `POST /<ADMIN_PATH>/mcp` behind Access needs an Access service token (the client sends `CF-Access-Client-Id` and `CF-Access-Client-Secret`) or a Service Auth policy on `/<ADMIN_PATH>/mcp`; the endpoint's own bearer token is checked after Access lets the request in. An invited person's link (`/<ADMIN_PATH>/invitation`) is behind the same guard, so the invitee needs an Access policy that admits them before their link works.

**Behind Cloudflare the address must be the visitor's**, or every bucket that counts an address counts the edge: the 50th failure from anyone closes sign-in for an hour for everyone, owners included, and three failures show the bot check to all. Such a site sets both `TRUSTED_PROXIES` to Cloudflare's ranges and `proxy.forward_headers: true` in `config/deploy.yml` ("The visitor's address behind a proxy", below); System status's "Visitor address" row warns while either is missing.

Tests: `test/models/sign_in/throttle_test.rb`, `password_attempt_test.rb`, `bot_check_test.rb` (Cloudflare and Have I Been Pwned are never asked: `with_bot_check` and `with_leaked_password_check` answer in their place, and the HTTP call itself is held against a server on 127.0.0.1, `test/support/sign_in_helper.rb`), `leaked_password_test.rb`; `test/integration/sign_in_throttles_test.rb` ("the fifth failure records one session.locked with the bucket, level and seconds, and the sixth attempt in that minute records nothing", "the right password during a lock is refused with the same sentence, and once the lock ends it signs in and the count starts again", "behind a trusted proxy two people count in two wide buckets, and the fiftieth failure of one leaves the other signing in", "the eleventh attempt in three minutes from one address is limited until the three minutes end"); the widget in a browser, `test/system/admin/sign_in_bot_check_test.rb`.

## The visitor's address behind a proxy

Every limit that counts a visitor counts `request.remote_ip`: sign-in's buckets (the address's 10 attempts in 3 minutes and its 50 failed attempts in an hour, "Sign-in on the open internet", above), the trigger of the bot check, and the forms' 5 sends in 10 minutes. Rails finds that address in `X-Forwarded-For`, skipping the hops it trusts from the nearest backwards, and the first hop it does not trust is the visitor. By default it trusts loopback and the private ranges (`ActionDispatch::RemoteIp::TRUSTED_PROXIES`), so kamal-proxy on the same host needs nothing.

**A CDN in front is a public address Rails does not trust.** Behind Cloudflare, which `config/deploy.yml` plans for, the header reads "visitor, Cloudflare's edge" by the time kamal-proxy hands it on, and the edge is the first hop Rails does not trust: every visitor counts as one of a few edge addresses. Fifty failed sign-ins from anyone then close sign-in for an hour for everyone, owners included; three failures show the bot check to all; the sixth form send in ten minutes, from anyone, is refused with "Too many messages".

**`TRUSTED_PROXIES`** names the CDN's ranges, comma-separated, and `TrustedProxies.apply` (`lib/trusted_proxies.rb`, called from `config/environments/production.rb` after `HostSettings.apply`) adds them to Rails' list, never in its place, as `config.action_dispatch.trusted_proxies`. A bare address is a range of one; an entry that is not an address or a range (a typo, an empty entry between two commas) stops the boot with a message that names it. Unset or blank, nothing changes. Like the other variables it is read when the application starts.

Behind Cloudflare it holds Cloudflare's published ranges, both lists of https://www.cloudflare.com/ips/ (`https://www.cloudflare.com/ips-v4` and `https://www.cloudflare.com/ips-v6` serve them as plain text, one range a line). Joined into one value:

```sh
{ curl -fsS https://www.cloudflare.com/ips-v4; echo; curl -fsS https://www.cloudflare.com/ips-v6; } | grep . | paste -sd, -
```

and the result goes into the site's environment (with Kamal, `env.clear` in `config/deploy.yml`: `TRUSTED_PROXIES: "173.245.48.0/20,…"`). The ranges are written into the site and not fetched at boot, so a start never depends on Cloudflare's page. **They change rarely, and are re-checked at every upgrade**: a range Cloudflare adds and the site lacks makes the visitors who come through it count as that edge again, which System status shows the next time someone who comes through it opens it.

kamal-proxy must hand on the header Cloudflare sent: with `proxy.ssl: true` it drops the incoming `X-Forwarded-For` and writes its own, naming only Cloudflare's edge, unless `proxy.forward_headers: true` is set. Without that the visitor is lost before Rails reads anything, whatever `TRUSTED_PROXIES` says, so a site behind Cloudflare sets both (`config/deploy.yml` and the site template's carry the line, commented, under `proxy:`). The row below warns in that case too, in the same words: a warning that stays after `TRUSTED_PROXIES` is set is this.

Trusting Cloudflare's ranges also trusts any request sent from Cloudflare's network with an `X-Forwarded-For` its sender wrote (a Worker that fetches the origin directly, say), which could rotate the address every limit counts. That is inherent to trusting a CDN: keep the origin reachable only through the zone, or firewall it to Cloudflare's ranges.

**System status's "Visitor address" row** (`Setup::SystemCheck#visitor_address`, the wizard's system check too) compares the request's `CF-Connecting-IP`, the visitor's address as Cloudflare saw it, with `request.remote_ip`. No header: OK ("Each visitor counts by the address their request comes from."). The two the same: OK. They differ: a warning, "Requests come through Cloudflare, but the visitor's own address is not read: every visitor counts as Cloudflare's. Set TRUSTED_PROXIES to Cloudflare's ranges.", with a link to this section. **The header never sets the address**: anyone can send it to a site that has no Cloudflare in front, so it only tells whether the setting is missing. A forged one makes the row warn for the person who sent it, and nothing else. Another CDN sends no such header, and the row says OK in front of it: nothing in the app can tell its edge from a visitor.

## Behind a DMZ

Some organisations put the backend where the public internet cannot reach it. A path prefix alone does not do that, so a host may give CS Studio a host of its own: `ADMIN_HOST`, with its scheme, beside `PUBLIC_HOST` (spec: `docs/superpowers/specs/2026-11-12-backend-under-admin-path-design.md`, "Behind a DMZ"). The same image, the same process and the same database serve both hosts; without the variable everything is as with one host.

**The routes.** `config/routes.rb` draws every route under `/<ADMIN_PATH>/` (the screens, sign-in, the preview, the setup wizard, MCP and the cable's mount) inside `constraints(HostRouteConstraint::Backend)`, and the public site's pages and the form send inside `constraints(HostRouteConstraint::Site)` (`app/constraints/host_route_constraint.rb`). Both read `SiteAddress.admin` **per request**, never while the routes are drawn, so a test switches them with `with_admin_address` and a route drawn in one environment holds in every other. Without `ADMIN_HOST` both match every request. With it, `Backend` matches the admin host alone and `Site` every host but the admin one: `config.hosts` already refuses every name but the two, so "not the admin host" is "the public host". A host is compared as `config.hosts` compares it, case-insensitively and with the port ignored.

**On the wrong host, a 404 and never a redirect.** A redirect would name the other host, and the admin host is what the DMZ hides. On the public host a backend path is not routed to the backend: it falls through to the page catch-all and is the public site's 404. On the admin host a page path finds no route and is a 404 too (`test/integration/admin_host_test.rb`: "every backend route is unknown on the public host", "every public route is unknown on the admin host", "on the public host the backend answers the public 404, with no redirect", "on the admin host a page path is a 404", "the admin host is matched as config.hosts matches it", "without ADMIN_HOST one host answers both").

**What answers on both hosts.** `/up` (the proxy asks it on either name, and host authorisation already leaves it out) and Active Storage's routes (a public page and a CS Studio screen embed the same files) carry neither constraint ("/up answers on both hosts", "a made width of a library image answers on both hosts"). The setup-required redirect and refusal stand outside both as well: inside the site's constraint they would stop gating CS Studio on the admin host while setup is pending. On the admin host they send to the wizard, which answers there; on the public host their target is a 404, which says nothing of the admin host ("while setup is pending the admin host is sent to the wizard, which answers there").

**Sessions and forms.** No cookie is given a `domain:`, so the session cookie is the admin host's alone and the public host never receives it ("the session cookie has no Domain attribute"; "no cookie is given a domain" refuses a `domain:` anywhere under `app`, `config` and `lib`). Request forgery protection is unchanged: a form's token belongs to the session it was drawn in, and the origin check compares with the request's own host.

**The cable.** It is mounted at `/<ADMIN_PATH>/cable` inside the backend's constraint, so it answers on the admin host alone. Who may open it is Action Cable's own same-origin rule (`allow_same_origin_as_host`, on by default): the admin host's pages are let in and every other origin is refused. No `allowed_request_origins` is set, and the content security policy sets neither `connect-src` nor `default-src`, so it does not restrict the socket; a change to either changes who the socket accepts ("the cable accepts its own origin and no other", "the content security policy restricts neither connect-src nor default-src").

**Addresses CS Studio hands out.** Every link a mail builds into CS Studio names the admin host, which wins over `PUBLIC_HOST` and over the request's origin in `ApplicationMailer#link_origin`: the reset mail's link, the lock-out mail's reset request link, the invitation's link, and the "Your account" link of the passkey-added and recovery-code-used mails (`test/mailers/passwords_mailer_test.rb`, `invites_mailer_test.rb`: "with an admin host the link names it, and without one it names the public host"; `sign_in_mailer_test.rb`: "with an admin host the reset request's and Your account's links name it, and without one the public host"; "a reset mail's link names the admin host"). `FormsMailer` and `SystemMailer` link nowhere. The API tokens screen's MCP address and client configuration name the admin origin (`Admin::ApiTokensController#mcp_url`; `test/integration/admin/api_tokens_test.rb`: "with an admin host the client configuration's url names it"). A preview link is a path, so it stays on the host CS Studio was opened on (the addresses a preview prints in its head name that host, below), the editor's copy link to a published page names `PUBLIC_HOST` ("the editor's copy link to a published page names the public host"), and "View on site" and a live record's "Exit preview" open the public host (`PublicSite::Urls.studio_link`, below). System status (and the wizard's system check) shows a "CS Studio address" row, OK, saying CS Studio answers at the admin origin alone and the public address answers none of its pages, only while `ADMIN_HOST` is set (`Setup::SystemCheck#admin_address`, words under `admin.system_status.admin_address`; `test/models/setup/system_check_test.rb`: "with an admin address the CS Studio address row says where CS Studio answers", "without an admin address there is no CS Studio address row").

**Passkeys follow the admin address.** Every passkey ceremony (sign-in, the second step, Confirm it's you, enrolment, Your account's add, the wizard's step) is under `/<ADMIN_PATH>/` and so runs on the admin host alone; `SignIn::RelyingParty` therefore takes `ADMIN_HOST` when it is set: the id is the registrable domain of the admin host (or the host itself when it has none: `studio.example.internal` gives `example.internal`, `cms` gives `cms`), and the one allowed origin is the admin origin (`test/models/sign_in/relying_party_test.rb`: "with an admin host in another domain the id and origin are the admin host's", "with an admin host in the public host's domain the id is shared and the origin the admin host's"; `test/integration/admin_host_test.rb`: "a passkey signs in on the admin host, under the admin host's relying party", "the registration options on the admin host name the admin host's relying party"). **Turning `ADMIN_HOST` on or off, or changing it, orphans every passkey already made**, unless the old and the new host share a registrable domain (`www.example.org` and `studio.example.org` share `example.org`, and their passkeys keep working; `studio.example.internal` shares nothing with `www.example.org`). After such a switch a person signs in with their password and a recovery code (the second step's "Use a recovery code") and adds a new passkey; one with no code left is let back in from the console with `remove_passkeys: true` ("The reset mail", above), and then enrols again. A site that wants its passkeys to survive the switch puts the admin host under the public host's registrable domain.

**Single sign-on follows the admin address.** Its two routes, the start (`POST /<ADMIN_PATH>/sign-in/sso`) and the provider's callback (`GET /<ADMIN_PATH>/sign-in/sso/callback`), are the app's own, inside the backend's constraint, so with `ADMIN_HOST` they answer on the admin host alone and the callback on the public host is the public 404. The redirect URI the provider is told, and must have registered, is built once per start from `SignIn::Oidc.callback_origin`: the admin origin when `ADMIN_HOST` is set, else `PUBLIC_HOST`'s, else (development and test) the request's, followed by `/<ADMIN_PATH>/sign-in/sso/callback`; the callback exchanges the code under the same string. The state's cookie (`cs_sso_state`) has no `Domain` and is pathed to `/<ADMIN_PATH>/sign-in/sso` (`test/integration/admin_host_test.rb`: "with an admin host the redirect URI names it, the callback answers there alone, and the public host's callback is the public 404").

**Readers of the public address that run on the admin host, and why.** A request under `/<ADMIN_PATH>/` that reads `SiteAddress.current` (directly, or through `PublicSite::Urls.configured_host`) is listed here with its decision, so a new one is decided rather than inherited:

- `SignIn::RelyingParty` follows the admin address when there is one, and reads the public address only when there is none (above).
- `SignIn::Oidc.callback_origin`, the single sign-on redirect URI's origin, decides as `SignIn::RelyingParty` does (above).
- `PublicSite::Urls.studio_link`, the one rule for a CS Studio link to a live public page: the editor's "View on site", the posts list's "View on site" and the preview bar's "Exit preview" of a live record. Without `ADMIN_HOST` they are paths, opening on the host CS Studio was opened on; with it, the path on the public origin, since a relative link would open a page path on the admin host, which is a 404 (`test/components/admin/editor_screen/header_component_test.rb`, `test/components/admin/posts_screen/table_component_test.rb`: "View on site is the path on one host and the public URL when CS Studio has its own"; `test/components/public/preview_bar_component_test.rb`: "Exit preview of a live page is its path on one host and its public URL when CS Studio has its own"; "View on site opens the public host").
- The editor's Copy address (`Admin::EditorScreen::HeaderComponent#absolute_urls`) and MCP's post URLs (`Mcp::PostSerializer`) keep the public address: they name a page as a visitor reaches it.
- `Admin::MailLinkOrigin` keeps it: it asks only whether an address is configured, to decide whether to hand the request's origin to a mail at all. With `ADMIN_HOST` the public address is configured too (the boot refuses one without the other), so it hands nothing on and `ApplicationMailer#link_origin` takes the admin address.
- `MailSettings.current` keeps it: production without a site address has mail "Not set up", and `PUBLIC_HOST` is always set beside `ADMIN_HOST`.
- `Setup::SystemCheck` reads both: the "Site address" row describes the public address, the "CS Studio address" row the admin one.

A preview's canonical, alternate and Open Graph addresses are built from the request (`PreviewController`, `PublicSite::Urls` over `request.base_url`), so on the admin host they name the admin host. That is harmless: a preview is `noindex`, is drawn only for a signed-in person and is never served on the public host, so the name stays inside the network. A form drawn in a preview posts its send to the public site's path on the host it was opened on, and **with `ADMIN_HOST` set the send is refused on the admin host** (the form route carries `HostRouteConstraint::Site`, so it is a 404 and the preview shows the form's network error): a preview then makes no real submissions, which is accepted. Without `ADMIN_HOST` a send from a preview is a real submission, stored with no page (`docs/reference/forms.md`).

**What the host arranges.** The admin host needs its own entry in the proxy in front of the app: kamal-proxy routes only the hosts it is given, so `proxy.hosts:` in `config/deploy.yml` names both (one `proxy.host` answers kamal-proxy's 404 on the other), or the admin host has its own proxy or load balancer. It also needs a certificate it can obtain: kamal-proxy's Let's Encrypt cannot issue one for a name that resolves only inside the network (`studio.example.internal`), so such a host takes a certificate from the organisation's own CA, or one issued by a DNS challenge for a name in a public domain, on the proxy or load balancer that serves it. The admin hostname resolves only inside the network (split DNS, or a load balancer listening on the internal interface alone), and is not proxied by the CDN in front of the public site, or has an Access application of its own; the Cloudflare Access policy on `/<ADMIN_PATH>` of "Sign-in on the open internet" then belongs on the admin hostname. `TRUSTED_PROXIES` is one setting for the process, so it covers both hosts: the public host's CDN ranges, and whatever internal proxy stands in front of the admin host when it is not on a private range Rails trusts already. The public host's proxy or WAF may refuse `/<ADMIN_PATH>/*` outright as an edge rule; without it the application answers 404 there anyway. A separate job container needs `ADMIN_HOST` as it needs `PUBLIC_HOST`, or its mails link to the public host.

**Not built: a public-only role.** Some organisations want no admin code reachable from the DMZ at all, not just unanswered: a process role in which the backend's routes, the cable, MCP and setup are not drawn, the database user only reads, and jobs and sweeps run on the admin box alone. It is named in the spec as a later, separate step and listed in `docs/roadmap.md`; today both hosts are served by one process that holds the whole application.

## Forms

A site's forms ask three things of its host (`docs/reference/forms.md`).

**Active Record encryption keys.** A visitor's answers are stored encrypted, and nothing else may hold them, so **a site without the keys takes no answers at all** (owner's ruling 2 on the forms plan, which bends the spec's "a site without keys can only mail submissions"): there is no mail-only path and no sealed copy in a job. Without them every form on the site is drawn with "This form can't take answers at the moment. Please try again later." and its fields disabled, a send is answered 503 and nothing is written or queued, keeping cannot be switched on, a gem destination's secret cannot be stored, and System status's Forms row says "This site has no encryption keys, so its forms can't take answers." The keys are the same three the AI key and the mail login need, provided in one place (`docs/reference/translations.md`, "Active Record encryption keys"). `Forms::Encryption.available?` is asked once per process outside test, so keys added to a running site take effect at the next start. **Keys that change after submissions were kept** make those unreadable ("Can't be read", deletable), and **keys that go** make no kept submission disappear: the daily clean-up decides from each form's stored setting, never from whether the keys are there.

**The answers are filtered from the request log by where they arrive**: a lambda in `config/initializers/filter_parameter_logging.rb` masks every String under `answers` or a field's key in a request to the controller `form_sends`, and nowhere else (not a bare `:answers`, which would match by substring and drop a snapshot key such as `faq_answers` from the audit log). Spans hold no body and no query string (Telemetry, above). Rails' own first request line still names the visitor's address ("Started POST "/forms/1" for <address>"), as for every request; it holds no answer.

**Forms behind a CDN.** The per-visitor rate limit (5 sends in 10 minutes) counts `request.remote_ip`, an IPv6 address by its /64, which is right only behind proxies Rails trusts. **A CDN in front (Cloudflare, which `config/deploy.yml` plans for) is a public address Rails does not trust**: every visitor then arrives "from" the CDN's edge, they all share one counter, and the sixth visitor in ten minutes is refused with "Too many messages". Such a site sets `TRUSTED_PROXIES` to the CDN's published ranges ("The visitor's address behind a proxy", above), and System status's "Visitor address" row warns when Cloudflare's header shows the setting missing; in front of another CDN nothing detects it (`Forms::SendLimit`'s comment, "WHO THE VISITOR IS"). The per-form limit (30 in 10 minutes) is unaffected.

## Releases

The CMS is released as numbered images that a site names (`ContentSpiel::VERSION` in `lib/content_spiel/version.rb`, `ContentSpiel::IMAGE` for the image's name). **The numbering rule:** `0.x.y` before 1.0. A breaking change to what themes or plugins rely on (the theme contract, the plugin hooks, an environment variable, a migration that needs action) raises the minor number; anything else raises the patch. A section's subsections are read in one order, by the GitHub Release and by `contentspiel upgrade` alike (`ContentSpiel::Release::FIRST`, through `Release.notes(…, ordered: true)` and `Release.order`): Breaking, Theme contract, Removed, Migrations needing action, Environment, then the rest in the file's order. **Every migration gets a line** under `### Migrations`, naming its version and saying what it does; `### Migrations needing action` is for the ones a person must also act on (`bin/changelog-guard`, below). Everything between releases is the commit image `ghcr.io/<owner>/content_spiel:<40-character sha>` that `image.yml` pushes on every merge to `main`.

**Cutting one.** From a clean `main`:

```sh
bin/rails 'release:prepare[0.5.0]'
```

`VERSION` is `0.0.0` until the first release, which is `release:prepare[0.1.0]`. It refuses a dirty tree, a number that is not greater than `VERSION`, a tag `v0.5.0` that exists, and an empty `## Unreleased` in `CHANGELOG.md`. Otherwise it rewrites the `VERSION` line, renames `## Unreleased` to `## 0.5.0 (today's date)` with a fresh empty `## Unreleased` above it, and prints four commands: `git switch -c release-0.5.0`, the commit, `git push -u origin release-0.5.0` and `gh pr create`. It runs none of them and touches no file but those two (`ContentSpiel::Release`, `test/lib/release_task_test.rb`). Run the commands, review the pull request, merge it.

**The changelog guard.** `bin/changelog-guard origin/<base>` runs in CI for every pull request (`ci.yml`, the base branch handed in through `env:`): a change to `test/support/contract_ledger.rb`, `lib/content_spiel/plugins.rb` or a file under `db/migrate/` fails it until `## Unreleased` changes too, and a migration the pull request adds fails it until its version is named under `### Migrations` in that section (`test/lib/changelog_guard_test.rb`). The environment is not guarded; the pull request template's checkbox asks for it.

**What the merge does.** `image.yml` builds the merge commit's amd64 image as for any merge. When it completes successfully on `main`, `.github/workflows/release.yml` (a `workflow_run`, so it never races that build) checks the push and the repository, and compares the commit's `VERSION` with the newest `v*` tag (`sort -V`); when it is not newer the run does nothing and is green, which is every merge but a release. A `VERSION` that is newer must also be a plain `MAJOR.MINOR.PATCH`, have no tag yet, have its dated section in `CHANGELOG.md`, with something in it beyond whitespace (`Release.notes` refuses an empty one, and its sentence is the run's error), and both install files present, **or the run fails before anything is pushed**. Then it builds `linux/arm64` from the same Dockerfile on an arm runner under the tag `<sha>-arm64`, joins that and the commit's amd64 image into the manifests `0.5.0` and `stable` (`docker buildx imagetools create`; the `<sha>-arm64` tag stays, the manifests refer to it), tags the commit `v0.5.0` and creates the GitHub Release, whose notes are the changelog section of that version in that order and whose assets are `install/install.sh` and `install/contentspiel`. There is no `latest`, for the reason `image.yml` gives. **A failed run releases nothing and tags nothing**, so `VERSION` stays newer than the newest tag: the next merge to `main` whose `image.yml` succeeds is released under that number, from its own commit (or the failed run is re-run, for the commit it was about). **Unproven until the first release is cut**: nothing in a test runs the workflow.

**Each release gets a post on the documentation site.** The guide (`contentspiel-docs`) keeps one post per release in its `posts/` folder, written from that version's changelog section and held back with `draft: true` until the release exists. Cutting a release includes, in that repository, setting the post's `date` to the release's and removing its `draft`, then loading the guide: the post is listed on the site's "What's new" page.

**What the site template's CI job holds.** `image.yml`'s job `site-template` runs after every image it pushes (a merge to `main`, or by hand): it runs that image's own `--version`, `new`, `generate`, `check`, `dev-files`, an `upgrade` that has nothing to do and, once `VERSION` is past `0.0.0`, an `upgrade` from a pin of `0.0.0` that must say "Next steps", leave the pin at the image's version and the site's files the runner's (skipped until the first release, since a commit before it is `0.0.0` itself), as the wrapper runs them (the runner's uid, the folder mounted at `/site`), builds the site's image `FROM` the commit's image, and starts production under it until `/up` answers. Its Postgres runs with the CMS's database user as the superuser, and the template's init script (`config/postgres/10-contentspiel-databases.sh`) is not run: `db:prepare` makes the four databases itself. What the script does for an ordinary role is proved by the documentation site, whose database is made by it, and not here. `release.yml` runs only on a successful `image.yml`, so a template that does not build or boot gives its commit no release number. It never runs for a pull request: a change that breaks the template shows on `main`, after the merge.

## A site's version

A site names the CMS release it is built on in ONE file at its top, `.contentspiel-version`: one line, a release number `X.Y.Z`. Everything else reads it there.

- **The site's image.** The generated `config/deploy.yml` reads the file (in its ERB head; a missing or empty file stops Kamal with a sentence) and hands it to the site's `Dockerfile` as the build argument `CMS_VERSION`, which has no default, so the image is `FROM ghcr.io/dominikknafelj/content_spiel:<the pin>` and a build without it stops.
- **The command.** The `contentspiel` command, run in the site's folder or any folder under it, runs the image of that version: every tool a site uses (`generate`, `check`, `dev`) is its pinned version's.
- **`contentspiel upgrade`** is the one command that runs another version: the wrapper pulls `stable` and runs it, and that image reads the pin, prints every changelog section after it up to its own version (oldest first; each in the order above, Breaking first), runs the theme check on the site's `theme/` in process, and only when that has no problem writes its own version into the file (through a temp file and a rename, keeping its mode). It refuses a pin that is not `X.Y.Z` (`stable` included: it is a way of running a command, not a version a site is on) and a pin newer than itself; a pin that is already its version is "Nothing to do." Its output is plain text under three fixed headings ("Release notes", "Theme check", "Next steps"), for an AI tool as much as for a person (`ContentSpiel::Upgrade`, `test/lib/upgrade_test.rb`). It commits nothing and deploys nothing: the owner commits the pin and runs `kamal deploy`, and migrations run at the deploy's boot as for any image.
- **Going back** is writing the old number into the file and deploying. It is safe only across releases with no migration: `upgrade`'s next steps say so, with the backup command, when a section between the two has "Migrations" or "Migrations needing action".

**What the image promises a pinned site.** A release image `X.Y.Z` is a manifest for `linux/amd64` and `linux/arm64`, pushed once, by `release.yml`, for a version that has no tag yet; `stable` moves to each new release. Its `CHANGELOG.md` holds every release's notes up to its own, which is what `upgrade` reads, so the only network use of the whole command is image pulls. A site that pins a commit (`CMS_REVISION`/`CMS_TAG` in the documentation site's `Dockerfile`, from before releases) still builds: the commit tags stay. It moves to a release by hand, once, by writing `.contentspiel-version` and building `FROM` that tag; the guide has the steps.

**The site template.** `contentspiel new NAME` (`ContentSpiel::SiteGenerator`, `lib/site_template/`) writes, into a folder that must not exist: `theme/` (the very code of `theme:new`, `Theme::Scaffold`), `.contentspiel-version` (this image's `VERSION`), the `Dockerfile` (the five lines of "How a site's image is built", on `CMS_IMAGE:CMS_VERSION`), `config/deploy.yml` (three placeholders at its top, refused while left; every variable production reads; secrets by name only), `config/postgres/10-contentspiel-databases.sh`, `.dockerignore` (an allow-list of `theme/`), `.gitignore`, `.kamal/secrets.example` (names only), `seeds/README.md` (a place, nothing reads it) and `README.md`, the steps a person or an AI tool follows. It is written in a hidden folder beside the target and renamed into place when whole. `contentspiel generate section_style|page_template NAME "Label"` (`ContentSpiel::ThemeGenerators`) adds an entry to `theme/theme.yml`, edited as text, and its stub, by the declarations' own rules; `contentspiel check` is `theme:check` on `/site/theme`; `contentspiel dev` runs `.contentspiel/compose.yml`, which `contentspiel dev-files` (`ContentSpiel::DevFiles`) writes again at every start from the pinned image: the image in development with `theme/` mounted read-only, the stylesheet watch, Postgres 17, `127.0.0.1:3000` only, a stylesheet volume named with the version. The image runs in development although it was built without the development group (`DevFiles`' comment says what that forbids).

## The command and the image

Two POSIX shell files are published as assets of every GitHub Release, and nothing else of the command lives on a person's machine:

- **`install/install.sh`**, `curl -fsSL https://github.com/dominikknafelj/ContentSpiel/releases/latest/download/install.sh | sh`: checks that `docker version` answers, downloads the wrapper from the latest release (`releases/latest/download/contentspiel`, whichever release the script itself came from: the wrapper is frozen, so every release's is the same file) into `~/.local/bin` (`CONTENTSPIEL_BIN_DIR` for another folder) through a temp file, makes it executable, and says how to put the folder on `PATH` when it is not. No `sudo`; a failure leaves nothing behind.
- **`install/contentspiel`, the wrapper**, frozen: it never has to change with a release. It finds the version (the first line of `.contentspiel-version` in the current folder or the nearest parent holding one, which is then the site; none is `stable`), refuses a pin that is not `X.Y.Z` or `stable` (it becomes part of an image name), and runs `docker run --rm -i [-t] --user "$(id -u):$(id -g)" --mount 'type=bind,"source=<the site>",target=/site' -w /site <image>:<version> contentspiel ARGS…`. Docker reads `--mount` as one line of CSV, so the source is a quoted field (a `"` in the path doubled) and a site path with a comma, or a colon, is mounted whole. Two commands are run differently: `upgrade` pulls `stable` and runs it, and stops when the pull fails; `dev` runs `contentspiel dev-files` and then `docker compose -f .contentspiel/compose.yml up` from the site's folder. **Pulls**: inside a site no other command pulls (`docker run` pulls a pinned image only when it is missing); outside a site, where there is no pin and the image is `stable`, the wrapper pulls `stable` before every command, as `upgrade` does, so `contentspiel new` writes a site on the newest release and not on a `stable` left on the machine; when that pull fails it says "could not fetch the newest release; using the one on this machine" on stderr and runs the local one. A pull's progress is on stderr, so stdout is the command's result. `CONTENTSPIEL_IMAGE` replaces the image's name, to try a local build.

**The wrapper's one promise.** Every installed wrapper relies on these, all of them and nothing else, and every release keeps them:

- inside every image there is an executable named `contentspiel` on `PATH`, and it takes the arguments exactly as they were typed (`bin/contentspiel`, with `/rails/bin` last on the image's `PATH` and `bin/docker-entrypoint` handing a `contentspiel` command over with no `db:prepare`);
- it runs with the site's folder mounted at `/site`, which is the working folder;
- the subcommand `dev-files` writes `.contentspiel/compose.yml` into the site, and the wrapper's `dev` runs that file with `docker compose`;
- the image's tags: `X.Y.Z` for a release, which is what a pin names, and `stable` for the newest, which `release.yml` pushes;
- `upgrade` is the command the wrapper runs from `stable` (pulled first), as it runs every command outside a site.

Every command lives in the image, so a site's tools are always its version's and every wrapper ever installed keeps working. **A change to any of the five breaks every installed wrapper** and is a breaking change in the changelog's terms (`test/lib/install_scripts_test.rb`: "arguments reach the image unchanged, spaces, quotes and flags included", "the line carries the user's uid and gid, the site mount and the working folder", "the release pushes the tags every installed wrapper runs: X.Y.Z and stable", "upgrade pulls stable, then runs stable and not the pin", "dev runs dev-files in the image and then compose from the site folder"; `test/lib/site_generator_test.rb`: "the image finds contentspiel on PATH, and its entrypoint hands it over with no db:prepare"; `test/lib/theme_generators_test.rb`: "dev-files writes .contentspiel/compose.yml, which every installed wrapper runs").

**The entrypoint runs as a stranger to the image.** The host's uid and gid (501:20 on a Mac), not the image's 1000, so what it writes into the site belongs to the person: `HOME` becomes `/tmp` when it is no writable folder, Bootsnap reads the build's cache and writes none, nothing is written into `/rails`. No command connects to a database. `--version`, `help`, `dev-files` and every refusal answer without starting the application; `new`, `generate`, `check` and `upgrade`'s check start it, in production with `SECRET_KEY_BASE_DUMMY` and the log at fatal. A refusal is a sentence on stderr and exit 1; an unknown command is the usage and exit 2.

## What a change can break silently

- **A `..._url` helper or `request.base_url` in a public view** prints the host the client sent into a cacheable page. The guard refuses the line; it does not see an address handed in from a controller outside the scanned set or a `PublicSite::Urls` built with another host.
- **A host or HTTPS setting written into `production.rb`** (or a `config.hosts <<` in an initializer) is not seen by `HostSettings`' own tests, which hand in their own config, and can contradict the boot lines, which are computed from the address and not from the configuration. `test/lib/production_boot_test.rb` reads the booted configuration for an https address and for none and catches what changes those values; it does not catch a setting it does not print. Add it to `HostSettings.apply`.
- **`RAILS_LOG_LEVEL=debug` in production** puts the reset token into the log: Action Mailer writes every mail it delivers at debug, whole (`ActionMailer::LogSubscriber`), the reset mail's link with its fragment among it. It is Rails' behaviour and older than the token's move out of the address, and it is the one place left where the application itself writes a valid token. A form's submission mail is the one exception: `FormsMailer` puts a placeholder in the place of the mail, so a visitor's answers are in no log at any level (`docs/reference/forms.md`, "Personal data"). Production's level is info unless the variable says otherwise and must stay at info or above; the boot warns at debug and does not refuse. The development log has always held the mail.
- **A new route with a credential in its path or query** is logged by Rails' first request line, by the proxy and, for a path, by every span; `filter_parameters` masks a query parameter in Rails' own log only. Nothing fails. A credential travels in a fragment, a form's body or a header.
- **A new mail** that builds its link from `default_url_options` has no host to build it from on a site without an address (production's are `{}` then); one that takes the request's origin outside development and test reopens reset poisoning. Build a mailed link the way `PasswordsMailer#reset_url` and `InvitesMailer#invite_url` do, from `ApplicationMailer#link_origin`, where the rule is written once; a link into CS Studio built without its options names the public host, where CS Studio does not answer behind a DMZ (`test/lib/mail_guards_test.rb` refuses an admin route helper in a mailer or a mailer's view that does not take `**@url_options`, line by line: a call split over lines is not read).
- **A reader of `PUBLIC_HOST` or `ADMIN_HOST` beside `SiteAddress`** gets the raw value: not normalised, possibly with user info, and not refused.
- **A route's own `constraints:` option that is an object or a lambda** (not a hash of segment patterns) REPLACES the surrounding `constraints(HostRouteConstraint::…)` block in Rails' mapper instead of joining it, so the route answers on every host. Such a route is drawn inside a nested `constraints(…)` block (`LocaleRouteConstraint` on the localised page and preview routes; the comments in `config/routes.rb` say so). `test/lib/backend_paths_test.rb` finds the bare route ("the site's check can fail" draws one).
- **A test that sets `ENV["ADMIN_HOST"]` without `with_admin_address`** leaves the memoised admin address, and with it every host constraint, to the tests after it in the same worker.
- **A test that sets `ENV["PUBLIC_HOST"]` without `with_site_address`** passes alone and changes the tests after it in the same worker, since the address is memoised.
- **A new instrumentation whose work begins with an INTERNAL, CLIENT or PRODUCER root** (an Action Cable channel action today, a hand-made `in_span` with no kind) is dropped whole by `Telemetry::WorkSampler`, and nothing fails: it is simply not in the backend. Start such a root as `:server` or `:consumer` when it is work a person or a job caused.
- **A new span attribute that holds an address** (an instrumentation's own, under another name) is not in `PathScrubber::ATTRIBUTES` and leaves with its query string.
- **A link, a redirect or a script that puts the reset token into a path or a query** (the expired state reached with the token as a parameter, the check sent as a GET) writes it into the request's first log line and the proxy's access log, which no filter reaches. The early check is a POST with the token in its body for that reason.
- **Making the early check the rule** (dropping `update`'s own lookup, or showing the expired state when the check could not be made) either lets a lapsed token through or costs a good link on a bad connection.
- **A second job or web container without `PUBLIC_HOST`** sends no reset mail and says so only in its own log.
- **`includeSubDomains` or `preload` added to HSTS** cannot be taken back for a browser that has seen it.
- **A site image whose last stage leaves `app/assets/builds` behind**, or whose `assets:precompile` ran without `THEME_PATH`, does not start, and says so; one that mounts its theme as a volume is refused at the first start after the volume's content differs from what the stylesheet was built with. A theme is a layer.
- **`theme:check` moved after `assets:precompile`** in a site's Dockerfile still fails a refused theme's build, with a trace in place of the list. Nothing fails here: the order is a comment in the `Dockerfile` and the paragraph above.
- **A CDN in front of the site without its ranges in `TRUSTED_PROXIES`**, or behind Cloudflare without kamal-proxy's `proxy.forward_headers: true` (both are needed), makes every visitor one visitor to every per-address limit: fifty failed sign-ins from anyone close sign-in for an hour for everyone, owners included, three show the bot check to all, and the sixth form send in ten minutes, from anyone, is refused. Nothing fails; System status's "Visitor address" row warns behind Cloudflare, and says OK in front of any other CDN, which sends no header it can read ("The visitor's address behind a proxy", above). A range Cloudflare adds later and the variable lacks is the same mistake for the visitors who come through it.
- **A new outside call made without `untraced`** (a third check of sign-in's, a webhook, a lookup) is recorded by the Net::HTTP instrumentation with its path, and a path the scrubber does not cut can hold a credential or part of one, as the range lookup's holds five characters of a password's hash. Nothing fails unless a test plants the value. Send it through `SignIn::OutsideCall.perform`, or `OpenTelemetry::Common::Utilities.untraced` with a CLIENT span of fixed words named in `Telemetry::SPANS`.
- **Turnstile keys set with Cloudflare's test secret in production**, or a widget whose hostnames lack the site's host, fail every check that is due: the test secret answers for `example.com` with no action, which is refused as another site's token, and a widget does not render on a host its list lacks, so no token comes. Neither is a failure of the site's that would fail open. Sign-in still opens for whoever is not yet due (fewer than three attempts from the address and the email in 15 minutes). Nothing fails; the spans say `auth.bot_check.result` `failed`.
- **A `config.action_dispatch.trusted_proxies =` written beside `TrustedProxies.apply`** (in `production.rb` or an initializer) replaces the list the variable built, Rails' private ranges included when it names none of its own, and the proxy on the host becomes every visitor. Nothing fails. Add a range to the variable.
- **A site deployed without its Active Record encryption keys** takes no form answers, and says so on every form and in System status; a deploy that drops them keeps every kept submission, unreadable until the keys are back ("Forms", above).
- **A change to the wrapper's promise** (the entrypoint renamed or its arguments read another way, the mount point `/site`, the subcommand `dev-files` or the path `.contentspiel/compose.yml`, the tags `X.Y.Z` and `stable`, or `upgrade` no longer the command run from `stable`) breaks every wrapper ever installed, on its next command. The tests hold each part from both sides as they are today (`test/lib/install_scripts_test.rb` reads the wrapper and `release.yml`; `test/lib/theme_generators_test.rb`: "dev-files writes .contentspiel/compose.yml, which every installed wrapper runs", reads the image's side and the wrapper's line); they do not stop a change to both sides at once, which passes here and breaks the wrappers already on people's machines. It is a breaking change, never a refactor ("The wrapper's one promise", above).
- **A change that breaks the site template** passes a pull request's CI, which never runs the `site-template` job; it fails on `main` after the merge, and that commit then gets no release number until it is fixed.
- **A changelog line under an older release's heading** does not satisfy `bin/changelog-guard`, and a line under "Unreleased" is not checked for saying anything true: the guard sees only that the section changed, and for a new migration that its version is named under "### Migrations". A migration that is changed and not added needs only some change to the section.

## Rules a change can break silently

Moved word for word from `CLAUDE.md`, where "above" and "below" meant the list these rules stood in: a rule named that way may now be in another reference file. Each names the test that guards it; a rule or a part of one with no guard is also said in `CLAUDE.md`.

- An absolute address that a public view, component, helper or controller prints comes only from `PublicSite::Urls` through `public_urls`, whose host `PublicController#public_urls` sets to the site's configured address (`SiteAddress.current`): never `request.base_url`, `request.host`, `request.original_url` or a `..._url` helper, which answer with the `Host` the client sent, into a page that is the same for everyone and cached. `og:url`, every `hreflang` and the canonical link are built that way; with no address configured they follow the request and the public ETag takes the request's origin in, so a 304 never confirms a body printed under another host (`test/lib/public_address_guard_test.rb`: "no public view, component, helper or controller takes an address from the request", "every allowed line is still there", a source grep over a derived set of files with two allowed lines, which does not see an address handed in from elsewhere and does not look at headers: a redirect's `Location` follows the request; `test/integration/public_head_address_test.rb`: "under a foreign Host, og:url, every hreflang and the canonical link carry the configured address", "with no address configured an ETag obtained under one Host is not confirmed under another, and is under the same one").
- `PUBLIC_HOST` is read by `SiteAddress` and by nothing else, and `SiteAddress::Invalid` never repeats the value and carries no cause: the message goes to the boot log, and a value typed with a password in it would be printed there, by the message or by the cause Ruby prints under it, so the error is never raised from inside a `rescue`. A test sets the address through `with_site_address` only, because `SiteAddress.current` is memoised for the life of the worker (`test/lib/site_address_test.rb`: "the message names the variable the value came from and never repeats the value", "the refusal carries no cause: an uncaught one prints nothing of the value", "with_site_address puts both variables and the memo back, also when the block raises"; `test/test_helper.rb` removes the variable from `ENV` before the application loads, so the suite does not depend on the shell's; no guard finds a second reader of the variable or a test that sets `ENV` itself).
- `config/environments/production.rb` decides nothing about hosts, HTTPS or the address in mailed links itself: it calls `HostSettings.apply(config)`, which sets `config.hosts` (the address's host, matched exactly: not `www.`, not another subdomain), `host_authorization` and the redirect's exclusion (`/up` and nothing beside it), `force_ssl` (the address's scheme; there is no `FORCE_SSL`), HSTS (exactly `max-age=31536000`: no `includeSubDomains`, no `preload`, neither of which a server can take back), `assume_ssl` (`ASSUME_SSL=1` and no other value) and `action_mailer.default_url_options`. A setting written beside it is seen by none of its tests and can contradict the boot lines, which are computed from the address (`test/lib/host_settings_test.rb`: "an https address: its host is the only one answered, HTTPS is forced and mailed links carry it", "HSTS is one year for this host alone: no subdomains, no preload, whatever Rails' default is", "assume_ssl is on for ASSUME_SSL=1 and for nothing else"; `test/integration/host_settings_test.rb`: "plain HTTP for another host is refused, never redirected to that host", "under an https address another host is refused, www. and a subdomain included", "only /up is the health check: beside it and under it nothing is answered by IP"; `test/lib/production_boot_test.rb` boots production in a child process and reads the configuration it ends with and the boot's lines: "production with an https address answers that host alone, forces HTTPS, mails the address and says so at boot", "production with no address refuses and forces nothing, says so, and warns about a debug log level", "production with a PUBLIC_HOST that is no address does not start, and says which variable without repeating it", which fail when the call is removed from `production.rb`, when `force_ssl` is set under it and when the announcement initializer loses a line; a setting it does not print is still unseen).
- No credential is part of a route's path or query: Rails writes a request's path to its log before the router is asked, a span holds it, and the proxy's access log, which is not this application's to filter, holds it too. The password-reset token travels in the mailed link's fragment (`<admin>/password/edit#<token>`), which a browser sends to no server, and from there in the form's body, where `filter_parameters` masks it;
