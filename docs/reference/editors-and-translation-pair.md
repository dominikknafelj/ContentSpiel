# The page and post editors

> Describes: `app/components/admin/editor_screen/`, `app/components/admin/posts_screen/`, `app/controllers/admin/pages_controller.rb`, `app/controllers/admin/posts_controller.rb`, `app/javascript/rich_text/`.

## Editor header

**Editor header.** One component serves the page and the post editor (`Admin::EditorScreen::HeaderComponent`, sticky): a breadcrumb row (a page's ancestors, a post's content type; a crumb the viewer may not open is plain text) carrying the save status, Preview, one primary action and a ⋯ menu; the title with its status chip; the public path (always shown while the record has one; "View on site" only while live); the language tabs; and a `suggest` slot for "Suggest translations for N empty fields". A live record has no primary button at all — only the hint that its changes appear on the site as soon as they're saved; a draft offers Publish, a scheduled record "Publish now" and "Edit schedule". Everything else sits in the ⋯ menu: Activity (`audit.view`), Schedule… (a draft only; **no scheduling a live record**), Unpublish, and Move to trash last after a divider (the homepage can't be). Every publish/unpublish/schedule/trash form carries `data-turbo-frame="_top"` so the answer re-renders the tree and the sidebar's Trash badge. The dialogs are siblings after the `<header>` (it is sticky and would clip a modal). Schedule is `Admin::EditorScreen::ScheduleDialogComponent`: a `datetime-local` read in the site time zone (the line below the field names it), "Remove schedule" when one exists, and the rules of `Admin::Scheduling` — a time in the future, at most 50 years ahead — enforced by the controllers' `schedule` actions and not by `Pages::Save`/`Posts::Save`, which may set a past `published_at`; a refusal travels as `flash[:schedule_error]` (never a toast) and reopens the dialog with it. **View only:** a readable record the viewer can't edit gets a "View only" badge and a hint (including "changing a live post needs the right to publish" for the interim publish rule), its form fields are wrapped in `<fieldset disabled>` styled `.admin-view-only`, and block cards, chip inputs and rich-text editors go inert.

## Translation pair

**Translation pair.** In a non-default language every translated field is a pair (`.admin-translation-pair`): the primary-language original in `Admin::EditorScreen::ReferenceCardComponent` beside the field's own input, stacking below 880px of the *form's* width (`container-type: inline-size` on `.admin-translation-form`, not the viewport; the card's `<details>` folds only when stacked). Fields that are the same in every language are not inputs on a translation tab (so its autosave can never send or change them) but one collapsed "Shared fields (N)" disclosure (`Admin::EditorScreen::SharedFieldsComponent`); a schema group field's value is shown there as a summary, and in the reference card as the raw hash. An outdated field's card turns `warn` and shows "↻ CHANGED <time ago>" and one of: the word diff of the text the translation was made from against the original now (`Translations::SourceDiff`), "Formatting changed", "The text is too long to compare word by word." or just the current original; its actions are **Suggest update** and **Still correct — mark up to date** (`Translations::Confirm`, writing only `translation_sources` via `update_columns`, so `updated_at` and the autosave base don't move; the button belongs to the layout's confirm form through `form=`). The slug is a prefixed input (`Admin::Ui::PrefixInputComponent`), the hero a library image with a per-use alt, SEO fields have soft character counters (`admin--ui--char-count`), and a content type's own fields sit in their own group. A per-use override (a page hero's alt, an image block's alt and caption) shows the library's text as its placeholder and a **Reset** once it holds its own (`admin--ui--override-field`, `admin/shared/_override_field`).

## Rich-text dialogs

**Rich-text dialogs.** The editor's toolbar is grouped (`RichTextColumnComponent::TOOLBAR_GROUPS`, plus the Insert menu) and one row wide. Insert image goes through the media picker and then a form-width dialog for alt text and caption; YouTube and "Page link" are dialogs too. `Admin::EditorScreen::RichTextDialogsComponent` renders the three once in the layout (outside `#content` and every autosave form, so their fields never feed an autosave); `admin--rich-text-dialog` fills and opens them over `rich-text-dialog:open` / `rich-text-dialog:closed` events naming the opening editor, so two editors on one page never cross wires. The page search is `app/javascript/rich_text/target_search.js` over `Admin::LinkTargetsController`.

## New page and New post

**New page and New post** are dialogs rendered once in the layout (`Admin::EditorScreen::NewPageDialogComponent`, `NewPostDialogComponent`, only for a viewer who holds `pages.create` / `posts.create` anywhere) as a shell — a loading line, an empty `<turbo-frame>` and a disabled Create button. `admin--new-record` loads the form when the dialog opens (`GET /pages/new?parent_id=&title=` or `/posts/new?type=&title=`, answered by `Admin::EditorScreen::NewPageFormComponent` / `NewPostFormComponent`), the trigger's own `data-new-page-*-param` / `data-new-post-*-param` attributes becoming the preset (read on `admin--ui--dialog:opening`), so the form is always built from the current tree; the same URLs are the standalone no-JS pages. The page form's "Inside" offers only parents where the viewer may create (`AccessControl.creatable_parents`). ⌘K's "New page" / "New post" open the same dialogs.

## The posts list

**The posts list.** `Admin::PostsController#index`: a toolbar (`Admin::PostsScreen::ToolbarComponent`: title search, a segmented `scope` control with counts — All, Live, Drafts, Scheduled — that respect every other filter but not the scope itself, and Type, Tag and Translation drop-downs; one GET form with `admin--ui--auto-submit`; `status` is the old name of `scope` and still reads), 50 rows a page, and a table (`TableComponent`) with a per-row ⋯ menu. Selecting rows shows the bulk bar (`BulkBarComponent`, `admin--bulk-select`) for **Publish** and **Move to trash**, posted to `POST /posts/bulk` and run by `Posts::Bulk` (an `# audit: none` service: it writes nothing itself — every post goes through `Posts::Save` or `Trash::Move`, so each is authorised with its own scope, audited and answered on its own). Ids load only through `AccessControl.scope(..., "posts.read")`: one that is missing, trashed or out of scope is *not found* — counted, never named. There is no all-or-nothing: each post runs in its own savepoint, an exception counts as that post's failure, and the answer is one toast (`Admin::BulkResponses`, bounded because it lives in the session cookie) separating done, refused (readable but not actionable), failed (with the first reason), already live, scheduled posts left as scheduled (publishing never discards a schedule) and not found. Something done *and* something refused, failed or not found is a warning toast (`flash[:warning]`, which never auto-hides, because the toast is the only place the failures are named); nothing done is an error toast. The selection column and the bulk bar exist only for a viewer who holds `posts.publish` or `posts.delete`; a row's own "Move to trash" replaces the selection with that row and puts the previous ticks back if its dialog is cancelled. At most `Posts::Bulk::MAX_IDS` (200) per call. A bulk trash offers Undo (`POST /trash/restore_many`, `Posts::BulkRestore`, the same contract through `Trash::Restore`) only while its URL fits `MAX_UNDO_URL` and the URL plus the sentences fit `MAX_FLASH_BYTES` (bytes, not characters — the answer lives in the session cookie); otherwise the toast says where to find the posts.
