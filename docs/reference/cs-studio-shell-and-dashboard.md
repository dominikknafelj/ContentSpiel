# CS Studio: shell, dashboard, audit log and small screens

> Describes: `app/controllers/admin/` (base, dashboard, audit events, system status, jump, mind graph), `app/components/admin/shell/`, `app/components/admin/dashboard_screen/`, `app/components/admin/audit_screen/`, `app/queries/dashboard/`, `app/queries/jump/`, `app/queries/post_graph.rb` and `app/queries/post_graph/`, `app/javascript/mind_graph/`, `app/javascript/controllers/admin/mind_graph/` (`graph_controller.js`, `swatches_controller.js`), `app/components/admin/mind_graph_screen/`, `app/views/admin/mind_graph/`, `app/models/audit/sentence.rb`, `app/components/public/preview_bar_component.rb`.

## Admin (CS Studio)

Our own admin, mounted at `ContentSpiel::ADMIN_PATH` (`config/initializers/admin_path.rb`, default `cs-studio`, configurable via `ADMIN_PATH`, one URL segment, can't be a reserved path), behind the same session-based auth as the rest of the app (no separate admin auth) plus the permission checks described in `docs/reference/access-control-and-audit.md`. Controllers live under `app/controllers/admin/` (`Admin::BaseController` and per-module controllers: `DashboardController`, `PagesController`, `PostsController`, `ContentBlocksController`, `TagsController`, `TagSuggestionsController`, `SettingsController`, `LanguagesController` (the Languages card's instant actions only; there is no Languages screen), `AiKeysController`, `UsersController`, `UserSuggestionsController`, `GroupsController`, `ApiTokensController`, `AuditEventsController`, `AccountsController`, `PasswordsController`, `SessionsController`, `SystemStatusController`, `TranslationsController`, `TranslationConfirmationsController`, `MindGraphController`, `LinkTargetsController`, `JumpController`, `MediaController`, `MediaAssetsController`, `StarterContentsController`, `TrashController`, `TreeController`, and the seven notes controllers, `NotesController`, `NoteThreadsController`, `NoteMessagesController`, `NoteMentionsController`, `NoteReactionsController`, `NoteFilesController` and `NoteInboxController`, described in `docs/reference/notes.md`). Every write goes through a service object (`app/services/`, e.g. `Pages::Save`, `ApiTokens::Issue`), never straight from a controller — see individual services' own comments for authorization and audit-event conventions. `Pages::Save` and `Posts::Save` take only the keys in their `ATTRIBUTES` lists in `attributes:`; any other (`parent_id`, `position`, the trash columns, a translated attribute) raises `ArgumentError`, because moving and trashing belong to `Pages::Move` and `Trash::Move`. `Admin::BaseController#require_permission(key)` gates whole admin areas (403 on refusal, rendered inside the CS Studio layout, never a bare error page); record-scoped controllers load through `AccessControl.scope` instead, so an out-of-scope id 404s; views use the `can?(key, record = nil)` helper (`app/helpers/access_control_helper.rb`) to hide buttons a signed-in user couldn't act on anyway. Content views use autosave (`admin--saving--autosave` Stimulus controller, `Admin::AutosaveResponses#autosave_stream`) rather than a submit button, configuration screens an explicit Save; `docs/reference/save-rule-and-write-queue.md` says which is which and how a stale save is refused.

CS Studio's start page is the **dashboard** (`Admin::DashboardController#show`, dashboard spec `2026-09-30-dashboard-design.md`), not the pages list: `root to: "dashboard#show"` inside the admin scope, so `admin_root_path` means the dashboard. The Pages module is at `/<admin>/pages`, which is not a list but a redirect: `Admin::PagesController#index` sends a viewer who can open Home to Home's editor (303, the editing language kept, the flash kept) and otherwise shows the empty state "Choose a page from the tree" beside the tree; `Admin::BaseController#pages_landing_path` is the same decision for every redirect that used to mean "the pages list" (the trash's post-move redirect, starter content, a page's own delete). Sign-in and setup completion deliberately land on `admin_root_*`, the dashboard. It's open to every signed-in user (`BaseController::MODULES`'s `permission: nil` entry, listed first), including one whose groups hold no grants at all: every list it shows is already read-scoped through `AccessControl.scope`/`AccessControl.holds?` the way every other admin list is, so a user who can read nothing simply sees empty cards rather than a 403. The page is a quick-create row (`Admin::DashboardScreen::QuickCreateComponent`: a title, a type select and "Create draft" — a post draft through `Posts::Save`; choosing "Page" opens the New page dialog with the title carried over instead of creating anything), three cards in an auto-fit grid — "Your drafts" and "Going live next" from `Dashboard::Feed` (`app/queries/dashboard/feed.rb`, at most five rows each, "→" to the posts list filtered by `scope=drafts|scheduled`), "Unpublished changes" (`Dashboard::Feed#unpublished_changes`, the live or scheduled records whose mark is set, five rows like "Your drafts", empty text "Nothing is waiting to be published.", `Publishable.with_unpublished_changes`), and "Needs translation" from `Dashboard::TranslationNeeds` (per target language the viewer's readable pages, posts and — for a `media.upload` holder — images from `Translations::StateIndex.summary`, plus the most recently changed outdated item; hidden with one language) — and then **Recent activity** (`Dashboard::Activity`), with a link to the full audit log for `audit.view`. "Mine" in the drafts card means `author_id` for a post or, for any record including a page, that its *newest* audit event's user is me — "newest" ignoring `access.denied` (a refused attempt is no change), a note's events and a take-over of an edit reservation (`Dashboard::Feed::NOT_A_CHANGE`) and, for a page or post, also counting events about any content block it currently owns, since editing a block is editing its owner. It is decided in SQL by one `LATERAL` join to each record's newest audit event rather than a Ruby-side filter-after-load, so each list stays one query per model whatever the data size.

**Recent activity** is the newest *content* audit events (pages, posts, blocks, library images; never `access.denied`, `session.*`, `user.*`, `group.*`, `token.*` or `settings.*`; the allow-list is `Dashboard::Activity::ACTIONS`), one sentence each — "<name> published “<title>”" with the title linking to the record's editor (`Admin::DashboardScreen::ActivityRowComponent`) — looking back `Dashboard::Activity::WINDOW` (90 days). The read scope is applied *in the event query itself* (`audit_events.subject_id IN (readable ids)` per subject type, a block event through its readable owner, images for a `media.upload` holder), never by over-fetching and filtering in Ruby, which under-filled the feed and leaked how much hidden activity there was; a record the viewer can't read, a trashed one or a deleted one leaves no row at all ("not found, not forbidden"), a trashed record's whole history disappearing with it until it is restored. `index_audit_events_on_recent` serves the `ORDER BY last_occurred_at DESC` scan. The query returns data only: a `Dashboard::Activity::Row` is `(event, record, sentence, at, span_end)`, the sentence an `Audit::Sentence` (see the audit log below) whose actor is facts, not a name — the viewer ("You"), a user, a `user_id` that names nobody any more, or nobody — and `ActivityRowComponent` hands it to `Admin::AuditScreen::SentenceComponent`, which is where a user is named, through `Admin::Ui::UserNameComponent` (the one place CS Studio names a user): the `display_name`, "a deleted user" when `user_id` names a user who no longer exists (`audit_events` has no FK on it; a token event whose user is gone reads the same), "System" only for an event with no user at all. A change made through an API token shows its *user* (round avatar) "via <token name>" beside an MCP chip (`Admin::Ui::ChannelChipComponent`, which draws an unknown channel as a plain chip and nothing for none), the name being the `audit_events.actor_label` written when the event was recorded (`Audit::Event#via_label`; it survives the token being deleted, and an event recorded before tokens had names reads "via an API token"), the token itself never loaded. A coalesced burst shows the time it last extended, the whole span as its tooltip.

**The audit log** (`Admin::AuditEventsController`, `audit.view`, never content-scoped) tells every event as one sentence through `Audit::Sentence` (`app/models/audit/sentence.rb`: plain data -- actor facts, parts, a route name + params for the subject, a `security` flag -- never markup or a component; `Admin::AuditScreen::SentenceComponent` draws it), the dashboard's feed words its rows through the same class so the two can't differ. A sentence for an action outside `Audit::Sentence::ACTIONS` (a plugin's) is the generic "<actor> did <action> on <subject>"; the actions in `Audit::Sentence::SECURITY_ACTIONS` (a failed sign-in, a refusal, an owner change, a token issued or revoked, a user or group deleted) carry the `security` flag, and the row draws their key in warn ink. `test/models/audit/sentence_test.rb` greps `app/` for every recorded action name and fails for one without a sentence (interpolated and variable call sites are listed explicitly there). A subject links only when the viewer may open it, decided for the whole page of events in a bounded number of queries (`Audit::Sentence::Targets`); an unreadable, trashed or deleted one is the label the event stored, as plain text, and a failed sign-in never echoes the attempted address. A refusal says what it was refused on when the event names a subject ("was refused permission to edit posts on" and the subject), and a schedule taken off a page or post reads "removed the schedule from". The list is `last_occurred_at DESC, id DESC` under day headers in the site time zone (`Admin::AuditScreen::DayListComponent`), filtered by `Audit::Filter` (user, action, type, channel, a `range` preset or custom `from`/`to`, a `subject_type`+`subject_id` chip; junk is "all"), "Load older" over `offset` (it replaces the page; "Newer" goes back). A coalesced row shows its span ("16:05–16:31", `Admin::AuditScreen::TimeSpan`), and `audit_events.occurrences` (1, incremented by `Audit::Coalescer` each time an event merges into the row) is the "N saves" on the event page ("N times" for anything but a `*.updated` event: twelve refusals are not twelve saves). The event page (`EventHeaderComponent`, `ChangesComponent`) shows field changes as word diffs per language (`Translations::SourceDiff` drawn by `Admin::Ui::WordDiffComponent`, shared with the translation reference card), "Changed" for a body, and Older/Newer through the same filtered order, every link on the page keeping the filters. The event is found by id whatever the filter says: one that exists but lies outside the active filter (a link carrying `range=today`, opened the next day) is answered 303 to its own filter-free address, the language kept, where Older and Newer walk the whole log; only an id that names nothing is a 404. Components live under `Admin::AuditScreen::`, never `Admin::Audit` (see "Key Conventions").

Every CS Studio and MCP request also runs inside the **site time zone** (`site_settings.time_zone`, default `"UTC"`, stored as a Rails zone name — an IANA identifier like `"Europe/Berlin"` is normalised to its Rails name on save, because the Settings select's option values are Rails names and every Save resends the whole form; the select also always lists the stored value, so a value written around the model is resent unchanged rather than replaced by the first option): `SiteSetting#effective_time_zone` resolves the stored name to an `ActiveSupport::TimeZone`, falling back to UTC for a value that doesn't resolve (a blank or no-longer-valid stored zone) rather than letting `Time.use_zone` raise and 500 every request; `Admin::BaseController` and `McpController` each wrap their actions in `around_action :use_site_time_zone { Time.use_zone(Current.site.effective_time_zone) { ... } }`. That's what lets the existing `Time.zone.parse`/`strftime` call sites (schedule inputs, "Saved HH:MM", the dashboard, the trash and audit screens) show and parse local time without change — storage stays UTC throughout, and MCP's own dates are still emitted as ISO-8601, now with the site's offset rather than always `Z`. The public site (and `/preview`) still renders dates in UTC — tracked in the roadmap, since it needs the render cache to vary on the zone.

**Notes on the dashboard and in the sidebar** (`docs/reference/notes.md`, "The inbox"). The dashboard has two cards about notes, each a frame of its own that can be fetched again by itself: **Notes for you** (`turbo-frame#notes-for-you`, `Dashboard::NotesForYou`: the viewer's deliveries on records they may read now, unread first, five rows, "N NEW" in accent, "Mark all read" and a link to the full list at `<admin>/notes`) and **Open threads** (`turbo-frame#notes-open-threads`, `Dashboard::OpenThreads`: one row per readable record that has open threads, with its count in the neutral pill, most recently active first). The sidebar's Dashboard entry carries the viewer's unread count (`#sidebar-badge-dashboard`, `Admin::BaseController#notes_badge_count`): the one filled badge of the sidebar, accent because accent in a marker means "unread and addressed to you" and nothing else; Trash's stays a plain mono number. It costs exactly one statement per page load. `admin--notes--inbox` on `<body>` fetches the badge and, on the dashboard, both cards again when the person's stream says something was addressed to them. Recent activity lists a note's start and its resolve only (`Dashboard::Activity::ACTIONS`), and "Mine" and "Changed by" never count a note as a change to the record (`Dashboard::Feed::NOT_A_CHANGE`). Presence is not shown on the dashboard, in the mind graph or in the media grid (`docs/reference/presence.md`, "What is not built"); the dashboard's cards and the sidebar's badge stay direct code, named exceptions in `test/lib/notes_boundary_test.rb` with the trigger that would make each a slot.

## Shell

**Shell.** `Admin::BaseController::MODULES` entries carry `group:` (`:content`, `:people`, `:system`), which `Admin::Shell::SidebarComponent` renders as the sidebar sections (Dashboard stays first); the sidebar also holds the ⌘K field, the account block and the theme switch. The account block is `Admin::Shell::AccountIdentityComponent` (`#account-identity`: `display_name`, then "email · role" on one line, the role being "Owner", up to two group names then "+N", or "No groups" — its own component because the account screen's Save replaces just it by stream, and a link to that screen), then Your account and Sign out. Sign out is a plain form with `data-turbo="false"`: a full document load, so nothing a tab's scripts hold for one user (the media upload queue's tiles) survives into the next sign-in, and with unsaved changes it is the browser's own prompt that asks. `Admin::Shell::TopBarComponent` appears below 1280px, where the sidebar becomes a drawer (the page-tree column becomes one below 1024px); the bar is 3rem tall, so everything sticky inside the content area (the editor header, Settings' nav, the Media panel) sits at `--admin-top-offset`, which is 0 and 3rem below 1280px; `admin--shell--drawer` owns open state, scrim and Escape, and the CSS keys on `data-open` (`.admin-shell` in `content-spiel.tailwind.css`). In the page tree, a context-only row (an ancestor shown only as the path to a readable page) is greyed text with no actions, a row has a hover "+" only where `pages.create` holds under it and a drag handle only where `pages.move` does, the homepage has no handle, and a row shows "↻N" (outdated) and "○N" (missing) summed over the target languages, hidden at zero, from `Translations::StateIndex.counts_for` read once by `Admin::PagesScreen::TreeComponent` (never red; the tooltip names the languages). The Trash entry carries `trash_badge_count` (`Admin::TrashController.visible/roots/counts/badge_count`: the page branch roots, posts and images the viewer may act on, the sum of the Trash screen's own tab counts). A 403 and a 404 render inside the layout (`admin/errors/forbidden`, `admin/errors/not_found`; `rescue_from ActiveRecord::RecordNotFound`); the 404's link is "Back to the dashboard" unless the screen names a nearer way on (`@not_found_back`: Media's "Back to Media", the search and segment kept); a non-HTML request (a Turbo Stream, a `fetch`) gets a bare `text/plain` 404 so the caller doesn't mistake it for a stream.

## Jump to…

**⌘K "Jump to…".** `Admin::JumpController` answers `GET /<admin>/jump?q=` with `Jump::Search` (`app/queries/jump/search.rb`): pages, posts and library images (read-scoped through `AccessControl.scope`, trash hidden), then CS Studio's modules as **Sections**, destinations inside the Settings screen as their own **Settings** group ("Settings › Site", "Publishing", "Languages", "AI translation", each behind the right that owns its card: `languages.manage` for Languages, `settings.manage` for the others), and **Actions** (New page and New post open their dialogs; the rest are links); five rows per group. Pages and posts match **titles only** — in every language, via `jsonb_each_text` on the translated jsonb columns (`TitleSearch`, `SqlNodes.any_json_value`) — never bodies (full-text search is a separate roadmap row); images go through `Media::Search` like the library does. A page or post row shows a non-Live status chip at its right end (`Admin::Ui::StatusChipComponent`, Live draws none). `Admin::Shell::CommandPaletteComponent` is the dialog (an ESC chip beside the field and a hint row, "↑↓ MOVE · ↵ OPEN · ⌘↵ NEW TAB"), `admin--shell--command-palette` the controller (⌘K / Ctrl+K, arrows, Enter; ⌘/Ctrl+Enter opens the row in a new tab). An Enter pressed while the results for the typed text are still on their way, or before any row is selected, is remembered and opens the first row when they arrive (⌘/Ctrl+Enter the same, in a new tab); the arrows do nothing meanwhile. A row that leads to a section of the screen already showing ("Settings › AI translation" used on Settings) is a same-page fragment link: it jumps there without a visit, so an unsaved form is not asked about leaving. The shortcut does nothing while another modal dialog is open: the editor closes what is open first.

## System status

**System status** (`Admin::SystemStatusController`, `system_status.view`): "N of M checks passed · last run HH:MM", warnings first, each check an `Admin::Ui::SystemCheckRowComponent` (the setup wizard draws the same rows with `copyable: false`). A check may carry a console `command`, shown in a code box with Copy (`admin--ui--clipboard`). The outgoing-mail warning's command resets a password through `Users::UpdatePassword` — never `update!` on the model — so it is audited and ends that user's sessions (`Setup::SystemCheck::MAIL_FALLBACK_COMMAND`, a static string). "Run checks again" is a GET with prefetch off, because the storage check writes and deletes a probe.

Two checks come first and are about where the site is reached. **Site address** names the configured origin (`SiteAddress.current`: "This site answers at https://www.example.org."), or warns that none is set, with what follows from that and `PUBLIC_HOST=https://www.example.org` to copy (`Setup::SystemCheck::SITE_ADDRESS_COMMAND`, a fixed string like the mail command). The warning has two wordings, because what follows differs: addresses in pages follow the request everywhere, but a password reset mail takes its link from the request in development and test and is not sent at all anywhere else, and "any host name is accepted" is said only in the second, since development refuses a made-up name by Rails' own list (`docs/reference/hosting.md`, "The reset mail"). Both screens hand the check `reset_link_from_request: PasswordsMailer.request_origin_used?`, a boolean, so the model names no mailer; a caller that hands nothing gets the wording that reset mails are not sent. **HTTPS** is in the list in production only, and only when the caller said how the request came: both screens hand over `request_ssl: request.ssl?`, and a caller that hands nothing (the console) gets no row. With an `https` address plain HTTP is redirected before it reaches the app, so the warning is seen only where the address is an `http` one or missing. An address that is configured as `http` on a page that was reached over HTTPS is a warning too ("The address is http but this page was reached over HTTPS: set PUBLIC_HOST to the https address."), so that the two rows do not both say OK while every address the site prints is still http. "Encrypted" is what `request.ssl?` says, which is the proxy's word (`X-Forwarded-Proto`) or `ASSUME_SSL=1`'s, not something the application can see for itself. And the **Outgoing mail** warning begins with one more sentence, `Setup::SystemCheck::MAIL_NEEDS_ADDRESS`, when a mail server is set and the site's address is what is missing: production's mailed links take their host from the address, so such a site otherwise reads "isn't configured" beside SMTP settings that are right (`test/models/setup/system_check_test.rb`: "a mail server without a site address: the warning names the address as what is missing", "where a reset mail takes its link from the request, the warning says that and not that none is sent").

**The plain-HTTP notice** (`Admin::Ui::InsecureNoticeComponent`, `#insecure-notice`) says the same thing where a person would otherwise not look: in production, on a request that is not `request.ssl?`, one warn alert (`border-warn bg-warn-tint text-warn-ink`, `role="alert"`). The `product` layout draws it for everyone above sign-in and both password pages, where a password is typed; the `admin` layout draws it at the top of `<main>`, outside `#content`, for someone who holds `settings.manage` or `system_status.view` (`Admin::BaseController#insecure_notice_viewer?`, navigation and not a gate; each of the two rights is enough alone, and `languages.manage`, which also shows the Settings link, is not one of them), since an editor can do nothing about it. The `setup` layout draws it for everyone at the top of every wizard page, since the wizard takes the setup token and the first account's password (`test/integration/admin/insecure_notice_test.rb`, `test/integration/setup_early_steps_test.rb`).

## The preview bar

**The preview bar** (`Public::PreviewBarComponent`, rendered first in the public layout on `/preview…` only): a fixed 36px bar, "PREVIEW · <title> · <Draft | Scheduled | Live> · <language>", Edit and Exit preview. It is the public site's chrome: the public stylesheet only, no admin JavaScript, and its colours are the theme tokens `--th-preview-bg` / `--th-preview-ink`, which do not switch with light and dark. Edit opens the record's editor in the previewed language. Exit preview goes to the record's public URL in that language when it is live, and otherwise to CS Studio's list (the pages landing for a page, the posts list for a post) — there is no public page to leave for.

## Mind graph

**Mind graph** (`Admin::MindGraphController`, the `PostGraph` queries in `app/queries/post_graph/`, `admin--mind-graph--graph` and `admin--mind-graph--swatches` over the modules in `app/javascript/mind_graph/`, the components in `app/components/admin/mind_graph_screen/`). Two specs: the canvas (`docs/superpowers/specs/2026-10-07-mind-graph-canvas-design.md`, whose §7 holds the first measurement and §11 the decisions made while building, the last part of it the round that followed the owner's first trial on 2026-10-08: motion, pinning, the card beside its node, the label as part of the target, the list beside the canvas) and pages (`docs/superpowers/specs/2026-10-12-pages-in-the-mind-graph-design.md`, whose "As built" holds every place the build left the approved text, and the measurement of 2026-10-13 at 204 pages and 2,005 posts). How the site hangs together: the pages and their tree, what each page's list blocks point at, and how posts relate through related-post links and shared tags, drawn on one 2D canvas and laid out by d3-force in a Web Worker. Read-only: a page is moved in the page tree, a list block is changed in the page editor, relations are edited in the post editor. **It opens for someone who holds `pages.read` or `posts.read` anywhere** (`require_graph_access`; the sidebar's entry is shown for either): a graph of pages alone is a graph. Each kind is then narrowed by its own scope, and everything the screen shows or counts is derived from the pages and posts the viewer may read.

**It shows THE ROWS, not the published copies, by decision** (pages spec, decision 3). CS Studio is the editors' view: the tree, the posts list and the editors all show the rows, and so does this. A lists line follows a list block's settings as they are being edited, so on a live page with unpublished changes a line can be one visitors do not get yet; the page's own mark says so (the corner dot, below), and that mark is the only cue. The other way round was rejected: reading the copies of live records and the rows of drafts would be two sources in one picture and a second writing of `Publishing::Listing`. Nothing under `app/queries/post_graph/` reads a published copy, and nothing there or in the scripts decides a record's state: a node's `status` and `changes` are `Publishing::State`'s (below). `test/lib/mind_graph_guards_test.rb` holds both, by refusing every line that NAMES `published_at`, one of `Publishable`'s scopes that compare it, or a copy, unless it is one of a short list of exact lines that only carry the column to where the rule is kept. What a name cannot see is held otherwise: a post's row carries a RECENCY, a number, and never the publication time (`PostGraph::Site.rows_of`; a row that carried the time as a place in an array could be compared under any name a block parameter gave it), and no script names a scheduled change's time or reads a clock for a date, so a look cannot be decided in the browser by comparing a time with now ("no script of the mind graph reads the clock for a date or names a scheduled change's time: a look is what the server answered").

**Three views, one screen.** `GET /<admin>/mind_graph` is the **whole graph**: every readable page and the best-connected readable posts, up to a cap. `?page=<id>`, `?post=<id>` or `?tag=<id>`, with `&depth=1|2`, is a **local** view: that page's, post's or tag's neighbourhood. A depth other than 2 is read as 1, and **a page wins over a post, a post over a tag** when more than one is given (`PostGraph::Focus.find`; the data URL carries every focus parameter the address had and the data picks the same one, while the bar's depth links carry only the winner). Changing the focus or the depth is an ordinary visit, so Back works. The third view is the one a large site opens in, the local view around Home with a bar that says why ("A site with too many lines", below): it has no address of its own. Four JSON reads belong to the screen and share its permission and scope (`config/routes.rb`, each `format: :json` by default): `mind_graph/data` with the same parameters answers the graph (and takes `everything=1`, which the page itself does not), `mind_graph/search?q=` the search field's rows, `mind_graph/unlisted` the posts no page lists and `mind_graph/listed?page=<id>&target=<target>` the posts behind one "+N more" pill. **A focus outside the viewer's scope is not found, never forbidden**: `PostGraph::Focus.find` raises `ActiveRecord::RecordNotFound` for an unknown id, a trashed page or post, one outside the read scope, and a tag that neither a readable post carries nor a readable page's list block names (a focus on it would say the tag exists and is used somewhere the viewer can't look; a tag a readable page lists is a node of the graph whatever carries it, so it is a focus too), and `Admin::BaseController` answers the 404 page, or a bare 404 for a JSON read. The page and `data` resolve the focus the same way, so they can't disagree. **An id is decimal digits and nothing else** (`\A\d+\z`, then base 10): without the base Ruby reads a prefix, so `?post=010` would be post 8 and `?post=0x1A` post 26, each a record other than the one the URL names, and `Integer` alone also takes `1_0`, a sign and surrounding spaces. Whatever is not a number names nothing and is a 404 (a word, a list such as `post[]=1`), while `q[]=x` on the search finds nothing and `depth=abc` is depth 1 (`test/integration/admin/mind_graph_data_test.rb`, `test/queries/post_graph/focus_test.rb`). **A focus that went between the request's finding it and the site's being loaded** (trashed, deleted, taken out of scope) is not found either, whatever its kind and before anything more is read: `PostGraph::Local` asks the site's own rows, which everything after is derived from, so the request that loses that race answers the 404 it would answer a moment later and never a 500 or an empty graph (`test/queries/post_graph/local_test.rb`: "a focus tag that went meanwhile is not found before anything but the site is read, and neither is one nothing readable uses any more"). `listed` finds its page as a focus is found, so the same holds for it; its `target` is only ever compared with the page's own targets, so a junk one, or one the page does not list, answers no rows and is echoed nowhere (an empty answer and not a 404: it says nothing a 404 would hide, since "a tag only an unreadable page lists" and "nothing more behind this pill" are the same answer).

**A node's id is its kind and its database id**, everywhere: `page-12`, `post-12`, `tag-12`, a post type's `type-<stored name>`, the one `all-posts`, a pill's `more-<target>`. `PostGraph.node_id` is the one writer on the server (the payload's `id`, both ends of every line, `parent`, a search row, `focus.node_id`), and `mind_graph/ids.js` (`recordId`, which cuts at the FIRST dash) the one place the page takes an id apart, for the URL templates and the notes, which want the record's own id. The server takes one kind of id apart too, with no function for it: a list target's kind is read by its literal prefix `"tag-"` in `PostGraph::Local` (`reached?`, `brought`, the walk around a page) and in `PostGraph::Builder` (`plan`, the type nodes). Nothing ties those five lines to `node_id`: a change of the separator or of the kind's spelling must be made in both, or a page's local view loses its tags and their lines with no error. A post's id was the bare number until this build and only a tag's was prefixed; a page and a post of one database id would have been one node. The data has no `kind` key: a node's kind is the array it came in, and a line's ends carry none (the id says it). The system test's `nid` helper refuses a bare number for the same reason: two trash-visibility assertions that compared a node's id with a record's number went on passing against typed ids while checking nothing.

**The data.** `PostGraph::Global` and `PostGraph::Local` answer one shape, built by `PostGraph::Builder` (the shape is written out at the top of `app/queries/post_graph.rb`): `nodes` (the posts), `tags`, `pages`, `types`, `edges`, in a page's local view `more`, plus `total`, `shown` and `isolated` (whole) or `focus: { kind, id, node_id, title, depth }` and `site: { pages, posts, tags }` (local). A post: `{ id, title, type, colour_index, status, changes, change_at, listed, url, degree, related_count, tag_count, open_notes }`. A page: `{ id, title, path, depth, home, parent, order, status, changes, change_at, url, degree, child_count, listed_count, open_notes }`, in tree order. A type: `{ id, name, label, colour_index, count, degree }`, by colour slot, then the retired types by name, then "all-posts" last. A line: `{ source, target, kind }`, of five kinds: `related` (two posts), `tag` (post to tag), `tree` (child to parent), `lists` (page to tag, type or all-posts) and `brings` (a page's local view only: hub to post, and hub or tag to its pill). `degree` is the number of lines the node has *in this response*, so a node's size and its label's priority match what is drawn, not what the site holds; a post's `related_count` and `tag_count` are two halves of it, counted where the lines are made so the card can say "3 related · 2 tags" without the page walking the lines (around a page a post can have one more, its hub's `brings` line). `total` is the posts the view could show (whole: the readable posts with at least one connection; local: the posts the walk reached), `shown` the posts in `nodes`, and `isolated` the readable posts with no connection, which the whole graph leaves out and counts in a sentence ("72 other posts have no connections yet and aren't shown.": "other" and "aren't shown" because the bare count read as a contradiction beside a canvas of connected posts; with nothing drawn at all it is `script.isolated_only`, "2 posts have no connections yet."). There is no colour in the data: a post and a type carry the content type's `colour_index` (nil for a type that is no longer registered, which is how a retired type's hub is told; "all-posts" has none either and is told by its id), and the page draws from tokens. `url` is the record's editor URL, built by the `url_for:` callable the controller passes (the route helper, with the editing language kept; called with a `Page` or a `Post`): a query knows no routes (`test/lib/dependency_direction_test.rb`), and `actor:` and `url_for:` have no default so nothing draws the whole graph, or a graph without links, by forgetting one. Posts and pages are loaded with the columns a node is made from (`Builder::COLUMNS`, `Site::PAGE_COLUMNS`), never a body. A post and a page also carry `open_notes`, the number of their open threads, which `PostGraph::Builder` reads for the ids it was handed in one grouped statement a kind (`Notes::Counts.by_container`) and the page draws as a neutral badge; the graph's data says nothing about what the viewer has read, which is said on the rows of the node's card, from the notes' own endpoint. **What went between the two reads goes whole** (`Builder#build`): the lines are planned from the site as it was loaded and the nodes are read afterwards, through the scope again, so a tag deleted in between has no name and a post trashed or taken out of the viewer's scope in between has no node. Both are dropped with every line that touches them and a pill on a gone tag, and every count is made from what is left (a node's `degree`, a post's `related_count` and `tag_count`, a tag's `count`, and the callers' `total` and `shown`); a focus post that went is not found. The page looks every end of a line up among its nodes, so a line to nothing fails the whole load: as first built for posts the node went and its lines stayed (`test/queries/post_graph/global_test.rb`: "a post that is trashed between the site's read and the nodes' goes whole: no node, no line to it, and every count is of what is left"; `local_test.rb`: "around a post, around a tag and around a page, a post trashed between the site's read and the nodes' goes whole, and a focus post that goes is not found").

**What the three counts mean** is easy to take for something else. A tag's `count` is the READABLE posts carrying it. A type hub's is the readable posts of that stored type, and "All posts"' is EVERY readable post, one of a retired type included: "the site total" of the design answer, as this viewer reads the site, and not what a block with no filter lists (it lists no post of a retired type). A page's `listed_count` is the readable posts its blocks list, past a block's own `limit` (a block showing 5 of 112 counts 112). None of the three is a pill's arithmetic: a pill counts what ITS target brings in to THIS page beyond the posts drawn. And a post's `type` need not have a hub: `types` holds only what a drawn lists line points at, so no script may assume `type-<post.type>` is a node.

**`status` and `changes` are `Publishing::State`'s**, together one of its five states: `status` is "draft", "scheduled" or "live", and `changes` (nil, "unpublished", "scheduled") tells apart the two further states of a live record, which a boolean could not. `change_at` is the time a scheduled change comes into force, in that state alone. The builder reads the pending copies ONCE for all the nodes of a kind (`Publishing::Version.pending(now)`, `Publishing.pending`'s own scope: when a copy comes into force, never its content) and hands each record's time to `Publishing::State.of(record, now:, pending_at:)`, which then asks the database nothing for `state` and `status` (`docs/reference/publishing.md`). What the caller owes for that: the same `now` in both, and only `state` and `status` asked, never `actions`, which would cost a statement a node. No words leave a query: the controller adds `change_on`, the day as CS Studio writes a short date (`I18n.l` with `admin.short`), to `nodes`, `pages` and the list's `rows` (`with_dates`), and the script formats no date (`test/queries/post_graph/global_test.rb`: "for every combination of the time, a pending copy and the mark, a node's status, changes and change_at are what Publishing::State answers by itself"; `test/integration/admin/mind_graph_data_test.rb`: "a scheduled change's day is in the data as CS Studio's short date, and a node without one has no such key").

**The site, loaded once.** Every view and both list reads start with `PostGraph::Site.load(actor:)`: the readable posts' rows (`[id, content_type, recency, updated_at]`), their tag links, the readable pages (in tree order), and from those, with no further statement, `PostGraph::Tree` and `PostGraph::Listings`. **`PostGraph::Tree`** is the page tree as far as THIS viewer can read it, from `(id, parent_id, position)` rows: closure_tree would ask per page. *What is not among the rows does not exist there*: a page whose parent the viewer cannot read has no parent (so no tree line is drawn to it and its parent's id is never handed out: `Tree#parent`, never the record's `parent_id`), stands at depth 1, is not Home and comes after the tree proper in `order`. Siblings are in the tree's one order, `TreeOrder` (`app/values/tree_order.rb`: by position, a page without one last, then by id), which the public branch, the Pages screen's tree and the New page dialog ask too; that key was written four times, the fourth here, until this build's last task made it one, with a guard that it is written nowhere else (`test/values/tree_order_test.rb`). `order` is a site-wide rank: in a local view it is a sort key, not an index.

**What a page lists** (`PostGraph::Listings`; pages spec §1, decisions 9 and 10). **A lists line is made from the block, never from the posts.** For each list block of the readable pages (a block whose type has the `lists_posts` capability, in a section or not: its owner is the page), its typed settings say the target: the tag when it names one (found by name whatever the case, as the listing finds it; a name no tag has makes no line, as it lists nothing), else the post type, else the one "All posts" node. One line per distinct target of a page; one "All posts" node however many pages list everything. So a type node joins only the pages that list it, never a post of its type, and no lists line joins a page to a post anywhere. **Which posts a page lists** is worked out in Ruby from the site's rows by asking `BlockTypes::PostList.matches?(settings, content_type:, tag_names:)`, the per-post criteria with no record, which `lists?` is too: the listing, a post's address and the graph cannot come to disagree, and `test/queries/post_graph/listings_test.rb` holds the parity ("the posts a page lists are the listing's own, for every shape of settings"). **"A page's first list block" is the first as a person reads the page**: `Listings.blocks` returns each page's list blocks in `BlockOutline#reading_order` (the sections loaded in the same statement, for their place alone), so a block dragged above an older one is the first; as first built it was the first by id, and the hub line and the "Open in Posts" filter came from whichever block had been made first. `target_of(page, post)` is the target of the first block that lists the post, so a post two blocks list is counted once, with the upper one. **It knows nothing of rights**: it is handed the pages and posts the viewer reads, so "listed", a page's `listed_count` and "Not listed on any page" are **true for the viewer, not for the site**. Someone who reads part of the tree is told a post is unlisted when a page they cannot read lists it; saying otherwise would disclose that page (`test/queries/post_graph/rows_test.rb`: "unlisted is true for the viewer: a post only a page they cannot read lists is a row, and a trashed post is none"). Two tags whose names differ only in case (an old row, a write around the model) are one name to the listing, so they are one target here, the tag of the lower id, and the posts of both are listed; the public page and a post's address go through `Publishing::Listing`, which takes one tag per name, so the application's two listings disagree about such a post, an older matter that is on the roadmap. **Its work in Ruby is bounded by counts a test holds, because no statement shows it.** As first built every page's posts were sorted for that page and the criteria were asked once per distinct filter AND post: at 204 pages and 2,005 posts the graph's data took 0.58 s where every page lists everything and 0.89 s where every page has a filter of its own, on every read that loads the site. Now the posts are put in order once, the criteria are asked once per distinct filter and distinct KIND of post (its stored type and which of the named tags it carries: all the criteria read), and pages whose blocks say the same share one frozen list: 0.15 s and 0.39 s ("the criteria are asked once for each distinct filter and each distinct kind of post, however many posts and pages there are", "pages whose list blocks say the same share one list of posts, the same object, and it is the list each would have had alone").

**Two steps: `plan`, then `build`.** `Builder#plan` says WHICH LINES the response holds, from what the caller has loaded, and asks the database nothing; `Builder#build` makes the nodes of a plan. The callers decide which posts, pages and lists lines; the builder decides nothing about access, and the rules that keep the graph from disclosing anything hold there because of what it is given: a line is made only between two nodes of the response (a tree line needs both pages drawn and the parent readable), and a tag's `count` is the readable number. The split exists for the next paragraph: the lines can be counted before a node is built.

**The cap, the cut and the cost.** The cap is `PostGraph::CAP`, 2,000 posts; it is not a setting, and raising it means measuring again. **Every readable page is drawn, always**: pages are few and are the frame the rest hangs on, and a tree with pages missing is not a tree. The two queries cut their posts differently. **Global** ranks every readable post by its connections (related-post links in either direction, plus one for each of its tags that at least two readable posts carry or that a readable page lists) *among all readable posts, before the cut*, keeps the top 2,000 with a count above zero, and breaks ties by newest `updated_at`, then id, so two requests cut the same; tags and lines are then derived from the kept posts only. **A lists line is not a post's connection**: a page points at a tag, a type or "All posts", never at a post, so a post only a page lists is still isolated, and a drawn post says whether a page lists it (`listed`). **Local** walks outward from the focus one level per depth, stepping only onto readable posts and pages (so an unreadable or trashed one is neither a node nor a bridge to what lies behind it); over the cap it keeps the focus, then nearer posts before farther ones, and among equals those with more connections *inside the neighbourhood*. A tag on thousands of posts is why a local view needs the cap at all. Over the cap the screen says what it kept, in a sentence per view because the two cut differently: "Showing the 2,000 best-connected of 5,791 posts." (`script.capped`) and "Showing the 2,000 nearest of 2,695 posts around this one." (`script.capped_local`, chosen when the response has a `focus`; never said around a page, where `shown` and `total` are the posts drawn and always equal); the search field is how a post the view doesn't draw is reached. Every figure in those sentences and in the isolated one is grouped for the messages' language (`Intl.NumberFormat` on their `@locale`): the count goes into its sentence as `%{figure}`, and `count` only chooses the plural form. One consequence of ranking before the cut: a kept post whose only link is a tag whose other posts were cut is drawn with no line and a `degree` of 0. **The cost is a fixed number of statements whatever the size, and each figure is a CEILING**, since Rails sends no statement for an empty `IN ()`. The whole graph: at most thirteen (the site's five: the readable posts, their tag links, the readable pages, the list blocks with the sections that place them, the tags the blocks name; the relations; the builder's seven: the tags' names, the pages' addresses, open notes and pending copies, the posts' open notes, pending copies and rows). What makes it vary: a site where no list block names a tag does not ask for the tags blocks name (twelve), one with no page or no post drawn does not ask for that kind's notes, and a viewer who is not an owner costs one more, constant, their grants, read once a request. The answer that says where to open instead (below): six, no node built. A local view: at most the thirteen, plus three per depth level around a post or a tag (the relations touching the frontier, the frontier posts' tags, the frontier tags' posts); **around a page the walk asks nothing** (it is the site's rows), so nine at depth 1, where no post is drawn, and thirteen at depth 2, and seven for a page that lists nothing on a site with no list block. Each of the list's two reads: at most eight for a pill's rows (the site's five and the nodes' three) and nine for the unlisted posts (one more: the relations that touch its rows, for what each row says of its post's connections), five with no row. The search: six. Never one per page, per block or per post: each has a `capture_sql` test at two sizes far apart (`test/queries/post_graph/global_test.rb`: "the statement count is thirteen for a small site and for one ten times its size in pages, blocks, posts, tags, notes and pending copies"; `local_test.rb`: "a page's local view costs nine statements at depth 1 and thirteen at depth 2, around two children and one sibling and around twelve children with their children and eight siblings"; `rows_test.rb`: "the unlisted read costs nine statements and a pill's eight, on a small site and on one with thirty more pages, their blocks and sections, and thirty more posts"; `search_test.rb`: "it costs six statements whatever the number of pages, posts, tags and list blocks, and loads no page and no post whole"). **A statement test must vary what could cost a statement.** The local view's first one varied only posts, with no child and no grandchild, so a statement per child would have gone unseen; and the first posts-scope assertions were vacuous in the same way (next paragraph). A new read of pages or posts for the graph goes into `PostGraph::Site`, not into a loop. Measured on 2026-10-13 at 204 pages and 2,005 posts (the pages spec's "As built" has the whole table and how each figure was taken): the whole graph's data 0.14 s and 844 kB (55 kB gzipped) for 2,202 nodes and 6,204 lines, of which the statements are about a tenth; where to open instead 0.05 s; a local view, a search and each list read under 0.06 s.

**Rights and the trash, at every read.** A page is in the graph only through `AccessControl.scope(actor, "pages.read", Page.all)` and a post only through the posts' scope, which also leave the trash out; what is outside is not a node, not in a count, not a search row, not a list row, and at no line's end. A tree line needs both pages readable, so a page whose parent is outside the scope (or in the trash) is drawn without one. A tag that only an unreadable page lists is no node. The legend names only the kinds and the post types the viewer can read something of (below). Both views, the search and both list reads are in `test/integration/trash_visibility_test.rb`, for a trashed page as for a trashed post. **Each of these needs a test that can fail.** The review of this build found the opposite twice: nothing failed when `PostGraph::Site` stopped asking the posts scope for rights, and the local view's posts-scope assertion held nothing about a pill's count, a hub's count or a page's `listed_count`, because the viewer it used could read every post. The tests that hold it now give the viewer a real partial scope and search the whole body for what must not be there (`test/queries/post_graph/local_test.rb`: "around a page a viewer who reads only some of the posts it lists is shown and counted those alone: the nodes, each pill, each hub's count and the page's listed count"; `test/queries/post_graph/global_test.rb`: "a post outside the viewer's posts scope is no node, in no count and at no line's end, and a tag only such posts carry is no node"; `test/integration/admin/mind_graph_data_test.rb`: "around a page, behind its pill and among the unlisted, a viewer is shown and counted only the posts they read").

**The tag rule.** A tag is derived only from readable posts and pages, and its `count` is the number of *readable* posts carrying it: never the tag's true total, which would disclose posts the viewer can't see, and not the smaller number drawn under a cap, which would understate it. A tag is a node when at least two readable posts carry it (`PostGraph::MIN_TAGGED_POSTS`) *and* it has enough lines in this response to say something: two in the whole graph, where a tag with one drawn post connects nothing, and one in a local view, where a post's own tags are its neighbours. Two exceptions: **a tag a drawn page's list block points at is a node whatever its count** (the lists line needs its end; the viewer can read the page, and its block names the tag), also with one post or none, and the focused tag of a local view is always a node. A listed tag's `degree` counts its lists lines. No line points at a node that isn't in the response.

**A page's local view.** Depth 1: its parent, its children, and the tags or post type its blocks list; no post (`nodes: []`, `total: 0`, so "no connections" must look at pages too). Depth 2 adds one more step along the tree (the grandparent, the grandchildren and the siblings, each with its tree line) and the posts it lists: the `PostGraph::LISTED_IN_VIEW` (20) newest OF THE PAGE, not of each target (by recency: when published, a draft when last changed). Each is joined by a faint `brings` line to the hub that brings it in (the type or "All posts" of the first block that lists it), NOT to the page; a post a TAG brings in has its "Shares a tag" line to that tag, which is its hub, and no other (two lines between the same two nodes would be one drawn twice). **"+N more" is one pill per target**: `more: [{ id: "more-<target>", count, page, target }]` (absent, not empty, when there is none), one for each target that brings in more than the view draws, each counting only what its own target brings in and hanging off it by a `brings` line; the pills' counts add up to what the twenty left out, a target that brings in nothing more has no pill, and a pill can hang off a hub none of whose posts is among the twenty. A drawn post also has its `tag` line to every listed tag it carries and its `related` line to any other post among the twenty; what it does not show is a tag the page does not list or a related post outside the twenty (the view is the page's). A neighbour page's lists line is drawn only to a target the focus itself reaches, so its card can say "lists 112 posts" with no line on screen. From a post or a tag the walk also steps along a lists line: the pages that list a tag are its depth 1. The answer also says what the site holds (`site:`, from the site's rows with no statement more: the pages and posts of the viewer's scope and the tags they can be shown), for the summary of the view a large site opens in (`test/queries/post_graph/local_test.rb`: "depth 2 around a page draws the twenty newest posts it lists, each joined to the hub that brings it in, and counts the rest behind more", "a page with two list blocks has a pill per target, each on its own hub or tag with its own count, and a target that brings in nothing more has none").

**The list's two reads** (`PostGraph::Rows`). `unlisted`: the readable posts no readable page lists. `listed(page, target)`: the posts one target of that page brings in beyond the twenty drawn, the rows behind that pill, each with `via` (the target), and the controller adds `posts_url`, the Posts screen filtered by the type and the tag of the block that points at the target (the tag named AS ITS ROW NAMES IT: a block finds its tag whatever the case and the Posts screen's filter does not, so a block spelled "News" for the tag "news" would have opened an empty list). Newest first, the first `PostGraph::ROW_LIMIT` (200) with the whole `total` (no paging: past 200 the answer only says `total` is more than its rows). A row is a post's node exactly as the graph's data has it, with no line counted (`degree`, `related_count` and `tag_count` 0), so the page adds a row that is not drawn to the canvas without another request. Each is its own read and neither a filter over the drawn nodes: a post no page lists is very likely a post with no connection, which the whole graph does not draw.

**Search.** `PostGraph::Search` answers up to ten of each, in this order: readable PAGES whose title matches in any language (`title_matching_any_locale`), in tree order (a tree is read by its order, not by a score; the first ten of the tree), each with its address in the editing language, else the default's (two pages may share a title, and the path tells them apart); readable posts by title, each with its type's `colour_index` for its dot; and tags by name (`Tag.name_containing`, those that start with the text first), a tag when a readable post carries it OR a readable page's list block names it, the two ways `Focus` finds a tag, so a result never leads to a 404. Every row carries the typed `id` and `record_id`, and the controller adds each row's local-view URL from the row's `kind` and `record_id`. A page is loaded with its id and title only and a post with its id, title and type (`test/queries/post_graph/search_test.rb` reads that from the statements). Three groups, not the list's four: a row opens its local view, and a post type has none. It reads the tree triple of every readable page and every list block of every readable page (to know which tags a page names) on each request: 7 to 23 ms at 204 pages (by the text and the shape of the site), which is on the roadmap as the first thing to cut if the search is ever slow.

**The page holds no data.** `show.html.erb` is a frame: the heading, the search field, the focus bar of a local view (or the hidden bar of the view a large site opens in), the legend, an empty canvas with the zoom control and the hidden "Release N pinned", the notice, the card's and the tooltip's containers, the list's empty region, and, OUTSIDE the graph's element, the status key's dialog. The script fetches `data-url`. The reason is size: at the cap the JSON is the better part of a megabyte, and inline it would sit in every load of the page and in Turbo's page cache. What the page does ask the database is small and independent of the site's size: the focus, whether this viewer can read a page at all, and the distinct content types of their readable posts, for the legend and for "No pages or posts yet." (said for *this* viewer: one who can read neither sees it whatever the site holds). The element carries the reads' addresses and the URL templates, all built by the route helpers so that no path is written in JavaScript: `data-url`; `data-open-url` (a page's local view's data, with `__ID__`) and `data-everything-url` (the data with `everything=1`); `data-unlisted-url` (only for a viewer who reads a page: for one who reads none every post is one no page lists, and the filter would say nothing) and `data-listed-url` (with `__ID__` and `__TARGET__`); the card's templates for a post's, a tag's and a page's focus, a tag's posts, and a post's and a page's open notes as JSON (each built for id 0 with that segment swapped, because the route takes digits only). It also carries `data-button-classes` and `data-dot-classes`, which are `Admin::Ui::ButtonComponent`'s and `Admin::Ui::ContentTypeDotComponent`'s own class strings (the card's actions and a type's dot in the card and the list are built in the script, and are handed the shared classes instead of holding copies), `data-type-labels`, and the script's strings as `data-messages` (every key written out in the view, because `test/lib/script_messages_test.rb` reads the literals; the same test reads a backticked `word.word` in a script's COMMENT as a message key, so a comment says "the worker's `add`" and not the dotted form). **The page takes no `everything` parameter**: only `data` does, so no address a person can keep or reload asks for everything (`test/integration/admin/mind_graph_test.rb`: "everything is no parameter of the page: the data url is the same with it"). **The scripts' class names are built only because the Tailwind build is told to read them**: `app/assets/tailwind/application.css` is `source(none)` plus explicit `@source` lines, and `@source "../../javascript/mind_graph"` is one of them. Without it nothing failed and `w-fit`, used nowhere else, was simply not in the stylesheet: each notice line was as wide as the longest one and each link of the card as wide as the card, so a click beside the text navigated. A new directory of scripts that writes class names needs its own line, and `test/lib/tailwind_sources_test.rb` fails until it has one.

**The layout of the screen.** The screen fills the window: from 1,100 pixels of width the heading and the box together are `100vh` less `<main>`'s padding and the top bar where there is one (`--admin-top-offset`), so the page does not scroll, and the box is a grid of the graph's column (a local view's focus bar or the opened view's, the legend, the canvas) and a 300-pixel panel on its right — the search field on top, the list below it, scrolling on its own. Below that width the three stack, the graph first, and the page scrolls. **The order of the document is not the order on screen, on purpose**: in the document the search comes first and the list last (the Tab key follows the document, and the list can hold two thousand rows), and the grid places each part by column and row. Move a part in the markup and the Tab order moves with it (`test/integration/admin/mind_graph_test.rb`: "the frame holds the search first, then the canvas with its controls, then the list; nothing is pinned", "the tab order is the search, the filter, the zoom buttons, then the canvas"). Within the graph's column the order is "Show everything" (inside its bar, hidden until a large site opens around Home), the legend's toggles, the "Status" link, then the zoom buttons and the canvas: the legend's toggles come before the zoom buttons.

**The worker, and why d3-force is imported by URL.** The layout runs in a module worker (`mind_graph/layout_worker.js`), so zoom, pan and clicks stay smooth while a graph of two thousand nodes is still settling; the page only draws. The worker is started from its own digest asset URL (`data-worker-url`) and is handed the vendored d3-force file's asset URL (`data-d3-url`) with its first message, which it imports dynamically: **an import map does not apply inside a worker**, so `import "d3-force"` can't resolve there, and the file is one self-contained bundle, so the URL is all it needs. Nothing else loads d3-force. Its pin in `config/importmap.rb` is `preload: false` and stays only so `bin/importmap audit` and `outdated` still see the package; `pin_all_from "app/javascript/mind_graph"` is `preload: false` too, and the thin controllers reach `mind_graph/app`, and `mind_graph/swatches` with `mind_graph/theme`, through a dynamic `import()`, so no other CS Studio screen fetches any of it (the swatches controller is loaded on every CS Studio page, as every `controllers/admin/*` file is, and imports the graph's modules only when a swatch is on the page; a static import there would preload them everywhere, and the test below would fail). (Before this, d3-force was `preload: "admin"` and every CS Studio page evaluated it.) `test/integration/public_javascript_test.rb` keeps both off the public pages and out of the other screens' preloads. There is no second code path that lays the graph out in the page: if the worker can't start, the box says "The graph can't be drawn in this browser.", with no Retry (a browser that can't run it once can't run it twice), nothing is drawn, and the list beside the canvas still gives every node, and still follows the legend, which is applied to the list, the counts and the canvas's name whenever there is data, a layout or not. A row then opens the node's card in the canvas's top-right corner, without Pin (there is no layout to hold anything in), and the card's links lead on.

**The worker's messages** (documented at the top of `layout_worker.js`). In: `start` (the d3 URL, nodes as `{ id, radius, anchor }`, lines as `{ source, target, kind }`, `reducedMotion`, and `springs` and `ease`), `drag` (a node held under the pointer), `drop` (the pointer let go; the node stays), `pin` (hold a node where it is), `unpin` (let these ids go) and `add` (one more node, placed where the page says, with its lines: a post added from the list). Out: `tick` with one `Float32Array` of x/y pairs covering every node given to `start` and after them every node an `add` brought, transferred and not copied; `settled`; `error`. Three rules here each answer a bug. **Messages are handled strictly in order**, each after the one before it has finished: `start` awaits the import of d3-force, and a message sent right behind it used to run before the simulation existed (it threw, or a drag was dropped). **`settled` carries `after`**, the number of messages the worker had taken up when the layout cooled down, and `layout_client.js` passes it on only when that equals the number it has sent: a small graph cools down inside the first slice, before a message sent right behind `start` is handled, and the page used to fit the view and call itself settled on a layout it had already asked to change. And **a `drag` wakes a cooled-down graph**: `alphaTarget` only pulls `alpha` up by ticking, and the loop does not tick below `alphaMin`. A message that moves nothing (a `pin`, a `drag` of a node that isn't there) is still answered with a `settled` when the layout is at rest, because the page waits for one that counts it. **There is no `filter` message.** The worker had one for the old radios, which laid the shown nodes out again; the legend's toggles are a filter on what the PAGE draws and send the worker nothing (below), the message was dead from then on, and it was removed with its code, with a guard that holds its absence from the page, the client and the worker alike (`test/lib/mind_graph_guards_test.rb`: "no script of the mind graph knows a filter message for the layout: not the page, not the client, not the worker"): whoever brings a second layout back for a toggle has to take that test away first, and read why. **A tick posted before the worker took an `add` is two numbers short** of what the page holds; the page completes it with the places it has (`graph_data.js`, `placedFor`), so an added node always has a position and no `NaN` reaches the renderer, the card or the camera. An added line one of whose ends the layout does not hold is not handed to the forces: d3 looks a line's ends up among the nodes it lays out and throws for one it does not find, and the worker's error would take the whole graph down for one line.

**Springs, the anchor and the ease are values the page hands the worker** (`mind_graph/layout_parameters.js`, sent with every `start` by `layout_client.js`): `SPRINGS`, a line's spring by its kind (`{ tree: { distance: 40, strength: 0.9 } }`: a tree line is short and stiff, so a subtree stays together; a kind that is not named has d3's own, a rest length of 90 and a strength that falls with the number of lines at its ends), and `EASE` (`{ keep: 0.85, within: 0.5 }`). They are the pages spec's starting values and were not tuned: at the measurement the tree held together as one cluster beside the posts and no page was drawn into a tag's cluster, and how tight that cluster should be is the designer's to say. They are values, not constants in the worker, so that a test can read them and LOWER them: a test of the worker gives it springs and an ease of its own instead of waiting out the real ones ("In tests"). **One node rests at the centre** (`graph_data.js`, `anchorOf`): **Home in the whole graph, the focus in a local view**, where Home, if it is drawn, is a page like any other. The worker holds it at 0, 0 (`fx` / `fy`). It is not a pin: `state.pinned` does not hold it, nothing shows it as pinned and nothing the page forgets or releases can let it go. Dragged or pinned it is held where the person put it, like any node, and `unpin` gives it back to the centre, not to the forces. The design answer fixed Home "while the layout runs", speaking of the whole graph; as first built Home was held in every view that contained it, so around any other page the focus hung off-centre, and a person who asks for the graph around something expects it in the middle. That holds for a post's and a tag's local view too, which is new: before this build nothing held a focus anywhere. **Back to the centre is eased**: a released anchor is held a little nearer with every tick, so it travels like every other released node and its subtree is not yanked after it; with reduced motion, and at `start`, it is simply there. The ease starts from where the node is HELD (`fx`), not from where it is: `x` follows `fx` only with a tick, and an anchor dropped and released before the next tick used to be taken for a node that never left, and jumped. No pinning by depth and no rings by level: they would fight the post clusters (`test/system/admin/mind_graph_test.rb`: "pages and what they list are drawn, and Home rests at the centre without being pinned", "in a local view the focus rests at the centre and Home does not"; `test/system/admin/mind_graph_modules_test.rb`: "graph data: the anchor is Home in the whole graph and the focus in a local view, of whatever kind", "layout parameters: the tree's spring and the anchor's ease are the configured values").

**The pacing** is the worker's, and is what makes the screen feel alive or dead. The simulation's own timer is stopped and the worker steps it by hand at one of three paces. *Frame pace*: one tick, one `tick` message, then 16 ms — a small graph's first layout (up to `SMALL_GRAPH`, 300 nodes; 300 ticks, about five seconds at the 18 ms a tick measured in 2026-10-08 and 6.2 s at the 21.5 ms measured on 2026-10-13, so the figure is the browser's timer more than the code's), a drag, and the settle after a drop, an added post or an unpin, so the neighbours visibly follow a held node and the graph eases to rest. *Fast*: as many ticks as fit in 12 ms, one message, and a zero timeout so a message that arrived meanwhile is handled before the next slice — a larger graph's first layout, until about 600 ms of ticks are left (`FINAL_STRETCH_MS`), which are then shown at frame pace. *Silent*, with reduced motion: no message until the layout is at rest, then one; a dragged node moves alone (`drag` posts the positions last shown with that one node moved, and ticks nothing) and `drop` shows the result in one step. Before this the worker always ran fast, so a small graph was at rest in its first message and nothing was ever seen to move — "it was more alive before" was the owner's first remark. Every run ends: `alpha` decays below `alphaMin`; only a held node keeps the layout warm, and `drop` takes that back. **The page tells the worker about reduced motion with `start`** (a worker has no reliable `matchMedia`), once per load. At the cap frame pace holds. A toggle of the legend starts no layout at all (below), so nothing eases after one. The system tests wait a first layout out, five to six seconds each. An error in the worker is posted to the page and reported with `console.error`, on purpose: the system tests fail on any console error, so a worker that breaks is never a graph that silently stays empty.

**The modules and what each owns.** `controllers/admin/mind_graph/graph_controller.js` is deliberately thin, because every `controllers/admin/*` file is loaded on every CS Studio page: it imports `mind_graph/app`, mounts it, destroys it on `disconnect()` and resets the snapshot's state (below). A `connect()` may be followed by `disconnect()` before the import has arrived, so a token (`this.live`) says whether the connection is still current and a late import mounts nothing. A failed `import()` is left unhandled so it is loud. `controllers/admin/mind_graph/swatches_controller.js` (`admin--mind-graph--swatches`) is the second, as thin: it sits on the legend and on the status key's list, paints their swatches on connect and on a theme change, and exists because the key is outside the graph's element, where the graph's script must write nothing. In `app/javascript/mind_graph/`, each file's header is its contract:
- `app.js`: wires the rest: the data request (aborted on leaving, timed out after 15 seconds into the same message as a failure, with Retry), the worker, the state, one redraw per animation frame and only when something asked for one, the legend's filter, the notice, the summary, the list's reads, the tooltip, and the state said on the element. `destroy()` stops all of it (the request, the worker, the frame, the observers), so nothing runs or draws after the screen is left.
- `ids.js`: `nodeId` and `recordId`, the one place an id is taken apart.
- `graph_data.js`: the payload as the page holds it, plain functions with no canvas and no element: `nodesOf` (nodes of five kinds), `anchorOf`, the label order (`rank`, `orderOf`) and the set named at any zoom (`freeOf`), `visible` and `counts` (the legend's filter), `countAdded` (the figures after a post is added) and `placedFor`.
- `marks.js`: every mark and its size, and the looks table (below).
- `layout_worker.js`, `layout_client.js`, `layout_parameters.js`: the layout, the page's side of it and its values; one worker per graph, terminated by `stop()`.
- `camera.js`: `{ k, tx, ty }` and pure functions: zoom at a point, pan, bounds, fit. Zoom is limited to 0.05 to 4, and a fit never zooms in past 1.5.
- `hit_test.js`: the node under a point (below).
- `labels.js`: which labels are shown (below).
- `renderer.js`: draws one frame: lines, nodes (each with its pin mark and its notes badge), labels, rings; the five line styles; and the states: hovered, selected, pinned.
- `theme.js`: the colours, fonts and the card's radius, read from the `--cs-*` custom properties and read again when `<html data-theme>` or the system scheme changes. The script holds no colour value (`test/lib/admin_design_rules_test.rb`).
- `summary.js`: the canvas's name, a pure function (below).
- `swatches.js`: the legend's and the key's swatches and a row's mark, drawn by the renderer (below).
- `input.js`: the canvas's pointer, wheel and key events as callbacks, a double click among them. It knows nothing of the graph. A pointer ends on `pointerup` or `pointercancel`, and a touch or a pen on `lostpointercapture` too: a touch can lose both of the first two, and its entry left in the table would turn every later touch into a pinch with a ghost. A mouse is left out of that, because its `pointerup` always comes and a capture dropped between the press and the first move would otherwise end a drag that is still held. After a pinch, a new finger arriving while one remains restarts the pinch.
- `card.js`, `card_notes.js`, `node_list.js`, `search_box.js`: the selection card's content and its notes, the list beside the canvas, the search field's results. All write text with `textContent` and URLs with `href`, never markup: a title, a path and a tag's name are the editor's text, whatever they contain.
- `card_placement.js`: where the card stands: pure numbers, so it is tested without a canvas.

**The camera.** The first view fits everything: the camera follows the layout from its first positions until it has settled, and that fit is final. From then on — or from the user's first zoom, pan or drag of a node, if that comes sooner — it moves only on the user's input or "Fit all"; a toggle of the legend, a resize and a later reheat of the layout leave it where it is. Nodes are not clamped to the box; the box is a window. The wheel and a trackpad's pinch (a wheel event with `ctrlKey`) zoom towards the pointer, a two-finger touch pinch zooms around the point between the fingers (tested with synthetic pointer events only), a drag on empty space pans, a drag on a node moves that node and pins it (below). The wheel always zooms: no modifier key and no hint, since the page itself does not scroll. With the canvas focused, the arrow keys pan and `+` / `-` zoom. A press released within five pixels of where it began is a click, whatever it was on. A row of the list centres the camera on its node, at the zoom it has. The zoom control — −, the zoom as a percentage, +, "Fit", each named in full by its `aria-label` and tooltip — comes before the canvas in the document, because Tab follows the document, and is positioned over its bottom-right corner, with "Release N pinned" beside it while a node is pinned.

**The marks** (`marks.js`; the values are the design answer's, its later parts where they replace earlier ones). Everything is in SCREEN pixels, the same at every zoom, and each kind is a shape of its own, so none is told by colour alone. A **post** is a dot filled with its type's hue (colour slots 1 to 6); a **ring type** (slots 7 to 12, and 13 on cycle) is the same mark, smaller (4/7 of the radius, rounded to half a pixel), inside a 1.5px ring of the hue; a post of a type that is **no longer registered** is a ring type in `meta` *with a diagonal stroke through it* (before the first redesign it was the same shape as a 7 to 12 ring and differed by colour alone). A **page** is a small card, 14 by 10 with the card's corner radius (`--cs-radius`, read through the theme), **Home** 18 by 13, in neutral ink: the hues mean post types. A **post type** a page lists is a hub: a 12px circle in the type's hue with a surface ring inside it, so it is not one more post; **"All posts"** is the same, filled in `dim`; a ring type's hub is a ring in the hue round a filled centre; a **retired** type's is a DASHED ring in `dim` round a small `dim` centre, so it differs from "All posts" by fill, not by shade, and from a ring type's hub by its dashes. A **tag** is a square. **"+N more"** is a pill with its words inside it (10px mono, the figure grouped), 16 high, as wide as its words need with 8px each side and never under 60. A post's and a tag's **size** follows `degree` in four steps (a post's radius 7, 10, 13 and 16, up to 2, 5 and 12 connections and beyond; a tag's half side 4.5, 6, 8.25 and 10.5: `STEPS`; a post's were a step smaller until the owner compared the screen with the design review's mock), because small differences in size can't be read; a page's, a hub's and the pill's size is fixed. **A mark's size is its outer size**: every outline is traced half its width INSIDE the mark's edge, so an outlined mark is exactly as large as a filled one and has the size the design gives (a draft page is 14 by 10, a ring type's hub 12 across, the pill 60 by 16 with its border in it). As first built strokes were centred on the edge and every outlined mark was 1.5px larger than its filled twin. Two marks are older than that rule and were left as they were: a live filled post's own outline in its hue, and a tag's square.

**The five looks are ONE table**, `LOOKS`, with `lookOf(node)` choosing the row from the data's `status` and `changes`; a page, a filled post and a ring type's inner mark all draw their row through one function, so the five are the same on every mark. A value of the table is a theme KEY, never a colour:

| State | Fill | Outline | Dashed | Centre dot | Corner dot |
|---|---|---|---|---|---|
| `live` | own | none | | | |
| `draft` | `surface` | `meta`, 1.5px | yes (3 / 2.5) | | |
| `scheduled` | `surface` | `dim`, 1.5px | no | `warn`, 4px across | |
| `unpublished` (live, `changes: "unpublished"`) | own | none | | | `dim`, 5px across on a 1.5px surface ring |
| `change_scheduled` (live, `changes: "scheduled"`) | own | none | | | `warn`, the same |

"Own" is ink for a page and the type's hue for a post (`meta` for a retired type's). **Warn means "scheduled" everywhere**, as on the status chip: a scheduled record's centre dot and a scheduled change's corner dot; unpublished changes are `dim`. **A draft is dashed on every mark**, so no state rests on colour alone. The corner dot stands one pixel in from the mark's bottom-right corner (on the 45 degree line of a circle, on the OUTER ring of a ring type), so the corners are: notes top-left, pin top-right, changes bottom-right. `changes` is read for a live record only, and a status the table does not know is drawn live, not left undrawn. A hub, a tag and the pill have no state. One test walks five marks by the five states against a second copy of the table written in the test and asserts the 25 drawings are all different (`test/system/admin/mind_graph_modules_test.rb`: "marks: every mark that has a state is drawn in each of the five looks exactly as the table says, no two alike, and a draft is dashed on every one").

**The theme's keys and the token behind each** (`theme.js`, `TOKENS`): `ink` `--cs-ink`, `meta` `--cs-meta`, `dim` `--cs-dim`, `warn` `--cs-warn`, `surface` `--cs-surface`, `sunken` `--cs-sunken`, `accent` `--cs-accent`, `line` `--cs-line-strong`, `faint` `--cs-line`, `categories` the six `--cs-cat-<n>` hues, the fonts from the page's own family and `--cs-mono`, and `radius` from `--cs-radius`, read as a number of pixels (a token given in `rem` would be read as that many pixels, with no error). Note the two names: the script's `line` is the STRONG line token (the tree's lines, the pill's and the notes badge's border) and its `faint` is the plain one (a hub's lines to what it brings in). Every module test but one draws with a theme whose values are their own names, which holds "the pill's border is the key `line`" and not "`line` is `--cs-line-strong`"; one test gives each token a value of its own and compares the whole object, because the review found the map held by nothing ("theme: every key reads the token the design names, the type hues, the fonts and the card's radius included").

**The lines** are five styles (`renderer.js`, `LINE_STYLES`), one path per style and strength, drawn in this order so a tree line is on top of a tag's: *Shares a tag* dashed `meta` (1px, 4 / 3, at 80%); *Related* solid ink (1.5px at 35%); a hub's *brings* line solid `faint` (1px); *Lists* dotted `dim`: 1.5px with ROUND caps and a dash of 0.1 / 3.5, which is a row of round dots 1.5px across (with a butt cap it would be a hairline); *Tree* solid `line` (1px). **Below 40% zoom a shared tag's lines are not drawn** (`HIDE_TAG_LINES_BELOW`): zoomed out they are most of the ink and say the least. That is a drawing rule only: the legend's counts and a selection's neighbours do not change with it. The focus of a local view has a dotted ring in the accent colour.

**The states** combine, and none is colour alone. *Hovered* — by the pointer or by its row in the list — is a 1px ink ring and the label in full ink on a backing, shown even where the label rule hides it; hovering dims nothing. *Selected* is a 2px accent ring with a gap, a semibold label, its own edges brightened, and every node and edge not connected to it at 28%. *Pinned* is a small ink dot with a surface ring at the mark's top-right, drawn with the node at the node's strength; the legend's "Pinned" swatch is the same mark, drawn by the same code. *With open notes* is the count in a small mono pill at the mark's top-left, opposite the pin (never a ring: a ring is hovered, selected or the focus), always neutral (unread is said on the card's rows); its right edge is fixed 4 px over the corner and it grows to the left, so it never reaches the pin's dot; above ninety-nine it reads "99+". A ring follows its mark: a tag's is a square, a page's card's a box, the pill's a pill (rounded as the pill is: as first built it was a square-cornered box round a rounded pill, two borders), every other a circle. So does what hangs on a corner: on a box the pin and the notes badge stand on the box's own corners (`marks.js`, `topCorner`), not where a circle as wide as it would have them (a pill's radius is half its width, 30 or more, so its pin would have stood 21px above a 16px-high pill).

**What is not drawn.** A node whose mark lies wholly outside the canvas is skipped, and so is an edge that can't cross it: both ends beyond the same side. Not "both ends outside" — an edge from far left to far right crosses the whole view. This came out of the measurement: zoomed in, most of the graph is outside, and a path of long dashed lines costs the rasteriser by its length whether it is seen or not, which made about one frame in fifty late at the cap. And nothing is drawn before the worker's first positions arrive (`state.placed`): until then every node is at 0, 0, and the first frame after the data came used to draw the whole graph as a pile in the canvas's top-left corner — for one frame normally, and for good when the worker failed.

**Hit testing is by containment first** (`hit_test.js`). A node's mark and its label are one target. *What is drawn comes first*: a press INSIDE a mark (within a dot's radius, on a box) is a press on that mark, whatever other target reaches the point with its slack; the nearer centre decides only among marks that hold the point, or, where none does, among the targets that reach it (a mark's radius plus four pixels of slack, never less than 24 pixels across, at any zoom). As first built the nearer CENTRE always won, and a pill is 60 pixels wide or more, so a press on its drawn end was 30 from its centre and a post resting against it took a press that was on the pill's words. A page's card and the pill are pressed ON THE BOX (`boxes`, from `marks.js`'s `boxOf`), grown by the same slack and never less than the least target either way: a circle as wide as the pill would take every press 25 pixels above and below it. Then the boxes of the labels *the last frame drew* (a label that is not drawn can't be pressed), the last drawn first, because that one is on top. Still a linear scan over the visible nodes: at 2,202 nodes a pointer move's handler returns in under 0.1 ms, 0.3 ms at worst, so the quadtree the design answer names is not built (pages spec, decision 12: only if a frame is late).

**The label rule** (`labels.js`). (1) Hubs first, among the nodes *on the canvas*: the zoom decides how many labels there are — 40 at zoom 1, growing with the square of the zoom — and they go to the best-connected nodes inside the view, so zoomed into a corner the budget is not spent on hubs nobody can see. The cost is that a label can appear or disappear while panning. The last quarter of that reach is drawn fainter, so a label arrives gradually with zoom; with `prefers-reduced-motion` it switches. (2) No overlap: a label is placed only where no earlier one is, and better-connected nodes place first. (3) The selected node, then the focus, then the selection's neighbours are labelled at any zoom and place before everything else — but rule 2 holds among them too: **no overlap wins over "always labelled"**, and a neighbour gives way to the selection however well connected it is. (4) **`free`**: Home, the top-level pages and the post-type nodes (`graph_data.js`, `freeOf`) are labelled at any zoom and do not count against the budget of rule 1; they place after rule 3's and before the ranked rest, and no overlap still wins over "always shown". `chooseLabels` has no default for `free`, on purpose: the wiring only shows on a graph with more free nodes than the zoom's budget, which no small test graph is, so a caller that forgets the argument throws in every frame instead. **The order** labels are placed in (`orderOf`) is Home, then the top-level pages and the type nodes, then everything else by its lines, a page ahead of a post with as many (`PAGE_BONUS`, half a line, a reading). **The colours**: a page's and a post type's label in ink, a tag's in mono `meta` (mono like a tag everywhere else in CS Studio, and still mono, semibold, when selected), a post's in `dim` until it is hovered or selected, both of which are full ink; the pill has no label, its words are inside it. A label's width is measured in the font it is drawn in (`renderer.js`, `labelFont`), once plain and once semibold, so the label rule, the hit test and the hover's backing agree with the words drawn. A label sits right of its node, is cut at 32 code points with an ellipsis (so an emoji is never cut in half), and a tag's keeps its count whole: "name (N)".

**Selecting, and the card.** A click on a node — its mark or its drawn label — selects it: it and its direct neighbours *by the edges shown* stay at full strength, the rest dims, and the card opens **beside the node** (`card_placement.js`): 22 pixels from the node's edge and vertically centred on it, on the node's left where the canvas's right edge is too near, and clamped 8 pixels inside the canvas. Its place is worked out in the frame that draws the node, from the card's size as measured once when it was filled, so it follows a pan, a zoom and the layout's own movement without lagging, and its style is written only when it moves. It hides while its own node is dragged and returns on the drop. It was in the canvas's top-right corner before, and the owner's remark was that it was far from what it is about; the corner is still where it goes for a node without a place (the worker failed and the selection came from the list). A post's card has its type's dot and name, its status chip (`Admin::Ui::StatusChipComponent`'s classes: a dot and the word), the title, "N related · N tags" in the small label style, and its actions as CS Studio's buttons: "Open post" (primary), "Focus", "Pin" / "Unpin"; and its open notes (`card_notes.js`: "Open notes · N", at most three rows, "+N more" into the post's editor with `?notes=open`, and a field that starts a note with origin view `mind_graph`), read from `GET notes/post/<id>/threads` (`admin_record_note_threads_data_path`, a bare 404 outside the read scope) after the card is shown, so the card is measured again when they arrive. The notes stand under the title and its counts and the actions follow them, on screen and in the document alike (the notes handoff's decision 12: the document order follows the screen), so Tab walks the card as it reads: the notes' rows and the "Start a note…" field, then "Open post", "Focus" and Pin. "Open post" is therefore no longer the first stop and has a key of its own: Enter on the selected node, on the canvas or on the card as it takes the focus from the list, opens the post (on a control inside the card Enter is that control's). As first built the notes were drawn above the actions but came after them in the document (the actions' row was `order-1`), so the focus order and the visual order disagreed. An unread row is ink for dim, an accent dot and the visually hidden word "new". The card's notes section is a `record` of `admin--notes--live`, so it reads its list again when a thread of the post changes (`docs/reference/notes.md`, "Live delivery"). A click on the node the card already shows does not build the card again, so a note half typed in it stays. **A page's card** (Home's is the same): its mark and its address in mono, the status chip, the title, "4 child pages · lists 112 posts" (`child_count`, `listed_count`: the scoped payload's, nothing is read a second time), its open notes as on a post's card (`data-page-notes-url`; the field says "Write a note on this page"), then "Open page" (the node's `url`), "Focus" and Pin; Enter on a selected page presses "Open page". **A post type's card**, and "All posts"': its hub's mark and "Post type", its name (a retired type's ends "(retired)"), "N posts" (`count`), Pin, and no link: a focus is a page, a post or a tag. **A pill is not selected**: a press on it opens its rows in the list (below). **The status chip**, on a page's and a post's card alike, keeps its three dots and names a live record's second state after the label: for the eye "● Live · Unpublished changes" with no second dot and "● Live · ● Change scheduled 14 Oct" with a warn dot, and that row is `aria-hidden`; a screen reader is given the status key's own sentence, "Live, unpublished changes" or "Live, change scheduled 14 Oct" (one set of words: `status_key.states` in `mind_graph_screen.en.yml` and `script.card.status` in `mind_graph.en.yml` are changed together, and nothing checks that). The day is the server's `change_on`. A chip of two states does not fit the first row of a 240-pixel card (217 pixels in English: it covered the address and ran under Close), so it stands in a row of its own. A mark in the card is a small canvas drawn by the graph's renderer (`markCanvas`, `paintMarks`), not a copy in CSS. **A post added from the list says nothing of its related posts and tags**: its row was read with no line counted, so its two counts are null and the card leaves the "N related · N tags" line out instead of saying "0 related · 0 tags" of a post that may have both. A tag's has "Show posts with this tag" (the posts list with its `tag` filter), "Focus" and "Pin" / "Unpin". What leads somewhere is a link drawn as a button, so it opens in a new tab like any link and a test follows it with `click_frame_link`; Pin is a button. Close is × in the card's corner, named "Close", and *last* in the document, so Tab meets the actions first. **A click on the canvas never navigates**; the card's links do. A click on empty canvas, Escape (from the canvas or from inside the card) and Close clear the selection; the last two give the focus back to where the card was opened from, the canvas or the list's row. A press that moves is a drag, not a click, and a plain click sends the worker nothing — a `drag` reheats the layout, and the graph would twitch under every click. A toggle of the legend recomputes the neighbours, and clears the selection when it hides the selected node. The tooltip with the whole title is shown only for a title the label cuts short: the hovered label on its backing already names the node.

**Pinning.** A dropped node stays where it was dropped: `drop` leaves `fx` / `fy` set in the worker, where `onDrop` used to send `unpin` — which is why it sprang back. A node can also be pinned where it stands from its card. Which nodes are pinned is the page's to know (`state.pinned`, indexes) and to show: the pin mark, the card's button reading "Unpin", `data-pinned` on the element, and "Release N pinned" beside the zoom control, which is in the page hidden and is shown, with its pluralised label, only while something is pinned. Three things release: "Unpin", "Release N pinned", and a double click on the node (`input.js`'s `onDoubleClick`; both of its clicks have selected the node already). **Pins live in the page that made them**: nothing is stored, a reload forgets them, and the controller's `reset()` takes the count and the button back on a restored snapshot. **A toggle of the legend touches no pin**: a pin is the layout's, and letting a hidden node go would warm the layout up, which a toggle must not do. A pinned node that a toggle hides is still held, still counted by "Release N pinned", and comes back pinned where it was dropped (`test/system/admin/mind_graph_test.rb`: "a toggle keeps every pin, also of a node it hides, which comes back pinned where it was dropped"). This reverses the radios' behaviour, where a filter change forgot the pins of the nodes it hid. A node is held where it was grabbed, not by its centre, so a drag by the label does not make the mark jump to the pointer.

**The legend is the FILTER, and a filter moves nothing.** `Admin::MindGraphScreen::LegendComponent` draws two fieldsets of native checkboxes (`Admin::Ui::CheckboxComponent`), all on: Pages, Posts, Tags, Post types; Tree, Lists, Related, Shares a tag; then the "Status" link, then the keys that are not controls (the post types' dots, "Retired type" when present, "Pinned", "Open notes"). The radios (All / Related / Tags) are gone, and there is no "Links in text" toggle, not even a disabled one (step two). `graph_data.js`'s `visible({ nodes, edges, on })` is the one place that decides what is shown: a kind of node that is off hides its nodes and every line that touches one; **a kind of line that is off hides its lines and nothing else**, so a node is hidden by its own toggle only; the pill stands for posts and goes with them; a hub's faint `brings` line has no toggle and follows "Lists". It is held over all 256 combinations of the eight toggles in one script call. **A toggle is a filter on what is DRAWN, not a new layout.** The layout is computed once, over everything the data holds; a toggle sends the worker nothing, moves no node, warms nothing up, leaves `data-settled`, the camera and every pin as they are, and what is switched back on comes back where it was. What a toggle changes is `state.visibleNodes` and `state.visibleEdges`, which the renderer, the hit test, the labels, the list and the summary read. **This departs from the pages spec's §5**, which hands a toggle "to the worker as today's filter is". That was the old radios' way, and as first built every toggle re-ran the whole layout at alpha 0.8: with eight toggles, four of them of lines alone, the picture reshuffled when a line was hidden, nodes the toggle did not touch moved, and one could leave the view with no refit (in the review's screenshot the page "Team" was outside the canvas after only tags had been switched off), while "comes back where it was" was asserted only as "has a position". The designer's "the legend is the filter" reads the other way, and so does a person. The price is said in `app.js`'s header and is the designer's to rule on: a cluster does not close up when what held it apart is hidden. The test compares every node's position before and after each of the eight toggles, off and on again, and records every message to the worker (`test/system/admin/mind_graph_test.rb`: "a toggle moves nothing: after each of the eight, off and on again, every node is where it was and the layout was told nothing").

**Which toggles a viewer gets is one rule**, `PostGraph::Kinds.shown(pages:, posts:)`, read off what the builder can answer: a page, a hub, a tree line and a lists line need a readable page; a post, a related line and a shared tag's line a readable post; **a tag needs either**. The tag is the case a rule of "tags hang on posts" misses, and as first built did miss: someone who reads pages and no post is shown the tags their pages list, and without a toggle for them could not switch them off and had no key that says what the square is. The legend asks `Kinds` and holds no rule of its own; `Kinds` is a hand-written table, held equal to what `Global` and `Local` answer by `test/queries/post_graph/kinds_test.rb` on a site built to contain every kind, so a new kind of node or line needs a row there. **A kind is hidden only by a toggle that is switched OFF, never by a toggle that is absent**: as first built "what is shown" was "the toggles that are checked", so a kind the viewer has no toggle for was never shown (a real viewer without a toggle has no such nodes in the data, and only a stubbed payload found it). The post types the legend names are those of the viewer's readable posts: a legend of every registered type would disclose types they can't read. Every toggle carries `autocomplete="off"`: "a new visit starts from the defaults" (decision 8), and Firefox would otherwise put a form's state back on a reload.

**The counts beside the toggles are the script's** (the page holds no data): `counts(nodes, edges)`, the number of each kind and of each kind of line in this response ("Post types" counts the type nodes and "All posts"; a hub's faint lines are no Lists lines), written once per load, with the checkbox's whole accessible name ("Pages, 200", one key). **A toggle changes none of them**: one that is off still says what switching it on brings. `reset()` takes the counts and those names back on a restored snapshot; **the checkboxes' state is the person's and is kept** (`test/system/admin/mind_graph_test.rb`: "Back to the graph draws it once, with what the legend shows: its counts gone until the data is back, its checkboxes kept"). A toggle can show a count of 0 for a kind the viewer may be shown and has none of.

**Status is not a filter.** The five looks are a key of their own: `Admin::MindGraphScreen::StatusKeyComponent`, CS Studio's modal dialog (`Admin::Ui::DialogComponent`, id `mind-graph-status-key`, named "Status key"), five rows in the chip's words and no control but the dialog's Close, opened by the legend's "Status" link (a button that reads as a link, wired to `admin--ui--dialog`; Escape closes it and the focus goes back to the link). It is rendered by the view OUTSIDE the graph's element, so it is not the graph's: the graph's script neither opens nor writes it, and `reset()` does not touch it.

**The swatches and the row marks are canvases drawn by the canvas's own marks.** `Admin::MindGraphScreen::SwatchComponent` renders an empty sized `<canvas data-swatch>` (`SIZES`: each swatch's size in CSS pixels; hidden from a screen reader, its name stands beside it), and `mind_graph/swatches.js` holds one scene per swatch, one node or one line, and hands it to `renderer.js`'s `draw`, so `marks.js` and `LINE_STYLES` draw it at the smallest size the canvas draws. A swatch is therefore not a copy of a mark in CSS or SVG that could drift from it: change a look in `LOOKS`, a size, a line's dash, and the key changes with the canvas. The pages plan had SVG on `.mg-*` classes and the approved spec said so; the swatches were ruled otherwise while building, every `.mg-*` rule that drew a mark is gone from the stylesheet (what is left is `.mg-swatch`, which draws nothing) and the older keys (retired, pinned, notes) became canvases too. A swatch that names no type has no hue (the hues mean post types): the toggles' post is `dim`, as "All posts" is, and the status key's mark is a post's dot in ink (`KEY_MARK`, a reading). **A row's mark** in the list, a search result and a card is the same thing for a node of the data: `markCanvas(node)` answers a small canvas for a PAGE or a POST TYPE and `paintMarks(root)` draws every one inside `root`, smaller than on the canvas by a scale and nothing else (`ROW_MARKS`: a hub at 10/12, a page at 10/14), so a post type's row shows its hub as the canvas has it. A row's mark shows the KIND, not the record's state: a page's is the live look whatever the page's state is. A post's dot and a tag's square in a row are NOT canvases: they are CS Studio's own type dot and tag square, and a list can hold two thousand posts. Nothing is lazy, and the bound is the pages and the hubs: 208 canvases painted in 1.4 to 1.8 ms at the measurement. Both controllers repaint on a theme change, and the swatches after Back; a change of the device pixel ratio (a window dragged to another screen) repaints nothing, which is on the roadmap. `element.querySelector("canvas")` in `app.js` would have found a swatch (the legend comes first in the document), so the graph's canvas is found by its target.

**The canvas's summary** (`mind_graph/summary.js`, `summaryOf`, a pure function, so every form is a module test with no layout). The canvas is one image to assistive technology (`role="img"`) and its name says what is on it NOW: the counts in view by type, then the lines, then the scope. Until the data has come it is "Mind graph". The forms, in the designer's words:

- the whole graph: "Mind graph: 9 pages, 3 post types, 13 posts and 4 tags, 27 connections. Showing everything.";
- a local view: "Mind graph around Blog, depth 2: 7 pages, 1 post type and 20 of 112 posts. 92 more are in the list." ("N of M posts" and the "more" sentence only around a page that lists more than the view draws: M is the page's `listed_count`, and "more" counts every pill in view together; a kind with nothing in view is left out);
- the view a large site opened in adds "Showing the area around Home. The site has 212 pages, 2,040 posts and 64 tags." (what the viewer can read of the site; no other view says it);
- a kind switched off adds "Tags hidden.", a kind of line "Shares-a-tag lines hidden.", after the scope, kinds then lines: "Showing everything. Tags hidden." are both said, since "everything" means no cap, not no filters;
- nothing in view: "Mind graph: nothing to show. All types are hidden." when every toggle the viewer HAS is off, "Mind graph: nothing to show. No pages, posts or tags yet." when there is nothing, and "Mind graph: nothing to show. 2 posts have no connections yet." when there are posts and no connection among them: the notice's own sentence, a reading, since neither of the designer's two is true there;
- **"Showing everything." is never said at a cap**: a whole graph cut at the posts' cap says the notice's cap sentence in its place.

A sentence is one message, two are joined by one space and nothing else, and the counts are joined by the messages' own `pair` and `series`, so another language can join them otherwise. After a toggle the same words go into the notice's polite live region in an `sr-only` line, which is how the change is announced. The old name counted pages, hubs and pills as "N posts and tags".

**The list** beside the canvas is the keyboard and screen-reader path, and a way to find a node by name for everyone: nothing on a canvas can take focus, so every drawn node is also a row. **Four groups**, each a list named by its heading: "Pages · N" first, in TREE order (not by connections: a tree is read by its order), then "Posts · N" and "Tags · N", best-connected first, then "Post types · N", a row for each post-type node and for "All posts" in the order the data has them (colour slot, then retired, then "All posts" last), so each has a keyboard path to its card; a row's number there is the type's POSTS, where a tag's row has its connections. **The Pages group is a tree for a screen reader too**, not an indent alone: a page's row stands in a list INSIDE its parent's item (by the data's `parent`), so the nesting is the document's and is announced as a level; the 12px a level is for the eye, and every list has `role="list"` (a list styled without markers loses its role in Safari). **A row is a button, and it selects**: it does to the graph what a click on the node does, centres the camera on the node, opens its card and moves the focus to the card (which is named by its title, so a screen reader says what opened); closing that card gives the focus back to the row. It never navigates; the card's links do. Its accessible name is one key that says all of it ("Alpha: post, 2 connections. Shows it in the graph."; `list.select_page` / `select_post` / `select_tag` / `select_type`), never strings joined in the script. Hovering or focusing a row gives its node the hovered state, and a node selected on the canvas has its row marked (`aria-current`) and scrolled into view *inside the panel*, by setting `scrollTop`, never `scrollIntoView`, which would scroll the page too where the panel stands under the canvas. The rows were links to a node's local view until the round of 2026-10-08, in a `<details>` under the box that started closed, and nobody found it. `node_list.js` rebuilds the list from the same data on every load and every toggle (about 30 ms for 2,202 rows at the measurement, row marks included), with one listener of each kind on the rows' region however many rows there are. It is filled before the layout starts, so it is there when the worker fails. **The focus is not lost when the rows are drawn again**: `render` and `showRows` replace the rows' own region and never the checkbox, and when the focus was in that region it is put on the row of the same node, else on the first row, else on the checkbox. In the document the search field comes first, then a local view's focus bar (or the opened view's bar), the legend, "Release N pinned", the zoom buttons, the canvas, the card and the list. The search results are plain links after the field, grouped Pages / Posts / Tags with each kind's mark and a page's path under its title, so Tab reaches them, and what a screen reader should hear about them goes through a `role="status"` line; the notice over the canvas is a polite live region too.

**"Not listed on any page"** is a checkbox above the groups (only for a viewer who reads a page). While it is on, the list shows the `unlisted` read's rows IN PLACE OF the groups, under "Posts · N" with the read's whole total, and the canvas is left as it is; the checkbox is the way back. **A row that is not in view**: a row whose post the canvas does not draw says "not in view" where its count would stand, is named as the designer wrote it ("Small sites, long lives, blog post, not in view. Activate to add it to the graph.", with the post TYPE's label as the messages' language lowers it; a post of a retired type says "talk, retired type"), and pressing it ADDS the post (`addPost`): the row is the post's node as the data has it, so nothing is fetched; it gets the line of the hub that brings it in (`via`: a faint line from a type or "All posts", a "Shares a tag" line to a tag; an unlisted row has no hub and floats), the worker is told (`add`), and the post is selected, centred and its card focused. A row whose post IS drawn is the drawn node, with its connections as on the canvas. **Without a graph there is nothing to add to**: the checkbox is there before the graph is, and its read does not wait for it, so its rows can come while the graph is still being read, after that read failed, or while "Show everything" is on its way. Such a row says only that it is not in view (`script.list.absent_post`, the design's sentence without "Activate to add it to the graph."; `aria-disabled`), a press on it does nothing, and `addPost` returns at once when the page holds no data. When the graph arrives the checkbox's rows are kept (`show` lets only a PILL's rows go, which were of the graph before) and are drawn again as rows that add. As first built a press there threw: the post was pushed among the nodes before `countAdded` or the summary read the data that was not there, and the row was dead or read as one in view. **With "Posts" switched off the press switches it back on first**: the row says "Activate to add it to the graph", and as first built the press added a node nobody saw (the legend's count of Posts went up by one). **A read of the list** is a plain `fetch`, ended when the screen is left and given up after the same fifteen seconds as the graph's own load (`AbortSignal.any` with `AbortSignal.timeout`, on both paths and with no fallback: Safari before 17.4 and Firefox before 124 have no `AbortSignal.any` and throw there, so the graph says it could not be loaded and the list that it couldn't be, with a Retry that cannot work); while one is out the rows' region is `aria-busy` (all the pending state there is: nobody gave words for one). An answer that comes after a later ask, or after the groups were asked back, is not drawn (`asked`). **A read that fails says so IN THE LIST**, not in a toast: "The list couldn't be loaded." and a small "Try again", in a `role="alert"`; the checkbox above stays ticked, and the error line stays through a toggle of the legend until the read is asked again or let go (as first built a toggle drew the groups under a ticked checkbox and the error line vanished without a word).

**The pills: one per target, a row per pill, three figures from one source.** In a page's local view each target that brings in more than the twenty drawn has its own "+N more" pill, hanging off its hub or tag. **A press on a pill opens the list** with the posts THAT pill stands for (`listed` for its page and its target), under the heading "More from Blog · 92" (the pill's own count, so it falls with the pill as its posts are added and never says another figure than "+N more" does) with "Open in Posts →" under the rows (only where there are rows: the address is there with none too, and it shows every post of the type or tag, more than the pill counted). **Each pill has a row in the list**, directly under the row of what it hangs off, indented one step, in the pill's own words ("+92 more") and named whole, beginning with those visible words so that voice control can press it by them ("+92 more: 92 more posts Blog lists, not in view. Activate to show them."); it is counted in no heading, and a pill whose hub has no row (its kind is switched off) stands at the end of the posts, or after the groups with no post drawn either, so a pill in view is never without a row. Activating it does what a press on the pill does and moves the focus to the first of its rows. **The way back is on screen and on the keyboard**: "Back to the list" beside the heading, before the rows in the document, and Escape pressed anywhere in the rows; both return the focus to the pill's row, and a failed pill read offers the same button beside "Try again". This is the largest correction of the build: the plan said "+N more has no row" on purpose, the pill could then be pressed only on the canvas, and the summary told a screen reader "92 more are in the list" of rows that a keyboard had no way to; and once the rows were open nothing on screen said how to get the four groups back. **After a row is added every figure is true**, from one source, what the page holds (`graph_data.js`, `countAdded`): the pill on the row's target stands for one post fewer (its words and its width are written again; at none the pill is not shown, its row goes, and if its rows were open the list returns to the groups), the canvas's summary adds up the pills in view as they now are, and for a row of "Not listed on any page" in the whole graph the notice no longer counts that post among those that aren't shown, when the row says its post has no connection (`unconnected`, which `PostGraph::Rows` works out by the rule `Global` ranks with: the page cannot, since at the posts' cap a post that is not drawn may be a connected one the cut left out). Such a connected post, added at the cap, raises the other figure of the notice instead: "Showing the 2,001 best-connected of 6,000 posts." And around a page, a post the person added from "Not listed on any page" (`added`, and `listed: false`) is in view and is not one the page lists, so the summary counts it beside the listed ones ("20 of 112 posts and 1 post. 92 more are in the list."): N and "more" still add up to M. **The notice is a live region, so a line that still says what it said is left as it is** (`say` finds it by its words and leaves its paragraph in the document, untouched: one taken out and put back would be announced as added): only the sentence whose figure moved is written, and so announced, when a post is added. As first built the pill still said "+2 more" and the summary "20 of 22 posts. 2 more are in the list." after one of them had been drawn. A spent pill (count zero) is nothing a person can meet: it is not drawn, takes no press and no hover, has no label, no row and no place in a count, and a pin on it is let go when its last post is added. One limit, on the roadmap: it is hidden, not removed, so it keeps its collision space in the layout.

**A site with too many lines for one picture opens around Home** (pages spec, decision 6). `PostGraph::Global` counts the lines it would answer BEFORE it builds any node (`Builder#plan` costs nothing), and above `PostGraph::OPEN_AROUND_HOME_ABOVE` (3,000) answers `{ open: "page-<home id>", edges: N }` and no graph, in six statements. The script then writes the figure on the element (`data-opened-lines`), reads Home's local view from `data-open-url` INTO THE SAME PAGE and shows a bar where a focused view has its own: "This site has 3,412 connections, so the graph opens around Home." and **"Show everything"**, a real `<button>` (its accessible name says how many lines pressing it draws, and it is described by the sentence), which reads `data-everything-url` into the same page. The canvas's name then says "Showing the area around Home." with the site's counts. **Nothing navigates and the address is never touched**: the page takes no `everything` parameter, so no address a person can keep asks for everything, and **neither a reload nor Back remembers the choice**: `reset()` takes `data-opened-lines`, the bar and the button's name back, so Back opens around Home again, as a reload does. (The plan navigated to `?page=<home>&lines=N`, made "Show everything" a link to `?everything=1` and then stripped the parameter from the address through Turbo's history; none of that is built.) Only the page's OWN address may be answered with `open`: a local view or "everything" that said it would be asked for ever, so the script throws. Over the threshold with no Home the viewer reads, the whole graph is answered: there is nowhere to open, and an address that would be a 404 is never handed out. The opened view has no depth switch; a page's card's "Focus" leads to the ordinary local view with both depths. **At the size the performance rule names this is the normal case**: the measurement's site of 204 pages and 2,005 posts holds 6,204 lines (3,162 related, 2,769 shared tags, 203 tree, 70 lists), the posts' own lines alone twice the threshold, so such a site always opens around Home (`test/system/admin/mind_graph_test.rb`: "a site with too many lines opens around Home and says why, Show everything draws the whole graph in the same page, and neither a reload nor Back remembers it").

**Turbo's page snapshot keeps script-written state, and `reset()` takes it back.** Turbo caches the page as it stood when it was left (`data-state="ready"`, `data-settled`, the counts, the canvas's `aria-label` with those counts in it, the notice's lines, an open selection card and where it stood, the search's text and results, the list's rows, the zoom's figure, the hovered node, the number of pinned nodes and the button that releases them, the legend's counts and the names made of them, the bar of the opened view) and Back restores exactly that, before anything has been fetched or laid out. Left alone, a test that waits for `[data-settled]` passes on the snapshot, and a person sees a card for a selection that no longer exists. So the controller's `reset()` runs first thing in `connect()` and takes all of it back, and the app writes it again as it becomes true: the state attributes (`data-opened-lines` among them), the opened view's bar with its sentence and the button's `aria-label`, the notice, the canvas's name (put back from its `data-label`, the name as the server wrote it: otherwise it would name the previous visit's counts until the data came, and for good if the load failed), the legend's counts and the inputs' `aria-label`, the search field and its status line, the list's rows, the zoom's figure, "Release N pinned", and the card, the tooltip and the results. **One thing is kept on purpose because it is the person's own state: the legend's checkboxes** (the graph shows what the control says: the state is read from the checkboxes when the data arrives). Pins are *not* kept: they belong to the page that made them, and the layout that comes back holds nothing. "Show everything" is not kept either. The status key is not the graph's and is not touched. Anything new the script writes into the page belongs in `reset()`.

**Testing it.** A canvas has no elements to find, so the app says what it shows on its element, and writes each only when it changes: `data-state` (`loading`, `ready`, `failed`, `worker-failed`), `data-settled` (present when what is shown is what was last asked for, at rest), `data-nodes` and `data-edges` (what the legend's toggles show; written by the toggle itself, so a toggle's effect is read at once, without `await_graph`: nothing is laid out), `data-zoom`, `data-labelled` (the labelled nodes' ids, the hovered one's among them), `data-selected`, `data-neighbours`, `data-hovered` and `data-pinned`. `data-settled` is written *before* the frame that writes `data-zoom` and `data-labelled` for the final fit, so the tests' `await_graph` waits for the attribute and then for that frame (`await_frames`); a test that needs one particular label waits for it with `await_js`. `element.mindGraph.screenPosition(id)` answers where a visible node is in client coordinates, and the test clicks there with a real mouse click; `element.mindGraph.labelBox(id)` answers the box of a node's label as the last frame drew it, for a click on a label; `.markBox(id)` the box of a mark that is one (a page's card, the pill); `.graphPosition(id)` where the layout has a node in GRAPH units, the camera not applied (the anchor's is 0, 0 while nobody holds it), which is how "a toggle moves nothing" compares positions; `element.mindGraph.draws()` is the number of frames drawn, for "nothing is drawn once the screen is left". What a mark *looks* like is held in two ways. **The recording context**: the module tests hand `marks.js` and `renderer.js` a context that only records its calls (`marks_drawn`, `lines_drawn`, with a theme whose values are their own names), so a shape, a size, a dash and a theme key are asserted exactly, and a STROKE is read by its outer edge (the path plus half the line's width), so an assertion states the size a person sees. And **the canvas's own pixels** (`pixel_at`, `ring_pixels` in `test/system/admin/mind_graph_test.rb`), for a few looks only: a canvas can pass every other test and still draw nothing. A pixel reading uses thresholds, not exact alphas, and samples where a mark could not be mistaken for another (Home is read as a card at four points: ink in its corner, where a dot as high has nothing, and nothing above and below its centre, where a dot as wide is filled; the first version sampled a point a dot of Home's radius fills too). The pages spec asked for all five looks from pixels on three marks; the recording context is the stronger check for sizes and dashes, and that is what was built. What the layout is *told* is recorded by wrapping `Worker.prototype.postMessage` (`record_worker_messages`), since no pixel shows that a plain click sent the worker nothing, and what it *answers* by wrapping the `Worker` constructor on a screen visited before (`record_worker_answers`), since no pixel shows that a layout arrived in one step; reduced motion is emulated through the DevTools protocol and taken back in an `ensure` (`with_reduced_motion`). **Every `await_graph` waits for a layout to ease to rest, five to six seconds**, since a small graph unfolds at frame pace: that is the screen as a person gets it, and the suite pays for it in time. **No test pins a measured layout figure, and no script call waits more than about two seconds.** A layout's own figures (where a node rests) are this machine's and this d3's; the tests that needed one were rewritten to compare layouts with each other (the tree's spring: the layout's own rests the branching page nearer Home than a weak spring and than a long one, by more than 10) or to assert what is exact by construction (an anchor at 0, 0 is set, not simulated; a dragged node is where it was put). And **the worker's parameters are lowered by a value**: the ease test hands the worker an ease of ten ticks (`keep: 0.5`) and sends the drag, the drop and the release right behind `start`, where its first version waited out three real settles and ran past the driver's limit for one script; it was that shorter test that found the anchor's jump. Reduced motion makes a layout arrive in one message, which three of the worker tests use. **A test presses a node only when the layout is at rest**: `drag_node` waits for `data-settled` first, because a node is held where it was grabbed, and one that is still easing has moved on between the test reading its place and the press reaching the browser — a few pixels on a slow runner, which is how "the node is where it was dropped" timed out in CI. And nothing may assume how much a machine lays out in one 12 ms slice: the client's rule for a stale `settled` is tested against a worker the test plays itself, the real worker only for what holds whichever way the race goes. Escape on the canvas goes through `escape_on_canvas` (the focus by script, the key real): Cuprite's `send_keys` clicks an unfocused element in its middle, where the card of a centred node stands. The card's links are inside the `#content` frame, so a test follows them with `click_frame_link`, like any other link there. The modules that are plain functions — camera, hit test, label rule, card placement, the renderer's culling and states (through a context that only records), the input's gestures, the worker and its client — are tested in `test/system/admin/mind_graph_modules_test.rb` by **importing them in the browser** from any CS Studio page: the project has no JavaScript test runner and gains none, the import map already resolves them there, and a camera's arithmetic can't be asserted through pixels. A test that stubs `window.fetch` or `AbortSignal.timeout` remembers the real one (`window.realFetch`, `window.realTimeout`) and the file's teardown puts it back; and a test of "a late answer is not drawn" waits for the page to have READ the answer (the held response's `json()` is wrapped), never for "released, then three frames", which on a slow machine passes before the late answer has come at all. A browser test of the opened view lowers the threshold with `with_singleton_override` on `PostGraph::Global`, which works because Capybara's Puma runs in the test's own process. The data sets for measuring are `script/dev/mind_graph_posts.rb` and `script/dev/mind_graph_pages.rb` (development only, deterministic, run against a throwaway database through `DATABASE_URL`); **the measurement is not a test**: no test asserts a time, and what the measurement found is held by counts (statements, calls of the criteria, the identity of a shared list).
