# CS Studio: shell, dashboard, audit log and small screens

> Describes: `app/controllers/admin/` (base, dashboard, audit events, system status, jump, mind graph), `app/components/admin/shell/`, `app/components/admin/dashboard_screen/`, `app/components/admin/audit_screen/`, `app/queries/dashboard/`, `app/queries/jump/`, `app/queries/post_graph.rb` and `app/queries/post_graph/`, `app/javascript/mind_graph/`, `app/javascript/controllers/admin/mind_graph_controller.js`, `app/views/admin/mind_graph/`, `app/models/audit/sentence.rb`, `app/components/public/preview_bar_component.rb`.

## Admin (CS Studio)

Our own admin, mounted at `ContentSpiel::ADMIN_PATH` (`config/initializers/admin_path.rb`, default `cs-studio`, configurable via `ADMIN_PATH`, one URL segment, can't be a reserved path), behind the same session-based auth as the rest of the app (no separate admin auth) plus the permission checks described in `docs/reference/access-control-and-audit.md`. Controllers live under `app/controllers/admin/` (`Admin::BaseController` and per-module controllers: `DashboardController`, `PagesController`, `PostsController`, `ContentBlocksController`, `TagsController`, `TagSuggestionsController`, `SettingsController`, `LanguagesController` (the Languages card's instant actions only; there is no Languages screen), `AiKeysController`, `UsersController`, `UserSuggestionsController`, `GroupsController`, `ApiTokensController`, `AuditEventsController`, `AccountsController`, `PasswordsController`, `SessionsController`, `SystemStatusController`, `TranslationsController`, `TranslationConfirmationsController`, `MindGraphController`, `LinkTargetsController`, `JumpController`, `MediaController`, `MediaAssetsController`, `StarterContentsController`, `TrashController`, `TreeController`, and the seven notes controllers, `NotesController`, `NoteThreadsController`, `NoteMessagesController`, `NoteMentionsController`, `NoteReactionsController`, `NoteFilesController` and `NoteInboxController`, described in `docs/reference/notes.md`). Every write goes through a service object (`app/services/`, e.g. `Pages::Save`, `ApiTokens::Issue`), never straight from a controller — see individual services' own comments for authorization and audit-event conventions. `Pages::Save` and `Posts::Save` take only the keys in their `ATTRIBUTES` lists in `attributes:`; any other (`parent_id`, `position`, the trash columns, a translated attribute) raises `ArgumentError`, because moving and trashing belong to `Pages::Move` and `Trash::Move`. `Admin::BaseController#require_permission(key)` gates whole admin areas (403 on refusal, rendered inside the CS Studio layout, never a bare error page); record-scoped controllers load through `AccessControl.scope` instead, so an out-of-scope id 404s; views use the `can?(key, record = nil)` helper (`app/helpers/access_control_helper.rb`) to hide buttons a signed-in user couldn't act on anyway. Content views use autosave (`admin--autosave` Stimulus controller, `Admin::AutosaveResponses#autosave_stream`) rather than a submit button, configuration screens an explicit Save; `docs/reference/save-rule-and-write-queue.md` says which is which and how a stale save is refused.

CS Studio's start page is the **dashboard** (`Admin::DashboardController#show`, dashboard spec `2026-09-30-dashboard-design.md`), not the pages list: `root to: "dashboard#show"` inside the admin scope, so `admin_root_path` means the dashboard. The Pages module is at `/<admin>/pages`, which is not a list but a redirect: `Admin::PagesController#index` sends a viewer who can open Home to Home's editor (303, the editing language kept, the flash kept) and otherwise shows the empty state "Choose a page from the tree" beside the tree; `Admin::BaseController#pages_landing_path` is the same decision for every redirect that used to mean "the pages list" (the trash's post-move redirect, starter content, a page's own delete). Sign-in and setup completion deliberately land on `admin_root_*`, the dashboard. It's open to every signed-in user (`BaseController::MODULES`'s `permission: nil` entry, listed first), including one whose groups hold no grants at all: every list it shows is already read-scoped through `AccessControl.scope`/`AccessControl.holds?` the way every other admin list is, so a user who can read nothing simply sees empty cards rather than a 403. The page is a quick-create row (`Admin::DashboardScreen::QuickCreateComponent`: a title, a type select and "Create draft" — a post draft through `Posts::Save`; choosing "Page" opens the New page dialog with the title carried over instead of creating anything), three cards in an auto-fit grid — "Your drafts" and "Going live next" from `Dashboard::Feed` (`app/queries/dashboard/feed.rb`, at most five rows each, "→" to the posts list filtered by `scope=drafts|scheduled`), and "Needs translation" from `Dashboard::TranslationNeeds` (per target language the viewer's readable pages, posts and — for a `media.upload` holder — images from `Translations::StateIndex.summary`, plus the most recently changed outdated item; hidden with one language) — and then **Recent activity** (`Dashboard::Activity`), with a link to the full audit log for `audit.view`. "Mine" in the drafts card means `author_id` for a post or, for any record including a page, that its *newest* audit event's user is me — "newest" ignoring `access.denied` (a refused attempt is no change, `Dashboard::Feed::NOT_A_CHANGE`) and, for a page or post, also counting events about any content block it currently owns, since editing a block is editing its owner. It is decided in SQL by one `LATERAL` join to each record's newest audit event rather than a Ruby-side filter-after-load, so each list stays one query per model whatever the data size.

**Recent activity** is the newest *content* audit events (pages, posts, blocks, library images; never `access.denied`, `session.*`, `user.*`, `group.*`, `token.*` or `settings.*`; the allow-list is `Dashboard::Activity::ACTIONS`), one sentence each — "<name> published “<title>”" with the title linking to the record's editor (`Admin::DashboardScreen::ActivityRowComponent`) — looking back `Dashboard::Activity::WINDOW` (90 days). The read scope is applied *in the event query itself* (`audit_events.subject_id IN (readable ids)` per subject type, a block event through its readable owner, images for a `media.upload` holder), never by over-fetching and filtering in Ruby, which under-filled the feed and leaked how much hidden activity there was; a record the viewer can't read, a trashed one or a deleted one leaves no row at all ("not found, not forbidden"), a trashed record's whole history disappearing with it until it is restored. `index_audit_events_on_recent` serves the `ORDER BY last_occurred_at DESC` scan. The query returns data only: a `Dashboard::Activity::Row` is `(event, record, sentence, at, span_end)`, the sentence an `Audit::Sentence` (see the audit log below) whose actor is facts, not a name — the viewer ("You"), a user, a `user_id` that names nobody any more, or nobody — and `ActivityRowComponent` hands it to `Admin::AuditScreen::SentenceComponent`, which is where a user is named, through `Admin::Ui::UserNameComponent` (the one place CS Studio names a user): the `display_name`, "a deleted user" when `user_id` names a user who no longer exists (`audit_events` has no FK on it; a token event whose user is gone reads the same), "System" only for an event with no user at all. A change made through an API token shows its *user* (round avatar) "via <token name>" beside an MCP chip (`Admin::Ui::ChannelChipComponent`, which draws an unknown channel as a plain chip and nothing for none), the name being the `audit_events.actor_label` written when the event was recorded (`Audit::Event#via_label`; it survives the token being deleted, and an event recorded before tokens had names reads "via an API token"), the token itself never loaded. A coalesced burst shows the time it last extended, the whole span as its tooltip.

**The audit log** (`Admin::AuditEventsController`, `audit.view`, never content-scoped) tells every event as one sentence through `Audit::Sentence` (`app/models/audit/sentence.rb`: plain data -- actor facts, parts, a route name + params for the subject, a `security` flag -- never markup or a component; `Admin::AuditScreen::SentenceComponent` draws it), the dashboard's feed words its rows through the same class so the two can't differ. A sentence for an action outside `Audit::Sentence::ACTIONS` (a plugin's) is the generic "<actor> did <action> on <subject>"; the actions in `Audit::Sentence::SECURITY_ACTIONS` (a failed sign-in, a refusal, an owner change, a token issued or revoked, a user or group deleted) carry the `security` flag, and the row draws their key in warn ink. `test/models/audit/sentence_test.rb` greps `app/` for every recorded action name and fails for one without a sentence (interpolated and variable call sites are listed explicitly there). A subject links only when the viewer may open it, decided for the whole page of events in a bounded number of queries (`Audit::Sentence::Targets`); an unreadable, trashed or deleted one is the label the event stored, as plain text, and a failed sign-in never echoes the attempted address. A refusal says what it was refused on when the event names a subject ("was refused permission to edit posts on" and the subject), and a schedule taken off a page or post reads "removed the schedule from". The list is `last_occurred_at DESC, id DESC` under day headers in the site time zone (`Admin::AuditScreen::DayListComponent`), filtered by `Audit::Filter` (user, action, type, channel, a `range` preset or custom `from`/`to`, a `subject_type`+`subject_id` chip; junk is "all"), "Load older" over `offset` (it replaces the page; "Newer" goes back). A coalesced row shows its span ("16:05–16:31", `Admin::AuditScreen::TimeSpan`), and `audit_events.occurrences` (1, incremented by `Audit::Coalescer` each time an event merges into the row) is the "N saves" on the event page ("N times" for anything but a `*.updated` event: twelve refusals are not twelve saves). The event page (`EventHeaderComponent`, `ChangesComponent`) shows field changes as word diffs per language (`Translations::SourceDiff` drawn by `Admin::Ui::WordDiffComponent`, shared with the translation reference card), "Changed" for a body, and Older/Newer through the same filtered order, every link on the page keeping the filters. The event is found by id whatever the filter says: one that exists but lies outside the active filter (a link carrying `range=today`, opened the next day) is answered 303 to its own filter-free address, the language kept, where Older and Newer walk the whole log; only an id that names nothing is a 404. Components live under `Admin::AuditScreen::`, never `Admin::Audit` (see "Key Conventions").

Every CS Studio and MCP request also runs inside the **site time zone** (`site_settings.time_zone`, default `"UTC"`, stored as a Rails zone name — an IANA identifier like `"Europe/Berlin"` is normalised to its Rails name on save, because the Settings select's option values are Rails names and every Save resends the whole form; the select also always lists the stored value, so a value written around the model is resent unchanged rather than replaced by the first option): `SiteSetting#effective_time_zone` resolves the stored name to an `ActiveSupport::TimeZone`, falling back to UTC for a value that doesn't resolve (a blank or no-longer-valid stored zone) rather than letting `Time.use_zone` raise and 500 every request; `Admin::BaseController` and `McpController` each wrap their actions in `around_action :use_site_time_zone { Time.use_zone(Current.site.effective_time_zone) { ... } }`. That's what lets the existing `Time.zone.parse`/`strftime` call sites (schedule inputs, "Saved HH:MM", the dashboard, the trash and audit screens) show and parse local time without change — storage stays UTC throughout, and MCP's own dates are still emitted as ISO-8601, now with the site's offset rather than always `Z`. The public site (and `/preview`) still renders dates in UTC — tracked in the roadmap, since it needs the render cache to vary on the zone.

**Notes on the dashboard and in the sidebar** (`docs/reference/notes.md`, "The inbox"). The dashboard has two cards about notes, each a frame of its own that can be fetched again by itself: **Notes for you** (`turbo-frame#notes-for-you`, `Dashboard::NotesForYou`: the viewer's deliveries on records they may read now, unread first, five rows, "N NEW" in accent, "Mark all read" and a link to the full list at `<admin>/notes`) and **Open threads** (`turbo-frame#notes-open-threads`, `Dashboard::OpenThreads`: one row per readable record that has open threads, with its count in the neutral pill, most recently active first). The sidebar's Dashboard entry carries the viewer's unread count (`#sidebar-badge-dashboard`, `Admin::BaseController#notes_badge_count`): the one filled badge of the sidebar, accent because accent in a marker means "unread and addressed to you" and nothing else; Trash's stays a plain mono number. It costs exactly one statement per page load. `admin--notes-live` on `<body>` fetches the badge and, on the dashboard, both cards again when the person's stream says something was addressed to them. Recent activity lists a note's start and its resolve only (`Dashboard::Activity::ACTIONS`), and "Mine" and "Changed by" never count a note as a change to the record (`Dashboard::Feed::NOT_A_CHANGE`).

## Shell

**Shell.** `Admin::BaseController::MODULES` entries carry `group:` (`:content`, `:people`, `:system`), which `Admin::Shell::SidebarComponent` renders as the sidebar sections (Dashboard stays first); the sidebar also holds the ⌘K field, the account block and the theme switch. The account block is `Admin::Shell::AccountIdentityComponent` (`#account-identity`: `display_name`, then "email · role" on one line, the role being "Owner", up to two group names then "+N", or "No groups" — its own component because the account screen's Save replaces just it by stream, and a link to that screen), then Your account and Sign out. Sign out is a plain form with `data-turbo="false"`: a full document load, so nothing a tab's scripts hold for one user (the media upload queue's tiles) survives into the next sign-in, and with unsaved changes it is the browser's own prompt that asks. `Admin::Shell::TopBarComponent` appears below 1280px, where the sidebar becomes a drawer (the page-tree column becomes one below 1024px); the bar is 3rem tall, so everything sticky inside the content area (the editor header, Settings' nav, the Media panel) sits at `--admin-top-offset`, which is 0 and 3rem below 1280px; `admin--drawer` owns open state, scrim and Escape, and the CSS keys on `data-open` (`.admin-shell` in `content-spiel.tailwind.css`). In the page tree, a context-only row (an ancestor shown only as the path to a readable page) is greyed text with no actions, a row has a hover "+" only where `pages.create` holds under it and a drag handle only where `pages.move` does, the homepage has no handle, and a row shows "↻N" (outdated) and "○N" (missing) summed over the target languages, hidden at zero, from `Translations::StateIndex.counts_for` read once by `Admin::PagesScreen::TreeComponent` (never red; the tooltip names the languages). The Trash entry carries `trash_badge_count` (`Admin::TrashController.visible/roots/counts/badge_count`: the page branch roots, posts and images the viewer may act on, the sum of the Trash screen's own tab counts). A 403 and a 404 render inside the layout (`admin/errors/forbidden`, `admin/errors/not_found`; `rescue_from ActiveRecord::RecordNotFound`); the 404's link is "Back to the dashboard" unless the screen names a nearer way on (`@not_found_back`: Media's "Back to Media", the search and segment kept); a non-HTML request (a Turbo Stream, a `fetch`) gets a bare `text/plain` 404 so the caller doesn't mistake it for a stream.

## Jump to…

**⌘K "Jump to…".** `Admin::JumpController` answers `GET /<admin>/jump?q=` with `Jump::Search` (`app/queries/jump/search.rb`): pages, posts and library images (read-scoped through `AccessControl.scope`, trash hidden), then CS Studio's modules as **Sections**, destinations inside the Settings screen as their own **Settings** group ("Settings › Site", "Publishing", "Languages", "AI translation", each behind the right that owns its card: `languages.manage` for Languages, `settings.manage` for the others), and **Actions** (New page and New post open their dialogs; the rest are links); five rows per group. Pages and posts match **titles only** — in every language, via `jsonb_each_text` on the translated jsonb columns (`TitleSearch`, `SqlNodes.any_json_value`) — never bodies (full-text search is a separate roadmap row); images go through `Media::Search` like the library does. A page or post row shows a non-Live status chip at its right end (`Admin::Ui::StatusChipComponent`, Live draws none). `Admin::Shell::CommandPaletteComponent` is the dialog (an ESC chip beside the field and a hint row, "↑↓ MOVE · ↵ OPEN · ⌘↵ NEW TAB"), `admin--command-palette` the controller (⌘K / Ctrl+K, arrows, Enter; ⌘/Ctrl+Enter opens the row in a new tab). An Enter pressed while the results for the typed text are still on their way, or before any row is selected, is remembered and opens the first row when they arrive (⌘/Ctrl+Enter the same, in a new tab); the arrows do nothing meanwhile. A row that leads to a section of the screen already showing ("Settings › AI translation" used on Settings) is a same-page fragment link: it jumps there without a visit, so an unsaved form is not asked about leaving. The shortcut does nothing while another modal dialog is open: the editor closes what is open first.

## System status

**System status** (`Admin::SystemStatusController`, `system_status.view`): "N of M checks passed · last run HH:MM", warnings first, each check an `Admin::Ui::SystemCheckRowComponent` (the setup wizard draws the same rows with `copyable: false`). A check may carry a console `command`, shown in a code box with Copy (`admin--ui--clipboard`). The outgoing-mail warning's command resets a password through `Users::UpdatePassword` — never `update!` on the model — so it is audited and ends that user's sessions (`Setup::SystemCheck::MAIL_FALLBACK_COMMAND`, a static string). "Run checks again" is a GET with prefetch off, because the storage check writes and deletes a probe.

## The preview bar

**The preview bar** (`Public::PreviewBarComponent`, rendered first in the public layout on `/preview…` only): a fixed 36px bar, "PREVIEW · <title> · <Draft | Scheduled | Live> · <language>", Edit and Exit preview. It is the public site's chrome: the public stylesheet only, no admin JavaScript, and its colours are the theme tokens `--th-preview-bg` / `--th-preview-ink`, which do not switch with light and dark. Edit opens the record's editor in the previewed language. Exit preview goes to the record's public URL in that language when it is live, and otherwise to CS Studio's list (the pages landing for a page, the posts list for a post) — there is no public page to leave for.

## Mind graph

**Mind graph** (`Admin::MindGraphController`, the `PostGraph` queries in `app/queries/post_graph/`, `admin--mind-graph` over the modules in `app/javascript/mind_graph/`; spec `docs/superpowers/specs/2026-10-07-mind-graph-canvas-design.md`, whose §7 holds the measured numbers and §11 the decisions made while building, the last part of it the round that followed the owner's first trial on 2026-10-08: motion, pinning, the card beside its node, the label as part of the target, the list beside the canvas). How posts relate through related-post links and shared tags, drawn on one 2D canvas and laid out by d3-force in a Web Worker. Read-only: relations are edited in the post editor. It needs `posts.read` somewhere, and everything it shows is derived from the posts the viewer may read.

**Two modes, one screen.** `GET /<admin>/mind_graph` is the **global** view: the best-connected readable posts, up to a cap. `?post=<id>` or `?tag=<id>`, with `&depth=1|2`, is a **local** view: that post's or tag's neighbourhood. A depth other than 2 is read as 1, and `post` wins when both are given. Changing the focus or the depth is an ordinary visit, so Back works. Two JSON reads belong to the screen and share its permission and scope (`config/routes.rb`, both `format: :json` by default): `mind_graph/data` with the same parameters answers the graph, and `mind_graph/search?q=` the search field's rows. **A focus outside the viewer's scope is not found, never forbidden**: `PostGraph::Focus.find` raises `ActiveRecord::RecordNotFound` for an unknown id, a trashed post, a post outside the read scope and a tag that no readable post carries (a focus on it would say the tag exists and is used somewhere the viewer can't look), and `Admin::BaseController` answers the 404 page, or a bare 404 for the JSON read. The page and `data` resolve the focus the same way, so they can't disagree. **An id is read as a decimal number and nothing else** (`Integer(value.to_s, 10, exception: false)`): without the base Ruby reads a prefix, so `?post=010` would be post 8 and `?post=0x1A` post 26, each a post other than the one the URL names. Whatever is not a number names nothing and is a 404 — a word, and a list such as `post[]=1` — while `q[]=x` on the search finds nothing and `depth=abc` is depth 1 (`test/integration/admin/mind_graph_data_test.rb`).

**The data.** `PostGraph::Global` and `PostGraph::Local` answer the same shape, built by `PostGraph::Builder`: `{ nodes: [{ id, title, type, colour_index, status, url, degree, related_count, tag_count, open_notes }], tags: [{ id: "tag-<id>", name, count, degree }], edges: [{ source, target, kind: "related" | "tag" }], total, shown }`, plus `isolated` (global) or `focus: { kind, id, node_id, title, depth }` (local). `degree` is the number of edges the node has *in this response*, so a node's size and its label's priority match what is drawn, not what the site holds; a post's `related_count` and `tag_count` are the two halves of it (its related-post edges, and its edges to tags that are nodes here), counted where the edges are made so the card can say "3 related · 2 tags" without the page walking the edges. Like `degree` they count what is drawn: a tag only one drawn post carries is no node and is not counted. `total` is the posts the view could show (global: the readable posts with at least one connection; local: the posts the walk reached), `shown` the posts in `nodes`, and `isolated` the readable posts with no connection, which the global view leaves out and counts in a sentence ("72 other posts have no connections yet and aren't shown." — "other" and "aren't shown" because the bare count read as a contradiction beside a canvas of connected posts; with nothing drawn at all it is `script.isolated_only`, "2 posts have no connections yet."). There is no colour in the data: a node carries its content type's `colour_index` (nil for a type that is no longer registered) and `Publishable#status`, and the page draws both from tokens. `url` is the post's editor URL, built by the `url_for:` callable the controller passes (the route helper, with the editing language kept): a query knows no routes (`test/lib/dependency_direction_test.rb`), and `actor:` and `url_for:` have no default so nothing draws the whole graph, or a graph without links, by forgetting one. Posts are loaded with four columns only (`Builder::COLUMNS`: id, title, content type, `published_at`), never the bodies.

**The cap** is `PostGraph::CAP`, 2,000 posts, confirmed by the measurement in the spec's §7 (at the cap: about a tenth of a second for the data, half a megabyte uncompressed, two and a half seconds to settle, and no late frame while panning — in headless Chrome on a development machine, so indicative). It is not a setting, and raising it means measuring again. The two queries cut differently. **Global** ranks every readable post by its connections — related-post links in either direction, plus one for each of its tags that at least two readable posts carry — *among all readable posts, before the cut*, keeps the top 2,000 with a count above zero, and breaks ties by newest `updated_at`, then id, so two requests cut the same; tags and edges are then derived from the kept posts only. **Local** walks outward from the focus one level per depth, following both kinds of edge and stepping only onto readable posts (so an unreadable or trashed post is neither a node nor a bridge to what lies behind it); over the cap it keeps the focus, then nearer posts before farther ones, and among equals those with more connections *inside the neighbourhood*. A tag on thousands of posts is why a local view needs the cap at all. Over the cap the screen says what it kept, in a sentence per view because the two cut differently: the global one "Showing the 2,000 best-connected of 5,791 posts." (`script.capped`), a local one "Showing the 2,000 nearest of 2,695 posts around this one." (`script.capped_local`, chosen when the response has a `focus`); the search field is how a post the view doesn't draw is reached. Every figure in those sentences and in the isolated one is grouped for the messages' language (`Intl.NumberFormat` on their `@locale`): the isolated count goes into its sentence as `%{figure}`, and `count` only chooses the plural form. One consequence of ranking before the cut: a kept post whose only link is a tag whose other posts were cut is drawn with no edge and a `degree` of 0. The cost does not grow with the number of posts: six statements for the global view, three per depth level plus six for a local one, never one per node — one of the six is the nodes' `open_notes`, the post's open threads, which `PostGraph::Builder` reads for the ids it was handed in one grouped statement (`Notes::Counts.by_container`); the graph's data says nothing about what the viewer has read (`test/queries/post_graph/`, with `capture_sql`).

**The tag rule.** A tag is derived only from readable posts, and its `count` is the number of *readable* posts carrying it: never the tag's true total, which would disclose posts the viewer can't see, and not the smaller number drawn under a cap, which would understate it. A tag is a node only when at least two readable posts carry it (`PostGraph::MIN_TAGGED_POSTS`) *and* it has enough edges in this response to say something: two in the global view, where a tag with one drawn post connects nothing, and one in a local view, where a post's own tags are its neighbours. The focused tag of a local view is always a node. No edge points at a post that isn't in `nodes`. Trashed posts are left out by `AccessControl.scope`, as everywhere, and both JSON reads are in `test/integration/trash_visibility_test.rb`.

**Search.** `PostGraph::Search` answers up to ten readable posts whose title matches in any language (`title_matching_any_locale`) and up to ten tags by name (`Tag.name_containing`, those that start with the text first), a tag only when a readable post carries it — the rule `Focus` applies, so a result never leads to a 404. The controller adds each row's local-view URL. A post is loaded with its id and title only (`select(:id, :title)`, as `PostGraph::Builder` selects its four columns), which `test/queries/post_graph/search_test.rb` reads from the statement.

**The page holds no data.** `show.html.erb` is a frame: the heading, the search field, the focus bar of a local view, the legend, the filter, an empty canvas with the zoom control and the hidden "Release N pinned", the notice, the card's and the tooltip's containers, and the list's empty region. The script fetches `data-url`. The reason is size: at the cap the JSON is half a megabyte, and inline it would sit in every load of the page and in Turbo's page cache. What the page does ask the database is small and independent of the site's size: the focus, and the distinct content types of the viewer's readable posts, for the legend and for "No posts yet." (said for *this* viewer: one who can read no post sees it whatever the site holds). `Admin::MindGraphScreen::LegendComponent` names only the types present among those posts — a legend of every registered type would disclose types the viewer can't read — then Tag, "Draft or scheduled", "Retired type" when one is present, the two edge kinds, "Pinned" and "Open notes". The element also carries four URL templates (the fourth, `data-post-notes-url`, is a post's open notes as JSON for its card, built for id 0 with that segment swapped, because the route takes digits only) built by the route helpers, with `__ID__` and `__NAME__` where the script puts a node's id or a tag's name, so no path is written in JavaScript; `data-button-classes` and `data-dot-classes`, which are `Admin::Ui::ButtonComponent`'s and `Admin::Ui::ContentTypeDotComponent`'s own class strings (the card's actions and a type's dot in the card and the list are built in the script, and are handed the shared classes instead of holding copies); and the script's strings as `data-messages` (every key written out in the view, because `test/lib/script_messages_test.rb` reads the literals). **The scripts' class names are built only because the Tailwind build is told to read them**: `app/assets/tailwind/application.css` is `source(none)` plus explicit `@source` lines, and `@source "../../javascript/mind_graph"` is one of them. Without it nothing failed and `w-fit`, used nowhere else, was simply not in the stylesheet — each notice line was as wide as the longest one and each link of the card as wide as the card, so a click beside the text navigated. A new directory of scripts that writes class names needs its own line, and `test/lib/tailwind_sources_test.rb` fails until it has one.

**The layout of the screen.** The screen fills the window: from 1,100 pixels of width the heading and the box together are `100vh` less `<main>`'s padding and the top bar where there is one (`--admin-top-offset`), so the page does not scroll, and the box is a grid of the graph's column (a local view's focus bar, the legend and filter row, the canvas) and a 300-pixel panel on its right — the search field on top, the list below it, scrolling on its own. Below that width the three stack, the graph first, and the page scrolls. **The order of the document is not the order on screen, on purpose**: in the document the search comes first and the list last (the Tab key follows the document, and the list can hold two thousand rows), and the grid places each part by column and row. Move a part in the markup and the Tab order moves with it (`test/integration/admin/mind_graph_test.rb`, and "the Tab key meets the search first and the list last" in the system test).

**The worker, and why d3-force is imported by URL.** The layout runs in a module worker (`mind_graph/layout_worker.js`), so zoom, pan and clicks stay smooth while a graph of two thousand nodes is still settling; the page only draws. The worker is started from its own digest asset URL (`data-worker-url`) and is handed the vendored d3-force file's asset URL (`data-d3-url`) with its first message, which it imports dynamically: **an import map does not apply inside a worker**, so `import "d3-force"` can't resolve there, and the file is one self-contained bundle, so the URL is all it needs. Nothing else loads d3-force. Its pin in `config/importmap.rb` is `preload: false` and stays only so `bin/importmap audit` and `outdated` still see the package; `pin_all_from "app/javascript/mind_graph"` is `preload: false` too, and the thin controller reaches `mind_graph/app` through a dynamic `import()`, so no other CS Studio screen fetches any of it. (Before this, d3-force was `preload: "admin"` and every CS Studio page evaluated it.) `test/integration/public_javascript_test.rb` keeps both off the public pages and out of the other screens' preloads. There is no second code path that lays the graph out in the page: if the worker can't start, the box says "The graph can't be drawn in this browser.", with no Retry (a browser that can't run it once can't run it twice), nothing is drawn, and the list beside the canvas still gives every node — and still follows the filter, which is applied to the list and the counts whenever there is data and handed to the layout only when there is one. A row then opens the node's card in the canvas's top-right corner, without Pin (there is no layout to hold anything in), and the card's links lead on.

**The worker's messages** (documented at the top of `layout_worker.js`). In: `start` (the d3 URL, nodes as `{ id, radius }`, edges, and `reducedMotion`), `filter` (the visible node ids and edge indexes), `drag` (a node held under the pointer), `drop` (the pointer let go; the node stays), `pin` (hold a node where it is) and `unpin` (let these ids go). Out: `tick` with one `Float32Array` of x/y pairs covering every node given to `start`, transferred and not copied; `settled`; `error`. Three rules here each answer a bug. **Messages are handled strictly in order**, each after the one before it has finished: `start` awaits the import of d3-force, and a `filter` or `pin` sent right behind it used to run before the simulation existed — the filter threw, the drag was dropped. **`settled` carries `after`**, the number of messages the worker had taken up when the layout cooled down, and `layout_client.js` passes it on only when that equals the number it has sent: a small graph cools down inside the first slice, before a `filter` sent right behind `start` (Back to a screen whose control says "Related") is handled, and the page used to fit the view and call itself settled on the layout before the filter. And **a `drag` wakes a cooled-down graph**: `alphaTarget` only pulls `alpha` up by ticking, and the loop does not tick below `alphaMin`. A message that moves nothing (a `pin`, a `drag` of a node that isn't there) is still answered with a `settled` when the layout is at rest, because the page waits for one that counts it.

**The pacing** is the worker's, and is what makes the screen feel alive or dead. The simulation's own timer is stopped and the worker steps it by hand at one of three paces. *Frame pace*: one tick, one `tick` message, then 16 ms — a small graph's first layout (up to `SMALL_GRAPH`, 300 nodes; about five seconds), a drag, and the settle after a drop, a filter change or an unpin, so the neighbours visibly follow a held node and the graph eases to rest. *Fast*: as many ticks as fit in 12 ms, one message, and a zero timeout so a message that arrived meanwhile is handled before the next slice — a larger graph's first layout, until about 600 ms of ticks are left (`FINAL_STRETCH_MS`), which are then shown at frame pace. *Silent*, with reduced motion: no message until the layout is at rest, then one; a dragged node moves alone (`drag` posts the positions last shown with that one node moved, and ticks nothing) and `drop` shows the result in one step. Before this the worker always ran fast, so a small graph was at rest in its first message and nothing was ever seen to move — "it was more alive before" was the owner's first remark. Every run ends: `alpha` decays below `alphaMin`; only a held node keeps the layout warm, and `drop` takes that back. **The page tells the worker about reduced motion with `start`** (a worker has no reliable `matchMedia`), once per load. At the cap frame pace holds (a tick every 18 ms), and a filter change is at rest after about five seconds where it used to take two and a half; the system tests wait that out, about five seconds per layout. An error in the worker is posted to the page and reported with `console.error`, on purpose: the system tests fail on any console error, so a worker that breaks is never a graph that silently stays empty.

**The modules and what each owns.** `controllers/admin/mind_graph_controller.js` is deliberately thin, because every `controllers/admin/*` file is loaded on every CS Studio page: it imports `mind_graph/app`, mounts it, destroys it on `disconnect()` and resets the snapshot's state (below). A `connect()` may be followed by `disconnect()` before the import has arrived, so a token (`this.live`) says whether the connection is still current and a late import mounts nothing. A failed `import()` is left unhandled so it is loud. In `app/javascript/mind_graph/`, each file's header is its contract:
- `app.js` — wires the rest: the data request (aborted on leaving, timed out after 15 seconds into the same message as a failure, with Retry), the worker, the state, one redraw per animation frame and only when something asked for one, the filter, the notice, the tooltip, and the state said on the element. `destroy()` stops all of it — the request, the worker, the frame, the observers — so nothing runs or draws after the screen is left.
- `layout_worker.js`, `layout_client.js` — the layout and the page's side of it; one worker per graph, terminated by `stop()`.
- `camera.js` — `{ k, tx, ty }` and pure functions: zoom at a point, pan, bounds, fit. Zoom is limited to 0.05–4, and a fit never zooms in past 1.5.
- `hit_test.js` — the node under a point: its mark or its label, which are one target. A linear scan over the visible nodes (0.2 ms at the cap), radius in screen pixels with four pixels of slack and never less than 24 pixels across; the nearer centre wins. Then the boxes of the labels *the last frame drew* (a label that is not drawn can't be pressed), the last drawn first, because that one is on top.
- `labels.js` — which labels are shown (below).
- `renderer.js` — draws one frame: edges, nodes (each with its pin mark), labels, rings; and the states: hovered, selected, pinned.
- `theme.js` — the colours, read from the `--cs-*` custom properties and read again when `<html data-theme>` or the system scheme changes. The script holds no colour value (`test/lib/admin_design_rules_test.rb`).
- `input.js` — the canvas's pointer, wheel and key events as callbacks, a double click among them. It knows nothing of the graph. A pointer ends on `pointerup` or `pointercancel`, and a touch or a pen on `lostpointercapture` too: a touch can lose both of the first two, and its entry left in the table would turn every later touch into a pinch with a ghost. A mouse is left out of that, because its `pointerup` always comes and a capture dropped between the press and the first move would otherwise end a drag that is still held. After a pinch, a new finger arriving while one remains restarts the pinch.
- `card.js`, `node_list.js`, `search_box.js` — the selection card's content, the list beside the canvas, the search field's results. All three write text with `textContent` and URLs with `href`, never markup: a title is the editor's text, whatever it contains.
- `card_placement.js` — where the card stands: pure numbers, so it is tested without a canvas.

**The camera.** The first view fits everything: the camera follows the layout from its first positions until it has settled, and that fit is final. From then on — or from the user's first zoom, pan or drag of a node, if that comes sooner — it moves only on the user's input or "Fit all"; a filter, a resize and a later reheat of the layout leave it where it is. Nodes are not clamped to the box; the box is a window. The wheel and a trackpad's pinch (a wheel event with `ctrlKey`) zoom towards the pointer, a two-finger touch pinch zooms around the point between the fingers (tested with synthetic pointer events only), a drag on empty space pans, a drag on a node moves that node and pins it (below). The wheel always zooms: no modifier key and no hint, since the page itself does not scroll. With the canvas focused, the arrow keys pan and `+` / `-` zoom. A press released within five pixels of where it began is a click, whatever it was on. A row of the list centres the camera on its node, at the zoom it has. The zoom control — −, the zoom as a percentage, +, "Fit", each named in full by its `aria-label` and tooltip — comes before the canvas in the document, because Tab follows the document, and is positioned over its bottom-right corner, with "Release N pinned" beside it while a node is pinned.

**The node shapes** carry two cues that never share a shape, exactly as `Admin::Ui::ContentTypeDotComponent` and the legend draw them. A post is a circle, a tag a square. The **type** is the fill: colour slots 1–6 are filled with the hue, 7–12 are a ring of the same six hues. The **status** is the outline: a live post's is solid, a draft's or scheduled post's dashed, with a small filled core for slots 1–6 so the hue is still there. **A post whose type is no longer registered** has no `colour_index` and is a ring in the `meta` grey *with a diagonal stroke through it* — before, it was the same shape as a 7–12 ring and differed by colour alone. **Size** follows `degree` in four steps (7, 10, 13 and 16 pixels radius, up to 2, 5 and 12 connections and beyond; a tag's half side is 4.5, 6, 8.25 and 10.5 — `STEPS` in `renderer.js`; a post's were a step smaller until the owner compared the screen with the design review's mock), because small differences in size can't be read, and a node is the same size on screen at every zoom. A related edge is solid, a shared tag's dashed. The focus of a local view has a dotted ring in the accent colour.

**The states** combine, and none is colour alone. *Hovered* — by the pointer or by its row in the list — is a 1px ink ring and the label in full ink on a backing, shown even where the label rule hides it; hovering dims nothing. *Selected* is a 2px accent ring with a gap, a semibold label, its own edges brightened, and every node and edge not connected to it at 28%. *Pinned* is a small ink dot with a surface ring at the mark's top-right, drawn with the node at the node's strength; the legend's "Pinned" swatch is the same mark (`.mg-key-pin`). *With open notes* is the count in a small mono pill at the mark's top-left, opposite the pin (never a ring: a ring is hovered, selected or the focus), always neutral (unread is said on the card's rows); its right edge is fixed 4 px over the corner and it grows to the left, so it never reaches the pin's dot; above ninety-nine it reads "99+" (`.mg-key-notes` in the legend). A tag's rings are squares.

**What is not drawn.** A node whose mark lies wholly outside the canvas is skipped, and so is an edge that can't cross it: both ends beyond the same side. Not "both ends outside" — an edge from far left to far right crosses the whole view. This came out of the measurement: zoomed in, most of the graph is outside, and a path of long dashed lines costs the rasteriser by its length whether it is seen or not, which made about one frame in fifty late at the cap. And nothing is drawn before the worker's first positions arrive (`state.placed`): until then every node is at 0, 0, and the first frame after the data came used to draw the whole graph as a pile in the canvas's top-left corner — for one frame normally, and for good when the worker failed.

**The label rule** (`labels.js`). (1) Hubs first, among the nodes *on the canvas*: the zoom decides how many labels there are — 40 at zoom 1, growing with the square of the zoom — and they go to the best-connected nodes inside the view, so zoomed into a corner the budget is not spent on hubs nobody can see. The cost is that a label can appear or disappear while panning. The last quarter of that reach is drawn fainter, so a label arrives gradually with zoom; with `prefers-reduced-motion` it switches. (2) No overlap: a label is placed only where no earlier one is, and better-connected nodes place first. (3) The selected node, then the focus, then the selection's neighbours are labelled at any zoom and place before everything else — but rule 2 holds among them too: **no overlap wins over "always labelled"**, and a neighbour gives way to the selection however well connected it is. A label sits right of its node, is cut at 32 code points with an ellipsis (so an emoji is never cut in half), and a tag's keeps its count whole: "name (N)".

**Selecting, and the card.** A click on a node — its mark or its drawn label — selects it: it and its direct neighbours *by the edges shown* stay at full strength, the rest dims, and the card opens **beside the node** (`card_placement.js`): 22 pixels from the node's edge and vertically centred on it, on the node's left where the canvas's right edge is too near, and clamped 8 pixels inside the canvas. Its place is worked out in the frame that draws the node, from the card's size as measured once when it was filled, so it follows a pan, a zoom and the layout's own movement without lagging, and its style is written only when it moves. It hides while its own node is dragged and returns on the drop. It was in the canvas's top-right corner before, and the owner's remark was that it was far from what it is about; the corner is still where it goes for a node without a place (the worker failed and the selection came from the list). A post's card has its type's dot and name, its status chip (`Admin::Ui::StatusChipComponent`'s classes: a dot and the word), the title, "N related · N tags" in the small label style, and its actions as CS Studio's buttons: "Open post" (primary), "Focus", "Pin" / "Unpin"; and its open notes (`card_notes.js`: "Open notes · N", at most three rows, "+N more" into the post's editor with `?notes=open`, and a field that starts a note with origin view `mind_graph`), read from `GET notes/post/<id>/threads` (`admin_record_note_threads_data_path`, a bare 404 outside the read scope) after the card is shown, so the card is measured again when they arrive. The notes stand under the title and its counts and the actions follow them, on screen and in the document alike (the notes handoff's decision 12: the document order follows the screen), so Tab walks the card as it reads: the notes' rows and the "Start a note…" field, then "Open post", "Focus" and Pin. "Open post" is therefore no longer the first stop and has a key of its own: Enter on the selected node, on the canvas or on the card as it takes the focus from the list, opens the post (on a control inside the card Enter is that control's). As first built the notes were drawn above the actions but came after them in the document (the actions' row was `order-1`), so the focus order and the visual order disagreed. An unread row is ink for dim, an accent dot and the visually hidden word "new". The card's notes section is a `record` of `admin--notes-live`, so it reads its list again when a thread of the post changes (`docs/reference/notes.md`, "Live delivery"). A click on the node the card already shows does not build the card again, so a note half typed in it stays. A tag's has "Show posts with this tag" (the posts list with its `tag` filter), "Focus" and "Pin" / "Unpin". What leads somewhere is a link drawn as a button, so it opens in a new tab like any link and a test follows it with `click_frame_link`; Pin is a button. Close is × in the card's corner, named "Close", and *last* in the document, so Tab meets the actions first. **A click on the canvas never navigates**; the card's links do. A click on empty canvas, Escape (from the canvas or from inside the card) and Close clear the selection; the last two give the focus back to where the card was opened from, the canvas or the list's row. A press that moves is a drag, not a click, and a plain click sends the worker nothing — a `drag` reheats the layout, and the graph would twitch under every click. A filter change recomputes the neighbours, and clears the selection when it hides the selected node. The tooltip with the whole title is shown only for a title the label cuts short: the hovered label on its backing already names the node.

**Pinning.** A dropped node stays where it was dropped: `drop` leaves `fx` / `fy` set in the worker, where `onDrop` used to send `unpin` — which is why it sprang back. A node can also be pinned where it stands from its card. Which nodes are pinned is the page's to know (`state.pinned`, indexes) and to show: the pin mark, the card's button reading "Unpin", `data-pinned` on the element, and "Release N pinned" beside the zoom control, which is in the page hidden and is shown, with its pluralised label, only while something is pinned. Three things release: "Unpin", "Release N pinned", and a double click on the node (`input.js`'s `onDoubleClick`; both of its clicks have selected the node already). **Pins live in the page that made them**: nothing is stored, a reload forgets them, the controller's `reset()` takes the count and the button back on a restored snapshot, and a filter change forgets those of the nodes it hides — the worker lets go of them in its `filter` — while a pinned node the filter still shows stays put through the new layout. A node is held where it was grabbed, not by its centre, so a drag by the label does not make the mark jump to the pointer.

**The filter** (All / Related / Tags) is three radios applied in the page: every edge of the chosen kind, and under "All" every node, otherwise only the nodes such an edge touches. The worker is handed only what is visible, and a hidden node keeps its last place, so it comes back where it was. At the cap a change costs about ten milliseconds in the page, list included; the layout then eases to rest at frame pace, about five seconds.

**The list** beside the canvas is the keyboard and screen-reader path, and a way to find a node by name for everyone. The canvas is one image to assistive technology (`role="img"`; its name says how many posts and tags and how many connections are drawn), and nothing on it can take focus, so every drawn node is also a row: two groups headed "Posts · N" and "Tags · N", best-connected first, each row with the type's dot or the tag's square, the title and the number of connections. **A row is a button, and it selects**: it does to the graph what a click on the node does, centres the camera on the node, opens its card and moves the focus to the card (which is named by its title, so a screen reader says what opened); closing that card gives the focus back to the row. It never navigates — the card's "Open post" and "Focus" do. Its accessible name is one key that says all of it ("Alpha: post, 2 connections. Shows it in the graph."; `list.select_post` / `select_tag`), never strings joined in the script. Hovering or focusing a row gives its node the hovered state, and a node selected on the canvas has its row marked (`aria-current`) and scrolled into view *inside the panel* — by setting `scrollTop`, never `scrollIntoView`, which would scroll the page too where the panel stands under the canvas. The rows were links to a node's local view until the round of 2026-10-08, in a `<details>` under the box that started closed, and nobody found it. `node_list.js` rebuilds the list from the same data on every load and every filter change (9 ms for 1,769 rows at the cap), with one listener of each kind on the container however many rows there are. It is filled before the layout starts, so it is there when the worker fails. In the document the search field comes first, then a local view's focus bar, the filter, "Release N pinned", the zoom buttons, the canvas, the card and the list. The search results are plain links after the field, so Tab reaches them, and what a screen reader should hear about them goes through a `role="status"` line; the notice over the canvas is a polite live region too.

**Turbo's page snapshot keeps script-written state.** Turbo caches the page as it stood when it was left — `data-state="ready"`, `data-settled`, the counts, the canvas's `aria-label` with those counts in it, the notice's lines, an open selection card and where it stood, the search's text and results, the list's rows, the zoom's figure, the hovered node, the number of pinned nodes and the button that releases them — and Back restores exactly that, before anything has been fetched or laid out. Left alone, a test that waits for `[data-settled]` passes on the snapshot, and a person sees a card for a selection that no longer exists. So the controller's `reset()` runs first thing in `connect()` and takes all of it back, and the app writes it again as it becomes true. The canvas's name is put back from its `data-label`, the name as the server wrote it: otherwise it would name the previous visit's counts until the data came, and for good if the load failed. One thing is kept on purpose because it is the person's own state: the filter's radios (the graph shows what the control says, and the filter is sent to the worker right behind `start`). Pins are *not* kept: they belong to the page that made them, and the layout that comes back holds nothing. Anything new the script writes into the page belongs in `reset()`.

**Testing it.** A canvas has no elements to find, so the app says what it shows on its element, and writes each only when it changes: `data-state` (`loading`, `ready`, `failed`, `worker-failed`), `data-settled` (present when what is shown is what was last asked for, at rest), `data-nodes` and `data-edges` (what the filter shows), `data-zoom`, `data-labelled` (the labelled nodes' ids, the hovered one's among them), `data-selected`, `data-neighbours`, `data-hovered` and `data-pinned`. `data-settled` is written *before* the frame that writes `data-zoom` and `data-labelled` for the final fit, so the tests' `await_graph` waits for the attribute and then for that frame (`await_frames`); a test that needs one particular label waits for it with `await_js`. `element.mindGraph.screenPosition(id)` answers where a visible node is in client coordinates, and the test clicks there with a real mouse click; `element.mindGraph.labelBox(id)` answers the box of a node's label as the last frame drew it, for a click on a label; `element.mindGraph.draws()` is the number of frames drawn, for "nothing is drawn once the screen is left". What a mark *looks* like is read from the canvas's own pixels (`pixel_at` in `test/system/admin/mind_graph_test.rb`): a canvas can pass every other test and still draw nothing. What the layout is *told* is recorded by wrapping `Worker.prototype.postMessage` (`record_worker_messages`), since no pixel shows that a plain click sent the worker nothing, and what it *answers* by wrapping the `Worker` constructor on a screen visited before (`record_worker_answers`), since no pixel shows that a layout arrived in one step; reduced motion is emulated through the DevTools protocol and taken back in an `ensure` (`with_reduced_motion`). **Every `await_graph` waits for a layout to ease to rest, about five seconds**, since a small graph unfolds at frame pace: that is the screen as a person gets it, and the suite pays for it in time. **A test presses a node only when the layout is at rest**: `drag_node` waits for `data-settled` first, because a node is held where it was grabbed, and one that is still easing has moved on between the test reading its place and the press reaching the browser — a few pixels on a slow runner, which is how "the node is where it was dropped" timed out in CI. And nothing may assume how much a machine lays out in one 12 ms slice: the client's rule for a stale `settled` is tested against a worker the test plays itself, the real worker only for what holds whichever way the race goes. Escape on the canvas goes through `escape_on_canvas` (the focus by script, the key real): Cuprite's `send_keys` clicks an unfocused element in its middle, where the card of a centred node stands. The card's links are inside the `#content` frame, so a test follows them with `click_frame_link`, like any other link there. The modules that are plain functions — camera, hit test, label rule, card placement, the renderer's culling and states (through a context that only records), the input's gestures, the worker and its client — are tested in `test/system/admin/mind_graph_modules_test.rb` by **importing them in the browser** from any CS Studio page: the project has no JavaScript test runner and gains none, the import map already resolves them there, and a camera's arithmetic can't be asserted through pixels. The data set for measuring is `script/dev/mind_graph_posts.rb` (development only, deterministic, run against a throwaway database through `DATABASE_URL`).
