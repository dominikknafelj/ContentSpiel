# Writing and running tests

How the suites are run, the test databases, coverage and what CI runs. What a browser test must and must not do is in `test/system/README.md`.

**Tests:** `bin/rails test` (full suite, minitest). Single file: `bin/rails test test/models/page_test.rb`. Single test: `bin/rails test test/models/page_test.rb -n test_method_name` or `bin/rails test test/models/page_test.rb:42` (line number). System tests (Capybara on Cuprite, headless Chrome) are separate: `bin/rails test:system` (the whole browser suite, whatever file is named after it: one file is `bin/rails test test/system/admin/tree_test.rb`); run `bin/rails tailwindcss:build` first, and on a laptop cap the workers (`PARALLEL_WORKERS=6 bin/rails test:system` — twelve flakes under load). On macOS no command needs `PGGSSENCMODE=disable` in front of it: libpq's GSSAPI negotiation goes through Kerberos, which is not safe after a fork, and can crash a parallel run's forked worker in the pg gem so the run hangs forever; `config/database.yml` turns it off for the development and test entries (`gssencmode: disable`; `test/lib/database_gssencmode_test.rb`: "the development and test databases are reached without GSSAPI encryption"). `bin/ci` (`config/ci.rb`) runs what CI runs, and the seed, which CI does not, one step after another: setup, lint, the changelog guard against `origin/main`, the scans, the unit suite, the browser suite, the seed and `bin/theme-build-check`. Each working folder has a test database of its own, named after the folder (`content_spiel_test` for `ContentSpiel`, `content_spiel_test_note` for a worktree `ContentSpiel-note`; `ContentSpiel::TestDatabase`, `lib/content_spiel/test_database.rb`, which `config/database.yml` requires by path): a new worktree runs `bin/rails db:test:prepare` once, and two folders can run tests at once without emptying each other's tables (two whole browser suites at once still crowd a laptop). What a browser test must and must not do: `test/system/README.md`. **The system suite needs a quiet machine:** macOS background services (Software Update, Spotlight, photo analysis) at a load average of 80 to 110 made two whole runs worthless on 2026-10-10, with failures that were the machine's. Check `sysctl -n vm.loadavg` before a run (a load near the core count is not quiet), and a run that takes twice its usual time is not a result. **Never run a build while tests run** (`bin/rails tailwindcss:build`, `bin/dev`'s `theme_css:watch`, `bin/theme-build-check`): the public stylesheet's build takes its stamp (`app/assets/builds/.theme.stamp`) away for as long as it runs and writes it again only when it succeeded, two tests read the working tree's stamp (`test/models/setup/system_check_test.rb`: "the row's own probe reads the build's stamp: this suite's stylesheet is the default theme's"; `test/integration/admin/system_status_test.rb`: "the theme row names the theme that draws the site and no path of the server, and warns when the stylesheet is another theme's"), and every public integration test reads `app/assets/builds/theme.css`. Development and test share that stylesheet and its entry (`tmp/theme/entry.css`): a test run leaves the default theme's behind, also under a running `bin/dev`, and `bin/theme-build-check` does the same on its way out.

A local run is quiet: what tests themselves print (the statements a migration test runs, the seed file's "Seeded dev accounts" lines) is swallowed, and shown only for a block that fails. `VERBOSE=1 bin/rails test` prints all of it, and CI always sets `VERBOSE` (`TestOutput` in `test/test_helper.rb`; a test that prints wraps the call in `TestOutput.quietly { ... }`).

Coverage is on request: `COVERAGE=1 bin/rails test` (SimpleCov, line and branch) writes `coverage/index.html`, which `bundle exec simplecov open` shows; the parallel workers' results are merged into the one report. It is off by default, since a run of one file would report a meaningless few percent. CI turns it on for the unit suite and keeps each shard's report as an artifact (`coverage-0`, `coverage-1`; not merged, since there is no minimum to check yet). There is no minimum yet, so a drop doesn't fail a run.

The section behaviours of the editor are eight browser files, `test/system/admin/sections_*_test.rb` (adding, menu moves, moves, panels, pointer, removing, settings, translation and unavailable), so a change to one is run by naming one file; they share `SectionsSystemTestCase`. `add_block` and `await_sortables` are described in `test/system/README.md`.

CI runs both suites for every pull request in jobs side by side (a runner has two cores): the browser suite as four, the unit suite (every test file outside `test/system/`) as two. `bin/test-shard <system|unit> <index> <total>` deals the files so each job takes about the same time, by the seconds per file in `test/system_test_seconds.yml` (measured on a runner on 2026-11-05) and `test/unit_test_seconds.yml` (measured on a runner on 2026-11-06). The tables need no upkeep: a file one does not list counts by its number of tests, and a stale number only makes the jobs a little uneven. `test/lib/test_shards_test.rb` keeps every file of either suite in exactly one shard. The checks that speak for the shards are `system-test` (four) and `test` (two, the name the main branch's ruleset requires; the matrix job itself is `test-shard`). `bin/theme-build-check` runs once, as a step of unit shard 0. The rest of CI runs for a pull request too, and a new push to it ends the run before it: a merge to `main` is not tested again, so `main` is run by hand when that is wanted (`gh workflow run CI --ref main`); a run started by hand has no base to compare with, so it always runs every shard. A push to `main` does build the CMS's image and push it to the registry under the commit's id (`.github/workflows/image.yml`; `docs/reference/hosting.md`, "How a site's image is built"), which is what a site pins. A change that touches only `docs/`, a top-level `.md` file or `.github/workflows/image.yml` skips the browser suite, and `system-test` passes with the docs message; the unit suite always runs, because its guards read `CLAUDE.md` and `docs/reference`.
