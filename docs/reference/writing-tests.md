# Writing and running tests

Moved word for word from `CLAUDE.md`'s "Setup & Commands": how the suites are run, what a system test must and must not do, and what CI runs.

**Tests:** `bin/rails test` (full suite, minitest). Single file: `bin/rails test test/models/page_test.rb`. Single test: `bin/rails test test/models/page_test.rb -n test_method_name` or `bin/rails test test/models/page_test.rb:42` (line number). System tests (Capybara on Cuprite, headless Chrome) are separate: `bin/rails test:system` (the whole browser suite, whatever file is named after it: one file is `bin/rails test test/system/admin/tree_test.rb`); run `bin/rails tailwindcss:build` first, and on a laptop cap the workers (`PARALLEL_WORKERS=6 bin/rails test:system` — twelve flakes under load). On macOS prefix every test command with `PGGSSENCMODE=disable`: a parallel run can otherwise crash a forked worker in the pg gem and hang forever. Each working folder has a test database of its own, named after the folder (`content_spiel_test` for `ContentSpiel`, `content_spiel_test_note` for a worktree `ContentSpiel-note`; `ContentSpiel::TestDatabase`, `lib/content_spiel/test_database.rb`, which `config/database.yml` requires by path): a new worktree runs `bin/rails db:test:prepare` once, and two folders can run tests at once without emptying each other's tables (two whole browser suites at once still crowd a laptop). `test/application_system_test_case.rb` prepends `StaleNodeAtOnce` to Cuprite's nodes so a poll whose element died in a Turbo visit fails at once instead of spending half a second per element — that is what made toasts that had come and gone look "missing". Two more rules for a system test: a link into the `#content` frame (a media tile, a trash tab, a list row) is promoted by Turbo to a page visit a few dozen milliseconds after the frame has rendered, and until that visit's `turbo:load` the screen is still arriving — a field typed into can be re-rendered, a Back can be cancelled by the late visit, a link clicked can lose to it — so a test that goes on to read or use the new screen follows the link through `click_frame_link` (`test/application_system_test_case.rb`: a link by its text, or a block for anything else, including a form whose answer redirects inside the frame), the one shared helper; `click_tile` in the media tests and `click_tab` in the trash tests are thin wrappers around it, and no test keeps its own copy of the wait. A `_top` form pressed in that window is held by the write queue and sent afterwards (the promotion hold, see `docs/reference/save-rule-and-write-queue.md`); `test/system/admin/promotion_hold_test.rb` presses without the wait on purpose and must keep doing so. And a test that resizes the window puts the size back in an `ensure`, because the browser is shared with the tests that follow. A test never waits for an element that only a `hover:` style reveals (the CI browser reports it can't hover): click it with `visible: :all`. A notes system test clears `localStorage["cs-notes-open"]` in its teardown (the drawer remembers "open" per browser), never follows a link inside `turbo-frame#notes` with `click_frame_link` (that frame is never promoted to a visit: click and assert), and, before it causes a signal, waits with `await_notes_live` until every cable subscription of the page has been answered; the suite's `test` cable adapter delivers to the browsers as it is, so no test switches adapters. A test that stubs `window.fetch` intercepts only its own request and hands every other to the real `fetch` it saved, because the editors' live parts (presence, notes, live editing) fetch too: a stub that takes everything answers or holds theirs; and a stub that counts or scripts "the writes" of an editor passes a request to `/cs-studio/editing/` through untouched and uncounted, because a claim and a release are writes in the queue. Two people are two Capybara sessions (`using_session`), and every presence system test is built that way (`test/system/admin/presence_test.rb`, `presence_lists_test.rb`): time is not moved with `backdate` (that moves `updated_at`, which `presence_marks` does not have). A test writes a mark's `seen_at` or `state_at` itself with `update_columns` to make a row stale or an away person older, and shortens a script's intervals (its refresh, its slow timer, its interval between readings) through the element's values; where it must show that nothing happens it holds a `sleep` with its `# sleep: <reason>`, which the sleeps guard permits. `await_notes_live` waits for presence's subscriptions as well as notes' (a part that is an element of the page says it on its own `data-live-part`, `app/javascript/live/state.js`). An open page or post editor catches up once when its live-editing subscription is confirmed, and `await_admin_controllers` waits for that too (`await_live_part`: the region `#editing` says `answered`), because a test that touched the page before it would see it reconciled under it. A test of the stale machinery itself (a 409, "Changed elsewhere") makes the colleague's save with `as_unheard(actor)`, which drops the signal: a save the editor heard of is drawn into it, and its next save is no longer stale. A reservation's clock is moved on its row (`update_all(changed_at: 3.minutes.ago)` for a lapsed hold, `requested_at: 6.seconds.ago` for a request that is due), the scripts' waits are shortened through the region's values, and the unit tests hand `now:` to the statements; the two-connection tests (`Editing::ReservationRaceTest`, `Editing::TakeOverRaceTest`) force an order with their `behind` helper, which waits until Postgres says the second statement is blocked behind the first (`docs/reference/live-editing.md`, "In tests"). **The system suite needs a quiet machine:** macOS background services (Software Update, Spotlight, photo analysis) at a load average of 80 to 110 made two whole runs worthless on 2026-10-10, with failures that were the machine's. Check `sysctl -n vm.loadavg` before a run (a load near the core count is not quiet), and a run that takes twice its usual time is not a result. **Never run a build while tests run** (`bin/rails tailwindcss:build`, `bin/dev`'s `theme_css:watch`, `bin/theme-build-check`): the public stylesheet's build takes its stamp (`app/assets/builds/.theme.stamp`) away for as long as it runs and writes it again only when it succeeded, two tests read the working tree's stamp (`test/models/setup/system_check_test.rb`: "the row's own probe reads the build's stamp: this suite's stylesheet is the default theme's"; `test/integration/admin/system_status_test.rb`: "the theme row names the theme that draws the site and no path of the server, and warns when the stylesheet is another theme's"), and every public integration test reads `app/assets/builds/theme.css`. Development and test share that stylesheet and its entry (`tmp/theme/entry.css`): a test run leaves the default theme's behind, also under a running `bin/dev`, and `bin/theme-build-check` does the same on its way out.

**System tests fail on any JavaScript error.** `JsErrorCollector` (`test/support/js_error_collector.rb`, prepended to `Ferrum::Page`) records `Runtime.exceptionThrown` and `console.error` (Stimulus reports a throwing action there, with an Error argument's first stack line appended to the message), and the teardown fails the test. A test that expects one wraps the step in `expect_js_error(pattern, times:)`; `JsErrorCollector::IGNORED` holds the matchers that are let through (one Turbo AbortError), each with its reason. A click is `press` (a native click, so a control a person couldn't press is not found); `press_by_script` is the exception and carries a one-line comment naming why. **No fixed sleeps:** `test/lib/system_test_sleeps_test.rb` fails on a `sleep` in a system test without `# sleep: <reason of at least ten characters>` on the same line; a test waits for a condition with `assert_eventually(wait:, message:)`, `await_js(condition, wait:)`, `click_frame_link`, `assert_writes_settled` (the write queue is empty; trivially true on a screen with no autosave form, so useless for a form that is paused or failed), `await_frames` (three animation frames and a task: enough to let an event's synchronous work finish before asserting that something did NOT happen, not enough to wait out a timer such as a debounce or a retry delay), `backdate(record, by:)` (puts `updated_at`, and a page's `settings_changed_at`, in the past without a callback, because the browser's clock does not follow `travel_to`) and, for an AI-provider test that needs a request kept in flight, `GatedProvider` (`test/support/gated_provider.rb`, a latch: `hold!`, `release`, `reset!`). `capture_sql` (`test/test_helper.rb`) returns the statements a block runs, for a test that says a write costs the same at any size.

A local run is quiet: what tests themselves print (the statements a migration test runs, the seed file's "Seeded dev accounts" lines) is swallowed, and shown only for a block that fails. `VERBOSE=1 bin/rails test` prints all of it, and CI always sets `VERBOSE` (`TestOutput` in `test/test_helper.rb`; a test that prints wraps the call in `TestOutput.quietly { ... }`).

Coverage is on request: `COVERAGE=1 bin/rails test` (SimpleCov, line and branch) writes `coverage/index.html`, which `bundle exec simplecov open` shows; the parallel workers' results are merged into the one report. It is off by default, since a run of one file would report a meaningless few percent. CI turns it on for the unit suite and keeps the report as the `coverage` artifact. There is no minimum yet, so a drop doesn't fail a run.

CI runs the browser suite for every pull request, as four jobs side by side (a runner has two cores): `bin/system-test-shard <index> <total>` deals the files so each job takes about the same time, by the seconds per file in `test/system_test_seconds.yml` (measured on a runner on 2026-10-26; the table needs no upkeep: a file it does not list counts by its number of tests, and a stale number only makes the jobs a little uneven), `test/lib/system_test_shards_test.rb` keeps every file in exactly one shard, and the one check `system-test` speaks for the four. The rest of CI runs for a pull request too, and a new push to it ends the run before it: a merge to `main` is not tested again, so `main` is run by hand when that is wanted (`gh workflow run CI --ref main`); a run started by hand has no base to compare with, so it always runs every shard. A push to `main` does build the CMS's image and push it to the registry under the commit's id (`.github/workflows/image.yml`; `docs/reference/hosting.md`, "How a site's image is built"), which is what a site pins. A change that touches only `docs/`, a top-level `.md` file or `.github/workflows/image.yml` skips the browser suite, and `system-test` passes with the docs message; the unit suite always runs, because its guards read `CLAUDE.md` and `docs/reference`.
