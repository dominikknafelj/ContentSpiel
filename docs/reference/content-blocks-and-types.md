# Content blocks and content types

> Describes: `app/models/content_block.rb`, `app/models/content_types/`, `app/models/block_types/`, `app/models/content_model/`, `app/values/block_outline.rb`, `app/services/content_blocks/`, `app/components/admin/editor_screen/block_*` (the block card and the block picker), `app/components/admin/editor_screen/section_*` (and the tile, panel-title, move-dialog and delete-dialog components beside them), `app/components/blocks/section_component.rb`, `app/controllers/admin/content_blocks_controller.rb`, `app/javascript/controllers/admin/editor/blocks_controller.js`, `app/javascript/controllers/admin/editor/section_controller.js`, `app/assets/tailwind/themes/default/sections.css`, and for the Code block `app/values/code_highlight.rb`, `app/models/block_types/code.rb`, `app/components/blocks/code_component.rb` and its template, `app/components/admin/fields/code_field.rb` and its template, `app/components/admin/editor_screen/tile_summary_component.rb`, `shared_fields_component.rb`, `app/javascript/controllers/code_copy_controller.js`, `app/javascript/controllers/admin/editor/code_limit_controller.js`, `app/assets/tailwind/themes/default/code.css`, `config/locales/public.en.yml`, `config/locales/admin/fields.en.yml`; and for a block type's declarations, the hook and the recipe, `lib/content_spiel/plugins.rb`, `lib/generators/block_type/`, `test/support/block_samples.rb`.

## Content blocks

`ContentBlock` (`app/models/content_block.rb`) is one polymorphic-by-enum table (`block_type`: `rich_text` / `image` / `code` / `post_list` / `section`) belonging to a `Page`, ordered by `position` within its container (the page's own list, or one column of one section — see "Sections" below), edited in CS Studio as block cards, each its own autosaving form (see "Blocks" below). `Post` uses the same single-model-plus-enum shape for its own `content_type` (`blog` / `resume_entry` / `now_update`). A `post_list` block's `settings` jsonb names a `content_type` filter, a `tag`, and a `limit`; `listed_posts` is the canonical query both the listing partial and the permalink-resolution fallback in `PagesController` must agree on. A post's typed fields (`Post#fields`) name themselves in words wherever an error shows — `Post.human_attribute_name` turns `fields.speakers.0.name` into "Speakers, row 1: name" (without I18n lookup, so the German admin UI will need to revisit it) — and a typed date must be `yyyy-mm-dd` (`ContentModel::FieldSet::DATE_FORMAT`): free text that doesn't parse is *refused* on the field rather than silently wiping the stored date.

## Blocks in CS Studio

**Blocks.** `Admin::EditorScreen::BlockCardComponent`: a drag handle, the type name (a button that collapses the card), and a ⋯ `Admin::Ui::MenuComponent` (Move up, Move down, "Move into section…", Duplicate, a divider, "Delete block…"); `admin--editor--blocks#refreshMoveState` keeps the move items right after every move, add and delete. A block whose stored type isn't registered any more is the minimal "Unavailable type" card (danger border, "Delete block…" its only action). There is one dashed "+ Add block" row at the end of the list (`Admin::EditorScreen::BlockPickerComponent`: a `button_to` per registered type POSTing to `create`); Duplicate is what inserts below a block. In a section each lane ends with the same picker as a "+" menu (`section:`, `column:`), without the container types: it posts `section_id` and `column`, and `create` answers with the block's form and tile (the form marked `data-open`, which `admin--editor--section` opens at once) and the section's count, or, refused, with the message and the lanes as they are now. A post-list block's Content type, Tag and Limit share one row, Tag being a one-value chip input (a schema field's label is `ContentModel::Definition::Field#label`: the type's own `label:` where it gives one, "File name" for the Code block's `filename`, and its name humanised otherwise; `Admin::Ui::FieldComponent#label_text` asks it, and CSS draws it in capitals: the markup says "Content type", the screen CONTENT TYPE). The block's "Delete this block?" dialog is `Admin::EditorScreen::DeleteBlockDialogComponent`, one per block, drawn inside the element that stands for the block (its card, or its tile in a section).

**What live editing puts on a card** (`docs/reference/live-editing.md`). A block's card is a *unit* of the editor's live refresh in each of its three placements (in the list, as a section's panel, in a translation tab's group): its wrapper carries `data-editing-unit`, `data-editing-subject` (`block-<id>`) and `data-editing-version` (`Editing.version`: the block's `updated_at`, who holds it for this viewer, and for a card of the list whether it is first or last, for a panel its section and column), and `data-editing-held` while someone else holds the block. Between the header and the form stands the strip's slot, `#block-<id>-hold` (`data-editing-strip-slot`), always there and empty unless the block is held, with a polite live region beside it; the header has `[data-editing-mark-slot]` for "Updated by …". A card held by someone else, for a viewer who could otherwise edit it, is drawn read-only: the border `border-line-strong`, the fields rewritten by `Admin::EditorScreen::HeldFields`, no autosave controller, and "Take over" as the first item of its "⋯" menu. The card's and the tile's markers are the slot `editor.block.markers` (the holder's avatar, on a tile only, then the notes marker), and neither draws a marker itself. A section's own settings **form** is the unit for the section's block (the card around it is not one, since it holds other blocks' forms), with its strip slot under the header; a tile is a *part* (`data-editing-part`), replaced like anything that holds no form. Every element between a unit and `#content-blocks-list` has an id (the section's header, each lane's wrapper), because the refresh reconciles the list around a form that holds unsaved text and finds its ancestors again by id.

## The Code block

Source code with a language, an optional file name and a caption: coloured on the server, with a Copy button on the public site, and a plain monospace field in the editor. The design is `docs/superpowers/specs/2026-10-12-code-block-design.md`, whose "As built" part lists where the code left it; what a theme can do with the block (seven tokens, a template of its own, the copy script's markup) is `docs/reference/theming.md`, "The Code block". It is the first block type added since the registries were opened; "What the Code block touched", near the end of this file, records the places it was written into by hand and where each went when block types came to declare what they bring, and "Adding a block type", the last section, is the recipe a new type follows now.

**The type and where its values are stored.** `BlockTypes::Code` (`app/models/block_types/code.rb`, registered in `config/initializers/types.rb` after `Image`) declares three fields, `language` (a select over `CodeHighlight::LANGUAGES`, `blank: "Plain text"`), `filename` (a string, `label: "File name"`) and `code` (a `:code` field, `max: CodeHighlight::MAX_CHARACTERS`), uses the `caption` column and has the component `Blocks::CodeComponent`; it declares everything else it brings (block types spec, decision 1): its line in the theme contract (`theme_methods`), its seven `syn-` tokens, its stylesheet (`code.css`), its tile's line (`summary`, `BlockTypes::Code.summary`), its read-only editor action and its sample. It has no capability: `:code` was one, read only by the tile's branch, and went when the line became the type's `summary` (decision 9). The three fields are the same in every language of the site and live in the block's `settings` jsonb; the caption is the block's existing translated `caption` column and its only translated value. **So the block needed no migration**: the published copy already holds `settings` and `caption` (`Publishing::Changes::BLOCK_CONTENT`), the audit snapshot already holds a block's attributes, and the test that every column of `content_blocks` is in exactly one of the copy, the rows and never stored did not move. A `code` column would have been a column for one type and a new entry in the copy's lists for nothing the jsonb does not do. **Nothing is required**: the picker makes an empty block first, as it does for an image, and an empty Code block draws nothing on the site. The caption being optional, a Code block never makes its page "missing" in a language, a caption translated before the original's changed reads "outdated" as an image's does, and a change of the code changes no translation state (`test/services/translation_state_parity_test.rb`: "a code block's caption is tracked like an image's, never missing, and a change of the code changes no state"). Writes are the existing services (`ContentBlocks::Save`, `Duplicate`, `Destroy`, `Reorder`): authorised, audited, under the page's row lock, with no service of the block's own. On a live page a save is a change to publish like any block's and a visitor reads the copy (`test/integration/public_blocks_test.rb`: "a code block on a live page is read from its published copy: a save shows nothing until it is published, and counts as a change"; `test/integration/public_canary_test.rb` draws the type's sample, with its caption in all three languages, on its samples page). `test/models/built_in_types_test.rb` ("code is a block of three settings and a caption, none of them required, the code never translated") holds the declaration.

**Three things the schema learned for it** (`ContentModel::Definition`, `ContentModel::FieldSet`; `test/models/content_model/code_field_test.rb`):

- **The field type `:code`** joins `SCALAR_TYPES`, because a `:text` value is stripped at both ends when it is cast and the first line of a sample would lose its indentation. `FieldSet#cast_code` keeps the value as typed (the first line's indentation, tabs, inner blank lines, trailing spaces) and changes two things that are not content: a line ending becomes `\n` whatever the browser sent (a form submits CRLF), and lines of only white space before the first line and after the last, which a paste brings along, are dropped; only white space is nil. It works on lines and not with a regular expression, so a run of blank lines in the middle of 20,000 characters is not walked once per line. The cast runs on read as on write, so a row written around the services reaches no reader with outer blank lines either. `max:` counts characters for this type (it is a number's upper bound for an `:integer`), after the line endings are one character each, and reports Rails' own `:too_long` with its `count`; the words are `errors.messages.code_too_long` (`config/locales/en.yml`), which says the limit grouped ("20,000"), as the counter under the field does. **A `:code` field is never translated**: the definition refuses `translated: true` on one ("the code is the same in every language"), and `Admin::Ui::FieldComponent::TRANSLATABLE_TYPES` does not list the type. Those two together are what keeps source code from an AI provider, since a translated field of a translatable type is the only thing the Translate button is offered for ("the first line's indentation, tabs and inner blank lines are kept as typed", "a line ending is one line break, whatever the browser sent", "leading and trailing lines of only white space are dropped, and only white space is nothing", "more characters than max is too long, counted after line endings are one character, and the text is still in the object", "a code field is never translated"; `test/components/admin/ui/field_component_test.rb`: "a code field is never offered to the AI translation").
- **`blank:`** is the label of a select's empty choice. Without it the choice of a select that is not required has no words; the Code block's says "Plain text". It is refused on anything but a select that is not required ("a blank label is for a select that is not required, and for nothing else"), and it changes nothing about validation: a value that is not on the list is still refused and no value is still nil ("a select with a blank label still refuses a value that is not on its list, and takes none"). `Admin::Fields::SelectField#blank_choice` draws it.
- **`label:`** is what CS Studio calls a field where its name humanised would read wrong. The plan had built "Filename" and left the wording as a question; the designer's answer was "File name, two words" (design answer C5), and the schema had no way to say it. It is a literal String in the type's definition, as a type's own label and a select's choices are, refused when it is blank or no String ("a label is a string with something in it"). **Everything that names a field to a person asks `Field#label` and never the name**: the input's label (`Admin::Ui::FieldComponent#label_text`), a switch and a group's legend (`Admin::Fields::BooleanField`, `GroupField`), a translation tab's shared fields, a post list block's tag input, a group's rows on the public page (`Fields::GroupComponent#rows`) and a validation message (`ContentBlock.human_attribute_name` and `Post.human_attribute_name`, which read the field from the type of the record Rails hands over as `base:` and fall back to the name humanised without one). `filename` is the only built-in field with a label of its own ("the Code block calls its file name File name, and no other built-in field has a label of its own"; `test/models/content_block_test.rb`: "a typed setting's error names its field by the field's own label where its type gives one"; `test/integration/open_types_test.rb`: "a typed field's error names it by the field's own label, the group's field included").

**`CodeHighlight` colours the code** (`app/values/code_highlight.rb`; `test/values/code_highlight_test.rb`). It is **the one file that names Rouge**. Rouge was in the bundle only through Lookbook, a development and test gem; a visitor's request runs it now, so it has its own line in the `Gemfile` with `require: false` (requiring Rouge loads every one of its lexers, so the one file that names it requires it). A hand-written highlighter was rejected: ERB, YAML, shell and Ruby are each wrong in corners (heredocs, `%w[]`, a `%>` inside a string) that a reader of documentation takes for a mistake in the documentation.

- `LANGUAGES` is Rouge's tag to the label a person reads, twenty of them (Rouge's tag for a Dockerfile is `docker`, its label "Dockerfile"). The list only grows: a stored tag that is no longer on it is drawn plain and names no language ("the twenty languages are the listed ones, each with a Rouge lexer, and a label is read by tag").
- `lines(code, language, block_id: nil)` answers **data, never markup**: one array per line of `[role, text]` pairs, the role nil for plain text and otherwise one of the seven in `ROLES` (`comment`, `keyword`, `string`, `constant`, `tag`, `attribute`, `embed`). Roles are Strings, not Symbols, so the cached value reads the same whatever serializer the cache store uses. `RULES` maps Rouge's token names to roles by prefix, most specific first (`Comment.Preproc` is `embed`, which is what makes ERB's delimiters stand out); everything that matches none is plain. Neighbours of one role are one pair, an empty line keeps its place, and the line break after the last line adds no line.
- **It never fails a page.** No language, a blank one, a tag that is not on the list, a lexer that raises, a lex that takes too long, lexers nested too deep and a stack that overflows are all plain text. What `lines` rescues is `StandardError` and `SystemStackError` and nothing wider: no memory, a script error (a gem's file that will not load), an exit and a signal are no failures of a lex and pass ("what is not a failure of the lex is not swallowed: no memory, a script error, an exit and a signal pass"). Bytes that are not text (invalid UTF-8, a binary-encoded string) are scrubbed to U+FFFD before anything else, so nothing raises and a visitor sees a replacement character where they were. A string in another encoding (US-ASCII, Shift_JIS, UTF-16) is transcoded first, its bad bytes replaced the same way, because `scrub` alone raises `Encoding::CompatibilityError` there; jsonb always hands UTF-8, so only a caller in Ruby can bring one ("a string in another encoding never raises, with bad bytes or without: US-ASCII, Shift_JIS, UTF-16LE and one Ruby cannot convert"). Code longer than `MAX_CHARACTERS` (20,000; only a row written around the services can hold it) is neither lexed nor cached. A lex that failed is logged with the language, the error's class and the block's id, and never with the code or the error's message, which can quote it ("a lexer that raises is plain text, and the log names the block and holds no code", "bytes that are not text never raise: invalid UTF-8 and a binary string are scrubbed, with or without a language", "code over the limit is plain text and is not cached or lexed, and code of exactly the limit is lexed", "a lexer that fails partway through gives plain text for all of it, not the part it had lexed"). The lexing runs inside the rescue and the budget on purpose: `lex` alone answers a lazy enumerator, and the `each` over it is what makes the lexer work.
- **What is cached is the lines**, not HTML, so a theme's template is never inside the cache. The key is `[ "code", the code's SHA-256, the language, Rouge.version, REVISION ]`: no locale and no content version, since the same code is coloured the same everywhere. **Bump `REVISION` when `RULES` changes**, or every cached block keeps its old roles until its code changes; nothing fails when it is forgotten, which is why it is a rule in `CLAUDE.md` ("the coloured lines are cached by the code, the language, Rouge's version and the revision").
- **A failure is cached, for five minutes, under a key of its own.** The first version cached whatever the block answered, and its review found the consequence: a lexer that raised once (one bad moment, a deploy half way) left the plain lines in the cache under the code's own key, and that block stayed uncoloured until its code or the revision changed, with one log line long gone. The second version cached no failure at all, and the whole-branch review found THAT consequence: the same code fails the same way on the next request, a public page is rendered for every request that brings no ETag, and so a block whose text makes one pattern run into the timeout cost every visitor's request a second, for ever. Now `lines` reads two keys in one `read_multi`: the lines of a lex that worked, stored without an end, and `failure_key` (`[ "code-failed", … ]`, the same parts under another first word), which `fail_for_a_while` writes with `expires_in: FAILURE_TTL` (five minutes) and which means plain text without a lex. A failure of one bad moment heals when the entry lapses; one that is in the code costs one lex per five minutes; and either heals at once when the code, the language, Rouge's version or `REVISION` changes, since each is in the key. One log line is written per entry, not per request ("a failure is remembered for five minutes: no second lex, one log line, and then it tries again", "a failure's entry is for that code and that language only, and a success is cached without an end", "one match past Regexp.timeout is a failure like any other: plain, remembered, and Rails sets that timeout"). With a cache that stores nothing (the test environment's; development's is a memory store, so a failure is remembered there as in production) every call lexes and logs again.
- **One lex has a deadline**, `LEX_SECONDS` (half a second, on the monotonic clock), and past it the block is plain text and the failure is remembered as above. Three things bound the time and none alone: the 20,000-character cap; Rails' `Regexp.timeout`, one second for ONE match (`load_defaults 8.1` sets it), which says nothing about a lex of many matches that each stay under it; and the deadline for the whole lex. The deadline is checked before every step of every Rouge regex lexer (`CodeHighlight::EachStep`, prepended once to `Rouge::RegexLexer`, reading a check kept for the running fiber only while a lex runs) and again for every token that reaches `coloured`; never by `Timeout.timeout`, which interrupts anywhere. The check has to be inside Rouge: `Lexer#continue_lex` joins neighbouring tokens of one type before it yields them, so a text of one token type yields once, at the end. One lex therefore costs at most the deadline plus the step that was running when it passed: a step tries the rules of its state in turn, each match under a second. Twenty thousand characters lex in 2 to 120 ms in each of the twenty languages (a laptop, 2026-10-12), so the budget is four times the slowest. A test shortens it through `CodeHighlight.budget` and moves the clock through `CodeHighlight.now` ("a lexer that never finishes is cut at the deadline and drawn plain, and nothing of the deadline is left behind", "a shortened budget cuts sooner, and the budget is half a second", "the deadline is checked inside Rouge, step by step: a text of one token type is cut although it yields once", which is also what fails when a Rouge upgrade renames `RegexLexer#step`).
- **Rouge's lexers call each other, and that is bounded, not closed.** HTML hands a script to JavaScript and a style to CSS, ERB and PHP hand what is around them to HTML, a Dockerfile hands its commands to the shell lexer, and Markdown hands a fenced block to whatever lexer its first line names, with Rouge's own guess for a fence that names none. So a Markdown block whose fence says `elixir`, which is not on the list, is coloured by Rouge's Elixir lexer: its tokens go through `RULES` like any other, so a role is still one of the seven, and it runs inside the same lex under the same deadline, because the check is in every regex lexer and not in the listed twenty. Closing it would mean a copy of Markdown's fence rule in this file. Three of Rouge's lexers are no regex lexers (console, plain text, escape): a fence that names one runs its loop unchecked, as Rouge's guess for a fence that names nothing does; their work is linear in the text and the step after them is checked ("a lexer Markdown hands a fenced block to is under the same deadline, listed or not").
- **How deep lexers nest is bounded: eight** (`MAX_DEPTH`). A lexer that hands text to another runs it inside its own rule, so each level is a whole turn of Rouge's loop further down the stack, and Markdown hands a fence to Markdown again: fences that each have another indentation nest as deep as the text is long. Five hundred of them (13,000 characters) overflowed the stack of a request's thread in 50 ms, long before the deadline, `SystemStackError` is no `StandardError`, and the public page was a 500 for every request. No test saw it, because a test runs on the main thread, whose stack is eight times a thread's. So the depth is counted around `RegexLexer#delegate` (in `CodeHighlight::Watch`, the object the deadline already keeps for the running fibre, through the same prepended `EachStep`) and past eight the lex ends as `CodeHighlight::TooDeep`, a failure like any other, with nothing to unwind from the edge of the stack; and `lines` rescues `SystemStackError` besides, for whatever else recurses in a lexer. An honest sample nests three or four deep (Markdown, a fence of ERB, the HTML around it, a script in that). **A test of this lexes on a thread** (`Thread.new { … }.value`), or it passes with the code broken ("nested fences are cut at a small depth and drawn plain, on a thread as a request runs on, and nothing overflows", "lexers nested as an honest sample nests them are coloured: a fence of ERB in Markdown in Markdown, with a script in it", "a stack that overflows inside a lexer is a failure like any other: plain, remembered, logged by its class"; `test/components/blocks/code_component_test.rb`: "a Markdown block of fences nested hundreds deep is drawn as its text on a thread, and raises nothing"; `test/integration/public_blocks_test.rb`: "a page that holds a Markdown block of fences nested hundreds deep answers 200 with the code as text, on a thread").
- **One request has two seconds for lexing** (`REQUEST_SECONDS`, four deadlines), because thirty blocks that each run to the deadline were thirty deadlines in one request, up to 45 seconds, and every request in flight when their negative entries lapsed paid it: three of them were all of Puma's threads. `PublicPageRendering` calls `CodeHighlight.start_request` before the action of the two public controllers, which puts the budget in `Current.lex_seconds_left` (reset with every request, as all of `Current` is); every lex, one that worked and one that failed, is taken from it; and once it is spent a block that is in neither cache entry is LATE: drawn plain with no lex, no negative entry and no log line, because it did not fail and was not tried, so the next request colours it. A cached block costs nothing and is coloured whatever is left. So all the lexes of one request cost at most the budget plus one lex, and thirty failing blocks are remembered over about eight requests of under three seconds each. Outside a request (a job, the console, a test that did not start one) nothing set the budget and there is none. A page on which a block was late must not be what a 304 confirms, since the ETag names nothing that moves when the block is coloured: `PublicPageRendering#forget_late_code` takes the ETag off that response. A page with a block that FAILED keeps its ETag (taking it off would make that page a full render for every request), so a visitor who was sent the plain page is confirmed it until something is published ("in a request the lexes of a page of slow blocks cost the request's budget and one deadline at most; the rest are plain, not lexed and not remembered", "a block that is cached costs a spent request nothing and is still coloured, and a failed one is still plain from its entry", "outside a request there is no budget: a job or the console lexes every block, however long the others took", "an honest lex is counted too: what it took is taken from what the request has left"; `test/integration/public_blocks_test.rb`: "a page on which a code block was late carries no ETag that confirms it: the next request draws the block coloured").

**The public component** (`Blocks::CodeComponent` and its template; `test/components/blocks/code_component_test.rb`) is built like `Blocks::ImageComponent`: it reads the block it is handed (a published view on the site, the rows in a preview) and nothing else, and `render?` is false without code. The markup is a `figure.content-block.content-block--code` holding a head strip (`div.code-head`: the file name, the language's label, the Copy button and a status line for a screen reader), a focusable `pre` with one `code` in it, and a `figcaption` when there is a caption.

- **The code is text, everywhere.** The template prints each pair's text through ERB's own escaping and wraps a coloured one in `tag.span(text, class: "syn-#{role}")`. Nothing in the component, in its template or in `CodeHighlight` marks a string as safe (`html_safe`, `raw`, `safe_join`, `<%==`, a `SafeBuffer`, `escape: false`), and Rouge's own formatters, which write HTML, are not used. **A span's class is built from the role, which comes from `ROLES`, never from the stored language**, so neither the code nor a language written around the services can add an element, an attribute or a class to a page. The file name and the caption are escaped text too ("source, file name and caption that look like markup are text: one pre, no script, no element the template did not write", "a stored language that is not on the list is plain text and names no language", "nothing in the component, its template or the highlighter marks a string as safe, and only the highlighter names Rouge", which is a source test: it reads those three files for the ways to print unescaped and all of `app/` for the word Rouge). The same holds in the editor: the tile's line is text ("a code block's line that looks like markup is text, and a refused save says so after it").
- **What is between the `pre`'s tags is the code and nothing else**: each pair's text and one line break between two lines, none before the first and none after the last, which is why the template writes the `pre` on one line. That is what a visitor copies ("the first line's indentation, tabs and blank inner lines are drawn as stored, coloured or plain").
- **The head strip is drawn only where it has something to show** (design answer C1; the spec had it always drawn, "since it holds the button", and the first build did, which left an empty box above the code of a block with no file name and no language wherever the button could not be shown). With a file name or a language the strip is drawn and only the button is `hidden`. With neither, the strip itself is `hidden` in the markup and is the copy script's `strip` target, shown together with the button where there is a clipboard. So a page without JavaScript, or without a clipboard, shows the code alone ("with no file name and no language the head is hidden in the markup and is the script's to show, with the button in it describing itself by nothing", "a file name alone and a language alone each draw the head as it is: not hidden, not the script's, only the button hidden"). The template says the condition itself, from `filename` and `language_label`, and makes the file name's id from `block`; neither is a method of the component (see "Two helpers taken back" below).
- **The four public strings** ("Copy", "Copy code", "Copied", "Not copied") are keys under `public.blocks.code` in `config/locales/public.en.yml`, read by `Blocks::CodeComponent#string` in the visitor's language where a `public.<locale>.yml` has the key and in English otherwise (`docs/reference/i18n.md`, "A string of the public site"). `string` answers those four keys (`STRINGS`) and no other: for any other key it raises where a theme is written (`Rails.env.local?`) and answers an empty string elsewhere, with one log line per key for the life of the process, because I18n's answer for a missing key is a sentence that would otherwise be a button's word on a public page ("string answers the four words and nothing else: another key raises with the four where a theme is written, and in production is empty and logged once"). `lines` is remembered, since a template may ask twice ("lines is read once however often a template asks").
- **The stylesheet** is `app/assets/tailwind/themes/default/code.css`, declared by the type (`t.stylesheet "code.css"`) and imported by the public stylesheet's generated entry directly after the default theme's `theme.css`, which no longer imports it (the built stylesheet is the same bytes: the rules stand where they stood): plain rules on tokens and not utilities, because the span classes are built from role names (`syn-keyword`), which no utility scan would find, and a theme that writes its own template keeps the rules by writing the same classes. It holds no colour of its own: each `.syn-<role>` is `var(--th-syn-<role>)`, and a role whose token is not declared inherits the code's ink. The status line is hidden from sight by the block's own class (`code-status`) and not by Tailwind's `sr-only`, which a review found would depend on the theme's scan reaching the component's template. A long line scrolls inside the `pre` (`overflow-x: auto`; the `pre` is focusable so a keyboard can scroll it) and the page never scrolls sideways; in a section's column what keeps the block narrow is the tracks' `minmax(0, …)` and the column's `min-width: 0` in `sections.css`, not a rule of the figure (it once had a `min-width: 0` that did nothing, since the figure is never a flex or grid item in the default theme). **Limits, as built** (each a roadmap row under "Code block" unless it says otherwise):

- **A slow lex is cut, not prevented.** Past the deadline a block is plain text for five minutes at a time, and a block whose text is slow in itself stays plain until its code changes; one such lex still costs a request up to the deadline and the step in flight, once per five minutes and block, and one request pays for four of them at most (the request's budget). The guesser Markdown asks for a fence that names no language, and the three lexers that are no regex lexers, run outside the steps the deadline checks. A machine under heavy load can push an honest lex past half a second (the deadline is wall time, and Puma's threads share one lock): the block is plain for five minutes and the log says `CodeHighlight::TooSlow`; a second is the first thing to try if that is seen for honest code. A visitor who was sent a page with a failed block is confirmed that page by a 304 until something is published.
- **Two ways to show code.** Rich text's own code block stays as it is: no language, not coloured, its Markdown form a fence, which in a post's Markdown stays rich text and does not become a Code block. The MCP server has no block tools, so no tool reads or writes a Code block.
- **The settings hold up to 20,000 characters**, and so does each published copy of its page and each audit snapshot of the block (one coalesced event for a typing session, as for a rich-text body). An audit event's changes do not: a `:code` field is two digests and two lengths there, by the field's type (`Audit::Snapshot.typed_changes`, `docs/reference/access-control-and-audit.md`).
- **No line numbers, highlighted lines or diffs**, no colours in the editor's field, no wrapping as an option.
- **The four public strings are English only** until the public site's strings are translated (roadmap, "Next", item 7).
- **A NUL character in any string field of a block** passes the schema's validation and is refused by Postgres' jsonb at the save (`ActiveRecord::StatementInvalid`), a 500 where a 422 belongs. It is older than this block and true of every string field.

## Sections

A section is a block that holds blocks: it arranges ordinary blocks in columns and gives them a band with a background and a width. It is the one container type, one level deep, on pages only. The design is `docs/superpowers/specs/2026-10-08-sections-layout-design.md`, whose "As built" part lists where the code left it.

**The data.** `content_blocks` has `section_id` (a nullable reference to `content_blocks`) and `section_column` (a nullable integer, 1-based); both are null for a top-level block. Two check constraints keep the pair together (`content_blocks_section_and_column_together`) and the column from 1 (`content_blocks_section_column_from_one`), and the index is `(section_id, section_column, position)`. The foreign key is the default NO ACTION, for the reason the keys to library images are (`docs/reference/media.md`: Postgres 18 reports a RESTRICT violation as SQLSTATE 23001, which Rails does not map to `ActiveRecord::InvalidForeignKey`): a section that still holds a block cannot be deleted around the service, and nothing cascades. `position` is counted per container — the page's top-level blocks among themselves, the blocks of one column of one section among themselves — so `position` alone never says where a block is on the page. **A block in a section still belongs to the page:** its `owner` is the page, `section_id` and `section_column` only place it, and `page.content_blocks` is every block of the page. That is why permissions (`ContentBlocks::OwnerPermissions`, the "editing a published page needs `publish`" rule), autosave with `base_updated_at`, translation tracking, the image foreign key, `media_usages` and a listing's `public_paths` read the same for a block in a column as for one outside (`test/services/translation_state_parity_test.rb`, `test/models/media/usage_index_test.rb`, `test/models/public_site/paths_test.rb` each have a case in a column). A section has no translatable content and adds nothing to `translation_states`. `ContentBlock.top_level` is the page's own list and `ContentBlock.in_column(section, column)` one container (`nil, nil` is the top level); `ContentBlock#section_blocks` is a section's blocks ordered by column, position and id, with no `dependent:` on purpose.

**The type.** `BlockTypes::Section` (`app/models/block_types/section.rb`) registers `section` with three select fields: `layout` (`LAYOUTS`: `one`, `two`, `three`, `four`, `one_two`, `two_one`, each mapped to its columns' weights — `one_two` is `[1, 2]`), `background` (`BACKGROUNDS`: `none`, `tinted`, `strong`) and `width` (`WIDTHS`: `content`, `full`); the defaults are `two`, `none`, `content`, and `BlockTypes::Section.weights` reads an unknown stored layout as the default. It declares the capability `:container` and `columns`, a callable on the definition (`ContentModel::BlockTypeDefinition`, `dsl_attribute :columns`) that takes a block's `settings` and answers how many columns it has; `finalize!` refuses a container type registered without it. **Code asks `ContentBlock#container?` (the capability) and `#column_count` (the definition's `columns`; 0 for a block that holds nothing and for a section whose type is gone), never `block_type == "section"`:** a container type a plugin registers is then a section everywhere, and the markup's word for the same thing is `data-container`.

**The rules the model enforces** (`ContentBlock#section_rules`): a top-level block names no column; a container never sits in a container; the section exists, is a container and is on the block's own page; the column is one of the section's layout. They run only for a new record or when `section_id`, `section_column` or `block_type` changed, because a block inside a section whose type is no longer registered fails every one of them and must still be editable until someone moves it out (`test/models/content_block_test.rb`, "a block in a section whose type is gone still saves").

**Display order comes from `BlockOutline`** (`app/values/block_outline.rb`), never from `position` alone. Built from a page's blocks already loaded, it costs no query and answers `top_level` (by position), `columns(section)` (one array per column of the layout, an empty column keeping its place; a block stored beyond the last column is left out of these and still in `blocks_in`), `blocks_in(section)` (reading order: column by column, each by position) and `reading_order` (each top-level block followed by the blocks in it). It also sets each block's `section` association from the same array, so `block.section` is no query afterwards. Its users: the public page (`ThemeHelper#block_outline`, memoised on the view, so **one outline per render** however many sections the page has — `Blocks::SectionComponent#columns` and `render_block` ask that one; `test/integration/public_blocks_test.rb`, "a page builds one outline however many sections it has"; for a post's permalink that outline is built a step earlier, by `PublicPageRendering#assign_record`, which reads from `reading_order` **which listing the post's detail stands in for — the first in reading order that lists it, never the first by `position`**, since a position is counted per container and a top-level listing and one in a column can tie — and hands the outline to the view in `@block_outlines`, the variable the helper memoises in, so it is still one per render: "a post's permalink stands in for the first listing in reading order, in a column or not, on every request" and "a post's permalink builds one outline, the one its page is drawn from"), the editor's page view (`app/views/admin/pages/show.html.erb`), every stream of `Admin::ContentBlocksController` that draws a section (`fresh_outline`, read after the action's service wrote), `Blocks::ImageComponent#sizes`, and the audit snapshot of a page, whose `content_block_ids` are in reading order (`Audit::Snapshot`). `test/models/block_outline_test.rb` holds its contract.

**The lock order: the page's row first, then block rows.** Every write to a page's blocks takes the page's row lock before it reads or writes a block row. `ContentBlocks::Structure#lock_owner` (`owner.class.where(id:).lock.pick(:id)`, so the caller's page object is left alone; nil and no query for an owner that is not saved yet) is the first statement of the transaction of `ContentBlocks::Save`, `ContentBlocks::Destroy`, `ContentBlocks::Reorder` and `ContentBlocks::Duplicate` — every call, a top-level block's ordinary autosave and the page's plain reorder included. `Translations::Confirm` includes the same module and takes the lock first when the record it confirms is a block (a page's, a post's or an image's confirm takes none: its own row is the first it writes). `Tags::Merge#repoint_blocks` locks the pages of the listing blocks it rewrites, in id order, before it locks those blocks; `Trash::Purge#purge_branch` locks the branch's pages, in id order, before the first block is destroyed; the one-off `RichText::ActionTextImport` locks a block's page before it writes the block's body. There are two reasons. What a structural write judges must be what the other writer committed: a fold to two columns and an add into column three, started together, would otherwise both pass their checks and leave a block in a column the section no longer has. And there must be one order: a section's fold, its lift ("keep blocks") and the renumbering after a delete or a move write *other* blocks' rows — the blocks in the section, and for a lift and a renumbering the top-level blocks around it — while holding the page's row. A block save used to take its own row first and the page's row afterwards, at `owner.touch`; the reorder, the tag merge and a page's destroy went block-first too. Any such writer on the same page and a fold or a lift could each hold what the other waits for, and Postgres ends one with `ActiveRecord::Deadlocked`. An earlier version exempted top-level blocks ("no structural write touches one"), which was wrong for exactly the lift and the renumbering, so no save is exempt. It costs one short `SELECT … FOR UPDATE` per block write and no new waiting, since the transaction always took that row at the touch. **What the page's row stands for is every row a block's write shares with the rest of its page**: the `pages` row, the other blocks, and the page's derived rows — `Translations::StateIndex.refresh` upserts the owner's `translation_states` rows for any block, changed or not, and an upsert locks them. That is the cycle `Translations::Confirm` used to close without ever writing the page: it wrote block B's `translation_sources` and then the state rows, while `ContentBlocks::Destroy` (which refreshes the states and then renumbers the siblings, B among them) and `ContentBlocks::Duplicate` (whose copy's save refreshes them before its reorder writes every sibling) held the state rows and waited for B. **So a new writer of a `content_blocks` row that writes, in the same transaction, the page, another block or a derived row of the page takes the page first.** The other writers of `translation_states` were checked against this and need nothing: `Pages::Save` and a page's own confirm write the `pages` row first; `Posts::Save`, `Media::Save`, `Media::Upload` and `Settings::Save` write their own record and its own state rows and no block; `Trash::Purge` removes a page's state rows under its page locks; the language services' `rebuild_all` writes state rows and nothing after them; and an AI suggestion is saved by the form's ordinary autosave (`AI::Translate` writes nothing). What shows it: tests that read the statements with `capture_sql` and assert the page's lock comes before the first block statement — in `test/services/content_blocks/save_test.rb`, `destroy_test.rb`, `reorder_test.rb` and `duplicate_test.rb`, `test/services/tags/merge_test.rb` ("the pages of the blocks it repoints are locked, in id order, before any block row is locked or written") `test/services/trash/purge_test.rb` ("the branch's pages are locked, in id order, before the first block is deleted"), `test/services/translations/confirm_test.rb` ("confirming a block's field locks the page's row first, before the block's row and the page's state rows", and "confirming a page's own field, a post's or an image's takes no extra lock") and `test/tasks/rich_text_migration_test.rb` ("a block's row is imported under its page's row lock, and a post's with no lock"). What is not covered: the order is proven by statement order, and the outcomes of two tabs by running the two writes one after the other, not by a test with two database connections; a purge's sibling renumbering (closure_tree's `_ct_reorder_siblings`) updates page rows outside the id-ordered lock, which leaves a narrow merge-against-purge deadlock and one between two purges of sibling pages; and a block create that waits on the lock of a page which is then purged goes on to write a block whose owner is gone, because `lock_owner`'s nil answer is not checked and the polymorphic owner has no foreign key. Each of those is a roadmap row.

**The services.** No controller writes a block; `test/support/service_calls.rb` has the factory for each.
- *Create into a column.* `ContentBlocks::Save` reads `section_id` and `section_column` from `attributes` **for a new block only** and appends it to the end of that column (`assign_position` counts within the container). For a block that exists both keys are ignored: a form that echoes them back must not move anything.
- *The fold.* Saving a section with a layout of fewer columns moves the blocks of each removed column to the end of the last remaining one, in column order, inside the save's transaction (`Save#fold_removed_columns`); a layout change never deletes a block. Two things about it are deliberate. The section is re-read from its row after the lock is taken (`reread_container`), because a second tab's copy may say "two" where the row has since been widened to "four", and assigning "two" to that copy would look like no change. And the fold is decided **from the rows** — every save of a container asks which blocks sit in a column beyond its layout — not from comparing the layout before and after on the caller's object, which the same stale copy would get wrong and strand a block. The stale-save 409 is not weakened by the re-read: it runs in the controller before the service is called.
- *Reorder and move.* `ContentBlocks::Reorder.call(page, ordered_ids, section:, column:, moved_from:)` writes the complete new order of **one container**: `section` and `column` name it (both nil for the page's list). An id in the order that sits in another container is moved here only if `moved_from` (`{ block id => { section_id:, column: } }`, blank for the top level) says where the caller believes it is and it is there; each container a block left is closed up (`Structure#renumber`). It writes with `update_columns`, so a moved block's `updated_at` — its autosave base — does not move. Its refusals write nothing: `STALE` (a block is not where the screen has it, arrived unannounced, is named twice or is missing from the order), `NO_COLUMN` (the section is gone or not a container, or has no such column — which includes every column of a section whose type is gone), `NESTED` (a container among the blocks moved into a column), and `NOT_THE_LIST`, the two-argument call's own refusal as it always read. Everything is looked up among the page's own blocks, so a stranger's id is not found and never moved in. **A block changes container in three places and no other**: a move through this service (with `moved_from`), the lift in `ContentBlocks::Destroy` (a column to the top level, "Remove section, keep blocks") and the fold in `ContentBlocks::Save` (a column to the last column left, when a section's layout is narrowed).
- *Both deletes of a section.* `ContentBlocks::Destroy.call(block, keep_blocks: false)`: with its blocks (each destroyed first, with its own callbacks), or `keep_blocks: true`, which lifts them to the top level at the section's place in reading order (`Destroy#lift`) before the section goes. What a block holds is read from the rows under the lock, not asked of the type, so a section whose type is gone is deleted or lifted like any other instead of running into the foreign key. A section that holds blocks is never refused: the person chooses between the two in the section's menu. The one event a delete records, `block.deleted`, lists the blocks that went with a section (`deleted_block_ids`) or stayed (`kept_block_ids`) and, for a block of a page, names the page (`page_id`): the row is gone when the audit notification runs after the commit, and live refresh hears that notification (`test/services/content_blocks/destroy_test.rb`: "the deleted block's event names its page"). `Page` has the same problem on its own destroy — `dependent: :destroy` goes in `position` order and would reach a section before the blocks in it — so a `before_destroy` declared ahead of the association destroys the blocks in sections first (`test/models/content_block_test.rb`, "destroying a page destroys the blocks in its sections first").
- *Duplicate.* `ContentBlocks::Duplicate` copies one block directly after its source in the source's container, and for a section every block in it into the same columns in the same order. Every copy is saved through `ContentBlocks::Save` (so the image-choice rule, the usage rows and the translation state are decided in one place) and placed by `ContentBlocks::Reorder`; the source and the blocks in it are re-read under the lock, and a source deleted meanwhile is the failure `Duplicate::GONE`. A copy refused part-way rolls everything back.

**The parameters of the controller.** `Admin::ContentBlocksController#reorder` takes `ids` (the container's complete order), `section_id` and `column` (absent for the page's list) and `moved_from[<id>][section_id]` / `[column]`; `admin--editor--blocks` sends them as JSON. Every one is read through `one_value`, `ordered_ids_param` or `moved_from_param`: a forged array or hash where one id belongs (`section_id[]=1`, `column[a]=1`, `moved_from[x][section_id][]=`) is read as not sent and answered with the service's refusal, never a 500 (`test/integration/admin/content_blocks_test.rb`, "a forged reorder whose section, column, ids or origin is not one value is answered, never an error"). `create` takes `section_id` and `column` beside `params[:block]`, and `destroy` takes `keep_blocks`. The section is looked up among the page's blocks, so another page's section is as gone as a deleted one.

**Audit.** There is no new action. A fold is in the section's `block.updated`, whose metadata is `folded_block_ids` — and that save is recorded with `coalesce: false`, an event of its own, because a coalesced extension of an open row leaves its `metadata` as first written and the ids would be lost exactly when someone adjusts a section's look and then its layout (`docs/reference/access-control-and-audit.md`). A section's delete is one `block.deleted` on the section with `deleted_block_ids` or `kept_block_ids`. A move is one `block.reordered` on the page whose `field_changes` are the target container's order before and after and whose metadata is `section_id`, `column` (both absent for the page's list) and `moved_block_ids`; it records where the block went, not where it came from. A duplicated section is several events, a `block.created` per copy and one `block.reordered`, none of which coalesces. A copy refused for want of permission (the image choice needs `media.upload`) had its `access.denied` written inside the transaction that was then rolled back, so `Duplicate` records it once more outside, on the block whose copy was refused.

### Sections in the editor

**The card, the lanes and the tiles.** On the default language's tab a section is `Admin::EditorScreen::SectionCardComponent`: a card of the block list like any other (`data-admin--editor--blocks-target="card"`, the block card's handle and Move up / Move down) marked `data-container`, with `admin--editor--section` on it. Its body is `SectionLanesComponent` — one lane per column, each a list whose **direct children are exactly its tiles** (the column's label and the lane's "+" are the lane's siblings inside an `.admin-section-lane` wrapper, never its children, because a lane's order is read from its children) carrying `data-section-id` and `data-column` — and under the lanes one `Admin::EditorScreen::BlockCardComponent` per block drawn as `placement: :panel`. A tile (`BlockTileComponent`) has the block's `dom_id`; its face is a button that opens the block's form, with one line of the block's content (`TileSummaryComponent`: a type's declared `summary` first, parts of the four kinds `text`, `word`, `mono` and `hint` (`LOOKS`) whose words are keys under `admin.components.editor_screen.tile_summary.types.<type, "/" as ".">`, a part of any other kind raising; else decided from the type's `uses_columns` and capabilities, never its name: an image's file name and thumbnail, the start of a text; a code block's file name or else its language and its first line of code, and a listing's filter, are their types' own `summary`, `BlockTypes::Code.summary` and `BlockTypes::PostList.summary`) that every autosave answer for a block in a section replaces, marked "Needs fixing" after an invalid save since the error slots are in a form nobody may be looking at. `SectionCardComponent.draws?(block, outline:)` is the one rule for "drawn as a section" (a container, or a block that still holds blocks) and `SectionCardComponent.for` the one door to the card or, on a translation tab, the group; the page view and `Admin::ContentBlocksController#card_for` both go through them, so a card streamed in is the card a page load draws.

**One open form per section, and every form is in the page.** All of a section's block forms are rendered with the page, each in a hidden panel (`Admin::EditorScreen::BlockCardComponent.panel_id`, `"block-<id>-panel"`), and `admin--editor--section` only shows one and hides the rest: pressing a tile opens its form under the lanes, headed "Image · column 2" (`PanelTitleComponent`); pressing another closes the first; Escape, the panel's Close and a second press on the open tile close it and give the tile the focus. **Do not fetch the open form, and do not remove a closed one.** A form that never leaves the document registers with the write queue once and keeps its debounce, its queued or in-flight save and its save state (paused by a 409, failed) whether it is showing or not; a design that fetched the form on demand would have to answer what happens to a save whose form has left the document, which is the case the queue's drain exists to guard against. Closing a form tells it to send what it holds at once (`admin--saving--autosave#saveNow`). Every way a panel closes goes through `admin--editor--section#hide`, which also says so with the event `admin--editor--section:closed`, on which the block's edit reservation is released once the form has nothing left to send. A panel marked `data-editing-gone` (the live refresh shows it because its block was deleted or moved away under unsaved text, and its tile with it) is not "the open one": opening a tile does not close it, and only its own Close button and Escape inside it do. Which form is open is read from the page — the panel that is not `hidden` — not remembered in the controller, because a section's card moved in the DOM disconnects and reconnects every target, and an id kept beside the DOM was once cleared while its form was still showing. A block just added arrives with its panel marked `data-open` and is opened by the script (the server never renders a panel shown: that would be a second open form). The panel is the same component, the same ids, the same `base_updated_at`, status line and error slots as a card, so `Admin::ContentBlocksController#update` answers a block in a column exactly as one outside, 409 included.

**The helpers a later change needs** (`Admin::ContentBlocksController`). `section_structure_streams(section)` is **the one redraw of a section's lanes**: it replaces the lanes, rewrites the text of every panel's heading (`panel_title_id`) and replaces both counts, from one fresh outline, because three things on screen say which column a block is in and they are brought up to date together or the screen contradicts itself. It never replaces a panel. `section_count_streams` replaces the header's "2 columns · 3 blocks" (`SectionSummaryComponent`) and the delete dialog's count (`SectionDeleteCountComponent`) after an add, a delete, a copy or a move. `tile_streams(block, open:)` appends a new block's panel and then its tile; `copy_tile_streams` puts a copy's tile after its source, unopened. `panel_removal_streams` removes the panel with a deleted tile (left behind it would stay open with no tile to close it from). `move_streams(origins)` draws each block a saved reorder moved between containers in its new shape — a card that went into a column becomes a tile plus a panel, a tile that left its section a card, a tile that changed sections takes its panel along, a tile that changed lanes inside its section has only its panel's heading rewritten — and recounts every section that gained or lost one. **A panel is replaced as a whole only there, when its block changes container**, which is why the browser makes the form safe first (see "Moves").

**The section's own settings** are a form in the card's header, an autosave form with the block card's ids (`Admin::EditorScreen::BlockCardComponent.autosave_form_data`, `status_id`, `base_updated_at_id`), answered by the same `update` action: a stale save is a 409 like any block's. Layout is a menu of six diagrams over a hidden input (`SectionLayoutMenuComponent`; a pick is sent at once, `admin--editor--section#chooseLayout`); background and width are selects. The answer replaces the layout menu **only when the stored layout changed** — replaced by a save of the background, the menu's button lost the focus someone had just moved onto it and an open menu was swapped for a closed one — and redraws the lanes (`section_structure_streams`) **only when the number of columns changed**, since a save of the background, the width or a layout with as many columns moves no block and the lanes are tiles a person may be focused on or dragging. The form holds no other form: the menu's Duplicate and "Remove section, keep blocks" are `button_to`s and sit after it. The ⋯ menu: Move up, Move down, Duplicate, "Remove section, keep blocks" (no question asked, `keep_blocks` beside the DELETE; the blocks take the section's place as cards, and because those cards replace the blocks' forms the press goes through `admin--saving--queue-hold`: it waits until the write queue is empty and does not run, with a toast, while any form on the screen ended unclean) and "Delete section and its blocks…", whose dialog says how many blocks go with it. Collapsed, the card is its header line.

**A block's delete dialog is in its tile or its card, never in a panel.** A `<dialog>` inside a `hidden` element is not drawn when opened, so "Delete block…" in a tile's menu would have done nothing while the form was closed. In the element that stands for the block, every answer that removes or redraws that element takes the dialog with it.

**The translation tab.** On any tab but the default language's a section is `SectionGroupComponent`: a heading over the card of each block it holds (`placement: :group`), in reading order, every form open, with no lanes, tiles, hidden panels, settings or `admin--editor--section`. The group stands in the list with the section's `dom_id` and `data-block-id` as a `card` target, because the cards around it are still moved on that tab and the order sent has to name the section; it has no handle and no menu, so structure is edited on the default tab only.

**View only.** A viewer who cannot edit sees the lanes and can open a tile: the form is the disabled one a view-only card shows, with no `admin--saving--autosave`. There is no grip, no ⋯ menu, no "+", and the section's three settings are a disabled fieldset (`test/system/admin/view_only_test.rb`).

**Small screens.** `.admin-section-card` is a container (`container-type: inline-size`), and the lanes sit side by side from 40rem of the *card's* width; below that they stack, each under its column label. The label is `aria-hidden` (a screen reader gets the same words from the lane's `aria-label` at every width). The column count reaches the stylesheet as `--lanes`.

**Unavailable types.** A tile of a type that is no longer registered keeps its four move items and "Delete block…" and has no Duplicate: it keeps its pointer grip, and everything a pointer can do has a keyboard path. A section whose own type is gone is still drawn as a section (`draws?` asks the rows): the "Unavailable type" card with the danger border, no handle, no settings form and no menu, and a section's own two removals as two buttons under the menu's words: "Remove section, keep blocks" (a form of its own with `keep_blocks`, through `admin--saving--queue-hold` as in the menu; the blocks take the card's place as cards in reading order) and "Delete section and its blocks…", which opens the section's delete dialog and deletes the section with the blocks in it. The sentence under the header names the ways out ("Its blocks are still here. Remove the section and keep them, move them out one by one, or delete it with them."). It never reads "Delete block…" as an unavailable block's card does, because it holds other blocks. Its blocks are listed under it in **closed lanes** — one per distinct stored column, marked `data-no-drop`, with no "+" — because the server has no column of it to take a block (`NO_COLUMN` for any order of one, including an order of the lane a block is already in). So `admin--editor--blocks#closed` shuts every way in or along: no drop, no sorting, Move up / Move down / "Move to column…" disabled, no choice in the Move dialog, and no Duplicate on its tiles. What is left on each tile is "Move out of section" and "Delete block…", and opening and editing its form; on the card itself, the two removals named above.

### Moves

**One sender.** `admin--editor--blocks#move(item, from, before)` is the one sender for a drop, a menu move and the handle's keyboard path; it sends the complete order of the container the element is in now, with `moved_from` when the server has the block elsewhere, through `app/javascript/saving/queue.js` (`docs/reference/save-rule-and-write-queue.md` has the queue's side). The list and every lane are Sortables of one group; a lane refuses a section's card (`accepts`, as the server answers `NESTED`). **A move ignores an edit reservation**, and so do adding, duplicating and deleting a block: they are instant actions that hold nothing, and a block moved into a section while someone holds it is still held by the same tab (`test/integration/admin/editing_claims_test.rb`: "moving, adding, duplicating and deleting ignore a hold", "a block moved into a section while held is still held, by the same tab"). A section's layout is not such an action: it is saved by the section's own autosave form, which claims the section's block. While a block is in someone's hand (a drag, a keyboard pick-up, a move not yet answered) the controller says so with the event `admin--editor--blocks:moving`, and the live refresh draws no list until it is over (`sayMoving`).

**A move between containers and the block's form.** A saved move between containers is the one time a form on the screen is replaced while its block stays (`move_streams`), so:
- as the move is queued every autosave form of the block list is told to send what it holds (`sendHeldEdits`), which puts those saves ahead of the move; this happens for any move that names a section or changes containers, a move along a lane included;
- when the move's turn comes, the moved block's own form must have ended saved (`formState`). One that did not end clean — paused by a 409, refused, invalid, offline — is **not moved**: everything is put back and a toast says "Reload or fix this block before moving it.";
- a form whose edit is still on its way (typed while its own save was on the wire, so its follow-up is queued behind the move) makes the move **stand back once**: the form is told to send again and the move is queued again behind it; still not saved at that turn, the move is given up like a refused one;
- the queue slot is **held until the answer is drawn** for a move that names a section or changes containers (`streamsApplied` in `saving/order_request.js`), because Turbo performs a stream a frame after it is handed over and the next queued write would otherwise be sent from the old elements;
- a queued move whose element is no longer where that move put it (put back, dropped again elsewhere, or the screen redrawn) is **dropped**, not sent;
- from the drop until its answer is drawn or it is put back, the moved element and, for a tile, its panel are `inert` (`hold`): grabbed again in that window, the second drag held an element the answer then removed, and words typed into the form went with the form.

**What goes back after a failure.** `restoreTo` is each container's order as the server last took it, kept **per container**: the `before` of the first move since then, not of each (two quick moves queue two requests, and the second's `before` is an order that was never saved); a request that succeeds while another waits makes the order it sent the one to go back to for its own container (`taken`), and after a saved crossing move the redrawn element takes the old one's place in what is remembered (`followRedraw`).

**A refused structural move.** The server answers a refused move that named a section or moved a block (and was not a denial) with the whole list as it is now (`blocks_list_stream`): the screen was behind, and how far is not known. **The browser draws that list only when no autosave form of the block list holds text the server does not have** (`formsHoldText`, asked as the answer arrives, so text typed during the round trip counts). Otherwise the answer is drawn without its list (`renderKeepingForms` stops that one stream at `turbo:before-stream-render`): the block is put back, the alert under the reason gains "Something on this page changed elsewhere. Reload once your unsaved text is safe." and nothing else on the screen changes. A 409 and a refused move have the same cause — a second editor on the page — so they arrive together, and the 409 bar has promised the typed text stays. The cost is that the screen stays behind the server until the reload and further moves may be refused again. The same line is added under any refusal that arrives while a form holds such text, a denial included, although only a structural refusal carries a list.

**Dragging past a section.** `besideSection` (the list's `onMove`): over a section's card the list sorts a dragged block before the section only from above its lanes and after it only from below; level with the lanes it does nothing, and a lane under the pointer takes the block itself. Without it a card dragged up from below jumped above the section the moment it touched its edge, pushing the lane being aimed at out from under the pointer. And a lane that was only *moved* — its section's card dragged or stepped along the list, which Stimulus reports as each lane disconnected and connected again — keeps its Sortable: `Sortable#destroy` ends whatever drag is under way, so destroying the lanes of the card being dragged dropped that card after its first step.

**No Undo for a structural move.** The Undo toast follows only a reorder of the page's own list. Its Undo is a reorder of that list back to the order before, which cannot put a block back into the column it left.

**The keyboard path is the menu.** A card keeps its handle's keyboard path along the list (Space, arrows, Space). A tile's grip is a `<span>` for the pointer only, hidden from a screen reader; its ⋯ menu has every move a drag makes: Move up and Move down along the lane, "Move to column…", "Move out of section" (to the list, directly after the section's card), and a top-level card's menu has "Move into section…". The last and "Move to column…" open **the one Move dialog of the page** (`MoveDialogComponent`), whose `<select>` is rendered empty and filled in the browser as it opens (`admin--editor--blocks#askWhere`) from the sections and lanes on screen — sections are added, removed and given other layouts without any other card being drawn again, so a list the server rendered would be stale; sections are numbered as they stand in the list, and closed lanes are neither offered nor counted. Each menu move makes the DOM move a drop would have made and calls `move`, and is **announced** in the live region the handle's keyboard path speaks in (`block_moves.*` in `config/locales/admin/editor_screen.en.yml`: which block, where, its position), with "… is back where it was." when it did not stand. **Focus:** it goes to the moved block at once — a card's handle, a tile's ⋯ button — and stays there for a move along one container. A block that changed containers is `inert` until its answer and so loses the focus; when its turn ends the element that stands for the block then (the redrawn card or tile, or the one put back) takes it, but only if nothing else has the focus by then. After Duplicate the focus goes to the copy; a copied tile is not opened.

### Sections on the public page

**The markup.** `app/views/pages/show.html.erb` walks `block_outline(@page).top_level` through `ThemeHelper#render_block`, and `Blocks::SectionComponent` draws the blocks in its columns through the same helper (so the listing-to-detail swap of a post permalink happens in a column too, and each block is drawn once). The component is asked of `Theme.current.component_for(definition, role)`, and a theme may replace a component's TEMPLATE, not its class: for a component whose template the site's theme folder holds, `component_for` answers a generated subclass that carries the theme's file (`docs/reference/theming.md`, "The four seams"). A block type's line in the contract is its own declarations, `theme_methods` (the methods its template may call) and `tokens`, read by `Theme::Contract.components` and the token lists; a type that declares no `theme_methods` is refused at registration, and a built-in's line and tokens are also written in the ledger ("Adding a block type", step 9). The markup:

```
section.content-section.content-section--<background>.content-section--<width>
  div.content-section__inner
    div.content-section__grid.content-section__grid--<layout>
      div.content-section__column   (one per column, in reading order)
```

The `<section>` has no accessible name and no heading, so it is a grouping element and not a landmark. Each of the three settings is read against its own list, so an unknown stored value becomes the default and never reaches the class attribute. A block's component does not know it is in a column, with the one exception of an image's `sizes`. A section with no block that draws anything renders nothing (`render?`); an empty column keeps its place while the columns sit side by side and is hidden while they are stacked (the template writes a column's tags closed up so `:empty` matches).

**The layouts and breakpoints** are CSS only (`app/assets/tailwind/themes/default/sections.css`), by container query on the section's own width, not the window's: below 30rem every layout is one column in reading order; from 30rem the columns sit side by side (`one_two` and `two_one` as 1fr/2fr), four of them two by two; from 44rem four are four across. **The container is the `<section>`** and a band's side padding sits on `.content-section__inner`: a query measures the container's content box, and with the padding on the section a tinted band in the 46rem content column would measure 43rem and its four columns could never get past two by two.

**Bands and width.** `tinted` and `strong` paint the band from the tokens `--th-band-tinted` and `--th-band-strong` (`tokens.css`, both themes). **A band re-values the `--th-*` tokens for everything inside it** instead of restyling selectors: the blocks in a band are drawn by components that know nothing of it and colour themselves with the theme's tokens, so a block added later is right without a rule. The strong band sets ink, dim, meta, accent, the lines and the sunken and surface backgrounds from `--th-on-band-strong`, `-dim` and `-accent`; the tinted band sets `--th-meta` to `--th-dim`, because plain meta on the light tinted band is 4.32:1, and `--th-sunken` to `--th-surface` so a code block does not vanish into it. Contrast, computed from the tokens: the strong band's body, dimmed and link colours are 16.7:1, 11.0:1 and 9.9:1 in the light theme and 16.3:1, 8.1:1 and 6.4:1 in the dark; the lowest pair in use anywhere is the dark theme's link on a code block inside a strong band, 4.95:1. `test/integration/design_tokens_test.rb` ("text on a band is readable in both themes") holds the strong band's three and the tinted band's ink, dim and accents at 4.5:1; no test reads the lines that re-value `--th-meta`. `width: full` breaks the band out to the window's edges and puts its content back on the content column (`margin-inline: calc(50% - 50vw)` with the same amount of padding); `100vw` includes a classic scrollbar's width, so `<body>` carries `overflow-x: clip` (`overflow-x-clip` in `app/views/layouts/application.html.erb`) — on `<body>` the value goes to the viewport, which stays the one scroller, so sticky elements and a code block's own sideways scroll behave as before. Adjacent sections with the same background join without a gap.

**Image `sizes`.** An image block in a column asks for its column's share (`Blocks::SectionComponent.image_sizes`, from the layout's weights): its share of the 736px content column from 768px of viewport, its share of the viewport from 480px, the full width below. It is a hint, so the grid gap and a band's padding are left out. An image *inside rich text* in a column still asks for the content width (a roadmap row).

**Types that are gone.** A block of an unregistered type in a column is skipped with a log line, as at the top level. A section whose own type is gone draws the blocks it holds once each, in reading order, stacked at the content width where the section was, with no band and no grid (`render_block`'s last branch): they are registered blocks, and rendering nothing would take a page's texts and pictures off the site because their wrapper's plugin was removed. Their images ask for the content-width `sizes`.

**Caching and preview** are unchanged: a block write that changes something touches the page (its `updated_at`, not the settings form's `settings_changed_at`): a delete, a duplicate and a changed order always, a save when the block itself changed or a section's column was folded, and a save that wrote nothing not at all (`test/services/no_change_save_test.rb`), a live page's `after_commit` moves the public content version, and `/preview` renders a section as the public page does (`test/integration/preview_test.rb`).

## Block types from outside

A gem (a Rails engine) registers its block types through one hook, `ContentSpiel::Plugins.block_types` (`lib/content_spiel/plugins.rb`, block types spec, decision 11), called from an `initializer` of its own:

```ruby
ContentSpiel::Plugins.block_types do |types|
  types.register "gallery/album" do |t|
    t.label "Album"
    t.field :title, :string, translated: true
    t.component Gallery::AlbumComponent
    t.theme_methods :block, :page, :title
    t.tokens themed: %w[gallery-frame]
    t.stylesheet Gallery::Engine.root.join("app/assets/stylesheets/gallery/album.css")
    t.sample translations: { "en" => { title: "Holiday pictures" } }, shows: [ "Holiday pictures" ]
  end
end
```

The hook keeps the block for the life of the process, and `config/initializers/types.rb` calls every kept block after the built-ins on every `to_prepare`: an engine's own `to_prepare` runs before the application's, whose first line is `reset!`, so a type registered there was wiped on every prepare. The file is required from `config/application.rb` before `Bundler.require`, so a gem may name the hook whenever its files load: the constant is already defined then, and a gem requires nothing (`lib/` is not on the load path that early, so a `require "content_spiel/plugins"` would fail). It is plain Ruby and is not reloaded. A gem registers ALWAYS through the hook: a `BlockTypes.register` of its own, in its engine's `to_prepare`, is wiped by the next `reset!`, and one inside the hook's block passes around the registrar's refusals (nothing refuses either yet). The replay is the LAST statement of the registration block, after the content types, field groups, rich text, permissions and AI providers, so a gem whose hook raises on a development reload leaves every registry of the CMS filled and only the outside block types missing; the refusal every public page then says tells the gem's author to restart the server once it is corrected, since a gem's files are not reloaded. The rules, each refused at registration with the type's name and, for the hook's own, the place the hook was called (`file:line`, so a site's log names the gem):

- **Order:** the built-ins in their written order, then the outside types in the order their hooks were called (the `Gemfile`'s). That is the picker's order.
- **Names:** `owner/name`; a bare name is a built-in's, one call of the hook registers the types of one owner, and an owner is one hook's (a second hook that registers under it is refused, with both places named), since the owner's prefix is what keeps two gems' tokens apart. A name taken twice is `ContentModel::DuplicateType`, and a component another type already hands out is refused (`BlockTypes.admit!`: one component, one line of the theme contract).
- **No `read_only_actions`:** the held form's allow-list is one list for every form of the site (`HeldFields.allowed_actions`), and in step 1 a gem brings no editor script, so any action it named would be one of the CMS's, kept alive in every form someone else holds. Step 2 opens it with the editor scripts, each action's identifier carrying the owner's prefix.
- **No capability:** `:container` is bound to the section classes and `BlockOutline`, `:lists_posts` to `BlockTypes::PostList`'s criteria, which decide posts' addresses; neither has a seam for an outside type yet (decision 12).
- **The four columns:** `uses` names `body`, `caption`, `alt` and `image` and no other, as for every block type; fields of every type and option are open.
- **Tokens from base tokens:** the type's token names start with its owner (`gallery-frame`; an owner's underscore is a dash there, `photo-gallery-frame` for `photo_gallery/album`, because a token name has none), its stylesheet is ONE file at an absolute path under the gem's root (an `@import` in it is refused: the build would resolve it and the guard would never read it), and its colours are `var()` or `color-mix()` of the theme's base tokens: a colour literal in a declaration's value is refused (`BlockTypeDefinition.colour_literal?`: a hex colour, a colour function, `color(` included, also inside a `color-mix()`, and a named colour; a selector, a comment, a string, a `url()` and a custom property's name are not read; decision 3). **Its template uses the theme's colour utilities only** (`text-ink`, `bg-surface`, `border-line` and the rest of the `@theme inline` mapping of the shared tokens), never Tailwind's own palette, for the same reason: on the site a block follows the theme (the owner's answer 1). That is a promise without a guard in step 1: the gem's component folder is scanned, so `text-red-600` in its template is built from Tailwind's whole palette and nothing refuses it, and an `@apply` of such a utility in its stylesheet (`.x { @apply text-red-600; }`) is no declaration value the colour guard reads; a guard for both is a roadmap item of step 2. Its tokens, its template and its stylesheet join the theme contract and the build as a built-in's do (`docs/reference/theming.md`, "An outside type's lines").
- **Its template: no guard.** `Theme::Check` refuses `cache`, `params`, `request`, `cookies`, `session` and `flash` in a THEME's template; the gem's own default template runs in the same public request and is not checked (as the CMS's own public templates are not). The public site's cookie wall still holds whatever it calls.
- **The tile:** a `summary` that raises, or answers a part of no known kind, draws the type's label on the tile and is logged once per registration, by the type's name and the error's class, never the block's content (`Admin::EditorScreen::TileSummaryComponent#own_summary`); a built-in's raises.

**A block of a type that is no longer registered is dormant** (decision 13): the public page skips it with a log line (a dormant section's inner blocks are drawn), the editor shows its card as "Unavailable type — gallery/album" with only Delete and the tile marks it, the picker does not offer it, saving it is refused, and removing a gem moves no published copy. A theme that still replaces its template is refused by the check (the owner's answer 3).

The test fixture is `gallery/album` (`test/fixtures/block_types/gallery/`, registered through the hook by `with_gallery_album`, `test/support/gallery_album.rb`); `test/lib/content_spiel/plugins_test.rb` holds the hook, and `test/lib/production_boot_test.rb` boots production with a hook that raises (`test/fixtures/block_types/bad_hook.rb`, loaded through `RUBYOPT`): the boot stops and names the hook's file and line. **Not built (step 2):** installing a gem into a site's image (the `Dockerfile` freezes the bundle), an engine's public and editor scripts (its import map and controllers), the stylesheet stamp covering the registered types' stylesheets, the set of outside types in the public ETag (a fingerprint of their names and versions or of their templates and stylesheets, beside the theme's: an image rebuilt with a gem added or removed on the same CMS revision would otherwise have a 304 confirm a page drawn with the old set), and a fixture engine loaded in a child process that proves the hook, the build, the check and `theme:new` from outside.

## What the Code block touched

The Code block was the first block type added after the registries were opened and the first to join the theme contract after it was written, and adding it meant writing it into about twenty places by hand. Most of them said nothing the type did not already know, each was a place to forget, and a gem could reach none of them. The block types build (`docs/superpowers/specs/2026-10-13-block-types-declare-what-they-bring-design.md`, whose "As built" lists where the code left it) made each place that only repeated the type a declaration of the type or a list derived from the registry. Where each went:

| Written by hand for the Code block | Now |
|---|---|
| its line in `config/initializers/types.rb` | still a line, which the generator writes above its marker |
| its component's line in the contract's constant list of components | `t.theme_methods`, read by `Theme::Contract.components`; and a line of the ledger |
| its seven `syn-*` names in the contract's constant list of themed tokens | `t.tokens themed:`, read by `Theme::Contract.themed_tokens`; and lines of the ledger |
| `@import "./code.css";` in the default theme's `theme.css` | `t.stylesheet "code.css"`, imported by the public stylesheet's generated entry after `theme.css` (`BlockTypes.theme_css_blocks`); the built stylesheet is the same bytes |
| `code.css` in the contract test's list of stylesheets that hold no colour | derived: the default theme's files and every type's declared stylesheet |
| the capability `:code`, its check of three fields in `finalize!`, and the tile's branch on it (`code_line`) | `t.summary`, `BlockTypes::Code.summary`; the capability is gone (decision 9), and a capability the CMS does not know is refused at registration |
| `admin--editor--code-limit#update` in the held form's constant allow-list | `t.read_only_actions`, read by `HeldFields.allowed_actions` |
| its row in the canary, and the scaffold test's ERB row on `/wide` with the words checked there | `t.sample`, built by every shared test (`test/support/block_samples.rb`); the sample is the scaffold row's values byte for byte, with the canary's captions in three languages |
| the built-in names written in `built_in_types_test.rb`, `content_block_test.rb`, `plugins_test.rb` and the two reload tests of `theme_pages_test.rb` | derived: `BlockTypes.built_in_names`, `BuiltInBlockTypes.names` (the initializer's lines, `test/support/built_in_block_types.rb`), and the names before a reload |
| the `@import` assertion in `design_tokens_test.rb` | derived: the entry imports every registered stylesheet once |
| its rows in the tables of `docs/reference/theming.md` | still by hand, held to the ledger (`test/lib/theming_reference_test.rb`) |

What stays per type is what is the type's own: its component's tests, its contrast pairs, its scripts and their browser files, a translated value's path through the translation state where it does something a sample does not show, the fixture theme and the reference's section. The recipe below is the Code block's walk-through as it reads now; the incidents behind its rules are in the Code block's own section above.

## Adding a block type

A built-in block type is one definition and the files Rails puts beside it (decision 15: no folder per type): the generator writes them, the definition declares what the type brings, and every list that only repeated that is derived from the registry. The steps are in the order a person takes them, each with the test it needs and the guard that is red until it is done. The Code block (`app/models/block_types/code.rb`) is the type that uses every declaration; the Image block (`app/models/block_types/image.rb`, `app/components/blocks/image_component.rb`) is the plain one to read beside it. A type from a gem is "Block types from outside" above; its generator is step 2's.

**0. Decide where each value is stored.** A value that is the same in every language of the site is a field of the block's `settings` jsonb; a value that is translated is a field with `translated: true` (stored in `translated_settings`) or one of the block's existing translated columns (`caption`, `alt`, `body`), which the type names with `t.uses`. The Code block's code, language and file name are settings and its caption is the `caption` column, so it added **no column, no migration and no service**. A new column on `content_blocks` would have to be placed in exactly one of the published copy, the rows and never stored (`test/models/publishing_test.rb`: "every column of content_blocks is in exactly one of the copy, the rows and never stored") and, where it is content, in `Publishing::Changes::BLOCK_CONTENT`, and `uses` would have to learn it (`BlockTypeDefinition::COLUMNS`); a type that needs a write of its own would need an `ApplicationService` with its entry in `EXPECTED_SERVICES`. Neither was needed, and both are reasons to stay in `settings`.

**1. Generate.** `bin/rails generate block_type <name>` (`lib/generators/block_type/`, Rails' place for a generator; `autoload_lib` ignores `lib/generators`). The name is lowercase words joined by underscores; an `owner/name` is refused, since an outside type is an engine's and its generator is not built. A name is refused, with nothing written, for what it would collide with too: a constant of the application (`post`, `tag`, `blocks`, `content_model`: the type's module `BlockTypes::Post` would be what a bare `Post` written inside `module BlockTypes` means, the shadowing "Never define `Admin::Media`" in `CLAUDE.md` describes), a block type that exists (`code`), a stylesheet of the default theme (`tokens`, `prose`, `theme`, `sections`), a file it would write that exists, a name that does not come back from its class name (`x_2` is `X2`, which is `x2`), and a word YAML reads as true, false or nil (`on`, `no`, `null`) (`test/lib/generators/block_type_generator_test.rb`: "a name with an owner, and one that is no type name, are refused", "a constant of the application, a block type, a stylesheet of the default theme and files that exist are refused, and nothing is written"). It writes a sound type of one translated `:text` field:

| File | What it holds |
|---|---|
| `app/models/block_types/<name>.rb` | `BlockTypes::<Name>.register` with its label, the field, the component, `theme_methods :block, :page`, `stylesheet "<name>.css"` and a sample whose text is in `shows` |
| `config/initializers/types.rb` | `BlockTypes::<Name>.register`, after the last built-in, above the marker line |
| `app/components/blocks/<name>_component.rb` and `.html.erb` | `initialize(block:, page:)`, `render?` false for an empty block, the outer element `content-block content-block--<name>` |
| `app/assets/tailwind/themes/default/<name>.css` | an empty rule under `.content-block--<name>`, with the comment that every colour is a token |
| `config/locales/public.en.yml`, `config/locales/admin/editor_screen.en.yml` | an empty `<name>:` scope under `public.blocks` and under the tile's `types`, below each file's marker line |
| `test/components/previews/blocks/<name>_component_preview.rb` | a Lookbook preview built from the sample |
| `test/models/block_types/<name>_test.rb`, `test/components/blocks/<name>_component_test.rb` | the declaration; the markup from the sample, nothing for an empty block, text that looks like markup is text |

The three inserted lines go beside marker lines (`BlockTypeGenerator::TYPES_MARKER`, `PUBLIC_MARKER`, `TILE_MARKER`), each held equal to a line that stands once in its file (`test/lib/generators/block_type_generator_test.rb`: "the markers are the files' own lines, character for character"); a locale file without its marker gets nothing, and the generator says where to write the scope by hand ("a locale file without its marker gets nothing, and the generator says so"). `bin/rails destroy block_type <name>` takes back everything it wrote, the inserted lines included ("destroy takes back every file and every line the generator wrote"), and only for a type whose definition, and stylesheet, still carry the line `Written by bin/rails generate block_type` (`BlockTypeGenerator::GENERATED`), which the generated files say to take out once the type is yours: `destroy block_type code` or `tokens` removes nothing ("destroy refuses a built-in, a stylesheet of the default theme, a constant and a type that is no longer the generator's, and removes nothing"). A scope that has been filled is not `<name>: {}` any more, and destroy leaves it in its locale file. What it writes is a type the suite takes in as it is: "a generated type registers, joins the contract and the shared samples, and its sample draws its words" generates into a temporary folder and registers the type in the test process (the whole suite cannot run in-process), and the whole suite was run by hand with a generated type in the working tree when the generator was built. **Red until step 9:** the ledger test of `test/values/theme/contract_ledger_test.rb` ("the built-in types' part of the contract is the ledger"), which names `blocks/<name>_component`, and nothing else (its self-test, "the ledger can fail", compares the ledger's own components and stays green). A definition written without the generator, or without its line in the initializer, is red in `test/models/built_in_types_test.rb` ("built-ins are registered": every file of `app/models/block_types` is registered by exactly one line of the initializer, and `BlockTypes.built_in_names` is those lines in their order, the picker's). A built-in's module is its name camelized (`post_list` is `BlockTypes::PostList`): that is how `built_in_names` knows a built-in from a test's bare type.

**2. Fill the definition.**

```ruby
BlockTypes.register :code do |t|
  t.label "Code"
  t.field :language, :select, options: CodeHighlight::LANGUAGES, blank: "Plain text"
  t.field :filename, :string, label: "File name"
  t.field :code, :code, max: CodeHighlight::MAX_CHARACTERS
  t.uses :caption
  t.component Blocks::CodeComponent
  t.theme_methods :block, :page, :lines, :code, :language, :language_label, :filename, :caption, :string
  t.tokens themed: %w[syn-comment syn-keyword syn-string syn-constant syn-tag syn-attribute syn-embed]
  t.stylesheet "code.css"
  t.summary ->(block, locale:) { Code.summary(block, locale: locale) }
  t.read_only_actions "admin--editor--code-limit#update"
  t.sample settings: { "language" => "erb", "filename" => "show.html.erb", "code" => "<p class=\"a\"><%= 1 %></p>\n<%# note %>" },
           translations: { "en" => { caption: "A template" }, "de" => { caption: "Code caption de" }, "es" => { caption: "Code caption es" } },
           shows: [ "show.html.erb", %(<span class="syn-embed">), "A template" ]
end
```

- A field's type is one of `ContentModel::Definition::SCALAR_TYPES` (`string`, `text`, `code`, `integer`, `boolean`, `date`, `url`, `select`, `content_type`, `tag`) or `group` / `groups`; its options are `required`, `default`, `min`, `max`, `translated`, `options`, `of`, `blank` and `label` (`OPTIONS`; anything else is refused at registration).
- **Require nothing unless the block is useless without it.** The picker creates an empty block first, so a required field is an error on a block nobody has typed into yet. The Code block requires nothing and its public component draws nothing until there is code.
- **`uses` names `body`, `caption`, `alt` and `image` and no other** (`BlockTypeDefinition::COLUMNS`): the card draws and the save services write those four, and a fifth name was once silently drawn as nothing (`test/models/content_model/block_type_definition_test.rb`: "uses outside body, caption, alt and image is refused").
- **A capability is how other code asks about the type**, never its name, and there are two, `:container` and `:lists_posts` (`BlockTypeDefinition::CAPABILITIES`), each checked in `finalize!` for what it promises (a container's `columns`, a listing's `content_type` and `tag` fields). A capability nothing asks for is refused at registration ("a capability the CMS does not know is refused at registration, naming the type and the capability"): what only the type itself can answer is a declaration, as the Code block's tile line, once the capability `:code` and a branch of the tile, is its `summary` now.
- **The six declarations** (block types spec, decision 1). Each is read by one list that once repeated it by hand, and each is refused at registration when it has the wrong shape, the type's name first in the message (`block_type_definition_test.rb`: "a declaration of the wrong shape is refused when it is written, and the message says the shape", "every refusal starts with the type's name, also when the type is registered"):

  | Declaration | What it says | Read by |
  |---|---|---|
  | `theme_methods :block, :page, …` (required) | the methods the type's public template may call | `Theme::Contract.components`: the type's line, which makes its template replaceable by a theme and copied by `theme:new` (step 5, step 9) |
  | `tokens themed: [], fixed: []` | the `--th-` tokens it brings, without the prefix: a themed one has a light and a dark value, a fixed one a value | `Theme::Contract.themed_tokens`, `.fixed_tokens`, `.tokens` (and so `theme:new`'s stylesheet comment) |
  | `stylesheet "<name>.css"` | its public stylesheet, a path in the default theme's folder (an outside type's is absolute) | `BlockTypes.theme_css_blocks`, which hands the build its entry's imports and the watch its files |
  | `summary ->(block, locale:) { … }` | its line on a closed block's tile, as parts | `Admin::EditorScreen::TileSummaryComponent` (step 8) |
  | `read_only_actions "identifier#method"` | its editor script's actions that only read or move the focus | `Admin::EditorScreen::HeldFields.allowed_actions` and `.rules` (step 8) |
  | `sample settings:, translations:, body:, image:, shows:` (required) | one filled block of itself | `test/support/block_samples.rb`, and through it every shared test |

  `finalize!` refuses a block type without `theme_methods` or a `sample` ("a block type without theme methods or a sample is refused, and the message says what to declare"; `test/values/theme/contract_test.rb`: "a block type registered without theme methods is refused at registration, and the message says what to declare"), a test's own type included (`TestTypes.declare(t)` gives one both).
- **The sample** (decision 14; `BlockTypeDefinition::Sample`): `settings` (string keys), `translations` (locale to values, `"en"` at least: translated schema fields and the `caption` and `alt` columns), `body` (Markdown, written in the default language), `image: true` (the shared test attaches a new library image) and `shows`, the texts the public page holds for the block. A container's sample holds no blocks: `sample_every_type` puts one sample of every other type in its first column. **A sample fills every column its type uses and every field of its schema** (`test/integration/block_samples_test.rb`: "a sample fills every column its type uses and every field of its schema, and names at least one text the public page shows"), or the field is named in that test's `UNFILLED_FIELDS` with the reason another test covers it (today Post list's `tag`, which the canary's own listing row fills), because a sample that left the caption empty would let the canary pass while no caption is ever compared. Choose its values as carefully as a hand-written row was chosen: they are what the canary and the scaffold compare. The Code block's is the scaffold's old ERB row byte for byte (code that looks like markup, which only the `syn-embed` path draws) with a caption in each of the three languages, which the canary reads in each. A `shows` that is one of the sample's values proves the value is drawn and is gone once the rows are overwritten and published; one that is a class name (`content-block--post-list`) proves only that the block is drawn.
- **`read_only_actions` is a promise read by review.** The definition refuses only a shape that is not `identifier#method`, and `test/components/admin/editor_screen/held_fields_test.rb` checks that each is a method of a controller file ("the allow-list is the CMS's four and every type's declared read-only actions, each a method of a controller file"). Whether the action only reads is the reviewer's to decide: one that writes, on that list, writes from a form someone else holds.
- Tests: the generator's `test/models/block_types/<name>_test.rb` for the fields (nothing required, what is translated), or a case in `test/models/built_in_types_test.rb` beside the others for a type whose declarations say more ("code is a block of three settings and a caption, none of them required, the code never translated"). If the new type's name is one a test used as its invented example, that test is red too: the contract test's invented type is `marquee` for that reason.

**3. A new field type, only if no existing one stores the value rightly.** The Code block needed one, because `:text` strips its value. A field type is five places:

- `ContentModel::Definition::SCALAR_TYPES`, and in `Definition#field` whatever the type refuses (`:code` refuses `translated: true`);
- `ContentModel::FieldSet#cast` (how a submitted value becomes the stored one: `cast_code`) and the validation (`:too_long` over `max:`);
- an input, `Admin::Fields::<Type>Field` in `app/components/admin/fields/`, which `Admin::Ui::FieldComponent#input_component` finds by the type's name, so there is no list to add it to;
- `Admin::EditorScreen::SharedFieldsComponent.display`, for how the value is shown read-only on a translation tab;
- a decision about `Admin::Ui::FieldComponent::TRANSLATABLE_TYPES`: a type listed there is offered to the AI translation when a field of it is translated.

Tests: `test/models/content_model/code_field_test.rb` (the cast, the limit, the refusals), `test/components/admin/fields/code_field_test.rb` (the input's markup), a case in `test/components/admin/editor_screen/shared_fields_component_test.rb` and one in `test/components/admin/ui/field_component_test.rb`. A new OPTION (`blank:`, `label:`) is a name in `OPTIONS`, its refusal in `Definition#field`, and every reader of it: for `label:` that was every place that had written `field.name.humanize` for itself (the list is in "Three things the schema learned for it" above). The block samples card test then draws a control for a field of the new type from any sample that fills one ("every type's card draws a control for each field of its schema, and its held form keeps every name and value").

**4. What the block needs that is no component's business** goes in a value object or a query, never in the component. The Code block's is `CodeHighlight` (`app/values/code_highlight.rb`, with `test/values/code_highlight_test.rb`): it answers data, and the component and its template decide the markup. A tile line that needs a computation is a module method of the type (`BlockTypes::Code.summary`, `BlockTypes::PostList.summary`), which answers parts and names no component. A new top-level name under `app/values`, `app/models`, `app/queries` or `app/services` is from that day a name `Admin::` may not define (`test/lib/admin_namespace_shadow_test.rb` derives its list from the directories), and it may reference no component, helper or controller (`test/lib/dependency_direction_test.rb`). A gem it needs gets its own line in the `Gemfile`, also when the bundle already holds it through a development gem, and `bin/bundler-audit` is run.

**5. The public component, its template, its stylesheet and its tokens.**

- `app/components/blocks/<name>_component.rb`, an `ApplicationComponent` with `initialize(block:, page:)` (that is how `ThemeHelper#render_block` builds every block's component), reading the block it is handed and nothing else: on the site that is a published view, in a preview the rows. `render?` is false for a block with nothing to draw.
- **Every method the template calls is a promise to themes**, and `theme_methods` names each: a theme's template may call exactly those (`test/values/theme/contract_test.rb`: "a default component template calls no method of its component that its line does not name", "every listed component has its default template and every method its template may call"). So the component's private readers are few and each answers for an empty block, and a helper that only this template's layout needs is written in the template: the Code block's line was eleven names for one review and is nine ("Two helpers taken back" above).
- The template prints whatever a person typed through ERB's own escaping. The outer element carries `content-block content-block--<name>`.
- The stylesheet, `app/assets/tailwind/themes/default/<name>.css`, declared with `t.stylesheet "<name>.css"`: the public stylesheet's generated entry imports the default theme's `theme.css` first, then every declared stylesheet once in registration order, then a theme's (`test/lib/theme_css_test.rb`: "the entry imports the default theme, each registered stylesheet once in registration order, then the theme's, and scans an outside component's folder"; `test/integration/design_tokens_test.rb`: "the public stylesheet's entry imports every registered type's stylesheet once, and the default theme's file imports none that a type declares"). Colours come from `--th-*` tokens only (`contract_test.rb`: "the default theme's styles and templates hold no colour literal: tokens.css is the one place", which reads every declared stylesheet). Plain rules where a class is built from data and no utility scan would find it. A band of a section re-values tokens for whatever is inside it, so the block needs no rule for a band; check it on a tinted and a strong band all the same. `theme_css:watch` reads the types once when it starts, so a new stylesheet needs `bin/dev` started again.
- **Its tokens follow the theme** (decision 3, the owner's answer 1): on the site a block is drawn in the theme's look. A built-in's names are in `t.tokens`, its values in both blocks of `app/assets/tailwind/themes/default/tokens.css` (the one place a colour literal is written), defined from the theme's base tokens (`var(--th-accent)`, `color-mix()` of `--th-ink` and `--th-surface`, …) wherever a base token is right, so a theme that re-colours its base re-colours the block, and a literal only where none is (the seven syntax colours); what a strong band makes of them goes in `sections.css` ("every declared token is defined, a themed one for light and for dark, and no --th- name is undeclared"). **A token's name is a promise from the day it ships**; a renamed one is a release note and a line of the ledger (step 9).
- Contrast of every new pair on every ground the block can stand on (the page, a tinted band, a strong band) in both schemes, computed in `test/integration/design_tokens_test.rb` ("every syntax colour is readable on every ground a code block has: the page, a tinted band and a strong band, in both themes").
- The Lookbook preview the generator wrote, built from the sample, beside the other blocks' in `test/components/previews/blocks/`.
- Tests: the component test the generator started (`test/components/blocks/<name>_component_test.rb`: the markup, nothing for an empty block, text that looks like markup, the caption's fallback); cases in `test/integration/public_blocks_test.rb` for what the type does that its sample does not show; and its stylesheet's rules in `design_tokens_test.rb`. **No row is added** to the canary, the scaffold's byte-for-byte page or a smoke test: they build the sample (step 2, and "What the shared tests build" below).

**6. Strings.**

- A word the public template says that no editor typed is a key in `config/locales/public.en.yml` under `public.blocks.<name>` (the generator made the empty scope), read in the visitor's language with English as the explicit fallback (`Blocks::CodeComponent#string`; `docs/reference/i18n.md`, "A string of the public site"). A word a script writes is handed to it by the server as a value, so the script holds no English.
- A string of CS Studio is a key in the one locale file of its component's folder (`config/locales/admin/fields.en.yml` for `app/components/admin/fields/`, `editor_screen.en.yml` for the card and the tile, whose words for a type's `summary` are under `tile_summary.types.<name>`, the scope the generator made), read with `t(".key")`; a script reads it from the element's `data-messages`. **Guards:** `test/lib/source_layout_test.rb` ("every relative translation key an admin component reads exists", "a locale file of admin components holds one folder's scope, in its own language", "a component scope has keys in one locale file per language, except where an exception names it, and names a folder"), and the new files join `CONVERTED` in `test/lib/admin_i18n_test.rb`, which then holds them free of English.
- The type's label, a select's choices, `blank:` and `label:` are literals in the definition, as every type's are today (`docs/reference/i18n.md`, "Out of scope, named").

**7. A script on the public site, if the block has behaviour.** A controller at the top level of `app/javascript/controllers/` (`code_copy_controller.js`, identifier `code-copy`), which every public page registers; nothing under `controllers/admin/` reaches a public page. It must work as progressive enhancement (the markup is whole without it; what only the script can make work is `hidden` in the markup and shown at `connect`), take back at `disconnect` whatever it wrote into the page, and at `turbo:before-cache` take back words but leave `hidden` alone ("The copy script" above has both incidents). Keep an element it needs in `disconnect` as a field: a target is not found any more once the controller is taken off its element. Tests: a case in `test/integration/public_javascript_test.rb` ("a public page with a Code block carries the copy controller and no admin script") and a browser file, `test/system/<name>_block_test.rb`; a system test fails on any JavaScript error, which is what caught the missing target. A script is no declaration: a built-in's controller is found by its place, and an engine's scripts are step 2.

**8. The editor.**

- **The card needs nothing** for a type made of schema fields and the columns it uses: `Admin::EditorScreen::BlockCardComponent` draws each field with `Admin::Ui::FieldComponent` in the order the type declares them, then the columns. What the Code block changed in it was one assumption that had only ever met the Image block, that a caption is an override of a library image's text (`caption_options`); a test pins the Image block's card as it was.
