# Content blocks and content types

> Describes: `app/models/content_block.rb`, `app/models/content_types/`, `app/models/block_types/`, `app/models/content_model/`, `app/values/block_outline.rb`, `app/services/content_blocks/`, `app/components/admin/block_*`, `app/components/admin/editor_screen/section_*` (and the tile, panel-title, move-dialog and delete-dialog components beside them), `app/components/blocks/section_component.rb`, `app/controllers/admin/content_blocks_controller.rb`, `app/javascript/controllers/admin/blocks_controller.js`, `app/javascript/controllers/admin/section_controller.js`, `app/assets/tailwind/themes/default/sections.css`.

## Content blocks

`ContentBlock` (`app/models/content_block.rb`) is one polymorphic-by-enum table (`block_type`: `rich_text` / `image` / `post_list` / `section`) belonging to a `Page`, ordered by `position` within its container (the page's own list, or one column of one section — see "Sections" below), edited in CS Studio as block cards, each its own autosaving form (see "Blocks" below). `Post` uses the same single-model-plus-enum shape for its own `content_type` (`blog` / `resume_entry` / `now_update`). A `post_list` block's `settings` jsonb names a `content_type` filter, a `tag`, and a `limit`; `listed_posts` is the canonical query both the listing partial and the permalink-resolution fallback in `PagesController` must agree on. A post's typed fields (`Post#fields`) name themselves in words wherever an error shows — `Post.human_attribute_name` turns `fields.speakers.0.name` into "Speakers, row 1: name" (without I18n lookup, so the German admin UI will need to revisit it) — and a typed date must be `yyyy-mm-dd` (`ContentModel::FieldSet::DATE_FORMAT`): free text that doesn't parse is *refused* on the field rather than silently wiping the stored date.

## Blocks in CS Studio

**Blocks.** `Admin::BlockCardComponent`: a drag handle, the type name (a button that collapses the card), and a ⋯ `Admin::MenuComponent` (Move up, Move down, "Move into section…", Duplicate, a divider, "Delete block…"); `admin--blocks#refreshMoveState` keeps the move items right after every move, add and delete. A block whose stored type isn't registered any more is the minimal "Unavailable type" card (danger border, "Delete block…" its only action). There is one dashed "+ Add block" row at the end of the list (`Admin::BlockPickerComponent`: a `button_to` per registered type POSTing to `create`); Duplicate is what inserts below a block. In a section each lane ends with the same picker as a "+" menu (`section:`, `column:`), without the container types: it posts `section_id` and `column`, and `create` answers with the block's form and tile (the form marked `data-open`, which `admin--section` opens at once) and the section's count, or, refused, with the message and the lanes as they are now. A post-list block's Type, Tag and Limit share one row, Tag being a one-value chip input. The block's "Delete this block?" dialog is `Admin::EditorScreen::DeleteBlockDialogComponent`, one per block, drawn inside the element that stands for the block (its card, or its tile in a section).

## Sections

A section is a block that holds blocks: it arranges ordinary blocks in columns and gives them a band with a background and a width. It is the one container type, one level deep, on pages only. The design is `docs/superpowers/specs/2026-10-08-sections-layout-design.md`, whose "As built" part lists where the code left it.

**The data.** `content_blocks` has `section_id` (a nullable reference to `content_blocks`) and `section_column` (a nullable integer, 1-based); both are null for a top-level block. Two check constraints keep the pair together (`content_blocks_section_and_column_together`) and the column from 1 (`content_blocks_section_column_from_one`), and the index is `(section_id, section_column, position)`. The foreign key is the default NO ACTION, for the reason the keys to library images are (`docs/reference/media.md`: Postgres 18 reports a RESTRICT violation as SQLSTATE 23001, which Rails does not map to `ActiveRecord::InvalidForeignKey`): a section that still holds a block cannot be deleted around the service, and nothing cascades. `position` is counted per container — the page's top-level blocks among themselves, the blocks of one column of one section among themselves — so `position` alone never says where a block is on the page. **A block in a section still belongs to the page:** its `owner` is the page, `section_id` and `section_column` only place it, and `page.content_blocks` is every block of the page. That is why permissions (`ContentBlocks::OwnerPermissions`, the "editing a published page needs `publish`" rule), autosave with `base_updated_at`, translation tracking, the image foreign key, `media_usages` and a listing's `public_paths` read the same for a block in a column as for one outside (`test/services/translation_state_parity_test.rb`, `test/models/media/usage_index_test.rb`, `test/models/public_site/paths_test.rb` each have a case in a column). A section has no translatable content and adds nothing to `translation_states`. `ContentBlock.top_level` is the page's own list and `ContentBlock.in_column(section, column)` one container (`nil, nil` is the top level); `ContentBlock#section_blocks` is a section's blocks ordered by column, position and id, with no `dependent:` on purpose.

**The type.** `BlockTypes::Section` (`app/models/block_types/section.rb`) registers `section` with three select fields: `layout` (`LAYOUTS`: `one`, `two`, `three`, `four`, `one_two`, `two_one`, each mapped to its columns' weights — `one_two` is `[1, 2]`), `background` (`BACKGROUNDS`: `none`, `tinted`, `strong`) and `width` (`WIDTHS`: `content`, `full`); the defaults are `two`, `none`, `content`, and `BlockTypes::Section.weights` reads an unknown stored layout as the default. It declares the capability `:container` and `columns`, a callable on the definition (`ContentModel::BlockTypeDefinition`, `dsl_attribute :columns`) that takes a block's `settings` and answers how many columns it has; `finalize!` refuses a container type registered without it. **Code asks `ContentBlock#container?` (the capability) and `#column_count` (the definition's `columns`; 0 for a block that holds nothing and for a section whose type is gone), never `block_type == "section"`:** a container type a plugin registers is then a section everywhere, and the markup's word for the same thing is `data-container`.

**The rules the model enforces** (`ContentBlock#section_rules`): a top-level block names no column; a container never sits in a container; the section exists, is a container and is on the block's own page; the column is one of the section's layout. They run only for a new record or when `section_id`, `section_column` or `block_type` changed, because a block inside a section whose type is no longer registered fails every one of them and must still be editable until someone moves it out (`test/models/content_block_test.rb`, "a block in a section whose type is gone still saves").

**Display order comes from `BlockOutline`** (`app/values/block_outline.rb`), never from `position` alone. Built from a page's blocks already loaded, it costs no query and answers `top_level` (by position), `columns(section)` (one array per column of the layout, an empty column keeping its place; a block stored beyond the last column is left out of these and still in `blocks_in`), `blocks_in(section)` (reading order: column by column, each by position) and `reading_order` (each top-level block followed by the blocks in it). It also sets each block's `section` association from the same array, so `block.section` is no query afterwards. Its users: the public page (`ThemeHelper#block_outline`, memoised on the view, so **one outline per render** however many sections the page has — `Blocks::SectionComponent#columns` and `render_block` ask that one; `test/integration/public_blocks_test.rb`, "a page builds one outline however many sections it has"), the editor's page view (`app/views/admin/pages/show.html.erb`), every stream of `Admin::ContentBlocksController` that draws a section (`fresh_outline`, read after the action's service wrote), `Blocks::ImageComponent#sizes`, and the audit snapshot of a page, whose `content_block_ids` are in reading order (`Audit::Snapshot`). `test/models/block_outline_test.rb` holds its contract.

**The lock order: the page's row first, then block rows.** Every write to a page's blocks takes the page's row lock before it reads or writes a block row. `ContentBlocks::Structure#lock_owner` (`owner.class.where(id:).lock.pick(:id)`, so the caller's page object is left alone; nil and no query for an owner that is not saved yet) is the first statement of the transaction of `ContentBlocks::Save`, `ContentBlocks::Destroy`, `ContentBlocks::Reorder` and `ContentBlocks::Duplicate` — every call, a top-level block's ordinary autosave and the page's plain reorder included. `Tags::Merge#repoint_blocks` locks the pages of the listing blocks it rewrites, in id order, before it locks those blocks; `Trash::Purge#purge_branch` locks the branch's pages, in id order, before the first block is destroyed. There are two reasons. What a structural write judges must be what the other writer committed: a fold to two columns and an add into column three, started together, would otherwise both pass their checks and leave a block in a column the section no longer has. And there must be one order: a section's fold, its lift ("keep blocks") and the renumbering after a delete or a move write *other* blocks' rows — the blocks in the section, and for a lift and a renumbering the top-level blocks around it — while holding the page's row. A block save used to take its own row first and the page's row afterwards, at `owner.touch`; the reorder, the tag merge and a page's destroy went block-first too. Any such writer on the same page and a fold or a lift could each hold what the other waits for, and Postgres ends one with `ActiveRecord::Deadlocked`. An earlier version exempted top-level blocks ("no structural write touches one"), which was wrong for exactly the lift and the renumbering, so no save is exempt. It costs one short `SELECT … FOR UPDATE` per block write and no new waiting, since the transaction always took that row at the touch. **A new service that writes `content_blocks` rows and the `pages` row in one transaction takes the page first.** What shows it: tests that read the statements with `capture_sql` and assert the page's lock comes before the first block statement — in `test/services/content_blocks/save_test.rb`, `destroy_test.rb`, `reorder_test.rb` and `duplicate_test.rb`, `test/services/tags/merge_test.rb` ("the pages of the blocks it repoints are locked, in id order, before any block row is locked or written") and `test/services/trash/purge_test.rb` ("the branch's pages are locked, in id order, before the first block is deleted"). What is not covered: the order is proven by statement order, and the outcomes of two tabs by running the two writes one after the other, not by a test with two database connections; `Translations::Confirm` writes one block row's `translation_sources` without the page lock (it takes no page row afterwards, so it closes no cycle); a purge's sibling renumbering (closure_tree's `_ct_reorder_siblings`) updates page rows outside the id-ordered lock, which leaves a narrow merge-against-purge deadlock and one between two purges of sibling pages; and a block create that waits on the lock of a page which is then purged goes on to write a block whose owner is gone, because `lock_owner`'s nil answer is not checked and the polymorphic owner has no foreign key. Each of those is a roadmap row.

**The services.** No controller writes a block; `test/support/service_calls.rb` has the factory for each.
- *Create into a column.* `ContentBlocks::Save` reads `section_id` and `section_column` from `attributes` **for a new block only** and appends it to the end of that column (`assign_position` counts within the container). For a block that exists both keys are ignored: a form that echoes them back must not move anything.
- *The fold.* Saving a section with a layout of fewer columns moves the blocks of each removed column to the end of the last remaining one, in column order, inside the save's transaction (`Save#fold_removed_columns`); a layout change never deletes a block. Two things about it are deliberate. The section is re-read from its row after the lock is taken (`reread_container`), because a second tab's copy may say "two" where the row has since been widened to "four", and assigning "two" to that copy would look like no change. And the fold is decided **from the rows** — every save of a container asks which blocks sit in a column beyond its layout — not from comparing the layout before and after on the caller's object, which the same stale copy would get wrong and strand a block. The stale-save 409 is not weakened by the re-read: it runs in the controller before the service is called.
- *Reorder and move.* `ContentBlocks::Reorder.call(page, ordered_ids, section:, column:, moved_from:)` writes the complete new order of **one container**: `section` and `column` name it (both nil for the page's list). An id in the order that sits in another container is moved here only if `moved_from` (`{ block id => { section_id:, column: } }`, blank for the top level) says where the caller believes it is and it is there; each container a block left is closed up (`Structure#renumber`). It writes with `update_columns`, so a moved block's `updated_at` — its autosave base — does not move. Its refusals write nothing: `STALE` (a block is not where the screen has it, arrived unannounced, is named twice or is missing from the order), `NO_COLUMN` (the section is gone or not a container, or has no such column — which includes every column of a section whose type is gone), `NESTED` (a container among the blocks moved into a column), and `NOT_THE_LIST`, the two-argument call's own refusal as it always read. Everything is looked up among the page's own blocks, so a stranger's id is not found and never moved in. **A block changes container only through this service.**
- *Both deletes of a section.* `ContentBlocks::Destroy.call(block, keep_blocks: false)`: with its blocks (each destroyed first, with its own callbacks), or `keep_blocks: true`, which lifts them to the top level at the section's place in reading order (`Destroy#lift`) before the section goes. What a block holds is read from the rows under the lock, not asked of the type, so a section whose type is gone is deleted or lifted like any other instead of running into the foreign key. `Page` has the same problem on its own destroy — `dependent: :destroy` goes in `position` order and would reach a section before the blocks in it — so a `before_destroy` declared ahead of the association destroys the blocks in sections first (`test/models/content_block_test.rb`, "destroying a page destroys the blocks in its sections first").
- *Duplicate.* `ContentBlocks::Duplicate` copies one block directly after its source in the source's container, and for a section every block in it into the same columns in the same order. Every copy is saved through `ContentBlocks::Save` (so the image-choice rule, the usage rows and the translation state are decided in one place) and placed by `ContentBlocks::Reorder`; the source and the blocks in it are re-read under the lock, and a source deleted meanwhile is the failure `Duplicate::GONE`. A copy refused part-way rolls everything back.

**The parameters of the controller.** `Admin::ContentBlocksController#reorder` takes `ids` (the container's complete order), `section_id` and `column` (absent for the page's list) and `moved_from[<id>][section_id]` / `[column]`; `admin--blocks` sends them as JSON. Every one is read through `one_value`, `ordered_ids_param` or `moved_from_param`: a forged array or hash where one id belongs (`section_id[]=1`, `column[a]=1`, `moved_from[x][section_id][]=`) is read as not sent and answered with the service's refusal, never a 500 (`test/integration/admin/content_blocks_test.rb`, "a forged reorder whose section, column, ids or origin is not one value is answered, never an error"). `create` takes `section_id` and `column` beside `params[:block]`, and `destroy` takes `keep_blocks`. The section is looked up among the page's blocks, so another page's section is as gone as a deleted one.

**Audit.** There is no new action. A fold is in the section's `block.updated`, whose metadata is `folded_block_ids` — and that save is recorded with `coalesce: false`, an event of its own, because a coalesced extension of an open row leaves its `metadata` as first written and the ids would be lost exactly when someone adjusts a section's look and then its layout (`docs/reference/access-control-and-audit.md`). A section's delete is one `block.deleted` on the section with `deleted_block_ids` or `kept_block_ids`. A move is one `block.reordered` on the page whose `field_changes` are the target container's order before and after and whose metadata is `section_id`, `column` (both absent for the page's list) and `moved_block_ids`; it records where the block went, not where it came from. A duplicated section is several events, a `block.created` per copy and one `block.reordered`, none of which coalesces. A copy refused for want of permission (the image choice needs `media.upload`) had its `access.denied` written inside the transaction that was then rolled back, so `Duplicate` records it once more outside, on the block whose copy was refused.

### Sections in the editor

**The card, the lanes and the tiles.** On the default language's tab a section is `Admin::EditorScreen::SectionCardComponent`: a card of the block list like any other (`data-admin--blocks-target="card"`, the block card's handle and Move up / Move down) marked `data-container`, with `admin--section` on it. Its body is `SectionLanesComponent` — one lane per column, each a list whose **direct children are exactly its tiles** (the column's label and the lane's "+" are the lane's siblings inside an `.admin-section-lane` wrapper, never its children, because a lane's order is read from its children) carrying `data-section-id` and `data-column` — and under the lanes one `Admin::BlockCardComponent` per block drawn as `placement: :panel`. A tile (`BlockTileComponent`) has the block's `dom_id`; its face is a button that opens the block's form, with one line of the block's content (`TileSummaryComponent`, decided from the type's `uses_columns` and capabilities, never its name: an image's file name and thumbnail, the start of a text, a listing's filter) that every autosave answer for a block in a section replaces, marked "Needs fixing" after an invalid save since the error slots are in a form nobody may be looking at. `SectionCardComponent.draws?(block, outline:)` is the one rule for "drawn as a section" (a container, or a block that still holds blocks) and `SectionCardComponent.for` the one door to the card or, on a translation tab, the group; the page view and `Admin::ContentBlocksController#card_for` both go through them, so a card streamed in is the card a page load draws.

**One open form per section, and every form is in the page.** All of a section's block forms are rendered with the page, each in a hidden panel (`Admin::BlockCardComponent.panel_id`, `"block-<id>-panel"`), and `admin--section` only shows one and hides the rest: pressing a tile opens its form under the lanes, headed "Image · column 2" (`PanelTitleComponent`); pressing another closes the first; Escape, the panel's Close and a second press on the open tile close it and give the tile the focus. **Do not fetch the open form, and do not remove a closed one.** A form that never leaves the document registers with the write queue once and keeps its debounce, its queued or in-flight save and its save state (paused by a 409, failed) whether it is showing or not; a design that fetched the form on demand would have to answer what happens to a save whose form has left the document, which is the case the queue's drain exists to guard against. Closing a form tells it to send what it holds at once (`admin--autosave#saveNow`). Which form is open is read from the page — the panel that is not `hidden` — not remembered in the controller, because a section's card moved in the DOM disconnects and reconnects every target, and an id kept beside the DOM was once cleared while its form was still showing. A block just added arrives with its panel marked `data-open` and is opened by the script (the server never renders a panel shown: that would be a second open form). The panel is the same component, the same ids, the same `base_updated_at`, status line and error slots as a card, so `Admin::ContentBlocksController#update` answers a block in a column exactly as one outside, 409 included.

**The helpers a later change needs** (`Admin::ContentBlocksController`). `section_structure_streams(section)` is **the one redraw of a section's lanes**: it replaces the lanes, rewrites the text of every panel's heading (`panel_title_id`) and replaces both counts, from one fresh outline, because three things on screen say which column a block is in and they are brought up to date together or the screen contradicts itself. It never replaces a panel. `section_count_streams` replaces the header's "2 columns · 3 blocks" (`SectionSummaryComponent`) and the delete dialog's count (`SectionDeleteCountComponent`) after an add, a delete, a copy or a move. `tile_streams(block, open:)` appends a new block's panel and then its tile; `copy_tile_streams` puts a copy's tile after its source, unopened. `panel_removal_streams` removes the panel with a deleted tile (left behind it would stay open with no tile to close it from). `move_streams(origins)` draws each block a saved reorder moved between containers in its new shape — a card that went into a column becomes a tile plus a panel, a tile that left its section a card, a tile that changed sections takes its panel along, a tile that changed lanes inside its section has only its panel's heading rewritten — and recounts every section that gained or lost one. **A panel is replaced as a whole only there, when its block changes container**, which is why the browser makes the form safe first (see "Moves").

**The section's own settings** are a form in the card's header, an autosave form with the block card's ids (`Admin::BlockCardComponent.autosave_form_data`, `status_id`, `base_updated_at_id`), answered by the same `update` action: a stale save is a 409 like any block's. Layout is a menu of six diagrams over a hidden input (`SectionLayoutMenuComponent`; a pick is sent at once, `admin--section#chooseLayout`); background and width are selects. The answer replaces the layout menu **only when the stored layout changed** — replaced by a save of the background, the menu's button lost the focus someone had just moved onto it and an open menu was swapped for a closed one — and redraws the lanes (`section_structure_streams`) **only when the number of columns changed**, since a save of the background, the width or a layout with as many columns moves no block and the lanes are tiles a person may be focused on or dragging. The form holds no other form: the menu's Duplicate and "Remove section, keep blocks" are `button_to`s and sit after it. The ⋯ menu: Move up, Move down, Duplicate, "Remove section, keep blocks" (no question asked, `keep_blocks` beside the DELETE; the blocks take the section's place as cards, and because those cards replace the blocks' forms the press goes through `admin--queue-hold`: it waits until the write queue is empty and does not run, with a toast, while any form on the screen ended unclean) and "Delete section and its blocks…", whose dialog says how many blocks go with it. Collapsed, the card is its header line.

**A block's delete dialog is in its tile or its card, never in a panel.** A `<dialog>` inside a `hidden` element is not drawn when opened, so "Delete block…" in a tile's menu would have done nothing while the form was closed. In the element that stands for the block, every answer that removes or redraws that element takes the dialog with it.

**The translation tab.** On any tab but the default language's a section is `SectionGroupComponent`: a heading over the card of each block it holds (`placement: :group`), in reading order, every form open, with no lanes, tiles, hidden panels, settings or `admin--section`. The group stands in the list with the section's `dom_id` and `data-block-id` as a `card` target, because the cards around it are still moved on that tab and the order sent has to name the section; it has no handle and no menu, so structure is edited on the default tab only.

**View only.** A viewer who cannot edit sees the lanes and can open a tile: the form is the disabled one a view-only card shows, with no `admin--autosave`. There is no grip, no ⋯ menu, no "+", and the section's three settings are a disabled fieldset (`test/system/admin/view_only_test.rb`).

**Small screens.** `.admin-section-card` is a container (`container-type: inline-size`), and the lanes sit side by side from 40rem of the *card's* width; below that they stack, each under its column label. The label is `aria-hidden` (a screen reader gets the same words from the lane's `aria-label` at every width). The column count reaches the stylesheet as `--lanes`.

**Unavailable types.** A tile of a type that is no longer registered keeps its four move items and "Delete block…" and has no Duplicate: it keeps its pointer grip, and everything a pointer can do has a keyboard path. A section whose own type is gone is still drawn as a section (`draws?` asks the rows): the "Unavailable type" card with the danger border, no handle, no settings form and no menu, and one button, "Delete block…", which opens the section's delete dialog and deletes the section with the blocks in it. Its blocks are listed under it in **closed lanes** — one per distinct stored column, marked `data-no-drop`, with no "+" — because the server has no column of it to take a block (`NO_COLUMN` for any order of one, including an order of the lane a block is already in). So `admin--blocks#closed` shuts every way in or along: no drop, no sorting, Move up / Move down / "Move to column…" disabled, no choice in the Move dialog, and no Duplicate on its tiles. What is left is "Move out of section" and "Delete block…" on each tile, and opening and editing each form. "Remove section, keep blocks" is not offered on that card although `ContentBlocks::Destroy` honours `keep_blocks` for it.

### Moves

**One sender.** `admin--blocks#move(item, from, before)` is the one sender for a drop, a menu move and the handle's keyboard path; it sends the complete order of the container the element is in now, with `moved_from` when the server has the block elsewhere, through `app/javascript/autosave/queue.js` (`docs/reference/save-rule-and-write-queue.md` has the queue's side). The list and every lane are Sortables of one group; a lane refuses a section's card (`accepts`, as the server answers `NESTED`).

**A move between containers and the block's form.** A saved move between containers is the one time a form on the screen is replaced while its block stays (`move_streams`), so:
- as the move is queued every autosave form of the block list is told to send what it holds (`sendHeldEdits`), which puts those saves ahead of the move; this happens for any move that names a section or changes containers, a move along a lane included;
- when the move's turn comes, the moved block's own form must have ended saved (`formState`). One that did not end clean — paused by a 409, refused, invalid, offline — is **not moved**: everything is put back and a toast says "Reload or fix this block before moving it.";
- a form whose edit is still on its way (typed while its own save was on the wire, so its follow-up is queued behind the move) makes the move **stand back once**: the form is told to send again and the move is queued again behind it; still not saved at that turn, the move is given up like a refused one;
- the queue slot is **held until the answer is drawn** for a move that names a section or changes containers (`streamsApplied` in `autosave/order_request.js`), because Turbo performs a stream a frame after it is handed over and the next queued write would otherwise be sent from the old elements;
- a queued move whose element is no longer where that move put it (put back, dropped again elsewhere, or the screen redrawn) is **dropped**, not sent;
- from the drop until its answer is drawn or it is put back, the moved element and, for a tile, its panel are `inert` (`hold`): grabbed again in that window, the second drag held an element the answer then removed, and words typed into the form went with the form.

**What goes back after a failure.** `restoreTo` is each container's order as the server last took it, kept **per container**: the `before` of the first move since then, not of each (two quick moves queue two requests, and the second's `before` is an order that was never saved); a request that succeeds while another waits makes the order it sent the one to go back to for its own container (`taken`), and after a saved crossing move the redrawn element takes the old one's place in what is remembered (`followRedraw`).

**A refused structural move.** The server answers a refused move that named a section or moved a block (and was not a denial) with the whole list as it is now (`blocks_list_stream`): the screen was behind, and how far is not known. **The browser draws that list only when no autosave form of the block list holds text the server does not have** (`formsHoldText`, asked as the answer arrives, so text typed during the round trip counts). Otherwise the answer is drawn without its list (`renderKeepingForms` stops that one stream at `turbo:before-stream-render`): the block is put back, the alert under the reason gains "Something on this page changed elsewhere. Reload once your unsaved text is safe." and nothing else on the screen changes. A 409 and a refused move have the same cause — a second editor on the page — so they arrive together, and the 409 bar has promised the typed text stays. The cost is that the screen stays behind the server until the reload and further moves may be refused again. The same line is added under any refusal that arrives while a form holds such text, a denial included, although only a structural refusal carries a list.

**Dragging past a section.** `besideSection` (the list's `onMove`): over a section's card the list sorts a dragged block before the section only from above its lanes and after it only from below; level with the lanes it does nothing, and a lane under the pointer takes the block itself. Without it a card dragged up from below jumped above the section the moment it touched its edge, pushing the lane being aimed at out from under the pointer. And a lane that was only *moved* — its section's card dragged or stepped along the list, which Stimulus reports as each lane disconnected and connected again — keeps its Sortable: `Sortable#destroy` ends whatever drag is under way, so destroying the lanes of the card being dragged dropped that card after its first step.

**No Undo for a structural move.** The Undo toast follows only a reorder of the page's own list. Its Undo is a reorder of that list back to the order before, which cannot put a block back into the column it left.

**The keyboard path is the menu.** A card keeps its handle's keyboard path along the list (Space, arrows, Space). A tile's grip is a `<span>` for the pointer only, hidden from a screen reader; its ⋯ menu has every move a drag makes: Move up and Move down along the lane, "Move to column…", "Move out of section" (to the list, directly after the section's card), and a top-level card's menu has "Move into section…". The last and "Move to column…" open **the one Move dialog of the page** (`MoveDialogComponent`), whose `<select>` is rendered empty and filled in the browser as it opens (`admin--blocks#askWhere`) from the sections and lanes on screen — sections are added, removed and given other layouts without any other card being drawn again, so a list the server rendered would be stale; sections are numbered as they stand in the list, and closed lanes are neither offered nor counted. Each menu move makes the DOM move a drop would have made and calls `move`, and is **announced** in the live region the handle's keyboard path speaks in (`block_moves.*` in `config/locales/admin/components.en.yml`: which block, where, its position), with "… is back where it was." when it did not stand. **Focus:** it goes to the moved block at once — a card's handle, a tile's ⋯ button — and stays there for a move along one container. A block that changed containers is `inert` until its answer and so loses the focus; when its turn ends the element that stands for the block then (the redrawn card or tile, or the one put back) takes it, but only if nothing else has the focus by then. After Duplicate the focus goes to the copy; a copied tile is not opened.

### Sections on the public page

**The markup.** `app/views/pages/show.html.erb` walks `block_outline(@page).top_level` through `ThemeHelper#render_block`, and `Blocks::SectionComponent` draws the blocks in its columns through the same helper (so the listing-to-detail swap of a post permalink happens in a column too, and each block is drawn once):

```
section.content-section.content-section--<background>.content-section--<width>
  div.content-section__inner
    div.content-section__grid.content-section__grid--<layout>
      div.content-section__column   (one per column, in reading order)
```

The `<section>` has no accessible name and no heading, so it is a grouping element and not a landmark. Each of the three settings is read against its own list, so an unknown stored value becomes the default and never reaches the class attribute. A block's component does not know it is in a column, with the one exception of an image's `sizes`. A section with no block that draws anything renders nothing (`render?`); an empty column keeps its place while the columns sit side by side and is hidden while they are stacked (the template writes a column's tags closed up so `:empty` matches).

**The layouts and breakpoints** are CSS only (`app/assets/tailwind/themes/default/sections.css`), by container query on the section's own width, not the window's: below 30rem every layout is one column in reading order; from 30rem the columns sit side by side (`one_two` and `two_one` as 1fr/2fr), four of them two by two; from 44rem four are four across. **The container is the `<section>`** and a band's side padding sits on `.content-section__inner`: a query measures the container's content box, and with the padding on the section a tinted band in the 46rem content column would measure 43rem and its four columns could never get past two by two.

**Bands and width.** `tinted` and `strong` paint the band from the tokens `--th-band-tinted` and `--th-band-strong` (`tokens.css`, both themes). **A band re-values the `--th-*` tokens for everything inside it** instead of restyling selectors: the blocks in a band are drawn by components that know nothing of it and colour themselves with the theme's tokens, so a block added later is right without a rule. The strong band sets ink, dim, meta, accent, the lines and the sunken and surface backgrounds from `--th-on-band-strong`, `-dim` and `-accent`; the tinted band sets `--th-meta` to `--th-dim`, because plain meta on the light tinted band is 4.32:1, and `--th-sunken` to `--th-surface` so a code block does not vanish into it. Contrast, computed from the tokens: the strong band's body, dimmed and link colours are 16.7:1, 11.0:1 and 9.9:1 in the light theme and 16.3:1, 8.1:1 and 6.4:1 in the dark; the lowest pair in use anywhere is the dark theme's link on a code block inside a strong band, 4.95:1. `test/integration/design_tokens_test.rb` ("text on a band is readable in both themes") holds the strong band's three and the tinted band's ink, dim and accents at 4.5:1; no test reads the lines that re-value `--th-meta`. `width: full` breaks the band out to the window's edges and puts its content back on the content column (`margin-inline: calc(50% - 50vw)` with the same amount of padding); `100vw` includes a classic scrollbar's width, so `<body>` carries `overflow-x: clip` (`overflow-x-clip` in `app/views/layouts/application.html.erb`) — on `<body>` the value goes to the viewport, which stays the one scroller, so sticky elements and a code block's own sideways scroll behave as before. Adjacent sections with the same background join without a gap.

**Image `sizes`.** An image block in a column asks for its column's share (`Blocks::SectionComponent.image_sizes`, from the layout's weights): its share of the 736px content column from 768px of viewport, its share of the viewport from 480px, the full width below. It is a hint, so the grid gap and a band's padding are left out. An image *inside rich text* in a column still asks for the content width (a roadmap row).

**Types that are gone.** A block of an unregistered type in a column is skipped with a log line, as at the top level. A section whose own type is gone draws the blocks it holds once each, in reading order, stacked at the content width where the section was, with no band and no grid (`render_block`'s last branch): they are registered blocks, and rendering nothing would take a page's texts and pictures off the site because their wrapper's plugin was removed. Their images ask for the content-width `sizes`.

**Caching and preview** are unchanged: every block write touches the page, a live page's `after_commit` moves the public content version, and `/preview` renders a section as the public page does (`test/integration/preview_test.rb`).
